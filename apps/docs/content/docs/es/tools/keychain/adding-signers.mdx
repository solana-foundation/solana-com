Esta guía está dirigida a proveedores de servicios de billetera y
desarrolladores que desean integrar nuevas soluciones de gestión de claves en la
biblioteca `solana-keychain`. Al añadir tu implementación de firmante,
permitirás a los desarrolladores usar tu servicio para la firma segura de
transacciones de Solana a través de una interfaz unificada.

Keychain mantiene sus implementaciones en Rust, TypeScript, Python y Go en paridad.
Se prefieren encarecidamente los PR que incluyan las cuatro. Si solo puedes aportar
una, no hay problema, pero ten en cuenta que se exigirán las demás antes de que el firmante se incluya
en una versión.

_¿Usas Claude Code? La
[skill `add-signer-ci`](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)
del repositorio configura los flujos de trabajo de CI para un nuevo firmante aportado mediante un PR desde un fork._

## Descripción General de la Arquitectura

La biblioteca utiliza una arquitectura basada en traits definida en `src/traits.rs`. Cada
firmante implementa el trait base `SolanaSigner` (`pubkey`, `sign_message`,
`is_available`) y exactamente un trait de capacidad que se ajuste al modelo del proveedor:

- `TransactionSigner` (`sign_transaction`): el proveedor firma los bytes
  del llamador y este los transmite. La mayoría de los backends.
- `ModifyingSigner` (`modify_and_sign_transaction`): el proveedor reescribe la
  transacción y luego la firma sin transmitirla.
- `SendingSigner` (`sign_and_send_transaction`): el proveedor firma y
  transmite desde el servidor.

La biblioteca también ofrece un enum `Signer` unificado que envuelve todas las
implementaciones y permite seleccionar los backends de firma en tiempo de ejecución. Implementa
solo el trait base; las capacidades se obtienen mediante `as_transaction_signer()`,
`as_modifying_signer()` y `as_sending_signer()`.

## Lista de Verificación Rápida para la Integración

- Crear tu módulo de firmante con la implementación
- Implementa el trait base `SolanaSigner` (`pubkey`, `sign_message`,
  `is_available`) y el trait de capacidad que se ajuste al modelo de tu proveedor
  (normalmente `TransactionSigner`)
- Añade un feature flag en `Cargo.toml`, incluyendo el marcador interno `_remote` si
  tu firmante usa reqwest
- Actualiza el enum `Signer` en `src/lib.rs` (variante, rama de `dispatch_signer!` y
  una rama en el accesor de capacidad que corresponda a tu modelo)
- Aplicar HTTPS y configurar tiempos de espera en clientes HTTP
- Firma los bytes del mensaje y verifica la firma devuelta antes de adjuntarla
- Añade pruebas unitarias exhaustivas (basadas en wiremock, en tu módulo)
- Añade un archivo de pruebas de integración y actualiza `.env.example`
- Añade las implementaciones en TypeScript, Python y Go
- Actualizar documentación
- Actualizaciones del flujo de trabajo de CI (coordínalas con los mantenedores; consulta
  [Actualizaciones del flujo de trabajo de CI](#ci-workflow-updates-fork-prs))
- Enviar PR

Crea un nuevo directorio bajo `src/` para tu implementación:

## Paso 2: Definir tu Struct de Firmante

En `src/your_service/mod.rs`, define tu struct de firmante:

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,
}

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## Paso 3: Implementar el Constructor y Métodos Auxiliares

Los firmantes remotos **deben** aplicar HTTPS y configurar tiempos de espera
HTTP. Usa el struct compartido `HttpClientConfig` para la configuración de
tiempos de espera.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## Paso 4: Implementar los traits del firmante

El trait base `SolanaSigner` tiene 2 métodos asíncronos (`sign_message`,
`is_available`) además de `pubkey()`. La firma de transacciones va en un trait de capacidad;
la mayoría de los proveedores implementan `TransactionSigner`, cuyo `sign_transaction` devuelve
`SignTransactionResult` (un enum etiquetado que indica si la transacción está firmada total o
parcialmente).

Firma los bytes del mensaje, nunca la transacción completa en formato wire, y verifica la
firma del proveedor contra ellos antes de adjuntarla. Usa los helpers compartidos de
`TransactionUtil` para la firma y la serialización.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

Si tu proveedor reescribe la transacción antes de firmarla, implementa
`ModifyingSigner` en su lugar y sustituye por completo la transacción del llamador por
los bytes del proveedor. Si transmite desde el servidor, implementa `SendingSigner`
y deja intacta la transacción del llamador. Nunca implementes una capacidad que tu
proveedor no pueda ofrecer.

## Paso 6: Agregar Feature Flag

Actualiza `Cargo.toml` para añadir tu firmante como feature opcional. Los backends remotos
incluyen el marcador interno `_remote`, que controla la implementación de `From<reqwest::Error>`
en `src/error.rs`; sin él, `?` en las llamadas a reqwest no compilará cuando solo
esté habilitada tu feature.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## Paso 7: Actualizar el Enum de Firmantes

Añade tu firmante a `src/lib.rs`. La implementación base de `SolanaSigner` despacha mediante
la macro `dispatch_signer!`, así que añade una rama ahí. El acceso a las capacidades reside en
los accesores `as_transaction_signer()`, `as_modifying_signer()` y `as_sending_signer()`:
añade una rama `Some(s)` al que corresponda a tu trait de capacidad (y,
para un backend de envío o de modificación, una rama `None` en `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## Paso 8: Agregar Pruebas Exhaustivas

Agrega pruebas a tu módulo (al final de `src/your_service/mod.rs`):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

Cubre también el fallo de verificación de la firma: una respuesta simulada cuya firma
no se verifique debe devolver un error.

## Paso 9: Añadir pruebas de integración

Crea `rust/src/tests/test_<name>_integration.rs`. Las pruebas de integración se ejecutan
contra la API real del servicio (no wiremock) y están condicionadas a la
feature `integration-tests`. Cada archivo necesita:

- Declaraciones `pub const` para los nombres de las variables de entorno
- Un helper `get_signer()` que lee las variables de entorno mediante `dotenvy`
- Tres funciones de prueba: `test_<name>_sign_message`,
  `test_<name>_sign_transaction` y `test_<name>_is_available`
- Feature gates: `#[cfg(feature = "your_service")]` en el módulo y
  `#[cfg(feature = "integration-tests")]` en cada prueba

Consulta `rust/src/tests/test_para_integration.rs` como referencia completa y
declara tu módulo en `rust/src/tests/mod.rs`:

```rust
pub mod test_your_service_integration;
```

## Probar Tu Integración

Usa las recetas de `just` en lugar de `cargo` directamente. Las features del SDK (`sdk-v2`,
`sdk-v3`, `sdk-v4`) son mutuamente excluyentes, por lo que `cargo test --all-features`
falla.

```bash
# Unit tests across the sdk-v2, sdk-v3 and sdk-v4 matrices
just rust-test

# Live integration tests (require credentials in .env)
just rust-test-integration
```

## Actualizaciones del flujo de trabajo de CI (PR desde forks)

La CI es un proceso en dos fases. Coordínate con los mantenedores para preparar `main` antes
de que se pueda probar tu PR: ellos actualizan `fork-external-live-manual.yml`, añaden variables de entorno
a `ci.yml` y configuran los GitHub Secrets.

Tu PR debe incluir estos cambios de la fase 2 junto con el código de tu firmante:

- **`ci.yml`**: añade tu feature de Rust a la matriz `backend` (antes de `all`) y
  tu función de prueba de integración a la matriz `test`
- **`typescript-ci.yml`**: añade tu paquete a las matrices de pruebas unitarias y de integración,
  y añade las variables de entorno al paso de pruebas de integración
- **`typescript-publish.yml`**: añade tu paquete a `PUBLISH_PACKAGES`, al
  array `packages` de la GitHub Release y a la tabla de resumen
- **`python-ci.yml`**: añade el backend al control `CI_SIGNER_*` en
  `resolve-signers` y a la matriz de integración
- **`go-ci.yml`**: añade el backend al control `CI_SIGNER_*` y a
  `moduleBySigner`

## Firmante TypeScript

Si también estás agregando un paquete de firmante TypeScript, créalo en
`typescript/packages/your-signer/`. Patrones clave:

- La función factory `createYourSigner()` devuelve
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>`; mantén la
  clase del firmante como interna y exporta solo la factory y su tipo de configuración
- Exportar interfaz de configuración (`YourSignerConfig`)
- Si tu backend no puede firmar mensajes, omite `SolanaMessageSigner` y no expongas ningún
  método `signMessages`: Kit clasifica los firmantes según la presencia de métodos, por lo que un
  stub que lance una excepción clasificaría mal al firmante
- Exige HTTPS en los campos de configuración `apiBaseUrl` con `assertHttpsUrl()` de
  `@solana/keychain-core`
- Realiza las llamadas remotas mediante `fetchSignerJson()` de `@solana/keychain-core`,
  que se encarga del mapeo de errores, la sanitización de respuestas, el rechazo de redirecciones y el
  tiempo de espera por defecto
- Sanitiza cualquier otro texto de error de la API remota con `sanitizeRemoteErrorResponse()`
  de `@solana/keychain-core`
- Usar `throwSignerError(SignerErrorCode.*, { cause, message })` desde
  `@solana/keychain-core`
- Respeta `config?.abortSignal` en cada método de firma, pasándolo a
  `fetchSignerJson()` y `signBatchStaggered()`
- Valida `requestDelayMs` con `validateRequestDelayMs()` y procesa por lotes con
  `signBatchStaggered()`
- Agregar `@throws` JSDoc a las funciones factory listando códigos de error
- Declara los paquetes `@solana/*` como peer dependencies en `>=8.1.0`
- Pruebas unitarias con vitest y `fetch` simulado; pruebas de integración con
  `runSignerIntegrationTest` de `@solana/keychain-test-utils`

### Firmantes de envío

Si tu proveedor reescribe la transacción o la transmite desde el servidor, su
firma no se puede aplicar a la transacción del llamador, por lo que debe ser un
`SolanaSendingSigner` en lugar de un `SolanaTransactionSigner`:

- Implementa `signAndSendTransactions()` y **no** expongas `signTransactions`
  (ni `signMessages`, a menos que el backend firme mensajes realmente)
- Respeta `config?.abortSignal`. Una vez que el proveedor haya aceptado la creación, notifica
  cualquier fallo (incluida una cancelación) como `BROADCAST_UNCONFIRMED` con el
  id de transacción del proveedor, conservando el motivo de la cancelación como `cause`
- Añade una sobrecarga tipada de `createKeychainSigner` que devuelva el tipo de tu firmante de envío
- Excluye tu backend de `KeychainKitPluginConfig` en
  `typescript/packages/kit-plugin/src/keychain-plugin.ts`, ya que un firmante
  de envío no puede actuar como `payer` o `identity` de un cliente de Kit
- Comprueba en las pruebas unitarias que `isTransactionPartialSigner()` es false y
  `isTransactionSendingSigner()` es true para tus instancias

### Actualizar Paquete Umbrella

Actualiza `typescript/packages/keychain/` (7 archivos que modificar):

1. `src/types.ts`: añade `YourSignerConfig` a la unión discriminada
   `KeychainSignerConfig`
2. `src/create-keychain-signer.ts`: añade el caso del switch (cada paquete de backend se
   carga con un `import()` dinámico)
3. `src/resolve-address.ts`: añade el caso al switch de la ruta rápida o de la ruta con fetch
4. `src/index.ts`: añade las exportaciones del tipo de configuración, el namespace y la función factory
5. `package.json`: añade la dependencia `@solana/keychain-your-signer: "workspace:*"`
6. `tsconfig.json`: añade la referencia `{ "path": "../your-signer" }`
7. `typescript/scripts/test-treeshake-umbrella.mjs`: añade tu paquete a
   `SIGNER_MARKERS` y tu factory a `FACTORIES`

Las sentencias switch tienen comprobaciones exhaustivas con `never`, por lo que TypeScript dará error
si añades a la unión pero olvidas un caso. Ejecuta `just ts-treeshake` después:
todos los paquetes y el paquete umbrella deben seguir siendo compatibles con tree-shaking.

## Firmante de Python

Crea el módulo en `python/src/solana_keychain/your_signer/` (`__init__.py`
más `signer.py`). Patrones clave:

- Crea una subclase de `SolanaSigner` de `solana_keychain.core` (propiedad `pubkey`,
  `async sign_message()`, `async is_available()`) y exactamente una clase de capacidad:
  `TransactionSigner` (`async sign_transaction()`), `ModifyingSigner`
  (`async modify_and_sign_transaction()`) o `SendingSigner`
  (`async sign_and_send_transaction()`)
- Exporta una factory `async create_your_signer()` que haga `await` de `init()` cuando el
  backend resuelva su dirección de forma remota; antes de init, la firma lanza
  `SignerErrorCode.NOT_INITIALIZED`
- Exporta un dataclass de configuración (`YourSignerConfig`) con los secretos marcados
  con `field(repr=False)`
- Exige HTTPS en los campos de URL base con `assert_https_url()` y canaliza cada
  solicitud a través de `fetch_signer_json()`

## Firmante en Go

Cada backend de Go es su propio módulo, ubicado en `go/signers/yoursigner/`, con la ruta de módulo
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`. Consulta
`go/signers/para/` como referencia. Patrones clave:

- Implementa `core.SolanaSigner` (`Pubkey()`, `SignMessage(ctx, message)`,
  `IsAvailable(ctx)`) y exactamente una interfaz de capacidad:
  `core.TransactionSigner`, `core.ModifyingSigner` o `core.SendingSigner`.
  La capacidad se detecta mediante aserción de tipo, por lo que un backend que no pueda firmar una
  transacción no debe tener ningún método `SignTransaction`
- Exporta una estructura `Config` y un constructor `New` (`New(ctx, cfg)` cuando el
  backend resuelve su dirección de forma remota; antes de eso, devuelve
  `core.NewNotInitializedError`)
- Crea clientes HTTP con `core.NewHTTPClient` o `core.ResolveHTTPClient`, y
  valida las URL base con `core.NormalizeHTTPSBaseURL`
- Firma las transacciones con `core.SignTransactionWith`, que firma los bytes del
  mensaje y adjunta la firma; verifica las firmas del proveedor con
  `core.VerifySignature`
- Devuelve los errores con `core.NewSignerError` / `core.WrapSignerError` y códigos
  estables como `core.CodeSigningFailed`
- Pruebas unitarias con `httptest`; pruebas de integración en `integration_test.go` bajo
  la etiqueta `//go:build integration`

## Consejos de Implementación

### Manejo de Errores

Usa siempre las variantes existentes de `SignerError`. Tanto `Display` como `Debug` en
`SignerError` están censurados, así que mantén los mensajes genéricos y nunca incluyas datos
sin procesar de las respuestas de la API. Nunca uses `.expect()` ni `.unwrap()` en respuestas de API no confiables:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### Requisitos de seguridad

Esto no son sugerencias: los consumidores eligen un backend en función de ellos. Si
tu proveedor hace imposible alguno, indícalo en el PR y en el archivo
`docs/SECURITY_MODEL.md` del repositorio.

- **Verifica lo que firmó el proveedor.** Calcula los bytes del mensaje localmente y
  verifica la firma devuelta contra ellos en la posición que requiere tu firmante antes de
  adjuntarla. Una firma que no se verifique debe producir un fallo y nunca
  adjuntarse.
- **Declara si el proveedor difunde la transacción.** Si la ejecuta en el servidor,
  implementa la variante de envío y devuelve la firma que identifica la
  transacción confirmada. Si el proveedor no tiene un endpoint solo de firma, haz que el
  backend sea solo de envío en lugar de enviar a espaldas de quien llama.
- **Nunca dejes a quien llama con una transacción que la firma no cubre.**
  Un proveedor que reescribe la transacción firma sus propios bytes: o bien deja intacta la
  transacción de quien llama (el caso de difusión gestionada), o bien adopta la variante
  modificadora y reemplázala por completo con los bytes del proveedor.
- **Informa de la incertidumbre en la difusión como tal.** Un fallo posterior al envío podría
  haberse confirmado igualmente. Devuelve `BROADCAST_UNCONFIRMED` en lugar de un error genérico,
  incluye el ID de transacción del proveedor siempre que lo tengas y envía una
  clave de idempotencia derivada del mensaje en cada creación, de modo que un reenvío idéntico byte a byte sea
  seguro.
- **Nunca firmes antes de inicializar.** Usa `Option<Pubkey>` (no `Pubkey::default()`) para
  la clave pública antes de `init()`, y falla con un error de configuración si se
  intenta firmar antes.
- Nunca registres en logs datos sensibles (claves privadas, secretos de API, respuestas de API sin procesar) y
  usa una implementación de `Debug` que oculte los campos sensibles
- Exige HTTPS (`https_only(true)`, condicionado con `#[cfg(not(test))]` para
  wiremock) y configura los tiempos de espera de solicitud y de conexión mediante `HttpClientConfig`
  (valores predeterminados: 30 s/5 s)
- Pon a cero el material de claves intermedio con `zeroize::Zeroizing<Vec<u8>>`

### Pruebas con Mocks

Utiliza `wiremock` para simular APIs HTTP. Verifica solo el tipo de error, no el
texto del mensaje de error:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
