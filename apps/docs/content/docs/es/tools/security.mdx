## Gestión de claves

- **Nunca expongas claves privadas en el código del frontend.** Usa firma desde el backend, hardware
  wallets, billeteras multifirma o servicios de gestión de claves.
- **Separa las billeteras calientes y frías.** Billetera caliente para operaciones, fría para
  la tesorería.
- **Haz copias de seguridad de todas las claves de producción.** Almacena copias cifradas en varias ubicaciones
  seguras. Perder una clave significa perder el acceso de forma permanente.
- **Usa claves distintas para devnet y mainnet.** Tus claves de devnet no deberían ser
  tus claves de mainnet. Utiliza una configuración basada en el entorno para asegurarte de que se carguen las claves
  correctas en cada red.

## Infraestructura de firma

Para la firma desde el backend en producción, usa [Keychain](/docs/tools/keychain), una biblioteca de
firma unificada que abstrae múltiples backends de gestión de claves a través de una única
interfaz: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP,
Para, Dfns, Crossmint, Openfort y Utila. Esto te permite desarrollar en local con
claves en memoria y luego cambiar a backends de nivel de producción sin modificar el
código de tu aplicación.

¿No sabes qué backend se ajusta a tus necesidades? Consulta
[Cómo elegir un backend](/docs/tools/keychain/choosing-a-backend). Keychain está
disponible tanto para [Rust](https://crates.io/crates/solana-keychain) como para
[TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Seguridad de RPC

Trata los endpoints RPC como claves de API: no los expongas en el código del frontend, donde
pueden ser extraídos y utilizados de forma abusiva. Usa un proxy en el backend o variables de entorno que
no se incluyan en el código del cliente.

- [QuickNode: mejores prácticas de seguridad para endpoints](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: protege tus claves de API de Solana: mejores prácticas de seguridad](https://www.helius.dev/docs/rpc/protect-your-keys)

## Monitorización

Haz seguimiento de estas métricas en producción:

| Métrica                   | Motivo                    |
| ------------------------ | ---------------------- |
| Tasa de éxito de transacciones | Detectar problemas a tiempo    |
| Latencia de confirmación     | Monitorizar el estado de la red |
| Gasto en tarifas de prioridad       | Control de costes        |
| Tasa de errores de RPC           | Estado del proveedor        |

Configura alertas para:

- Transferencias desde la tesorería que superen un umbral
- Picos en la tasa de transacciones fallidas
- Patrones inusuales de destinatarios
- Aumentos en la tasa de errores de RPC

Para la monitorización de transacciones en tiempo real a gran escala, consulta nuestra
[Guía de indexación](/docs/payments/accept-payments/indexing).

## Verificar direcciones

Cada token y cada programa tiene exactamente una dirección correcta en mainnet. Los tokens
falsificados que imitan a USDC u otras stablecoins son habituales: tendrán el mismo nombre
y símbolo, pero un mint diferente. Tu aplicación debe codificar de forma fija o incluir en una lista de permitidos
las direcciones de mint (según tus requisitos), y nunca aceptarlas dinámicamente
de fuentes no confiables.

**Configuración basada en el entorno:** Devnet y Mainnet suelen usar mints de token completamente
distintos. Configura tu aplicación para que cargue las direcciones correctas
por entorno: no codifiques de forma fija las direcciones de mainnet y te olvides de cambiarlas
durante las pruebas, o peor aún, publiques direcciones de devnet en producción.

Algunos mints comunes de stablecoins son:

| Token | Emisor | Dirección del mint                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Las direcciones de los programas también importan. Enviar instrucciones al programa equivocado
fallará o, peor aún, provocará una pérdida irreversible de fondos. Las direcciones del Token Program
son:

| Programa            | Dirección                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Incluir en la lista de permitidos las direcciones correctas protege contra tokens falsificados, pero
no protege contra el envío a un _tipo_ de cuenta equivocado. La dirección de un destinatario
puede ser una billetera, una token account, un mint o un programa, y cada una requiere
un tratamiento distinto. El SOL nativo enviado a cualquier cosa que no sea una billetera queda fuera del
control del remitente (se pierde por completo si va a un mint o a un programa, y solo lo puede recuperar el
propietario de la cuenta si va a una token account), sin que haya una transacción fallida que avise al usuario.

<Callout type="warn" title="Valida los destinatarios antes de enviar">
  Clasifica cada dirección de destinatario antes de firmar una transferencia. Consulta [Verificar
  dirección](/docs/payments/send-payments/verify-address) para ver el árbol de decisión completo
  y el código de referencia que distingue entre billeteras, token accounts, mints y
  programas.
</Callout>
