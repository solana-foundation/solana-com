## Gestión de claves

- **Nunca expongas claves privadas en el código del frontend.** Usa firma desde el backend, monederos de
  hardware, monederos multifirma o servicios de gestión de claves.
- **Separa los monederos calientes y fríos.** El monedero caliente para operaciones y el frío para
  la tesorería.
- **Haz copias de seguridad de todas las claves de producción.** Guarda copias de seguridad cifradas en varias ubicaciones
  seguras. Perder una clave significa perder el acceso de forma permanente.
- **Usa claves diferentes para devnet y mainnet.** Tus claves de devnet no deberían ser
  tus claves de mainnet. Usa una configuración basada en el entorno para asegurarte de que se carguen las claves
  correctas para cada red.

## Infraestructura de firma

Para la firma en el backend en producción, usa [Keychain](/docs/tools/keychain), una biblioteca de
firma unificada que abstrae varios backends de gestión de claves a través de una única
interfaz: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP,
Para, Dfns, Crossmint, Openfort y Utila. Esto te permite desarrollar en local con
claves en memoria y luego cambiar a backends de nivel de producción sin modificar el
código de la aplicación.

¿No estás seguro de qué backend se adapta mejor? Consulta
[Cómo elegir un backend](/docs/tools/keychain/choosing-a-backend). Keychain está
disponible tanto para [Rust](https://crates.io/crates/solana-keychain) como para
[TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Seguridad de RPC

Trata los endpoints de RPC como claves de API: no los expongas en el código del frontend, donde
pueden extraerse y utilizarse de forma abusiva. Usa un proxy de backend o variables de entorno que
no se incluyan en el código del cliente.

- [QuickNode: mejores prácticas de seguridad de endpoints](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: protege tus claves de API de Solana: mejores prácticas de seguridad](https://www.helius.dev/docs/rpc/protect-your-keys)

## Monitorización

Haz seguimiento de estas métricas en producción:

| Métrica                   | Motivo                    |
| ------------------------ | ---------------------- |
| Tasa de éxito de transacciones | Detectar problemas a tiempo    |
| Latencia de confirmación     | Supervisar el estado de la red |
| Gasto en tarifas de prioridad       | Control de costos        |
| Tasa de errores de RPC           | Estado del proveedor        |

Configura alertas para:

- Transferencias desde la tesorería que superen un umbral
- Picos en la tasa de transacciones fallidas
- Patrones inusuales de destinatarios
- Aumentos en la tasa de errores de RPC

Para la monitorización de transacciones en tiempo real a gran escala, consulta nuestra
[Guía de indexación](/docs/payments/accept-payments/indexing).

## Verificar direcciones

Cada token y programa tiene exactamente una dirección correcta en mainnet. Los tokens
falsificados que imitan a USDC u otras stablecoins son comunes: tendrán el mismo nombre
y símbolo, pero un mint diferente. Tu aplicación debe codificar de forma fija o incluir en una lista de permitidos
las direcciones de mint (según tus requisitos) y nunca aceptarlas dinámicamente
de fuentes no confiables.

**Configuración basada en el entorno:** Devnet y Mainnet suelen usar mints de token completamente
distintos. Configura tu aplicación para que cargue las direcciones correctas
por entorno: no codifiques de forma fija las direcciones de mainnet y olvides cambiarlas
durante las pruebas ni, peor aún, envíes direcciones de devnet a producción.

Algunos mints comunes de stablecoins son:

| Token | Emisor | Dirección de mint                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Las direcciones de los programas también importan. Enviar instrucciones al programa equivocado
fallará o, peor aún, provocará una pérdida irreversible de fondos. Las direcciones del Token Program
son:

| Programa            | Dirección                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Incluir en la lista de permitidos las direcciones correctas protege contra tokens falsificados, pero
no protege contra el envío a un _tipo_ de cuenta equivocado. Una dirección de destinatario
puede ser un monedero, una token account, un mint o un programa, y cada uno requiere
un tratamiento distinto. Los SOL nativos enviados a cualquier cosa que no sea un monedero escapan del
control del remitente: se pierden por completo si van a un mint o a un programa, y solo el propietario de la
cuenta puede recuperarlos si van a una token account, sin que ninguna transacción fallida avise al usuario.

<Callout type="warn" title="Valida a los destinatarios antes de enviar">
  Clasifica cada dirección de destinatario antes de firmar una transferencia. Consulta [Verificar
  direcciones](/docs/payments/send-payments/verify-address) para ver el árbol de
  decisión completo y el código de referencia que distingue monederos, token accounts, mints y
  programas.
</Callout>
