Wersja 2.0 to pierwsze stabilne wydanie pakietu dla Pythona. 
[Przewodnik migracji do wersji 2.0](https://github.com/solana-foundation/solana-keychain/blob/main/docs/MIGRATING_V2.md)
opisuje formy podpisywania, które pakiet współdzieli z Rustem i TypeScriptem.

## Instalacja

Zainstaluj pakiet bazowy oraz po jednym dodatku (extra) dla każdego backendu, który wymaga zależności od dostawcy:

```shell
pip install solana-keychain                # memory, vault and para
pip install 'solana-keychain[aws-kms]'     # AWS KMS (boto3)
pip install 'solana-keychain[gcp-kms]'     # GCP KMS (google-cloud-kms)
pip install 'solana-keychain[privy]'       # Privy
pip install 'solana-keychain[turnkey]'     # Turnkey
pip install 'solana-keychain[fireblocks]'  # Fireblocks
pip install 'solana-keychain[cdp]'         # Coinbase Developer Platform
pip install 'solana-keychain[crossmint]'   # Crossmint
pip install 'solana-keychain[dfns]'        # Dfns
pip install 'solana-keychain[openfort]'    # Openfort
pip install 'solana-keychain[utila]'       # Utila
pip install 'solana-keychain[fordefi]'     # Fordefi

# Several at once
pip install 'solana-keychain[aws-kms,privy]'
```

Wymaga Pythona 3.10 lub nowszego. Transakcje to obiekty
[`solders`](https://pypi.org/project/solders/) `VersionedTransaction`;
akceptowane są wiadomości legacy, v0 i v1, z wyjątkiem Fireblocks z
`use_program_call=True`, który akceptuje wyłącznie legacy i v0.

Memory, Vault i Para można importować z katalogu głównego pakietu. Każdy inny backend
jest importowany z własnego podmodułu (na przykład `solana_keychain.aws_kms`), a
import bez odpowiedniego dodatku zgłasza `ImportError` ze wskazaniem dodatku, który
należy zainstalować. Ledger jest dostępny tylko w Rust.

## Podstawowe użycie

Każdy backend ma dataclass konfiguracji oraz asynchroniczną fabrykę `create_<backend>_signer`,
która zwraca gotowy do użycia signer. Wszystkie metody podpisywania są korutynami:

```python
import asyncio

from solana_keychain import MemorySigner
from solders.transaction import VersionedTransaction


async def sign(transaction: VersionedTransaction) -> str:
    signer = MemorySigner.from_private_key_file("/path/to/id.json")
    print("Signing with:", signer.pubkey)

    # Check availability (useful for remote signers)
    if not await signer.is_available():
        raise RuntimeError("Signer offline")

    result = await signer.sign_transaction(transaction)
    print("Signature:", result.signature)
    print("Fully signed:", result.is_complete)
    return result.encoded_transaction  # base64 wire transaction
```

`sign_transaction` zwraca `SignedTransaction` z polami `encoded_transaction`,
`signature`, `is_complete` i `transaction`. Pole `transaction` jest wiarygodną,
podpisaną transakcją: to od niej należy kontynuować, zwłaszcza w przypadku signera modyfikującego, którego
wynik jest innym obiektem niż ten, który został przekazany.

### Ujednolicona fabryka

`create_keychain_signer` przyjmuje nazwę backendu oraz dataclass konfiguracji tego
backendu i importuje backend leniwie (lazy), więc wystarczy zainstalować tylko te dodatki, z których
korzystasz:

```python
from solana_keychain import create_keychain_signer
from solana_keychain.privy import PrivySignerConfig

signer = await create_keychain_signer(
    "privy",
    PrivySignerConfig(
        app_id="your-app-id",
        app_secret="your-app-secret",
        wallet_id="your-wallet-id",
    ),
)
```

Nazwy są wymienione w `SUPPORTED_BACKENDS`: `aws-kms`, `cdp`, `crossmint`,
`dfns`, `fireblocks`, `fordefi`, `gcp-kms`, `memory`, `openfort`, `para`,
`privy`, `turnkey`, `utila` i `vault`. Nieznana nazwa lub konfiguracja
niewłaściwej klasy zgłasza `SignerError` z kodem `SignerErrorCode.CONFIG_ERROR`. Typ
zwracany przez fabrykę to bazowy `SolanaSigner`, więc przed podpisywaniem zawęź go za pomocą
`isinstance` (zobacz [Możliwości signerów](#signer-capabilities)).

### Zdalni klienci HTTP

Zdalne backendy HTTP akceptują opcjonalny `http_client` (`httpx.AsyncClient`)
do niestandardowego TLS lub proxy. Gdy nie jest ustawiony, każde żądanie używa jednorazowego klienta
z limitem czasu 60 sekund, wymuszonym HTTPS w bazowym adresie URL oraz odrzucanymi
przekierowaniami.

## Możliwości signerów

Każdy backend dziedziczy po abstrakcyjnej klasie bazowej `SolanaSigner` (`pubkey`, `sign_message`,
`is_available`) oraz po dokładnie jednej klasie możliwości:

- `TransactionSigner`: `sign_transaction(tx)` podpisuje transakcję w miejscu
  i zwraca `SignedTransaction`. Transakcję rozgłaszasz samodzielnie.
- `ModifyingSigner`: `modify_and_sign_transaction(tx)` pozwala dostawcy przepisać
  transakcję, a następnie podpisuje ją bez rozgłaszania. Twój obiekt pozostaje
  nienaruszony; kontynuuj od zwróconego `SignedTransaction.transaction`.
- `SendingSigner`: `sign_and_send_transaction(tx)` podpisuje i rozgłasza za pośrednictwem
  dostawcy, a następnie zwraca `Signature` transakcji, która trafiła do sieci. Twoja
  transakcja nigdy nie jest mutowana.

| Backend                                                                           | Klasa możliwości    | `sign_message`                                  |
| --------------------------------------------------------------------------------- | ------------------- | ----------------------------------------------- |
| memory, vault, privy, turnkey, aws-kms, fireblocks, gcp-kms, dfns, para, openfort | `TransactionSigner` | Tak                                             |
| cdp                                                                               | `TransactionSigner` | Tylko ładunki UTF-8, w przeciwnym razie `SERIALIZATION_ERROR` |
| utila                                                                             | `TransactionSigner` | Zgłasza `SIGNING_FAILED`                         |
| fordefi black box (`FordefiBlackBoxSigner`)                                       | `TransactionSigner` | Tak                                             |
| fordefi native manual (`FordefiNativeManualSigner`)                               | `ModifyingSigner`   | Tak                                             |
| fordefi native auto (`FordefiNativeAutoSigner`)                                   | `SendingSigner`     | Tak                                             |
| crossmint                                                                         | `SendingSigner`     | Zgłasza `SIGNING_FAILED`                         |

Zawężaj typ za pomocą `isinstance`. Wszystkie klasy możliwości są eksportowane z katalogu głównego
pakietu:

```python
from solana_keychain import ModifyingSigner, SendingSigner, TransactionSigner

if isinstance(signer, SendingSigner):
    signature = await signer.sign_and_send_transaction(transaction)
elif isinstance(signer, ModifyingSigner):
    result = await signer.modify_and_sign_transaction(transaction)
elif isinstance(signer, TransactionSigner):
    result = await signer.sign_transaction(transaction)
```

### Inicjalizacja

Fabryki `create_*` oraz `create_keychain_signer` wykonują całą wymaganą konfigurację
za Ciebie. Jeśli bezpośrednio tworzysz instancję klasy signera Privy, Fireblocks, Dfns, Crossmint, Para, Openfort lub
Utila, wywołaj `await signer.init()` przed użyciem. Do tego czasu
`pubkey` i każde wywołanie podpisywania zgłaszają `SignerErrorCode.NOT_INITIALIZED`.

## Konfiguracja backendów

### Memory

Utwórz z pliku keypair Solana CLI, ciągu base58 lub `"[1,2,...]"`, surowych
bajtów albo obiektu `Keypair` z `solders`:

```python
from solana_keychain import MemorySigner, MemorySignerConfig, create_memory_signer
from solders.keypair import Keypair

signer = MemorySigner.from_private_key_file("/path/to/id.json")
signer = MemorySigner.from_private_key_string("base58_private_key")
signer = MemorySigner.from_bytes(secret_key_bytes)  # 64 or 32 bytes
signer = await create_memory_signer(MemorySignerConfig(keypair=Keypair()))
```

Klucz znajduje się w pamięci procesu, a Python nie może jej wyzerować. Używaj tego backendu
do programowania i testów.

### HashiCorp Vault

Kluczem musi być klucz ed25519 w silniku transit. Zwykły HTTP jest akceptowany
tylko dla adresu loopback, na potrzeby `vault server -dev`:

```python
from solana_keychain import VaultSignerConfig, create_vault_signer

signer = await create_vault_signer(
    VaultSignerConfig(
        api_base_url="https://vault.example.com:8200",
        token="hvs.xxxxx",
        key_name="my-solana-key",
        public_key="base58_public_key",
    )
)
```

### AWS KMS

`key_id` to identyfikator klucza, ARN lub alias klucza `ECC_NIST_EDWARDS25519`. Przekaż
gotowego klienta boto3 KMS jako `client`, aby użyć niestandardowych poświadczeń lub punktów końcowych; `region`
jest wtedy ignorowany:

```python
from solana_keychain.aws_kms import AwsKmsSignerConfig, create_aws_kms_signer

signer = await create_aws_kms_signer(
    AwsKmsSignerConfig(
        key_id="alias/my-solana-key",
        public_key="base58_public_key",
        region="us-east-1",  # optional, defaults to the AWS config chain
    )
)
```

### Crossmint

```python
from solana_keychain.crossmint import CrossmintSignerConfig, create_crossmint_signer

signer = await create_crossmint_signer(
    CrossmintSignerConfig(
        api_key="api_key",
        wallet_locator="wallet_locator",
    )
)

signature = await signer.sign_and_send_transaction(transaction)
```

Crossmint działa wyłącznie w trybie wysyłania. Jego API zawsze wykonuje zatwierdzoną transakcję
po stronie serwera i pokrywa opłaty gas, więc `CrossmintSigner` jest `SendingSigner`, a
`sign_message` zgłasza `SIGNING_FAILED`. Zwrócony podpis identyfikuje
transakcję, którą Crossmint umieścił w sieci, a ta może różnić się od Twojej. Ustawienie
`signer_secret` (sekretu delegowanego signera `xmsk1_...`) zatwierdza transakcje
automatycznie, co deleguje decyzję o tym, co zostanie zatwierdzone, na Crossmint.

### Fordefi

Fordefi ma trzy tryby podpisywania, ustalane podczas tworzenia przez `chain` oraz
`push_mode`. `create_fordefi_signer` wybiera klasę, każda klasa odrzuca
konfigurację przeznaczoną dla innej, a wszystkie trzy podpisują wiadomości:

| Tryb          | Konfiguracja                                     | Klasa                       | Metoda                        |
| ------------- | ------------------------------------------ | --------------------------- | ----------------------------- |
| Black box     | `chain` nieustawione                              | `FordefiBlackBoxSigner`     | `sign_transaction`            |
| Native auto   | `chain` ustawione, `push_mode` nieustawione lub `"auto"` | `FordefiNativeAutoSigner`   | `sign_and_send_transaction`   |
| Native manual | `chain` ustawione, `push_mode="manual"`          | `FordefiNativeManualSigner` | `modify_and_sign_transaction` |

Żądania API są uwierzytelniane podpisem żądania ECDSA P-256: podaj
klucz jako `private_key_pem` albo przechowuj go w KMS/HSM, przekazując
podklasę `FordefiRequestSigner` jako `request_signer`.

**Tryb Native auto**: ustaw `chain` (`"solana_devnet"` lub `"solana_mainnet"`), a
Fordefi może zastąpić blockhash i opłaty, a następnie sam podpisuje i rozgłasza
transakcję. Akceptuje tylko niepodpisaną transakcję, w której jedynym wymaganym
podpisującym jest skarbiec (vault). `fee` jest przekazywane do Fordefi bez zmian:

```python
import os

from solana_keychain.fordefi import FordefiSignerConfig, create_fordefi_signer

signer = await create_fordefi_signer(
    FordefiSignerConfig(
        access_token=os.environ["FORDEFI_ACCESS_TOKEN"],
        vault_id=os.environ["FORDEFI_VAULT_ID"],
        public_key=os.environ["FORDEFI_PUBLIC_KEY"],  # vault address (base58)
        private_key_pem=open("./secret/private.pem").read(),
        chain="solana_devnet",
        fee={"type": "custom", "priority_fee": "1000"},  # optional
    )
)

signature = await signer.sign_and_send_transaction(transaction)
```

**Tryb Native manual**: ustaw `chain` oraz `push_mode="manual"`. Fordefi przepisuje
wiadomość (najnowszy blockhash, instrukcje opłat Compute Budget) i podpisuje ją,
ale jej nie rozgłasza. Zwrócona transakcja zastępuje tę, którą przesłałeś,
dlatego zawsze kontynuuj od `result.transaction`. Fordefi musi być płatnikiem opłaty (fee payer) i
musi podpisać przed każdym innym wymaganym podpisującym: transakcja, która już zawiera
podpisy, jest akceptowana, ale przepisanie je unieważnia. Przepisanie nie generuje różnicy (diff),
dlatego sprawdź wynik przed rozgłoszeniem i rozgłoś go niezwłocznie, ponieważ Fordefi
nie zwraca wysokości wygaśnięcia nowego blockhasha.

```python
signer = await create_fordefi_signer(
    FordefiSignerConfig(
        access_token=os.environ["FORDEFI_ACCESS_TOKEN"],
        vault_id=os.environ["FORDEFI_VAULT_ID"],
        public_key=os.environ["FORDEFI_PUBLIC_KEY"],
        private_key_pem=open("./secret/private.pem").read(),
        chain="solana_devnet",
        push_mode="manual",
    )
)

result = await signer.modify_and_sign_transaction(transaction)
...  # inspect result.transaction, then add any remaining signatures
```

Rozgłoś sprawdzoną transakcję tak jak w sekcji [Podpisywanie i wysyłanie](#sign-and-send), a
w razie niepowodzenia wysyłki przed ponowną próbą zweryfikuj jej stan.

**Tryb Black box**: pomiń `chain`. Fordefi podpisuje dokładnie te bajty wiadomości, które mu przekażesz, i
nie rozgłasza. Używaj tego z skarbcem Fordefi typu black box.

```python
signer = await create_fordefi_signer(
    FordefiSignerConfig(
        access_token=os.environ["FORDEFI_ACCESS_TOKEN"],
        vault_id=os.environ["FORDEFI_BB_VAULT_ID"],
        public_key=os.environ["FORDEFI_BB_PUBLIC_KEY"],
        private_key_pem=open("./secret/private.pem").read(),
    )
)
```

## Podpisywanie i wysyłanie

`sign_and_send_transaction` umieszcza transakcję w łańcuchu niezależnie od typu
signera. `SendingSigner` rozgłasza ją przez swojego dostawcę, a Twoja funkcja wysyłająca
nigdy nie jest wywoływana. `TransactionSigner` lub `ModifyingSigner` podpisuje, a Twoja funkcja
wysyłająca rozgłasza wynik zakodowany w base64 (pakiet nie zawiera klienta RPC):

```python
import httpx
from solana_keychain import sign_and_send_transaction
from solders.signature import Signature


async def send(encoded: str) -> Signature:
    async with httpx.AsyncClient() as client:
        response = await client.post(
            "https://api.devnet.solana.com",
            json={
                "jsonrpc": "2.0",
                "id": 1,
                "method": "sendTransaction",
                "params": [encoded, {"encoding": "base64"}],
            },
        )
    return Signature.from_string(response.json()["result"])


signature = await sign_and_send_transaction(signer, transaction, send)
```

Signer wyłącznie podpisujący, bez funkcji wysyłającej, zgłasza `CONFIG_ERROR`, a
transakcja, której po podpisaniu nadal brakuje podpisów, zgłasza `SIGNING_FAILED`.

## Obsługa błędów

Każdy błąd to `SignerError` ze stabilnym `code` z `SignerErrorCode`:
`BROADCAST_UNCONFIRMED`, `CONFIG_ERROR`, `EXPECTED_SOLANA_SIGNER`, `HTTP_ERROR`,
`INVALID_PRIVATE_KEY`, `INVALID_PUBLIC_KEY`, `IO_ERROR`, `NOT_AVAILABLE`,
`NOT_INITIALIZED`, `OTHER`, `PARSING_ERROR`, `REMOTE_API_ERROR`,
`SERIALIZATION_ERROR` i `SIGNING_FAILED`. Dopasowuj po `code`, a nie po komunikacie:
`str()` i `repr()` zawierają wyłącznie stały, ogólny komunikat, nigdy materiał kluczowy ani
surowe odpowiedzi dostawców. `status_code` i `provider_error_code` są ustawiane, gdy
błąd pochodził z odpowiedzi dostawcy.

`SignerErrorCode.BROADCAST_UNCONFIRMED` (`"SIGNER_BROADCAST_UNCONFIRMED"`) oznacza, że
transakcja mogła trafić do sieci:

- W Crossmint i Fordefi native auto `provider_transaction_id` jest ustawiane, gdy
  utworzenie zostało zaakceptowane, a `idempotency_key` zawiera klucz wyprowadzony
  z wiadomości, z którym wysłano żądanie utworzenia. Ponowne wysłanie bajt w bajt identycznej
  transakcji jest bezpieczne; przebudowana transakcja (na przykład z nowym blockhashem) to nowy
  transfer.
- W przypadku `sign_and_send_transaction` błąd funkcji wysyłającej zgłasza ten kod
  z ustawionym `transaction_signature` na podpis ukończonej transakcji.
- Fireblocks zgłasza go tylko wtedy, gdy odpytywanie (poll) pokaże, że Fireblocks rozgłosił
  transakcję `use_program_call`, mimo że została wysłana w trybie wyłącznie podpisu.

```python
from solana_keychain import SignerError, SignerErrorCode

try:
    signature = await sign_and_send_transaction(signer, transaction, send)
except SignerError as error:
    if error.code is SignerErrorCode.BROADCAST_UNCONFIRMED:
        reconcile(
            error.provider_transaction_id,
            error.idempotency_key,
            error.transaction_signature,
        )
    raise
```

Anulowane wywołanie ponownie zgłasza `asyncio.CancelledError`, który nie zawiera żadnych pól. Aby
odzyskać identyfikator zaakceptowany przez dostawcę przed anulowaniem, przekaż
`PendingTransactionId()` (z `solana_keychain.core`) jako `pending_transaction_id`
w konfiguracji Crossmint lub Fordefi native auto i odczytaj `.get()` po
anulowaniu. Przed ponowną próbą uzgodnij stan z dostawcą.

Keychain weryfikuje etap podpisywania, a nie to, co robi transakcja: podpis
zwrócony przez dostawcę jest weryfikowany algorytmem ed25519 względem lokalnie obliczonej
wiadomości, zanim zostanie dołączony. Python nie może zerować buforów kluczy, więc w przypadku
backendów z kluczem lokalnym (Memory oraz klucze API i PEM przechowywane w konfiguracjach
zdalnych backendów) traktuj całą pamięć procesu jako wrażliwą. Zobacz
[model bezpieczeństwa](https://github.com/solana-foundation/solana-keychain/blob/main/docs/SECURITY_MODEL.md),
aby dowiedzieć się, co gwarantuje każda forma podpisywania.

## Dodawanie niestandardowych signerów

Utwórz podklasę jedynej klasy możliwości, która odpowiada Twojemu backendowi (`TransactionSigner`,
`ModifyingSigner` lub `SendingSigner`), z modułu `solana_keychain.core`. Zobacz
[przewodnik Adding Signers](/docs/tools/keychain/adding-signers), aby zintegrować
dodatkowe usługi zarządzania kluczami.
