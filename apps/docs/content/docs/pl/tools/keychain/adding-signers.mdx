Niniejszy przewodnik jest przeznaczony dla dostawców usług portfeli i
programistów, którzy chcą zintegrować nowe rozwiązania zarządzania kluczami z
biblioteką `solana-keychain`. Dodając swoją implementację signera, umożliwisz
programistom korzystanie z Twojej usługi do bezpiecznego podpisywania transakcji
Solana poprzez ujednolicony interfejs.

Keychain utrzymuje swoje implementacje w Rust, TypeScript, Python i Go na tym samym poziomie funkcjonalnym.
Zdecydowanie preferowane są PR-y, które zawierają wszystkie cztery. Jeśli możesz dodać
tylko jedną, nie ma problemu, ale pamiętaj, że pozostałe będą wymagane, zanim signer trafi
do wydania.

_Korzystasz z Claude Code? [Skill `add-signer-ci`](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)
z repozytorium
konfiguruje przepływy CI dla nowego signera dodawanego przez PR z forka._

## Przegląd Architektury

Biblioteka wykorzystuje architekturę opartą na traitach, zdefiniowanych w `src/traits.rs`. Każdy
signer implementuje bazowy trait `SolanaSigner` (`pubkey`, `sign_message`,
`is_available`) oraz dokładnie jeden trait możliwości odpowiadający charakterowi danego providera:

- `TransactionSigner` (`sign_transaction`): provider podpisuje bajty przekazane przez
  wywołującego, a wywołujący samodzielnie je rozgłasza. Większość backendów.
- `ModifyingSigner` (`modify_and_sign_transaction`): provider przepisuje
  transakcję, a następnie ją podpisuje, bez rozgłaszania.
- `SendingSigner` (`sign_and_send_transaction`): provider podpisuje i
  rozgłasza transakcję po stronie serwera.

Biblioteka udostępnia również zunifikowany enum `Signer`, który opakowuje wszystkie
implementacje i umożliwia wybór backendu podpisywania w czasie wykonania. Implementuje
tylko trait bazowy; dostęp do możliwości uzyskuje się przez `as_transaction_signer()`,
`as_modifying_signer()` i `as_sending_signer()`.

## Szybka Lista Kontrolna Integracji

- Utwórz moduł swojego signera z implementacją
- Zaimplementuj bazowy trait `SolanaSigner` (`pubkey`, `sign_message`,
  `is_available`) oraz jeden trait możliwości odpowiadający charakterowi Twojego providera
  (zwykle `TransactionSigner`)
- Dodaj feature flag w `Cargo.toml`, w tym wewnętrzny marker `_remote`, jeśli
  Twój signer używa reqwest
- Zaktualizuj enum `Signer` w `src/lib.rs` (wariant, ramię `dispatch_signer!` oraz
  ramię w akcesorze możliwości odpowiadającym Twojemu typowi)
- Wymuś HTTPS i skonfiguruj limity czasu w klientach HTTP
- Podpisz bajty wiadomości i zweryfikuj zwrócony podpis przed jego dołączeniem
- Dodaj kompleksowe testy jednostkowe (oparte na wiremock, w Twoim module)
- Dodaj plik testów integracyjnych i zaktualizuj `.env.example`
- Dodaj implementacje w TypeScript, Python i Go
- Zaktualizuj dokumentację
- Aktualizacje przepływów CI (skoordynuj się z maintainerami, zobacz
  [Aktualizacje przepływów CI](#ci-workflow-updates-fork-prs))
- Wyślij PR

## Krok 2: Zdefiniuj Strukturę Swojego Signera

W `src/your_service/mod.rs` zdefiniuj strukturę swojego signera:

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,
}

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## Krok 3: Zaimplementuj Konstruktor i Metody Pomocnicze

Zdalne signery **muszą** wymuszać HTTPS i konfigurować limity czasu HTTP. Użyj
wspólnej struktury `HttpClientConfig` do ustawień limitów czasu.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## Krok 4: Zaimplementuj traity signera

Bazowy trait `SolanaSigner` ma 2 metody asynchroniczne (`sign_message`,
`is_available`) oraz `pubkey()`. Podpisywanie transakcji znajduje się w traicie możliwości;
większość providerów implementuje `TransactionSigner`, którego `sign_transaction` zwraca
`SignTransactionResult` (oznaczony enum wskazujący, czy transakcja jest w pełni, czy
częściowo podpisana).

Podpisuj bajty wiadomości, nigdy całej transakcji w formacie wire, i zweryfikuj
podpis providera względem tych bajtów, zanim go dołączysz. Użyj współdzielonych
helperów `TransactionUtil` do podpisywania i serializacji.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

Jeśli Twój provider przepisuje transakcję przed podpisaniem, zaimplementuj zamiast tego
`ModifyingSigner` i zastąp transakcję wywołującego w całości
bajtami od providera. Jeśli provider rozgłasza transakcję po stronie serwera, zaimplementuj `SendingSigner`
i pozostaw transakcję wywołującego bez zmian. Nigdy nie implementuj możliwości, której Twój
provider nie obsługuje.

## Krok 6: Dodaj flagę funkcji

Zaktualizuj `Cargo.toml`, aby dodać swój signer jako opcjonalny feature. Backendy zdalne
zawierają wewnętrzny marker `_remote`, który odblokowuje implementację `From<reqwest::Error>`
w `src/error.rs`; bez niego `?` przy wywołaniach reqwest nie skompiluje się, gdy włączony jest tylko
Twój feature.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## Krok 7: Zaktualizuj wyliczenie Signer

Dodaj swój signer do `src/lib.rs`. Bazowa implementacja `SolanaSigner` przekazuje wywołania przez
makro `dispatch_signer!`, więc dodaj tam jedno ramię. Dostęp do możliwości znajduje się w
akcesorach `as_transaction_signer()`, `as_modifying_signer()` i `as_sending_signer()`:
dodaj ramię `Some(s)` do tego, który odpowiada Twojemu traitowi możliwości (a dla backendu
wysyłającego lub modyfikującego także ramię `None` w `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## Krok 8: Dodaj kompleksowe testy

Dodaj testy do swojego modułu (na dole `src/your_service/mod.rs`):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

Uwzględnij również błąd weryfikacji podpisu: zamockowana odpowiedź, której podpis
nie przejdzie weryfikacji, musi zwracać błąd.

## Krok 9: Dodaj testy integracyjne

Utwórz `rust/src/tests/test_<name>_integration.rs`. Testy integracyjne uruchamiane są
na prawdziwym API usługi (nie wiremock) i są ukryte za feature
`integration-tests`. Każdy plik wymaga:

- deklaracji `pub const` dla nazw zmiennych środowiskowych
- Helpera `get_signer()`, który odczytuje zmienne środowiskowe przez `dotenvy`
- Trzech funkcji testowych: `test_<name>_sign_message`,
  `test_<name>_sign_transaction` i `test_<name>_is_available`
- Bramek feature: `#[cfg(feature = "your_service")]` na module oraz
  `#[cfg(feature = "integration-tests")]` na każdym teście

Pełny wzorcowy przykład znajdziesz w `rust/src/tests/test_para_integration.rs`; swój moduł
zadeklaruj w `rust/src/tests/mod.rs`:

```rust
pub mod test_your_service_integration;
```

## Aktualizacje przepływów CI (PR-y z forków)

CI to proces dwufazowy. Skoordynuj się z maintainerami, aby przygotowali `main`, zanim

## Signer TypeScript

Jeśli dodajesz również pakiet signer TypeScript, utwórz go w
`typescript/packages/your-signer/`. Kluczowe wzorce:

- Funkcja fabryczna `createYourSigner()` zwraca
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>`; klasę
  signera zachowaj jako wewnętrzną i eksportuj tylko fabrykę oraz jej typ konfiguracji
- Wyeksportuj interfejs konfiguracji (`YourSignerConfig`)
- Jeśli Twój backend nie potrafi podpisywać wiadomości, pomiń `SolanaMessageSigner` i w ogóle nie udostępniaj
  metody `signMessages`: Kit klasyfikuje signery na podstawie obecności metod, więc
  atrapa rzucająca wyjątek spowodowałaby błędną klasyfikację signera
- Wymuszaj HTTPS w polach konfiguracji `apiBaseUrl` za pomocą `assertHttpsUrl()` z
  `@solana/keychain-core`
- Wykonuj zdalne wywołania przez `fetchSignerJson()` z `@solana/keychain-core`,
  która odpowiada za mapowanie błędów, sanityzację odpowiedzi, odrzucanie przekierowań oraz
  domyślny limit czasu
- Sanityzuj każdy inny tekst błędu zdalnego API za pomocą `sanitizeRemoteErrorResponse()`
  z `@solana/keychain-core`
- Użyj `throwSignerError(SignerErrorCode.*, { cause, message })` z
  `@solana/keychain-core`
- Respektuj `config?.abortSignal` w każdej metodzie podpisywania, przekazując go do
  `fetchSignerJson()` i `signBatchStaggered()`
- Waliduj `requestDelayMs` za pomocą `validateRequestDelayMs()` i przetwarzaj partie przez
  `signBatchStaggered()`
- Dodaj `@throws` JSDoc do funkcji fabrykujących z wykazem kodów błędów
- Zadeklaruj pakiety `@solana/*` jako peer dependencies w wersji `>=8.1.0`
- Testy jednostkowe z vitest i zamockowanym `fetch`; testy integracyjne z
  `runSignerIntegrationTest` z `@solana/keychain-test-utils`

### Signery wysyłające

Jeśli Twój provider przepisuje transakcję lub rozgłasza ją po stronie serwera, jego
podpis nie może zostać zastosowany do transakcji wywołującego, więc musi to być
`SolanaSendingSigner`, a nie `SolanaTransactionSigner`:

- Zaimplementuj `signAndSendTransactions()` i **nie** udostępniaj `signTransactions`
  (ani `signMessages`, chyba że backend faktycznie podpisuje wiadomości)
- Respektuj `config?.abortSignal`. Gdy provider zaakceptuje utworzenie, zgłaszaj
  każdy błąd (w tym przerwanie) jako `BROADCAST_UNCONFIRMED` wraz z identyfikatorem
  transakcji providera, a powód przerwania zachowaj jako `cause`
- Dodaj typowane przeciążenie `createKeychainSigner` zwracające typ Twojego signera wysyłającego
- Wyklucz swój backend z `KeychainKitPluginConfig` w
  `typescript/packages/kit-plugin/src/keychain-plugin.ts`, ponieważ signer wysyłający
  nie może pełnić roli `payer` ani `identity` klienta Kit
- Sprawdź w testach jednostkowych, że `isTransactionPartialSigner()` zwraca false, a
  `isTransactionSendingSigner()` zwraca true dla Twoich instancji

## Signer w Pythonie

Utwórz moduł w `python/src/solana_keychain/your_signer/` (`__init__.py`
oraz `signer.py`). Kluczowe wzorce:

- Dziedzicz po `SolanaSigner` z `solana_keychain.core` (właściwość `pubkey`,
  `async sign_message()`, `async is_available()`) oraz po dokładnie jednej klasie możliwości:
  `TransactionSigner` (`async sign_transaction()`), `ModifyingSigner`
  (`async modify_and_sign_transaction()`) lub `SendingSigner`
  (`async sign_and_send_transaction()`)
- Wyeksportuj fabrykę `async create_your_signer()`, która oczekuje na `init()`, gdy
  backend rozwiązuje swój adres zdalnie; przed inicjalizacją podpisywanie zgłasza
  `SignerErrorCode.NOT_INITIALIZED`
- Wyeksportuj dataclass konfiguracji (`YourSignerConfig`), w którym sekrety są oznaczone
  `field(repr=False)`
- Wymuszaj HTTPS w polach bazowego URL za pomocą `assert_https_url()` i kieruj każde
  żądanie przez `fetch_signer_json()`
- Zweryfikuj podpis providera, zanim go zwrócisz; użyj
  `signed_message_bytes()` dla bajtów objętych podpisem, nigdy własnoręcznie napisanego
  prefiksu wersji
- Zarejestruj backend w `_BACKENDS` w
  `python/src/solana_keychain/keychain.py`
- Jeśli backend wymaga SDK dostawcy, zabezpiecz import warunkowo, zgłoś `ImportError`
  ze wskazaniem `pip install 'solana-keychain[your-signer]'`, zadeklaruj dodatek (extra) w
  `python/pyproject.toml` i nigdy nie importuj backendu zachłannie z głównego modułu
  pakietu
- Testy jednostkowe z pytest: `respx` dla backendów HTTP, klienty zastępcze (stub) dla backendów
  SDK oraz sprawdzenie, że żaden sekret nie pojawia się w `str()` ani `repr()` zgłaszanych
  błędów
- Dodaj fabrykę `make_your_signer()` do
  `python/tests/integration/test_live_signers.py` i zarejestruj ją w
  `_MESSAGE_CAPABLE` (lub w `_TRANSACTION_ONLY` dla backendów bez
  `sign_message`)

## Go Signer

Każdy backend w Go to osobny moduł w `go/signers/yoursigner/` ze ścieżką modułu
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`. Wzorcowy przykład znajdziesz w
`go/signers/para/`. Kluczowe wzorce:

- Zaimplementuj `core.SolanaSigner` (`Pubkey()`, `SignMessage(ctx, message)`,
  `IsAvailable(ctx)`) oraz dokładnie jeden interfejs możliwości:
  `core.TransactionSigner`, `core.ModifyingSigner` lub `core.SendingSigner`.
  Możliwości są wykrywane przez asercję typu, więc backend, który nie może podpisać
  transakcji, nie może w ogóle mieć metody `SignTransaction`
- Wyeksportuj strukturę `Config` i konstruktor `New` (`New(ctx, cfg)`, gdy
  backend zdalnie ustala swój adres; wcześniej zwracaj
  `core.NewNotInitializedError`)
- Twórz klientów HTTP za pomocą `core.NewHTTPClient` lub `core.ResolveHTTPClient` i
  waliduj bazowe adresy URL za pomocą `core.NormalizeHTTPSBaseURL`
- Podpisuj transakcje za pomocą `core.SignTransactionWith`, która podpisuje bajty
  wiadomości i dołącza podpis; weryfikuj podpisy dostawcy za pomocą
  `core.VerifySignature`
- Zwracaj błędy za pomocą `core.NewSignerError` / `core.WrapSignerError` i stabilnych
  kodów, takich jak `core.CodeSigningFailed`
- Testy jednostkowe z `httptest`; testy integracyjne w `integration_test.go` pod
  tagiem `//go:build integration`

## Wskazówki implementacyjne

### Obsługa błędów

Zawsze używaj istniejących wariantów `SignerError`. Zarówno `Display`, jak i `Debug` w
`SignerError` są zredagowane, więc komunikaty powinny być ogólne i nigdy nie mogą zawierać surowych danych
odpowiedzi API. Nigdy nie używaj `.expect()` ani `.unwrap()` na niezaufanych odpowiedziach API:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### Wymagania bezpieczeństwa

To nie są sugestie: użytkownicy wybierają backend na ich podstawie. Jeśli
twój dostawca uniemożliwia spełnienie któregoś z nich, napisz o tym w PR oraz w pliku
`docs/SECURITY_MODEL.md` repozytorium.

- **Weryfikuj to, co podpisał dostawca.** Oblicz bajty wiadomości lokalnie i
  zweryfikuj zwrócony podpis względem nich na pozycji wymaganej przez twój signer, zanim
  go dołączysz. Podpis, który się nie weryfikuje, musi zakończyć się błędem i nigdy nie może zostać
  dołączony.
- **Zadeklaruj, czy dostawca rozgłasza transakcje.** Jeśli wykonuje je po stronie serwera,
  zaimplementuj wariant wysyłający i zwróć podpis identyfikujący
  transakcję, która trafiła do sieci. Jeśli dostawca nie ma endpointu tylko do podpisywania, uczyń
  backend wyłącznie wysyłającym, zamiast wysyłać transakcje za plecami wywołującego.
- **Nigdy nie zostawiaj wywołującego z transakcją, której podpis nie obejmuje.**
  Dostawca, który przepisuje transakcję, podpisuje własne bajty: albo pozostaw
  transakcję wywołującego nietkniętą (przypadek rozgłaszania zarządzanego przez dostawcę), albo użyj
  wariantu modyfikującego i zastąp ją w całości bajtami dostawcy.
- **Zgłaszaj niepewność co do rozgłoszenia jako taką.** Błąd po wysłaniu transakcji mógł
  mimo to zakończyć się jej zatwierdzeniem. Zwracaj `BROADCAST_UNCONFIRMED` zamiast ogólnego
  błędu, przekazuj identyfikator transakcji dostawcy, gdy tylko go masz, i wysyłaj przy każdym utworzeniu
  klucz idempotentności wyprowadzony z wiadomości, aby ponowne wysłanie identycznych bajtów było
  bezpieczne.
- **Nigdy nie podpisuj przed inicjalizacją.** Użyj `Option<Pubkey>` (a nie `Pubkey::default()`) dla
  klucza publicznego przed `init()` i zwróć błąd konfiguracji, jeśli
  podpisywanie zostanie podjęte wcześniej.
- Nigdy nie loguj danych wrażliwych (kluczy prywatnych, sekretów API, surowych odpowiedzi API) i
  używaj implementacji `Debug`, która ukrywa wrażliwe pola
- Wymuszaj HTTPS (`https_only(true)`, z bramką `#[cfg(not(test))]` dla
  wiremock) i skonfiguruj limity czasu żądania i połączenia przez `HttpClientConfig`
  (domyślnie: 30 s/5 s)
- Zeruj pośredni materiał kluczowy za pomocą `zeroize::Zeroizing<Vec<u8>>`

### Testowanie z mockami

Użyj `wiremock` do mockowania API HTTP. Sprawdzaj tylko typ błędu, a nie tekst
komunikatu błędu:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
