## Zarządzanie kluczami

- **Nigdy nie ujawniaj kluczy prywatnych w kodzie frontendu.** Używaj podpisywania po stronie backendu, portfeli sprzętowych, portfeli multisig lub usług zarządzania kluczami.
- **Oddziel portfele hot od cold.** Portfel hot służy do operacji, a cold do przechowywania środków skarbca.
- **Twórz kopie zapasowe wszystkich kluczy produkcyjnych.** Przechowuj zaszyfrowane kopie zapasowe w wielu bezpiecznych lokalizacjach. Utrata klucza oznacza trwałą utratę dostępu.
- **Używaj różnych kluczy dla devnetu i mainnetu.** Klucze devnetu nie powinny być kluczami mainnetu. Użyj konfiguracji opartej na środowisku, aby dla każdej sieci ładowały się właściwe klucze.

## Infrastruktura podpisywania

Do podpisywania po stronie backendu w środowisku produkcyjnym użyj [Keychain](/docs/tools/keychain) — ujednoliconej biblioteki podpisywania, która za pomocą jednego interfejsu abstrahuje wiele backendów zarządzania kluczami: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP, Para, Dfns, Crossmint, Openfort i Utila. Pozwala to tworzyć rozwiązanie lokalnie z kluczami w pamięci, a następnie przejść na backendy klasy produkcyjnej bez zmiany kodu aplikacji.

Nie wiesz, który backend będzie odpowiedni? Zobacz [Wybór backendu](/docs/tools/keychain/choosing-a-backend). Keychain jest dostępny zarówno dla języka [Rust](https://crates.io/crates/solana-keychain), jak i [TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Bezpieczeństwo RPC

Traktuj endpointy RPC jak klucze API — nie ujawniaj ich w kodzie frontendu, gdzie można je wyodrębnić i nadużyć. Użyj proxy backendowego lub zmiennych środowiskowych, które nie są dołączane do kodu klienta.

- [QuickNode: Najlepsze praktyki zabezpieczania endpointów](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Chroń swoje klucze API Solana – najlepsze praktyki bezpieczeństwa](https://www.helius.dev/docs/rpc/protect-your-keys)

## Monitorowanie

Śledź w środowisku produkcyjnym następujące metryki:

| Metryka                   | Dlaczego                    |
| ------------------------ | ---------------------- |
| Wskaźnik powodzenia transakcji | Wczesne wykrywanie problemów    |
| Opóźnienie potwierdzenia     | Monitorowanie kondycji sieci |
| Wydatki na opłaty priorytetowe       | Zarządzanie kosztami        |
| Wskaźnik błędów RPC           | Kondycja dostawcy        |

Skonfiguruj alerty dla:

- Przelewów ze skarbca przekraczających próg
- Nagłych wzrostów odsetka nieudanych transakcji
- Nietypowych wzorców odbiorców
- Wzrostu wskaźnika błędów RPC

Informacje o monitorowaniu transakcji w czasie rzeczywistym na dużą skalę znajdziesz w naszym [Przewodniku po indeksowaniu](/docs/payments/accept-payments/indexing).

## Weryfikacja adresów

Każdy token i program ma w mainnecie dokładnie jeden prawidłowy adres. Sfałszowane tokeny podszywające się pod USDC lub inne stablecoiny są powszechne — mają taką samą nazwę i symbol, ale inny mint. Twoja aplikacja powinna na stałe zakodować lub umieścić na liście dozwolonych adresy mintów (zgodnie z Twoimi wymaganiami) i nigdy nie przyjmować ich dynamicznie z niezaufanych źródeł.

**Konfiguracja oparta na środowisku:** Devnet i Mainnet często używają zupełnie różnych mintów tokenów. Skonfiguruj aplikację tak, aby ładowała właściwe adresy dla każdego środowiska — nie zakodowuj na stałe adresów mainnetu, zapominając o ich podmianie podczas testów, ani, co gorsza, nie wypuszczaj adresów devnetu na produkcję.

Oto niektóre popularne mincy stablecoinów:

| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Adresy programów również mają znaczenie. Wysłanie instrukcji do niewłaściwego programu zakończy się niepowodzeniem — lub, co gorsza, nieodwracalną utratą środków. Adresy Token Program to:

| Program            | Adres                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Umieszczenie właściwych adresów na liście dozwolonych chroni przed sfałszowanymi tokenami, ale nie chroni przed wysłaniem środków na niewłaściwy _rodzaj_ konta. Adres odbiorcy może być portfelem, token account, mintem lub programem, a każdy z nich wymaga innej obsługi. Natywny SOL wysłany na cokolwiek innego niż portfel wymyka się spod kontroli nadawcy — w przypadku mintu lub programu zostaje utracony bezpowrotnie, a w przypadku token account może go odzyskać tylko właściciel konta — a użytkownik nie otrzymuje ostrzeżenia w postaci nieudanej transakcji.

<Callout type="warn" title="Weryfikuj odbiorców przed wysłaniem">
  Przed podpisaniem przelewu sklasyfikuj każdy adres odbiorcy. Zobacz [Weryfikacja adresu](/docs/payments/send-payments/verify-address), gdzie znajdziesz pełne drzewo decyzyjne oraz kod referencyjny rozróżniający portfele, token accounts, mincy i programy.
</Callout>
