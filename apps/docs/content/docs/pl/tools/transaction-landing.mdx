## Infrastruktura RPC

[Publiczne endpointy](https://solana.com/docs/references/clusters#solana-public-rpc-endpoints)
(`api.mainnet.solana.com`) mają limity zapytań i nie oferują SLA. Nadają się do
deweloperki, ale zawiodą w produkcyjnych przepływach płatności — to jak próba obsługi
procesora płatności przez współdzielone API bez gwarancji dostępności.

<Callout type="caution" title="Nigdy nie używaj publicznego RPC w środowisku produkcyjnym">
  Użyj [prywatnego dostawcy RPC](https://solana.com/rpc), aby uzyskać niezawodny dostęp
  z niskimi opóźnieniami.
</Callout>

Wybierając dostawcę RPC, zwróć uwagę na:

- **Niezawodność**: SLA z gwarancją dostępności (99,9%+)
- **Opóźnienia**: bliskość geograficzna do Twoich użytkowników
- **Funkcje**: funkcje landingu transakcji, indeksowanie, API opłat priorytetowych

Pełną listę dostawców RPC znajdziesz w przewodniku
[Dostawcy infrastruktury RPC](https://solana.com/rpc).

### Redundantna konfiguracja RPC

Jak każdy dostawca usług sieciowych, dostawcy RPC mogą mieć przestoje lub
okresy obniżonej wydajności. Aby zapewnić odporność aplikacji, należy
skonfigurować ją tak, by korzystała z wielu dostawców RPC.

[Solana Kit](https://github.com/anza-xyz/kit/tree/main/packages/rpc-transport-http)
oferuje bibliotekę do dostosowywania transportów RPC, która pozwala zbudować
własnego redundantnego klienta RPC. Oto przykład, jak można jej użyć do zbudowania
redundantnego klienta RPC:

```ts
import { RpcTransport } from "@solana/rpc-spec";
import { RpcResponse } from "@solana/rpc-spec-types";
import { createHttpTransport } from "@solana/rpc-transport-http";

// Create a transport for each RPC server
const transports = [
  createHttpTransport({ url: "https://mainnet-beta.my-server-1.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-2.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-3.com" })
];

// Create a wrapper transport that distributes requests to them
let nextTransport = 0;
async function roundRobinTransport<TResponse>(
  ...args: Parameters<RpcTransport>
): Promise<RpcResponse<TResponse>> {
  const transport = transports[nextTransport];
  nextTransport = (nextTransport + 1) % transports.length;
  return await transport(...args);
}
```

Jeśli nie chcesz budować własnych narzędzi do routingu, możesz skorzystać z usługi
zewnętrznej, takiej jak [Iron Forge](https://www.ironforge.sanctum.so/), która zajmie się
routingiem za Ciebie.

## Landing transakcji

W sieci Devnet transakcje trafiają do bloków dość łatwo. W sieci Mainnet konkurujesz o
miejsce w bloku. Aby zwiększyć szansę na to, że Twoja transakcja zostanie
uwzględniona w bloku, upewnij się, że została prawidłowo przygotowana. Oznacza
to:

- dołączenie świeżego blockhasha przed wysłaniem transakcji
- dołączenie do transakcji instrukcji opłaty priorytetowej z konkurencyjną
  opłatą priorytetową
- dołączenie do transakcji instrukcji limitu jednostek obliczeniowych, z limitem
  opartym na szacowanej liczbie jednostek obliczeniowych wymaganych przez transakcję

Dodatkowo warto rozważyć inne narzędzia, takie jak Jito Bundles, aby zwiększyć
szansę na uwzględnienie transakcji w bloku. Przyjrzyjmy się tym narzędziom
bliżej.

### Konfiguracja wysyłania transakcji

Podczas wysyłania transakcji w sieci Mainnet skonfiguruj te parametry, aby uzyskać optymalny
wskaźnik landingu:

**Zarządzanie blockhashem:**

- Pobieraj z poziomem zatwierdzenia `confirmed`
- Zapisz wartość `lastValidBlockHeight` zwróconą przez `getLatestBlockhash` — informuje
  ona, kiedy Twoja transakcja wygaśnie
- Blockhashe wygasają po czasie ustalonym przez protokół, zależnym od długości
  slot.

**Opcje wysyłania:**

- `maxRetries: 0` — wyłącza automatyczne ponawianie prób przez RPC. Obsługuj ponowienia samodzielnie,
  aby w razie potrzeby odświeżyć blockhash.
- `skipPreflight: true` — pomija symulację przed wysłaniem. Używaj tego, gdy
  transakcja została już zwalidowana i zależy Ci na najniższych opóźnieniach. W trakcie
  rozwoju zostaw `false`, aby wcześnie wychwytywać błędy.

```typescript
import { createSolanaRpc } from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);

// 1. Get blockhash with confirmed commitment
const { value: latestBlockhash } = await rpc
  .getLatestBlockhash({ commitment: "confirmed" })
  .send();

// 2. Build and sign your transaction with the blockhash
// ... (transaction building code)

// 3. Send with production settings
const signature = await rpc
  .sendTransaction(encodedTransaction, {
    encoding: "base64",
    maxRetries: 0n, // Handle retries yourself
    skipPreflight: true, // Skip simulation for speed (use false during dev)
    preflightCommitment: "confirmed"
  })
  .send();

// 4. Track expiration using lastValidBlockHeight
const { lastValidBlockHeight } = latestBlockhash;
// Stop retrying when current block height exceeds lastValidBlockHeight
```

### Korzystaj z opłat priorytetowych

Każda transakcja Solana wymaga opłaty transakcyjnej, płatnej w SOL. Opłaty
transakcyjne dzielą się na dwie części: opłatę podstawową i opłatę priorytetową. Opłata podstawowa
wynagradza każdy validator za przetworzenie transakcji. Opłata priorytetowa jest
opcjonalna i zwiększa szansę, że obecny lider przetworzy Twoją
transakcję. Pomyśl o tym jak o ekspresowej wysyłce: płacisz więcej za szybszą,
bardziej niezawodną dostawę.

**Jak działają opłaty:**

```
Total fee = Base fee (5,000 lamports per signature) + Priority fee
Priority fee (legacy/v0) = ceil(compute_unit_price * compute_unit_limit / 1,000,000) lamports
Priority fee (v1 only) = Absolute total in lamports set in the message config
```

**Rzeczywiste koszty:**

- Prosty transfer USDC: ~0,001–0,005 USD w normalnych warunkach
- Podczas zatorów: ~0,01–0,05 USD
- Szczyt zatorów: koszty mogą wzrosnąć jeszcze bardziej

**Przykładowa implementacja:**

Pakiet
[`@solana-program/compute-budget`](https://github.com/solana-program/compute-budget)
dostarcza funkcję pomocniczą, która ułatwia aktualizację lub dołączenie do transakcji instrukcji
ceny jednostki obliczeniowej (w mikro-lamportach).

```typescript
import { updateOrAppendSetComputeUnitPriceInstruction } from "@solana-program/compute-budget";

const tx = pipe(
  createTransactionMessage({ version: 0 }),
  (m) => setTransactionMessageFeePayerSigner(payer, m),
  (m) => setTransactionMessageLifetimeUsingBlockhash(latestBlockhash, m),
  (m) => appendTransactionMessageInstructions([myInstructions], m),
  (m) => updateOrAppendSetComputeUnitPriceInstruction(1000n as MicroLamports, m)
);
```

**Uzyskiwanie szacunków opłat:** większość dostawców RPC oferuje API opłat priorytetowych:

- [Helius Priority Fee API](https://docs.helius.dev/solana-apis/priority-fee-api)
- [QuickNode Priority Fee Add-on](https://marketplace.quicknode.com/add-on/solana-priority-fee)
- [Triton Priority Fees API](https://docs.triton.one/chains/solana/improved-priority-fees-api)

Pełne informacje o mechanizmie opłat znajdziesz w [Opłatach transakcyjnych](/docs/core/fees) oraz w naszym
przewodniku:
[Jak dodać opłaty priorytetowe do transakcji](https://solana.com/developers/cookbook/transactions/add-priority-fees).

### Optymalizuj jednostki obliczeniowe

Moc obliczeniowa w Solana jest mierzona w jednostkach obliczeniowych (CU), które są
przybliżoną miarą pracy wykonywanej przez program. Obecne limity to 50 milionów
CU na blok i 1,4 miliona CU na transakcję. Przesyłając
transakcję, musisz oszacować ilość zużywanej mocy obliczeniowej i
odpowiednio ustawić limit jednostek obliczeniowych — jest to w praktyce żądanie zarezerwowania dla Twojej transakcji
danej części całkowitej przepustowości. W
praktyce oznacza to, że prawidłowe oszacowanie jednostek obliczeniowych wymaganych przez
transakcję ma kluczowe znaczenie dla uwzględnienia jej w bloku (oraz
istotne dla zarządzania opłatami priorytetowymi). Limity obliczeniowe transakcji i bloku
są określane przez protokół.

Solana JSON RPC API udostępnia metodę
[`simulatetransaction`](/docs/rpc/http/simulatetransaction), której można użyć
do oszacowania jednostek obliczeniowych wymaganych przez transakcję, w tym
szacunku jednostek, które zostaną zużyte.
[`@solana/kit`](https://github.com/anza-xyz/kit) zapewnia funkcje pomocnicze, które
oszacowują limity zasobów transakcji i ustawiają je w wiadomości w jednym kroku
(wykorzystując pod spodem metodę `simulatetransaction`). W przypadku transakcji
wersji 1 funkcje te szacują także limit rozmiaru danych wczytywanych kont.

```ts
import {
  estimateResourceLimitsFactory,
  estimateAndSetResourceLimitsFactory
} from "@solana/kit";

const estimateResourceLimits = estimateResourceLimitsFactory({ rpc });
const estimateAndSetResourceLimits = estimateAndSetResourceLimitsFactory(
  estimateResourceLimits
);
const txWithResourceLimits = await estimateAndSetResourceLimits(tx);
```

<Callout type="info">
  Jeśli budujesz i wysyłasz transakcje za pomocą klienta z wtyczką kit, zazwyczaj
  nie potrzebujesz tego kroku — klient dodaje instrukcje budżetu obliczeniowego za Ciebie
  podczas wysyłania (`.sendTransaction()`). Powyższy ręczny przepływ jest przeznaczony dla sytuacji, gdy
  składasz transakcje bezpośrednio za pomocą `@solana/kit`.
</Callout>

W środowisku produkcyjnym, jeśli wielokrotnie wysyłasz ten sam typ transakcji,
warto rozważyć buforowanie oszacowania mocy obliczeniowej dla danego typu transakcji, aby
uniknąć narzutu związanego z szacowaniem jednostek obliczeniowych za każdym razem.

### Jito Bundles

Jito Bundles to narzędzie do zarządzania atomowym wykonaniem wielu transakcji.
Osiąga się to przez wysłanie wielu transakcji do sieci Jito wraz z
napiwkiem. Napiwki mogą zachęcić sieć Jito do uwzględnienia Twoich
transakcji w bloku.

### Strategie ponawiania

Transakcje mogą się nie powieść z wielu powodów. W przeciwieństwie do tradycyjnych API płatności, które
zwracają sukces lub porażkę natychmiast, transakcje blockchain wymagają śledzenia
potwierdzenia.

**Kluczowe pojęcia:**

- **Wygaśnięcie blockhasha**: blockhashe transakcji pozostają
  ważne przez 150 slot (około 30 sekund przy czasie slot wynoszącym 200 ms). Rzeczywisty
  czas wygaśnięcia może się różnić w zależności od tempa produkcji bloków. Użyj
  lastValidBlockHeight, aby ustalić, kiedy blockhash wygasł.
- **Idempotentność**: ta sama podpisana transakcja zawsze daje ten sam
  podpis — ponowne przesłanie jest bezpieczne
- **Wykładniczy backoff**: unikaj przeciążania sieci szybkimi ponowieniami

```typescript
import {
  createSolanaRpc,
  createSolanaRpcSubscriptions,
  sendAndConfirmTransactionFactory,
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED
} from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);
const rpcSubscriptions = createSolanaRpcSubscriptions(process.env.RPC_WSS_URL!);

const sendAndConfirmTransaction = sendAndConfirmTransactionFactory({
  rpc,
  rpcSubscriptions
});

// Send with automatic confirmation tracking and block height monitoring
try {
  await sendAndConfirmTransaction(signedTransaction, {
    commitment: "confirmed",
    // Optional: abort after 75 seconds
    abortSignal: AbortSignal.timeout(75_000)
  });
} catch (e) {
  if (isSolanaError(e, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED)) {
    // Blockhash expired—rebuild transaction with fresh blockhash and retry
    rebuildAndRetryTransaction(); // implement your own logic for rebuilding and retrying the transaction
  }
  throw e;
}
```

Funkcja `sendAndConfirmTransactionFactory` z `@solana/kit` automatycznie obsługuje
cykliczne sprawdzanie potwierdzeń i śledzenie wysokości bloku. Zgłasza błąd
`SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED`, gdy blockhash transakcji wygaśnie,
sygnalizując, że musisz odbudować transakcję ze świeżym blockhashem.

## Obsługa błędów

Solana Kit udostępnia typowane błędy przez `isSolanaError()`. Używaj konkretnych kodów błędów
zamiast dopasowywania ciągów znaków:

```typescript
import {
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED,
  SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE,
  SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND,
  SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS
} from "@solana/kit";

function handlePaymentError(error: unknown): {
  message: string;
  retryable: boolean;
} {
  // Blockhash expired—rebuild and retry
  if (
    isSolanaError(error, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED) ||
    isSolanaError(error, SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND)
  ) {
    return { message: "Transaction expired—rebuilding", retryable: true };
  }

  // Insufficient SOL for fees
  if (
    isSolanaError(
      error,
      SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE
    )
  ) {
    return { message: "Not enough SOL for fees", retryable: false };
  }

  // Insufficient token balance
  if (
    isSolanaError(error, SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS)
  ) {
    return { message: "Insufficient balance", retryable: false };
  }

  // Unknown error
  console.error("Payment error:", error);
  return { message: "Payment failed—please retry", retryable: true };
}
```

**Typowe kody błędów:**

| Kod błędu                   | Przyczyna                 | Rozwiązanie                                                                                                 |
| ---------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------- |
| `BLOCK_HEIGHT_EXCEEDED`      | Blockhash wygasł     | Odbuduj ze świeżym blockhashem                                                                             |
| `BLOCKHASH_NOT_FOUND`        | Nie znaleziono blockhasha   | Odbuduj ze świeżym blockhashem                                                                             |
| `INSUFFICIENT_FUNDS_FOR_FEE` | Za mało SOL        | Zasil konto płacącego opłatę lub użyj [abstrakcji opłat](/docs/payments/send-payments/payment-processing/fee-abstraction) |
| `INSUFFICIENT_FUNDS`         | Za mało tokenów     | Użytkownik potrzebuje większego salda                                                                                  |
| `ACCOUNT_NOT_FOUND`          | Brak token account | Utwórz ATA w transakcji                                                                                |

## Transakcje bez opłat gas

Użytkownicy oczekują płatności w stablecoinach i nie chcą zdobywać SOL na opłaty sieciowe. Transakcje
bez opłat gas rozwiązują ten problem — podobnie jak użytkownicy Venmo nie myślą o opłatach ACH.
Zobacz
[Abstrakcja opłat](/docs/payments/send-payments/payment-processing/fee-abstraction),
aby poznać pełną implementację.
