Это руководство предназначено для поставщиков сервисов кошельков и
разработчиков, которые хотят интегрировать новые решения для управления ключами
в библиотеку `solana-keychain`. Добавив реализацию вашего подписанта, вы
позволите разработчикам использовать ваш сервис для безопасной подписи
транзакций Solana через единый интерфейс.

Keychain поддерживает паритет своих реализаций на Rust, TypeScript, Python и Go.
PR, включающие все четыре реализации, особенно приветствуются. Если вы можете внести
только одну, это тоже нормально, но будьте готовы к тому, что остальные потребуются до выхода signer
в релизе.

_Используете Claude Code? [Навык `add-signer-ci`](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)
из репозитория
настраивает CI-воркфлоу для нового signer, добавленного через PR из форка._

## Обзор архитектуры

Библиотека использует архитектуру на основе трейтов, определённых в `src/traits.rs`. Каждый
signer реализует базовый трейт `SolanaSigner` (`pubkey`, `sign_message`,
`is_available`) плюс ровно один трейт возможностей, соответствующий устройству провайдера:

- `TransactionSigner` (`sign_transaction`): провайдер подписывает байты
  вызывающей стороны, а транзакцию рассылает сама вызывающая сторона. Подходит для большинства бэкендов.
- `ModifyingSigner` (`modify_and_sign_transaction`): провайдер переписывает
  транзакцию, затем подписывает её без рассылки.
- `SendingSigner` (`sign_and_send_transaction`): провайдер подписывает и
  рассылает транзакцию на стороне сервера.

Библиотека также предоставляет единое перечисление `Signer`, которое оборачивает все
реализации и позволяет выбирать бэкенд подписи во время выполнения. Оно реализует
только базовый трейт; доступ к возможностям осуществляется через `as_transaction_signer()`,
`as_modifying_signer()` и `as_sending_signer()`.

## Краткий контрольный список интеграции

- Создайте модуль вашего подписанта с реализацией
- Реализуйте базовый трейт `SolanaSigner` (`pubkey`, `sign_message`,
  `is_available`) плюс один трейт возможностей, соответствующий устройству вашего провайдера
  (обычно `TransactionSigner`)
- Добавьте feature flag в `Cargo.toml`, включая внутренний маркер `_remote`, если
  ваш signer использует reqwest
- Обновите перечисление `Signer` в `src/lib.rs` (вариант, ветку `dispatch_signer!` и
  ветку в аксессоре возможностей, соответствующую вашему типу)
- Обеспечьте HTTPS и настройте таймауты для HTTP-клиентов
- Подпишите байты сообщения и проверьте возвращённую подпись перед тем, как прикрепить её
- Добавьте исчерпывающие модульные тесты (на основе wiremock, в вашем модуле)
- Добавьте файл интеграционных тестов и обновите `.env.example`
- Добавьте реализации на TypeScript, Python и Go
- Обновите документацию
- Обновления CI-воркфлоу (согласуйте с мейнтейнерами, см.
  [Обновления CI-воркфлоу](#ci-workflow-updates-fork-prs))
- Отправьте PR

## Шаг 1: Создайте модуль вашего подписанта

Создайте новую директорию в `src/` для вашей реализации:

```
src/
├── your_service/
│   ├── mod.rs      # Main implementation with SolanaSigner trait
│   └── types.rs    # API request/response types (if needed)
```

## Шаг 2: Определите структуру вашего подписанта

В `src/your_service/mod.rs` определите структуру вашего подписанта:

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,
}

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## Шаг 3: Реализуйте конструктор и вспомогательные методы

Удаленные подписанты **должны** обеспечивать HTTPS и настраивать таймауты HTTP.
Используйте общую структуру `HttpClientConfig` для настройки таймаутов.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## Шаг 4: реализация трейтов Signer

Базовый трейт `SolanaSigner` содержит 2 асинхронных метода (`sign_message`,
`is_available`) плюс `pubkey()`. Подпись транзакций выносится в трейт возможностей;
большинство провайдеров реализуют `TransactionSigner`, чей `sign_transaction` возвращает
`SignTransactionResult` (помеченное перечисление, указывающее, что транзакция подписана полностью или
частично).

Подписывайте байты сообщения, а не всю транзакцию целиком, и проверяйте
подпись провайдера по ним перед тем, как прикрепить её. Используйте общие вспомогательные функции
`TransactionUtil` для подписи и сериализации.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

Если ваш провайдер переписывает транзакцию перед подписью, реализуйте вместо этого
`ModifyingSigner` и полностью замените транзакцию вызывающей стороны на
байты провайдера. Если он рассылает транзакцию на стороне сервера, реализуйте `SendingSigner`
и оставьте транзакцию вызывающей стороны нетронутой. Никогда не реализуйте возможность, которую
ваш провайдер не может обеспечить.

## Шаг 6: Добавьте флаг функции

Обновите `Cargo.toml`, добавив свой signer как опциональную feature. Удалённые бэкенды
включают внутренний маркер `_remote`, который управляет реализацией `From<reqwest::Error>`
в `src/error.rs`; без него `?` при вызовах reqwest не скомпилируется, если включена только
ваша feature.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## Шаг 7: Обновите перечисление Signer

Добавьте свой signer в `src/lib.rs`. Базовая реализация `SolanaSigner` диспетчеризуется через
макрос `dispatch_signer!`, поэтому добавьте туда одну ветку. Доступ к возможностям находится в
аксессорах `as_transaction_signer()`, `as_modifying_signer()` и `as_sending_signer()`:
добавьте ветку `Some(s)` в тот, который соответствует вашему трейту возможностей (а для
бэкенда с отправкой или модификацией — ещё и ветку `None` в `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## Шаг 8: Добавьте комплексные тесты

Добавьте тесты в ваш модуль (в конце `src/your_service/mod.rs`):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

Также покройте случай сбоя проверки подписи: замоканный ответ, подпись в котором
не проходит проверку, должен возвращать ошибку.

## Шаг 9: добавление интеграционных тестов

Создайте `rust/src/tests/test_<name>_integration.rs`. Интеграционные тесты выполняются
с реальным API сервиса (не wiremock) и закрыты feature
`integration-tests`. В каждом файле необходимы:

- объявления `pub const` для имён переменных окружения
- вспомогательная функция `get_signer()`, читающая переменные окружения через `dotenvy`
- три тестовые функции: `test_<name>_sign_message`,
  `test_<name>_sign_transaction` и `test_<name>_is_available`
- feature-гейты: `#[cfg(feature = "your_service")]` на модуле и
  `#[cfg(feature = "integration-tests")]` на каждом тесте

Полный эталонный пример см. в `rust/src/tests/test_para_integration.rs`, а свой модуль
объявите в `rust/src/tests/mod.rs`:

```rust
pub mod test_your_service_integration;
```

## Тестирование вашей интеграции

Используйте рецепты `just`, а не «сырой» `cargo`. Функции SDK (`sdk-v2`,
`sdk-v3`, `sdk-v4`) взаимоисключающие, поэтому `cargo test --all-features`
завершится ошибкой.

```bash
# Unit tests across the sdk-v2, sdk-v3 and sdk-v4 matrices
just rust-test

# Live integration tests (require credentials in .env)
just rust-test-integration
```

## Обновления CI-воркфлоу (PR из форков)

CI — это двухфазный процесс. Согласуйте с мейнтейнерами подготовку `main`, прежде чем
ваш PR можно будет протестировать: они обновляют `fork-external-live-manual.yml`, добавляют переменные окружения
в `ci.yml` и настраивают GitHub Secrets.

Ваш PR должен включать эти изменения второй фазы наряду с кодом вашего signer:

- **`ci.yml`**: добавьте свою Rust feature в матрицу `backend` (перед `all`) и
  свою функцию интеграционного теста в матрицу `test`
- **`typescript-ci.yml`**: добавьте свой пакет в матрицы модульных и интеграционных
  тестов и добавьте переменные окружения в шаг интеграционных тестов
- **`typescript-publish.yml`**: добавьте свой пакет в `PUBLISH_PACKAGES`, в массив
  `packages` GitHub Release и в сводную таблицу
- **`python-ci.yml`**: добавьте бэкенд в гейтинг `CI_SIGNER_*` в
  `resolve-signers` и в матрицу интеграционных тестов
- **`go-ci.yml`**: добавьте бэкенд в гейтинг `CI_SIGNER_*` и в
  `moduleBySigner`

## Подписывающий модуль TypeScript

Если вы также добавляете пакет подписывающего модуля TypeScript, создайте его в
`typescript/packages/your-signer/`. Ключевые паттерны:

- Фабричная функция `createYourSigner()` возвращает
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>`; держите
  класс signer внутренним и экспортируйте только фабрику и тип её конфигурации
- Экспортировать интерфейс конфигурации (`YourSignerConfig`)
- Если ваш бэкенд не может подписывать сообщения, опустите `SolanaMessageSigner` и не добавляйте
  метод `signMessages` вообще: Kit классифицирует signer по наличию методов, поэтому
  заглушка, выбрасывающая ошибку, приведёт к неверной классификации signer
- Принудительно требуйте HTTPS в полях конфигурации `apiBaseUrl` с помощью `assertHttpsUrl()` из
  `@solana/keychain-core`
- Выполняйте удалённые вызовы через `fetchSignerJson()` из `@solana/keychain-core`,
  который отвечает за сопоставление ошибок, очистку ответов, отклонение редиректов и
  таймаут по умолчанию
- Очищайте любой другой текст ошибок удалённого API с помощью `sanitizeRemoteErrorResponse()`
  из `@solana/keychain-core`
- Использовать `throwSignerError(SignerErrorCode.*, { cause, message })` из
  `@solana/keychain-core`
- Учитывайте `config?.abortSignal` в каждом методе подписи, передавая его в
  `fetchSignerJson()` и `signBatchStaggered()`
- Проверяйте `requestDelayMs` с помощью `validateRequestDelayMs()` и выполняйте пакетную обработку через
  `signBatchStaggered()`
- Добавить JSDoc `@throws` к фабричным функциям со списком кодов ошибок
- Объявляйте пакеты `@solana/*` как peer-зависимости версии `>=8.1.0`
- Модульные тесты на vitest с замоканным `fetch`; интеграционные тесты через
  `runSignerIntegrationTest` из `@solana/keychain-test-utils`

### Sending Signers

Если ваш провайдер переписывает транзакцию или рассылает её на стороне сервера, его
подпись нельзя применить к транзакции вызывающей стороны, поэтому это должен быть
`SolanaSendingSigner`, а не `SolanaTransactionSigner`:

- Реализуйте `signAndSendTransactions()` и **не** добавляйте `signTransactions`
  (как и `signMessages`, если только бэкенд действительно не подписывает сообщения)
- Учитывайте `config?.abortSignal`. После того как провайдер принял запрос на создание, сообщайте
  о любом сбое (включая прерывание) как о `BROADCAST_UNCONFIRMED` с идентификатором
  транзакции провайдера, сохраняя причину прерывания в `cause`
- Добавьте типизированную перегрузку `createKeychainSigner`, возвращающую тип вашего sending-signer
- Исключите свой бэкенд из `KeychainKitPluginConfig` в
  `typescript/packages/kit-plugin/src/keychain-plugin.ts`, поскольку sending
  signer не может выступать в роли `payer` или `identity` клиента Kit
- Проверьте в модульных тестах, что для ваших экземпляров `isTransactionPartialSigner()` возвращает false, а
  `isTransactionSendingSigner()` — true

### Обновление основного пакета

Обновите `typescript/packages/keychain/` (нужно изменить 7 файлов):

1. `src/types.ts`: добавьте `YourSignerConfig` в дискриминируемое объединение
   `KeychainSignerConfig`
2. `src/create-keychain-signer.ts`: добавьте ветку switch (каждый пакет бэкенда
   загружается через динамический `import()`)
3. `src/resolve-address.ts`: добавьте в ветку switch быстрого пути или пути с запросом
4. `src/index.ts`: добавьте экспорты типа конфигурации, пространства имён и фабричной функции
5. `package.json`: добавьте зависимость `@solana/keychain-your-signer: "workspace:*"`
6. `tsconfig.json`: добавьте ссылку `{ "path": "../your-signer" }`
7. `typescript/scripts/test-treeshake-umbrella.mjs`: добавьте свой пакет в
   `SIGNER_MARKERS`, а свою фабрику — в `FACTORIES`

Инструкции switch содержат исчерпывающие проверки `never`, поэтому TypeScript выдаст ошибку,
если вы добавите вариант в объединение, но пропустите ветку. После этого запустите `just ts-treeshake`:
каждый пакет и umbrella-пакет должны оставаться пригодными для tree-shaking.

## Python Signer

Создайте модуль в `python/src/solana_keychain/your_signer/` (`__init__.py`
плюс `signer.py`). Ключевые паттерны:

- Унаследуйтесь от `SolanaSigner` из `solana_keychain.core` (свойство `pubkey`,
  `async sign_message()`, `async is_available()`) плюс ровно один класс возможностей:
  `TransactionSigner` (`async sign_transaction()`), `ModifyingSigner`
  (`async modify_and_sign_transaction()`) или `SendingSigner`
  (`async sign_and_send_transaction()`)
- Экспортируйте фабрику `async create_your_signer()`, которая ожидает `init()`, если
  бэкенд определяет свой адрес удалённо; до инициализации подпись вызывает
  `SignerErrorCode.NOT_INITIALIZED`
- Экспортируйте dataclass конфигурации (`YourSignerConfig`), в котором секреты помечены как
  `field(repr=False)`
- Принудительно требуйте HTTPS в полях базового URL с помощью `assert_https_url()` и направляйте каждый
  запрос через `fetch_signer_json()`
- Проверяйте подпись провайдера перед тем, как вернуть её; используйте
  `signed_message_bytes()` для получения байтов, которые покрывает подпись, и никогда не добавляйте
  префикс версии вручную
- Зарегистрируйте бэкенд в `_BACKENDS` в
  `python/src/solana_keychain/keychain.py`
- Если бэкенду нужен SDK провайдера, защитите импорт, вызовите `ImportError`
  с указанием `pip install 'solana-keychain[your-signer]'`, объявите extra в
  `python/pyproject.toml` и никогда не импортируйте бэкенд безусловно из корня
  пакета
- Модульные тесты с pytest: `respx` для HTTP-бэкендов, клиенты-заглушки для
  бэкендов на базе SDK и проверка того, что ни один секрет не попадает в `str()`
  или `repr()` возникающих ошибок
- Добавьте фабрику `make_your_signer()` в
  `python/tests/integration/test_live_signers.py` и зарегистрируйте её в
  `_MESSAGE_CAPABLE` (или в `_TRANSACTION_ONLY` для бэкендов без
  `sign_message`)

## Go Signer

Каждый Go-бэкенд — это отдельный модуль в `go/signers/yoursigner/` с путём модуля
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`. Образец
смотрите в `go/signers/para/`. Основные подходы:

- Реализуйте `core.SolanaSigner` (`Pubkey()`, `SignMessage(ctx, message)`,
  `IsAvailable(ctx)`) и ровно один интерфейс возможностей:
  `core.TransactionSigner`, `core.ModifyingSigner` или `core.SendingSigner`.
  Возможности определяются приведением типа, поэтому бэкенд, который не может
  подписывать транзакцию, не должен содержать метод `SignTransaction` вообще
- Экспортируйте структуру `Config` и конструктор `New` (`New(ctx, cfg)`, если
  бэкенд получает свой адрес удалённо; до этого возвращайте
  `core.NewNotInitializedError`)
- Создавайте HTTP-клиенты через `core.NewHTTPClient` или `core.ResolveHTTPClient`
  и проверяйте базовые URL с помощью `core.NormalizeHTTPSBaseURL`
- Подписывайте транзакции через `core.SignTransactionWith`, который подписывает
  байты сообщения и прикрепляет подпись; проверяйте подписи провайдера с помощью
  `core.VerifySignature`
- Возвращайте ошибки через `core.NewSignerError` / `core.WrapSignerError` со
  стабильными кодами, например `core.CodeSigningFailed`
- Модульные тесты с `httptest`; интеграционные тесты в `integration_test.go` под
  тегом `//go:build integration`

## Рекомендации по реализации

### Обработка ошибок

Всегда используйте существующие варианты `SignerError`. И `Display`, и `Debug`
у `SignerError` скрывают данные, поэтому делайте сообщения общими и никогда не
включайте в них необработанные данные ответа API. Никогда не используйте
`.expect()` или `.unwrap()` для ненадёжных ответов API:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### Требования безопасности

Это не рекомендации: потребители выбирают бэкенд, полагаясь на них. Если
ваш провайдер делает какое-либо из требований невыполнимым, укажите это в PR и в
`docs/SECURITY_MODEL.md` репозитория.

- **Проверяйте то, что подписал провайдер.** Вычислите байты сообщения локально и
  проверьте возвращённую подпись относительно них на позиции, которую требует
  ваш signer, прежде чем прикреплять её. Подпись, не прошедшая проверку, должна
  приводить к ошибке и ни в коем случае не прикрепляться.
- **Укажите, рассылает ли провайдер транзакции.** Если он выполняет их на стороне
  сервера, реализуйте форму отправки и возвращайте подпись, идентифицирующую
  попавшую в сеть транзакцию. Если у провайдера нет эндпоинта только для
  подписи, сделайте бэкенд только отправляющим, а не отправляйте транзакции
  втайне от вызывающей стороны.
- **Никогда не оставляйте вызывающей стороне транзакцию, которую подпись не
  покрывает.** Провайдер, который переписывает транзакцию, подписывает свои
  собственные байты: либо оставьте транзакцию вызывающей стороны нетронутой
  (случай, когда рассылкой управляет провайдер), либо используйте изменяющую
  форму и полностью замените транзакцию байтами провайдера.
- **Сообщайте о неопределённости рассылки как о таковой.** Сбой после отправки
  всё равно мог завершиться попаданием транзакции в сеть. Возвращайте
  `BROADCAST_UNCONFIRMED`, а не общую ошибку, передавайте идентификатор
  транзакции провайдера, если он у вас есть, и отправляйте при каждом создании
  ключ идемпотентности, выведенный из сообщения, чтобы побайтно идентичная
  повторная отправка была безопасной.
- **Никогда не подписывайте до инициализации.** Используйте `Option<Pubkey>` (а не
  `Pubkey::default()`) для открытого ключа до `init()` и завершайте работу с
  ошибкой конфигурации, если подпись запрошена раньше.
- Никогда не логируйте конфиденциальные данные (приватные ключи, секреты API,
  необработанные ответы API) и используйте реализацию `Debug`, скрывающую
  конфиденциальные поля
- Принудительно используйте HTTPS (`https_only(true)`, с условием
  `#[cfg(not(test))]` для wiremock) и настраивайте таймауты запроса и соединения
  через `HttpClientConfig` (по умолчанию: 30 с/5 с)
- Обнуляйте промежуточный ключевой материал с помощью
  `zeroize::Zeroizing<Vec<u8>>`

### Тестирование с использованием моков

Используйте `wiremock` для имитации HTTP API. Проверяйте только тип ошибки, а не
текст сообщения об ошибке:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
