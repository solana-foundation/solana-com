Перед развёртыванием приложения в Mainnet убедитесь, что у вас есть следующее:

- ELF-файл программы — обычно результат выполнения `anchor build` или
  `cargo-build-sbf`, имеющий расширение `.so`
- keypair программы — JSON-файл, содержащий массив целых чисел

В этом разделе мы расскажем, где найти эти ресурсы и как их
подготовить.

## Подготовка ELF-файла

ELF-файл содержит скомпилированный байт-код, информацию о структуре памяти и
метаданные, необходимые виртуальной машине Solana (SVM), чтобы понять, как загрузить
и запустить вашу программу. ELF-файл создаётся при компиляции исходного кода.

Чтобы создать ELF-файл, для Anchor можно выполнить следующую команду:

```bash
anchor build
```

или следующую для других фреймворков:

```bash
cargo build-sbf
```

После этого ELF-файл можно найти в каталоге вида
`target/deploy/<PROGRAM_NAME>.so`.

Ваша программа готова, если ELF-файл скомпилирован под
[sBPFv3](https://www.anza.xyz/blog/migrating-solana-programs-to-sbpfv3). Чтобы
проверить программу, выполните в Linux следующую команду:

```bash
readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

А в macOS — следующие команды:

```bash
# brew install llvm
$(brew --prefix llvm)/bin/llvm-readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

Если вы видите вывод, подобный следующему, программа готова:

```
  Flags:                             0x3
```

Если нет, следуйте руководству по миграции, ссылка на которое приведена
[здесь](https://solana.com/upgrades/sbpfv3-programs).

## Подготовка адреса программы

Адрес программы — это ID программы, который вы будете использовать для вызова инструкций
программы. Вы можете 1) использовать keypair программы, сгенерированный при
сборке, 2) подобрать (grind) новый keypair, адрес которого начинается с заданного префикса, или 3)
получить адрес аккаунта из базового адреса и seed. Первые два варианта
дают keypair, который может подписывать от имени program account. Аккаунт, созданный с
seed, не имеет собственного приватного ключа; им управляет базовый аккаунт.

### Использование сгенерированного keypair

По умолчанию `anchor build` и `cargo build-sbf` размещают keypair программы по следующему пути:

```text
target/deploy/<PROGRAM_NAME>-keypair.json
```

Сделайте резервную копию этого файла перед очисткой каталога сборки. Любой, у кого есть доступ к
keypair, может подписывать от имени program account, поэтому не добавляйте его в систему контроля версий.

### Подбор keypair с произвольным префиксом

Используйте [`vanity`](https://github.com/cavemanloverboy/vanity), чтобы найти
Ed25519 keypair, публичный ключ которого начинается с заданного префикса base58. Установите
CPU-версию из crates.io:

```bash
cargo install vanity
```

Проект также предоставляет сборки CUDA, Metal и OpenCL для поиска с GPU-ускорением.
Требования для каждого бэкенда см. в инструкции по установке `vanity`.

```bash
vanity grind-keypair --pattern Acme...
```

Когда совпадение найдено, `vanity` выводит публичный ключ, приватный seed в hex
и JSON-массив keypair, совместимый с Solana. Сохраните JSON-файл в безопасном
месте, затем убедитесь, что он содержит ожидаемый публичный ключ:

```bash
solana-keygen pubkey path/to/keypair.json
```

Относитесь к выводу команды и сохранённому JSON-файлу как к материалу приватного ключа.

### Создание аккаунта с seed

Для более быстрого поиска `vanity grind` перебирает строки seed для
`CreateAccountWithSeed` вместо генерации keypair Ed25519. Укажите
публичный ключ базового аккаунта, который авторизует создание, владельца аккаунта
и искомый префикс. Для обновляемого program account используйте в качестве владельца
загрузчик BPF с возможностью обновления (upgradeable BPF loader):

```bash
vanity grind \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --pattern Acme...
```

Результат включает производный адрес и строку seed. Проверьте их перед
созданием аккаунта:

```bash
vanity verify \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --seed <SEED>
```

Используйте тот же базовый адрес, seed и владельца, чтобы получить адрес с помощью
`Pubkey::create_with_seed`, затем отправьте инструкцию System Program
`create_account_with_seed`. Транзакцию должны подписать базовый аккаунт и финансирующий аккаунт.
Поскольку производный аккаунт не имеет отдельного
keypair, этот вариант требует процесса создания аккаунта и развёртывания, который использует
базовый аккаунт, а не файл keypair программы.

### Обновление адреса программы в исходном коде

После выбора keypair или аккаунта с seed используйте его публичный адрес в качестве
ID программы везде, где проект его объявляет. Если в исходном коде остался
старый адрес, клиенты могут отправлять инструкции не той программе, а проверки ID
в среде выполнения могут завершаться ошибкой.

В рабочей области Anchor обновите и запись программы в корневом `Anchor.toml`,
и вызов `declare_id!` в `programs/<PROGRAM_NAME>/src/lib.rs`. Ключ
в `[programs.<CLUSTER>]` — это имя программы в рабочей области. Обновите каждую
таблицу кластера, где вы собираетесь использовать новый адрес; в примере ниже обновляется
Mainnet.

В Anchor.toml:

```diff
 [programs.mainnet]
-my_program = "<OLD_PROGRAM_ID>"
+my_program = "<NEW_PROGRAM_ID>"
```

В `programs/<your_program>/lib.rs`:

```diff
-declare_id!("<OLD_PROGRAM_ID>");
+declare_id!("<NEW_PROGRAM_ID>");
```

Pinocchio не использует `Anchor.toml`. Обновите вызов `declare_id!` в
`src/lib.rs` крейта программы. Текущие проекты на Pinocchio импортируют макрос из
`pinocchio::address`.

Quasar также объявляет адрес в `src/lib.rs` крейта ончейн-программы и
не использует `Anchor.toml`. Макрос `declare_id!` доступен через
`quasar_lang::prelude::*`.

После изменения адреса пересоберите программу и заново сгенерируйте IDL и клиентские артефакты.
Также найдите в скриптах развёртывания, тестах и конфигурации приложения
старый ID программы и замените все жёстко заданные ссылки.
