---
title: Ресурсы для деплоя
description: Подготовка сборки программы к деплою в Mainnet
---

Прежде чем деплоить приложение в Mainnet, убедитесь, что у вас есть следующее:

- ELF-файл программы — обычно результат выполнения `anchor build` или
  `cargo-build-sbf`, имеющий расширение `.so`
- keypair программы — JSON-файл, содержащий массив целых чисел

В этом разделе мы расскажем, где найти эти ресурсы и как их
подготовить.

## Подготовка ELF-файла [#preparing-your-elf-file]

ELF-файл содержит скомпилированный байткод, информацию о раскладке памяти и
метаданные, необходимые виртуальной машине Solana (SVM), чтобы понять, как загрузить
и запустить вашу программу. ELF-файл создаётся при компиляции исходного кода.

Чтобы создать ELF-файл, выполните следующую команду для Anchor:

```bash
anchor build
```

или следующую для других фреймворков:

```bash
cargo build-sbf
```

После этого ELF-файл можно найти в каталоге вроде
`target/deploy/<PROGRAM_NAME>.so`.

Ваша программа готова, когда ELF-файл скомпилирован под
[sBPFv3](https://www.anza.xyz/blog/migrating-solana-programs-to-sbpfv3). Чтобы
проверить программу, выполните следующую команду в Linux:

```bash
readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

И следующие команды в macOS:

```bash
# brew install llvm
$(brew --prefix llvm)/bin/llvm-readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

Если вы видите вывод, подобный приведённому ниже, ваша программа готова:

```
  Flags:                             0x3
```

Если нет, следуйте руководству по миграции, ссылка на которое находится
[здесь](https://solana.com/upgrades/sbpfv3-programs).

## Подготовка адреса программы [#preparing-your-program-address]

Адрес программы — это идентификатор программы (program ID), который вы будете использовать для вызова инструкций
программы. Вы можете 1) использовать keypair программы, сгенерированный во время
сборки, 2) подобрать (grind) новый keypair, адрес которого начинается с произвольного префикса, или 3)
вывести адрес аккаунта из базового адреса и seed. Первые два варианта
создают keypair, который может подписывать от имени program account. Аккаунт, созданный с
seed, не имеет собственного приватного ключа; им управляет базовый аккаунт.

### Использование сгенерированного keypair

По умолчанию `anchor build` и `cargo build-sbf` помещают keypair программы по адресу:

```text
target/deploy/<PROGRAM_NAME>-keypair.json
```

Сделайте резервную копию этого файла, прежде чем очищать каталог сборки. Любой, у кого есть доступ к
keypair, может подписывать от имени program account, поэтому не коммитьте его в систему контроля версий.

### Подбор keypair с произвольным префиксом

Используйте [`vanity`](https://github.com/cavemanloverboy/vanity) для поиска
keypair Ed25519, публичный ключ которого начинается с заданного префикса base58. Установите
CPU-версию из crates.io:

```bash
cargo install vanity
```

Проект также предоставляет сборки CUDA, Metal и OpenCL для поиска с GPU-ускорением.
Требования для каждого бэкенда см. в инструкциях по установке `vanity`.

```bash
vanity grind-keypair --pattern Acme...
```

Когда совпадение найдено, `vanity` выводит публичный ключ, закрытый сид в hex-формате
и JSON-массив keypair, совместимый с Solana. Сохраните JSON-файл в безопасном
месте, затем убедитесь, что он содержит ожидаемый публичный ключ:

```bash
solana-keygen pubkey path/to/keypair.json
```

Относитесь к выводу команды и сохранённому JSON-файлу как к материалу закрытого ключа.

### Создание аккаунта с seed

Для более быстрого поиска `vanity grind` перебирает строки seed для
`CreateAccountWithSeed` вместо генерации keypair Ed25519. Укажите
публичный ключ базового аккаунта, который авторизует создание, владельца аккаунта
и префикс для поиска. Для обновляемого program account в качестве владельца укажите
обновляемый загрузчик BPF:

```bash
vanity grind \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --pattern Acme...
```

Результат включает производный адрес и строку seed. Проверьте их перед
созданием аккаунта:

```bash
vanity verify \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --seed <SEED>
```

Используйте тот же базовый адрес, seed и владельца, чтобы получить адрес с помощью
`Pubkey::create_with_seed`, затем отправьте инструкцию System Program
`create_account_with_seed`. Базовый аккаунт и аккаунт-плательщик
должны подписать транзакцию. Поскольку у производного аккаунта нет отдельного
keypair, этот вариант требует процесса создания аккаунта и деплоя, в котором используется
базовый аккаунт, а не файл keypair программы.

### Обновление адреса программы в исходном коде

После выбора keypair или аккаунта с seed используйте его публичный адрес в качестве
program ID везде, где проект его объявляет. Если в исходном коде остаётся
старый адрес, клиенты могут отправлять инструкции не той программе, а проверки
ID в рантайме могут завершаться ошибкой.

В рабочем пространстве Anchor обновите и запись программы в корневом `Anchor.toml`,
и вызов `declare_id!` в `programs/<PROGRAM_NAME>/src/lib.rs`. Ключ
в `[programs.<CLUSTER>]` — это имя программы в рабочем пространстве. Обновите каждую
таблицу кластера, в которой вы намерены использовать новый адрес; в примере ниже обновляется
Mainnet.

В Anchor.toml:

```diff
 [programs.mainnet]
-my_program = "<OLD_PROGRAM_ID>"
+my_program = "<NEW_PROGRAM_ID>"
```

В `programs/<your_program>/lib.rs`:

```diff
-declare_id!("<OLD_PROGRAM_ID>");
+declare_id!("<NEW_PROGRAM_ID>");
```

Pinocchio не использует `Anchor.toml`. Обновите вызов `declare_id!` в
`src/lib.rs` крейта программы. Современные проекты Pinocchio импортируют макрос из
`pinocchio::address`.

Quasar также объявляет адрес в `src/lib.rs` крейта ончейн-программы и
не использует `Anchor.toml`. Макрос `declare_id!` доступен через
`quasar_lang::prelude::*`.

После изменения адреса пересоберите программу и заново сгенерируйте IDL и клиентские артефакты.
Также найдите старый program ID в скриптах деплоя, тестах и конфигурации
приложения и замените все захардкоженные ссылки.
