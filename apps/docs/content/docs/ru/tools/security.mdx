## Управление ключами

- **Никогда не раскрывайте приватные ключи во фронтенд-коде.** Используйте подпись на стороне бэкенда, аппаратные кошельки, мультиподписные кошельки или сервисы управления ключами.
- **Разделяйте горячие и холодные кошельки.** Горячий кошелёк — для операций, холодный — для казны.
- **Делайте резервные копии всех продакшен-ключей.** Храните зашифрованные копии в нескольких защищённых местах. Потеря ключа означает безвозвратную потерю доступа.
- **Используйте разные ключи для devnet и mainnet.** Ключи от devnet не должны совпадать с ключами от mainnet. Применяйте конфигурацию на основе окружения, чтобы для каждой сети загружались правильные ключи.

## Инфраструктура подписи

Для подписи на стороне бэкенда в продакшене используйте [Keychain](/docs/tools/keychain) — унифицированную библиотеку подписи, которая абстрагирует несколько бэкендов управления ключами через единый интерфейс: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP, Para, Dfns, Crossmint, Openfort и Utila. Это позволяет вести локальную разработку с ключами в памяти, а затем переключиться на бэкенды промышленного уровня без изменения кода приложения.

Не уверены, какой бэкенд подойдёт? См. [Выбор бэкенда](/docs/tools/keychain/choosing-a-backend). Keychain доступна для [Rust](https://crates.io/crates/solana-keychain) и [TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Безопасность RPC

Относитесь к RPC-эндпоинтам как к API-ключам: не раскрывайте их во фронтенд-коде, откуда их можно извлечь и использовать во вред. Используйте бэкенд-прокси или переменные окружения, которые не включаются в клиентский код.

- [QuickNode: лучшие практики безопасности эндпоинтов](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: защитите свои API-ключи Solana — лучшие практики безопасности](https://www.helius.dev/docs/rpc/protect-your-keys)

## Мониторинг

Отслеживайте в продакшене следующие метрики:

| Метрика                   | Зачем                    |
| ------------------------ | ---------------------- |
| Доля успешных транзакций | Раннее выявление проблем    |
| Задержка подтверждения     | Контроль состояния сети |
| Расходы на приоритетные комиссии       | Управление затратами        |
| Доля ошибок RPC           | Состояние провайдера        |

Настройте оповещения о:

- переводах из казны, превышающих пороговое значение
- резком росте доли неудачных транзакций
- необычных шаблонах получателей
- росте доли ошибок RPC

О мониторинге транзакций в реальном времени в больших масштабах читайте в нашем [руководстве по индексированию](/docs/payments/accept-payments/indexing).

## Проверка адресов

У каждого токена и каждой программы в mainnet есть ровно один корректный адрес. Поддельные токены, имитирующие USDC или другие стейблкоины, — обычное явление: у них то же название и символ, но другой mint. Ваше приложение должно жёстко задавать адреса mint или использовать список разрешённых (в зависимости от ваших требований) и никогда не принимать их динамически из недоверенных источников.

**Конфигурация на основе окружения:** в Devnet и Mainnet часто используются совершенно разные mint токенов. Настройте конфигурацию приложения так, чтобы для каждого окружения загружались правильные адреса: не прописывайте адреса mainnet жёстко и не забывайте заменять их при тестировании — а ещё хуже, не выпускайте адреса devnet в продакшен.

Некоторые распространённые mint стейблкоинов:

| Токен | Эмитент | Mint-адрес                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Адреса программ тоже важны. Отправка инструкций не той программе приведёт к ошибке — или, что хуже, к безвозвратной потере средств. Адреса Token Program:

| Программа            | Адрес                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Список разрешённых адресов защищает от поддельных токенов, но не защищает от отправки на аккаунт неправильного _типа_. Адрес получателя может принадлежать кошельку, token account, mint или программе, и каждый случай требует особой обработки. Нативный SOL, отправленный на любой адрес, кроме кошелька, выходит из-под контроля отправителя: для mint или программы он теряется безвозвратно, а для token account его может вернуть только владелец аккаунта — при этом транзакция не завершается ошибкой, и пользователь не получает никакого предупреждения.

<Callout type="warn" title="Проверяйте получателей перед отправкой">
  Классифицируйте каждый адрес получателя перед подписанием перевода. Полное дерево решений и пример кода, который различает кошельки, token account, mint и программы, см. в разделе [Проверка адреса](/docs/payments/send-payments/verify-address).
</Callout>
