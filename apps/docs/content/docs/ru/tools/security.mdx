## Управление ключами

- **Никогда не раскрывайте приватные ключи во фронтенд-коде.** Используйте подпись на бэкенде, аппаратные кошельки, мультиподписные кошельки или сервисы управления ключами.
- **Разделяйте горячие и холодные кошельки.** Горячий кошелёк — для операций, холодный — для казначейства.
- **Делайте резервные копии всех продакшен-ключей.** Храните зашифрованные копии в нескольких защищённых местах. Потеря ключа означает безвозвратную потерю доступа.
- **Используйте разные ключи для devnet и mainnet.** Ключи от devnet не должны совпадать с ключами от mainnet. Используйте конфигурацию на основе окружения, чтобы для каждой сети загружались правильные ключи.

## Инфраструктура подписи

Для подписи на продакшен-бэкенде используйте [Keychain](/docs/tools/keychain) — универсальную библиотеку подписи, которая абстрагирует несколько бэкендов управления ключами через единый интерфейс: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP, Para, Dfns, Crossmint, Openfort и Utila. Это позволяет разрабатывать локально с ключами в памяти, а затем переходить на бэкенды промышленного уровня без изменения кода приложения.

Не уверены, какой бэкенд вам подходит? См. [Выбор бэкенда](/docs/tools/keychain/choosing-a-backend). Keychain доступен для [Rust](https://crates.io/crates/solana-keychain) и [TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Безопасность RPC

Относитесь к RPC-эндпоинтам как к API-ключам: не размещайте их во фронтенд-коде, где их можно извлечь и использовать во вред. Применяйте бэкенд-прокси или переменные окружения, которые не включаются в клиентский код.

- [QuickNode: лучшие практики безопасности эндпоинтов](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: защита API-ключей Solana — лучшие практики безопасности](https://www.helius.dev/docs/rpc/protect-your-keys)

## Мониторинг

Отслеживайте в продакшене следующие метрики:

| Метрика                   | Зачем                    |
| ------------------------ | ---------------------- |
| Доля успешных транзакций | Раннее выявление проблем    |
| Задержка подтверждения     | Контроль состояния сети |
| Расходы на приоритетные комиссии       | Управление затратами        |
| Доля ошибок RPC           | Состояние провайдера        |

Настройте оповещения о:

- переводах из казначейства выше порогового значения
- резком росте доли неудачных транзакций
- необычных шаблонах получателей
- росте доли ошибок RPC

Для мониторинга транзакций в реальном времени в больших масштабах см. наше [руководство по индексации](/docs/payments/accept-payments/indexing).

## Проверяйте адреса

У каждого токена и программы в mainnet есть ровно один правильный адрес. Поддельные токены, имитирующие USDC или другие стейблкоины, встречаются часто: у них то же название и символ, но другой mint. Ваше приложение должно жёстко задавать адреса mint в коде или использовать список разрешённых (в зависимости от ваших требований) и никогда не принимать их динамически из недоверенных источников.

**Конфигурация на основе окружения:** в Devnet и Mainnet часто используются совершенно разные mint токенов. Настройте конфигурацию приложения так, чтобы для каждого окружения загружались правильные адреса: не прописывайте адреса mainnet в коде, забыв заменить их при тестировании, и тем более не выкатывайте адреса devnet в продакшен.

Некоторые распространённые mint стейблкоинов:

| Токен | Эмитент | Адрес mint                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Адреса программ тоже важны. Отправка инструкций не той программе приведёт к ошибке или, что хуже, к необратимой потере средств. Адреса Token Program:

| Программа            | Адрес                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Список разрешённых адресов защищает от поддельных токенов, но не защищает от отправки на аккаунт не того _типа_. Адрес получателя может принадлежать кошельку, token account, mint или программе, и каждый случай требует своей обработки. Нативные SOL, отправленные на любой адрес, кроме кошелька, выходят из-под контроля отправителя: в случае mint или программы они теряются безвозвратно, а в случае token account их может вернуть только владелец аккаунта. При этом нет неудачной транзакции, которая предупредила бы пользователя.

<Callout type="warn" title="Проверяйте получателей перед отправкой">
  Определяйте тип каждого адреса получателя перед подписанием перевода. Полное дерево решений и пример кода, различающий кошельки, token account, mint и программы, см. в разделе [Проверка адреса](/docs/payments/send-payments/verify-address).
</Callout>
