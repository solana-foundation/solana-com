Kora — это рабочее пространство Rust с тремя крейтами:

- `kora-lib` содержит основную логику и RPC-сервер,
- `kora-cli` собирает бинарный файл `kora`, который запускают операторы, а
- `kora-deploy` — специализированный инструмент для развёртывания программ, версионируется отдельно.
  Всё описанное ниже находится в `crates/lib/src`, если не указано иное.

## Где находится каждый этап

| Этап на диаграмме | Исходный файл                               | Точка входа                           |
| -------------------- | ------------------------------------ | ------------------------------------- |
| Шлюз              | `rpc_server/server.rs`               | `run_rpc_server`                      |
| Диспетчеризация             | `rpc_server/rpc.rs`                  | `KoraRpc`                             |
| Логика отдельных методов     | `rpc_server/method/`                 | по одному файлу на каждый метод JSON-RPC          |
| Валидация           | `validator/transaction_validator.rs` | `TransactionValidator`                |
| Плагины              | `plugin/mod.rs`                      | `TransactionPluginRunner`             |
| Подписание              | `signer/`                            | на основе крейта `solana-keychain` |

Стоит знать ещё два файла: `config.rs` определяет всю схему `kora.toml`, а
`state.rs` хранит десериализованную конфигурацию в глобальном состоянии процесса.

### Изучаем RPC-сервер

`rpc.rs` — это тонкий слой диспетчеризации: один метод на каждую конечную точку JSON-RPC и
самый быстрый способ увидеть весь API. Логика каждого метода находится в отдельном файле в
`rpc_server/method/`. Прочитайте `sign_transaction.rs` целиком; остальные методы подписания
являются его вариациями.

### Изучаем валидатор

`transaction_validator.rs` и `transaction/instruction_util.rs` содержат логику
валидации транзакций и инструкций. Кроме того, здесь находятся тесты свойств безопасности
fee-payer-policy, которые размещены по одному файлу на каждую защищаемую программу в
`validator/transaction_validator/fee_payer_policy_props/`.

## Полезные соглашения

**Валидация по умолчанию.** Каждый флаг в `[validation.fee_payer_policy]`
по умолчанию равен `false`, а структуры политики имеют атрибут `#[serde(default)]`. Это
сочетание сделано намеренно: добавление новой защищаемой инструкции не должно ломать
конфигурацию существующего оператора, а результатом должен быть отказ, а не
случайное разрешение. Сохраняйте оба условия при добавлении флага.

**Валидируйте разрешённую транзакцию, а не исходную.** Исходная
`VersionedTransaction` содержит только статические ключи аккаунтов, поэтому при валидации или
оценке стоимости транзакции V0 по ней аккаунты из lookup-таблиц молча пропускаются, и
комиссия занижается. `VersionedTransactionResolved::from_transaction` заранее разрешает эти
адреса, поэтому все последующие этапы принимают разрешённый тип.

## Добавление плагина транзакций

Плагины реализуют трейт `TransactionPlugin` в `plugin/mod.rs`. У него два
метода: `validate` выполняется для каждой транзакции в процессе подписания, а
`validate_config` выполняется один раз при запуске и возвращает оператору ошибки и
предупреждения. `PluginExecutionContext` сообщает плагину, какой из четырёх методов
подписания его вызвал.

`TransactionPluginRunner::from_config` выполняет сопоставление по `TransactionPluginType`,
определённому в `config.rs`. Новый встроенный плагин — это новый вариант там плюс новая
ветка match в раннере. Сейчас поставляются два плагина: `gas_swap` и
`deploy_authority`.

## Тестирование

Kora хранит конфигурацию в глобальном состоянии процесса, поэтому в `tests/` объявлена
одна цель `[[test]]` на каждую фазу, и каждая цель поднимает собственный встроенный surfnet и
узел Kora, инициализируемые с нуля. Одна конфигурация на бинарный файл: для новой фазы нужна новая
цель, а не новый модуль в существующей.

```bash
cargo test -p tests --test <target>
```

Всё остальное настроено через `justfile`. Читайте его, а не
восстанавливайте команды вручную.
