Транзакция выполняется, только если она содержит действительную
[подпись](/docs/core/transactions/transaction-structure#signatures) каждого
обязательного подписанта. При локальной разработке этот ключ обычно хранится в виде
[`Keypair`](/developers/cookbook/wallets/create-keypair), и вы подписываете напрямую. В
продакшене важен другой вопрос: **где хранится закрытый ключ
и кто вправе разрешать подписание с его помощью?**

<Callout type="warn">
  Никогда не встраивайте закрытые ключи в клиентский код, не включайте их в сборку фронтенда и не
  коммитьте в систему контроля версий. Любой, кто получит ключ, получит полный контроль над средствами
  этого аккаунта.
</Callout>

## Подходы к подписанию

| Подход                  | Где хранится ключ                                     | Кто подписывает                                          | Лучше всего подходит для                                                      |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **Локальный keypair**         | Файл или переменная окружения на машине           | Ваш код напрямую                                | Локальной разработки, тестов, CI                                  |
| **Браузерный кошелёк**        | Кошелёк конечного пользователя (например, Phantom, Solflare)          | Конечный пользователь, для каждой транзакции                      | Фронтенд-dApp, где пользователи сами подписывают свои транзакции        |
| **Облачный KMS / HSM**       | Сервис хранения ключей с аппаратной защитой (AWS KMS, GCP KMS, Vault) | Ваш бэкенд запрашивает подпись у сервиса | Бэкенд-сервисов, операций с казначейством, регулируемых сред |
| **Управляемые / MPC-кошельки** | Разделён или хранится на инфраструктуре провайдера   | Провайдер сопровождает подписание в соответствии с вашей политикой     | Встроенных кошельков, процессов согласования, институционального хранения   |

Локальный keypair — единственный подход, при котором необработанный ключевой материал находится внутри вашего
приложения. Во всех production-подходах ключ хранится на выделенной инфраструктуре,
и именно она подписывает от вашего имени.

## Подписание на бэкенде

Когда серверу нужно подписывать (оплачивать комиссии, отправлять транзакции программ или
управлять казначейством), используйте специализированный бэкенд для управления ключами, а не «сырой»
keypair. Solana Foundation поддерживает [Keychain](/docs/tools/keychain) —
единую библиотеку подписания (Rust, TypeScript, Python и Go), которая предоставляет один интерфейс
`SolanaSigner` для всех бэкендов из таблицы выше: Memory,
HashiCorp Vault, AWS KMS, GCP KMS, Fireblocks, Privy, Turnkey, CDP, Crossmint,
Dfns, Para, Openfort, Utila и Fordefi.

Поскольку интерфейс общий для всех бэкендов, вы можете разрабатывать локально с ключом
в памяти и переключаться на production-бэкенд через конфигурацию, не
переписывая код приложения (бэкенды, которые сами рассылают транзакции, например Crossmint,
вызываются через путь «подписать и отправить»). Keychain совместим с
[`@solana/kit`](/docs/clients/official/javascript),
[Rust SDK](/docs/clients/official/rust), `solders` (Python) и `solana-go` v2
(Go).
