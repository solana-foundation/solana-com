Пополнение — это обычный `TransferChecked` в эскроу плеча, поэтому любой кошелёк
или система кастодиального хранения, способные отправить перевод токенов, могут
пополнить плечо. Клиент DvP нужен только для чтения записи сделки перед
пополнением. Программа проверяет балансы эскроу только при расчёте; ничто не
проверяет перевод в момент его поступления, поэтому каждая сторона читает запись
сделки до перевода.

Эта страница продолжает раздел
[создание сделки](/docs/defi/dvp-program/create-a-trade); клиент и подписанты
остаются теми же.

## Проверьте условия

Создание записи не требует разрешений, а адреса эскроу выводятся только из
записи и минта, но не из условий. Поэтому перевод в эскроу может попасть под
условия, с которыми вы не соглашались, включая адреса расчёта, которые
перенаправляют средства вашего контрагента на третий адрес. Перед пополнением
прочитайте аккаунт `SwapDvp` и сверьте его с согласованной сделкой.

`verifySwapDvp` в TypeScript и `verify::decode_swap_dvp_account` в Rust
подтверждают, что аккаунт принадлежит программе DvP, имеет размер ровно 458 байт
и находится по адресу, который выводится из его собственных полей
(`fetchSwapDvpChecked` выполняет только первые две проверки). Обычные функции
чтения `fetchSwapDvp` и `decodeSwapDvp` не выполняют ни одной из этих проверок.
Проверки сторон, сумм, сроков и адресов назначения вызывающая сторона выполняет
самостоятельно, сверяя их с согласованной сделкой.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { unwrapOption } from "@solana/kit";
    import { verifySwapDvp } from "./dvp";

    const trade = await verifySwapDvp(client.rpc, swapDvp);
    const t = trade.data;

    const expectedAmountA = 1_000_000_000n;
    const expectedAmountB = 998_500_000n;
    const expectedEarliestSettlement: bigint | null = null; // as agreed
    const expectedExpiry = 1_798_761_600n; // as agreed, unix seconds

    if (
      t.userA !== userA ||
      t.userB !== userB ||
      t.mintA !== mintA ||
      t.mintB !== mintB ||
      t.settlementAuthority !== settlementAuthority ||
      t.tokenProgramA !== tokenProgramA ||
      t.tokenProgramB !== tokenProgramB ||
      t.amountA !== expectedAmountA ||
      t.amountB !== expectedAmountB ||
      unwrapOption(t.earliestSettlementTimestamp) !== expectedEarliestSettlement ||
      t.expiryTimestamp !== expectedExpiry ||
      t.userASettlementDestination !== userA ||
      t.userBSettlementDestination !== userB
    ) {
      throw new Error("Stored terms do not match the agreed trade; do not fund");
    }

    if (t.expiryTimestamp <= BigInt(Math.floor(Date.now() / 1000)) + 60n) {
      throw new Error("Trade expires too soon to fund safely");
    }
    ```

  </Tab>

  <Tab value="Rust">
    ```rust
    use dvp_swap_program_client::verify::decode_swap_dvp_account;
    use solana_client::rpc_client::RpcClient;
    use solana_commitment_config::CommitmentConfig;

        CommitmentConfig::confirmed(),
    );

    let trade = decode_swap_dvp_account(&swap_dvp, &account)?;

    let expected_amount_a: u64 = 1_000_000_000;
    let expected_amount_b: u64 = 998_500_000;
    let expected_earliest_settlement: Option<i64> = None; // as agreed
    let expected_expiry: i64 = 1_798_761_600; // as agreed, unix seconds

    if trade.user_a != user_a
        || trade.user_b != user_b
        || trade.mint_a != mint_a
        || trade.mint_b != mint_b
        || trade.settlement_authority != settlement_authority
        || trade.token_program_a != token_program_a
        || trade.token_program_b != token_program_b
        || trade.amount_a != expected_amount_a
        || trade.amount_b != expected_amount_b
        || trade.earliest_settlement_timestamp != expected_earliest_settlement
        || trade.expiry_timestamp != expected_expiry
        || trade.user_a_settlement_destination != user_a
        || trade.user_b_settlement_destination != user_b
    {
        return Err("stored terms do not match the agreed trade; do not fund".into());
    }

    let now_seconds: i64 = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)?
        .as_secs() as i64;
    if trade.expiry_timestamp <= now_seconds + 60 {
        return Err("trade expires too soon to fund safely".into());
    }
    ```

  </Tab>

Если запись создал ваш контрагент или расчётный орган, сравните каждое поле с
условиями, которые вы согласовали вне блокчейна. Если вы создали её сами, это
чтение подтвердит, что запись попала в сеть в том виде, в каком была отправлена.

## Перевод в эскроу

Пополняйте плечо ровно на согласованную сумму. Программа ограничивает расчёт
значением `amount_x` и возвращает любой излишек стороне плеча, поэтому излишек
не теряется, но он добавляет второй перевод при расчёте и может вызвать сбой
из-за некоторых transfer hooks (см. примечания ниже).

Используйте `TransferChecked`, а не непроверяемый `Transfer`. Токены Token-2022
с расширениями, которые зависят от mint account, например Pausable, отклоняют
перевод, в котором он не указан, а минт с transfer hook требует, чтобы аккаунты
hook были определены и добавлены так же, как и при любом другом переводе этого
токена.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    Сторона актива, подписывающая как `userASigner`, пополняет эскроу A:

    ```ts
    import {
      findAssociatedTokenPda,
      getTransferCheckedInstruction,
    } from "@solana-program/token-2022";

    const [userAAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: userA,
      tokenProgram: tokenProgramA,
    });
    const [userBAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: userB,
      tokenProgram: tokenProgramB,
    });

    const fundAssetLeg = getTransferCheckedInstruction({
      source: userAAtaA,
      mint: mintA,
      destination: escrowA,
      authority: userASigner,
      amount: t.amountA,
      decimals: 6,
    }, { programAddress: tokenProgramA });

    await client.sendTransaction([fundAssetLeg]);
    ```

    Сторона денежного плеча делает то же для эскроу B с `userBAtaB`, `mintB`,
    `userBSigner`, `t.amountB` и `{ programAddress: tokenProgramB }`.

  </Tab>

    `user_b` и `trade.amount_b`.

Пополнение, замеченное на уровне [`confirmed`](/docs/rpc#configuring-state-commitment),
всё ещё может быть вытеснено. Программа читает баланс эскроу ончейн при расчёте,
поэтому Settle, отправленный при пополнении, которое не прошло, завершится
с ошибкой `LegNotFunded`, и ничего не сдвинется; цена — неудавшийся Settle и
повторная отправка. Считайте плечо пополненным, когда его перевод достиг
уровня `finalized`.

## Примечания

- **Плечи с wrapped SOL.** Программа читает баланс нативного эскроу после его
  синхронизации, поэтому lamports, отправленные в эскроу wrapped SOL системным
  переводом, учитываются. Никогда не отправляйте SOL в эскроу для любого другого
  минта: программа не сможет вернуть их, и они достанутся тому, кто закроет аккаунт.
- **Минты с ограничениями.** Если у минта Default Account State имеет значение
  frozen, эскроу создаётся замороженным, и перевод не проходит, пока эмитент не
  разморозит его или не допустит. Взаимодействие с Token ACL описано
  в [обзоре](/docs/defi/dvp-program#mint-configuration-constraints).
- **Transfer hooks.** Пополняйте эскроу с hook ровно на согласованную сумму. Если
  излишек вынуждает сделать возврат при расчёте, возврат использует аккаунты hook
  плеча с другим адресом назначения и другой суммой, что некоторые hook
  отклоняют. Выход — Reclaim, повторное пополнение на точную сумму и новый расчёт.
- **Пополнение после истечения срока.** Ничто не мешает переводу после
  `expiry_timestamp`. Он поступит, но расчёт уже будет невозможен, и сторона
  плеча вернёт средства через Reclaim, пока сделка открыта, или через Recover
  после её закрытия. См. [отмена сделки](/docs/defi/dvp-program/unwind-a-trade).
- **Кто пополняет первым.** Программа не задаёт очерёдность двух плеч. Порядок
  определяют сами стороны; каждая из них может вернуть своё плечо в любой момент
  до расчёта, если только mint authority (заморозка, пауза или transfer hook) не
  блокирует эскроу.
