# Защита от MEV с Jito DontFront

Максимальная извлекаемая стоимость (MEV) — это стоимость, которую можно получить,
изменяя порядок транзакций в блоке, добавляя их или исключая. MEV не
свойственна какому-то одному блокчейну: это фундаментальное свойство любого блокчейна, где
производители блоков контролируют порядок транзакций. Одни формы MEV, например арбитраж,
помогают поддерживать эффективность рынков, устраняя расхождения цен между DEX.
Другие, например сэндвич-атаки, извлекают прибыль непосредственно у пользователей. Для разработчиков
DeFi-приложений это может означать худшее исполнение сделок и упущенную
прибыль.

В этом руководстве речь пойдёт о сэндвич-атаках, распространённой форме вредоносного MEV, и о том, как
снизить их риск с помощью функции `dontfront` от Jito.

Рекомендуется предварительно прочитать:
[Бандлы Jito](https://solana.com/docs/tools/transaction-landing#jito-bundles)

## MEV в Solana

Архитектура Solana уже уменьшает поверхность для MEV по сравнению с блокчейнами
с публичными мемпулами. Транзакции пересылаются напрямую следующему лидеру
блока, а не лежат в общем мемпуле, а необработанные транзакции
истекают примерно через 150 блоков (~1 минута). Это существенно сужает
окно, в которое серчеры могут увидеть ожидающие транзакции и среагировать на них.

Тем не менее MEV-извлечение всё равно происходит. Серчеры с оптимизированной инфраструктурой
и прямыми подключениями к validator могут наблюдать за потоком транзакций и реагировать на него.
Значительная часть MEV-активности в Solana — это атомарный арбитраж: боты, которые устраняют
разницу цен между DEX в рамках одной транзакции. Этот тип MEV, как правило,
полезен, поскольку повышает согласованность цен на разных рынках.

Вредоносная разновидность — сэндвич-атаки — именно то, от чего разработчикам следует
активно защищаться.

## Что такое сэндвич-атака?

Сэндвич-атака происходит, когда серчер обнаруживает ваш ожидающий своп и использует
порядок транзакций в своих интересах:

1. **Фронтраннинг**: серчер покупает токен до вашей сделки, поднимая
   цену
2. **Ваша сделка исполняется** по цене хуже ожидаемой
3. **Бэкраннинг**: серчер продаёт токен после вашей сделки, забирая
   разницу себе

В Solana это может происходить через
[бандлы Jito](https://docs.jito.wtf/lowlatencytxnsend/#what-are-bundles). Серчер
отправляет бандл транзакций вида:
`[frontrun_tx, your_tx, backrun_tx]`, а block engine исполняет их
атомарно в заданном порядке. Жертва получает худшую цену исполнения, а серчер
зарабатывает на спреде.

## Как работает DontFront

[DontFront](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation) — это
функция block engine от Jito, которая не позволяет серчерам размещать
транзакции перед вашей в бандле.

Механизм такой: добавьте любой допустимый публичный ключ Solana, начинающийся с `jitodontfront`,
в любую инструкцию вашей транзакции. Block engine распознаёт этот префикс
и применяет правило: **любой бандл, содержащий вашу транзакцию, должен разместить её
под индексом 0**.

```
Without dontfront:  [frontrun_tx, your_tx, backrun_tx]  ← sandwich possible
With dontfront:     [your_tx, ...]                       ← your tx must be first
```

### Пошаговая инструкция

1. **Выберите допустимый адрес**, начинающийся с `jitodontfront` (например,
   `jitodontfront111111111111111111111111111111`). Аккаунт не обязан
   существовать в блокчейне: он никогда не читается и не изменяется. Проверить, что строка является
   допустимым адресом, можно с помощью функции
   [`assertIsAddress`](https://www.solanakit.com/api/functions/assertIsAddress)
   из @solana/kit, либо ввести адрес в Solana Explorer и
   посмотреть, распознаётся ли он. Вот пример
   [недопустимого адреса](https://explorer.solana.com/address/jitodontfront11111111111111111111111111111INVALID).

2. **Добавьте его как аккаунт только для чтения без подписи** в любую инструкцию
   вашей транзакции. Пометьте его как только для чтения для оптимальной скорости попадания в блок. Большинство программ
   (включая System Program) игнорируют лишние аккаунты сверх ожидаемых.

3. **Отправьте через block engine Jito**:
   - `sendTransaction`:
     `https://mainnet.block-engine.jito.wtf/api/v1/transactions`
   - `sendBundle`: `https://mainnet.block-engine.jito.wtf/api/v1/bundles`

   Документация:
   [sendTransaction](https://docs.jito.wtf/lowlatencytxnsend/#sendtransaction)
   и [sendBundle](https://docs.jito.wtf/lowlatencytxnsend/#sendbundle)

4. Block engine обнаруживает префикс `jitodontfront` и применяет правила
   упорядочивания.

### Что происходит в block engine

Когда block engine видит транзакцию, содержащую аккаунт `jitodontfront`:

- При отправке через `sendTransaction`: транзакция защищена. Ни один бандл не может поместить
  другую транзакцию перед ней
- При отправке через `sendBundle`: транзакция должна находиться под индексом 0, иначе весь бандл
  отклоняется

Транзакции и бандлы, не содержащие аккаунт `jitodontfront`, остаются
без изменений.

## Правила упорядочивания бандлов

Эти правила действуют, когда транзакция `jitodontfront` находится в бандле.

### Допустимые схемы

```
[tx_with_dontfront, tip]
[tx_with_dontfront, arbitrage, tip]
[tx_with_dontfront_signer1, tx_with_dontfront_signer1_and_signer2, tip]
```

### Несколько транзакций DontFront в одном бандле

Несколько транзакций dontfront в одном бандле допускаются, если выполнены **оба**
условия:

1. Все транзакции dontfront расположены **непрерывно в начале** бандла
2. Каждая транзакция dontfront имеет **хотя бы одного общего подписанта** с первой
   транзакцией dontfront

```
✅ [txA_df, txB_df, txC_df, arbitrage, tip]
   (contiguous at front, overlapping signers)

✅ [txA_df_signer1_signer2, txB_df_signer1_signer3, txC_df_signer2_signer4]
   (each shares a signer with txA)
```

### Отклоняемые схемы

```
❌ [tip, tx_with_dontfront]
   → dontfront tx is not at index 0

❌ [txA_df_signer1, txB_df_signer2]
   → no overlapping signer between txA and txB

❌ [trade, tx_with_dontfront, arbitrage, tip]
   → dontfront tx is not at the front
```

## Примеры интеграции

Краткий пример кода смотрите в
[рецепте по защите от MEV в кукбуке](/developers/cookbook/transactions/mev-protection).

### TypeScript (@solana/kit)

Основная идея — вспомогательная функция, которая добавляет аккаунт dontfront в любую инструкцию:

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
import {
  address,
  AccountRole,
  type Instruction,
  type Address
} from "@solana/kit";

const DONT_FRONT: Address = address(
  "jitodontfront111111111111111111111111111111"
);

// !mark(1:9)
function withDontFront(ix: Instruction): Instruction {
  return {
    ...ix,
    accounts: [
      ...(ix.accounts ?? []),
      { address: DONT_FRONT, role: AccountRole.READONLY }
    ]
  };
}
```

```rs !! title="Rust"
use solana_sdk::{
    instruction::{AccountMeta, Instruction},
    pubkey::Pubkey,
};
use std::str::FromStr;

const DONT_FRONT_ACCOUNT: &str =
    "jitodontfront111111111111111111111111111111";

// !mark(1:6)
fn with_dontfront(ix: &mut Instruction) {
    let dontfront =
        Pubkey::from_str(DONT_FRONT_ACCOUNT).unwrap();
    ix.accounts
        .push(AccountMeta::new_readonly(dontfront, false));
}
```

</CodeTabs>

Затем отправьте подписанную транзакцию в block engine Jito вместо
обычного RPC-узла. Всегда используйте кодировку base64. Base58 объявлена устаревшей в API
Jito.

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
// !mark(1:2)
const response = await fetch(
  "https://mainnet.block-engine.jito.wtf/api/v1/transactions",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      jsonrpc: "2.0",
      id: 1,
      method: "sendTransaction",
      // !mark
      params: [base64Tx, { encoding: "base64" }]
    })
  }
);
```

```rs !! title="Rust"
let serialized = bincode::serialize(&tx)?;
// !mark
let base64_tx = base64::engine::general_purpose::STANDARD
    .encode(&serialized);

// !mark(1:2)
let response = client
    .post("https://mainnet.block-engine.jito.wtf/api/v1/transactions")
    .json(&serde_json::json!({
        "jsonrpc": "2.0",
        "id": 1,
        "method": "sendTransaction",
        "params": [base64_tx, {"encoding": "base64"}]
    }))
    .send()
    .await?;
```

## Лучшие практики

DontFront — это один из уровней защиты. Надёжная стратегия снижения MEV-рисков сочетает
несколько подходов:

### Защита на уровне транзакций

- **Устанавливайте жёсткие допуски по проскальзыванию.** Самая эффективная защита от
  сэндвич-атак — ограничение допустимого проскальзывания при свопах. Чем меньше окно
  проскальзывания, тем ниже маржа прибыли для атакующих, и тем менее
  привлекательной для сэндвича становится ваша транзакция.

- **Устанавливайте подходящие чаевые и приоритетные комиссии.** При перегрузке сети более высокие чаевые и
  приоритетные комиссии повышают вероятность быстрого попадания вашей транзакции или бандла в блок,
  сокращая окно для действий серчеров. Подробнее о том, как выбирать подходящие чаевые, см. документацию Jito:
  [Размеры чаевых](https://docs.jito.wtf/lowlatencytxnsend/#tip-amount).

- **Оптимизируйте использование вычислительных единиц.** В каждом блоке доступно ограниченное число вычислительных
  единиц (compute units), и у аккаунтов тоже ограниченное число вычислительных единиц
  на блок. Чтобы максимально повысить вероятность включения вашей транзакции или бандла
  в блок, оптимизируйте использование вычислительных единиц. Подробности смотрите в руководстве
  [Как оптимизировать использование вычислений в Solana](/developers/cookbook/transactions/optimize-compute).

### Специфика DontFront

1. **Помечайте аккаунт dontfront как только для чтения.** Пометка как записываемого тоже работает, но режим
   только для чтения
   [оптимизирует скорость попадания в блок](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation).

2. **Используйте уникальный pubkey dontfront для каждого приложения.** Подойдёт любой pubkey, начинающийся с
   `jitodontfront`. Использование уникального варианта (например,
   `jitodontfront111111111111111111111111111123`) позволяет различать использование по
   приложениям при анализе данных в блокчейне.

3. **DontFront поддерживает Address Lookup Tables.** Аккаунт dontfront можно
   включить через ALT. Но не используйте ALT для аккаунтов чаевых.

## Ограничения

- **Только через block engine.** DontFront применяется block engine от Jito.
  Транзакции, отправленные напрямую на узлы validator (в обход Jito), не
  защищены.

- **Не является гарантией.** Из документации Jito: _«Эта функция может помочь снизить число сэндвич-атак,
  но не гарантирует этого и не является решением для всех
  вариантов упорядочивания транзакций, включая любое упорядочивание, выполняемое
  третьими сторонами.»_

- **Только Mainnet/Testnet.** Это функция block engine от Jito. Она не
  работает в devnet или на localhost.
