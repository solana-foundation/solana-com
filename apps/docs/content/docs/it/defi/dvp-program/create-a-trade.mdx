`CreateDvp` registra i termini di uno scambio e crea i due account di escrow che le
parti finanzieranno. Non sposta alcun token. Chiunque può inviarla, quindi il record può
provenire da una controparte, dall'operatore dell'autorità di regolamento o da una terza parte,
e ogni altro partecipante verifica i termini memorizzati prima di agire in base ad essi (vedi
[finanziare i leg](/docs/defi/dvp-program/fund-the-legs)).

Gli snippet usano direttamente il client generato, con indirizzi segnaposto, in modo che
gli account e i firmatari coinvolti siano visibili. Hanno come destinazione devnet, dove il
programma è distribuito allo stesso indirizzo di mainnet-beta.

## Installazione

Al 2 ottobre 2026 non è stato pubblicato alcun pacchetto per i client DvP. Entrambi sono
generati dall'IDL del programma nel repository e usati dal sorgente.

## Ricavare gli indirizzi

Il record dello scambio è un program-derived address calcolato sull'autorità di regolamento, sulle
due parti, sui due mint e su un nonce. Ogni escrow è l'associated
token account del record per uno dei mint. Entrambe le derivazioni non richiedono accesso alla rete.

Usa un nonce casuale a 64 bit per ogni scambio. Poiché la creazione è senza permessi, un
nonce prevedibile consente a una terza parte di occupare l'indirizzo che uno scambio avrebbe
dovuto usare. Passa il nonce e gli importi come `bigint` in TypeScript; il client
generato rifiuta un `number`.

Sostituisci ogni segnaposto `..._HERE` con un indirizzo reale prima dell'esecuzione.
`address()` convalida il formato base58 e genera un errore con un segnaposto, mentre `pubkey!` non
viene compilato.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { address, createClient } from "@solana/kit";
    import { solanaRpc } from "@solana/kit-plugin-rpc";
    import { signer } from "@solana/kit-plugin-signer";
    import { TOKEN_2022_PROGRAM_ADDRESS } from "@solana-program/token-2022";
    import { findSwapDvpEscrowAta, findSwapDvpPda } from "./dvp";

    const client = createClient()
      .use(signer(payerSigner))
      .use(
        solanaRpc({
          rpcUrl: "https://api.devnet.solana.com",
          rpcSubscriptionsUrl: "wss://api.devnet.solana.com",
        }),
      );

    const settlementAuthority = address("SETTLEMENT_AUTHORITY_ADDRESS_HERE");
    const userA = address("ASSET_LEG_PARTY_ADDRESS_HERE");
    const userB = address("CASH_LEG_PARTY_ADDRESS_HERE");
    const mintA = address("ASSET_MINT_ADDRESS_HERE");
    const mintB = address("CASH_MINT_ADDRESS_HERE");
    const tokenProgramA = TOKEN_2022_PROGRAM_ADDRESS;
    const tokenProgramB = TOKEN_2022_PROGRAM_ADDRESS;

    // A fresh random nonce per trade, as a bigint.
    const nonce = new DataView(
      crypto.getRandomValues(new Uint8Array(8)).buffer,
    ).getBigUint64(0);

    const [swapDvp] = await findSwapDvpPda({
      settlementAuthority,
      userA,
      userB,
      mintA,
      mintB,
      nonce,
    });
    const [escrowA] = await findSwapDvpEscrowAta({
      swapDvp,
      mint: mintA,
      tokenProgram: tokenProgramA,
    });
    const [escrowB] = await findSwapDvpEscrowAta({
      swapDvp,
      mint: mintB,
      tokenProgram: tokenProgramB,
    });
    ```

  </Tab>

## Registrare i termini

`CreateDvp` accetta i due importi in unità di base, una scadenza, il nonce e quattro
campi facoltativi: un riferimento opaco fino a 64 byte, una destinazione di regolamento
per ciascun lato e un orario minimo di regolamento (vedi Note). La destinazione è
dove finiscono i proventi di quella parte al momento del regolamento, ad esempio il wallet di
deposito di un custode; per impostazione predefinita è l'indirizzo della parte stessa e non può essere modificata una volta creato
il record. I rimborsi e i recuperi vanno sempre al token account della parte
per il mint di quel leg, mai a una destinazione, indipendentemente da chi ha finanziato l'escrow.

Chi paga finanzia il rent per il record, il tombstone del nonce e entrambi gli escrow.
Alla chiusura, quel rent va a chi firma l'istruzione di chiusura, non torna
a chi ha pagato. Il tombstone non viene mai chiuso, quindi ogni scambio lascia un piccolo saldo
permanente. Quando pianifichi il budget di SOL di chi paga, ricava gli importi del rent con il
metodo RPC `getMinimumBalanceForRentExemption` invece di codificarli in modo fisso.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { getCreateDvpInstruction } from "./dvp";

    const nowSeconds = BigInt(Math.floor(Date.now() / 1000));

    const createInstruction = getCreateDvpInstruction({
      payer: payerSigner,
      swapDvp,
      nonceTombstone: (
        await getProgramDerivedAddress({
          programAddress: DVP_SWAP_PROGRAM_PROGRAM_ADDRESS,
          seeds: ["nonce", getAddressEncoder().encode(swapDvp)],
        })
      )[0],
      settlementAuthority,
      userA,
      userB,
      mintA,
      mintB,
      dvpAtaA: escrowA,
      dvpAtaB: escrowB,
      tokenProgramA,
      tokenProgramB,
      amountA: 1_000_000_000n, // 1,000 units of a 6-decimal asset
      amountB: 998_500_000n, // 998.50 units of a 6-decimal cash token
      expiryTimestamp: nowSeconds + 60n * 60n * 24n, // one day
      nonce,
      refString: "ORDER-2026-10-02-0001",
      userASettlementDestination: null, // defaults to userA
      userBSettlementDestination: null, // defaults to userB
      earliestSettlementTimestamp: null,
    });

    const { context } = await client.sendTransaction([createInstruction]);
    console.log("Trade record:", swapDvp, "signature:", context.signature);
    ```

Lo snippet TypeScript richiede che `getProgramDerivedAddress` e `getAddressEncoder`
da `@solana/kit`, e `DVP_SWAP_PROGRAM_PROGRAM_ADDRESS` dal client, siano nello
scope. Il builder Rust lascia il system program e l'associated token program
ai valori predefiniti.

## Note

- **Scadenza.** Solo Settle controlla la scadenza. Reclaim, Cancel e Reject funzionano
  anche dopo di essa, e un deposito che arriva dopo la scadenza può essere recuperato dalla parte
  del leg. La scadenza può essere al massimo un anno dopo la creazione.
- **Il tempo è quello della rete.** Il programma legge l'orologio onchain, che può
  differire dall'ora reale, a volte di decine di secondi, e può saltare
  in avanti. Lascia un margine tra la scadenza e l'orario di regolamento previsto,
  evita di finanziare o regolare vicino a entrambi i limiti e non fare affidamento sulla scadenza
  per imporre un termine al secondo. Il README del programma suggerisce di prevedere
  circa un minuto di scostamento.
- **Regolamento minimo.** Facoltativo. Se impostato, Settle viene rifiutata prima di tale orario,
  e non deve essere successivo alla scadenza.
- **Controlli in fase di creazione.** La creazione fallisce con `PartyNotSignerCapable` se una parte
  non è un account system-owned (questo esclude un multisig SPL Token),
  `SettlementDestinationIsSwapDvp`, `SelfDvp`, `SameMint`, `ZeroAmount`,
  `SettlementAuthorityIsParty` oppure `ExpiryNotInFuture`. L'elenco completo è nella
  [tabella degli errori](/docs/defi/dvp-program#errors).
