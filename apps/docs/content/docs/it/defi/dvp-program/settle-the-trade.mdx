`SettleDvp` è firmata dall'autorità di regolamento indicata nel record dello
scambio. In un'unica transazione sposta `amount_a` del leg asset verso la
destinazione della parte del leg cash e `amount_b` del leg cash verso la
destinazione della parte del leg asset, restituisce l'eventuale eccedenza di
ciascun escrow alla parte del relativo leg e chiude il record ed entrambi gli
escrow. Se uno qualsiasi di questi trasferimenti non può essere completato,
l'istruzione fallisce e nulla viene spostato.

Questa pagina prosegue da [creare uno scambio](/docs/defi/dvp-program/create-a-trade)
e [finanziare i leg](/docs/defi/dvp-program/fund-the-legs); il client, i firmatari,
`trade` e i token account delle parti restano gli stessi.

## Riconvalidare prima di firmare

L'autorità di regolamento firma la transazione che sposta entrambi i leg, quindi
effettua prima di firmare la stessa lettura di ciascuna parte: proprietario,
dimensione, parti, mint, importi, scadenza ed entrambe le destinazioni (vedi
[finanziare i leg](/docs/defi/dvp-program/fund-the-legs#verify-the-terms)). Il
programma stesso ricontrolla al momento del regolamento che ogni mint appartengaancora al token program registrato alla creazione, non abbia estensioni bloccate
e abbia la stessa mint authority di quando lo scambio è stato creato, perciò un
mint ricreato con un'estensione bloccata, un diverso token program o una diversa
mint authority non può essere regolato.

## Creare gli account destinatari

Settle scrive su quattro token account che il programma non crea:

| Account                | Riceve                     | Proprietario                           |
| ---------------------- | ---------------------------- | ------------------------------- |
| `userADestinationAtaB` | Il leg cash (`amount_b`)    | `user_a_settlement_destination` |
| `userBDestinationAtaA` | Il leg asset (`amount_a`)   | `user_b_settlement_destination` |
| `userAAtaA`            | Eventuale eccedenza sul leg asset | `user_a`                        |
| `userBAtaB`            | Eventuale eccedenza sul leg cash  | `user_b`                        |

I token account per l'eccedenza vengono usati solo quando un escrow contiene più
dell'importo concordato, ma chiunque possieda il mint può creare un'eccedenza
inviando poche unità base nell'escrow. Se il token account di rimborso non
esiste, l'intera istruzione Settle fallisce, quindi crea tutti e quattro i
token account in modo idempotente nella stessa transazione.

  <Tab value="TypeScript">

    import {
      findAssociatedTokenPda,
      getCreateAssociatedTokenIdempotentInstruction,
    } from "@solana-program/token-2022";

    const destinationA = t.userASettlementDestination; // defaults to userA
    const destinationB = t.userBSettlementDestination; // defaults to userB

    const [userADestinationAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: destinationA,
      tokenProgram: tokenProgramB,
    });
    const [userBDestinationAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: destinationB,
      tokenProgram: tokenProgramA,
    });
    // userAAtaA and userBAtaB are from fund the legs.

    const createRecipientAccounts = [
      { ata: userADestinationAtaB, owner: destinationA, mint: mintB, tokenProgram: tokenProgramB },
      { ata: userBDestinationAtaA, owner: destinationB, mint: mintA, tokenProgram: tokenProgramA },
      { ata: userAAtaA, owner: userA, mint: mintA, tokenProgram: tokenProgramA },
      { ata: userBAtaB, owner: userB, mint: mintB, tokenProgram: tokenProgramB },
    ].map(({ ata, owner, mint, tokenProgram }) =>
      getCreateAssociatedTokenIdempotentInstruction({
        payer: authoritySigner,
        ata,
        owner,
        mint,
        tokenProgram,
      }),
    );

## Eseguire il regolamento

`legAExtrasCount` indica al programma quanti degli account aggiunti dopo l'elenco
fisso appartengono al transfer hook del leg asset; i restanti vanno a quello
del leg cash. Per i mint senza transfer hook, passa zero e non aggiungere nulla.
Il memo program account è richiesto dall'istruzione e viene usato solo per le
destinazioni che richiedono un memo.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { MEMO_PROGRAM_ADDRESS } from "@solana-program/memo";
    import { getSettleDvpInstruction } from "./dvp";

    const settleInstruction = getSettleDvpInstruction({
      settlementAuthority: authoritySigner,
      swapDvp,
      mintA,
      mintB,
      dvpAtaA: escrowA,
      dvpAtaB: escrowB,
      userADestinationAtaB,
      userBDestinationAtaA,
      userAAtaA,
      userBAtaB,
      tokenProgramA,
      tokenProgramB,
      memoProgram: MEMO_PROGRAM_ADDRESS,
      legAExtrasCount: 0,
    });

    const { context: settleContext } = await client.sendTransaction([
      ...createRecipientAccounts,
      settleInstruction,
    ]);
    const settleSignature = settleContext.signature;
    console.log("Submitted:", settleSignature);

    // sendTransaction returns at the client's commitment (confirmed by default).
    // Wait for finalized before recording the trade as settled.
    let finalized = false;
    for (let attempt = 0; attempt < 30 && !finalized; attempt++) {
      const {
        value: [status],
      } = await client.rpc.getSignatureStatuses([settleSignature]).send();
      if (status?.err) {
        throw new Error("Settle transaction failed");
      }
      finalized = status?.confirmationStatus === "finalized";
      if (!finalized) {
        await new Promise((resolve) => setTimeout(resolve, 2_000));
      }
    }
    if (!finalized) {
      // A closed record means it settled; an open one is safe to settle again.
      throw new Error("Settle not finalized after 60s; read the trade record");
    }
    console.log("Settled:", settleSignature);
    ```

### Transfer hook

L'IDL generato elenca solo gli account fissi, quindi i builder generati non
conoscono gli account degli hook. Risolvi gli extra account meta di ciascun mint
con hook nello stesso modo in cui lo faresti per un trasferimento diretto di quel
token, quindi aggiungili all'istruzione: prima gli account del leg asset, poi
quelli del leg cash, con `legAExtrasCount` impostato al numero del primo gruppo.
In TypeScript, espandi (spread) i meta risolti nell'array `accounts`
dell'istruzione; in Rust, usa `add_remaining_accounts` sul builder. Il limite è
di 32 account per leg, inclusi il programma hook e l'account di validazione; il
limite di account della transazione può essere raggiunto prima quando entrambi i
leg hanno hook. Il programma rimuove il flag di firmatario da ogni account
inoltrato, quindi un hook non può ottenere la firma dell'autorità di regolamento
tramite questo percorso.

## Registrare il risultato

Considera lo scambio regolato quando la transazione Settle raggiunge
`finalized`. Dopo il regolamento il record ed entrambi gli escrow non esistono
più, quindi un sistema che ha bisogno dei termini in seguito li salva dalla
lettura precedente al regolamento o dalla transazione di creazione. Il rent
degli account chiusi è andato all'autorità di regolamento.

## Errori di Settle

`LegNotFunded` significa che un escrow contiene meno del proprio importo
concordato; `DvpExpired` e `SettlementTooEarly` indicano che la finestra
temporale è stata mancata; `MintAuthorityChanged` e `BlockedMintExtension`
indicano che un mint è cambiato dopo la creazione; `RecipientAtaMismatch`
significa che un token account di destinazione o di rimborso è mancante oppure
non appartiene più al proprietario e al mint previsti, di solito perché il passo
di creazione degli account descritto sopra è stato saltato. In ogni caso nulla è
stato spostato e le parti possono annullare l'operazione, in base alle autorità
del mint (vedi [annullare uno scambio](/docs/defi/dvp-program/unwind-a-trade)).
