Una transazione viene eseguita solo se riporta una
[firma](/docs/core/transactions/transaction-structure#signatures) valida di ogni
firmatario richiesto. Durante lo sviluppo locale, di solito si detiene quella chiave come
[`Keypair`](/developers/cookbook/wallets/create-keypair) e si firma direttamente. In
produzione la domanda importante è un'altra: **dove risiede la chiave privata
e chi è autorizzato ad approvare una firma con essa?**

<Callout type="warn">
  Non incorporare mai le chiavi private nel codice lato client, non includerle in un frontend e non
  farne il commit nel controllo del codice sorgente. Chiunque ottenga una chiave ottiene il controllo completo
  dei fondi di quell'account.
</Callout>

## Approcci alla firma

| Approccio                  | Dove risiede la chiave                                     | Chi firma                                          | Ideale per                                                      |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **Keypair locale**         | Un file o una variabile d'ambiente sulla macchina           | Il tuo codice, direttamente                                | Sviluppo locale, test, CI                                  |
| **Wallet del browser**        | Il wallet dell'utente finale (ad es. Phantom, Solflare)          | L'utente finale, per ogni transazione                      | dApp frontend in cui gli utenti firmano le proprie transazioni        |
| **KMS / HSM cloud**       | Un servizio di chiavi basato su hardware (AWS KMS, GCP KMS, Vault) | Il tuo backend richiede una firma al servizio | Servizi backend, operazioni di tesoreria, ambienti regolamentati |
| **Wallet gestiti / MPC** | Suddivisa o custodita sull'infrastruttura di un provider   | Il provider co-firma in base alla tua policy     | Wallet integrati, flussi di approvazione, custodia istituzionale   |

Il keypair locale è l'unico approccio che inserisce il materiale della chiave grezza all'interno della
tua applicazione. Ogni approccio per la produzione mantiene la chiave in un'infrastruttura dedicata
e le chiede di firmare per tuo conto.

## Firma lato backend

Quando un server deve firmare (pagando le commissioni, inviando transazioni di programma o
gestendo una tesoreria), usa un backend dedicato alla gestione delle chiavi anziché un
keypair grezzo. La Solana Foundation mantiene [Keychain](/docs/tools/keychain), una
libreria di firma unificata (Rust, TypeScript, Python e Go) che espone un'unica
interfaccia `SolanaSigner` per tutti i backend della tabella qui sopra: Memory,
HashiCorp Vault, AWS KMS, GCP KMS, Fireblocks, Privy, Turnkey, CDP, Crossmint,
Dfns, Para, Openfort, Utila e Fordefi.

Poiché l'interfaccia è condivisa tra i backend, puoi sviluppare in locale con una
chiave in memoria e passare a un backend di produzione tramite configurazione, senza
riscrivere il codice dell'applicazione (i backend che eseguono il broadcast per te, come Crossmint,
vengono invece richiamati tramite un percorso di firma e invio). Keychain è compatibile con
[`@solana/kit`](/docs/clients/official/javascript), l'
[SDK Rust](/docs/clients/official/rust), `solders` (Python) e `solana-go` v2
(Go).
