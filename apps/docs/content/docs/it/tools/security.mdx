## Gestione delle chiavi

- **Non esporre mai le chiavi private nel codice frontend.** Usa la firma lato backend, hardware
  wallet, wallet multifirma o servizi di gestione delle chiavi.
- **Separa i hot wallet dai cold wallet.** Hot wallet per le operazioni, cold wallet per la
  tesoreria.
- **Esegui il backup di tutte le chiavi di produzione.** Conserva backup crittografati in più
  luoghi sicuri. Perdere una chiave significa perdere l'accesso in modo permanente.
- **Usa chiavi diverse per devnet e mainnet.** Le chiavi di devnet non dovrebbero essere
  le tue chiavi di mainnet. Usa una configurazione basata sull'ambiente per assicurarti che le chiavi corrette
  vengano caricate per ciascuna rete.

## Infrastruttura di firma

Per la firma lato backend in produzione, usa [Keychain](/docs/tools/keychain), una libreria di firma unificata che astrae più backend di gestione delle chiavi attraverso un'unica
interfaccia: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP,
Para, Dfns, Crossmint, Openfort e Utila. Questo ti permette di sviluppare in locale con
chiavi in memoria, per poi passare a backend di livello produttivo senza modificare
il codice dell'applicazione.

Non sai quale backend faccia al caso tuo? Consulta
[Come scegliere un backend](/docs/tools/keychain/choosing-a-backend). Keychain è
disponibile sia per [Rust](https://crates.io/crates/solana-keychain) sia per
[TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Sicurezza RPC

Tratta gli endpoint RPC come chiavi API: non esporli nel codice frontend, dove
possono essere estratti e usati in modo illecito. Usa un proxy backend o variabili d'ambiente che
non vengano incluse nel bundle del codice client.

- [QuickNode: Best practice per la sicurezza degli endpoint](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Proteggi le tue chiavi API Solana: best practice di sicurezza](https://www.helius.dev/docs/rpc/protect-your-keys)

## Monitoraggio

Monitora queste metriche in produzione:

| Metrica                   | Perché                    |
| ------------------------ | ---------------------- |
| Tasso di successo delle transazioni | Rilevare tempestivamente i problemi    |
| Latenza di conferma     | Monitorare lo stato di salute della rete |
| Spesa per le priority fee       | Gestione dei costi        |
| Tasso di errori RPC           | Stato di salute del provider        |

Imposta degli avvisi per:

- Trasferimenti dalla tesoreria superiori alla soglia
- Picchi nel tasso di transazioni non riuscite
- Schemi insoliti nei destinatari
- Aumenti del tasso di errori RPC

Per il monitoraggio delle transazioni in tempo reale su larga scala, consulta la nostra
[Guida all'indicizzazione](/docs/payments/accept-payments/indexing).

## Verifica degli indirizzi

Ogni token e ogni programma hanno esattamente un indirizzo corretto su mainnet. I token
contraffatti che imitano USDC o altre stablecoin sono comuni: avranno lo stesso nome
e lo stesso simbolo, ma un mint diverso. La tua applicazione dovrebbe inserire nel codice o in una allowlist
i mint address (in base alle tue esigenze) e non accettarli mai dinamicamente
da fonti non attendibili.

**Configurazione basata sull'ambiente:** Devnet e Mainnet usano spesso mint di token
completamente diversi. Configura la tua applicazione in modo che carichi gli indirizzi corretti
per ciascun ambiente: non inserire nel codice gli indirizzi di mainnet dimenticando di sostituirli
durante i test o, peggio ancora, rilasciare in produzione gli indirizzi di devnet.

Alcuni mint comuni di stablecoin sono:

| Token | Emittente | Mint address                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Anche gli indirizzi dei programmi sono importanti. Inviare istruzioni al programma sbagliato
fallirà o, peggio, comporterà la perdita irreversibile dei fondi. Gli indirizzi del Token Program
sono:

| Programma            | Indirizzo                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Inserire nella allowlist gli indirizzi giusti protegge dai token contraffatti, ma
non protegge dall'invio al _tipo_ di account sbagliato. L'indirizzo di un destinatario
può essere un wallet, un token account, un mint o un programma, e ognuno richiede
una gestione diversa. Gli SOL nativi inviati a qualsiasi cosa diversa da un wallet escono dal
controllo del mittente — persi definitivamente nel caso di un mint o di un programma, recuperabili solo dal
proprietario dell'account nel caso di un token account — senza alcuna transazione non riuscita che avvisi l'utente.

<Callout type="warn" title="Convalida i destinatari prima dell'invio">
  Classifica ogni indirizzo di destinatario prima di firmare un trasferimento. Consulta [Verifica
  dell'indirizzo](/docs/payments/send-payments/verify-address) per l'albero decisionale completo
  e il codice di riferimento che distingue wallet, token account, mint e
  programmi.
</Callout>
