Підписання повідомлення доводить, що користувач контролює гаманець, без
транзакції, комісії та мережевих викликів. Застосунки використовують підписані
повідомлення, щоб входити в акаунт, фіксувати прийняття користувачем умов,
пов’язувати гаманець з наявним акаунтом або авторизувати дію, що відбувається
off-chain, наприклад розміщення замовлення.

Гаманці Solana підписують повідомлення двома способами:

- **Off-chain повідомлення** (`solana:signOffchainMessage`) обгортають ваш текст у
  стандартний формат, визначений у [специфікації](https://docs.anza.xyz/proposals/off-chain-message-signing) off-chain підписування
  повідомлень (OCMS).
  Цей формат неможливо сплутати з транзакцією, він називає облікові записи, які
  мають його підписати, і саме цей формат підписують апаратні гаманці.
- **Необроблені повідомлення** (`solana:signMessage`) підписують точно ті байти,
  які передає ваш застосунок, без префікса та без оголошених підписантів. Їх
  підтримує більшість програмних гаманців, але ніщо в цих байтах не вказує, що
  це повідомлення, а не транзакція.

Використовуйте off-chain повідомлення там, де гаманець їх підтримує, а де не
підтримує — переходьте на необроблені повідомлення. Далі в цьому посібнику як
приклад використано вхід в акаунт, але ті самі кроки підписування та перевірки
підходять для будь-якого повідомлення.

## Виберіть формат повідомлення

|                           | Off-chain повідомлення     | Необроблене повідомлення   | Транзакція                   |
| ------------------------- | --------------------- | ------------- | ----------------------------- |
| Можливість гаманця            | `signOffchainMessage` | `signMessage` | `signTransaction`             |
| Підтримка апаратних гаманців   | Залежить від пристрою     | Ні            | Так                           |
| Зрозуміле для користувача      | Так                   | Лише програмні гаманці | Залежить від пристрою             |
| Оголошує необхідних підписантів | Так                   | Ні            | Так                           |
| RPC-виклики та комісії        | Немає                  | Немає          | Blockhash, надсилання, комісія, підтвердження |

### Чому не транзакція?

Раніше апаратні гаманці не могли підписати зрозуміле повідомлення. Багато
застосунків просили таких користувачів підписати натомість порожню транзакцію.
Це працює, але додає затримки, витрат і ризиків:

- **Мережеві комісії.** Транзакція сплачує комісію, навіть якщо нічого не робить.
- **Кілька RPC-викликів.** Ваш застосунок отримує blockhash, симулює, надсилає,
  а потім опитує мережу, очікуючи підтвердження.
- **Додаткова затримка.** Кожен із цих викликів — це окремий цикл запит-відповідь
  до того, як користувач увійде в акаунт.
- **Нічого зрозумілого.** Користувач схвалює байти транзакції, а не опис того,
  з чим він погоджується.
- **Поведінковий ризик.** Якщо просити користувачів підписувати транзакцію лише
  для входу, їх легше обманом змусити підписати шкідливу.

Off-chain повідомлення оминає все це. Єдиний цикл запит-відповідь — до вашого
власного сервера.

## Що підписує гаманець

Off-chain повідомлення починається з фіксованого домену підписання,
`\xffsolana offchain`. Жодна коректна транзакція не починається з цих байтів,
тому підписане повідомлення ніколи не можна використати як транзакцію. Далі
версія 1 формату перелічує необхідних підписантів і містить повідомлення як
текст UTF-8 без обмеження довжини.

Гаманець формує ці байти, підписує їх і повертає разом із підписом.
[Специфікація](https://docs.anza.xyz/proposals/off-chain-message-signing)
описує повний формат, зокрема застарілу версію 0.

/>

## Виберіть спосіб входу

Не кожен гаманець уже підтримує off-chain повідомлення. Перш ніж просити підпис,
перевірте можливості підключеного облікового запису, а якщо потрібної можливості
немає — використайте резервний варіант:

1. Якщо обліковий запис підтримує `solana:signOffchainMessage` із версією
   повідомлення 1, підпишіть off-chain повідомлення.
2. В іншому разі підпишіть той самий виклик (challenge) через `solana:signMessage`.
   Його підтримує більшість програмних гаманців.
3. Для користувачів апаратних гаманців без підтримки повідомлень передбачте
   явне ввімкнення, наприклад перемикач «Я використовую апаратний гаманець»,
   який натомість підписує транзакцію входу. Не спрямовуйте їх цим шляхом за
   замовчуванням.

## Підписування повідомлення в браузері

<Tabs items={["Wallet Standard (Kit)", "Wallet Adapter"]}>
  <Tab value="Wallet Standard (Kit)">
    Установіть пакети Wallet Standard разом із Kit:

    ```terminal
    $ npm install @solana/kit @solana/wallet-standard-features @wallet-standard/ui @wallet-standard/ui-features @wallet-standard/ui-registry
    ```

    Ці допоміжні функції приймають `UiWalletAccount`, наприклад `account`, який
    повертає `useConnectedWallet` у [посібнику з React](/docs/frontend/react-hooks):

    ```ts title="offchain-message.ts"
    import {
      SolanaSignOffchainMessage,
      type SolanaSignOffchainMessageFeature
    } from "@solana/wallet-standard-features";
    import type { UiWalletAccount } from "@wallet-standard/ui";
    import { getWalletAccountFeature } from "@wallet-standard/ui-features";
    import { getWalletAccountForUiWalletAccount } from "@wallet-standard/ui-registry";

    type OffchainMessageFeature =
      SolanaSignOffchainMessageFeature[typeof SolanaSignOffchainMessage];

    export function supportsOffchainMessages(account: UiWalletAccount) {
      if (!account.features.includes(SolanaSignOffchainMessage)) return false;
      const feature = getWalletAccountFeature(
        account,
        SolanaSignOffchainMessage
      ) as OffchainMessageFeature;
      return feature.supportedMessageVersions.includes(1);
    }

    export async function signOffchainMessage(
      account: UiWalletAccount,
      message: string
    ) {
      const feature = getWalletAccountFeature(
        account,
        SolanaSignOffchainMessage
      ) as OffchainMessageFeature;
      const [output] = await feature.signOffchainMessage({
        messageVersion: 1,
        account: getWalletAccountForUiWalletAccount(account),
        message,
        requiredSigners: [account.publicKey]
      });
      return output;
    }
    ```

  </Tab>

  <Tab value="Wallet Adapter">
    `useWallet` з `@solana/wallet-adapter` надає `signOffchainMessage` лише тоді,
    коли підключений обліковий запис підтримує `solana:signOffchainMessage`. Він
    підписує повідомлення версії 1, де підключений обліковий запис є необхідним
    підписантом, і завершується відхиленням із `WalletNotReadyError`, якщо гаманець
    не може підписати версію 1:

    ```terminal
    $ npm install @solana/web3.js@3 @solana/wallet-adapter
    ```

    ```tsx title="SignOffchainMessage.tsx"
    "use client";

    import { useWallet } from "@solana/wallet-adapter";

    export function SignOffchainMessage({ challenge }: { challenge: string }) {
      const { publicKey, signOffchainMessage } = useWallet();

      const onClick = async () => {
        if (!publicKey || !signOffchainMessage) return;
        const { signature, signedOffchainMessage } =
          await signOffchainMessage(challenge);
        const valid = await publicKey.verifySignature(
          signature,
          signedOffchainMessage
        );
        // Server logic
      };

      return (
        <button onClick={onClick} disabled={!signOffchainMessage}>
          Sign in
        </button>
      );
    }
    ```

    `publicKey.verifySignature` перевіряє підпис щодо підписаних байтів у
    браузері. Ваш сервер усе одно має підтвердити, що ці байти — це виданий ним
    challenge. Якщо `signOffchainMessage` має значення `undefined`, перейдіть на
    `signMessage` з того самого хука.

  </Tab>
</Tabs>

`signOffchainMessage` повертає `signedOffchainMessage` — повні байти, які
підписав гаманець, — та `signature`. Закодуйте обидва значення в Base64 і
надішліть на свій сервер разом з адресою гаманця.

Складіть challenge так, щоб його було зручно читати на малому екрані. Вкажіть
назву застосунку й домен, поясніть, що означає підписання, і додайте одноразовий
nonce та час видачі з вашого сервера:

```text
swap.app wants you to sign in with your Solana account.

Signing in costs nothing and does not submit a transaction.

Nonce: 8f3a1c9e
Issued at: 2026-09-29T17:04:00Z
```

## Перевірка підпису на вашому сервері

Перевірка підпису відбувається локально й не потребує RPC-з’єднання. Декодуйте
байти, які підписав гаманець, переконайтеся, що вони збігаються з виданим вами
challenge, а тоді перевірте підпис:

```ts title="verify-sign-in.ts"
import {
  address,
  assertOffchainMessageV1Equal,
  getBase64Encoder,
  getOffchainMessageDecoder,
  verifyOffchainMessageEnvelope,
  type OffchainMessageBytes,
  type SignatureBytes
} from "@solana/kit";

export async function verifySignIn(input: {
  walletAddress: string;
  expectedMessage: string;
  signedOffchainMessage: string;
  signature: string;
}) {
  const signer = address(input.walletAddress);
  const base64 = getBase64Encoder();
  const content = base64.encode(
    input.signedOffchainMessage
  ) as OffchainMessageBytes;
  const signature = base64.encode(input.signature) as SignatureBytes;

  const received = getOffchainMessageDecoder().decode(content);
  if (received.version !== 1) {
    throw new Error(`Expected a v1 message, got v${received.version}`);
  }
  assertOffchainMessageV1Equal(received, {
    version: 1,
    requiredSignatories: [{ address: signer }],
    content: input.expectedMessage
  });

  await verifyOffchainMessageEnvelope({
    content,
    signatures: { [signer]: signature }
  });
}
```

`assertOffchainMessageV1Equal` викидає помилку, якщо вміст або підписанти
відрізняються від очікуваних. `verifyOffchainMessageEnvelope` викидає помилку,
якщо підпис відсутній або недійсний. Шукайте `expectedMessage` за nonce на
своєму сервері, а не довіряйте копії, яку повертає клієнт. Використайте nonce
одразу після успішної перевірки, щоб той самий підпис не можна було застосувати
для входу вдруге.

### Перевірка необробленого повідомлення

Підпис `signMessage` охоплює байти challenge безпосередньо, тому клієнтові
потрібно надіслати лише підпис і адресу гаманця. Перевірте його щодо виданого
вами challenge:

```ts title="verify-raw-sign-in.ts"
import {
  address,
  getBase64Encoder,
  getPublicKeyFromAddress,
  getUtf8Encoder,
  signatureBytes,
  verifySignature
} from "@solana/kit";

export async function verifyRawSignIn(input: {
  walletAddress: string;
  expectedMessage: string;
  signature: string;
}) {
  const publicKey = await getPublicKeyFromAddress(address(input.walletAddress));
  const signature = signatureBytes(getBase64Encoder().encode(input.signature));
  const message = getUtf8Encoder().encode(input.expectedMessage);
  if (!(await verifySignature(publicKey, signature, message))) {
    throw new Error("Invalid signature");
  }
}
```

Діють ті самі правила щодо nonce: шукайте `expectedMessage` за nonce і
використайте його одразу після успішної перевірки.

<Callout type="info">
  `@solana/kit` повторно експортує ці допоміжні функції з
  `@solana/offchain-messages`. Використовуйте окремий пакет, якщо ваш сервер не
  залежить від Kit.
</Callout>

## Sign In With Solana

[Sign In With Solana](https://github.com/phantom/sign-in-with-solana) (SIWS)
стандартизує сам challenge. Ваш застосунок передає структуровані поля, як-от
`domain`, `statement`, `nonce` та `issuedAt`, у функцію `solana:signIn` гаманця.
Гаманець форматує їх у стандартне повідомлення, за потреби підключається й
підписує його за один крок.

Версія `1.1.0` функції `solana:signIn` додає опцію `useOffchainMessage`. Якщо
передати `useOffchainMessage: { messageVersion: 1 }`, гаманець обгортає текст
SIWS в off-chain повідомлення версії 1, де підписувальний обліковий запис є
єдиним необхідним підписантом. Апаратні гаманці можуть його відобразити й
підписати, а у вихідних даних буде
`signedMessageFormat: { kind: "offchainMessage", messageVersion: 1 }`. Гаманці,
що заявляють версію `1.0.0`, цієї опції не знають, тож спершу перевірте версію
функції, а якщо вона нижча — не передавайте опцію.

  <Tab value="Wallet Standard">
    `solana:signIn` — це можливість гаманця, а не облікового запису, тому ці
    допоміжні функції приймають `UiWallet`:

    ```ts title="sign-in.ts"
    import {
      SolanaSignIn,
      type SolanaSignInFeature,
      type SolanaSignInInput
    } from "@solana/wallet-standard-features";
    import type { UiWallet } from "@wallet-standard/ui";
    import { getWalletFeature } from "@wallet-standard/ui-features";

    type SignInFeature = SolanaSignInFeature[typeof SolanaSignIn];

    export function supportsOffchainSignIn(wallet: UiWallet) {
      if (!wallet.features.includes(SolanaSignIn)) return false;
      const feature = getWalletFeature(wallet, SolanaSignIn) as SignInFeature;
      return feature.version === "1.1.0";
    }

    export async function signIn(wallet: UiWallet, input: SolanaSignInInput) {
      const feature = getWalletFeature(wallet, SolanaSignIn) as SignInFeature;
      const [output] = await feature.signIn({
        ...input,
        ...(supportsOffchainSignIn(wallet) && {
          useOffchainMessage: { messageVersion: 1 }
        })
      });
      return output;
    }
    ```

    `useWallet` надає `signIn`, коли вибраний гаманець підтримує `solana:signIn`, і
    `supportsSignInWithOffchainMessage`, коли він заявляє версію `1.1.0`. Якщо
    передати `useOffchainMessage` гаманцю, який його не підтримує, виклик
    завершиться відхиленням із `WalletSignInError`:

    ```tsx title="SignIn.tsx"
    "use client";

    import {
      useWallet,
      verifySignIn,
      type SolanaSignInInput
    } from "@solana/wallet-adapter";

    export function SignIn({ input }: { input: SolanaSignInInput }) {
      const { signIn, supportsSignInWithOffchainMessage } = useWallet();

      const onClick = async () => {
        if (!signIn) return;
        const output = await signIn({
          ...input,
          ...(supportsSignInWithOffchainMessage && {
            useOffchainMessage: { messageVersion: 1 }
          })
        });
        const valid = await verifySignIn(input, output);
      };

      return (
        <button onClick={onClick} disabled={!signIn}>
          Sign in with Solana
        </button>
      );
    }
    ```

    `verifySignIn` перевіряє, що підписане повідомлення відтворює кожне поле
    вхідних даних і містить дійсний підпис від підписувального облікового запису
    — незалежно від того, чи гаманець підписав звичайний текст SIWS, чи off-chain
    повідомлення. Виконайте таку саму перевірку на своєму сервері, імпортувавши
    функцію з `@solana/wallet-adapter/core`, який не залежить від React.

  </Tab>
</Tabs>

Сформуйте вхідні дані на своєму сервері з одноразовим `nonce` та часом
`issuedAt` і зберігайте копію за ключем nonce. Використайте nonce одразу після
успішної перевірки входу.

Без Wallet Adapter `verifySignIn` з `@solana/wallet-standard-util` перевіряє
лише звичайні вихідні дані SIWS. Коли `signedMessageFormat` вказує на off-chain
повідомлення, `signedMessage` є off-chain повідомленням, вмістом якого є текст
SIWS. Відтворіть очікуваний текст зі збережених вхідних даних та адреси
підписанта за допомогою `createSignInMessageText` з
`@solana/wallet-standard-util`, а потім перевірте його як будь-яке інше off-chain
повідомлення, як описано в розділі
[Перевірка підпису на вашому сервері](#verify-the-signature-on-your-server). Цей процес у Kit описано в
[README `@solana/offchain-messages`](https://github.com/anza-xyz/kit/tree/main/packages/offchain-messages#verifying-a-signed-offchain-message).

## Для гаманців

Гаманці додають підтримку, реалізуючи можливість Wallet Standard
`solana:signOffchainMessage` з `@solana/wallet-standard-features`:

- Вкажіть `version: "1.0.0"` і перелічіть версії повідомлень, які ви можете
  підписувати, в `supportedMessageVersions`. Наразі це `[1]`.
- Сформуйте преамбулу версії 1 на основі `requiredSigners`, який ви відсортуєте та перевірите
  на дублікати. Відхиліть запит, якщо акаунт не входить до числа обов’язкових
  підписантів.
- Повністю покажіть текст повідомлення користувачеві перед підписанням, зокрема й на
  апаратних пристроях.
- Поверніть точні байти, які ви підписали, як `signedOffchainMessage` разом з
  підписом Ed25519 `signature`.
- Щоб підтримувати офчейн-версію Sign In With Solana, повідомляйте `version: "1.1.0"` для
  `solana:signIn`. Якщо вхідні дані містять `useOffchainMessage`, підпишіть текст SIWS
  як офчейн-повідомлення версії 1, поверніть його байти як `signedMessage`
  і задайте `signedMessageFormat`.
- Надалі підтримуйте `solana:signMessage`. Він не змінився, і застосунки досі використовують
  його як резервний варіант.
