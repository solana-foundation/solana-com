`SettleDvp` підписує розрахунковий орган, указаний у записі угоди. В одній
транзакції інструкція переказує `amount_a` зі сторони активу на адресу
призначення учасника грошової сторони та `amount_b` з грошової сторони на адресу
призначення учасника сторони активу, повертає учаснику відповідної сторони будь-який
зайвий залишок в ескроу та закриває запис і обидва ескроу. Якщо будь-який із цих
переказів не може завершитися, інструкція завершується помилкою, і жодних
переміщень не відбувається.

Ця сторінка продовжує матеріали [«Створення угоди»](/docs/defi/dvp-program/create-a-trade)
та [«Фінансування сторін угоди»](/docs/defi/dvp-program/fund-the-legs); клієнт, підписанти,
`trade` і token accounts учасників переходять звідти.

## Повторна перевірка перед підписанням

Розрахунковий орган підписує транзакцію, яка переміщує обидві сторони угоди, тому
перед підписанням він виконує те саме зчитування, що й кожен учасник: власник, розмір, учасники,
mint-акаунти, суми, строк дії та обидві адреси призначення (див.
[«Фінансування сторін угоди»](/docs/defi/dvp-program/fund-the-legs#verify-the-terms)). Сама
програма під час розрахунку повторно перевіряє, що кожен mint досі належить до token
program, записаної під час створення, не містить заблокованого розширення і має
той самий mint authority, що й на момент створення угоди. Тому mint, відтворений із заблокованим
розширенням, іншою token program або іншим mint authority, не може
брати участі в розрахунку.

## Створення акаунтів отримувачів

Settle записує дані в чотири token accounts, які програма не створює:

| Акаунт                | Отримує                     | Власник                           |
| ---------------------- | ---------------------------- | ------------------------------- |
| `userADestinationAtaB` | Грошову сторону (`amount_b`)    | `user_a_settlement_destination` |
| `userBDestinationAtaA` | Сторону активу (`amount_a`)   | `user_b_settlement_destination` |
| `userAAtaA`            | Будь-який залишок на стороні активу | `user_a`                        |
| `userBAtaB`            | Будь-який залишок на грошовій стороні  | `user_b`                        |

Акаунти для залишків використовуються лише тоді, коли в ескроу лежить більше за узгоджену
суму, але будь-хто, хто має mint, може створити такий залишок, надіславши кілька базових
одиниць в ескроу. Якщо акаунта для повернення не існує, уся інструкція Settle
завершується помилкою, тому створіть усі чотири ідемпотентно в тій самій транзакції.

    import {
      findAssociatedTokenPda,

    const destinationA = t.userASettlementDestination; // defaults to userA
    const destinationB = t.userBSettlementDestination; // defaults to userB

    const [userADestinationAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: destinationA,
      tokenProgram: tokenProgramB,
    });
    const [userBDestinationAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: destinationB,
      tokenProgram: tokenProgramA,
    });
    // userAAtaA and userBAtaB are from fund the legs.

    const createRecipientAccounts = [
      { ata: userADestinationAtaB, owner: destinationA, mint: mintB, tokenProgram: tokenProgramB },
      { ata: userBDestinationAtaA, owner: destinationB, mint: mintA, tokenProgram: tokenProgramA },
      { ata: userAAtaA, owner: userA, mint: mintA, tokenProgram: tokenProgramA },
      { ata: userBAtaB, owner: userB, mint: mintB, tokenProgram: tokenProgramB },

      getCreateAssociatedTokenIdempotentInstruction({
        payer: authoritySigner,
        ata,
        owner,
        mint,
        tokenProgram,
      }),

## Розрахунок

`legAExtrasCount` повідомляє програмі, скільки з акаунтів, доданих після
фіксованого списку, належать до transfer hook сторони активу; решта належать до
gрошової сторони. Для mint-акаунтів без transfer hooks передайте нуль і нічого не додавайте. Акаунт
програми memo (program account) обов’язковий для інструкції й використовується лише для адрес призначення,
що вимагають memo.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { MEMO_PROGRAM_ADDRESS } from "@solana-program/memo";
    import { getSettleDvpInstruction } from "./dvp";

    const settleInstruction = getSettleDvpInstruction({
      settlementAuthority: authoritySigner,
      swapDvp,
      mintA,
      mintB,
      dvpAtaA: escrowA,
      dvpAtaB: escrowB,
      userADestinationAtaB,
      userBDestinationAtaA,
      userAAtaA,
      userBAtaB,
      tokenProgramA,
      tokenProgramB,
      memoProgram: MEMO_PROGRAM_ADDRESS,
      legAExtrasCount: 0,
    });

    const { context: settleContext } = await client.sendTransaction([
      ...createRecipientAccounts,
      settleInstruction,
    ]);
    const settleSignature = settleContext.signature;
    console.log("Submitted:", settleSignature);

    // sendTransaction returns at the client's commitment (confirmed by default).
    // Wait for finalized before recording the trade as settled.
    let finalized = false;
    for (let attempt = 0; attempt < 30 && !finalized; attempt++) {
      const {
        value: [status],
      } = await client.rpc.getSignatureStatuses([settleSignature]).send();
      if (status?.err) {
        throw new Error("Settle transaction failed");
      }
      finalized = status?.confirmationStatus === "finalized";
      if (!finalized) {
        await new Promise((resolve) => setTimeout(resolve, 2_000));
      }
    }
    if (!finalized) {
      // A closed record means it settled; an open one is safe to settle again.
      throw new Error("Settle not finalized after 60s; read the trade record");
    }
    console.log("Settled:", settleSignature);
    ```

### Transfer hooks

Згенерований IDL перелічує лише фіксовані акаунти, тож згенеровані білдери
не знають про акаунти hook. Визначте додаткові account metas кожного hook mint
так само, як для прямого переказу цього токена, а потім додайте їх до
інструкції: спочатку акаунти сторони активу, потім грошової сторони, а
`legAExtrasCount` має дорівнювати кількості в першій групі. У TypeScript розгорніть
визначені metas у масив `accounts` інструкції; у Rust використовуйте
`add_remaining_accounts` у білдері. Ліміт становить 32 акаунти на сторону,
у тому числі програма hook і акаунт валідації; ліміт акаунтів у транзакції
може спрацювати раніше, коли hooks є в обох сторін. Програма видаляє прапорець підписанта
з кожного переданого акаунта, тож hook не може отримати підпис розрахункового
органу цим шляхом.

## Фіксація результату

Вважайте угоду розрахованою, коли транзакція Settle досягає статусу `finalized`.
Після розрахунку запису й обох ескроу більше не існує, тож система, якій згодом потрібні
умови, зберігає їх зі зчитування перед розрахунком або з транзакції, що створила угоду.
Rent закритих акаунтів перейшов до розрахункового органу.

## Помилки розрахунку

`LegNotFunded` означає, що в ескроу менше за узгоджену суму; `DvpExpired`
і `SettlementTooEarly` означають, що часове вікно пропущено; `MintAuthorityChanged`
і `BlockedMintExtension` означають, що mint змінився після створення;
`RecipientAtaMismatch` означає, що token account призначення або повернення відсутній чи
більше не належить очікуваному власнику та mint, зазвичай через те, що крок
створення акаунтів, описаний вище, було пропущено. У кожному з цих випадків нічого не переміщено, і
учасники можуть скасувати угоду з урахуванням повноважень mint (див.
[«Скасування угоди»](/docs/defi/dvp-program/unwind-a-trade)).
