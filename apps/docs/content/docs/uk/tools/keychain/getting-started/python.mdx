Версія 2.0 — це перший стабільний випуск пакета Python.
[Посібник із міграції на 2.0](https://github.com/solana-foundation/solana-keychain/blob/main/docs/MIGRATING_V2.md)
описує схеми підпису, спільні з Rust і TypeScript.

## Встановлення

Встановіть базовий пакет і по одному додатковому пакету (extra) для кожного бекенду, якому потрібна залежність від провайдера:

```shell
pip install solana-keychain                # memory, vault and para
pip install 'solana-keychain[aws-kms]'     # AWS KMS (boto3)
pip install 'solana-keychain[gcp-kms]'     # GCP KMS (google-cloud-kms)
pip install 'solana-keychain[privy]'       # Privy
pip install 'solana-keychain[turnkey]'     # Turnkey
pip install 'solana-keychain[fireblocks]'  # Fireblocks
pip install 'solana-keychain[cdp]'         # Coinbase Developer Platform
pip install 'solana-keychain[crossmint]'   # Crossmint
pip install 'solana-keychain[dfns]'        # Dfns
pip install 'solana-keychain[openfort]'    # Openfort
pip install 'solana-keychain[utila]'       # Utila
pip install 'solana-keychain[fordefi]'     # Fordefi

# Several at once
pip install 'solana-keychain[aws-kms,privy]'
```

Потрібен Python 3.10 або новіший. Транзакції — це об'єкти
[`solders`](https://pypi.org/project/solders/) `VersionedTransaction`;
приймаються повідомлення legacy, v0 і v1, окрім Fireblocks із
`use_program_call=True`, який приймає лише legacy і v0.

Memory, Vault і Para можна імпортувати з кореня пакета. Усі інші бекенди
імпортуються з власних підмодулів (наприклад, `solana_keychain.aws_kms`), а
імпорт без відповідного extra спричиняє `ImportError` із назвою extra, який
потрібно встановити. Ledger підтримується лише в Rust.

## Базове використання

Кожен бекенд має dataclass конфігурації та асинхронну фабрику `create_<backend>_signer`,
яка повертає готовий до використання підписувач. Усі методи підпису є корутинами:

```python
import asyncio

from solana_keychain import MemorySigner
from solders.transaction import VersionedTransaction


async def sign(transaction: VersionedTransaction) -> str:
    signer = MemorySigner.from_private_key_file("/path/to/id.json")
    print("Signing with:", signer.pubkey)

    # Check availability (useful for remote signers)
    if not await signer.is_available():
        raise RuntimeError("Signer offline")

    result = await signer.sign_transaction(transaction)
    print("Signature:", result.signature)
    print("Fully signed:", result.is_complete)
    return result.encoded_transaction  # base64 wire transaction
```

`sign_transaction` повертає `SignedTransaction` із полями `encoded_transaction`,
`signature`, `is_complete` і `transaction`. `transaction` — це авторитетна
підписана транзакція: продовжуйте роботу саме з нею, особливо у випадку підписувача з модифікацією, результат якого є іншим об'єктом, ніж той, що ви передали.

### Уніфікована фабрика

`create_keychain_signer` приймає назву бекенду та dataclass конфігурації цього бекенду
і імпортує бекенд ліниво, тож встановити потрібно лише ті extras, які ви
використовуєте:

```python
from solana_keychain import create_keychain_signer
from solana_keychain.privy import PrivySignerConfig

signer = await create_keychain_signer(
    "privy",
    PrivySignerConfig(
        app_id="your-app-id",
        app_secret="your-app-secret",
        wallet_id="your-wallet-id",
    ),
)
```

Назви перелічено в `SUPPORTED_BACKENDS`: `aws-kms`, `cdp`, `crossmint`,
`dfns`, `fireblocks`, `fordefi`, `gcp-kms`, `memory`, `openfort`, `para`,
`privy`, `turnkey`, `utila` і `vault`. Невідома назва або конфігурація
неправильного класу спричиняє `SignerError` із `SignerErrorCode.CONFIG_ERROR`.
Фабрика типізована як така, що повертає базовий `SolanaSigner`, тому перед підписом звузьте тип за допомогою
`isinstance` (див. [Можливості підписувачів](#signer-capabilities)).

### Віддалені HTTP-клієнти

Віддалені HTTP-бекенди приймають необов'язковий `http_client` (`httpx.AsyncClient`)
для власного TLS або проксі. Якщо його не задано, кожен запит використовує одноразовий клієнт
із тайм-аутом 60 секунд, примусовим HTTPS для базової URL-адреси та відхиленням
переадресацій.

## Можливості підписувачів

Кожен бекенд є підкласом ABC `SolanaSigner` (`pubkey`, `sign_message`,
`is_available`) плюс рівно один клас можливостей:

- `TransactionSigner`: `sign_transaction(tx)` підписує вашу транзакцію на місці
  та повертає `SignedTransaction`. Транзакцію надсилаєте ви.
- `ModifyingSigner`: `modify_and_sign_transaction(tx)` дозволяє провайдеру переписати
  транзакцію, а потім підписує її без надсилання в мережу. Ваш об'єкт залишається
  незмінним; продовжуйте з повернутого `SignedTransaction.transaction`.
- `SendingSigner`: `sign_and_send_transaction(tx)` підписує та надсилає в мережу через
  провайдера й повертає `Signature` транзакції, що потрапила в блокчейн. Вашу
  транзакцію ніколи не змінюють.

| Бекенд                                                                           | Клас можливостей    | `sign_message`                                  |
| --------------------------------------------------------------------------------- | ------------------- | ----------------------------------------------- |
| memory, vault, privy, turnkey, aws-kms, fireblocks, gcp-kms, dfns, para, openfort | `TransactionSigner` | Так                                             |
| cdp                                                                               | `TransactionSigner` | Лише дані в UTF-8, інакше `SERIALIZATION_ERROR` |
| utila                                                                             | `TransactionSigner` | Викликає помилку `SIGNING_FAILED`                         |
| fordefi «чорна скринька» (`FordefiBlackBoxSigner`)                                       | `TransactionSigner` | Так                                             |
| fordefi нативний ручний режим (`FordefiNativeManualSigner`)                               | `ModifyingSigner`   | Так                                             |
| fordefi нативний автоматичний режим (`FordefiNativeAutoSigner`)                                   | `SendingSigner`     | Так                                             |
| crossmint                                                                         | `SendingSigner`     | Викликає помилку `SIGNING_FAILED`                         |

Звужуйте тип за допомогою `isinstance`. Усі класи можливостей експортуються з кореня
пакета:

```python
from solana_keychain import ModifyingSigner, SendingSigner, TransactionSigner

if isinstance(signer, SendingSigner):
    signature = await signer.sign_and_send_transaction(transaction)
elif isinstance(signer, ModifyingSigner):
    result = await signer.modify_and_sign_transaction(transaction)
elif isinstance(signer, TransactionSigner):
    result = await signer.sign_transaction(transaction)
```

### Ініціалізація

Фабрики `create_*` і `create_keychain_signer` виконують усе необхідне налаштування
за вас. Якщо ви створюєте клас підписувача Privy, Fireblocks, Dfns, Crossmint, Para, Openfort або
Utila напряму, викличте `await signer.init()` перед використанням. До цього
`pubkey` і кожен виклик підпису спричиняють `SignerErrorCode.NOT_INITIALIZED`.

## Конфігурація бекендів

### Memory

Створюйте з файлу keypair Solana CLI, рядка base58 або `"[1,2,...]"`, сирих
байтів чи `Keypair` з `solders`:

```python
from solana_keychain import MemorySigner, MemorySignerConfig, create_memory_signer
from solders.keypair import Keypair

signer = MemorySigner.from_private_key_file("/path/to/id.json")
signer = MemorySigner.from_private_key_string("base58_private_key")
signer = MemorySigner.from_bytes(secret_key_bytes)  # 64 or 32 bytes
signer = await create_memory_signer(MemorySignerConfig(keypair=Keypair()))
```

Ключ зберігається в пам'яті процесу, і Python не може його занулити. Використовуйте цей бекенд
для розробки та тестування.

### HashiCorp Vault

Ключ має бути ключем ed25519 у рушії transit. Звичайний HTTP допускається
лише для loopback-адреси, для `vault server -dev`:

```python
from solana_keychain import VaultSignerConfig, create_vault_signer

signer = await create_vault_signer(
    VaultSignerConfig(
        api_base_url="https://vault.example.com:8200",
        token="hvs.xxxxx",
        key_name="my-solana-key",
        public_key="base58_public_key",
    )
)
```

### AWS KMS

`key_id` — це ідентифікатор ключа, ARN або псевдонім ключа `ECC_NIST_EDWARDS25519`. Передайте
готовий клієнт boto3 KMS `client` для власних облікових даних або кінцевих точок; `region`
тоді ігнорується:

```python
from solana_keychain.aws_kms import AwsKmsSignerConfig, create_aws_kms_signer

signer = await create_aws_kms_signer(
    AwsKmsSignerConfig(
        key_id="alias/my-solana-key",
        public_key="base58_public_key",
        region="us-east-1",  # optional, defaults to the AWS config chain
    )
)
```

### GCP KMS

Версія ключа має бути ключем `EC_SIGN_ED25519`. `client` за потреби приймає
готовий `KeyManagementServiceAsyncClient`:

```python
from solana_keychain.gcp_kms import GcpKmsSignerConfig, create_gcp_kms_signer

signer = await create_gcp_kms_signer(
    GcpKmsSignerConfig(
```

```python
        public_key="base58_public_key",
    )
)
```

### Fireblocks

```python
from solana_keychain.fireblocks import FireblocksSignerConfig, create_fireblocks_signer

signer = await create_fireblocks_signer(
    FireblocksSignerConfig(
        api_key="api_key",
        private_key_pem="-----BEGIN RSA PRIVATE KEY-----\n...",
        vault_account_id="0",
        asset_id="SOL",  # or "SOL_TEST" for devnet
    )
)
```

`use_program_call=True` підписує операцією PROGRAM_CALL замість RAW. Запит
надсилається лише для підпису, тож Fireblocks не переписує і не надсилає
транзакцію в мережу, а ви надсилаєте її як зазвичай. Потрібен гарячий гаманець, і цю опцію
має ввімкнути для вашого workspace Fireblocks.

### Crossmint

```python
from solana_keychain.crossmint import CrossmintSignerConfig, create_crossmint_signer

signer = await create_crossmint_signer(
    CrossmintSignerConfig(
        api_key="api_key",
        wallet_locator="wallet_locator",
    )
)

signature = await signer.sign_and_send_transaction(transaction)
```

Crossmint лише надсилає транзакції. Його API завжди виконує схвалену транзакцію
на стороні сервера та спонсорує gas, тому `CrossmintSigner` є `SendingSigner`, а
`sign_message` викликає `SIGNING_FAILED`. Повернутий підпис ідентифікує
транзакцію, яку Crossmint відправив у мережу, і вона може відрізнятися від вашої. Налаштування
`signer_secret` (секрету делегованого підписувача `xmsk1_...`) схвалює транзакції
автоматично, що делегує Crossmint вибір того, що саме схвалюється.

### Fordefi

Fordefi має три режими підпису, які визначаються під час створення параметрами `chain` і
`push_mode`. `create_fordefi_signer` обирає клас, кожен клас відхиляє
конфігурацію, призначену для іншого, і всі три підписують повідомлення:

| Режим          | Конфігурація                                     | Клас                       | Метод                        |
| ------------- | ------------------------------------------ | --------------------------- | ----------------------------- |
| Чорна скринька     | `chain` не задано                              | `FordefiBlackBoxSigner`     | `sign_transaction`            |
| Нативний авторежим   | `chain` задано, `push_mode` не задано або `"auto"` | `FordefiNativeAutoSigner`   | `sign_and_send_transaction`   |
| Нативний ручний режим | `chain` задано, `push_mode="manual"`          | `FordefiNativeManualSigner` | `modify_and_sign_transaction` |

API-запити автентифікуються підписом запиту ECDSA P-256: передайте
ключ як `private_key_pem` або зберігайте його в KMS/HSM, передавши підклас
`FordefiRequestSigner` як `request_signer`.

**Нативний авторежим**: задайте `chain` (`"solana_devnet"` або `"solana_mainnet"`), і
Fordefi може замінити blockhash та комісії, після чого сам підписує й надсилає
транзакцію в мережу. Він приймає лише непідписану транзакцію, єдиним обов'язковим
підписувачем якої є vault. `fee` передається до Fordefi без змін:

```python
import os

from solana_keychain.fordefi import FordefiSignerConfig, create_fordefi_signer

signer = await create_fordefi_signer(
    FordefiSignerConfig(
        access_token=os.environ["FORDEFI_ACCESS_TOKEN"],
        vault_id=os.environ["FORDEFI_VAULT_ID"],
        public_key=os.environ["FORDEFI_PUBLIC_KEY"],  # vault address (base58)
        private_key_pem=open("./secret/private.pem").read(),
        chain="solana_devnet",
        fee={"type": "custom", "priority_fee": "1000"},  # optional
    )
)

signature = await signer.sign_and_send_transaction(transaction)
```

**Нативний ручний режим**: задайте `chain` і `push_mode="manual"`. Fordefi переписує
повідомлення (recent blockhash, інструкції комісії Compute Budget) і підписує його,
але не надсилає в мережу. Повернута транзакція замінює ту, яку ви надіслали,
тому завжди продовжуйте з `result.transaction`. Fordefi має бути платником комісії та
має підписувати раніше за будь-якого іншого обов'язкового підписувача: транзакція, що вже містить
підписи, приймається, але перезапис їх анулює. Перезапис не показується у вигляді diff,
тому перевірте результат перед надсиланням і надсилайте оперативно, оскільки Fordefi
не повертає висоту закінчення терміну дії нового blockhash.

```python
signer = await create_fordefi_signer(
    FordefiSignerConfig(
        access_token=os.environ["FORDEFI_ACCESS_TOKEN"],
        vault_id=os.environ["FORDEFI_VAULT_ID"],
        public_key=os.environ["FORDEFI_PUBLIC_KEY"],
        private_key_pem=open("./secret/private.pem").read(),
        chain="solana_devnet",
        push_mode="manual",
    )
)

result = await signer.modify_and_sign_transaction(transaction)
...  # inspect result.transaction, then add any remaining signatures
```

Надішліть перевірену транзакцію, як описано в [Підпис і надсилання](#sign-and-send), і
узгодьте стан перед повторною спробою, якщо надсилання не вдалося.

**Режим «чорна скринька»**: не вказуйте `chain`. Fordefi підписує точні байти вашого повідомлення
і не надсилає його в мережу. Використовуйте його з vault Fordefi «чорна скринька».

```python
signer = await create_fordefi_signer(
    FordefiSignerConfig(
        access_token=os.environ["FORDEFI_ACCESS_TOKEN"],
        vault_id=os.environ["FORDEFI_BB_VAULT_ID"],
        public_key=os.environ["FORDEFI_BB_PUBLIC_KEY"],
        private_key_pem=open("./secret/private.pem").read(),
    )
)
```

## Підпис і надсилання

`sign_and_send_transaction` доставляє транзакцію в блокчейн незалежно від типу
підписувача. `SendingSigner` надсилає через свого провайдера, а ваша функція
надсилання ніколи не викликається. `TransactionSigner` або `ModifyingSigner` підписує, а ваша функція
надсилання передає в мережу результат у кодуванні base64 (пакет не має RPC-клієнта):

```python
import httpx
from solana_keychain import sign_and_send_transaction
from solders.signature import Signature


async def send(encoded: str) -> Signature:
    async with httpx.AsyncClient() as client:
        response = await client.post(
            "https://api.devnet.solana.com",
            json={
                "jsonrpc": "2.0",
                "id": 1,
                "method": "sendTransaction",
                "params": [encoded, {"encoding": "base64"}],
            },
        )
    return Signature.from_string(response.json()["result"])


signature = await sign_and_send_transaction(signer, transaction, send)
```

Підписувач лише для підпису без функції надсилання спричиняє `CONFIG_ERROR`, а
транзакція, у якій після підпису все ще бракує підписів, спричиняє `SIGNING_FAILED`.

## Обробка помилок

Кожна помилка — це `SignerError` зі стабільним `code` з `SignerErrorCode`:
`BROADCAST_UNCONFIRMED`, `CONFIG_ERROR`, `EXPECTED_SOLANA_SIGNER`, `HTTP_ERROR`,
`INVALID_PRIVATE_KEY`, `INVALID_PUBLIC_KEY`, `IO_ERROR`, `NOT_AVAILABLE`,
`NOT_INITIALIZED`, `OTHER`, `PARSING_ERROR`, `REMOTE_API_ERROR`,
`SERIALIZATION_ERROR` і `SIGNING_FAILED`. Орієнтуйтеся на `code`, а не на повідомлення:
`str()` і `repr()` містять лише фіксоване загальне повідомлення, ніколи не ключові матеріали чи
сирі відповіді провайдера. `status_code` і `provider_error_code` задаються, коли
помилка надійшла у відповіді провайдера.

`SignerErrorCode.BROADCAST_UNCONFIRMED` (`"SIGNER_BROADCAST_UNCONFIRMED"`) означає,
що транзакція, можливо, потрапила в блокчейн:

- У Crossmint і Fordefi в нативному авторежимі `provider_transaction_id` задається, коли
  створення було прийнято, а `idempotency_key` містить ключ, отриманий із
  повідомлення, з яким було надіслано запит на створення. Повторне надсилання побайтово ідентичної
  транзакції безпечне; перебудована (наприклад, з новим blockhash) — це новий
  переказ.
- У `sign_and_send_transaction` помилка функції надсилання викликає її з
  `transaction_signature`, заданим як підпис завершеної транзакції.
- Fireblocks викликає її лише тоді, коли опитування показує, що Fireblocks надіслав у мережу
  транзакцію `use_program_call`, попри те що її було відправлено лише для підпису.

```python
from solana_keychain import SignerError, SignerErrorCode

try:
    signature = await sign_and_send_transaction(signer, transaction, send)
except SignerError as error:
    if error.code is SignerErrorCode.BROADCAST_UNCONFIRMED:
        reconcile(
            error.provider_transaction_id,
            error.idempotency_key,
            error.transaction_signature,
        )
    raise
```

Скасований виклик повторно генерує `asyncio.CancelledError`, який не містить полів. Щоб
відновити ідентифікатор, який провайдер прийняв до скасування, передайте
`PendingTransactionId()` (з `solana_keychain.core`) як `pending_transaction_id` у конфігурації Crossmint або
Fordefi в нативному авторежимі та прочитайте `.get()` після
скасування. Звіртеся з провайдером перед повторною спробою.

Keychain перевіряє етап підпису, а не те, що робить транзакція: підпис, повернений
провайдером, перевіряється за ed25519 щодо локально обчисленого
повідомлення, перш ніж його буде додано. Python не може занулити буфери ключів, тому з
бекендами з локальними ключами (Memory, а також API-ключі та PEM, що зберігаються в конфігураціях віддалених бекендів)
вважайте всю пам'ять процесу чутливою. Дивіться
[модель безпеки](https://github.com/solana-foundation/solana-keychain/blob/main/docs/SECURITY_MODEL.md),
щоб дізнатися, що гарантує кожна схема підпису.

## Додавання власних підписувачів

Створіть підклас того єдиного класу можливостей, який відповідає вашому бекенду (`TransactionSigner`,
`ModifyingSigner` або `SendingSigner`), із `solana_keychain.core`. Щоб інтегрувати
додаткові сервіси керування ключами, перегляньте [посібник із додавання підписантів](/docs/tools/keychain/adding-signers).
