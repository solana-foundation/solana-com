Цей посібник призначений для провайдерів гаманців та розробників, які хочуть
інтегрувати нові рішення для керування ключами в бібліотеку `solana-keychain`.
Додавши вашу реалізацію підписувача, ви дозволите розробникам використовувати
ваш сервіс для безпечного підписання транзакцій Solana через уніфікований
інтерфейс.

Keychain підтримує реалізації на Rust, TypeScript, Python і Go на однаковому рівні.
PR, що містять усі чотири реалізації, мають значну перевагу. Якщо ви можете додати лише
одну, це нормально, але очікуйте, що решту доведеться додати до того, як підписувач потрапить
у реліз.

_Використовуєте Claude Code? [Навичка `add-signer-ci`](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)
з репозиторію налаштовує CI-воркфлоу для нового підписувача, доданого через PR із форка._

## Огляд архітектури

Бібліотека використовує архітектуру на основі трейтів, визначену в `src/traits.rs`. Кожен
підписувач реалізує базовий трейт `SolanaSigner` (`pubkey`, `sign_message`,
`is_available`) плюс рівно один трейт можливостей, що відповідає особливостям провайдера:

- `TransactionSigner` (`sign_transaction`): провайдер підписує байти, надані
  викликачем, а викликач сам їх розповсюджує в мережу. Більшість бекендів.
- `ModifyingSigner` (`modify_and_sign_transaction`): провайдер змінює
  транзакцію, а потім підписує її без розповсюдження в мережу.
- `SendingSigner` (`sign_and_send_transaction`): провайдер підписує та
  розповсюджує транзакцію на боці сервера.

Бібліотека також надає уніфікований enum `Signer`, що обгортає всі
реалізації та дає змогу вибирати бекенд підписування під час виконання. Він реалізує
лише базовий трейт; до можливостей можна дістатися через `as_transaction_signer()`,
`as_modifying_signer()` та `as_sending_signer()`.

## Швидкий чеклист інтеграції

- Створіть модуль вашого підписувача з реалізацією
- Реалізуйте базовий трейт `SolanaSigner` (`pubkey`, `sign_message`,
  `is_available`) плюс один трейт можливостей, що відповідає особливостям вашого провайдера
  (зазвичай `TransactionSigner`)
- Додайте feature flag у `Cargo.toml`, включно з внутрішнім маркером `_remote`, якщо
  ваш підписувач використовує reqwest
- Оновіть enum `Signer` у `src/lib.rs` (варіант, гілка `dispatch_signer!` та
  гілка в акцесорі можливостей, що відповідає вашому типу)
- Забезпечте HTTPS та налаштуйте тайм-аути для HTTP-клієнтів
- Підпишіть байти повідомлення та перевірте отриманий підпис, перш ніж додавати його
- Додайте повний набір модульних тестів (на основі wiremock, у вашому модулі)
- Додайте файл інтеграційних тестів та оновіть `.env.example`
- Додайте реалізації на TypeScript, Python і Go
- Оновіть документацію
- Оновлення CI-воркфлоу (узгоджуйте з мейнтейнерами, див.
  [Оновлення CI-воркфлоу](#ci-workflow-updates-fork-prs))
- Надішліть PR

## Крок 2: Визначте структуру вашого підписувача

У `src/your_service/mod.rs` визначте структуру вашого підписувача:

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,
}

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## Крок 3: Реалізуйте конструктор та допоміжні методи

Віддалені підписувачі **повинні** забезпечувати HTTPS та налаштовувати тайм-аути
HTTP. Використовуйте спільну структуру `HttpClientConfig` для налаштувань
тайм-аутів.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## Крок 4: реалізуйте трейти підписувача

Базовий трейт `SolanaSigner` має 2 асинхронні методи (`sign_message`,
`is_available`) плюс `pubkey()`. Підписування транзакцій винесено в трейт можливостей;
більшість провайдерів реалізують `TransactionSigner`, чий `sign_transaction` повертає
`SignTransactionResult` (позначений enum, що вказує, чи транзакцію підписано повністю,
чи частково).

Підписуйте байти повідомлення, а не всю транзакцію в мережевому форматі, і перевіряйте
підпис провайдера щодо них, перш ніж додавати його. Для підписування та серіалізації використовуйте спільні
допоміжні функції `TransactionUtil`.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

Якщо ваш провайдер змінює транзакцію перед підписуванням, реалізуйте натомість
`ModifyingSigner` і повністю замініть транзакцію викликача на
байти від провайдера. Якщо він розповсюджує транзакцію на боці сервера, реалізуйте `SendingSigner`
і залиште транзакцію викликача без змін. Ніколи не реалізуйте можливість, яку
ваш провайдер не може забезпечити.

## Крок 6: Додайте прапорець функції

Оновіть `Cargo.toml`, додавши свого підписувача як необов'язкову feature. Віддалені бекенди
включають внутрішній маркер `_remote`, який керує реалізацією `From<reqwest::Error>`
у `src/error.rs`; без нього `?` на викликах reqwest не скомпілюється, якщо ввімкнено лише
вашу feature.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## Крок 7: Оновіть перерахування підписувачів

Додайте свого підписувача до `src/lib.rs`. Базова реалізація `SolanaSigner` диспетчеризує через
макрос `dispatch_signer!`, тож додайте туди одну гілку. Доступ до можливостей зосереджено в
акцесорах `as_transaction_signer()`, `as_modifying_signer()` та `as_sending_signer()`:
додайте гілку `Some(s)` до того, що відповідає вашому трейту можливостей (а для
бекенда, що розповсюджує або змінює транзакції, ще й гілку `None` в `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## Крок 8: Додайте повні тести

Додайте тести до вашого модуля (в кінці `src/your_service/mod.rs`):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

Також покрийте помилку перевірки підпису: змокована відповідь, підпис у якій
не проходить перевірку, має повертати помилку.

## Крок 9: додайте інтеграційні тести

Створіть `rust/src/tests/test_<name>_integration.rs`. Інтеграційні тести виконуються
проти реального API сервісу (не wiremock) і закриті за feature
`integration-tests`. Кожен файл має містити:

- оголошення `pub const` для назв змінних середовища
- допоміжну функцію `get_signer()`, що читає змінні середовища через `dotenvy`
- Три тестові функції: `test_<name>_sign_message`,
  `test_<name>_sign_transaction` та `test_<name>_is_available`
- Feature-гейти: `#[cfg(feature = "your_service")]` на модулі та
  `#[cfg(feature = "integration-tests")]` на кожному тесті

Повний приклад дивіться в `rust/src/tests/test_para_integration.rs`, а свій модуль
оголосіть у `rust/src/tests/mod.rs`:

```rust
pub mod test_your_service_integration;
```

## Тестування вашої інтеграції

Користуйтеся рецептами `just`, а не «сирим» `cargo`. Функції SDK (`sdk-v2`,
`sdk-v3`, `sdk-v4`) взаємовиключні, тому `cargo test --all-features`
завершується помилкою.

```bash
# Unit tests across the sdk-v2, sdk-v3 and sdk-v4 matrices

# Live integration tests (require credentials in .env)
just rust-test-integration
```

## Оновлення CI-воркфлоу (PR із форків)

CI — це двофазний процес. Узгодьте з мейнтейнерами підготовку `main`, перш ніж
ваш PR можна буде протестувати: вони оновлюють `fork-external-live-manual.yml`, додають змінні середовища
до `ci.yml` та налаштовують GitHub Secrets.

Ваш PR має включати ці зміни фази 2 разом із кодом вашого підписувача:

- **`ci.yml`**: додайте свою Rust feature до матриці `backend` (перед `all`) та
  свою функцію інтеграційного тесту до матриці `test`
- **`typescript-ci.yml`**: додайте свій пакет до матриць модульних та інтеграційних
  тестів і додайте змінні середовища до кроку інтеграційних тестів
- **`typescript-publish.yml`**: додайте свій пакет до `PUBLISH_PACKAGES`, масиву
  `packages` у GitHub Release та підсумкової таблиці
- **`python-ci.yml`**: додайте бекенд до гейтингу `CI_SIGNER_*` у
  `resolve-signers` та до інтеграційної матриці
- **`go-ci.yml`**: додайте бекенд до гейтингу `CI_SIGNER_*` та до
  `moduleBySigner`

## Підписувач TypeScript

Якщо ви також додаєте пакет підписувача TypeScript, створіть його в
`typescript/packages/your-signer/`. Ключові шаблони:

- Фабрична функція `createYourSigner()` повертає
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>`; тримайте клас
  підписувача внутрішнім і експортуйте лише фабрику та тип її конфігурації
- Експортувати інтерфейс конфігурації (`YourSignerConfig`)
- Якщо ваш бекенд не вміє підписувати повідомлення, не додавайте `SolanaMessageSigner` і не відкривайте жодного
  методу `signMessages`: Kit класифікує підписувачів за наявністю методів, тому
  заглушка, що викидає помилку, призведе до хибної класифікації підписувача
- Примусово вимагайте HTTPS у конфігураційних полях `apiBaseUrl` за допомогою `assertHttpsUrl()` з
  `@solana/keychain-core`
- Виконуйте віддалені виклики через `fetchSignerJson()` з `@solana/keychain-core`,
  який відповідає за мапінг помилок, санітизацію відповідей, відхилення редиректів і
  таймаут за замовчуванням
- Санітизуйте будь-який інший текст помилок віддаленого API за допомогою `sanitizeRemoteErrorResponse()`
  з `@solana/keychain-core`
- Використовувати `throwSignerError(SignerErrorCode.*, { cause, message })` з
  `@solana/keychain-core`
- Враховуйте `config?.abortSignal` у кожному методі підписування, передаючи його до
  `fetchSignerJson()` та `signBatchStaggered()`
- Валідуйте `requestDelayMs` за допомогою `validateRequestDelayMs()` і виконуйте пакетне підписування через
  `signBatchStaggered()`
- Додати `@throws` JSDoc до функцій-фабрик зі списком кодів помилок
- Оголошуйте пакети `@solana/*` як peer-залежності версії `>=8.1.0`
- Модульні тести з vitest і змокованим `fetch`; інтеграційні тести з
  `runSignerIntegrationTest` з `@solana/keychain-test-utils`

### Підписувачі з надсиланням

Якщо ваш провайдер змінює транзакцію або розповсюджує її на боці сервера, його
підпис не можна застосувати до транзакції викликача, тому це має бути
`SolanaSendingSigner`, а не `SolanaTransactionSigner`:

- Реалізуйте `signAndSendTransactions()` і **не** відкривайте `signTransactions`
  (як і `signMessages`, якщо бекенд насправді не підписує повідомлення)
- Враховуйте `config?.abortSignal`. Щойно провайдер прийняв запит на створення, повідомляйте
  про будь-яку помилку (включно зі скасуванням) як `BROADCAST_UNCONFIRMED` з ідентифікатором
  транзакції провайдера, а причину скасування зберігайте як `cause`
- Додайте типізований перевантажений варіант `createKeychainSigner`, що повертає тип вашого підписувача з надсиланням
- Виключіть свій бекенд з `KeychainKitPluginConfig` у
  `typescript/packages/kit-plugin/src/keychain-plugin.ts`, оскільки підписувач
  з надсиланням не може бути `payer` або `identity` клієнта Kit
- Перевіряйте в модульних тестах, що для ваших екземплярів `isTransactionPartialSigner()` повертає false,
  а `isTransactionSendingSigner()` — true

### Оновлення Основного Пакета

Оновіть `typescript/packages/keychain/` (потрібно змінити 7 файлів):

1. `src/types.ts`: додайте `YourSignerConfig` до дискримінованого об'єднання
   `KeychainSignerConfig`
2. `src/create-keychain-signer.ts`: додайте гілку switch (кожен пакет бекенда
   завантажується через динамічний `import()`)
3. `src/resolve-address.ts`: додайте до гілки switch для швидкого шляху або шляху з отриманням адреси
4. `src/index.ts`: додайте експорти типу конфігурації, простору імен і фабричної функції
5. `package.json`: додайте залежність `@solana/keychain-your-signer: "workspace:*"`
6. `tsconfig.json`: додайте посилання `{ "path": "../your-signer" }`
7. `typescript/scripts/test-treeshake-umbrella.mjs`: додайте свій пакет до
   `SIGNER_MARKERS`, а свою фабрику — до `FACTORIES`

Оператори switch мають вичерпні перевірки `never`, тому TypeScript видасть помилку,
якщо ви додасте варіант до об'єднання, але пропустите гілку. Після цього запустіть `just ts-treeshake`:
кожен пакет і зведений пакет мають залишатися придатними до tree-shaking.

## Підписувач на Python

Створіть модуль у `python/src/solana_keychain/your_signer/` (`__init__.py`
плюс `signer.py`). Ключові шаблони:

- Успадкуйте `SolanaSigner` з `solana_keychain.core` (властивість `pubkey`,
  `async sign_message()`, `async is_available()`) плюс рівно один клас можливостей:
  `TransactionSigner` (`async sign_transaction()`), `ModifyingSigner`
  (`async modify_and_sign_transaction()`) або `SendingSigner`
  (`async sign_and_send_transaction()`)
- Експортуйте фабрику `async create_your_signer()`, що очікує `init()`, коли
  бекенд віддалено визначає свою адресу; до ініціалізації підписування викликає
  `SignerErrorCode.NOT_INITIALIZED`
- Експортуйте dataclass конфігурації (`YourSignerConfig`), у якому секрети позначено
  `field(repr=False)`
- Примусово вимагайте HTTPS у полях базового URL за допомогою `assert_https_url()` і спрямовуйте кожен
  запит через `fetch_signer_json()`
- Перевіряйте підпис провайдера, перш ніж повертати його; використовуйте
  `signed_message_bytes()` для байтів, які покриває підпис, і ніколи не додавайте префікс
  версії вручну
- Зареєструйте бекенд у `_BACKENDS` в
  `python/src/solana_keychain/keychain.py`
- Якщо бекенду потрібен SDK провайдера, захистіть імпорт перевіркою, згенеруйте `ImportError`
  із зазначенням `pip install 'solana-keychain[your-signer]'`, оголосіть extra у
  `python/pyproject.toml` і ніколи не імпортуйте бекенд завчасно з кореня
  пакета
- Модульні тести з pytest: `respx` для HTTP-бекендів, заглушки клієнтів для
  SDK-бекендів і перевірка того, що жоден секрет не потрапляє в `str()` або `repr()` згенерованих
  помилок
- Додайте фабрику `make_your_signer()` до
  `python/tests/integration/test_live_signers.py` і зареєструйте її в
  `_MESSAGE_CAPABLE` (або `_TRANSACTION_ONLY` для бекендів без
  `sign_message`)

## Go-підписувач

Кожен Go-бекенд є окремим модулем у `go/signers/yoursigner/` зі шляхом модуля

  кодами, як-от `core.CodeSigningFailed`

  тегом `//go:build integration`

## Поради щодо Реалізації

### Обробка Помилок

Завжди використовуйте наявні варіанти `SignerError`. І `Display`, і `Debug` для
`SignerError` приховують дані, тому робіть повідомлення загальними та ніколи не включайте необроблені дані
відповіді API. Ніколи не використовуйте `.expect()` чи `.unwrap()` для недовірених відповідей API:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### Вимоги безпеки

Це не рекомендації: споживачі обирають бекенд, спираючись саме на них. Якщо
ваш провайдер унеможливлює якусь із них, повідомте про це в PR і в
`docs/SECURITY_MODEL.md` репозиторію.

- **Перевіряйте те, що підписав провайдер.** Обчисліть байти повідомлення локально та
  перевірте за ними повернутий підпис на потрібній для вашого підписувача позиції
  до того, як додавати його. Підпис, що не пройшов перевірку, має призводити до помилки, і його ніколи
  не можна додавати.
- **Вказуйте, чи провайдер транслює транзакції.** Якщо він виконує їх на стороні сервера,
  реалізуйте відправну (sending) модель і повертайте підпис, що ідентифікує
  транзакцію, яка потрапила в мережу. Якщо в провайдера немає кінцевої точки лише для підпису, зробіть
  бекенд лише відправним, а не надсилайте транзакцію за спиною викликача.
- **Ніколи не залишайте викликачу транзакцію, яку підпис не покриває.**
  Провайдер, що переписує транзакцію, підписує власні байти: або залиште
  транзакцію викликача без змін (випадок, коли трансляцією керує провайдер), або застосуйте
  модифікаційну модель і повністю замініть її байтами провайдера.
- **Повідомляйте про невизначеність трансляції як є.** Збій після надсилання все одно міг
  призвести до потрапляння транзакції в мережу. Повертайте `BROADCAST_UNCONFIRMED` замість загальної помилки,
  додавайте ідентифікатор транзакції провайдера, коли він у вас є, і надсилайте
  ключ ідемпотентності, похідний від повідомлення, при кожному створенні, щоб побайтно ідентичне повторне надсилання
  було безпечним.
- **Ніколи не підписуйте до ініціалізації.** Використовуйте `Option<Pubkey>` (а не `Pubkey::default()`) для
  публічного ключа до `init()` і повертайте помилку конфігурації, якщо спробу підпису
  зроблено раніше.
- Ніколи не журналюйте чутливі дані (приватні ключі, секрети API, необроблені відповіді API) і
  використовуйте реалізацію `Debug`, що приховує чутливі поля
- Вимагайте HTTPS (`https_only(true)`, з умовою `#[cfg(not(test))]` для
  wiremock) і налаштовуйте тайм-аути запиту та з'єднання через `HttpClientConfig`
  (за замовчуванням: 30 с/5 с)
- Занулюйте проміжний ключовий матеріал за допомогою `zeroize::Zeroizing<Vec<u8>>`

### Тестування з мок-об'єктами

Використовуйте `wiremock` для імітації HTTP API. Перевіряйте лише тип помилки, а
не текст повідомлення про помилку:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
