---
title: Ресурси для розгортання
description: Підготовка збірки вашої програми до розгортання в Mainnet
---

Перш ніж розгортати застосунок у Mainnet, переконайтеся, що у вас є таке:

- ELF-файл програми — зазвичай результат виконання `anchor build` або
  `cargo-build-sbf`, який має розширення `.so`
- keypair програми — JSON-файл, що містить масив цілих чисел

У цьому розділі ми опишемо, де знайти ці ресурси та як їх підготувати.

## Підготовка ELF-файлу

ELF-файл містить скомпільований байткод, інформацію про структуру пам'яті та
метадані, потрібні віртуальній машині Solana (SVM), щоб зрозуміти, як
завантажити й запустити вашу програму. ELF-файл створюється під час компіляції
вихідного коду.

Щоб створити ELF-файл, для Anchor можна виконати таку команду:

```bash
anchor build
```

або таку для інших фреймворків:

```bash
cargo build-sbf
```

Після цього ELF-файл можна знайти в каталозі на кшталт
`target/deploy/<PROGRAM_NAME>.so`.

Ваша програма готова, коли ELF-файл скомпільовано під
[sBPFv3](https://www.anza.xyz/blog/migrating-solana-programs-to-sbpfv3). Щоб
перевірити програму, виконайте в Linux таку команду:

```bash
readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

А в macOS — такі команди:

```bash
# brew install llvm
$(brew --prefix llvm)/bin/llvm-readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

Якщо ви бачите вивід, подібний до наведеного нижче, програма готова:

```
  Flags:                             0x3
```

Якщо ні, скористайтеся посібником із міграції за посиланням
[тут](https://solana.com/upgrades/sbpfv3-programs).

## Підготовка адреси програми

Адреса вашої програми — це ID програми, який ви використовуватимете для виклику
інструкцій програми. Ви можете: 1) використати keypair програми, згенерований
під час збірки, 2) підібрати новий keypair, адреса якого починається з власного
префікса, або 3) вивести адресу акаунта з базової адреси та seed. Перші два
варіанти створюють keypair, який може підписувати від імені program account.
Акаунт, створений за допомогою seed, не має власного приватного ключа; ним
керує базовий акаунт.

### Використання згенерованого keypair

За замовчуванням `anchor build` і `cargo build-sbf` розміщують keypair програми
тут:

```text
target/deploy/<PROGRAM_NAME>-keypair.json
```

Створіть резервну копію цього файлу, перш ніж очищати каталог збірки. Будь-хто,
хто має доступ до keypair, може підписувати від імені program account, тому не
додавайте його до системи контролю версій.

### Підбір keypair із власним префіксом

Використовуйте [`vanity`](https://github.com/cavemanloverboy/vanity) для пошуку
keypair Ed25519, публічний ключ якого починається із заданого префікса base58.
Встановіть CPU-версію з crates.io:

```bash
cargo install vanity
```

Проєкт також надає збірки CUDA, Metal і OpenCL для пошуку з GPU-прискоренням.
Вимоги до кожного бекенда дивіться в інструкціях зі встановлення `vanity`.

```bash
vanity grind-keypair --pattern Acme...
```

Коли `vanity` знаходить збіг, він виводить публічний ключ, приватне зерно в hex
і JSON-масив keypair, сумісний із Solana. Збережіть JSON-файл у безпечному
місці, а потім переконайтеся, що він містить очікуваний публічний ключ:

```bash
solana-keygen pubkey path/to/keypair.json
```

Ставтеся до виводу команди та збереженого JSON-файлу як до матеріалу приватного
ключа.

### Створення акаунта за допомогою seed

Для швидшого пошуку `vanity grind` шукає seed-рядки для
`CreateAccountWithSeed` замість генерації keypair Ed25519. Вкажіть публічний
ключ базового акаунта, який авторизуватиме створення, власника акаунта та
префікс для пошуку. Для program account з можливістю оновлення використовуйте
BPF-завантажувач з можливістю оновлення як власника:

```bash
vanity grind \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --pattern Acme...
```

Результат містить виведену адресу та seed-рядок. Перевірте їх перед створенням
акаунта:

```bash
vanity verify \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --seed <SEED>
```

Використайте ту саму базову адресу, seed і власника, щоб вивести адресу за
допомогою `Pubkey::create_with_seed`, а потім надішліть інструкцію
`create_account_with_seed` програми System Program. Транзакцію мають підписати
базовий акаунт і акаунт, що надає кошти. Оскільки виведений акаунт не має
окремого keypair, цей варіант потребує процесу створення акаунта та розгортання,
який використовує базовий акаунт, а не файл keypair програми.

### Оновлення адреси програми у вихідному коді

Після вибору keypair або акаунта з seed використовуйте його публічну адресу як
ID програми в усіх місцях, де проєкт її оголошує. Якщо у вихідному коді
залишилася стара адреса, клієнти можуть надсилати інструкції не тій програмі, а
перевірки ID під час виконання можуть завершуватися помилкою.

У робочому просторі Anchor оновіть і запис програми в кореневому `Anchor.toml`,
і виклик `declare_id!` у `programs/<PROGRAM_NAME>/src/lib.rs`. Ключ у
`[programs.<CLUSTER>]` — це назва програми в робочому просторі. Оновіть кожну
таблицю кластера, де збираєтеся використовувати нову адресу; наведений нижче
приклад оновлює Mainnet.

В Anchor.toml:

```diff
 [programs.mainnet]
-my_program = "<OLD_PROGRAM_ID>"
+my_program = "<NEW_PROGRAM_ID>"
```

У `programs/<your_program>/lib.rs`:

```diff
-declare_id!("<OLD_PROGRAM_ID>");
+declare_id!("<NEW_PROGRAM_ID>");
```

Pinocchio не використовує `Anchor.toml`. Оновіть виклик `declare_id!` у
`src/lib.rs` крейту програми. Поточні проєкти Pinocchio імпортують макрос із
`pinocchio::address`.

Quasar також оголошує адресу в `src/lib.rs` крейту ончейн-програми та не
використовує `Anchor.toml`. Макрос `declare_id!` доступний через
`quasar_lang::prelude::*`.

Перезберіть програму та повторно згенеруйте всі IDL або клієнтські артефакти
після зміни адреси. Також знайдіть у скриптах розгортання, тестах і конфігурації
застосунку старий ID програми та замініть усі жорстко закодовані посилання на
нього.
