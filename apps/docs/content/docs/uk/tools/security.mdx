## Керування ключами

- **Ніколи не розкривайте приватні ключі у фронтенд-коді.** Використовуйте підписання на бекенді, апаратні
  гаманці, мультипідписні гаманці або сервіси керування ключами.
- **Розділяйте гарячі та холодні гаманці.** Гарячий гаманець — для операцій, холодний — для
  скарбниці.
- **Створюйте резервні копії всіх продакшн-ключів.** Зберігайте зашифровані копії в кількох захищених
  місцях. Втрата ключа означає остаточну втрату доступу.
- **Використовуйте різні ключі для devnet і mainnet.** Ваші ключі devnet не повинні бути
  ключами mainnet. Використовуйте конфігурацію на основі середовища, щоб для кожної мережі
  завантажувалися правильні ключі.

## Інфраструктура підписання

Для підписання на продакшн-бекенді використовуйте [Keychain](/docs/tools/keychain) — єдину
бібліотеку підписання, яка абстрагує кілька бекендів керування ключами через один
інтерфейс: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP,
Para, Dfns, Crossmint, Openfort і Utila. Це дає змогу розробляти локально з
ключами в пам'яті, а потім переходити на бекенди продакшн-рівня без зміни
коду застосунку.

Не знаєте, який бекенд обрати? Дивіться
[Вибір бекенду](/docs/tools/keychain/choosing-a-backend). Keychain
доступний для [Rust](https://crates.io/crates/solana-keychain) і
[TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Безпека RPC

Ставтеся до RPC-ендпоінтів як до API-ключів: не розміщуйте їх у фронтенд-коді, де вони
можуть бути витягнуті та використані зловмисниками. Використовуйте бекенд-проксі або змінні середовища, які
не потрапляють у клієнтський код.

- [QuickNode: найкращі практики безпеки ендпоінтів](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: захист ваших API-ключів Solana — найкращі практики безпеки](https://www.helius.dev/docs/rpc/protect-your-keys)

## Моніторинг

Відстежуйте ці метрики в продакшні:

| Метрика                   | Навіщо                    |
| ------------------------ | ---------------------- |
| Частка успішних транзакцій | Раннє виявлення проблем    |
| Затримка підтвердження     | Моніторинг стану мережі |
| Витрати на пріоритетні комісії       | Контроль витрат        |
| Частка помилок RPC           | Стан провайдера        |

Налаштуйте сповіщення про:

- Перекази зі скарбниці, що перевищують поріг
- Стрибки частки невдалих транзакцій
- Незвичні шаблони одержувачів
- Зростання частки помилок RPC

Про моніторинг транзакцій у реальному часі у великих масштабах читайте в
[посібнику з індексування](/docs/payments/accept-payments/indexing).

## Перевірка адрес

Кожен токен і програма мають лише одну правильну адресу в mainnet. Підроблені
токени, що імітують USDC або інші стейблкоїни, трапляються часто — вони матимуть таку саму назву
і символ, але інший mint. Ваш застосунок має жорстко прописувати або додавати до списку дозволених
adреси mint (залежно від ваших вимог) і ніколи не приймати їх динамічно
з недовірених джерел.

**Конфігурація на основі середовища:** у Devnet і Mainnet часто використовуються абсолютно
різні токени mint. Налаштуйте конфігурацію застосунку так, щоб завантажувалися правильні
адреси для кожного середовища — не прописуйте адреси mainnet жорстко, забувши замінити
їх під час тестування, і тим більше не відправляйте адреси devnet у продакшн.

Ось деякі поширені mint-адреси стейблкоїнів:

| Токен | Емітент | Mint-адреса                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Адреси програм також мають значення. Надсилання інструкцій на неправильну програму
завершиться невдачею або, що гірше, незворотною втратою коштів. Адреси Token Program
такі:

| Програма            | Адреса                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Додавання правильних адрес до списку дозволених захищає від підроблених токенів, але
не захищає від надсилання на акаунт неправильного _типу_. Адреса одержувача
може бути гаманцем, token account, mint або програмою, і кожен варіант потребує
особливого поводження. Native SOL, надісланий на будь-що, крім гаманця, виходить із-під контролю
відправника — він втрачається остаточно у разі mint або програми і може бути відновлений лише
власником акаунта у випадку token account — і при цьому немає невдалої транзакції, яка б попередила користувача.

<Callout type="warn" title="Перевіряйте одержувачів перед надсиланням">
  Класифікуйте кожну адресу одержувача перед підписанням переказу. Дивіться [Перевірка
  адреси](/docs/payments/send-payments/verify-address), де наведено повне дерево
  рішень і референсний код, що розрізняє гаманці, token account, mint і
  програми.
</Callout>
