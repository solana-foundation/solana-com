## Керування ключами

- **Ніколи не розкривайте приватні ключі у фронтенд-коді.** Використовуйте підписання на бекенді, апаратні
  гаманці, мультипідписні гаманці або сервіси керування ключами.
- **Розділяйте гарячі та холодні гаманці.** Гарячий гаманець — для операцій, холодний — для
  скарбниці.
- **Створюйте резервні копії всіх продакшн-ключів.** Зберігайте зашифровані резервні копії в кількох захищених
  місцях. Втрата ключа означає безповоротну втрату доступу.
- **Використовуйте різні ключі для devnet і mainnet.** Ключі devnet не повинні
  бути ключами mainnet. Використовуйте конфігурацію на основі середовища, щоб для кожної мережі
  завантажувалися правильні ключі.

## Інфраструктура підписання

Для підписання на продакшн-бекенді використовуйте [Keychain](/docs/tools/keychain) — уніфіковану
бібліотеку підписання, яка абстрагує кілька бекендів керування ключами через єдиний
інтерфейс: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP,
Para, Dfns, Crossmint, Openfort і Utila. Це дозволяє розробляти локально з
ключами в пам'яті, а потім переходити на бекенди промислового рівня без зміни
коду застосунку.

Не знаєте, який бекенд обрати? Дивіться
[Вибір бекенду](/docs/tools/keychain/choosing-a-backend). Keychain
доступний для [Rust](https://crates.io/crates/solana-keychain) та
[TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Безпека RPC

Ставтеся до RPC-ендпоінтів як до API-ключів — не розкривайте їх у фронтенд-коді, звідки вони
можуть бути вилучені та використані зловмисниками. Використовуйте бекенд-проксі або змінні середовища, які
не включаються до клієнтського коду.

- [QuickNode: найкращі практики безпеки ендпоінтів](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: захистіть свої API-ключі Solana — найкращі практики безпеки](https://www.helius.dev/docs/rpc/protect-your-keys)

## Моніторинг

Відстежуйте ці метрики в продакшні:

| Метрика                   | Навіщо                    |
| ------------------------ | ---------------------- |
| Частка успішних транзакцій | Раннє виявлення проблем    |
| Затримка підтвердження     | Моніторинг стану мережі |
| Витрати на пріоритетні комісії       | Контроль витрат        |
| Частка помилок RPC           | Стан провайдера        |

Налаштуйте сповіщення про:

- Перекази зі скарбниці понад встановлений поріг
- Раптове зростання частки невдалих транзакцій
- Незвичні шаблони отримувачів
- Зростання частки помилок RPC

Для моніторингу транзакцій у реальному часі у великому масштабі дивіться наш
[посібник з індексування](/docs/payments/accept-payments/indexing).

## Перевірка адрес

Кожен токен і програма мають лише одну правильну адресу в mainnet. Підроблені
токени, що імітують USDC або інші стейблкоїни, трапляються часто — вони матимуть таку саму назву
і символ, але інший mint. Ваш застосунок має жорстко прописувати або додавати до списку дозволених
адреси mint (залежно від ваших вимог) і ніколи не приймати їх динамічно
з ненадійних джерел.

**Конфігурація на основі середовища:** Devnet і Mainnet часто використовують зовсім
різні mint токенів. Налаштуйте конфігурацію застосунку так, щоб вона завантажувала правильні
адреси для кожного середовища — не прописуйте адреси mainnet жорстко, забувши замінити
їх під час тестування, і, що ще гірше, не відправляйте адреси devnet у продакшн.

Ось деякі поширені mint стейблкоїнів:

| Токен | Емітент | Адреса mint                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Адреси програм також важливі. Надсилання інструкцій до неправильної програми
завершиться невдачею або, що гірше, призведе до безповоротної втрати коштів. Адреси Token Program
такі:

| Програма            | Адреса                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Додавання правильних адрес до списку дозволених захищає від підроблених токенів, але
не захищає від надсилання на неправильний _тип_ акаунта. Адреса отримувача
може бути гаманцем, token account, mint або програмою, і кожен тип потребує
окремої обробки. Нативний SOL, надісланий на будь-що, окрім гаманця, виходить із-під контролю
відправника — безповоротно втрачається для mint або програми, а для token account може бути відновлений лише
власником акаунта — без жодної невдалої транзакції, яка б попередила користувача.

<Callout type="warn" title="Перевіряйте отримувачів перед надсиланням">
  Класифікуйте кожну адресу отримувача перед підписанням переказу. Дивіться [Перевірка
  адреси](/docs/payments/send-payments/verify-address) — повне дерево
  рішень і еталонний код, що розрізняє гаманці, token account, mint і
  програми.
</Callout>
