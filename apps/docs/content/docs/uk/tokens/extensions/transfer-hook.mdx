Розширення Transfer Hook та інтерфейс Transfer Hook Interface надають можливість створювати mint account, які виконують власну логіку інструкцій при кожному переказі токенів.

Це відкриває багато нових варіантів використання для переказів токенів, наприклад:

- Примусове стягнення роялті для NFT
- Чорні або білі списки гаманців, які можуть отримувати токени
- Реалізація власних комісій при переказах токенів
- Створення власних подій переказу токенів
- Відстеження статистики переказів токенів
- Та багато іншого

Для цього розробники повинні створити програму, яка реалізує
[Transfer Hook Interface](https://github.com/solana-labs/solana-program-library/tree/master/token/transfer-hook/interface)
та ініціалізувати mint account з увімкненим розширенням Transfer Hook.

При кожному переказі токенів, що належать до цього mint account, Token Extensions Program виконує Cross Program Invocation (CPI) для виклику інструкції в програмі Transfer Hook.

<Callout type="info">

Коли Token Extensions Program виконує CPI до програми Transfer Hook, усі акаунти з початкового переказу перетворюються на акаунти лише для читання. Це означає, що привілеї підписанта відправника не поширюються на програму Transfer Hook.

Це проєктне рішення прийнято для запобігання зловмисному використанню програм Transfer Hook.

</Callout>

У цьому посібнику ми створимо програму Transfer Hook за допомогою фреймворку Anchor, однак реалізувати Transfer Hook Interface також можна за допомогою нативної програми. Дізнайтесь більше про фреймворк Anchor тут:
[Anchor Framework](https://www.anchor-lang.com/)

## Огляд Transfer Hook Interface

Transfer Hook Interface надає розробникам спосіб реалізації власної логіки інструкцій, яка виконується при кожному переказі токенів для конкретного mint account.

Transfer Hook Interface визначає наступні
[інструкції](https://github.com/solana-labs/solana-program-library/blob/master/token/transfer-hook/interface/src/instruction.rs):

- `Execute`: Інструкція, яку Token Extension Program викликає при кожному переказі токенів.
- `InitializeExtraAccountMetaList` (необов'язково): Створює акаунт, що зберігає список додаткових акаунтів, необхідних для власної інструкції `Execute`.
- `UpdateExtraAccountMetaList` (необов'язково): Оновлює список додаткових акаунтів шляхом перезапису наявного списку.

Технічно не обов'язково реалізовувати інструкцію `InitializeExtraAccountMetaList` за допомогою інтерфейсу. Акаунт може бути створений будь-якою інструкцією програми Transfer Hook.

Однак Program Derived Address (PDA) для цього акаунту повинна бути виведена з використанням наступних seed:

- Жорстко закодований рядок "extra-account-metas"
- Адреса mint account
- ID програми Transfer Hook

```js
const [pda] = PublicKey.findProgramAddressSync(
  [Buffer.from("extra-account-metas"), mint.publicKey.toBuffer()],
  program.programId // transfer hook program ID
);
```

Зберігаючи додаткові акаунти, необхідні для інструкції `Execute`, у визначеній PDA, ці акаунти можуть бути автоматично додані до інструкції переказу токенів з клієнта.

## Transfer Hook "Hello World"

Цей приклад є еквівалентом "Hello World" для transfer hook. Це простий transfer hook, який виводитиме повідомлення при кожному переказі токенів. Почнемо з відкриття прикладу в Solana Playground — онлайн-інструменті для створення та розгортання програм Solana:
[link](https://beta.solpg.io/github.com/solana-developers/anchor-transfer-hook/tree/hello_world)

Приклад складається з програми Anchor, яка реалізує інтерфейс transfer hook, та тестового файлу для перевірки програми.

Ця програма міститиме лише 3 інструкції:

1. `initialize_extra_account_meta_list`: Створює акаунт, що зберігає список додаткових акаунтів, необхідних для інструкції `transfer_hook`. У прикладі "Hello World" ми залишаємо його порожнім.
2. `transfer_hook`: Ця інструкція викликається через CPI при кожному переказі токенів для виконання переказу wrapped SOL токенів.
3. `fallback`: Оскільки ми використовуємо Anchor, а token program є нативною програмою, нам потрібно додати запасну інструкцію для ручного зіставлення дискримінатора інструкції та виклику нашої власної інструкції `transfer_hook`. Цю функцію змінювати не потрібно.

Щоразу, коли токен переказується, ця функція `transfer_hook` буде викликана token program.

```rust
pub fn transfer_hook(ctx: Context<TransferHook>, amount: u64) -> Result<()> {

    msg!("Hello Transfer Hook!");

    Ok(())
}
```

У цій функції ви можете додати власну логіку. Наприклад, можна зробити так, щоб переказ завершувався помилкою, коли переказувана сума перевищує 50:

```rust
#[error_code]
pub enum MyError {
    #[msg("The amount is too big")]
    AmountTooBig,
}

pub fn transfer_hook(ctx: Context<TransferHook>, amount: u64) -> Result<()> {

    msg!("Hello Transfer Hook!");

    if amount > 50 {
        return err!(MyError::AmountTooBig);
    }

    Ok(())
}
```

## Transfer Hook з лічильником

Наступний приклад покаже, як можна збільшувати лічильник щоразу, коли ваш токен переказується.
[link](https://beta.solpg.io/github.com/solana-developers/anchor-transfer-hook/tree/counter)

Якщо ви хочете додати до transfer hook логіку, яка потребує додаткових акаунтів, їх необхідно додати до акаунту ExtraAccountMetaList. У нашому випадку нам потрібна PDA, яка зберігає кількість переказів токена.

Це можна зробити, додавши наступний код до інструкції `initialize_extra_account_meta_list`:

```rust
let account_metas = vec![
    ExtraAccountMeta::new_with_seeds(
        &[Seed::Literal {
            bytes: "counter".as_bytes().to_vec(),
        }],
        false, // is_signer
        true,  // is_writable
    )?,
];
```

Також нам потрібно створити цей акаунт при ініціалізації нового mint account, і передавати його щоразу при переказі токена.

```rust
#[derive(Accounts)]
pub struct InitializeExtraAccountMetaList<'info> {
    #[account(mut)]
    payer: Signer<'info>,

    /// CHECK: ExtraAccountMetaList Account, must use these seeds
    #[account(
        mut,
        seeds = [b"extra-account-metas", mint.key().as_ref()],
        bump
    )]
    pub extra_account_meta_list: AccountInfo<'info>,
    pub mint: InterfaceAccount<'info, Mint>,
    #[account(
        init_if_needed,
        seeds = [b"counter"],
        bump,
        payer = payer,
        space = 16
    )]
    pub counter_account: Account<'info, CounterAccount>,
    pub token_program: Interface<'info, TokenInterface>,
    pub associated_token_program: Program<'info, AssociatedToken>,
    pub system_program: Program<'info, System>,
}

#[derive(Accounts)]
pub struct TransferHook<'info> {
    #[account(
        token::mint = mint,
        token::authority = owner,
    )]
    pub source_token: InterfaceAccount<'info, TokenAccount>,
    pub mint: InterfaceAccount<'info, Mint>,
    #[account(
        token::mint = mint,
    )]
    pub destination_token: InterfaceAccount<'info, TokenAccount>,
    /// CHECK: source token account owner, can be SystemAccount or PDA owned by another program
    pub owner: UncheckedAccount<'info>,
    /// CHECK: ExtraAccountMetaList Account,
    #[account(
        seeds = [b"extra-account-metas", mint.key().as_ref()],
        bump
    )]
    pub extra_account_meta_list: UncheckedAccount<'info>,
    #[account(
        mut,
        seeds = [b"counter"],
        bump
    )]
    pub counter_account: Account<'info, CounterAccount>,
}
```

Акаунт зберігатиме змінну лічильника типу `u64`:

```rust
#[account]
pub struct CounterAccount {
    counter: u64,
}
```

Тепер у функції transfer hook ми можемо просто збільшувати цей лічильник на одиницю при кожному виклику:

```rust
pub fn transfer_hook(ctx: Context<TransferHook>, amount: u64) -> Result<()> {

    ctx.accounts.counter_account.counter.checked_add(1).unwrap();
    msg!("This token has been transferred {0} times", ctx.accounts.counter_account.counter);

    Ok(())
}
```

На стороні клієнта ці додаткові акаунти автоматично додаються допоміжною функцією createTransferCheckedWithTransferHookInstruction:

```js
    destinationTokenAccount,
    wallet.publicKey,
    amountBigInt,
    decimals,

    "confirmed",
    TOKEN_2022_PROGRAM_ID

```

Перевірку можна додати ось так:

```rust
fn assert_is_transferring(ctx: &Context<TransferHook>) -> Result<()> {
    let source_token_info = ctx.accounts.source_token.to_account_info();
    let mut account_data_ref: RefMut<&mut [u8]> = source_token_info.try_borrow_mut_data()?;
    let mut account = PodStateWithExtensionsMut::<PodAccount>::unpack(*account_data_ref)?;
    let account_extension = account.get_extension_mut::<TransferHookAccount>()?;

    if !bool::from(account_extension.transferring) {
        return err!(TransferError::IsNotCurrentlyTransferring);
    }

    Ok(())
}
```

А потім викликати її на початку вашої функції `transfer_hook`:

```rust
    #[error_code]
    pub enum TransferError {
        #[msg("The token is not currently transferring")]
        IsNotCurrentlyTransferring,
    }

    #[interface(spl_transfer_hook_interface::execute)]
    pub fn transfer_hook(ctx: Context<TransferHook>, _amount: u64) -> Result<()> {
        // Fail this instruction if it is not called from within a transfer hook
        assert_is_transferring(&ctx)?;

        ctx.accounts.counter_account.counter.checked_add(1).unwrap();
        msg!("This token has been transferred {0} times", ctx.accounts.counter_account.counter);

        Ok(())
    }
```

## Transfer Hook з комісією wSOL (розширений приклад)

У наступній частині цього посібника ми створимо більш просунуту програму Transfer Hook за допомогою фреймворку Anchor. Ця програма вимагатиме від відправника сплати комісії wSOL за кожен переказ токенів.

Перекази wSOL будуть виконуватися за допомогою делегата, який є PDA, виведеною з програми Transfer Hook. Це необхідно, оскільки підпис початкового відправника інструкції переказу токенів недоступний у програмі Transfer Hook.

Ця програма міститиме лише 3 інструкції:

1. `initialize_extra_account_meta_list`: Створює акаунт, що зберігає список додаткових акаунтів, необхідних для інструкції `transfer_hook`.
2. `transfer_hook`: Ця інструкція викликається через CPI при кожному переказі токенів для виконання переказу wrapped SOL токенів.
3. `fallback`: Інструкції інтерфейсу transfer hook мають специфічні дискримінатори (ідентифікатори інструкцій). У програмі Anchor ми можемо використовувати запасну інструкцію для ручного зіставлення дискримінатора інструкції та виклику нашої власної інструкції `transfer_hook`.

Ця програма вимагатиме від відправника сплати комісії у wrapped SOL (wSOL) за кожен переказ токенів. Ось
[фінальна програма](https://beta.solpg.io/github.com/solana-developers/anchor-transfer-hook/tree/main).

### Інструкція ініціалізації акаунту ExtraAccountMetas

На цьому кроці ми реалізуємо інструкцію `initialize_extra_account_meta_list` для нашої програми Transfer Hook. Ця інструкція створює акаунт ExtraAccountMetas, який зберігатиме додаткові акаунти, необхідні для нашої інструкції `transfer_hook`.

У цьому прикладі інструкція `initialize_extra_account_meta_list` потребує 7 акаунтів:

- `payer`: Акаунт, який використовується для оплати створення акаунту ExtraAccountMetas.
- `extra_account_meta_list`: Акаунт ExtraAccountMetas, створений для зберігання списку акаунтів, необхідних для нашої інструкції `transfer_hook`.
- `mint`: mint account, який вказує на цю програму Transfer Hook. Адреса mint є обов'язковим seed для виведення PDA `extra_account_meta_list`.
- `wsol_mint`: Wrapped SOL mint.
- `token_program`: Оригінальний ID Token Program
- `associated_token_program`: ID Associated Token Program.
- `system_program`: System Program, який є обов'язковим акаунтом при створенні нових акаунтів.

Адреси `mint`, `wsol_mint` та `associated_token_program` будуть використовуватися для виведення адрес wSOL associated token account. Ці акаунти необхідні для інструкції `transfer_hook` і будуть збережені в акаунті ExtraAccountMetas.

Оновіть структуру `InitializeExtraAccountMetaList`, замінивши наступний стартовий код:

```rust
#[derive(Accounts)]
pub struct InitializeExtraAccountMetaList {}
```

Наведеним нижче кодом:

```rust
#[derive(Accounts)]
pub struct InitializeExtraAccountMetaList<'info> {
    #[account(mut)]
    payer: Signer<'info>,

    /// CHECK: ExtraAccountMetaList Account, must use these seeds
    #[account(
        mut,
        seeds = [b"extra-account-metas", mint.key().as_ref()],
        bump
    )]
    pub extra_account_meta_list: AccountInfo<'info>,
    pub mint: InterfaceAccount<'info, Mint>,
    pub wsol_mint: InterfaceAccount<'info, Mint>,
    pub token_program: Interface<'info, TokenInterface>,
    pub associated_token_program: Program<'info, AssociatedToken>,
    pub system_program: Program<'info, System>,
```

### Резервна інструкція (Fallback)

Нарешті, нам потрібно додати резервну інструкцію до програми Anchor для обробки CPI від Token Extensions Program.

Цей крок необхідний через різницю в тому, як Anchor генерує дискримінатори інструкцій, порівняно з тими, що використовуються в інструкціях інтерфейсу Transfer Hook. Дискримінатор інструкції для `transfer_hook` не збігатиметься з дискримінатором інтерфейсу Transfer Hook.

Оновіть інструкцію `fallback`, замінивши наступний початковий код:

```rust

    program_id: &Pubkey,

    Ok(())

```

Оновленим кодом нижче:

```rust
// fallback instruction handler as workaround to anchor instruction discriminator check
pub fn fallback<'info>(
    program_id: &Pubkey,
    accounts: &'info [AccountInfo<'info>],
    data: &[u8],
) -> Result<()> {
    let instruction = TransferHookInstruction::unpack(data)?;

    // match instruction discriminator to transfer hook interface execute instruction
    // token2022 program CPIs this instruction on token transfer
    match instruction {
        TransferHookInstruction::Execute { amount } => {
            let amount_bytes = amount.to_le_bytes();

            // invoke custom transfer hook instruction on our program
            __private::__global::transfer_hook(program_id, accounts, &amount_bytes)
        }
        _ => return Err(ProgramError::InvalidInstructionData.into()),
    }
}
```

Резервна інструкція перевіряє, чи збігається дискримінатор вхідної інструкції з інструкцією `Execute` з інтерфейсу Transfer Hook. У разі успішного збігу вона викликає інструкцію `transfer_hook` у нашій програмі Anchor.

### Використання даних token account у transfer hook

Іноді вам може знадобитися використовувати дані облікового запису для отримання додаткових облікових записів у extra account metas. Це корисно, наприклад, якщо ви хочете використати власника token account як seed для PDA.

При створенні ExtraAccountMeta ви можете використовувати дані будь-якого облікового запису як додатковий seed. У цьому випадку ми хочемо отримати обліковий запис лічильника від власника token account та рядка 'counter'. Це означає, що ми завжди зможемо бачити, як часто власник цього token account здійснював перекази токенів.

Ось як це налаштовується у функції `extra_account_metas()`.

```rust
// Define extra account metas to store on extra_account_meta_list account
impl<'info> InitializeExtraAccountMetaList<'info> {
    pub fn extra_account_metas() -> Result<Vec<ExtraAccountMeta>> {
        Ok(
            vec![
                ExtraAccountMeta::new_with_seeds(
                    &[
                        Seed::Literal {
                            bytes: b"counter".to_vec(),
                        },
                        Seed::AccountData { account_index: 0, data_index: 32, length: 32 },
                    ],
                    false, // is_signer
                    true // is_writable
                )?
            ]
        )
    }
}
```

Розглянемо структуру token account, щоб зрозуміти, як зберігаються дані облікового запису. Нижче наведено приклад структури token account. Ми можемо взяти 32 байти на позиції від 32 до 64 як власника token account, що відповідає 'account_index: 0'. 'account_index' посилається на індекс облікового запису в масиві облікових записів. У випадку transfer hook власний token account є першим записом у масиві облікових записів. Другий обліковий запис — завжди mint, а третій — цільовий token account. Цей порядок облікових записів такий самий, як і в старому Token Program.

```rust
/// Account data.
#[repr(C)]
#[derive(Clone, Copy, Debug, Default, PartialEq)]
pub struct Account {
    /// The mint associated with this account
    pub mint: Pubkey,
    /// The owner of this account.
    pub owner: Pubkey,
    /// The amount of tokens this account holds.
    pub amount: u64,
    pub delegate: COption<Pubkey>,
    pub state: AccountState,
    pub is_native: COption<u64>,
    pub delegated_amount: u64,
    pub close_authority: COption<Pubkey>,
}
```

У нашому випадку ми хочемо отримати обліковий запис лічильника від власника token account відправника, тому при створенні облікових записів ExtraAccountMeta ми ініціалізуємо (`init`) цей PDA-обліковий запис лічильника, що отримується від власника token account відправника та рядка 'counter'. Після ініціалізації PDA-лічильника ми зможемо використовувати його в transfer hook для збільшення значення при кожному переказі.

````rust
struct.

```rust

pub struct InitializeExtraAccountMetaList<'info> {
    #[account(mut)]
    payer: Signer<'info>,

    /// CHECK: ExtraAccountMetaList Account, must use these seeds
    #[account(
        init,
        seeds = [b"extra-account-metas", mint.key().as_ref()],
````

Нам також потрібно визначити цей додатковий обліковий запис лічильника в структурі TransferHook. Це облікові записи, що передаються до нашої програми TransferHook при кожному переказі. Клієнт отримує ці додаткові облікові записи з PDA ExtraAccountsMetaList і включає їх в інструкцію переказу токенів, але тут у програмі нам все одно потрібно його визначити.

```rust
#[derive(Accounts)]
pub struct TransferHook<'info> {
    #[account(token::mint = mint, token::authority = owner)]
    pub source_token: InterfaceAccount<'info, TokenAccount>,
    pub mint: InterfaceAccount<'info, Mint>,
    #[account(token::mint = mint)]
    pub destination_token: InterfaceAccount<'info, TokenAccount>,
    /// CHECK: source token account owner, can be SystemAccount or PDA owned by another program
    pub owner: UncheckedAccount<'info>,
    /// CHECK: ExtraAccountMetaList Account,
    #[account(seeds = [b"extra-account-metas", mint.key().as_ref()], bump)]
    pub extra_account_meta_list: UncheckedAccount<'info>,
    #[account(seeds = [b"counter", owner.key().as_ref()], bump)]
    pub counter_account: Account<'info, CounterAccount>,
}
```

На стороні клієнта цей обліковий запис генерується автоматично, і ви можете використовувати його наступним чином.

Зверніть увагу, що обліковий запис лічильника отримується від власника token account і повинен бути ініціалізований перед здійсненням переказу. У цьому прикладі ми ініціалізуємо обліковий запис лічильника під час ініціалізації extra account metas. Тому ми матимемо PDA лічильника лише для власника token account, який викликав цю функцію. Якщо ви хочете мати обліковий запис лічильника для кожного token account вашого mint, вам потрібно буде реалізувати функціонал для попереднього створення цих PDA. Можна додати кнопку у вашому dapp для реєстрації лічильника, яка створює цей PDA, і після цього користувачі зможуть використовувати цей токен лічильника.
