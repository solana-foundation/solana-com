Транзакція виконується, лише якщо містить дійсний
[підпис](/docs/core/transactions/transaction-structure#signatures) від кожного
необхідного підписанта. Під час локальної розробки цей ключ зазвичай зберігають як
[`Keypair`](/developers/cookbook/wallets/create-keypair) і підписують напряму. У
продакшені ключове питання інше: **де зберігається приватний ключ
і кому дозволено авторизувати підпис за його допомогою?**

<Callout type="warn">
  Ніколи не вбудовуйте приватні ключі в клієнтський код, не включайте їх у збірку фронтенду
  і не комітьте їх у систему контролю версій. Той, хто отримає ключ, здобуде повний контроль над коштами
  відповідного акаунта.
</Callout>

## Підходи до підписання

| Підхід                  | Де зберігається ключ                                     | Хто підписує                                          | Найкраще підходить для                                                      |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **Локальний keypair**         | Файл або змінна середовища на машині           | Ваш код, напряму                                | Локальна розробка, тести, CI                                  |
| **Браузерний гаманець**        | Гаманець кінцевого користувача (наприклад, Phantom, Solflare)          | Кінцевий користувач, для кожної транзакції                      | Фронтенд-dApps, де користувачі підписують власні транзакції        |
| **Хмарний KMS / HSM**       | Сервіс ключів з апаратним захистом (AWS KMS, GCP KMS, Vault) | Ваш бекенд запитує підпис у сервісу | Бекенд-сервіси, казначейські операції, регульовані середовища |
| **Кероване / MPC-гаманці** | Розділений або кастодіальний ключ в інфраструктурі провайдера   | Провайдер співпідписує відповідно до вашої політики     | Вбудовані гаманці, процеси погодження, інституційне кастодіальне зберігання   |

Локальний keypair — єдиний підхід, за якого сирий ключовий матеріал опиняється всередині вашого
застосунку. Усі продакшен-підходи зберігають ключ у виділеній інфраструктурі
і просять цю інфраструктуру підписувати від вашого імені.

## Підписання на бекенді

Коли сервер має підписувати (сплачувати комісії, надсилати транзакції програм
або керувати казначейством), використовуйте спеціалізований бекенд керування ключами замість звичайного
keypair. Solana Foundation підтримує [Keychain](/docs/tools/keychain) —
уніфіковану бібліотеку підписання (Rust, TypeScript, Python і Go), яка надає єдиний
інтерфейс `SolanaSigner` для всіх бекендів із таблиці вище: Memory,
HashiCorp Vault, AWS KMS, GCP KMS, Fireblocks, Privy, Turnkey, CDP, Crossmint,
Dfns, Para, Openfort, Utila та Fordefi.

Оскільки інтерфейс спільний для всіх бекендів, ви можете розробляти локально з
ключем у пам'яті й перейти на продакшен-бекенд через конфігурацію, без
переписування коду застосунку (бекенди, які самі розсилають транзакції, як-от Crossmint,
викликаються через шлях «підписати й надіслати»). Keychain сумісний із
[`@solana/kit`](/docs/clients/official/javascript),
[Rust SDK](/docs/clients/official/rust), `solders` (Python) і `solana-go` v2
(Go).
