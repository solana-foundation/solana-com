Транзакція виконується лише тоді, коли містить дійсний
[підпис](/docs/core/transactions/transaction-structure#signatures) від кожного
обов'язкового підписанта. Під час локальної розробки цей ключ зазвичай зберігається як
[`Keypair`](/developers/cookbook/wallets/create-keypair), і підписання виконується безпосередньо. У
production головне питання інше: **де зберігається приватний ключ і кому дозволено
авторизувати підпис за його допомогою?**

<Callout type="warn">
  Ніколи не вбудовуйте приватні ключі в клієнтський код, не включайте їх до складу фронтенду і
  не комітьте в систему контролю версій. Той, хто отримає ключ, отримує повний контроль над
  коштами цього акаунта.
</Callout>

## Підходи до підписання

| Підхід                  | Де зберігається ключ                                     | Хто підписує                                          | Найкраще підходить для                                                      |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **Локальний keypair**         | Файл або змінна середовища на машині           | Ваш код, безпосередньо                                | Локальна розробка, тести, CI                                  |
| **Браузерний гаманець**        | Гаманець кінцевого користувача (наприклад, Phantom, Solflare)          | Кінцевий користувач, для кожної транзакції                      | Фронтенд-dApps, де користувачі підписують власні транзакції        |
| **Хмарний KMS / HSM**       | Сервіс ключів з апаратним захистом (AWS KMS, GCP KMS, Vault) | Ваш бекенд запитує підпис у сервісу | Бекенд-сервіси, операції з казначейством, регульовані середовища |
| **Керовані / MPC-гаманці** | Розділені або зберігаються в інфраструктурі провайдера   | Провайдер співпідписує відповідно до вашої політики     | Вбудовані гаманці, процеси погодження, інституційне зберігання   |

Локальний keypair — єдиний підхід, за якого необроблений ключовий матеріал опиняється всередині
вашого застосунку. У кожному production-підході ключ зберігається у спеціалізованій інфраструктурі,
і саме ця інфраструктура підписує від вашого імені.

## Підписання на бекенді

Коли серверу потрібно підписувати (сплачувати комісії, надсилати транзакції програм або
керувати казначейством), використовуйте спеціалізований бекенд керування ключами замість звичайного
keypair. Solana Foundation підтримує [Keychain](/docs/tools/keychain) —
уніфіковану бібліотеку підписання (Rust, TypeScript, Python і Go), яка надає єдиний
інтерфейс `SolanaSigner` для всіх бекендів із таблиці вище: Memory,
HashiCorp Vault, AWS KMS, GCP KMS, Fireblocks, Privy, Turnkey, CDP, Crossmint,
Dfns, Para, Openfort, Utila і Fordefi.

Оскільки інтерфейс спільний для всіх бекендів, ви можете розробляти локально з
ключем у пам'яті, а потім перейти на production-бекенд через конфігурацію, без
переписування коду застосунку (бекенди, які самі розсилають транзакції, як-от Crossmint,
викликаються натомість через шлях «підписати й надіслати»). Keychain сумісний з
[`@solana/kit`](/docs/clients/official/javascript),
[Rust SDK](/docs/clients/official/rust), `solders` (Python) і `solana-go` v2
(Go).
