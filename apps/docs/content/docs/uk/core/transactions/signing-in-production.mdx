Транзакція виконується лише тоді, коли вона містить дійсний
[підпис](/docs/core/transactions/transaction-structure#signatures) від кожного
обов'язкового підписанта. Під час локальної розробки ви зазвичай тримаєте цей ключ як
[`Keypair`](/developers/cookbook/wallets/create-keypair) і підписуєте напряму. У
продакшні головне питання інше: **де зберігається приватний ключ
і хто має право авторизувати підпис ним?**

<Callout type="warn">
  Ніколи не вбудовуйте приватні ключі у клієнтський код, не включайте їх у фронтенд-збірку та
  не комітьте до системи контролю версій. Будь-хто, хто отримає ключ, матиме повний контроль над
  коштами цього акаунта.
</Callout>

## Підходи до підписання

| Підхід                  | Де зберігається ключ                                     | Хто підписує                                          | Найкраще для                                                      |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **Локальний keypair**         | Файл або змінна середовища на машині           | Ваш код, напряму                                | Локальна розробка, тести, CI                                  |
| **Браузерний гаманець**        | Гаманець кінцевого користувача (наприклад, Phantom, Solflare)          | Кінцевий користувач, для кожної транзакції                      | Фронтенд-dApps, де користувачі самостійно підписують транзакції        |
| **Хмарний KMS / HSM**       | Апаратно захищений сервіс ключів (AWS KMS, GCP KMS, Vault) | Ваш бекенд запитує підпис у сервісу | Бекенд-сервіси, операції з казначейством, регульовані середовища |
| **Керовані / MPC-гаманці** | Розподілено або передано на зберігання в інфраструктуру провайдера   | Провайдер спільно підписує відповідно до вашої політики     | Вбудовані гаманці, робочі процеси погодження, інституційне зберігання   |

Локальний keypair — єдиний підхід, який розміщує необроблений ключовий матеріал безпосередньо у вашому
додатку. Кожен продакшн-підхід зберігає ключ у спеціалізованій інфраструктурі
та доручає цій інфраструктурі підписувати від вашого імені.

## Підписання на бекенді

Коли серверу потрібно підписувати транзакції (сплачувати комісії, надсилати транзакції програм або
керувати скарбницею), використовуйте окремий бекенд для керування ключами замість «сирого»
keypair. Solana Foundation підтримує [Keychain](/docs/tools/keychain) —
єдину бібліотеку підписання (Rust, TypeScript, Python і Go), яка надає один інтерфейс
`SolanaSigner` для всіх бекендів із таблиці вище: Memory,
HashiCorp Vault, AWS KMS, GCP KMS, Fireblocks, Privy, Turnkey, CDP, Crossmint,
Dfns, Para, Openfort, Utila та Fordefi.

Оскільки інтерфейс спільний для всіх бекендів, ви можете розробляти локально з ключем
у пам’яті, а потім перейти на продакшн-бекенд через конфігурацію, без
переписування коду застосунку (бекенди, що самі транслюють транзакції, як-от Crossmint,
викликаються натомість через шлях підписання й надсилання). Keychain сумісний із
[`@solana/kit`](/docs/clients/official/javascript),
[Rust SDK](/docs/clients/official/rust), `solders` (Python) та `solana-go` v2
(Go).
