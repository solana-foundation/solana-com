Події Anchor — це типізовані записи, серіалізовані за допомогою Borsh, які входять до IDL програми.
Вони дають змогу клієнтам інтерпретувати активність програми без розбору зрозумілих людині
лог-повідомлень.

Події корисні для індексації та сповіщень, але не є станом програми. Зберігайте
в акаунті будь-яке значення, яке програма має прочитати знову, а події
розглядайте як запис, похідний від успішної транзакції.

## Визначення та генерація події

Додайте `#[event]` до структури та викликайте `emit!` після успішної зміни стану.

```rust title="lib.rs"
use anchor_lang::prelude::*;

#[program]
pub mod payments {
    use super::*;

    pub fn record_payment(ctx: Context<RecordPayment>, amount: u64) -> Result<()> {
        emit!(PaymentRecorded {
            authority: ctx.accounts.authority.key(),
            amount,
        });
        Ok(())
    }
}

#[derive(Accounts)]
pub struct RecordPayment<'info> {
    pub authority: Signer<'info>,
}

#[event]
pub struct PaymentRecorded {
    pub authority: Pubkey,
    pub amount: u64,
}
```

`emit!` записує байти події за допомогою системного виклику Solana `sol_log_data`. Логи
транзакції показують результат як `Program data: <base64>`. Закодоване значення починається з
дискримінатора події, за яким ідуть її поля, серіалізовані за Borsh.

Робіть події компактними. Великі рядки та вектори споживають обчислювальні ресурси, збільшують
метадані транзакції й з більшою ймовірністю постраждають від обрізання логів.

## Вибір між подіями в логах і CPI-подіями

Anchor підтримує два шляхи генерації:

| Шлях        | Місце зберігання                  | Компроміс                                               |
| ----------- | --------------------------------- | ------------------------------------------------------ |
| `emit!`     | Логи program data                 | Простіше й дешевше, але логи можуть бути обрізані         |
| `emit_cpi!` | instruction data внутрішньої інструкції з CPI | Надійніші метадані, але з додатковими акаунтами та обчисленнями |

Щоб використовувати CPI-події, увімкніть функцію `event-cpi` в Anchor:

```toml title="Cargo.toml"
[dependencies]
anchor-lang = { version = "1.1.2", features = ["event-cpi"] }
```

Потім позначте структуру акаунтів інструкції атрибутом `#[event_cpi]` і генеруйте подію
в обробнику, змінна контексту якого має назву `ctx`:

```rust title="lib.rs"
pub fn record_payment(ctx: Context<RecordPayment>, amount: u64) -> Result<()> {
    emit_cpi!(PaymentRecorded {
        authority: ctx.accounts.authority.key(),
        amount,
    });
    Ok(())
}

#[event_cpi]
#[derive(Accounts)]
pub struct RecordPayment<'info> {
    pub authority: Signer<'info>,
}
```

`#[event_cpi]` додає акаунт event authority і program account поточної програми, потрібні для
підписаного self-CPI. CPI-події не можна отримати через підписку Anchor на події
з логів; натомість отримайте транзакцію та декодуйте відповідну внутрішню
інструкцію.

<Callout type="info" title="Використовуйте реєстр як джерело істини">
  RPC-провайдери можуть обрізати логи програм. Якщо пропуск події вплине
  на баланси, дозволи чи інший критичний для коректності процес, виводьте
  результат з акаунтів програми або з instruction data транзакції. Використовуйте події, щоб
  зробити індексацію ефективною, а не як єдиний запис стану.
</Callout>

## Підписка з TypeScript

Поточний клієнт Anchor для TypeScript — `@anchor-lang/core`. Екземпляр `Program`,
створений з IDL програми, може декодувати відповідні події з логів і доставляти
їх через підписку на логи RPC:

```ts
const listenerId = program.addEventListener(
  "PaymentRecorded",
  (event, slot, signature) => {
    console.log({ event, slot, signature });
  },
  "confirmed"
);

// Remove the websocket subscription when it is no longer needed.
await program.removeEventListener(listenerId);
```

Колбек отримує декодовані дані події, slot і підпис транзакції. Підписки охоплюють лише логи, доставлені, поки з'єднання
активне. Зберігайте оброблені підписи та донаповнюйте пропущені транзакції після
розриву з'єднання, якщо споживачу потрібна повна історія.

## Декодування логів отриманої транзакції

Для бекфілів і разової перевірки отримайте транзакцію та передайте кожен
пейлоад `Program data:` кодеру подій:

```ts
const transaction = await connection.getTransaction(signature, {
  commitment: "confirmed",
  maxSupportedTransactionVersion: 0
});

if (!transaction?.meta || transaction.meta.err) {
  throw new Error("Transaction was not found or did not succeed");
}

for (const log of transaction.meta.logMessages ?? []) {
  const prefix = "Program data: ";
  if (!log.startsWith(prefix)) continue;

  const decoded = program.coder.events.decode(log.slice(prefix.length));
  if (decoded) console.log(decoded.name, decoded.data);
}
```

Транзакція може викликати кілька програм. Для продакшн-парсера відстежуйте межі логів
`Program <address> invoke` і `success` або використовуйте парсер подій Anchor, щоб запис
`Program data:` іншої програми не було декодовано як вашу.
Невдалі транзакції можуть зберігати логи та внутрішні інструкції від роботи, виконаної
до помилки, тому завжди відхиляйте метадані транзакції з ненульовим `err`
перед індексацією будь-якої форми події. Підписка Anchor на логи виконує цю перевірку
перед доставкою колбека події.

Для події `emit_cpi!` знайдіть self-CPI в `meta.innerInstructions`,
переконайтеся, що його ID програми — це ваша програма, і декодуйте його instruction data з base58.
Перш ніж відкидати будь-які байти, перевірте
[`EVENT_IX_TAG_LE`](https://github.com/solana-foundation/anchor/blob/v1.1.2/lang/src/event.rs#L1-L3) Anchor:

```ts
import bs58 from "bs58";

const EVENT_IX_TAG_LE = Buffer.from("e445a52e51cb9a1d", "hex");
const instructionData = Buffer.from(bs58.decode(innerInstruction.data));

if (!instructionData.subarray(0, 8).equals(EVENT_IX_TAG_LE)) {
  // This is an ordinary self-CPI, not an emit_cpi! event.
  continue;
}

const eventData = instructionData.subarray(8).toString("base64");
const decoded = program.coder.events.decode(eventData);
```

Перевірка і ID програми, і тегу запобігає тому, щоб звичайний self-CPI було
помилково сприйнято за подію.

## Версіювання схем подій

За замовчуванням Anchor виводить 8-байтовий дискримінатор події з її назви.
Anchor також підтримує явний дискримінатор через
`#[event(discriminator = ...)]`. Дискримінатори мають залишатися унікальними в межах
програми та стабільними для кожного клієнта, що декодує подію.

Зміна полів структури події змінює її розкладку Borsh. Для несумісної зміни
схеми визначайте нову подію, наприклад `PaymentRecordedV2`, замість
тихої зміни `PaymentRecorded`. Продовжуйте генерувати стару подію протягом періоду
міграції, поки наявні індексатори від неї залежать.

Для даних, що еволюціонують, віддавайте перевагу полям фіксованої ширини та ідентифікаторам, які дають змогу
індексатору окремо отримувати розширені дані акаунта. Публікуйте оновлений IDL до оновлення програми або
разом з ним, щоб споживачі могли одразу декодувати нову подію.

## Тестування подій

Тестуйте декодований контракт, а не рядок base64. Реєструйте слухача до
надсилання інструкції, перевіряйте декодовані поля та підпис транзакції
й завжди видаляйте слухача:

```ts
let listenerId = 0;
const received = new Promise<{
  event: { authority: PublicKey; amount: BN };
  signature: string;
}>((resolve) => {
  listenerId = program.addEventListener(
    "PaymentRecorded",
    (event, _slot, signature) => resolve({ event, signature }),
    "confirmed"
  );
});

try {
  const signature = await program.methods.recordPayment(new BN(500)).rpc();
  const result = await received;

  assert.equal(result.signature, signature);
  assert.equal(result.event.amount.toString(), "500");
} finally {
  await program.removeEventListener(listenerId);
}
```

Також перевіряйте, що індексатор ігнорує байти подій, збережені в метаданих невдалих транзакцій,
і додайте фікстуру для кожної підтримуваної версії події. Якщо ви використовуєте
`emit_cpi!`, тестуйте декодування з `innerInstructions`, адже слухачі логів не
отримують ці події напряму.
