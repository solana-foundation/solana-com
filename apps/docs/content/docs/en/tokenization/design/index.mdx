<Callout type="info" title="Summary">

Whether the token is the asset itself or a record of one held elsewhere sets
where the register of record lives and what has to be reconciled. The asset type
then sets the controls, and each control brings operating duties. The extension
set is fixed at mint creation: adding one later requires a new mint and a
migration.

</Callout>

## Is the token the asset, or a record of one?

**The token is the asset.** The mint is the authoritative record of the
entitlement and no other register governs it. A stablecoin or e-money token is
itself the issuer's liability. A tokenized deposit, a natively issued note, or a
fund whose share register is maintained onchain work the same way.

**The token records an asset held elsewhere.** An off-chain register governs - a
custodian's books, a transfer agent's register, a position at a central
securities depository - and the token is a transferable record of a claim on it.
Tokenized equities commonly work this way, with shares held by a custodian and
the token tracking them.

Both models are in use. A program may run the second model indefinitely, because
the underlying asset may have a statutory register that cannot be relocated
onchain.

|                     | Token is the asset                                            | Token records an asset held elsewhere                                      |
| ------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Register of record  | The mint                                                      | An off-chain register                                                      |
| Reconciliation      | Internal controls only                                        | A standing obligation between two books                                    |
| Main failure mode   | Loss or misuse of an authority key                            | Token supply drifting out of correspondence with the underlying            |
| The legal work      | Establishing that the chain record is the definitive register | Characterizing the token as a claim on the underlying                      |
| Role of finality    | It is the register                                            | It records a transfer of the claim                                         |
| Additional controls | None inherent to the model                                    | Evidence of backing, and mint and burn tied to movements in the underlying |

A fund or a note can be issued either way. Which model applies depends on which
register governs the entitlement in law, a question for counsel.

## Controls by asset type

| If the asset is                  | Core controls                            | Optional controls                                                                                    |
| -------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| A fund or money market fund      | Holder allowlist, forced transfer, pause | Scaled UI amount for distributed yield or share splits, permissioned burn for redemptions            |
| A security or equity             | Holder allowlist, forced transfer, pause | Permissioned burn, scaled UI amount for splits and dividends, metadata for instrument reference data |
| A deposit token or e-money claim | Holder allowlist, forced transfer, pause | Confidential Balances, sponsored fees                                                                |
| A commodity or physical claim    | Holder allowlist, forced transfer        | Metadata pointing at custody attestations                                                            |
| A collateral instrument for repo | Forced transfer, pause                   | Atomic settlement against the cash leg                                                               |

The DvP program does not accept mints with scaled UI amount; see
[mint configuration constraints](/docs/tokenization/settlement/dvp-program#mint-configuration-constraints).

## Operating obligations by control

- **A holder allowlist** requires someone to maintain the list and to account
  for a wallet that should have been removed and was not. It also limits the
  token to venues that can hold an allowlisted position.
- **A forced-transfer power** (permanent delegate) means a key exists that can
  move any holder's balance. Document where it is held, who can use it, and what
  authorization evidence exists for each use.
- **A pause power** allows the token to be halted globally. Decide in advance
  who may invoke it, on what evidence, and how the unwind works.
- **Permissioned burn** requires the issuer to co-sign redemptions, which adds a
  liveness dependency on the issuer's own systems.
- **Backing evidence**, in a mirror structure, sits outside the mint. Someone
  has to attest that the underlying exists, on a cadence, in a form that can be
  checked independently.

Choosing fewer controls is a valid design. A token with no forced-transfer power
cannot execute a court order onchain, and has no delegate key to compromise.

## Decide these before you build

1. Is the mint the register of record, or does an off-chain register govern?
2. What does the token represent in law, and in which jurisdiction?
3. Who is permitted to hold it, and how is that determined?
4. Does the balance change without a transfer - accrual, splits, dividends?
5. What must you be able to do to a holder's balance without their cooperation?
6. Who signs for each of those powers, and what is the quorum? See
   [choosing controls](/docs/tokenization/design/choosing-controls#split-authorities-from-the-start).
