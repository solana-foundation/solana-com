<Callout type="info" title="Summary">

Token-2022 carries the extensions regulated issuance uses; SPL Token and a
custom program are the alternatives, compared below. Give every authority its
own key from the start, and decide for each one whether it should be a
program-enforced PDA, an onchain multisig, or a single custodied key. Every
program in your token's transfer path - including a transfer hook you write - is
a dependency of the asset.

</Callout>

## Which token program

| Option                     | Provides                                                                                              | Considerations                                                                                                                                                                                                                                              |
| -------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SPL Token**              | The original token program. Supported by the wallets, indexers, custodians, and venues in general use | No holder-level control beyond freeze. No default-frozen accounts, pause, or permanent delegate, so no forced transfer for a court order                                                                                                                    |
| **Token-2022**             | The same core behavior plus the extension set that regulated issuance depends on                      | Support is broad but not universal. Confirm your venues, custodians, and wallets handle it                                                                                                                                                                  |
| **A custom token program** | Anything you can write                                                                                | You own an audit after every change, the upgrade authority, liveness, and integrations. Wallets, indexers, custodians, and venues need custom integration to support it. Applies where a requirement cannot be expressed in Token-2022 plus a transfer hook |

**Token-2022.** This section and its tutorials are written against Token-2022.
The controls used in regulated issuance are extensions enforced inside the
program, so they are shared standards rather than code you maintain. See
[Token Extensions](/docs/tokens/extensions) for the full list and
[choosing controls](/docs/tokenization/design/choosing-controls) for which ones
to turn on.

Token-2022 support varies by counterparty. Confirm that your custodian, your
transfer agent, the venues you expect to list on, and any wallet your holders
will use support Token-2022 mints **with the specific extensions you intend to
enable**. Support for the program does not imply support for every extension on
it - a venue may handle a plain Token-2022 mint and still reject one carrying a
transfer hook.

## Authority design

[Choosing controls](/docs/tokenization/design/choosing-controls#split-authorities-from-the-start)
lists the authorities. Each can be held by one of three options: a single
custodied key, an onchain multisig, or a PDA. They differ in how fast the
authority can act and how hard it is to misuse.

### A single custodied key

One keypair, held in an HSM or a custody service. It acts fastest with the
fewest steps, and is a single point of compromise.

Appropriate for low-consequence, high-frequency authorities - the metadata
authority is one example. Also used for the **pause authority**, which is only
useful if it can be exercised within minutes of an incident. A pause that
requires multiple signatures out of hours may not be available when the incident
occurs.

### An onchain multisig

M-of-N approval enforced by the token program, so no single holder can act
alone. Slower, auditable, and appropriate where misuse would be hard to reverse.

Use it for the **mint authority** (new supply), the **permanent delegate**
(moving or burning a holder's balance), and the **Confidential Balances
authority**. For the permanent delegate, the slowness is deliberate: its
legitimate uses are court orders, fraud response, and lost-key recovery. Active
fraud may not allow time to convene a quorum; a pause authority on a single key
can act in that interval.

See [adding signers](/docs/tools/keychain/adding-signers) for the mechanics and
[production best practices](/docs/tools/keychain/production-best-practices) for
how to hold the underlying keys.

### A PDA

A program-derived address has no private key. It can only act when a program
executes a code path that signs for it, so the policy is enforced by code rather
than by whoever holds a key.

A PDA suits rules that are mechanical and from which human discretion is to be
removed. One case is the **freeze authority under Token ACL**: delegating it to
the ACL program's PDA lets any address that satisfies the gate thaw itself,
without an issuer signature. In allowlist mode the issuer, or its operator,
still adds each holder to the list.

If the program has no code path for an action, a PDA authority cannot take it.
An issuer override is the route for an action outside the policy. With Token ACL
that override is the ability to freeze or thaw directly, swap the gate, or
reclaim the freeze authority.

<Callout type="info">

Authorities are set at creation; rotating one afterwards is a separate procedure
per authority type, and a multisig or PDA rotation is not the same operation as
a single-key rotation.

</Callout>

## Audit and upgrade risk

Every program that can execute in your token's transfer path is a dependency of
the asset. For a Token-2022 mint with frozen-by-default accounts and Token ACL,
that list is at least: the Token-2022 program, the Token ACL program, and the
gate program the ACL delegates to. Add a transfer hook and it is your program
too.

For each one, be able to answer:

| Question                                             | Risk                                                                                                                              |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Who holds the upgrade authority?                     | A single key held by a third party can change the token's behavior without the issuer's consent                                   |
| Is it immutable, and should it be?                   | Revoking the upgrade authority removes that risk and the ability to fix a bug, which suits a program audited against a fixed spec |
| When was it last audited, and against which version? | An audit covers a commit, so after an upgrade it describes different code                                                         |
| What happens if it stops working?                    | An unavailable gate program does not freeze existing balances but can stop new holders from onboarding                            |

If you write a transfer hook, the four questions apply to it, and you maintain
it. A hook that panics makes every transfer of your token fail.
