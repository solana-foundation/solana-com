An asset-manager vault holding a gated token is subject to that gate like any
other holder. If the vault's accounts were not allowlisted at deployment, the
first deposit fails.

This tutorial does the part that can be done with first-party tooling: prove the
gate applies to a vault, get every account the vault touches onto the allowlist,
and verify each one. It continues from
[gate the holders](/docs/tokenization/tutorials/issuing/gate-the-holders), so
`$MINT` should already be exported.

The verification steps below use `spl-token`. The Anza release install from the
issuing tutorials includes it; if it is missing, install it:

```bash
cargo install spl-token-cli
```

<Callout type="warn" title="Where this tutorial stops">

**Mosaic issues and operates tokens; it does not deploy vaults.** The steps
below prepare and verify the token-layer conditions a vault needs, using an
ordinary keypair to stand in for the vault's authority.

</Callout>

<Steps>

<Step>
### Stand up the vault authority

In a deployed vault this address is a PDA owned by the vault program. On devnet
a keypair stands in, which is enough to demonstrate the allowlist interactions:
in allowlist mode the gate checks the address only, so a PDA and a keypair are
treated the same way. The same holds in blocklist mode.

```bash
solana-keygen new --no-bip39-passphrase --silent \
  --outfile ~/.config/solana/demo-vault.json

export VAULT=$(solana-keygen pubkey ~/.config/solana/demo-vault.json)
solana airdrop 1 $VAULT --url https://api.devnet.solana.com
echo "vault authority: $VAULT"
```

<Callout type="info">

When you move to a real vault, substitute the program's PDA here. Derive it the
same way the program does and allowlist that, not a wallet - see
[program and authority design](/docs/tokenization/design/program-and-authority-design#a-pda)
for why the vault's token account should be owned by a PDA.

</Callout>

</Step>

<Step>
### Prove the gate blocks an unlisted vault

Before allowlisting, confirm the failure mode. Try to move the asset into the
vault while it is not on the list.

<CodeTabs storage="tokenization" flags="r">

```

```ts !! title="Kit" file=packages/docs-examples/tokenization/issuing/transfer-kit.ts#region=transfer output=packages/docs-examples/tokenization/issuing/transfer-kit.vault-blocked.output.txt

```

```ts !! title="Legacy" file=packages/docs-examples/tokenization/issuing/transfer-legacy.ts#region=transfer output=packages/docs-examples/tokenization/issuing/transfer-legacy.vault-blocked.output.txt

```

```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/transfer.rs#region=transfer output=packages/docs-examples/tokenization/rust/src/bin/transfer.vault-blocked.output.txt

```

```bash !! title="Mosaic CLI" output=packages/docs-examples/tokenization/vault/transfer-blocked.output.txt
mosaic transfer \
  --mint-address $MINT \
  --recipient $VAULT \
  --amount 1 \
  --keypair ~/.config/solana/demo-holder.json \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

This fails. The vault's token account is created frozen, and the permissionless
thaw that `mosaic transfer` inserts for it is rejected by the gate program with
`Custom program error: #4098` (`0x1002` in the Legacy and Rust output) because
the vault is not on the list. A program is not exempt from the gate. A deposit
that inserts the thaw fails with this error; one that does not fails on the
frozen account (`#17`).

</Step>

<Step>
### Allowlist every account the vault touches

Enumerate them before you start. A vault over a gated token needs at least the
vault's wallet or PDA on this mint's list and, if the fund's shares are
themselves a restricted token, each participant's wallet on the share mint's
list. The command below covers the first.

<CodeTabs storage="tokenization" flags="r">

```ts !! title="Mosaic SDK" file=packages/docs-examples/tokenization/issuing/allowlist-add.ts#region=allowlist-add

```

```ts !! title="Kit" file=packages/docs-examples/tokenization/issuing/allowlist-add-kit.ts#region=allowlist-add

```

```ts !! title="Legacy" file=packages/docs-examples/tokenization/issuing/allowlist-add-legacy.ts#region=allowlist-add

```

```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/allowlist-add.rs#region=allowlist-add

```

```bash !! title="Mosaic CLI"
mosaic allowlist add \
  --mint-address $MINT \
  --account $VAULT \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

Repeat for each address in your enumeration. Missing one produces a failure when
a participant tries to transact.

</Step>

<Step>
### Verify the gate state of each account

Before going live, read every account the vault depends on and confirm its
state. This is the pre-deployment check to automate.

<CodeTabs storage="tokenization" flags="r">

```bash !! title="spl-token" output=packages/docs-examples/tokenization/vault/display-vault.output.txt
export VAULT_ATA=$(spl-token address --token $MINT --owner $VAULT \
  --url https://api.devnet.solana.com --verbose \
  | awk '/Associated token address/ {print $NF}')

spl-token display $VAULT_ATA --url https://api.devnet.solana.com
```

```ts !! title="Kit" file=packages/docs-examples/tokenization/custodian/read-account.ts#region=read-account output=packages/docs-examples/tokenization/custodian/read-account.vault.output.txt

**State** must read `Initialized`. `Frozen` means the account is gated out and
any deposit or settlement touching it will fail.

</Step>

### Confirm what a pause does to the vault

A token-wide pause stops the vault along with everything else: in-flight
requests cannot settle while it holds.

```bash !! title="Mosaic CLI"

  --mint-address $MINT \
  --skip-warning \
  --keypair ~/.config/solana/demo-authorities/pause.json \

  --mint-address $MINT \
  --rpc-url https://api.devnet.solana.com

## Building the vault itself

The remaining decisions are set out in
[vault architectures](/docs/tokenization/custody/vault-architectures): whether
the design is synchronous or async, what is escrowed at request time, how the
cut-off is enforced, who may publish a valuation, and what happens to a request
that cannot settle.

If subscriptions or redemptions are to settle through the
[DvP program](/docs/tokenization/settlement/dvp-program), note that it rejects
mints carrying Scaled UI Amount, which the tutorials' template adds.
