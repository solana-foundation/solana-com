Your mint creates every token account frozen. This tutorial adds the gate: an
address you approve thaws itself against an onchain list, and an address you
have not approved cannot.

## How the pieces fit

Three programs cooperate:

1. **Token-2022** holds the mint and enforces that new accounts start frozen.
2. **The Token ACL program** holds the delegated freeze authority, through a
   per-mint config account, and exposes a permissionless thaw. It does not
   decide who qualifies.
3. **A gate program** makes that decision. With an address-based list as the
   gate, qualifying means being on the list.

Three overrides remain with the issuer: freeze or thaw an account directly, swap
the gate program, or reclaim the freeze authority from Token ACL.

### Confirm the gate is wired up

The `--enable-srfc37 true` flag in the previous tutorial provisioned all of this
inside the create transaction: it delegated the freeze authority to the Token
ACL mint config, created the address-based list, pointed the gate at it, and
enabled permissionless thaw. Confirm that before adding anyone.

```bash !! title="Mosaic CLI" output=packages/docs-examples/tokenization/issuing/inspect-mint-gated.output.txt
mosaic inspect-mint \
  --mint-address $MINT \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

`Freeze Authority` should read `$MINT_CONFIG`, the Token ACL mint config for
this mint. That address is a program derived address owned by the Token ACL
program (`TACLkU6CiCdkQN2MjoyDkVg2yAH9zkxiHDsiztQ52TP`); it is not the program
ID itself. In the SDK tab, `tokenAcl` is `true` and `aclMode` is `allowlist`;
the Kit, Legacy, and Rust tabs print `tokenAcl: true` and the gating program.

If the freeze authority is your own key or none, the mint was created without
`--enable-srfc37 true`, and as it stands nothing can thaw an account through the
gate. Whether that is recoverable depends on which of the two it is; the note
below covers both cases.

<Accordions>
<Accordion title="Wiring the gate on a mint that was created without it">

Start from the `Freeze Authority` row in the `inspect-mint` output above. What
it says decides whether the mint can be rescued at all:

- **Your own key** - recoverable. `mosaic token-acl create` signs with that key
  and delegates the freeze authority to the mint config as part of creating it.
  Run all four commands below.
- **A Token ACL mint config** - the config already exists. Skip the first
  command and run the other three as needed.
- **None** - a freeze authority cannot be restored once it is unset. Nothing can
  thaw an account, so the mint cannot be gated. Create a new one.

Do not move the freeze authority with `spl-token authorize` first. The Token ACL
program requires the current freeze authority to sign its `create` instruction
and sets the new authority itself; a freeze authority pointed at the program ID
by hand cannot sign anything, and the mint is then unrecoverable.

These commands do what `--enable-srfc37 true` does automatically, and take
`--mint` rather than `--mint-address`:

```bash
# Create the Token ACL config for the mint. Signs with the current freeze
# authority and delegates it to the mint config.
mosaic token-acl create \
  --mint $MINT \
  --gating-program GATEzzqxhJnsWF6vHRsgtixxSB8PaQdcqGEVTEHWiULz \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com

# Create the address-based list that acts as the gate
mosaic abl create-list \
  --mint $MINT \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com

# Register the list's extra account metas so a thaw can resolve it
mosaic abl set-extra-metas \
  --mint $MINT \
  --list <the List Config printed by create-list> \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com

# Allow qualifying wallets to self-thaw
mosaic token-acl enable-permissionless-thaw \
  --mint $MINT \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com
```

Run `mosaic token-acl --help` and `mosaic abl --help` for the current commands
and flags - the CLI is pre-1.0 at the time of writing, and the flags vary by
command.

</Accordion>
</Accordions>

If permissionless thaw was never enabled on the mint config, `mosaic mint` still
builds the thaw instruction and the transaction fails onchain. Confirm the gate
before minting.

</Step>

### Create a holder to approve

Generate a second keypair to stand in for an onboarded client, and fund it so it
can pay its own transaction fees.

```bash
solana-keygen new --no-bip39-passphrase --silent \
  --outfile ~/.config/solana/demo-holder.json

export HOLDER=$(solana-keygen pubkey ~/.config/solana/demo-holder.json)
solana airdrop 1 $HOLDER --url https://api.devnet.solana.com
echo "holder: $HOLDER"
```

<Step>
### Mint to the holder

Minting creates the holder's token account and thaws it in the same transaction:
`mosaic mint` inserts the Token ACL permissionless thaw between the account
creation and the mint, and the gate program approves it because the holder is on
the list. If the holder is not on the list the whole transaction fails, so there
is no partially minted state.

This should fail. `mosaic transfer` inserts a permissionless thaw for the new
account, Token ACL hands the decision to the gate program, and the gate rejects
a wallet that is not on the list with `Custom program error: #4098` (`0x1002` in
the Legacy and Rust output). The transfer instruction never runs. The decoded
mint config and the list address printed above the error are debugging output
the 0.2.0 CLI emits on this path.

Now add the outsider to the list and run the same transfer again. It succeeds.
The only change was the onboarding decision recorded on the list.

## Blocklists

The same gate supports a blocklist instead of an allowlist, where every address
qualifies except those you name:

```bash
mosaic blocklist add \
  --mint-address $MINT \
  --account <address> \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com
```

An allowlist fails closed: an address holds the token only after it has been
added. A blocklist fails open: an address holds the token unless it has been
named. A blocklist suits cases where open holding is the intended design and the
list acts as a sanctions overlay.
