This tutorial creates the mint. When you finish, you will have a Token-2022 mint
on devnet carrying the extension set Mosaic's tokenized-security template
configures, gated by an onchain allowlist, with pause, permanent delegate,
permissioned burn and metadata on separate keys. The mint, Confidential Balances
and scaled UI amount authorities stay on the fee payer.

<Steps>

<Step>
### Generate a key per authority

This step produces four separate keys, one per operational power. If one key
holds every power, one compromise exposes all of them.

```bash
mkdir -p ~/.config/solana/demo-authorities

for role in metadata pause delegate burn; do
  solana-keygen new --no-bip39-passphrase --silent \
    --outfile ~/.config/solana/demo-authorities/$role.json
  echo "$role: $(solana-keygen pubkey ~/.config/solana/demo-authorities/$role.json)"
done
```

In production each can sit in its own custody arrangement, for example: an
incident-response key for pause, a legal and compliance quorum for the permanent
delegate, a redemption-operations key for permissioned burn, a low-privilege
operations key for metadata. The tutorial uses local files so the separation is
visible as you work through it.

<Callout type="warn">

The mint authority is the exception. Mosaic provisions the Token ACL gate in the
create transaction only when the mint authority is the same key that pays for
it, so this tutorial leaves the mint authority on your fee payer. That is a
property of the toolkit. A supervised issuance should hold the mint authority on
a treasury quorum. Assigning it separately means building the instruction
yourself; see
[program and authority design](/docs/tokenization/design/program-and-authority-design).

</Callout>

<Step>
### Create the mint

The `tokenized-security` template enables the extension set described below.
Point each authority flag at the key you generated for it.

<CodeTabs storage="tokenization" flags="r">

```ts !! title="Mosaic SDK" file=packages/docs-examples/tokenization/issuing/create-the-mint.ts#region=create

```

```ts !! title="Kit" file=packages/docs-examples/tokenization/issuing/create-the-mint-kit.ts#region=create

```

```ts !! title="Legacy" file=packages/docs-examples/tokenization/issuing/create-the-mint-legacy.ts#region=create

```

```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/create-the-mint.rs#region=create

```

```bash !! title="Mosaic CLI"
mosaic create tokenized-security \
  --name "Demo Tokenized Note" \
  --symbol "DEMOTN" \
  --decimals 6 \
  --uri https://example.com/demotn.json \
  --acl-mode allowlist \
  --enable-srfc37 true \
  --metadata-authority $(solana-keygen pubkey ~/.config/solana/demo-authorities/metadata.json) \
  --pausable-authority $(solana-keygen pubkey ~/.config/solana/demo-authorities/pause.json) \
  --permanent-delegate-authority $(solana-keygen pubkey ~/.config/solana/demo-authorities/delegate.json) \
  --permissioned-burn-authority $(solana-keygen pubkey ~/.config/solana/demo-authorities/burn.json) \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

<Callout type="warn">

At `@solana/mosaic-cli@0.2.0` this command fails before sending, with
`mintAuthority must be a TransactionSigner<string> (or undefined) when TokenMetadata extension is present`.
The CLI passes the mint authority as an address and the SDK requires a signer.
Run the SDK tab to create the mint; it passes the fee payer as the signing mint
authority. The CLI command shows the intended usage. See the defect list in
[the issuing tutorials overview](/docs/tokenization/tutorials/issuing#before-you-start).

</Callout>

In the Mosaic CLI tab, two flags have defaults that a gated issuance needs to
change.

`--enable-srfc37 true` makes the mint usable. It delegates the freeze authority
to the Token ACL program's mint config for this mint, a program derived address,
which is then the only party that can thaw a frozen account. **Omit it and the
mint is created with frozen-by-default accounts but no Token ACL gate to thaw
them, so no account can hold the token.** The flag defaults to off. Recovering
from that depends on where the freeze authority ended up - see the recovery note
in [gate the holders](/docs/tokenization/tutorials/issuing/gate-the-holders).

`--acl-mode allowlist` selects a fail-closed gate: nobody holds the token until
they are added. The default is `blocklist`, which fails open. Because the mint
authority here is also the fee payer, this one transaction also creates the
Token ACL config, creates the list, points the gate at it, and enables
permissionless thaw - so the next tutorial starts with a working gate.

The SDK, Kit, Legacy, and Rust tabs print three addresses you need for the rest
of the section: the mint, the allowlist, and the Token ACL mint config; the left
column shows the labels the CLI prints once its create defect is fixed. Export
all three.

```bash
# CLI output:                                    script output:
#   Mint Address:                                  Mint:
#   Allowlist Address:                             Allowlist:
#   SRFC-37 allowlist mint config Address:         Freeze authority (Token ACL mint config):
export MINT=<the mint>
export LIST=<the list>
export MINT_CONFIG=<the mint config>
```

</Step>

<Step>
### Review the template's extensions

The `tokenized-security` template configures these Token-2022 extensions:

| Extension             | Effect                                                                                                                                 | Reference                                                               |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Default Account State | Every new token account is created frozen                                                                                              | [Default state](/docs/tokens/extensions/default-state)                  |
| Metadata              | Name, symbol, and URI stored onchain                                                                                                   | [Metadata](/docs/tokens/extensions/metadata)                            |
| Pausable              | One action halts mint, burn, and transfer                                                                                              | [Pausable](/docs/tokens/extensions/pausable)                            |
| Permanent Delegate    | Forced transfer and forced burn from any account                                                                                       | [Permanent delegate](/docs/tokens/extensions/permanent-delegate)        |
| Permissioned Burn     | A holder's burn needs the burn authority's co-signature                                                                                | [Permissioned burn](/docs/tokens/extensions/permissioned-burn)          |
| Scaled UI Amount      | A multiplier applied to displayed balances; the [DvP program](/docs/tokenization/settlement/dvp-program) does not accept mints with it | [Scaled UI amount](/docs/tokens/extensions/scaled-ui-amount)            |
| Confidential Balances | Balances and amounts can be hidden from the public ledger                                                                              | [Confidential transfers](/docs/tokens/extensions/confidential-transfer) |

**Permissioned burn** makes redemption a two-party operation: a holder cannot
extinguish their own balance without the burn authority signing alongside them.
It suits a redemption process with an off-chain settlement leg, and it is fixed
at creation. If holders must be able to burn unilaterally, this template does
not fit; use a different template or build the mint directly - see
[choosing controls](/docs/tokenization/design/choosing-controls).

**Scaled UI amount** allows an accrual or a corporate action to change every
holder's displayed balance without a transfer. It can only be enabled when the
mint is created. Carrying it unused does not change any balance, but it does
appear on the mint, so it belongs in the extension-by-extension support
confirmation described in
[custody integration](/docs/tokenization/custody/custody-integration). The
template always adds it, with the multiplier authority on the mint authority
(your fee payer here). A mint without it needs a different template or direct
instruction building.

**Confidential Balances** is configured by the template but not active for any
holder until that holder configures their account and the confidential transfer
authority approves it. Activating it requires client-side zero-knowledge proof
handling on every confidential operation, and it changes what the permanent
delegate can reach.
[Confidential transfers](/docs/tokens/extensions/confidential-transfer) and
[privacy and transfer controls](/docs/tokenization/compliance/privacy-and-transfer-controls)
cover both.

<Callout type="warn">

The Mosaic CLI has no `set-authority` command. Authorities are assigned when the
mint is created, and rotating them afterwards - including moving the mint
authority off your fee payer - means using the SDK's
`getUpdateAuthorityTransaction` or building the instruction yourself. Decide
your authority layout before you run the create command.

</Callout>

</Step>

<Step>
### Confirm what you built

Read the mint back and check the extensions and authorities against what you
intended. The CLI reads the Token-2022 mint; the script tabs add the Token ACL
view, which the CLI does not print: the SDK tab as `aclMode` and `tokenAcl`, the
Kit, Legacy, and Rust tabs as `tokenAcl`, `gatingProgram`, and
`permissionlessThaw`.

```bash !! title="Mosaic CLI" output=packages/docs-examples/tokenization/issuing/inspect-mint-created.output.txt
mosaic inspect-mint \
  --mint-address $MINT \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

Check four things:

1. Under **Mint Details**, `Mint Authority` is your fee payer. That is expected
   here, per the note above.
2. **`Freeze Authority` is `$MINT_CONFIG`, the Token ACL mint config for this
   mint - not your own key and not none.** If it is anything else,
   `--enable-srfc37 true` did not take effect and the mint is unusable - create
   a new one.
3. In the CLI tab, the `PermanentDelegate` delegate and `PausableConfig`
   authority under **Extension Details** and the `Update Authority` under
   **Metadata** are three different addresses, each matching the key you passed.
   The SDK tab shows them under `authorities` (`permanentDelegate`,
   `pausableAuthority`, `updateAuthority`), with `permissionedBurnAuthority` as
   a fourth.
4. In the CLI tab, `DefaultAccountState` shows `State: 2`, which is Frozen, and
   the extension list matches the table above. The CLI lists `MetadataPointer`
   and `TokenMetadata` for the metadata row and `Pausable` and `PausableConfig`
   for the pausable row. In the SDK tab, `aclMode` is `allowlist` and `tokenAcl`
   is `true`; the Kit, Legacy, and Rust tabs print `tokenAcl: true` and
   `permissionlessThaw: true`.

The CLI's `Token Type Detection` section knows only Mosaic's stablecoin and
arcade templates, so it labels this mint a stablecoin. The SDK tab's `patterns`
field lists `tokenized-security` alongside `stablecoin`.

If one of the operational authorities came back as your fee-payer address rather
than the key you passed, that flag did not take effect. Create a new mint rather
than correcting it; on devnet the cost is negligible.
