You have a mint and an allowlist. This tutorial runs each power an issuer
operates day to day once, on devnet, against the token from the previous two
tutorials.

Note which key signs each one: pause, forced transfer, and burn use the
dedicated authorities from the first tutorial, while the gate operations use
your fee payer.

<Steps>

<Step>
### Freeze one account

Freezing targets a single holder. Use it when one account needs to stop and the
rest of the token should keep working - a suspected compromise, a client under
investigation, an account pending re-documentation.

The CLI command takes the holder's **token account**, not their wallet, so
derive it first. The script tabs take the wallet and derive the account.

<CodeTabs storage="tokenization" flags="r">

```ts !! title="Mosaic SDK" file=packages/docs-examples/tokenization/issuing/freeze.ts#region=freeze

```

```ts !! title="Kit" file=packages/docs-examples/tokenization/issuing/freeze-kit.ts#region=freeze

```ts !! title="Legacy" file=packages/docs-examples/tokenization/issuing/freeze-legacy.ts#region=freeze

```

```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/freeze.rs#region=freeze

```

```bash !! title="Mosaic CLI"
export HOLDER_ATA=$(spl-token address --token $MINT --owner $HOLDER \
  --url https://api.devnet.solana.com --verbose \
  | awk '/Associated token address/ {print $NF}')

mosaic token-acl freeze \
  --token-account $HOLDER_ATA \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

<Callout type="warn">

At `@solana/mosaic-cli@0.2.0`, `token-acl freeze` and `token-acl thaw` are
present in the CLI source but not registered as subcommands, so the CLI tab
returns an unknown-command error. The SDK, Kit, Legacy, and Rust tabs perform
the same operation and run; the SDK tab uses `getFreezeWalletTransaction`. Check
`mosaic token-acl --help` on the version you install.

</Callout>

tutorial, and in Mosaic that removal also freezes the existing account.

<Step>
### Pause the whole token

Pausing halts mint, burn, and transfer activity across every holder at once.
This is the incident-response control. Its authority needs to be reachable on
the timescale an incident requires.

Without `--skip-warning`, the CLI prints what a pause does and exits without
sending anything. A runbook script has to pass the flag to execute the pause.

<Step>
### Force a transfer

The permanent delegate can move any holder's balance without their signature.
This is the power used to comply with a court order, to recover from a lost key,
and to move a balance after a fraudulent transfer. It moves tokens onward; the
original transfer remains on the ledger.

<CodeTabs storage="tokenization" flags="r">

```ts !! title="Mosaic SDK" file=packages/docs-examples/tokenization/issuing/force-transfer.ts#region=force-transfer

```

```ts !! title="Kit" file=packages/docs-examples/tokenization/issuing/force-transfer-kit.ts#region=force-transfer

```

```ts !! title="Legacy" file=packages/docs-examples/tokenization/issuing/force-transfer-legacy.ts#region=force-transfer

```

```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/force-transfer.rs#region=force-transfer

```

```bash !! title="Mosaic CLI"
mosaic force-transfer \
  --mint-address $MINT \
  --from-account $HOLDER \
  --recipient $OUTSIDER \
  --amount 10 \
  --keypair ~/.config/solana/demo-authorities/delegate.json \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

<Callout type="warn">

At `@solana/mosaic-cli@0.2.0`, `force-transfer` builds the transaction with the
delegate as an address rather than a signer and fails with
`Transaction is missing signatures`. The SDK, Kit, Legacy, and Rust tabs run.

</Callout>

The destination still has to be able to hold the token. Mosaic inserts a
permissionless thaw for a new or frozen destination account, and the gate
rejects it if the wallet is not on the list, so a forced transfer to an unlisted
wallet fails with the same `#4098` as a blocked transfer. Move the balance to a
listed recovery wallet.

This works here because no holder has opted into confidential transfers. On a
mint where a holder has moved a balance into the confidential extension, the
delegate reaches the public balance only - see
[privacy and transfer controls](/docs/tokenization/compliance/privacy-and-transfer-controls#which-controls-still-work).

In this tutorial the permanent delegate sits on its own keypair. In production,
holding it offline and behind a quorum reduces the chance that a compromise of
day-to-day operations keys reaches it.

</Step>

<Step>
### Redeem with the holder

This mint carries permissioned burn, so a holder cannot burn their own balance
alone: the burn authority co-signs. On this mint, that is the redemption path -
the holder instructs, the issuer confirms the off-chain leg has settled, and the
two signatures extinguish the position together.

<CodeTabs storage="tokenization" flags="r">

```ts !! title="Mosaic SDK" file=packages/docs-examples/tokenization/issuing/burn.ts#region=burn

```

```ts !! title="Kit" file=packages/docs-examples/tokenization/issuing/burn-kit.ts#region=burn

```

```ts !! title="Legacy" file=packages/docs-examples/tokenization/issuing/burn-legacy.ts#region=burn

```

```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/burn.rs#region=burn

```

```bash !! title="Mosaic CLI"
mosaic burn \
  --mint-address $MINT \
  --amount 1 \
  --keypair ~/.config/solana/demo-holder.json \
  --permissioned-burn-keypair ~/.config/solana/demo-authorities/burn.json \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

Run the command without `--permissioned-burn-keypair` and it stops before
sending, reporting that the mint's burn authority differs from the signer.

</Step>

<Step>
### Burn without the holder

The permanent delegate can burn a balance without the holder's signature, for
redemptions where there is no cooperating holder - a lost key, an unresponsive
account, a position being extinguished under a court order. Because the mint
carries permissioned burn on a separate key, the burn authority co-signs this
path too.

<CodeTabs storage="tokenization" flags="r">

```ts !! title="Mosaic SDK" file=packages/docs-examples/tokenization/issuing/force-burn.ts#region=force-burn

```

```ts !! title="Kit" file=packages/docs-examples/tokenization/issuing/force-burn-kit.ts#region=force-burn

```

```ts !! title="Legacy" file=packages/docs-examples/tokenization/issuing/force-burn-legacy.ts#region=force-burn

```

```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/force-burn.rs#region=force-burn

```

```bash !! title="Mosaic CLI"
mosaic force-burn \
  --mint-address $MINT \
  --from-account $OUTSIDER \
  --amount 1 \
  --keypair ~/.config/solana/demo-authorities/delegate.json \
  --permissioned-burn-keypair ~/.config/solana/demo-authorities/burn.json \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

Token-2022 does not burn from a frozen account. Where the account has been
frozen, or its wallet offboarded, thaw it first or re-add the wallet for the
duration of the burn. Mosaic inserts that thaw itself, and the gate rejects it
for an unlisted wallet.

<Callout type="warn">

Permissioned burn is fixed at creation and cannot be removed without a new mint.
Pointing `--permissioned-burn-authority` at the permanent delegate's key at
creation lets one signer cover both roles on a forced burn; keeping them
separate, as this tutorial does, means every extinguishment of supply has two
signatures behind it. Both are in use.

</Callout>

Where the token records an asset held elsewhere, record each burn in the
off-chain register with a shared reference; see
[token design](/docs/tokenization/design).

</Step>

<Step>
### Offboard a holder

Offboarding removes the wallet from the allowlist. In Mosaic, the same
transaction also freezes the wallet's associated token account if it is
initialized and thawed, so an offboarded holder can neither receive nor send.

<CodeTabs storage="tokenization" flags="r">

```ts !! title="Kit" file=packages/docs-examples/tokenization/issuing/allowlist-remove-kit.ts#region=allowlist-remove

```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/allowlist-remove.rs#region=allowlist-remove

```bash !! title="Mosaic CLI"
mosaic allowlist remove \
  --mint-address $MINT \
  --account $OUTSIDER \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

scripts print the raw amount in base units: 10 tokens at six decimals prints as
10000000:

  | awk '/Associated token address/ {print $NF}')

```

```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/read-account.rs#region=read-account output=packages/docs-examples/tokenization/rust/src/bin/read-account.offboarded.output.txt

```

</CodeTabs>

Two limits to plan around. Mosaic freezes the associated token account only; a
wallet holding the token in other accounts needs each frozen separately.
Re-adding the wallet through the Mosaic CLI or SDK also thaws its account in the
same transaction; the Kit, Legacy, and Rust scripts add the entry only.

A forced transfer to a recovery wallet or a forced burn both need the source
account thawed, so sequence them before the removal, or re-add the wallet for
the duration.

</Step>
