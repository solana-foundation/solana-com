You have a mint and an allowlist. This tutorial exercises the powers an issuer
runs day to day, so each is exercised once on devnet before it is needed in
production.

Run these on devnet against the token from the previous two tutorials. Note
which key signs each one: pause, forced transfer, and burn use the dedicated
authorities from the first tutorial, while the gate operations use your fee
payer.

<Steps>

<Step>
### Freeze one account

Freezing targets a single holder. Use it when one account needs to stop and the
rest of the token should keep working - a suspected compromise, a client under
investigation, an account pending re-documentation.

The CLI command takes the holder's **token account**, not their wallet, so
derive it first. The SDK call takes the wallet and derives the account itself.

<CodeTabs storage="tokenization" flags="r">

```bash !! title="Mosaic CLI"
export HOLDER_ATA=$(spl-token address --token $MINT --owner $HOLDER \
  --url https://api.devnet.solana.com --verbose \
  | awk '/Associated token address/ {print $NF}')

mosaic token-acl freeze \
  --token-account $HOLDER_ATA \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com
```

<Step>
### Pause the whole token

Pausing halts mint, burn, and transfer activity across every holder at once.
This is the incident-response control. Its authority needs to be reachable on
the timescale an incident requires.

Without `--skip-warning`, the CLI prints what a pause does and exits without
sending anything. The flag is what executes the pause, so a runbook script has
to pass it.

<CodeTabs storage="tokenization" flags="r">

```bash !! title="Mosaic CLI" output=packages/docs-examples/tokenization/issuing/control-status-paused.output.txt
mosaic control pause \
  --mint-address $MINT \
  --skip-warning \
  --keypair ~/.config/solana/demo-authorities/pause.json \
  --rpc-url https://api.devnet.solana.com

mosaic control status \
  --mint-address $MINT \
  --rpc-url https://api.devnet.solana.com
```

<Step>
### Force a transfer

The permanent delegate can move any holder's balance without their signature.
This is the power used to comply with a court order, to recover from a lost key,
and to move a balance after a fraudulent transfer. It moves tokens onward; the
original transfer remains on the ledger.

<CodeTabs storage="tokenization" flags="r">

```bash !! title="Mosaic CLI"
mosaic force-transfer \
  --mint-address $MINT \
  --from-account $HOLDER \
  --recipient $OUTSIDER \
  --amount 10 \
  --keypair ~/.config/solana/demo-authorities/delegate.json \
  --rpc-url https://api.devnet.solana.com
```

<Callout type="warn">

At `@solana/mosaic-cli@0.2.0`, `force-transfer` builds the transaction with the
delegate as an address rather than a signer and fails with
`Transaction is missing signatures`. The SDK tab runs.

</Callout>

The destination still has to be able to hold the token. Mosaic inserts a
permissionless thaw for a new or frozen destination account, and the gate
rejects it if the wallet is not on the list, so a forced transfer to an unlisted
wallet fails with the same `#4098` as a blocked transfer. Move the balance to a
listed recovery wallet.

This works here because no holder has opted into confidential transfers. On a
mint where a holder has moved a balance into the confidential extension, the
delegate reaches the public balance only - see
[privacy and transfer controls](/docs/tokenization/compliance/privacy-and-transfer-controls#which-controls-still-work).

Each use needs a documented authorization trail created before the transaction
is signed. Holding the key offline and behind a quorum reduces the chance that a
compromise of day-to-day operations keys reaches it, which is why it sits on its
own keypair.

</Step>

<Step>
### Redeem with the holder

This mint carries permissioned burn, so a holder cannot burn their own balance
alone: the burn authority co-signs. That is the ordinary redemption path - the
holder instructs, the issuer confirms the off-chain leg has settled, and the two
signatures extinguish the position together.

<CodeTabs storage="tokenization" flags="r">

```bash !! title="Mosaic CLI"
mosaic burn \
  --mint-address $MINT \
  --amount 1 \
  --keypair ~/.config/solana/demo-holder.json \
  --permissioned-burn-keypair ~/.config/solana/demo-authorities/burn.json \
  --rpc-url https://api.devnet.solana.com
```

<Step>
### Burn without the holder

The permanent delegate can burn a balance without the holder's signature, for
redemptions where there is no cooperating holder - a lost key, an unresponsive
account, a position being extinguished under a court order. Because the mint
carries permissioned burn on a separate key, the burn authority co-signs this
path too.

<CodeTabs storage="tokenization" flags="r">

```bash !! title="Mosaic CLI"
mosaic force-burn \
  --mint-address $MINT \
  --from-account $OUTSIDER \
  --amount 1 \
  --keypair ~/.config/solana/demo-authorities/delegate.json \
  --permissioned-burn-keypair ~/.config/solana/demo-authorities/burn.json \
  --rpc-url https://api.devnet.solana.com
```


```rust !! title="Rust" file=packages/docs-examples/tokenization/rust/src/bin/force-burn.rs#region=force-burn

```

</CodeTabs>

Token-2022 does not burn from a frozen account. Where the account has been
frozen, or its wallet offboarded, thaw it first or re-add the wallet for the
duration of the burn. Mosaic inserts that thaw itself, and the gate rejects it
for an unlisted wallet.

<Callout type="warn">

Permissioned burn is fixed at creation and cannot be removed without a new mint.
Pointing `--permissioned-burn-authority` at the permanent delegate's key at
creation lets one signer cover both roles on a forced burn; keeping them
separate, as this tutorial does, means every extinguishment of supply has two
signatures behind it. Both are in use. Record which one the mint uses.

</Callout>

What a burn completes depends on where your register of record sits. Where the
mint is the register, the burn is the redemption and the liability is
extinguished when the transaction finalizes. Where the token records an asset
held elsewhere, the burn records a redemption that also has to happen in the
off-chain register, and the two need a shared reference so the pair can be
reconciled afterwards. See [token design](/docs/tokenization/design).

</Step>

<Step>
### Offboard a holder

Offboarding removes the wallet from the allowlist. In Mosaic, the same
transaction also freezes the wallet's associated token account if it is
initialized and thawed, so an offboarded holder can neither receive nor send.

<CodeTabs storage="tokenization" flags="r">

```bash !! title="Mosaic CLI"
mosaic allowlist remove \
  --mint-address $MINT \
  --account $OUTSIDER \
  --keypair ~/.config/solana/tokenization-demo.json \
  --rpc-url https://api.devnet.solana.com
```

Two limits to plan around. Mosaic freezes the associated token account only; a
wallet holding the token in other accounts needs each frozen separately. And
adding the wallet back to the list thaws the account again in the same
transaction, so re-onboarding is one operation as well.

Decide before offboarding what happens to the balance. A forced transfer to a
recovery wallet or a forced burn both need the source account thawed, so
sequence them before the removal, or re-add the wallet for the duration.

</Step>

## Scaled UI amount and reconciliation

On a mint carrying the scaled UI amount extension, the raw balance stored
onchain differs from the balance a holder owns. A multiplier is applied for
display, and it changes each time a new one is struck.

<Callout type="warn">

Supply, holdings, and valuations on a mint that uses scaled UI amount need the
current multiplier applied to the raw onchain amount. Tooling that reads the raw
value without applying the multiplier reports positions that are off by it, in
either direction, since a multiplier can be below one. Check against
[scaled UI amount](/docs/tokens/extensions/scaled-ui-amount) before building a
reconciliation process on a third-party figure.

</Callout>

## Procedures to settle before mainnet

The commands above are the mechanism. The operating procedure around them is
specific to each issuer:

| Power             | Decide                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| Freeze            | Who can request, who approves, how the holder is told                                                         |
| Pause             | Trigger conditions, who is reachable, unwind and communication                                                |
| Force transfer    | Evidence required before signing, quorum, where the record lives                                              |
| Permissioned burn | What evidence of the off-chain settlement leg the burn authority needs before co-signing, and its turnaround  |
| Forced burn       | Evidence required before signing, and how the redemption is recorded off-chain                                |
| Offboarding       | Who decides, what happens to the balance first, and how the holder is told                                    |
| Mint and burn     | In a mirror structure, which movement in the underlying authorizes each, and who evidences the correspondence |
| Every power       | Key custody, rotation procedure, and rehearsal schedule                                                       |

Rotation is worth rehearsing in particular. The Mosaic CLI has no
`set-authority` command; the SDK's `getUpdateAuthorityTransaction` builds the
instruction. Run authority rotation on devnet through the path intended for
production before it is needed.
