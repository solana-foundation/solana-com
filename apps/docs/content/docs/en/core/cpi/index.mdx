## In short

<ConceptShort />

<ConceptUsedIn />

A cross-program invocation (CPI) is one [program](/developers/docs/core/programs)
calling an [instruction](/developers/docs/core/instructions) on another while it runs.
Any program can call any other program's instructions.

## Key facts

- **Privilege extension**: Account privileges (signer, writable) extend from
  caller to callee. A callee cannot escalate privileges
  beyond what the caller passed.
- **Shared compute budget**: A callee's CU consumption reduces the caller's
  remaining budget.
- **Reentrancy**: Direct self-recursion is allowed (A->A->A). Indirect
  reentrancy is not (A->B->A returns `ReentrancyNotAllowed`).

<Security title="Verify the program you invoke">
  The program you CPI into is an account the caller passes in. If your
  program invokes whatever account sits in the `token_program` position, an
  attacker can pass their own program. It receives every account and
  privilege you forward, can return success without doing the work, and can
  use your users' signatures. Check the program ID before invoking:

  ```rust title="Native Rust"
  if token_program.key != &spl_token::ID {
      return Err(ProgramError::IncorrectProgramId);
  }
  ```

  In Anchor, `Program<'info, Token>` checks the ID for one program, and
  `Interface<'info, TokenInterface>` accepts either the Token Program or the
  Token Extensions Program. Instruction builders such as
  `system_instruction::transfer` hard-code the program ID, which is safe as
  long as you don't overwrite it.
</Security>

<Security title="Forward only the privileges the callee needs">
  Signer and writable privileges pass from caller to callee for the duration
  of the CPI. Passing a user's signer account into a program you don't
  control gives that program the user's signature for anything it does
  during the call, including CPIs of its own. Forward signer accounts only
  to programs you trust, and only the accounts that instruction needs.
</Security>

## `invoke` vs `invoke_signed`

| Function        | Use case                                                                     | PDA signing           |
| --------------- | ---------------------------------------------------------------------------- | --------------------- |
| `invoke`        | CPIs where all required signers have already signed the original transaction | No                    |
| `invoke_signed` | CPIs where the calling program needs to sign on behalf of a PDA it owns      | Yes, via signer seeds |

`invoke` is `invoke_signed` with an empty signer seeds array. Both use the same
syscall
([`sol_invoke_signed_rust`](https://github.com/anza-xyz/agave/blob/v3.1.8/syscalls/src/cpi.rs#L11-L33))
and runtime path
([`cpi_common`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/cpi.rs#L802-L925)).
When seeds are provided, the runtime derives the PDA addresses and adds them to
the valid signers before checking privileges.
