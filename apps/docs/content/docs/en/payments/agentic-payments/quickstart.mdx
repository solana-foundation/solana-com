---
title: "Quickstart: pay for an API"
description:
  Make a sandbox agentic payment, inspect the HTTP 402 exchange, and run a local
  paid API gateway without moving real funds.
---

Use the `pay` CLI to make a sandbox payment and see the complete `402` flow. The
sandbox uses temporary local accounts, so no real funds move.

You need a terminal and either Homebrew or Node.js 20 or later.

## 1. Install Pay

On macOS, install the prebuilt binary:

```bash
brew install pay
```

On other platforms, install the npm package:

```bash
npm install --global @solana/pay
```

Verify the command and create a locally protected signing account:

```bash
pay --version
pay setup
pay whoami
```

`pay setup` keeps signing outside the agent process and configures an approval
mechanism available on your operating system. Rejecting the approval prompt
cancels the payment.

## 2. Inspect an unpaid MPP request

Call the endpoint with ordinary `curl`:

```bash
curl -i https://debugger.pay.sh/mpp/quote/AAPL
```

The response has status `402 Payment Required`, a `WWW-Authenticate: Payment`
challenge, and a problem-details body. No payment occurs.

Now wrap the same request with `pay`:

```bash
pay --sandbox curl https://debugger.pay.sh/mpp/quote/AAPL
```

The CLI reads the challenge, displays the payment for approval, signs with the
local account, and retries with an `Authorization: Payment` credential. The
server settles the sandbox transfer and returns the quote with a
`Payment-Receipt` header.

<Callout type="info">
  Do not copy a challenge or construct a credential by hand. Use a protocol
  client so request binding, expiry, encoding, and replay protection remain
  intact.
</Callout>

## 3. Run a paid API locally

Open two terminals. In the first, start the bundled sandbox gateway and payment
debugger:

```bash
pay --sandbox server demo
```

The command writes a sample paywall specification, starts a local server, and
prints the paid routes it exposes. Keep this terminal running.

In the second terminal, copy one of the printed routes and request it first with
`curl`, then with `pay curl`:

```bash
curl -i http://127.0.0.1:1402/api/v1/reports/usage
pay --sandbox curl http://127.0.0.1:1402/api/v1/reports/usage
```

The first command should return `402`; the second should return the resource.
Open the debugger URL printed by the server to inspect the challenge,
authorization, settlement, and retry as separate events.

## 4. Put the gateway in front of an API

The generated YAML file is a starting point for a provider. A paid route names
the HTTP method and path, then defines what one unit costs:

```yaml filename=paywall.yml
name: example-api
subdomain: example-api
title: Example API
description: Example paid endpoint
category: data
version: v1

routing:
  type: proxy
  url: http://127.0.0.1:3000/

endpoints:
  - method: GET
    path: v1/report
    description: Generate one report
    metering:
      schemes: [mpp-charge, x402-exact]
      dimensions:
        - direction: usage
          unit: requests
          scale: 1
          tiers:
            - price_usd: 0.01
```

Validate and run it in the sandbox:

```bash
pay --sandbox server start paywall.yml --bind 127.0.0.1:1402
```

The gateway accepts either advertised protocol, verifies payment before proxying
to the upstream API, and keeps payment credentials away from the upstream
service.

## 5. Use the wallet with an agent

You can launch a supported coding agent through the same payment boundary:

```bash
pay codex
# or
pay claude
```

The agent can discover and request a paid endpoint, but the wallet still
enforces its signing and approval policy. Before using real funds, configure
per-payment and cumulative limits, restrict allowed services, and test rejection
and timeout behavior.
