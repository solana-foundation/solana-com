Your mint creates every token account frozen. This tutorial makes that useful:
an address you approve thaws itself against an onchain list, and an address you
have not approved cannot.

## How the pieces fit

Three programs cooperate:

1. **Token-2022** holds the mint and enforces that new accounts start frozen.
2. **The Token ACL program** holds the delegated freeze authority and exposes a
   permissionless thaw. It does not decide who qualifies.
3. **A gate program** makes that decision. With an address-based list as the
   gate, qualifying means being on the list.

You keep an override at every level: freeze or thaw an account directly, swap
the gate program, or reclaim the freeze authority from Token ACL entirely.

<Callout type="warn">

Token ACL is specified in sRFC-37, which is not finalized. The gate program and
the list accounts are dependencies distinct from your mint, each with its own
deployment, upgrade, audit, and availability considerations. Read
[Token ACL](/docs/tokenization/token-acl) before relying on this design in
production.

</Callout>

<Steps>

<Step>
### Confirm the gate is wired up

The `--enable-srfc37 true` flag in the previous tutorial provisioned all of this
inside the create transaction: it delegated the freeze authority to Token ACL,
created the address-based list, pointed the gate at it, and enabled
permissionless thaw. Confirm that before adding anyone.

<CodeTabs flags="r">

```bash !! title="mosaic inspect-mint" output=packages/docs-examples/institutional/issuing/inspect-mint-gated.output.txt
mosaic inspect-mint \
  --mint-address $MINT \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

The freeze authority should read `TACLkU6CiCdkQN2MjoyDkVg2yAH9zkxiHDsiztQ52TP`,
the Token ACL program. If it is your own key or none, the mint was created
without `--enable-srfc37 true`, and as it stands nothing can thaw an account
through the gate. Whether that is recoverable depends on which of the two it is;
the note below covers both cases.

<Accordions>
<Accordion title="Wiring the gate on a mint that was created without it">

Start from the `Freeze` row in the `inspect-mint` output above. What it says
decides whether the mint can be rescued at all:

- **`TACLkU6CiCdkQN2MjoyDkVg2yAH9zkxiHDsiztQ52TP`** - the freeze authority is
  already delegated to Token ACL. The four commands below finish the wiring.
- **Your own key** - delegate it first with
  `spl-token authorize $MINT freeze TACLkU6CiCdkQN2MjoyDkVg2yAH9zkxiHDsiztQ52TP`,
  then run the four commands. The Mosaic CLI cannot move a freeze authority,
  which is why this step uses `spl-token`.
- **None** - a freeze authority cannot be restored once it is unset. Nothing can
  thaw an account, so the mint cannot be gated. Create a new one.

These four commands do what `--enable-srfc37 true` does automatically, and take
`--mint` rather than `--mint-address`:

```bash
# Create the Token ACL config, pointing it at the address-based list program
mosaic token-acl create-config \
  --mint $MINT \
  --keypair ~/.config/solana/institutional-demo.json \
  --rpc-url https://api.devnet.solana.com

# Create the address-based list that acts as the gate
mosaic abl create-list \
  --mint $MINT \
  --keypair ~/.config/solana/institutional-demo.json \
  --rpc-url https://api.devnet.solana.com

# Point the config at the gate program
mosaic token-acl set-gating-program \
  --mint $MINT \
  --gating-program GATEzzqxhJnsWF6vHRsgtixxSB8PaQdcqGEVTEHWiULz \
  --keypair ~/.config/solana/institutional-demo.json \
  --rpc-url https://api.devnet.solana.com

# Allow qualifying wallets to self-thaw
mosaic token-acl enable-permissionless-thaw \
  --mint $MINT \
  --keypair ~/.config/solana/institutional-demo.json \
  --rpc-url https://api.devnet.solana.com
```

You may also need `mosaic abl set-extra-metas` so the thaw can resolve the
list's extra account metas. Run `mosaic token-acl --help` and
`mosaic abl --help` for the current surface - the CLI is pre-1.0 and the flags
vary by command.

</Accordion>
</Accordions>

If permissionless thaw was never enabled on the mint config, `mosaic mint` still
builds the thaw instruction and the transaction fails onchain. Confirm the gate
before minting.

</Step>

<Step>
### Create a holder to approve

Generate a second keypair to stand in for an onboarded client, and fund it so it
can pay its own transaction fees.

```bash
solana-keygen new --no-bip39-passphrase --silent \
  --outfile ~/.config/solana/demo-holder.json

export HOLDER=$(solana-keygen pubkey ~/.config/solana/demo-holder.json)
solana airdrop 1 $HOLDER --url https://api.devnet.solana.com
echo "holder: $HOLDER"
```

</Step>

<Step>
### Add the holder to the allowlist

This step corresponds to the onboarding decision. The preceding steps are setup.

```bash
mosaic allowlist add \
  --mint-address $MINT \
  --account $HOLDER \
  --keypair ~/.config/solana/institutional-demo.json \
  --rpc-url https://api.devnet.solana.com
```

Read the list back to confirm. `abl fetch-list` takes the **list** address, not
the mint. That address is the `List` row in the `inspect-mint` output from the
first step of this page - export it now:

```bash
# Copy the List row from the inspect-mint output above
export LIST=6RnKpTvW2nXcJdYbQa5SgLoZe4UhSm7MyXi5B8CrPkWu
```

If you did not record it, `mosaic abl fetch-lists --mint-address $MINT` shows
every list for your mint.

<CodeTabs flags="r">

```bash !! title="mosaic abl fetch-list" output=packages/docs-examples/institutional/issuing/abl-fetch-list.output.txt
mosaic abl fetch-list \
  --list $LIST \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

</Step>

<Step>
### Mint to the holder

Minting creates the holder's token account and thaws it in the same transaction:
`mosaic mint` inserts the Token ACL permissionless thaw between the account
creation and the mint, and the gate program approves it because the holder is on
the list. If the holder is not on the list the whole transaction fails, so there
is no partially minted state.

```bash
mosaic mint \
  --mint-address $MINT \
  --recipient $HOLDER \
  --amount 1000 \
  --keypair ~/.config/solana/institutional-demo.json \
  --rpc-url https://api.devnet.solana.com
```

This signs with the fee payer, which holds the mint authority on this mint.
Where the mint authority sits on its own key - as it should in production - this
is the command that would use it, and no other key can create supply.

</Step>

<Step>
### Prove the gate rejects a non-holder

Test the rejection path. Generate a third address, leave it off the list, and
try to move tokens to it.

<CodeTabs flags="r">

```bash !! title="mosaic transfer" output=packages/docs-examples/institutional/issuing/transfer-blocked.output.txt
solana-keygen new --no-bip39-passphrase --silent \
  --outfile ~/.config/solana/demo-outsider.json

export OUTSIDER=$(solana-keygen pubkey ~/.config/solana/demo-outsider.json)

mosaic transfer \
  --mint-address $MINT \
  --recipient $OUTSIDER \
  --amount 1 \
  --keypair ~/.config/solana/demo-holder.json \
  --rpc-url https://api.devnet.solana.com
```

</CodeTabs>

This should fail. The outsider's token account is created frozen and has no
basis on which to thaw, so the transfer cannot complete. This failure
demonstrates the control.

Now add the outsider to the list and run the same transfer again. It succeeds.
The only change was the onboarding decision recorded on the list.

```bash
mosaic allowlist add \
  --mint-address $MINT \
  --account $OUTSIDER \
  --keypair ~/.config/solana/institutional-demo.json \
  --rpc-url https://api.devnet.solana.com
```

</Step>

<Step>
### Remove an address

Removal is the same operation in reverse.

```bash
mosaic allowlist remove \
  --mint-address $MINT \
  --account $OUTSIDER \
  --keypair ~/.config/solana/institutional-demo.json \
  --rpc-url https://api.devnet.solana.com
```

Removing an address from the list stops it from thawing a new account. An
account that is already thawed stays thawed; freezing an existing holder is a
separate action, covered in
[operate the token](/docs/institutional/tutorials/issuing/operate-the-token). An
offboarding procedure generally needs both steps.

</Step>

</Steps>

## Blocklists

The same gate supports a blocklist instead of an allowlist, where every address
qualifies except those you name:

```bash
mosaic blocklist add \
  --mint-address $MINT \
  --account <address> \
  --keypair ~/.config/solana/institutional-demo.json \
  --rpc-url https://api.devnet.solana.com
```

An allowlist fails closed: an address holds the token only after it has been
added. A blocklist fails open: an address holds the token unless it has been
named. Fail-closed is the behavior a supervised issuance normally needs. A
blocklist suits cases where open holding is the intended design and the list
acts as a sanctions overlay.
