This guide is for wallet service providers and developers who want to integrate
new key management solutions into the `solana-keychain` library. By adding your
signer implementation, you'll enable developers to use your service for secure
Solana transaction signing through a unified interface.

Keychain keeps its Rust, TypeScript, Python and Go implementations at parity.
PRs that include all four are strongly preferred. If you can only contribute
one, that's fine, but expect the others to be required before the signer ships
in a release.

_Using Claude Code? The repo's
[`add-signer-ci` skill](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)
wires up the CI workflows for a new signer contributed via a fork PR._

## Architecture Overview

The library uses a trait-based architecture defined in `src/traits.rs`. Every
signer implements the `SolanaSigner` base trait (`pubkey`, `sign_message`,
`is_available`) plus exactly one capability trait matching the provider's shape:

- `TransactionSigner` (`sign_transaction`): the provider signs the caller's
  bytes and the caller broadcasts. Most backends.
- `ModifyingSigner` (`modify_and_sign_transaction`): the provider rewrites the
  transaction, then signs it without broadcasting.
- `SendingSigner` (`sign_and_send_transaction`): the provider signs and
  broadcasts server-side.

The library also provides a unified `Signer` enum that wraps all
implementations, allowing runtime selection of signing backends. It implements
only the base trait; capabilities are reached through `as_transaction_signer()`,
`as_modifying_signer()` and `as_sending_signer()`.

## Quick Integration Checklist

- Create your signer module with implementation
- Implement the `SolanaSigner` base trait (`pubkey`, `sign_message`,
  `is_available`) plus the one capability trait matching your provider's shape
  (usually `TransactionSigner`)
- Add a feature flag in `Cargo.toml`, including the internal `_remote` marker if
  your signer uses reqwest
- Update the `Signer` enum in `src/lib.rs` (variant, `dispatch_signer!` arm, and
  an arm in the capability accessor matching your shape)
- Enforce HTTPS and configure timeouts on HTTP clients
- Sign the message bytes and verify the returned signature before attaching it
- Add comprehensive unit tests (wiremock-based, in your module)
- Add an integration test file and update `.env.example`
- Add the TypeScript, Python and Go implementations
- Update documentation
- CI workflow updates (coordinate with maintainers, see
  [CI Workflow Updates](#ci-workflow-updates-fork-prs))
- Submit PR

## Step 1: Create Your Signer Module

Create a new directory under `src/` for your implementation:

```
src/
├── your_service/
│   ├── mod.rs      # Main implementation with SolanaSigner trait
│   └── types.rs    # API request/response types (if needed)
```

## Step 2: Define Your Signer Struct

In `src/your_service/mod.rs`, define your signer struct:

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,
}

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## Step 3: Implement Constructor and Helper Methods

Remote signers **must** enforce HTTPS and configure HTTP timeouts. Use the
shared `HttpClientConfig` struct for timeout settings.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## Step 4: Implement the Signer Traits

The `SolanaSigner` base trait has 2 async methods (`sign_message`,
`is_available`) plus `pubkey()`. Transaction signing goes in a capability trait;
most providers implement `TransactionSigner`, whose `sign_transaction` returns
`SignTransactionResult` (a tagged enum marking the transaction fully or
partially signed).

Sign the message bytes, never the whole wire transaction, and verify the
provider's signature against them before attaching it. Use the shared
`TransactionUtil` helpers for signing and serialization.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

If your provider rewrites the transaction before signing, implement
`ModifyingSigner` instead and replace the caller's transaction wholesale with
the provider's bytes. If it broadcasts server-side, implement `SendingSigner`
and leave the caller's transaction untouched. Never implement a capability your
provider cannot serve.

## Step 6: Add Feature Flag

Update `Cargo.toml` to add your signer as an optional feature. Remote backends
include the internal `_remote` marker, which gates the `From<reqwest::Error>`
impl in `src/error.rs`; without it, `?` on reqwest calls won't compile when only
your feature is enabled.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## Step 7: Update the Signer Enum

Add your signer to `src/lib.rs`. The base `SolanaSigner` impl dispatches through
the `dispatch_signer!` macro, so add one arm there. Capability access lives in
the `as_transaction_signer()`, `as_modifying_signer()` and `as_sending_signer()`
accessors: add a `Some(s)` arm to the one matching your capability trait (and,
for a sending or modifying backend, a `None` arm in `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## Step 8: Add Comprehensive Tests

Add tests to your module (at the bottom of `src/your_service/mod.rs`):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

Also cover signature-verification failure: a mocked response whose signature
does not verify must return an error.

## CI Workflow Updates (Fork PRs)

CI is a two-phase process. Coordinate with maintainers to prepare `main` before
your PR can be tested: they update `fork-external-live-manual.yml`, add env vars
to `ci.yml`, and configure GitHub Secrets.

Your PR must include these Phase 2 changes alongside your signer code:

- **`ci.yml`**: add your Rust feature to the `backend` matrix (before `all`) and
  your integration test function to the `test` matrix
- **`typescript-ci.yml`**: add your package to the unit and integration test
  matrices, and add env vars to the integration test step
- **`typescript-publish.yml`**: add your package to `PUBLISH_PACKAGES`, the
  GitHub Release `packages` array, and the summary table
- **`python-ci.yml`**: add the backend to the `CI_SIGNER_*` gating in
  `resolve-signers` and to the integration matrix
- **`go-ci.yml`**: add the backend to the `CI_SIGNER_*` gating and to
  `moduleBySigner`

## TypeScript Signer

If you're also adding a TypeScript signer package, create it at
`typescript/packages/your-signer/`. Key patterns:

- Factory function `createYourSigner()` returns
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>`; keep the
  signer class internal and export only the factory and its config type
- Export config interface (`YourSignerConfig`)
- If your backend cannot sign messages, omit `SolanaMessageSigner` and expose no
  `signMessages` method at all: Kit classifies signers by method presence, so a
  throwing stub would misclassify the signer
- Enforce HTTPS on `apiBaseUrl` config fields with `assertHttpsUrl()` from
  `@solana/keychain-core`
- Make remote calls through `fetchSignerJson()` from `@solana/keychain-core`,
  which owns error mapping, response sanitization, redirect rejection and the
  default timeout
- Sanitize any other remote API error text with `sanitizeRemoteErrorResponse()`
  from `@solana/keychain-core`
- Use `throwSignerError(SignerErrorCode.*, { cause, message })` from
  `@solana/keychain-core`
- Honor `config?.abortSignal` in every signing method, threading it into
  `fetchSignerJson()` and `signBatchStaggered()`
- Validate `requestDelayMs` with `validateRequestDelayMs()` and batch with
  `signBatchStaggered()`
- Add `@throws` JSDoc to factory functions listing error codes
- Declare `@solana/*` packages as peer dependencies at `>=8.1.0`
- Unit tests with vitest and mocked `fetch`; integration tests with
  `runSignerIntegrationTest` from `@solana/keychain-test-utils`

### Sending Signers

If your provider rewrites the transaction or broadcasts server-side, its
signature cannot be applied to the caller's transaction, so it must be a
`SolanaSendingSigner` instead of a `SolanaTransactionSigner`:

- Implement `signAndSendTransactions()` and expose **no** `signTransactions`
  (nor `signMessages`, unless the backend genuinely signs messages)
- Honor `config?.abortSignal`. Once the provider has accepted the create, report
  any failure (including an abort) as `BROADCAST_UNCONFIRMED` carrying the
  provider transaction id, with the abort reason kept as `cause`
- Add a typed `createKeychainSigner` overload returning your sending-signer type
- Exclude your backend from `KeychainKitPluginConfig` in
  `typescript/packages/kit-plugin/src/keychain-plugin.ts`, since a sending
  signer cannot serve as a Kit client `payer` or `identity`
- Assert in unit tests that `isTransactionPartialSigner()` is false and
  `isTransactionSendingSigner()` is true for your instances

### Update Umbrella Package

Update `typescript/packages/keychain/` (7 files to modify):

1. `src/types.ts`: Add `YourSignerConfig` to the `KeychainSignerConfig`
   discriminated union
2. `src/create-keychain-signer.ts`: Add the switch case (each backend package is
   loaded with a dynamic `import()`)
3. `src/resolve-address.ts`: Add to the fast-path or fetch-path switch case
4. `src/index.ts`: Add the config type, namespace and factory function exports
5. `package.json`: Add `@solana/keychain-your-signer: "workspace:*"` dependency
6. `tsconfig.json`: Add `{ "path": "../your-signer" }` reference
7. `typescript/scripts/test-treeshake-umbrella.mjs`: Add your package to
   `SIGNER_MARKERS` and your factory to `FACTORIES`

The switch statements have exhaustive `never` checks, so TypeScript will error
if you add to the union but miss a case. Run `just ts-treeshake` afterwards:
every package and the umbrella must stay tree-shakable.

## Python Signer

Create the module at `python/src/solana_keychain/your_signer/` (`__init__.py`
plus `signer.py`). Key patterns:

- Subclass `SolanaSigner` from `solana_keychain.core` (`pubkey` property,
  `async sign_message()`, `async is_available()`) plus exactly one capability
  class: `TransactionSigner` (`async sign_transaction()`), `ModifyingSigner`
  (`async modify_and_sign_transaction()`) or `SendingSigner`
  (`async sign_and_send_transaction()`)
- Export an `async create_your_signer()` factory that awaits `init()` when the
  backend resolves its address remotely; before init, signing raises
  `SignerErrorCode.NOT_INITIALIZED`
- Export a config dataclass (`YourSignerConfig`) with secrets marked
  `field(repr=False)`
- Enforce HTTPS on base-URL fields with `assert_https_url()`, and route every
  request through `fetch_signer_json()`
- Verify the provider's signature before returning it; use
  `signed_message_bytes()` for the bytes a signature covers, never a hand-rolled
  version prefix
- Register the backend in `_BACKENDS` in
  `python/src/solana_keychain/keychain.py`
- If the backend needs a provider SDK, guard the import, raise an `ImportError`
  naming `pip install 'solana-keychain[your-signer]'`, declare the extra in
  `python/pyproject.toml`, and never import the backend eagerly from the package
  root
- Unit tests with pytest: `respx` for HTTP backends, stub clients for SDK
  backends, and a check that no secret appears in `str()` or `repr()` of raised
  errors
- Add a `make_your_signer()` factory to
  `python/tests/integration/test_live_signers.py` and register it in
  `_MESSAGE_CAPABLE` (or `_TRANSACTION_ONLY` for backends without
  `sign_message`)

## Go Signer

Each Go backend is its own module, at `go/signers/yoursigner/` with module path
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`. See
`go/signers/para/` for a reference. Key patterns:

- Implement `core.SolanaSigner` (`Pubkey()`, `SignMessage(ctx, message)`,
  `IsAvailable(ctx)`) plus exactly one capability interface:
  `core.TransactionSigner`, `core.ModifyingSigner` or `core.SendingSigner`.
  Capability is detected by type assertion, so a backend that cannot sign a
  transaction must carry no `SignTransaction` method at all
- Export a `Config` struct and a `New` constructor (`New(ctx, cfg)` when the
  backend resolves its address remotely; before that, return
  `core.NewNotInitializedError`)
- Build HTTP clients with `core.NewHTTPClient` or `core.ResolveHTTPClient`, and
  validate base URLs with `core.NormalizeHTTPSBaseURL`
- Sign transactions with `core.SignTransactionWith`, which signs the message
  bytes and attaches the signature; verify provider signatures with
  `core.VerifySignature`
- Return errors with `core.NewSignerError` / `core.WrapSignerError` and stable
  codes such as `core.CodeSigningFailed`
- Unit tests with `httptest`; integration tests in `integration_test.go` behind
  the `//go:build integration` tag

## Implementation Tips

### Error Handling

Always use the existing `SignerError` variants. Both `Display` and `Debug` on
`SignerError` are redacted, so keep messages generic and never include raw API
response data. Never use `.expect()` or `.unwrap()` on untrusted API responses:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### Security Requirements

These are not suggestions: consumers pick a backend on the strength of them. If
your provider makes one impossible, say so in the PR and in the repo's
`docs/SECURITY_MODEL.md`.

- **Verify what the provider signed.** Compute the message bytes locally and
  verify the returned signature against them at your signer's required position
  before attaching it. A signature that does not verify must fail, never be
  attached.
- **Declare whether the provider broadcasts.** If it executes server-side,
  implement the sending shape and return the signature that identifies the
  landed transaction. If the provider has no sign-only endpoint, make the
  backend sending-only rather than submitting behind the caller's back.
- **Never leave the caller holding a transaction the signature does not cover.**
  A provider that rewrites the transaction signs its own bytes: either leave the
  caller's transaction untouched (the broadcast-managed case), or take the
  modifying shape and replace it wholesale with the provider's bytes.
- **Report broadcast uncertainty as such.** A failure after submission may still
  have landed. Surface `BROADCAST_UNCONFIRMED` rather than a generic error,
  carry the provider transaction id whenever you have one, and send a
  message-derived idempotency key on every create so a byte-identical resend is
  safe.
- **Never sign before init.** Use `Option<Pubkey>` (not `Pubkey::default()`) for
  the public key before `init()`, and fail with a config error if signing is
  attempted first.
- Never log sensitive data (private keys, API secrets, raw API responses), and
  use a `Debug` impl that hides sensitive fields
- Enforce HTTPS (`https_only(true)`, gated with `#[cfg(not(test))]` for
  wiremock) and configure request and connect timeouts via `HttpClientConfig`
  (defaults: 30s/5s)
- Zeroize intermediate key material with `zeroize::Zeroizing<Vec<u8>>`

### Testing with Mocks

Use `wiremock` for mocking HTTP APIs. Assert on error type only, not error
message text:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```

## Getting Help

- Review existing signer implementations for patterns:
  - `src/memory/mod.rs`: Simple, synchronous
  - `src/privy/mod.rs`: Requires initialization
  - `src/turnkey/mod.rs`: Complex signature handling
  - `src/vault/mod.rs`: External client library
  - `typescript/packages/para/`, `python/src/solana_keychain/para/` and
    `go/signers/para/`: complete references in the other languages
- Key files: `src/traits.rs` (trait definitions), `src/transaction_util.rs` and
  `src/signature_util.rs` (shared helpers), `src/http_client_config.rs` (timeout
  config)
