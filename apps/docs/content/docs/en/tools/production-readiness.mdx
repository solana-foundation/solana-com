Devnet and mainnet differ once real value moves.

| Devnet                                   | Mainnet                                                                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------- |
| Free SOL from faucets                    | [Acquire real SOL](https://solana.com/ecosystem/explore?categories=exchange) for fees |
| Low competition for block space          | Priority fees matter                                                                  |
| Transactions land with little contention | Transaction configuration determines whether they land                                |
| Public RPC is fine                       | Production RPC required                                                               |
| Devnet keypairs and mints                | Different keys and token mints - update your config                                   |

## RPC infrastructure

[Public endpoints](https://solana.com/docs/references/clusters#solana-public-rpc-endpoints)
(`api.mainnet.solana.com`) are rate-limited and carry no SLA. They suit
development and will not sustain a production workload.

<Callout type="caution" title="Never use public RPC for production">
  Use a [private RPC provider](https://solana.com/rpc).
</Callout>

Compare providers on:

- **Reliability**: an SLA with an uptime commitment
- **Latency**: geographic proximity to the application's servers
- **Method coverage**: the RPC methods and historical depth the workload needs
- **Transaction landing**: staked connections, priority fee APIs, and bundle
  support where the workload depends on them
- **Credential handling**: per-environment keys and a way to rotate them

[RPC Infrastructure Providers](https://solana.com/rpc) lists the providers.

### Redundant RPC configuration

RPC providers experience downtime and periods of degraded performance. Configure
the application to use more than one.

[Solana Kit](https://github.com/anza-xyz/kit/tree/main/packages/rpc-transport-http)
provides a library for customizing RPC transports, which allows you to build a
redundant RPC client:

```ts
import { RpcTransport } from "@solana/rpc-spec";
import { RpcResponse } from "@solana/rpc-spec-types";
import { createHttpTransport } from "@solana/rpc-transport-http";

// Create a transport for each RPC server
const transports = [
  createHttpTransport({ url: "https://mainnet-beta.my-server-1.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-2.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-3.com" })
];

// Create a wrapper transport that distributes requests to them
let nextTransport = 0;
async function roundRobinTransport<TResponse>(
  ...args: Parameters<RpcTransport>
): Promise<RpcResponse<TResponse>> {
  const transport = transports[nextTransport];
  nextTransport = (nextTransport + 1) % transports.length;
  return await transport(...args);
}
```

A third-party routing service such as
[Iron Forge](https://www.ironforge.sanctum.so/) can handle the routing instead.

## Transaction landing

A transaction that does not land has not failed; it has not happened yet.

On mainnet you are competing for block space. To increase the chance that a
transaction is included in a block, assemble it with:

- a fresh blockhash, fetched just before sending
- a priority fee instruction with a competitive price
- a compute unit limit based on the estimated compute the transaction needs

Jito bundles are a further option for transactions that must execute together.

### Transaction send configuration

**Blockhash management:**

- Fetch with `confirmed` commitment
- Store the `lastValidBlockHeight` returned by `getLatestBlockhash` - this tells
  you when your transaction expires
- A blockhash is valid for 150 blocks. Convert that to wall-clock using the
  current slot time; see
  [settlement and finality](/docs/tokenization/settlement/finality)

**Send options:**

- `maxRetries: 0` - Disable automatic RPC retries. Handle retries yourself so
  you can refresh the blockhash when needed.
- `skipPreflight: true` - Bypass simulation before sending. Use it only when the
  transaction has already been simulated, for example to estimate its compute
  units. Otherwise keep it `false` so errors surface before a fee is spent.

```typescript
import { createSolanaRpc } from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);

// 1. Get blockhash with confirmed commitment
const { value: latestBlockhash } = await rpc
  .getLatestBlockhash({ commitment: "confirmed" })
  .send();

// 2. Build and sign your transaction with the blockhash
// ... (transaction building code)

// 3. Send with production settings
const signature = await rpc
  .sendTransaction(encodedTransaction, {
    encoding: "base64",
    maxRetries: 0n, // Handle retries yourself
    skipPreflight: true, // Only after the transaction has been simulated
    preflightCommitment: "confirmed"
  })
  .send();

// 4. Track expiration using lastValidBlockHeight
const { lastValidBlockHeight } = latestBlockhash;
// Stop retrying when current block height exceeds lastValidBlockHeight
```

The [retry strategy](#retry-strategies) below uses
`sendAndConfirmTransactionFactory`, which does the expiration tracking in step 4
for you.

### Use priority fees

Every Solana transaction requires a transaction fee, paid in SOL. Transaction
fees are split into two parts: the base fee and the priority fee. The base fee
compensates validators for processing the transaction. The priority fee is an
optional fee that increases the chance the current leader will process the
transaction.

**How fees work:**

```
Total fee = Base fee (5,000 lamports per signature) + Priority fee
Priority fee = Compute units x Price per unit (micro-lamports per compute unit)
```

The base fee is a protocol constant; see [transaction fees](/docs/core/fees).
Priority fee levels move with demand, so read the current distribution from
`getRecentPrioritizationFees` or a provider's fee API rather than from
documentation.

**Sample implementation:**

The
[`@solana-program/compute-budget`](https://github.com/solana-program/compute-budget)
package provides a helper that updates or appends the compute unit price
instruction (in micro-lamports) on a transaction message.

```typescript
import { updateOrAppendSetComputeUnitPriceInstruction } from "@solana-program/compute-budget";

const tx = pipe(
  createTransactionMessage({ version: 0 }),
  (m) => setTransactionMessageFeePayerSigner(payer, m),
  (m) => setTransactionMessageLifetimeUsingBlockhash(latestBlockhash, m),
  (m) => appendTransactionMessageInstructions([myInstructions], m),
  (m) => updateOrAppendSetComputeUnitPriceInstruction(1000n as MicroLamports, m)
);
```

**Getting fee estimates:** several RPC providers offer priority fee APIs:

- [Helius Priority Fee API](https://docs.helius.dev/solana-apis/priority-fee-api)
- [QuickNode Priority Fee Add-on](https://marketplace.quicknode.com/add-on/solana-priority-fee)
- [Triton Priority Fees API](https://docs.triton.one/chains/solana/improved-priority-fees-api)

For the full fee mechanics, see [Transaction Fees](/docs/core/fees) and
[How to Add Priority Fees to a Transaction](https://solana.com/developers/cookbook/transactions/add-priority-fees).

### Optimize compute units

Compute is a measure of the work a program does. A transaction may use at most
1.4 million compute units, and a single writable account may be touched by at
most 12 million compute units per block. Both limits are feature-gated values;
[compute budget](/docs/core/fees/compute-budget) carries the current figures and
their source.

When you submit a transaction, estimate the compute it will use and set the
compute unit limit accordingly - a request for how much of the block's capacity
should be reserved for the transaction. Estimating accurately affects both
whether the transaction is included and what the priority fee costs.

The Solana JSON RPC API has a
[`simulateTransaction`](/docs/rpc/http/simulatetransaction) method that returns
the compute units a transaction consumed in simulation.
[`@solana/kit`](https://github.com/anza-xyz/kit) provides helper functions that
estimate a transaction's resource limits and set them on the message in one
step, using `simulateTransaction` under the hood.

```ts
import {
  estimateResourceLimitsFactory,
  estimateAndSetResourceLimitsFactory
} from "@solana/kit";

const estimateResourceLimits = estimateResourceLimitsFactory({ rpc });
const estimateAndSetResourceLimits = estimateAndSetResourceLimitsFactory(
  estimateResourceLimits
);
const txWithResourceLimits = await estimateAndSetResourceLimits(tx);
```

<Callout type="info">
  If you build and send transactions with a kit plugin client, you typically
  don't need this step - the client adds compute budget instructions for you
  when it sends (`.sendTransaction()`). The manual flow above is for when you
  assemble transactions directly with `@solana/kit`.
</Callout>

If the same type of transaction repeats, cache the compute estimate per
transaction type rather than simulating every time.

### Jito bundles

Jito bundles group several transactions so that they execute atomically and in
order when a Jito-connected leader includes them. Bundles are submitted to the
Jito network with a tip, which is an incentive for inclusion rather than a
guarantee of it.

**Resources:**

- [Jito documentation](https://docs.jito.wtf/lowlatencytxnsend/)
- [Video: Jito Bundles](https://www.youtube.com/watch?v=HZ1pK9i6zx4)
- [QuickNode guide on Jito bundles](https://www.quicknode.com/guides/solana-development/transactions/jito-bundles)

### Retry strategies

Transactions can fail for many reasons. Unlike an API that returns success or
failure immediately, a Solana transaction requires confirmation tracking.

**Key concepts:**

- **Blockhash expiration**: a transaction is valid for 150 blocks from its
  blockhash
- **Idempotency**: the same signed transaction always produces the same
  signature, so resubmitting is safe
- **Exponential backoff**: avoid overwhelming the network with rapid retries

```typescript
import {
  createSolanaRpc,
  createSolanaRpcSubscriptions,
  sendAndConfirmTransactionFactory,
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED
} from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);
const rpcSubscriptions = createSolanaRpcSubscriptions(process.env.RPC_WSS_URL!);

const sendAndConfirmTransaction = sendAndConfirmTransactionFactory({
  rpc,
  rpcSubscriptions
});

// Send with automatic confirmation tracking and block height monitoring
try {
  await sendAndConfirmTransaction(signedTransaction, {
    commitment: "confirmed",
    // Optional: abort after 75 seconds
    abortSignal: AbortSignal.timeout(75_000)
  });
} catch (e) {
  if (isSolanaError(e, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED)) {
    // Blockhash expired - rebuild transaction with fresh blockhash and retry
    rebuildAndRetryTransaction(); // implement your own logic for rebuilding and retrying the transaction
  }
  throw e;
}
```

`sendAndConfirmTransactionFactory` handles confirmation polling and block height
tracking. It throws `SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED` when the transaction's
blockhash expires, signaling that the transaction needs to be rebuilt with a
fresh blockhash.

Further reading:

- [Transaction confirmation and expiration](https://solana.com/developers/cookbook/transactions/confirmation)
- [Helius: How to Land Transactions on Solana](https://www.helius.dev/blog/how-to-land-transactions-on-solana)
- [QuickNode: Strategies to Optimize Solana Transactions](https://www.quicknode.com/docs/solana/transactions)

## Commitment levels

Solana exposes three commitment levels:

| Level       | Definition                | Use case                                    |
| ----------- | ------------------------- | ------------------------------------------- |
| `processed` | In a block, not yet voted | Immediate interface feedback only           |
| `confirmed` | Supermajority voted       | Crediting a display; most user-facing flows |
| `finalized` | Rooted                    | Anything that feeds a book of record        |

Which commitment level the records treat as settled is a decision about the
books. [Settlement and finality](/docs/tokenization/settlement/finality) is the
authoritative page on what each level means, how many slots each takes, why a
blockhash should be fetched at one level and a result judged at another, and why
protocol finality is not legal finality.

For more on checking transaction status, see
[Interacting with Solana](/docs/payments/interacting-with-solana).

## Error handling

Solana Kit provides typed errors via `isSolanaError()`. Use specific error codes
instead of string matching:

```typescript
import {
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED,
  SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE,
  SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND,
  SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS
} from "@solana/kit";

function handleTransactionError(error: unknown): {
  message: string;
  retryable: boolean;
} {
  // Blockhash expired - rebuild and retry
  if (
    isSolanaError(error, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED) ||
    isSolanaError(error, SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND)
  ) {
    return { message: "Transaction expired - rebuilding", retryable: true };
  }

  // Insufficient SOL for fees
  if (
    isSolanaError(
      error,
      SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE
    )
  ) {
    return { message: "Not enough SOL for fees", retryable: false };
  }

  // Insufficient token balance
  if (
    isSolanaError(error, SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS)
  ) {
    return { message: "Insufficient balance", retryable: false };
  }

  // Unknown error
  console.error("Transaction error:", error);
  return { message: "Transaction failed - please retry", retryable: true };
}
```

`ACCOUNT_NOT_FOUND` on a transfer usually means the recipient's token account
does not exist yet; create the associated token account in the same transaction.
Where the fee payer is short of SOL, see
[fee abstraction](/docs/payments/send-payments/payment-processing/fee-abstraction)
for sponsoring fees so end users transact without holding SOL.

## Security

### Authority custody

An issued asset has authorities - mint, freeze, pause, metadata, and any
delegate - and losing one is usually unrecoverable. Before mainnet:

- No authority is a single hot key on a single machine.
- Each authority is held by the smallest party that needs it, rather than one
  key holding everything. See
  [program and authority design](/docs/tokenization/design/program-and-authority-design).
- Someone other than the original engineer can execute a recovery, and that path
  has been rehearsed.

### Key management

- **Never expose private keys in frontend code.** Use backend signing, hardware
  wallets, multisignature wallets, or key management services.
- **Separate hot and cold wallets.** Hot wallet for operations, cold for
  treasury.
- **Back up all production keys.** Store encrypted backups in multiple secure
  locations. Losing a key means losing access permanently.
- **Use different keys for devnet and mainnet.** Use environment-based
  configuration so the right keys load for each network.

### Signing infrastructure

For production backend signing, use [Keychain](/docs/tools/keychain) - a unified
signing library that abstracts key-management backends behind a single
interface, so an application can develop against in-memory keys and move to a
production backend without changing application code. The Keychain docs carry
the current backend list.

[Choosing a backend](/docs/tools/keychain/choosing-a-backend) compares them.
Keychain is available for both [Rust](https://crates.io/crates/solana-keychain)
and [TypeScript](https://www.npmjs.com/package/@solana/keychain).

### RPC security

Treat RPC endpoints like API keys - don't expose them in frontend code where
they can be extracted and abused. Use a backend proxy or environment variables
that aren't bundled into client code, and rotate keys per environment.

- [QuickNode: Endpoint Security Best Practices](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Protect Your Solana API Keys: Security Best Practices](https://www.helius.dev/docs/rpc/protect-your-keys)

### Monitoring and reconciliation

Track these metrics in production:

| Metric                   | Why                    |
| ------------------------ | ---------------------- |
| Transaction success rate | Detect issues early    |
| Confirmation latency     | Monitor network health |
| Priority fee spend       | Cost management        |
| RPC error rate           | Provider health        |

Set up alerts for:

- Transfers above threshold from treasury
- Failed transaction rate spikes
- Unusual recipient patterns
- RPC error rate increases

For real-time transaction monitoring at scale, see the
[Indexing Guide](/docs/payments/accept-payments/indexing).

Monitoring shows whether the system is healthy. Reconciliation shows whether the
records match chain state.

- Record the transaction signature and the commitment level at which you
  accepted it, for every state change that matters.
- Order your own records by slot, not by wall-clock time.
- Reconcile against the chain rather than against your own optimistic writes,
  and reconcile against a custodian's view where one holds the asset. See
  [custody integration](/docs/tokenization/custody/custody-integration).
- Alert on transactions that were sent and never confirmed, which leaves records
  and chain state diverged.

### Verify addresses

Each token mint and each deployed program has a single canonical address on
mainnet. A spoofed token can carry the same name and symbol as a stablecoin
under a different mint. Hardcode or allowlist the mint addresses the application
accepts; never take them from an untrusted source at runtime.

**Environment-based configuration:** devnet and mainnet use different token
mints. Load the correct addresses per environment, so devnet addresses are not
shipped to production and mainnet addresses are not used in testing.

Common stablecoin mints on mainnet:

| Token | Issuer | Mint address                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Confirm each against the issuer's own published address before use.

Program addresses matter too. Sending instructions to the wrong program fails,
or results in irreversible loss of funds. The Token Program addresses are:

| Program            | Address                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Allowlisting the right addresses protects against spoofed tokens, but it does
not protect against sending to the wrong _kind_ of account. A recipient address
can be a wallet, a token account, a mint, or a program, and each requires
different handling. Native SOL sent to anything other than a wallet leaves the
sender's control - lost outright for a mint or program, recoverable only by the
account owner for a token account - with no failed transaction to warn the user.

<Callout type="warn" title="Validate recipients before sending">
  Classify every recipient address before signing a transfer. See [Verify
  Address](/docs/payments/send-payments/verify-address) for the full decision
  tree and reference code that distinguishes wallets, token accounts, mints, and
  programs.
</Callout>

## Pre-launch checklist

- [ ] Mainnet SOL acquired for fees and rent
- [ ] Production RPC configured (not public endpoint)
- [ ] Fallback RPC endpoint configured
- [ ] Priority fees implemented with dynamic pricing
- [ ] Retry logic handles blockhash expiration
- [ ] Confirmation level appropriate for use case
- [ ] All common errors handled
- [ ] Fee sponsorship configured, if end users will not hold SOL
- [ ] Mainnet token addresses verified (not devnet mints)
- [ ] Recipient address validation before sending (wallet vs token account vs
      mint vs program)
- [ ] All keys backed up securely
- [ ] Key management reviewed (no keys in frontend)
- [ ] Transaction monitoring and alerting active
- [ ] Load tested at expected volume
- [ ] The commitment level your books call settled, written down
- [ ] Every authority held in auditable signing infrastructure, with a rehearsed
      recovery path
- [ ] Signatures and commitment levels recorded for every material state change
- [ ] Reconciliation running against the chain and against any custodian

If the application deploys its own program,
[Deploying Programs](/docs/programs/deploying) covers program keypairs, buffer
accounts, upgrade authority, and verified builds.
