交易只有在带有每一位所需签名者的有效[签名](/docs/core/transactions/transaction-structure#signatures)时才会执行。在本地开发期间,你通常会以 [`Keypair`](/developers/cookbook/wallets/create-keypair) 的形式持有该密钥并直接签名。而在生产环境中,关键问题则有所不同:**私钥存放在哪里,谁有权授权使用它进行签名?**

<Callout type="warn">
  切勿在客户端代码中嵌入私钥,也不要将私钥打包进前端或提交到源代码管理中。任何人一旦获取私钥,就能完全控制该账户中的资金。
</Callout>

## 签名方式

| 方式                  | 密钥存放位置                                     | 签名者                                          | 最适用场景                                                      |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **本地 keypair**         | 机器上的文件或环境变量           | 你的代码,直接签名                                | 本地开发、测试、CI                                  |
| **浏览器钱包**        | 终端用户的钱包(例如 Phantom、Solflare)          | 终端用户,逐笔交易签名                      | 由用户自行签署交易的前端 dApp        |
| **云端 KMS / HSM**       | 硬件支持的密钥服务(AWS KMS、GCP KMS、Vault) | 你的后端向该服务请求签名 | 后端服务、资金库操作、受监管环境 |
| **托管 / MPC 钱包** | 拆分或托管于服务提供商的基础设施中   | 服务提供商根据你的策略共同签名     | 嵌入式钱包、审批工作流、机构托管   |

本地 keypair 是唯一会把原始密钥材料放进你应用内部的方式。所有生产环境方案都会将密钥保存在专用基础设施中,并请该基础设施代表你进行签名。

## 后端签名

当服务器需要签名时(支付费用、发送程序交易或管理资金库),请使用专用的密钥管理后端,而不是原始 keypair。Solana 基金会维护着 [Keychain](/docs/tools/keychain),这是一个统一的签名库(支持 Rust、TypeScript、Python 和 Go),它在上表中的每个后端之上都提供同一个 `SolanaSigner` 接口:Memory、HashiCorp Vault、AWS KMS、GCP KMS、Fireblocks、Privy、Turnkey、CDP、Crossmint、Dfns、Para、Openfort、Utila 和 Fordefi。

由于各后端共用同一接口,你可以在本地使用内存中的密钥进行开发,然后通过配置切换到生产后端,而无需重写应用代码(像 Crossmint 这类替你广播交易的后端,则改为通过签名并发送的路径来调用)。Keychain 兼容 [`@solana/kit`](/docs/clients/official/javascript)、[Rust SDK](/docs/clients/official/rust)、`solders`(Python)以及 `solana-go` v2(Go)。
