## 架构

Private Channels 由四个组件构成：两个链上 Solana 程序（Escrow 和 Withdraw）以及两个链下服务（Gateway 和 Auth Service）。它们共同构成一个状态通道协议，资金存储于主网，但转账在链下完成结算。

### Escrow 程序

Escrow 程序是一个链上 Solana 程序，用于托管已存入的 SPL 代币。它是系统的信任锚点：所有资金最终存放于托管合约中，直到运营商提供有效的稀疏默克尔树排除证明方可释放。

- 程序 ID：`9tgHa1DcnaSSUtmMsst8ovKTe1Gfxzezn27KnH9xXYeU`
- 该 ID 通过 `declare_id!()` 编译进程序二进制文件。链下服务在编译时从生成的客户端 crate 中读取相同的 ID，而非从环境变量中获取。
- 管理 `Instance`、`AllowedMint` 和 `Operator` PDA
- 指令：`CreateInstance`、`AllowMint`、`BlockMint`、`AddOperator`、`RemoveOperator`、`SetNewAdmin`、`Deposit`、`ReleaseFunds`、`ResetSmtRoot`

### Withdraw 程序

Withdraw 程序运行在私有通道网络上，而非 Solana 主网。用户调用 `WithdrawFunds` 来销毁其通道侧的代币余额。此销毁操作不会自动释放资金，而是向运营商发出提款待处理的信号。运营商随后在 Escrow 程序上携带有效的 SMT 证明调用 `ReleaseFunds`，以完成结算。

- 程序 ID：`J231K9UEpS4y4KAPwGc4gsMNCjKFRMYcQBcjVW7vBhVi`
- 该 ID 已编译进程序二进制文件。链下服务在编译时从生成的客户端 crate 中读取相同的 ID，而非从环境变量中获取。

### Gateway

Gateway 是一个兼容 Solana JSON-RPC 的代理，负责将客户端请求路由至通道网络的写节点（用于交易提交）和读节点（用于查询）。它通过环境变量进行配置：`GATEWAY_PORT`、`GATEWAY_WRITE_URL`、`GATEWAY_READ_URL`。

健康检查端点（无需认证）：

- `GET /health` - 存活检查；返回 `200 {"status":"ok"}`
- `GET /ready` - 深度就绪检查，探测写节点与读节点；返回 `200 {"status":"ready"}` 或 `503 {"status":"degraded"}`

#### RPC 方法路由与访问控制

Gateway 将 `sendTransaction` 路由至写节点，其余所有方法路由至读节点。超过 64 KB 的请求将被拒绝并返回 HTTP 413。启用认证后，方法访问权限由 JWT 角色控制。完整的方法权限矩阵请参阅 **[认证与角色](/docs/tools/private-channels/concepts/auth)**。

### Auth Service

Auth Service 是一个可选组件，为 Gateway 访问控制签发 HS256 JWT（有效期 24 小时）。当设置了 `JWT_SECRET` 环境变量时，该组件将被启用。若未设置，Gateway 将接受所有连接。

JWT 声明字段：`sub`（用户 UUID）、`role`（`"user"` 或 `"operator"`）、`iss`（`"private-channel-auth"`）、`aud`（`"private-channel-gateway"`）、`exp`（Unix 时间戳）。`iss` 和 `aud` 由 Gateway 的 JWT 配置验证，不会被反序列化到应用层声明结构体中；应用层代码只能访问 `sub`、`role` 和 `exp`。

角色：

- `user` - 访问权限仅限于自身已验证的钱包；不能调用 `getBlock`、`getTransaction` 或 `simulateTransaction`
- `operator` - 绕过所有所有权检查；拥有完整的 RPC 方法访问权限；必须在数据库中预先配置（不支持自助提权）

### Streamer

Streamer 是一个 WebSocket 服务器，可实时向已连接的客户端推送通道状态更新，无需轮询 RPC。它通过轮询 PostgreSQL 获取状态变更。Streamer 属于基础 Docker Compose 技术栈的一部分，而非本指南所部署的 devnet 技术栈；详情请参阅 [配置参考](/docs/tools/private-channels/operators/configuration#service-port-reference)。

- 端口：`8902`，可通过 `STREAMER_PORT` 配置
- 连接地址：`ws://localhost:8902`
- 健康检查端点：`GET /health` - 若任意内部轮询循环停滞超过 30 秒，则返回 `503`

<Callout type="warning">

</Callout>

## 交易流水线

```text
Transaction -> [1:Dedup] -> [2:SigVerify] -> [3:Sequencer] -> [4:Executor] -> [5:Settler] -> Database
```

提交至 Gateway 的交易在状态被提交前，需经过五个阶段的流水线处理：

1. **去重（Dedup）** - 在交易进入流水线之前过滤重复交易
2. **签名验证（SigVerify）** - 根据签名者的公钥验证交易签名
3. **排序器（Sequencer）** - 对有效交易进行确定性排序，以建立规范历史记录
4. **执行器（Executor）** - 在通道账户层（BOB Cache + AccountsDB）上执行交易，在链下更新余额
5. **结算器（Settler）** - 将累积的交易结果提交至 PostgreSQL 并更新 Redis 缓存；为下一个出块周期生成新的区块哈希。主网结算（调用 `ReleaseFunds`）由 `operator-private-channel` 服务单独处理

## 核心特性

### 隐私性

通道参与者之间的转账不会记录在 Solana 主网上。只有存款（进入通道）和最终提款（离开通道）会上链。在通道运行期间，交易对手身份和转账金额对外部观察者不可见。

### 性能

链下流水线将 Solana 的出块时间从关键路径中移除。转账在排序器处理时即完成确认，而无需等待 Solana 区块确认。这使得应用层转账能够实现亚秒级最终确定性，吞吐量也超越了 Solana 原生 TPS 的限制。

### 结算

每笔提款均受链上稀疏默克尔树证明的保护。SMT 根存储在 Escrow 程序的 `Instance.withdrawal_transactions_root` 中。调用 `ReleaseFunds` 时，程序首先针对当前链上根验证一个未见过的 nonce 的排除证明，然后针对调用方提供的新根验证该 nonce 的包含证明。只有在两项检查均通过后，程序才会存储新根，即使运营商密钥泄露，双重花费也无法实现。

## 安全模型

**管理员密钥** - 控制实例创建（`CreateInstance`）和运营商配置（`AddOperator` / `RemoveOperator`）。管理员密钥一旦泄露，攻击者可任意配置运营商。`SetNewAdmin` 以单步不可逆的方式转移管理员权限；请妥善保管管理员密钥。

**运营商密钥** - 可调用 `ReleaseFunds` 和 `ResetSmtRoot`。在没有针对当前链上根的有效 SMT 排除证明的情况下，无法释放资金。链上 `verify_smt_exclusion_proof` 检查是防范未授权提款的最后一道防线：仅凭泄露的运营商密钥不足以清空托管合约中的资金。

**SMT 根** - 存储在链上的 `Instance.withdrawal_transactions_root` 中，随每次 `ReleaseFunds` 调用原子性更新。由于每个证明必须引用一个未见过的 nonce，即使运营商密钥泄露，对同一通道余额的双重花费也无法实现。

**树轮换** - `Instance.current_tree_index` 追踪树的 epoch。调用 `ResetSmtRoot` 时，会递增树索引并使前一个树 epoch 中的所有 nonce 失效，为新的结算周期提供一个干净的起点。

## 操作密钥安全

<Callout type="warning">
  链下服务使用其自身的签名者配置，与上述安全模型中描述的链上管理员/运营商权限无关。`ADMIN_PRIVATE_KEY` 是所有运营商服务的必填项，用于支付交易手续费；独立的可选项 `OPERATOR_PRIVATE_KEY` 为 `ReleaseFunds` 和 `ResetSmtRoot` 提供链上运营商签名，若未设置则回退使用 `ADMIN_PRIVATE_KEY` 的值。切勿将协议级实例管理员密钥（用于 `CreateInstance` / `AddOperator` / `SetNewAdmin`）放入上述任一变量或在运行时暴露；请将该密钥离线冷存储。
</Callout>

`ReleaseFunds` 和 `ResetSmtRoot` 需要两个链上签名：手续费支付方（来自 `ADMIN_PRIVATE_KEY`）和运营商 PDA 的授权方（来自 `OPERATOR_PRIVATE_KEY`，若未设置则使用 `ADMIN_PRIVATE_KEY`）。本部署指南的 devnet 演练将生成的运营商 keypair 放入 `ADMIN_PRIVATE_KEY` 并保持 `OPERATOR_PRIVATE_KEY` 未设置，因此同一个 keypair 同时充当两个签名者角色。请将最终存入 `ADMIN_PRIVATE_KEY` 的密钥以与热钱包私钥同等级别的方式加以保护：

- 仅将其存储在已被 gitignore 的 `.env` 文件中，切勿存入 `.env.devnet` 或任何已提交的配置文件
- 对于生产环境部署，建议使用密钥管理服务（如 AWS Secrets Manager、HashiCorp Vault），而非明文环境变量
- 协议级实例管理员 keypair（用于调用 `AddOperator` / `SetNewAdmin`）应保持冷存储；该密钥仅在实例初始化和运营商配置期间使用，运行时无需用到

`SetNewAdmin` **以单笔交易不可逆地**转移管理员权限：当前管理员在没有新管理员配合的情况下没有任何恢复路径。在验证目标地址之前，请勿调用此指令。
