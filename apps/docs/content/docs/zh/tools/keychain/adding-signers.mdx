本指南面向希望将新密钥管理解决方案集成到 `solana-keychain`
库中的钱包服务提供商和开发者。通过添加您的签名器实现，您将使开发者能够通过统一接口使用您的服务进行安全的 Solana 交易签名。

Keychain 的 Rust、TypeScript、Python 和 Go 实现保持功能对等。我们强烈建议 PR 同时包含这四种语言的实现。如果你只能贡献其中一种,也没有问题,但在该签名器随版本发布之前,其余几种实现也需要补齐。

_正在使用 Claude Code?仓库中的 [`add-signer-ci` skill](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci) 可以为通过 fork PR 贡献的新签名器配置 CI 工作流。_

## 架构概述

该库采用基于 trait 的架构,定义在 `src/traits.rs` 中。每个签名器都需要实现 `SolanaSigner` 基础 trait(`pubkey`、`sign_message`、`is_available`),外加且仅加一个与服务提供方形态相匹配的能力 trait:

- `TransactionSigner`(`sign_transaction`):服务提供方对调用方提供的字节进行签名,由调用方负责广播。适用于大多数后端。
- `ModifyingSigner`(`modify_and_sign_transaction`):服务提供方先改写交易,再对其签名,但不进行广播。
- `SendingSigner`(`sign_and_send_transaction`):服务提供方在服务端完成签名并广播。

该库还提供了一个统一的 `Signer` 枚举,封装了所有实现,支持在运行时选择签名后端。它只实现基础 trait;各项能力需通过 `as_transaction_signer()`、`as_modifying_signer()` 和 `as_sending_signer()` 获取。

## 第三步：实现构造函数和辅助方法

远程签名器**必须**强制使用 HTTPS 并配置 HTTP 超时。使用共享的 `HttpClientConfig`
结构体进行超时设置。

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## 第 4 步:实现签名器 Trait

`SolanaSigner` 基础 trait 包含 2 个异步方法(`sign_message`、`is_available`)以及 `pubkey()`。交易签名放在能力 trait 中;大多数服务提供方实现 `TransactionSigner`,其 `sign_transaction` 返回 `SignTransactionResult`(一个带标签的枚举,用于标记交易为完全签名或部分签名)。

请对消息字节进行签名,而不是对整个传输格式的交易签名,并在附加签名之前,针对这些字节验证服务提供方返回的签名。签名和序列化请使用共享的 `TransactionUtil` 辅助函数。

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

如果你的服务提供方在签名前会改写交易,请改为实现 `ModifyingSigner`,并用服务提供方返回的字节整体替换调用方的交易。如果它在服务端广播交易,请实现 `SendingSigner`,并保持调用方的交易不变。切勿实现服务提供方无法提供的能力。

## 步骤 6：添加特性标志

更新 `Cargo.toml`,将你的签名器添加为可选 feature。远程后端需要包含内部的 `_remote` 标记,它用于控制 `src/error.rs` 中 `From<reqwest::Error>` 的实现;如果没有该标记,在仅启用你的 feature 时,对 reqwest 调用使用 `?` 将无法编译。

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## 步骤 7：更新签名器枚举

将你的签名器添加到 `src/lib.rs` 中。基础的 `SolanaSigner` 实现通过 `dispatch_signer!` 宏进行分发,因此需要在那里添加一个分支。能力访问位于 `as_transaction_signer()`、`as_modifying_signer()` 和 `as_sending_signer()` 这几个访问器中:在与你的能力 trait 相匹配的访问器中添加一个 `Some(s)` 分支(对于发送型或改写型后端,还需要在 `as_transaction_signer()` 中添加一个 `None` 分支)。

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## 步骤 8：添加全面的测试

在你的模块中添加测试（位于 `src/your_service/mod.rs` 底部）：

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,

    #[tokio::test]

        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(

            "test-secret".to_string(),
            "test-wallet".to_string(),

            None,

        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
```

## CI 工作流更新(Fork PR)

CI 分为两个阶段。在你的 PR 能够被测试之前,请与维护者协调,先准备好 `main` 分支:他们会更新 `fork-external-live-manual.yml`,在 `ci.yml` 中添加环境变量,并配置 GitHub Secrets。

## TypeScript 签名器

如果你还要添加 TypeScript 签名器包，请在 `typescript/packages/your-signer/`
创建它。关键模式：

- 工厂函数 `createYourSigner()` 返回 `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>`;签名器类保持为内部使用,仅导出工厂函数及其配置类型
- 导出配置接口（`YourSignerConfig`）
- 如果你的后端无法对消息签名,请省略 `SolanaMessageSigner`,并且完全不要暴露 `signMessages` 方法:Kit 通过方法是否存在来对签名器分类,因此抛出异常的占位实现会导致签名器被错误分类
- 使用 `@solana/keychain-core` 中的 `assertHttpsUrl()` 对 `apiBaseUrl` 配置字段强制使用 HTTPS
- 通过 `@solana/keychain-core` 中的 `fetchSignerJson()` 发起远程调用,它负责错误映射、响应清理、拒绝重定向以及默认超时
- 使用 `@solana/keychain-core` 中的 `sanitizeRemoteErrorResponse()` 清理其他任何远程 API 错误文本
- 使用 `@solana/keychain-core` 中的
  `throwSignerError(SignerErrorCode.*, { cause, message })`
- 在每个签名方法中遵循 `config?.abortSignal`,并将其传递给 `fetchSignerJson()` 和 `signBatchStaggered()`
- 使用 `validateRequestDelayMs()` 校验 `requestDelayMs`,并使用 `signBatchStaggered()` 进行批量处理
- 向工厂函数添加 `@throws` JSDoc，列出错误代码
- 将 `@solana/*` 包声明为 peer 依赖,版本为 `>=8.1.0`
- 使用 vitest 和模拟的 `fetch` 编写单元测试;使用 `@solana/keychain-test-utils` 中的 `runSignerIntegrationTest` 编写集成测试

### 发送型签名器

如果你的服务提供方会改写交易或在服务端广播交易,其签名就无法应用到调用方的交易上,因此它必须是 `SolanaSendingSigner`,而不是 `SolanaTransactionSigner`:

- 实现 `signAndSendTransactions()`,并且**不要**暴露 `signTransactions`(也不要暴露 `signMessages`,除非该后端确实支持消息签名)
- 遵循 `config?.abortSignal`。一旦服务提供方接受了创建请求,任何失败(包括中止)都应报告为携带服务提供方交易 ID 的 `BROADCAST_UNCONFIRMED`,并将中止原因保留为 `cause`
- 添加一个带类型的 `createKeychainSigner` 重载,返回你的发送型签名器类型
- 在 `typescript/packages/kit-plugin/src/keychain-plugin.ts` 中,将你的后端从 `KeychainKitPluginConfig` 中排除,因为发送型签名器无法用作 Kit 客户端的 `payer` 或 `identity`
- 在单元测试中断言:对你的实例而言,`isTransactionPartialSigner()` 为 false,`isTransactionSendingSigner()` 为 true

更新 `typescript/packages/keychain/`(需修改 7 个文件):

2. `src/create-keychain-signer.ts`:添加 switch 分支(每个后端包都通过动态 `import()` 加载)
3. `src/resolve-address.ts`:添加到快速路径或获取路径的 switch 分支中
4. `src/index.ts`:添加配置类型、命名空间和工厂函数的导出
5. `package.json`:添加 `@solana/keychain-your-signer: "workspace:*"` 依赖
6. `tsconfig.json`:添加 `{ "path": "../your-signer" }` 引用
7. `typescript/scripts/test-treeshake-umbrella.mjs`:将你的包添加到 `SIGNER_MARKERS`,并将你的工厂函数添加到 `FACTORIES`

switch 语句带有穷尽的 `never` 检查,因此如果你向联合类型中添加了成员却遗漏了某个分支,TypeScript 会报错。之后请运行 `just ts-treeshake`:每个包以及总包都必须保持可 tree-shaking。

## Python 签名器

在 `python/src/solana_keychain/your_signer/` 下创建模块(`__init__.py` 和 `signer.py`)。关键模式:

- 从 `solana_keychain.core` 继承 `SolanaSigner`(`pubkey` 属性、`async sign_message()`、`async is_available()`),外加且仅加一个能力类:`TransactionSigner`(`async sign_transaction()`)、`ModifyingSigner`(`async modify_and_sign_transaction()`)或 `SendingSigner`(`async sign_and_send_transaction()`)
- 导出一个 `async create_your_signer()` 工厂函数;当后端需要远程解析其地址时,该函数会 await `init()`;在初始化之前,签名会抛出 `SignerErrorCode.NOT_INITIALIZED`
- 导出一个配置 dataclass(`YourSignerConfig`),其中的密钥字段标记为 `field(repr=False)`
- 使用 `assert_https_url()` 对基础 URL 字段强制使用 HTTPS,并让每个请求都经由 `fetch_signer_json()` 发出
- 在返回服务提供方的签名之前先进行验证;使用 `signed_message_bytes()` 获取签名所覆盖的字节,切勿手写版本前缀
- 在 `python/src/solana_keychain/keychain.py` 的 `_BACKENDS` 中注册该后端
- 如果后端需要提供商 SDK,请对导入加以保护,抛出 `ImportError`
  并给出 `pip install 'solana-keychain[your-signer]'` 的提示,在
  `python/pyproject.toml` 中声明该 extra,且绝不要从包的根目录
  提前导入该后端
- 使用 pytest 编写单元测试:HTTP 后端使用 `respx`,SDK 后端使用桩客户端(stub client),并检查抛出错误的 `str()` 或 `repr()` 中不会出现任何密钥
- 在
  `python/tests/integration/test_live_signers.py` 中添加 `make_your_signer()` 工厂函数,并将其注册到
  `_MESSAGE_CAPABLE`(对于不支持
  `sign_message` 的后端,则注册到 `_TRANSACTION_ONLY`)

## Go 签名器

每个 Go 后端都是独立的模块,位于 `go/signers/yoursigner/`,模块路径为
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`。可参考
`go/signers/para/`。关键模式:

- 实现 `core.SolanaSigner`(`Pubkey()`、`SignMessage(ctx, message)`、
  `IsAvailable(ctx)`),并且仅实现一个能力接口:
  `core.TransactionSigner`、`core.ModifyingSigner` 或 `core.SendingSigner`。
  能力通过类型断言来检测,因此无法签署交易的后端
  根本不能带有 `SignTransaction` 方法
- 导出 `Config` 结构体和 `New` 构造函数(当后端需要远程解析其地址时,使用 `New(ctx, cfg)`;在此之前,返回
  `core.NewNotInitializedError`)
- 使用 `core.NewHTTPClient` 或 `core.ResolveHTTPClient` 构建 HTTP 客户端,并使用 `core.NormalizeHTTPSBaseURL`
  校验基础 URL
- 使用 `core.SignTransactionWith` 签署交易,它会对消息字节进行签名并附加签名;使用
  `core.VerifySignature` 验证提供商返回的签名
- 使用 `core.NewSignerError` / `core.WrapSignerError` 以及稳定的错误码(例如 `core.CodeSigningFailed`)返回错误
- 使用 `httptest` 编写单元测试;集成测试放在 `integration_test.go` 中,并置于
  `//go:build integration` 标签之后

## 实现提示

### 错误处理

请始终使用现有的 `SignerError` 变体。`SignerError` 的 `Display` 和 `Debug` 输出均已做脱敏处理,因此请保持错误消息通用,切勿包含原始 API
响应数据。切勿对不受信任的 API 响应使用 `.expect()` 或 `.unwrap()`:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### 安全要求

这些并非建议:使用方正是基于这些要求来选择后端的。如果
您的提供商无法满足其中某一项,请在 PR 以及仓库的
`docs/SECURITY_MODEL.md` 中说明。

- **验证提供商签署的内容。** 在本地计算消息字节,并在附加签名之前,针对您的签名器所要求的位置,
  用这些字节验证返回的签名。验证未通过的签名必须视为失败,绝不能
  附加。
- **声明提供商是否会广播交易。** 如果提供商在服务端执行交易,
  请实现发送形态,并返回可标识已上链交易的签名。如果提供商没有仅签名的端点,
  请将该后端设为仅发送,而不是在调用方不知情的情况下提交交易。
- **绝不要让调用方持有签名未覆盖的交易。**
  会改写交易的提供商签署的是其自身的字节:要么保持
  调用方的交易不变(由广播托管的情形),要么采用修改形态,
  并用提供商的字节整体替换原交易。
- **如实报告广播的不确定性。** 提交之后发生的失败,交易仍可能
  已经上链。请抛出 `BROADCAST_UNCONFIRMED`,而不是通用错误;
  只要持有提供商的交易 ID,就应一并携带;并且在每次创建时发送由消息派生的幂等键,
  这样字节完全相同的重发才是
  安全的。
- **初始化之前绝不签名。** 在 `init()` 之前,公钥应使用 `Option<Pubkey>`(而非 `Pubkey::default()`),
  如果过早尝试签名,则返回配置错误。
- 切勿记录敏感数据(私钥、API 密钥、原始 API 响应),
  并使用会隐藏敏感字段的 `Debug` 实现
- 强制使用 HTTPS(`https_only(true)`,并为 wiremock 使用 `#[cfg(not(test))]` 进行条件编译),
  同时通过 `HttpClientConfig` 配置请求超时和连接超时
  (默认值:30s/5s)
- 使用 `zeroize::Zeroizing<Vec<u8>>` 对中间密钥材料进行清零

### 使用模拟进行测试

使用 `wiremock` 来模拟 HTTP API。仅对错误类型进行断言,而不是错误消息文本:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
