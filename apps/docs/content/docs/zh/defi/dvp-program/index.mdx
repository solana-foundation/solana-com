DvP 程序是 Solana 上券款对付的标准程序,由 Solana 基金会维护,并经 Cantina 审计。双方先就交易达成一致,各自通过普通的代币转账将自己的一端发送到托管账户,再由结算授权方在一笔交易中完成两端的结算,因此要么两端同时转移,要么都不转移。结算授权方是交易中指定的第三方地址,例如撮合该交易的交易场所或代理方。双方都无需编写或部署程序,任何能够发送标准代币转账(`TransferChecked`)的钱包或托管方,无需任何 DvP 专属集成即可为某一端注资。在结算之前,任何一方都可以取回自己的那一端,或解除交易。

<Callout type="warn" title="操作前请先读取记录">

创建交易记录无需许可,因此一条记录并不能证明双方已达成一致。各方在注资前应先读取已存储的条款,结算授权方在结算前也应如此(参见 [验证](#verification-before-funding-and-settlement))。

</Callout>

## 工作原理

每笔交易都有一条由程序所有的记录和两个托管账户,每一端对应一个。资产端参与方(`user_a`)和资金端参与方(`user_b`)分别将代币转入对应一端的托管账户,为该端注资。结算授权方是唯一能够执行结算的签名者。结算时,每一端约定数量的代币会转给对方,多余部分退还给该端的所有者,同时关闭记录和两个托管账户。原子性来自 Solana [交易](/docs/core/transactions):两笔转账位于同一笔交易中,因此要么同时生效,要么都不生效。

所有退款、取回和多余部分的退还,都会发送到参与方自己的 associated token account:`mint_a` 对应 `user_a` 的账户,`mint_b` 对应 `user_b` 的账户。托管方或资金管理系统可以用自己的账户为某一端注资,但任何退还的资产都会进入参与方的账户,而不会退回托管方。每笔交易还会留下一个永久性的标记账户(参见 [状态](#state))。

## 在程序与委托之间做出选择

[使用委托的券款对付(DvP)](/docs/tokenization/dvp)无需程序即可完成同样的交换:双方各自将自己的头寸委托给结算代理,由其在一笔交易中转移两端的资产。

- **程序方式**无需委托,因此每个 token account 只能有一个委托人的限制不适用,且结算授权方无法改变收款去向。每笔交易都依赖一个可升级的程序及其升级权限。
- **委托模式**不依赖任何程序,并且适用于带有 Scaled UI Amount 的 mint。程序会拒绝这类 mint,这意味着任何由 Mosaic 的 `tokenized-security` 模板创建的 mint 都不可用(参见 [mint 配置限制](#mint-configuration-constraints))。

## 角色

该程序是对称的。在其接口中,双方分别是交付 `mint_a` 的 `user_a` 和交付 `mint_b` 的 `user_b`。README 和生成的客户端把 `mint_a` 称为资产端,把 `mint_b` 称为资金端,本文档也沿用这一约定,但程序并不要求资金端必须是现金类工具。两种资产或两种稳定币,同样可以按此方式结算。

| 角色                 | 对象                               | 签名内容                                              | 说明                                                                                                                                                                                                     |
| -------------------- | --------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 资产端参与方      | `user_a`,交付 `mint_a`       | 自己的注资转账;Reclaim、Reject、Recover | keypair 钱包,或基于 PDA 的智能钱包(例如多签金库)。SPL Token 多签账户或 program account 不能作为参与方:Create 会以 `PartyNotSignerCapable` 失败                   |
| 资金端参与方       | `user_b`,交付 `mint_b`       | 自己的注资转账;Reclaim、Reject、Recover | 要求相同                                                                                                                                                                                          |
| 结算授权方 | 创建时指定的第三方地址 | Settle、Cancel                                     | 唯一能够执行结算的签名者。它无法改变收款去向,收款去向在创建时已固定。结算或取消时,已关闭账户的 rent 由它领取                                         |
| rent 支付方           | 签署 `CreateDvp` 的任何人         | Create                                             | 为记录、nonce 墓碑账户以及两个托管账户支付 rent(保持账户开启的 SOL 存款)。不会被记录为 rent 接收方:已关闭账户的 rent 归关闭该交易的人所有 |

## 生命周期

```mermaid
flowchart TD
  C["CreateDvp<br/>permissionless, rent payer signs"] --> FA["Asset-leg party funds escrow A<br/>plain TransferChecked"]
  C --> FB["Cash-leg party funds escrow B<br/>plain TransferChecked"]
  FA --> G{Both legs hold<br/>the agreed amounts}
  FB --> G
  G -->|settlement authority| S["SettleDvp<br/>cash to A, asset to B,<br/>surplus refunded, accounts closed"]
  G -->|settlement authority| X["CancelDvp<br/>both legs refunded, accounts closed"]
  G -->|either party| R["RejectDvp<br/>both legs refunded, accounts closed"]
  FA -.->|asset-leg party, while open| L["ReclaimDvp<br/>own leg back, trade stays open"]
  S -.->|escrow recreated and funded after close| V["RecoverDvp<br/>party drains the recreated escrow"]
```

从 `CreateDvp` 开始,交易一直处于开启状态,直到 Settle、Cancel 或 Reject 之一将其关闭。注资没有专门的指令:当某一端的托管账户中持有的数量不少于约定数量时,该端即视为已注资。Reclaim 针对单独一端,并且不会关闭交易,因此某一端出现问题时,不必迫使另一方取消整笔交易。

## 状态

每笔交易对应一个由程序所有、大小为 458 字节的 `SwapDvp` 账户。其地址由结算授权方、双方、两个 mint 以及一个 nonce 派生而来(种子为 `["dvp", settlement_authority, user_a, user_b, mint_a, mint_b, nonce]`)。金额和时间存储在账户内部,不影响地址,因此必须读取而不能推断。一个小型标记账户,即位于 `["nonce", swap_dvp]` 的 nonce 墓碑账户,会随交易一同创建且永不关闭,因此每一种由参与方、mint、授权方和 nonce 组成的组合只能用于一笔交易。

```mermaid
flowchart TD
  R["SwapDvp record, 458 bytes<br/>PDA seeds: #quot;dvp#quot;, settlement_authority, user_a, user_b, mint_a, mint_b, nonce"]
  R -->|token account owner| EA["Escrow A<br/>Associated token account of the trade record for mint_a"]
  R -->|token account owner| EB["Escrow B<br/>Associated token account of the trade record for mint_b"]
  R -.->|created with the trade| N["Nonce tombstone<br/>Seeds: #quot;nonce#quot;, SwapDvp address<br/>Holds no data; never closed"]
```

| 字段                                  | 类型          | 含义                                                                                                 |
| -------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------- |
| `bump`                                 | `u8`          | PDA bump                                                                                                |
| `user_a`、`user_b`                     | `Pubkey`      | 交易双方                                                                                         |
| `mint_a`、`mint_b`                     | `Pubkey`      | 资产端和资金端的 mint                                                                        |
| `settlement_authority`                 | `Pubkey`      | 唯一能够执行结算或取消的签名者                                                               |
| `token_program_a`、`token_program_b`   | `Pubkey`      | 拥有各 mint 的 token program;一笔交易可以混用 SPL Token 和 Token-2022 的两端                    |
| `amount_a`、`amount_b`                 | `u64`         | 每一端的约定数量,以 mint 的最小单位(基本单位)计                                 |
| `expiry_timestamp`                     | `i64`         | 超过该网络时间(链上时钟)后,Settle 会被拒绝。Reclaim、Cancel 和 Reject 仍然可用 |
| `nonce`                                | `u64`         | 用于区分种子其他部分相同的交易。仅可使用一次                                             |
| `ref_string`                           | `[u8; 64]`    | 不透明的客户端引用,以零填充;程序从不读取它                                     |
| `user_a_settlement_destination`        | `Pubkey`      | 在 Settle 时接收资金端;默认为 `user_a`                                                   |
| `user_b_settlement_destination`        | `Pubkey`      | 在 Settle 时接收资产端;默认为 `user_b`                                                  |
| `mint_a_authority`、`mint_b_authority` | `Pubkey`      | 创建时记录的 mint 授权方;若其中任何一个发生变化,Settle 会失败                           |
| `earliest_settlement_timestamp`        | `Option<i64>` | 如已设置,则在该网络时间之前 Settle 会被拒绝                                                     |

字段列表取自该程序 IDL 中 [创建交易](/docs/defi/dvp-program/create-a-trade#install) 下所指明的提交版本。

## 指令

| 指令  | 签名者               | 作用                                                                                                                                                              |
| ------------ | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CreateDvp`  | 任意支付方            | 创建 `SwapDvp` 记录、其 nonce 墓碑账户以及两个托管账户。不转移任何代币                                                                        |
| `ReclaimDvp` | `user_a` 或 `user_b` | 从托管账户中退回签名者自己的那一端。交易保持开启,该端可以再次注资                                                                      |
| `SettleDvp`  | 结算授权方 | 将 `amount_a` 转到 `user_b` 的目标地址,将 `amount_b` 转到 `user_a` 的目标地址,把多余部分退还给该端的参与方,并关闭记录和两个托管账户 |
| `CancelDvp`  | 结算授权方 | 将托管账户 A 中的全部余额退还给 `user_a`,将托管账户 B 中的全部余额退还给 `user_b`,并关闭记录和两个托管账户                                                            |
| `RejectDvp`  | `user_a` 或 `user_b` | 效果与 Cancel 相同,但由参与方签名                                                                                                                            |
| `RecoverDvp` | `user_a` 或 `user_b` | 交易关闭后:将重新创建的托管账户中的资产转入签名者自己的 token account 并关闭该托管账户。适用于在 Settle、Cancel 或 Reject 之后才到账的存款  |

无论是谁为托管账户注资,所有退款都会发送到参与方针对该端 mint 的 associated token account。

每条指令的账户和参数,请参见对应步骤的页面。

## 事件与索引

该程序不会发出任何链上事件。索引器或对账系统会读取 `SwapDvp` 账户状态以及两个托管账户的代币余额,并使用 `ref_string` 将交易与其链下订单关联起来。由于记录会在结算时关闭,事后需要交易条款的系统应在读取时将其存储下来,或从创建该交易的链上交易中重建。

## 支持的代币

一笔交易可以将 SPL Token 腿与 Token-2022 腿配对;每条腿都带有各自的 Token Program。支持 Wrapped SOL 腿。

| 某一腿 mint 上的 Token-2022 扩展                                                     | 程序行为                                                  |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| TransferFee、InterestBearing、ScaledUiAmount、NonTransferable                            | 在 Create 和 Settle 时被拒绝,并返回 `BlockedMintExtension`         |
| PermanentDelegate、Pausable、DefaultAccountState、冻结权限(freeze authority)、MintCloseAuthority | 可接受;各权限方均可对托管的代币执行操作           |
| ConfidentialTransfer                                                                     | 可接受;该腿上的金额是公开的                          |
| TransferHook                                                                             | 支持,每条腿最多 32 个额外账户                        |
| 目标账户或退款账户上的 MemoTransfer                                          | 可接受;程序会在转账前发出所需的 memo |

转账费用会导致接收方实际收到的金额少于约定金额。Interest Bearing 和 Scaled UI Amount 不会改变原始金额,但其利率或乘数可能在交易创建与结算之间发生变化,从而改变约定金额的显示方式。NonTransferable 会让两条腿都无法动用。

在交易存续期间,被接受的权限方可以转移、冻结或暂停托管的代币(见下文)。托管账户无法配置为接收机密转账,因此机密腿上的托管金额和结算金额都是公开的。

对于带 hook 的 mint,客户端会解析该 hook 的额外账户,并将其附加到 Settle、Cancel、Reject、Reclaim 和 Recover 中。每条腿 32 个的上限包含 hook 程序及其验证账户。如果 hook 权限方将 hook 的账户列表扩充到超过该上限,则该腿上的所有转账都会失败,包括 Reclaim、Cancel、Reject 和 Recover,直到该权限方撤销此更改。当两条腿都带有 hook 时,交易账户数量限制可能会先于每条腿的上限生效。

当目标账户或退款账户要求 memo 时,程序会在转账前调用 Memo 程序,这就是为什么每条将代币转出托管的指令都需要一个 `memo_program` 账户。

### Mint 配置约束

**Scaled UI Amount。** Solana 基金会的发行工具包 [Mosaic](https://github.com/solana-foundation/mosaic) 中的 `tokenized-security` 模板始终会添加 Scaled UI Amount,因此程序不接受使用该模板创建的 mint 作为交易腿。供本程序使用的 mint 可以在不带该扩展的情况下创建(参见 [Token Extensions](/docs/tokens/extensions));[使用委托的 DvP](/docs/tokenization/dvp) 通过委托权限结算,不适用此检查。

**默认冻结的 mint。** 每笔交易的托管账户都是一个 associated token account,由为该交易新生成的 Program Derived Address 所拥有。在 Default Account State 设为冻结的 mint 上,托管账户创建后即处于冻结状态,向其注资的转账会失败,直到它被解冻。在 [Token ACL](/docs/tokenization/token-acl) 下,这意味着发行方或其过户代理需要在注资前准入该笔交易的托管账户:要么将交易记录的地址(即托管账户的所有者)加入允许名单,这样在 mint 的 Token ACL 配置启用了无许可解冻的情况下,任何人都可以解冻该托管账户;要么由冻结权限方直接解冻。冻结的托管账户还会阻止该腿上的 Settle、Reclaim、Cancel、Reject 和 Recover,因此在交易存续期间,冻结权限方(对于带 hook 的 mint 还包括 hook 权限方)是受信任的一方。此处描述了冻结托管账户的路径,devnet 代码片段中未演示该路径。

## 限制

- 不提供撮合、价格发现或订单簿。交易双方在账本之外约定条款,并由其中一方记录。
- 不支持轧差,且仅限双边:一条记录就是两方之间的一笔交易。
- 不支持部分成交。Settle 会精确转移每条腿的约定金额,并将任何剩余部分退还给该腿的交易方。
- 不支持账本外的腿。两条腿都必须是 Solana 上的 token account;基于现有支付渠道的现金腿单独结算并进行对账。
- 不进行资格检查,也没有允许名单或 KYC。持有人资格由 mint 自身的控制机制来保证。
- 不支持自动结算。结算授权方必须签名。
- 没有事件,除交易手续费和 rent 外也没有协议费用。

该程序消除了双方之间的本金风险:除非两条腿同时转移,否则任何一条腿都不会转移。但它无法消除任一代币的发行方信用风险或赎回风险、mint 的冻结、暂停或永久委托权限对托管代币采取操作的可能性(参见[支持的代币](#supported-tokens)),也无法消除对结算授权方能够及时签名的依赖。

## 注资与结算前的验证

`CreateDvp` 是无需许可的:只有付款方需要签名,交易方和结算授权方无需签名。因此任何人都可以创建一条指定任意交易方和任意条款的记录。在注资之前以及结算之前,请读取 `SwapDvp` 账户并确认:

1. 该账户由 DvP 程序拥有,且大小恰好为 458 字节。不属于该程序的账户可能被填入能够解码成真实记录的字节。
2. `user_a`、`user_b`、`mint_a`、`mint_b` 和 `settlement_authority` 与约定的交易一致。
3. `amount_a`、`amount_b`、`expiry_timestamp` 和 `earliest_settlement_timestamp` 与约定的条款一致。
4. 两个结算目标地址均为约定的地址。伪造的记录可能会重定向收益。

[为各条腿注资](/docs/defi/dvp-program/fund-the-legs#verify-the-terms)列出了生成的客户端中带检查的读取器,并通过代码展示了该检查。

当 Settle 交易达到 [`finalized`](/docs/rpc#configuring-state-commitment) 时,即可将该笔交易视为已结算。这是网络层面的确认级别;它是否同时构成法律意义上的结算终局性,取决于各方的协议以及适用的法律制度。

## 版本管理

`SwapDvp` 账户不含版本字段。其布局固定为 458 字节(`SwapDvp::LEN`),带检查的读取器会拒绝任何其他长度的账户。IDL 自带版本号,截至 2026 年 10 月 2 日为 `0.1.0`。

该程序在两个集群上均可升级(参见 [Program ID](#program-id))。交易记录仅在结算、取消或拒绝之前存在,因此请查阅代码仓库,了解升级会如何处理未完成的交易,并根据已部署版本的 IDL 重新生成客户端。
