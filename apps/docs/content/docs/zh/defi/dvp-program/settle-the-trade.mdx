`SettleDvp` 由交易记录中指定的结算授权方签名。它在一笔交易中将资产端的 `amount_a` 转入现金端一方的目标账户，将现金端的 `amount_b` 转入资产端一方的目标账户，把任一托管账户中的多余部分退还给该端的一方，并关闭交易记录和两个托管账户。如果其中任何一笔转账无法完成，该指令会失败，所有资产都不会发生移动。

本页承接[创建交易](/docs/defi/dvp-program/create-a-trade)和[为两端注资](/docs/defi/dvp-program/fund-the-legs)；客户端、签名者、`trade` 以及各方的 token account 均沿用之前的设置。

## 签名前重新验证

结算授权方签署的交易会移动两端的资产，因此它在签名前要执行与各方相同的读取检查：所有者、大小、各方、mint、金额、到期时间以及两个目标账户（参见[为两端注资](/docs/defi/dvp-program/fund-the-legs#verify-the-terms)）。程序本身还会在结算时重新检查：每个 mint 是否仍属于创建时记录的 token program，是否不含被禁止的扩展，以及 mint authority 是否与创建交易时相同。因此，如果 mint 被重新创建后带有被禁止的扩展、使用了不同的 token program 或不同的 mint authority，则无法完成结算。

## 创建接收方账户

Settle 会写入四个程序不会创建的 token account：

| 账户                | 接收内容                     | 所有者                           |
| ---------------------- | ---------------------------- | ------------------------------- |
| `userADestinationAtaB` | 现金端（`amount_b`）    | `user_a_settlement_destination` |
| `userBDestinationAtaA` | 资产端（`amount_a`）   | `user_b_settlement_destination` |
| `userAAtaA`            | 资产端的任何多余部分 | `user_a`                        |
| `userBAtaB`            | 现金端的任何多余部分  | `user_b`                        |

只有当托管账户中的金额超过约定金额时，才会用到多余部分的退还账户，但任何持有该 mint 的人只需向托管账户转入少量最小单位，就能制造出多余部分。如果退款账户不存在，整个 Settle 指令都会失败，因此请在同一笔交易中以幂等方式创建全部四个账户。

    import {

    const destinationA = t.userASettlementDestination; // defaults to userA
    const destinationB = t.userBSettlementDestination; // defaults to userB

      tokenProgram: tokenProgramB,

    const [userBDestinationAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: destinationB,
      tokenProgram: tokenProgramA,
    });
    // userAAtaA and userBAtaB are from fund the legs.

    const createRecipientAccounts = [
      { ata: userADestinationAtaB, owner: destinationA, mint: mintB, tokenProgram: tokenProgramB },
      { ata: userBDestinationAtaA, owner: destinationB, mint: mintA, tokenProgram: tokenProgramA },

      { ata: userBAtaB, owner: userB, mint: mintB, tokenProgram: tokenProgramB },

      getCreateAssociatedTokenIdempotentInstruction({
        payer: authoritySigner,
        ata,
        owner,
        mint,
        tokenProgram,
      }),
    );

## 执行 Settle

`legAExtrasCount` 告诉程序：在固定列表之后追加的账户中，有多少个属于资产端转账的 transfer hook，其余的则属于现金端。对于没有 transfer hook 的 mint，传入零并且不追加任何账户。memo 程序的 program account 是该指令的必需账户，仅用于要求附带 memo 的目标账户。

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { MEMO_PROGRAM_ADDRESS } from "@solana-program/memo";
    import { getSettleDvpInstruction } from "./dvp";

    const settleInstruction = getSettleDvpInstruction({
      settlementAuthority: authoritySigner,
      swapDvp,
      mintA,
      mintB,
      dvpAtaA: escrowA,
      dvpAtaB: escrowB,
      userADestinationAtaB,
      userBDestinationAtaA,
      userAAtaA,
      userBAtaB,
      tokenProgramA,
      tokenProgramB,
      memoProgram: MEMO_PROGRAM_ADDRESS,
      legAExtrasCount: 0,
    });

    const { context: settleContext } = await client.sendTransaction([
      ...createRecipientAccounts,
      settleInstruction,
    ]);
    const settleSignature = settleContext.signature;
    console.log("Submitted:", settleSignature);

    // sendTransaction returns at the client's commitment (confirmed by default).
    // Wait for finalized before recording the trade as settled.
    let finalized = false;
    for (let attempt = 0; attempt < 30 && !finalized; attempt++) {
      const {
        value: [status],
      } = await client.rpc.getSignatureStatuses([settleSignature]).send();
      if (status?.err) {
        throw new Error("Settle transaction failed");
      }
      finalized = status?.confirmationStatus === "finalized";
      if (!finalized) {
        await new Promise((resolve) => setTimeout(resolve, 2_000));
      }
    }
    if (!finalized) {
      // A closed record means it settled; an open one is safe to settle again.
      throw new Error("Settle not finalized after 60s; read the trade record");
    }
    console.log("Settled:", settleSignature);
    ```

### Transfer hook

生成的 IDL 只列出固定账户，因此生成的构建器并不了解 hook 账户。请按照直接转账该代币时的相同方式，解析每个 hook mint 的额外账户元数据，然后将它们追加到指令中：先是资产端的账户，再是现金端的账户，并将 `legAExtrasCount` 设置为第一组的账户数量。在 TypeScript 中，将解析得到的元数据展开到指令的 `accounts` 数组中；在 Rust 中，则在构建器上使用 `add_remaining_accounts`。每一端的上限为 32 个账户，其中包括 hook 程序和验证账户；当两端都带有 hook 时，交易的账户数量上限可能会先达到。程序会去除所有转发账户的签名者标记，因此 hook 无法通过这条路径获取结算授权方的签名。

## 记录结果

当 Settle 交易达到 `finalized` 时，才应将该交易视为已结算。结算后，交易记录和两个托管账户将不复存在，因此如果系统之后需要这些条款，应当从结算前的读取结果或创建交易中获取并保存。已关闭账户的 rent 已转给结算授权方。

## Settle 错误

`LegNotFunded` 表示某个托管账户中的金额低于约定金额；`DvpExpired` 和 `SettlementTooEarly` 表示错过了时间窗口；`MintAuthorityChanged` 和 `BlockedMintExtension` 表示某个 mint 在创建后发生了变化；`RecipientAtaMismatch` 表示目标账户或退款 token account 缺失，或者不再属于预期的所有者和 mint，通常是因为跳过了上面的账户创建步骤。在所有这些情况下，资产都不会发生移动，各方可以撤销交易，但会受制于 mint 的相关权限（参见[撤销交易](/docs/defi/dvp-program/unwind-a-trade)）。
