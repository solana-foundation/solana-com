# 使用 Jito DontFront 进行 MEV 防护

最大可提取价值(Maximal Extractable Value,MEV)是指通过对区块内的交易进行重新排序、插入或排除所能获取的价值。MEV 并非某一条链所独有,而是任何由区块生产者控制交易顺序的区块链的基本属性。某些形式的 MEV,例如套利,通过纠正各个 DEX 之间的价格差异,有助于保持市场效率;而另一些形式,例如三明治攻击,则直接从用户身上攫取价值。对于构建 DeFi 应用的开发者而言,这可能意味着更差的交易执行效果和利润损失。

本指南重点介绍三明治攻击(一种常见的有害 MEV),以及如何使用 Jito 的 `dontfront` 功能来缓解这类攻击。

推荐先阅读:
[Jito Bundles](https://solana.com/docs/tools/transaction-landing#jito-bundles)

## Solana 上的 MEV

与拥有公开内存池(mempool)的链相比,Solana 的架构本身就缩小了 MEV 的攻击面。交易会被直接转发给即将出块的 leader,而不是停留在共享的内存池中;未处理的交易大约在 150 个区块(约 1 分钟)后过期。这大大缩短了 searcher 观察并利用待处理交易的时间窗口。

即便如此,MEV 提取仍然存在。拥有优化基础设施并直连 validator 的 searcher 可以观察交易流并作出响应。Solana 上的大部分 MEV 活动是原子套利:即机器人在单笔交易中纠正各个 DEX 之间的价格差异。这类 MEV 通常是有益的,因为它提升了各市场之间价格的一致性。

有害的那一类,即三明治攻击,才是开发者应当主动防范的对象。

## 什么是三明治攻击?

当 searcher 检测到您待处理的兑换交易并利用交易排序进行攻击时,就会发生三明治攻击:

1. **抢跑(Front-run)**:searcher 在您的交易之前买入该代币,从而推高价格
2. **您的交易执行**,成交价格比预期更差
3. **尾随(Back-run)**:searcher 在您的交易之后卖出该代币,赚取差价

在 Solana 上,这可以通过
[Jito bundle](https://docs.jito.wtf/lowlatencytxnsend/#what-are-bundles)实现。searcher 提交一个类似 `[frontrun_tx, your_tx, backrun_tx]` 的交易 bundle,区块引擎会按顺序原子地执行这些交易。受害者得到更差的成交价格,而 searcher 则从价差中获利。

## DontFront 的工作原理

[DontFront](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation) 是 Jito 区块引擎的一项功能,可防止 searcher 在 bundle 中将交易放在您的交易之前。

其机制是:在您交易的任意指令中添加任何以 `jitodontfront` 开头的有效 Solana 公钥。区块引擎会识别该前缀并强制执行一条规则:**任何包含您交易的 bundle 都必须将其放在索引 0 的位置**。

```
Without dontfront:  [frontrun_tx, your_tx, backrun_tx]  ← sandwich possible
With dontfront:     [your_tx, ...]                       ← your tx must be first
```

### 分步说明

1. **选择一个以 `jitodontfront` 开头的有效地址**(例如 `jitodontfront111111111111111111111111111111`)。该账户无需在链上存在;它不会被读取或写入。您可以使用 @solana/kit 中的 [`assertIsAddress`](https://www.solanakit.com/api/functions/assertIsAddress) 函数来验证字符串是否为有效地址,也可以在 Solana Explorer 中输入该地址,查看其是否能够解析。以下是一个[无效地址](https://explorer.solana.com/address/jitodontfront11111111111111111111111111111INVALID)的示例。

2. **将其作为只读、非签名者账户添加**到交易中的任意指令里。为了获得最佳的上链速度,请将其标记为只读。大多数程序(包括 System Program)都会忽略超出其预期的额外账户。

3. **通过 Jito 区块引擎提交**:
   - `sendTransaction`:
     `https://mainnet.block-engine.jito.wtf/api/v1/transactions`
   - `sendBundle`: `https://mainnet.block-engine.jito.wtf/api/v1/bundles`

   文档:
   [sendTransaction](https://docs.jito.wtf/lowlatencytxnsend/#sendtransaction)
   和 [sendBundle](https://docs.jito.wtf/lowlatencytxnsend/#sendbundle)

4. 区块引擎会检测 `jitodontfront` 前缀并强制执行排序规则。

### 区块引擎的处理方式

当区块引擎发现某笔交易包含 `jitodontfront` 账户时:

- 通过 `sendTransaction`:该交易受到保护。任何 bundle 都无法将其他交易放在它之前
- 通过 `sendBundle`:该交易必须出现在索引 0 的位置,否则整个 bundle 会被拒绝

不包含 `jitodontfront` 账户的交易和 bundle 不受影响。

## Bundle 排序规则

当 `jitodontfront` 交易出现在 bundle 中时,适用以下规则。

### 允许的模式

```
[tx_with_dontfront, tip]
[tx_with_dontfront, arbitrage, tip]
[tx_with_dontfront_signer1, tx_with_dontfront_signer1_and_signer2, tip]
```

### 同一 Bundle 中的多笔 DontFront 交易

当**同时**满足以下两个条件时,允许在单个 bundle 中包含多笔 dontfront 交易:

1. 所有 dontfront 交易都**连续排列在** bundle 的**最前面**
2. 每笔 dontfront 交易与第一笔 dontfront 交易**至少共享一个签名者**

```
✅ [txA_df, txB_df, txC_df, arbitrage, tip]
   (contiguous at front, overlapping signers)

✅ [txA_df_signer1_signer2, txB_df_signer1_signer3, txC_df_signer2_signer4]
   (each shares a signer with txA)
```

### 被拒绝的模式

```
❌ [tip, tx_with_dontfront]
   → dontfront tx is not at index 0

❌ [txA_df_signer1, txB_df_signer2]
   → no overlapping signer between txA and txB

❌ [trade, tx_with_dontfront, arbitrage, tip]
   → dontfront tx is not at the front
```

## 集成示例

如需快速的代码示例,请参阅
[MEV 防护 cookbook 条目](/developers/cookbook/transactions/mev-protection)。

### TypeScript(@solana/kit)

核心思路是编写一个辅助函数,将 dontfront 账户追加到任意指令中:

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
import {
  address,
  AccountRole,
  type Instruction,
  type Address
} from "@solana/kit";

const DONT_FRONT: Address = address(
  "jitodontfront111111111111111111111111111111"
);

// !mark(1:9)
function withDontFront(ix: Instruction): Instruction {
  return {
    ...ix,
    accounts: [
      ...(ix.accounts ?? []),
      { address: DONT_FRONT, role: AccountRole.READONLY }
    ]
  };
}
```

```rs !! title="Rust"
use solana_sdk::{
    instruction::{AccountMeta, Instruction},
    pubkey::Pubkey,
};
use std::str::FromStr;

const DONT_FRONT_ACCOUNT: &str =
    "jitodontfront111111111111111111111111111111";

// !mark(1:6)
fn with_dontfront(ix: &mut Instruction) {
    let dontfront =
        Pubkey::from_str(DONT_FRONT_ACCOUNT).unwrap();
    ix.accounts
        .push(AccountMeta::new_readonly(dontfront, false));
}
```

</CodeTabs>

然后将已签名的交易提交到 Jito 区块引擎,而不是标准的 RPC 节点。请始终使用 base64 编码。Jito 的 API 已弃用 Base58。

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
// !mark(1:2)
const response = await fetch(
  "https://mainnet.block-engine.jito.wtf/api/v1/transactions",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      jsonrpc: "2.0",
      id: 1,
      method: "sendTransaction",
      // !mark
      params: [base64Tx, { encoding: "base64" }]
    })
  }
);
```

```rs !! title="Rust"
let serialized = bincode::serialize(&tx)?;
// !mark
let base64_tx = base64::engine::general_purpose::STANDARD
    .encode(&serialized);

// !mark(1:2)
let response = client
    .post("https://mainnet.block-engine.jito.wtf/api/v1/transactions")
    .json(&serde_json::json!({
        "jsonrpc": "2.0",
        "id": 1,
        "method": "sendTransaction",
        "params": [base64_tx, {"encoding": "base64"}]
    }))
    .send()
    .await?;
```

## 最佳实践

DontFront 只是其中一层防护。强健的 MEV 缓解策略应结合多种方法:

### 交易层面的防护

- **设置严格的滑点容忍度。** 防御三明治攻击最有效的单一手段是限制兑换时可接受的滑点。更小的滑点窗口会压缩攻击者可获得的利润空间,使您的交易不那么容易成为三明治攻击的目标。

- **设置合适的小费和优先费。** 在网络拥堵期间,更高的小费和优先费能提高您的交易/bundle 快速上链的可能性,从而缩短 searcher 采取行动的时间窗口。有关如何设置合适小费的更多详情,请参阅 Jito 关于
  [小费金额(Tip Amounts)](https://docs.jito.wtf/lowlatencytxnsend/#tip-amount)的文档。

- **优化计算单元使用。** 每个区块可用的计算单元数量有限(每个账户在每个区块中可用的计算单元数量也有限)。为了最大限度地提高您的交易/bundle 被打包进区块的可能性,您应当优化计算单元的使用。详情请参阅
  [如何在 Solana 上优化计算用量](/developers/cookbook/transactions/optimize-compute)指南。

### DontFront 专项建议

1. **将 dontfront 账户标记为只读。** 标记为可写同样有效,但只读可以
   [优化上链速度](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation)。

2. **为每个应用使用唯一的 dontfront pubkey。** 任何以 `jitodontfront` 开头的 pubkey 都可以使用。使用唯一的变体(例如 `jitodontfront111111111111111111111111111123`),可以在检查链上数据时区分各个应用的使用情况。

3. **DontFront 支持地址查找表(Address Lookup Table)。** dontfront 账户可以通过 ALT 引入。但请勿对小费账户使用 ALT。

## 局限性

- **仅限区块引擎。** DontFront 由 Jito 区块引擎强制执行。直接提交给 validator(绕过 Jito)的交易不受保护。

- **不作保证。** 摘自 Jito 文档:_“此功能可能有助于减少三明治攻击,但不保证一定有效,也不能解决交易排序方面的所有情形,包括由第三方进行的任何排序。”_

- **仅限 Mainnet/Testnet。** 这是 Jito 区块引擎的功能,在 devnet 或 localhost 上无法使用。
