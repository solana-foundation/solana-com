## Sleutelbeheer

- **Maak privésleutels nooit zichtbaar in frontendcode.** Gebruik backend-ondertekening, hardwarewallets, multisignature-wallets of sleutelbeheerdiensten.
- **Scheid hot en cold wallets.** Gebruik de hot wallet voor operationele zaken en de cold wallet voor de treasury.
- **Maak een back-up van alle productiesleutels.** Bewaar versleutelde back-ups op meerdere beveiligde locaties. Als je een sleutel kwijtraakt, verlies je permanent de toegang.
- **Gebruik verschillende sleutels voor devnet en mainnet.** Je devnet-sleutels mogen niet dezelfde zijn als je mainnet-sleutels. Gebruik omgevingsgebaseerde configuratie om ervoor te zorgen dat voor elk netwerk de juiste sleutels worden geladen.

## Infrastructuur voor ondertekening

Gebruik voor backend-ondertekening in productie [Keychain](/docs/tools/keychain), een uniforme ondertekeningsbibliotheek die meerdere sleutelbeheer-backends via één interface abstraheert: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP, Para, Dfns, Crossmint, Openfort en Utila. Zo kun je lokaal ontwikkelen met sleutels in het geheugen en daarna overstappen op backends van productiekwaliteit zonder je applicatiecode te wijzigen.

Weet je niet welke backend het beste past? Zie
[Een backend kiezen](/docs/tools/keychain/choosing-a-backend). Keychain is
beschikbaar voor zowel [Rust](https://crates.io/crates/solana-keychain) als
[TypeScript](https://www.npmjs.com/package/@solana/keychain).

## RPC-beveiliging

Behandel RPC-endpoints als API-sleutels: maak ze niet zichtbaar in frontendcode, waar ze kunnen worden onderschept en misbruikt. Gebruik een backend-proxy of omgevingsvariabelen die niet in clientcode worden gebundeld.

- [QuickNode: Best practices voor endpointbeveiliging](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Bescherm je Solana API-sleutels: best practices voor beveiliging](https://www.helius.dev/docs/rpc/protect-your-keys)

## Monitoring

Houd in productie deze metrics bij:

| Metric                   | Waarom                    |
| ------------------------ | ---------------------- |
| Slagingspercentage van transacties | Problemen vroegtijdig opsporen    |
| Bevestigingslatentie     | De netwerkgezondheid bewaken |
| Uitgaven aan prioriteitsfees       | Kostenbeheer        |
| RPC-foutpercentage           | Gezondheid van de provider        |

Stel waarschuwingen in voor:

- Overboekingen vanuit de treasury boven een drempelwaarde
- Pieken in het percentage mislukte transacties
- Ongebruikelijke ontvangerspatronen
- Stijgingen in het RPC-foutpercentage

Zie onze [Indexeringsgids](/docs/payments/accept-payments/indexing) voor realtime transactiemonitoring op schaal.

## Adressen verifiëren

Elk token en elk programma heeft precies één correct adres op mainnet. Gespoofde tokens die USDC of andere stablecoins nabootsen komen vaak voor: ze hebben dezelfde naam en hetzelfde symbool, maar een andere mint. Je applicatie moet de mint-adressen hardcoden of op een allowlist zetten (afhankelijk van je vereisten) en ze nooit dynamisch accepteren uit onbetrouwbare bronnen.

**Omgevingsgebaseerde configuratie:** Devnet en Mainnet gebruiken vaak totaal verschillende token-mints. Zet de configuratie van je applicatie zo op dat per omgeving de juiste adressen worden geladen. Hardcode geen mainnet-adressen om ze tijdens het testen te vergeten te wisselen, en lever al helemaal geen devnet-adressen uit naar productie.

Enkele veelgebruikte stablecoin-mints zijn:

| Token | Uitgever | Mint-adres                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Ook programma-adressen zijn belangrijk. Instructies naar het verkeerde programma sturen mislukt, of erger: leidt tot onomkeerbaar verlies van fondsen. De adressen van het Token Program zijn:

| Programma            | Adres                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Het op een allowlist zetten van de juiste adressen beschermt tegen gespoofde tokens, maar niet tegen het verzenden naar het verkeerde _soort_ account. Een ontvangersadres kan een wallet, een token account, een mint of een programma zijn, en elk vereist een andere afhandeling. Native SOL die naar iets anders dan een wallet wordt gestuurd, valt buiten de controle van de afzender — volledig verloren bij een mint of programma, alleen door de accounteigenaar te herstellen bij een token account — zonder dat een mislukte transactie de gebruiker waarschuwt.

<Callout type="warn" title="Valideer ontvangers vóór het verzenden">
  Classificeer elk ontvangersadres voordat je een overboeking ondertekent. Zie [Adres verifiëren](/docs/payments/send-payments/verify-address) voor de volledige beslisboom en referentiecode waarmee wallets, token accounts, mints en programma's worden onderscheiden.
</Callout>
