## Sleutelbeheer

- **Maak nooit privésleutels zichtbaar in frontendcode.** Gebruik backend-ondertekening, hardwarewallets, multisignature-wallets of sleutelbeheerdiensten.
- **Scheid hot en cold wallets.** Gebruik een hot wallet voor operaties en een cold wallet voor de treasury.
- **Maak een back-up van alle productiesleutels.** Bewaar versleutelde back-ups op meerdere beveiligde locaties. Het verlies van een sleutel betekent permanent verlies van toegang.
- **Gebruik verschillende sleutels voor devnet en mainnet.** Je devnet-sleutels mogen niet dezelfde zijn als je mainnet-sleutels. Gebruik omgevingsgebaseerde configuratie om ervoor te zorgen dat voor elk netwerk de juiste sleutels worden geladen.

## Ondertekeningsinfrastructuur

Gebruik voor backend-ondertekening in productie [Keychain](/docs/tools/keychain): een uniforme ondertekeningsbibliotheek die meerdere sleutelbeheer-backends abstraheert via één enkele interface: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP, Para, Dfns, Crossmint, Openfort en Utila. Hiermee kun je lokaal ontwikkelen met in-memory-sleutels en vervolgens overstappen op backends van productiekwaliteit zonder de applicatiecode te wijzigen.

Weet je niet welke backend bij je past? Zie [Een backend kiezen](/docs/tools/keychain/choosing-a-backend). Keychain is beschikbaar voor zowel [Rust](https://crates.io/crates/solana-keychain) als [TypeScript](https://www.npmjs.com/package/@solana/keychain).

## RPC-beveiliging

Behandel RPC-endpoints als API-sleutels: maak ze niet zichtbaar in frontendcode, waar ze kunnen worden onderschept en misbruikt. Gebruik een backend-proxy of omgevingsvariabelen die niet in clientcode worden gebundeld.

- [QuickNode: Endpoint Security Best Practices](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Protect Your Solana API Keys: Security Best Practices](https://www.helius.dev/docs/rpc/protect-your-keys)

## Monitoring

Houd deze metrics bij in productie:

| Metric                   | Waarom                    |
| ------------------------ | ---------------------- |
| Slagingspercentage van transacties | Problemen vroegtijdig opsporen    |
| Bevestigingslatentie     | De netwerkgezondheid bewaken |
| Uitgaven aan prioriteitsvergoedingen       | Kostenbeheer        |
| RPC-foutpercentage           | Gezondheid van de provider        |

Stel waarschuwingen in voor:

- Overboekingen vanuit de treasury boven een drempelwaarde
- Pieken in het percentage mislukte transacties
- Ongebruikelijke ontvangerpatronen
- Toename van het RPC-foutpercentage

Zie onze [Indexeringsgids](/docs/payments/accept-payments/indexing) voor realtime transactiemonitoring op schaal.

## Adressen verifiëren

Elk token en elk programma heeft precies één correct adres op mainnet. Nagemaakte tokens die USDC of andere stablecoins nabootsen komen vaak voor: ze hebben dezelfde naam en hetzelfde symbool, maar een andere mint. Je applicatie moet de mint-adressen hardcoden of op een allowlist zetten (afhankelijk van je vereisten) en ze nooit dynamisch accepteren van onbetrouwbare bronnen.

**Omgevingsgebaseerde configuratie:** Devnet en Mainnet gebruiken vaak compleet verschillende token-mints. Stel de configuratie van je applicatie zo in dat per omgeving de juiste adressen worden geladen. Hardcode geen mainnet-adressen om ze vervolgens tijdens het testen te vergeten om te wisselen, of erger nog, devnet-adressen naar productie te sturen.

Enkele veelgebruikte stablecoin-mints zijn:

| Token | Uitgever | Mint-adres                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Ook programma-adressen zijn belangrijk. Instructies sturen naar het verkeerde programma mislukt, of leidt erger nog tot onherstelbaar verlies van geld. De adressen van het Token Program zijn:

| Programma            | Adres                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Het op een allowlist zetten van de juiste adressen beschermt tegen nagemaakte tokens, maar niet tegen het verzenden naar het verkeerde _soort_ account. Een ontvangersadres kan een wallet, een token account, een mint of een programma zijn, en elk vereist een andere afhandeling. Native SOL die naar iets anders dan een wallet wordt gestuurd, valt buiten de controle van de afzender: bij een mint of programma is het volledig verloren, bij een token account kan alleen de accounteigenaar het terughalen. Er is geen mislukte transactie die de gebruiker waarschuwt.

<Callout type="warn" title="Valideer ontvangers voordat je verzendt">
  Classificeer elk ontvangersadres voordat je een overboeking ondertekent. Zie [Adres verifiëren](/docs/payments/send-payments/verify-address) voor de volledige beslisboom en referentiecode die wallets, token accounts, mints en programma's van elkaar onderscheidt.
</Callout>
