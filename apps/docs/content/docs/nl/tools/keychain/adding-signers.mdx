Deze handleiding is bedoeld voor wallet service providers en ontwikkelaars die
nieuwe key management-oplossingen willen integreren in de `solana-keychain`
library. Door jouw signer-implementatie toe te voegen, stel je ontwikkelaars in
staat om jouw service te gebruiken voor veilige Solana-transactieondertekening
via een uniforme interface.

Keychain houdt de implementaties in Rust, TypeScript, Python en Go op gelijke voet.
PR's die alle vier bevatten genieten sterk de voorkeur. Als je er maar één kunt bijdragen,
is dat prima, maar verwacht dat de overige vereist zijn voordat de signer wordt opgenomen
in een release.

_Gebruik je Claude Code? De
[`add-signer-ci`-skill](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)
van de repo zet de CI-workflows op voor een nieuwe signer die via een fork-PR is bijgedragen._

## Architectuuroverzicht

De bibliotheek gebruikt een architectuur op basis van traits, gedefinieerd in `src/traits.rs`. Elke
signer implementeert de basistrait `SolanaSigner` (`pubkey`, `sign_message`,
`is_available`) plus precies één capability-trait die past bij de opzet van de provider:

- `TransactionSigner` (`sign_transaction`): de provider ondertekent de bytes van de
  aanroeper en de aanroeper verstuurt de transactie. De meeste backends.
- `ModifyingSigner` (`modify_and_sign_transaction`): de provider herschrijft de
  transactie en ondertekent deze vervolgens zonder te versturen.
- `SendingSigner` (`sign_and_send_transaction`): de provider ondertekent en
  verstuurt aan de serverzijde.

De bibliotheek biedt ook een uniforme `Signer`-enum die alle
implementaties omvat, waardoor signing-backends tijdens runtime kunnen worden gekozen. Deze implementeert
alleen de basistrait; capabilities zijn bereikbaar via `as_transaction_signer()`,
`as_modifying_signer()` en `as_sending_signer()`.

## Snelle Integratie Checklist

- Creëer je signer-module met implementatie
- Implementeer de basistrait `SolanaSigner` (`pubkey`, `sign_message`,
  `is_available`) plus de ene capability-trait die past bij de opzet van je provider
  (meestal `TransactionSigner`)
- Voeg een feature flag toe in `Cargo.toml`, inclusief de interne `_remote`-marker als
  je signer reqwest gebruikt
- Werk de `Signer`-enum bij in `src/lib.rs` (variant, `dispatch_signer!`-arm en

## Stap 2: Definieer Je Signer Struct

Definieer in `src/your_service/mod.rs` je signer struct:

```rust

impl std::fmt::Debug for YourServiceSigner {

        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
```

## Stap 3: Implementeer Constructor en Hulpmethoden

Remote signers **moeten** HTTPS afdwingen en HTTP-timeouts configureren. Gebruik
de gedeelde `HttpClientConfig` struct voor timeout-instellingen.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## Stap 4: Implementeer de signer-traits

De basistrait `SolanaSigner` heeft 2 asynchrone methoden (`sign_message`,
`is_available`) plus `pubkey()`. Transactieondertekening hoort in een capability-trait;
de meeste providers implementeren `TransactionSigner`, waarvan `sign_transaction`
`SignTransactionResult` teruggeeft (een getagde enum die aangeeft of de transactie volledig of
gedeeltelijk is ondertekend).

Onderteken de bytes van het bericht, nooit de volledige wire-transactie, en controleer de
handtekening van de provider ertegen voordat je die toevoegt. Gebruik de gedeelde
`TransactionUtil`-helpers voor ondertekening en serialisatie.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

Als je provider de transactie herschrijft voordat deze wordt ondertekend, implementeer dan
in plaats daarvan `ModifyingSigner` en vervang de transactie van de aanroeper volledig door
de bytes van de provider. Als de provider aan de serverzijde verstuurt, implementeer dan `SendingSigner`
en laat de transactie van de aanroeper ongemoeid. Implementeer nooit een capability die je
provider niet kan leveren.

## Stap 6: Feature flag toevoegen

Werk `Cargo.toml` bij om je signer als optionele feature toe te voegen. Remote backends
bevatten de interne `_remote`-marker, die de `From<reqwest::Error>`-
impl in `src/error.rs` activeert; zonder deze marker compileert `?` op reqwest-aanroepen niet als alleen
jouw feature is ingeschakeld.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## Stap 7: De signer-enum updaten

Voeg je signer toe aan `src/lib.rs`. De basisimpl van `SolanaSigner` verwerkt aanroepen via
de macro `dispatch_signer!`, dus voeg daar één arm toe. Capability-toegang zit in
de accessors `as_transaction_signer()`, `as_modifying_signer()` en `as_sending_signer()`:
voeg een `Some(s)`-arm toe aan de accessor die past bij je capability-trait (en,
voor een sending- of modifying-backend, een `None`-arm in `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## Stap 8: Uitgebreide tests toevoegen

Voeg tests toe aan je module (onderaan `src/your_service/mod.rs`):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

## Stap 9: Integratietests toevoegen

Maak `rust/src/tests/test_<name>_integration.rs` aan. Integratietests draaien
tegen de echte service-API (niet wiremock) en zijn afgeschermd achter de
feature `integration-tests`. Elk bestand heeft nodig:

- `pub const`-declaraties voor namen van omgevingsvariabelen
- Een `get_signer()`-helper die omgevingsvariabelen leest via `dotenvy`
- Drie testfuncties: `test_<name>_sign_message`,
  `test_<name>_sign_transaction` en `test_<name>_is_available`
- Feature gates: `#[cfg(feature = "your_service")]` op de module en
  `#[cfg(feature = "integration-tests")]` op elke test

Zie `rust/src/tests/test_para_integration.rs` voor een volledige referentie en
declareer je module in `rust/src/tests/mod.rs`:

```rust
pub mod test_your_service_integration;
```

## Updates van CI-workflows (fork-PR's)

CI is een proces in twee fasen. Stem af met de maintainers om `main` voor te bereiden voordat
jouw PR getest kan worden: zij werken `fork-external-live-manual.yml` bij, voegen omgevingsvariabelen
toe aan `ci.yml` en configureren GitHub Secrets.

Je PR moet deze wijzigingen uit fase 2 bevatten naast je signercode:

- **`ci.yml`**: voeg je Rust-feature toe aan de `backend`-matrix (vóór `all`) en
  je integratietestfunctie aan de `test`-matrix
- **`typescript-ci.yml`**: voeg je package toe aan de unit- en integratietestmatrices
  en voeg omgevingsvariabelen toe aan de integratieteststap
- **`typescript-publish.yml`**: voeg je package toe aan `PUBLISH_PACKAGES`, de
  `packages`-array van de GitHub Release en de overzichtstabel
- **`python-ci.yml`**: voeg de backend toe aan de `CI_SIGNER_*`-gating in
  `resolve-signers` en aan de integratiematrix
- **`go-ci.yml`**: voeg de backend toe aan de `CI_SIGNER_*`-gating en aan
  `moduleBySigner`

## TypeScript Signer

Als je ook een TypeScript signer-package toevoegt, maak deze dan aan op
`typescript/packages/your-signer/`. Belangrijkste patronen:

- De factory-functie `createYourSigner()` geeft
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>` terug; houd de
  signer-klasse intern en exporteer alleen de factory en het bijbehorende configuratietype
- Exporteer config-interface (`YourSignerConfig`)
- Als je backend geen berichten kan ondertekenen, laat dan `SolanaMessageSigner` weg en stel helemaal geen
  `signMessages`-methode beschikbaar: Kit classificeert signers op basis van de aanwezigheid van methoden, dus een
  stub die een fout gooit zou de signer verkeerd classificeren
- Dwing HTTPS af op `apiBaseUrl`-configuratievelden met `assertHttpsUrl()` uit
  `@solana/keychain-core`
- Doe externe aanroepen via `fetchSignerJson()` uit `@solana/keychain-core`,
  dat de foutafhandeling, responssanering, het weigeren van redirects en de
  standaardtimeout beheert
- Saneer alle andere foutteksten van externe API's met `sanitizeRemoteErrorResponse()`
  uit `@solana/keychain-core`
- Gebruik `throwSignerError(SignerErrorCode.*, { cause, message })` van
  `@solana/keychain-core`
- Respecteer `config?.abortSignal` in elke signing-methode en geef het door aan
  `fetchSignerJson()` en `signBatchStaggered()`
- Valideer `requestDelayMs` met `validateRequestDelayMs()` en verwerk batches met
  `signBatchStaggered()`
- Voeg `@throws` JSDoc toe aan factory-functies met een lijst van foutcodes
- Declareer `@solana/*`-packages als peer dependencies op `>=8.1.0`
- Unittests met vitest en gemockte `fetch`; integratietests met
  `runSignerIntegrationTest` uit `@solana/keychain-test-utils`

### Sending signers

Als je provider de transactie herschrijft of aan de serverzijde verstuurt, kan de
handtekening ervan niet op de transactie van de aanroeper worden toegepast, dus moet het een
`SolanaSendingSigner` zijn in plaats van een `SolanaTransactionSigner`:

- Implementeer `signAndSendTransactions()` en stel **geen** `signTransactions`
  beschikbaar (en ook geen `signMessages`, tenzij de backend echt berichten ondertekent)
- Respecteer `config?.abortSignal`. Zodra de provider de create heeft geaccepteerd, meld je
  elke fout (inclusief een abort) als `BROADCAST_UNCONFIRMED` met de
  transactie-id van de provider, waarbij de abort-reden als `cause` behouden blijft
- Voeg een getypeerde `createKeychainSigner`-overload toe die het type van je sending signer teruggeeft
- Sluit je backend uit van `KeychainKitPluginConfig` in
  `typescript/packages/kit-plugin/src/keychain-plugin.ts`, aangezien een sending
  signer niet kan dienen als `payer` of `identity` van een Kit-client
- Controleer in unittests dat `isTransactionPartialSigner()` false en
  `isTransactionSendingSigner()` true is voor je instanties

### Update Overkoepelend Pakket

Werk `typescript/packages/keychain/` bij (7 te wijzigen bestanden):

1. `src/types.ts`: voeg `YourSignerConfig` toe aan de gediscrimineerde union
   `KeychainSignerConfig`
2. `src/create-keychain-signer.ts`: voeg de switch case toe (elk backend-package wordt
   geladen met een dynamische `import()`)
3. `src/resolve-address.ts`: voeg toe aan de switch case voor het fast-path of fetch-path
4. `src/index.ts`: voeg de exports van het configuratietype, de namespace en de factory-functie toe
5. `package.json`: voeg de dependency `@solana/keychain-your-signer: "workspace:*"` toe
6. `tsconfig.json`: voeg de verwijzing `{ "path": "../your-signer" }` toe
7. `typescript/scripts/test-treeshake-umbrella.mjs`: voeg je package toe aan
   `SIGNER_MARKERS` en je factory aan `FACTORIES`

De switch-statements hebben uitputtende `never`-controles, dus TypeScript geeft een foutmelding
als je iets aan de union toevoegt maar een case mist. Voer daarna `just ts-treeshake` uit:
elk package en de umbrella moeten tree-shakable blijven.

## Python-signer

Maak de module aan op `python/src/solana_keychain/your_signer/` (`__init__.py`
plus `signer.py`). Belangrijkste patronen:

- Maak een subklasse van `SolanaSigner` uit `solana_keychain.core` (`pubkey`-property,
  `async sign_message()`, `async is_available()`) plus precies één capability-
  klasse: `TransactionSigner` (`async sign_transaction()`), `ModifyingSigner`
  (`async modify_and_sign_transaction()`) of `SendingSigner`
  (`async sign_and_send_transaction()`)
- Exporteer een `async create_your_signer()`-factory die `init()` afwacht wanneer de
  backend zijn adres remote oplost; vóór init geeft ondertekening de fout
  `SignerErrorCode.NOT_INITIALIZED`
- Exporteer een config-dataclass (`YourSignerConfig`) waarbij geheimen zijn gemarkeerd met
  `field(repr=False)`
- Dwing HTTPS af op base-URL-velden met `assert_https_url()` en laat elk
  verzoek via `fetch_signer_json()` lopen
- Controleer de handtekening van de provider voordat je die teruggeeft; gebruik
  `signed_message_bytes()` voor de bytes die een handtekening dekt, nooit een zelfgemaakt
  versieprefix
- Registreer de backend in `_BACKENDS` in
  `python/src/solana_keychain/keychain.py`
- Als de backend een provider-SDK nodig heeft, bescherm dan de import, geef een `ImportError`
  met `pip install 'solana-keychain[your-signer]'`, declareer de extra in
  `python/pyproject.toml` en importeer de backend nooit direct (eager) vanuit de root van het pakket
- Unittests met pytest: `respx` voor HTTP-backends, stub-clients voor SDK-backends en een controle dat er geen geheim voorkomt in `str()` of `repr()` van gegenereerde
  fouten
- Voeg een `make_your_signer()`-factory toe aan
  `python/tests/integration/test_live_signers.py` en registreer deze in
  `_MESSAGE_CAPABLE` (of `_TRANSACTION_ONLY` voor backends zonder
  `sign_message`)

## Go-signer

Elke Go-backend is een eigen module, in `go/signers/yoursigner/` met modulepad
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`. Zie
`go/signers/para/` voor een referentie. Belangrijkste patronen:

- Implementeer `core.SolanaSigner` (`Pubkey()`, `SignMessage(ctx, message)`,
  `IsAvailable(ctx)`) plus precies één capability-interface:
  `core.TransactionSigner`, `core.ModifyingSigner` of `core.SendingSigner`.
  De capability wordt gedetecteerd via type assertion, dus een backend die geen
  transactie kan ondertekenen mag helemaal geen `SignTransaction`-methode hebben
- Exporteer een `Config`-struct en een `New`-constructor (`New(ctx, cfg)` wanneer de
  backend zijn adres op afstand opvraagt; geef daarvoor
  `core.NewNotInitializedError` terug)
- Bouw HTTP-clients met `core.NewHTTPClient` of `core.ResolveHTTPClient` en
  valideer basis-URL's met `core.NormalizeHTTPSBaseURL`
- Onderteken transacties met `core.SignTransactionWith`, dat de bytes van het bericht ondertekent en de handtekening toevoegt; verifieer handtekeningen van de provider met
  `core.VerifySignature`
- Geef fouten terug met `core.NewSignerError` / `core.WrapSignerError` en stabiele
  codes zoals `core.CodeSigningFailed`
- Unittests met `httptest`; integratietests in `integration_test.go` achter
  de tag `//go:build integration`

## Implementatietips

### Foutafhandeling

Gebruik altijd de bestaande `SignerError`-varianten. Zowel `Display` als `Debug` op
`SignerError` zijn geredigeerd, dus houd berichten algemeen en neem nooit ruwe API-responsedata op. Gebruik nooit `.expect()` of `.unwrap()` op onbetrouwbare API-responses:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### Beveiligingsvereisten

Dit zijn geen suggesties: consumenten kiezen een backend op basis hiervan. Als
je provider er een onmogelijk maakt, vermeld dat dan in de PR en in
`docs/SECURITY_MODEL.md` van de repository.

- **Verifieer wat de provider heeft ondertekend.** Bereken de berichtbytes lokaal en
  verifieer de geretourneerde handtekening daartegen op de positie die jouw signer vereist,
  voordat je de handtekening toevoegt. Een handtekening die niet geverifieerd kan worden, moet mislukken en mag nooit
  worden toegevoegd.
- **Geef aan of de provider uitzendt (broadcast).** Als de provider aan de serverkant uitvoert,
  implementeer dan de sending-variant en geef de handtekening terug die de
  verwerkte transactie identificeert. Als de provider geen endpoint heeft om alleen te ondertekenen, maak de
  backend dan sending-only in plaats van achter de rug van de aanroeper om in te dienen.
- **Laat de aanroeper nooit achter met een transactie die de handtekening niet dekt.**
  Een provider die de transactie herschrijft, ondertekent zijn eigen bytes: laat ofwel de
  transactie van de aanroeper ongemoeid (het broadcast-beheerde geval), ofwel kies de
  modifying-variant en vervang de transactie volledig door de bytes van de provider.
- **Meld onzekerheid over de broadcast als zodanig.** Een fout na indiening kan alsnog
  zijn verwerkt. Geef `BROADCAST_UNCONFIRMED` terug in plaats van een algemene fout,
  neem de transactie-ID van de provider mee zodra je die hebt, en stuur bij elke create een
  van het bericht afgeleide idempotency-sleutel mee, zodat een byte-identieke herhaling
  veilig is.
- **Onderteken nooit vóór init.** Gebruik `Option<Pubkey>` (niet `Pubkey::default()`) voor
  de publieke sleutel vóór `init()`, en faal met een configuratiefout als er eerst
  wordt geprobeerd te ondertekenen.
- Log nooit gevoelige data (privésleutels, API-geheimen, ruwe API-responses) en
  gebruik een `Debug`-implementatie die gevoelige velden verbergt
- Dwing HTTPS af (`https_only(true)`, afgeschermd met `#[cfg(not(test))]` voor
  wiremock) en configureer request- en verbindingstimeouts via `HttpClientConfig`
  (standaard: 30s/5s)
- Zeroize tussenliggend sleutelmateriaal met `zeroize::Zeroizing<Vec<u8>>`

### Testen met Mocks

Gebruik `wiremock` voor het mocken van HTTP-API's. Assert alleen op het
fouttype, niet op de fouttekst:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
