## RPC-infrastructuur

[Publieke endpoints](https://solana.com/docs/references/clusters#solana-public-rpc-endpoints)
(`api.mainnet.solana.com`) hebben rate limits en geen SLA. Ze zijn prima voor
ontwikkeling, maar laten betalingsstromen in productie falen—alsof je een
betalingsverwerker laat draaien via een gedeelde API zonder uptimegarantie.

<Callout type="caution" title="Gebruik nooit publieke RPC voor productie">
  Gebruik een [private RPC-provider](https://solana.com/rpc) voor betrouwbare toegang
  met lage latency.
</Callout>

Let bij het kiezen van een RPC-provider op:

- **Betrouwbaarheid**: SLA's met uptimegaranties (99,9%+)
- **Latency**: Geografische nabijheid tot je gebruikers
- **Functies**: Functies voor transaction landing, indexering, priority fee-API's

Voor een volledige lijst van RPC-providers, zie de gids
[RPC Infrastructure Providers](https://solana.com/rpc).

### Redundante RPC-configuratie

Net als elke andere netwerkserviceprovider kunnen RPC-providers downtime of
periodes met verminderde prestaties hebben. Om ervoor te zorgen dat je applicatie
weerbaar is, moet je je applicatie configureren om meerdere RPC-providers te
gebruiken.

[Solana Kit](https://github.com/anza-xyz/kit/tree/main/packages/rpc-transport-http)
biedt een bibliotheek voor het aanpassen van RPC-transports, waarmee je je
eigen redundante RPC-client kunt bouwen. Hier is een voorbeeld van hoe je dit
kunt gebruiken om een redundante RPC-client te bouwen:

```ts
import { RpcTransport } from "@solana/rpc-spec";
import { RpcResponse } from "@solana/rpc-spec-types";
import { createHttpTransport } from "@solana/rpc-transport-http";

// Create a transport for each RPC server
const transports = [
  createHttpTransport({ url: "https://mainnet-beta.my-server-1.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-2.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-3.com" })
];

// Create a wrapper transport that distributes requests to them
let nextTransport = 0;
async function roundRobinTransport<TResponse>(
  ...args: Parameters<RpcTransport>
): Promise<RpcResponse<TResponse>> {
  const transport = transports[nextTransport];
  nextTransport = (nextTransport + 1) % transports.length;
  return await transport(...args);
}
```

Als je liever geen eigen routeringstools bouwt, kun je een externe dienst zoals
[Iron Forge](https://www.ironforge.sanctum.so/) gebruiken om de routering voor je af te handelen.

## Transaction Landing

Op Devnet landen transacties vrij gemakkelijk. Op Mainnet strijd je om
blokruimte. Om de kans te vergroten dat je transactie in een blok wordt
opgenomen, moet je ervoor zorgen dat je transactie correct is samengesteld.
Dat betekent:

- een verse blockhash opnemen voordat je de transactie verzendt
- een priority fee-instructie met een concurrerende priority fee opnemen in de
  transactie
- een instructie voor de compute unit-limiet opnemen in de transactie, met een
  compute unit-limiet gebaseerd op het geschatte aantal compute units dat de
  transactie nodig heeft

Daarnaast kun je andere tools overwegen, zoals Jito Bundles, om de kans te
vergroten dat je transactie in een blok wordt opgenomen. Laten we deze tools
nader bekijken.

### Configuratie voor het verzenden van transacties

Configureer bij het verzenden van transacties op Mainnet deze parameters voor
optimale landingspercentages:

**Blockhash-beheer:**

- Haal op met `confirmed` commitment
- Sla de `lastValidBlockHeight` op die `getLatestBlockhash` retourneert—hiermee
  weet je wanneer je transactie verloopt
- Blockhashes verlopen na een door het protocol bepaalde tijd, afhankelijk van
  de lengte van de slot.

**Verzendopties:**

- `maxRetries: 0` — Schakel automatische RPC-retries uit. Handel retries zelf af
  zodat je de blockhash kunt vernieuwen wanneer nodig.
- `skipPreflight: true` — Sla de simulatie over vóór het verzenden. Gebruik dit
  wanneer je de transactie al hebt gevalideerd en de laagste latency wilt. Houd
  het tijdens de ontwikkeling op `false` om fouten vroeg te ontdekken.

```typescript
import { createSolanaRpc } from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);

// 1. Get blockhash with confirmed commitment
const { value: latestBlockhash } = await rpc
  .getLatestBlockhash({ commitment: "confirmed" })
  .send();

// 2. Build and sign your transaction with the blockhash
// ... (transaction building code)

// 3. Send with production settings
const signature = await rpc
  .sendTransaction(encodedTransaction, {
    encoding: "base64",
    maxRetries: 0n, // Handle retries yourself
    skipPreflight: true, // Skip simulation for speed (use false during dev)
    preflightCommitment: "confirmed"
  })
  .send();

// 4. Track expiration using lastValidBlockHeight
const { lastValidBlockHeight } = latestBlockhash;
// Stop retrying when current block height exceeds lastValidBlockHeight
```

### Gebruik priority fees

Elke Solana-transactie vereist een transactiekost, betaald in SOL.
Transactiekosten bestaan uit twee delen: de basisfee en de priority fee. De
basisfee vergoedt validators voor het verwerken van de transactie. De priority
fee is een optionele fee om de kans te vergroten dat de huidige leader je
transactie verwerkt. Zie het als expresverzending: je betaalt meer voor een
snellere, betrouwbaardere levering.

**Hoe fees werken:**

```
Total fee = Base fee (5,000 lamports per signature) + Priority fee
Priority fee (legacy/v0) = ceil(compute_unit_price * compute_unit_limit / 1,000,000) lamports
Priority fee (v1 only) = Absolute total in lamports set in the message config
```

**Kosten in de praktijk:**

- Eenvoudige USDC-overdracht: ~$0,001-0,005 onder normale omstandigheden
- Tijdens congestie: ~$0,01-0,05
- Piekcongestie: kan nog hoger oplopen

**Voorbeeldimplementatie:**

Het pakket
[`@solana-program/compute-budget`](https://github.com/solana-program/compute-budget)
biedt een hulpfunctie om eenvoudig de instructie voor de compute unit-prijs (in
micro-lamports) bij te werken of toe te voegen aan een transactie.

```typescript
import { updateOrAppendSetComputeUnitPriceInstruction } from "@solana-program/compute-budget";

const tx = pipe(
  createTransactionMessage({ version: 0 }),
  (m) => setTransactionMessageFeePayerSigner(payer, m),
  (m) => setTransactionMessageLifetimeUsingBlockhash(latestBlockhash, m),
  (m) => appendTransactionMessageInstructions([myInstructions], m),
  (m) => updateOrAppendSetComputeUnitPriceInstruction(1000n as MicroLamports, m)
);
```

**Fee-schattingen ophalen:** De meeste RPC-providers bieden priority fee-API's:

- [Helius Priority Fee API](https://docs.helius.dev/solana-apis/priority-fee-api)
- [QuickNode Priority Fee Add-on](https://marketplace.quicknode.com/add-on/solana-priority-fee)
- [Triton Priority Fees API](https://docs.triton.one/chains/solana/improved-priority-fees-api)

Voor de volledige werking van fees, zie [Transaction Fees](/docs/core/fees) en onze
gids:
[How to Add Priority Fees to a Transaction](https://solana.com/developers/cookbook/transactions/add-priority-fees).

### Optimaliseer compute units

Compute op Solana wordt gemeten in compute units (CU's), een grove schatting
van de hoeveelheid werk die het programma verricht. De huidige computelimieten
zijn 50 miljoen CU's per blok en 1,4 miljoen CU's per transactie. Wanneer je een
transactie indient, moet je inschatten hoeveel compute er gebruikt zal worden en
de compute unit-limiet dienovereenkomstig instellen—dit is in feite een verzoek
om een bepaald deel van de totale capaciteit voor je transactie te reserveren.
In de praktijk betekent dit dat een juiste schatting van de benodigde compute
units voor je transactie cruciaal is om je transactie in een blok te laten
opnemen (en belangrijk voor het beheer van je priority fees). De compute-limiet
van transacties en blokken wordt door het protocol bepaald.

De Solana JSON RPC API heeft een
[`simulatetransaction`](/docs/rpc/http/simulatetransaction)-methode die kan
worden gebruikt om de benodigde compute units voor een transactie in te
schatten, inclusief een schatting van de compute units die zullen worden
gebruikt. [`@solana/kit`](https://github.com/anza-xyz/kit) biedt hulpfuncties die de resourcelimieten van
een transactie schatten en deze in één stap op het bericht instellen (met onder
de motorkap de `simulatetransaction`-methode). Voor transacties van versie 1
schatten deze hulpfuncties ook de limiet voor de grootte van de geladen
accountdata.

```ts
import {
  estimateResourceLimitsFactory,
  estimateAndSetResourceLimitsFactory
} from "@solana/kit";

const estimateResourceLimits = estimateResourceLimitsFactory({ rpc });
const estimateAndSetResourceLimits = estimateAndSetResourceLimitsFactory(
  estimateResourceLimits
);
const txWithResourceLimits = await estimateAndSetResourceLimits(tx);
```

<Callout type="info">
  Als je transacties bouwt en verzendt met een kit plugin-client, heb je deze
  stap meestal niet nodig — de client voegt compute budget-instructies voor je
  toe wanneer hij verzendt (`.sendTransaction()`). De handmatige flow hierboven
  is voor wanneer je transacties rechtstreeks met `@solana/kit` samenstelt.
</Callout>

Als je in productie hetzelfde type transactie meerdere keren herhaalt, overweeg
dan om de compute-schatting voor dat transactietype te cachen, zodat je niet
elke keer de overhead hebt van het schatten van de compute units.

### Jito Bundles

Jito bundles zijn een tool voor het beheren van de atomaire uitvoering van
meerdere transacties. Dit wordt bereikt door meerdere transacties met een tip
naar het Jito-netwerk te sturen. Tips kunnen worden gebruikt om het Jito-netwerk
te stimuleren je transacties in een blok op te nemen.

### Retry-strategieën

Transacties kunnen om vele redenen mislukken. In tegenstelling tot traditionele
betaal-API's die direct succes of falen retourneren, vereisen
blockchaintransacties het bijhouden van bevestigingen.

**Kernconcepten:**

- **Verlopen van blockhash**: Verlopen van blockhash: Blockhashes van transacties
  blijven 150 slots geldig (ongeveer 30 seconden bij slots van 200 ms). De
  werkelijke verlooptijd kan variëren afhankelijk van de snelheid van
  blockproductie. Gebruik lastValidBlockHeight om te bepalen wanneer een
  blockhash is verlopen.
- **Idempotentie**: Dezelfde ondertekende transactie levert altijd dezelfde
  handtekening op—opnieuw indienen is veilig
- **Exponentiële backoff**: Voorkom dat je het netwerk overbelast met snelle
  retries

```typescript
import {
  createSolanaRpc,
  createSolanaRpcSubscriptions,
  sendAndConfirmTransactionFactory,
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED
} from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);
const rpcSubscriptions = createSolanaRpcSubscriptions(process.env.RPC_WSS_URL!);

const sendAndConfirmTransaction = sendAndConfirmTransactionFactory({
  rpc,
  rpcSubscriptions
});

// Send with automatic confirmation tracking and block height monitoring
try {
  await sendAndConfirmTransaction(signedTransaction, {
    commitment: "confirmed",
    // Optional: abort after 75 seconds
    abortSignal: AbortSignal.timeout(75_000)
  });
} catch (e) {
  if (isSolanaError(e, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED)) {
    // Blockhash expired—rebuild transaction with fresh blockhash and retry
    rebuildAndRetryTransaction(); // implement your own logic for rebuilding and retrying the transaction
  }
  throw e;
}
```

De `sendAndConfirmTransactionFactory` uit `@solana/kit` handelt het pollen van
bevestigingen en het bijhouden van de blokhoogte automatisch af. Hij gooit
`SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED` wanneer de blockhash van de transactie
verloopt, als signaal dat je de transactie opnieuw moet opbouwen met een verse
blockhash.

## Foutafhandeling

Solana Kit biedt getypeerde fouten via `isSolanaError()`. Gebruik specifieke
foutcodes in plaats van string matching:

```typescript
import {
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED,
  SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE,
  SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND,
  SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS
} from "@solana/kit";

function handlePaymentError(error: unknown): {
  message: string;
  retryable: boolean;
} {
  // Blockhash expired—rebuild and retry
  if (
    isSolanaError(error, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED) ||
    isSolanaError(error, SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND)
  ) {
    return { message: "Transaction expired—rebuilding", retryable: true };
  }

  // Insufficient SOL for fees
  if (
    isSolanaError(
      error,
      SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE
    )
  ) {
    return { message: "Not enough SOL for fees", retryable: false };
  }

  // Insufficient token balance
  if (
    isSolanaError(error, SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS)
  ) {
    return { message: "Insufficient balance", retryable: false };
  }

  // Unknown error
  console.error("Payment error:", error);
  return { message: "Payment failed—please retry", retryable: true };
}
```

**Veelvoorkomende foutcodes:**

| Foutcode                   | Oorzaak                 | Herstel                                                                                                 |
| ---------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------- |
| `BLOCK_HEIGHT_EXCEEDED`      | Blockhash verlopen     | Opnieuw opbouwen met verse blockhash                                                                             |
| `BLOCKHASH_NOT_FOUND`        | Blockhash niet gevonden   | Opnieuw opbouwen met verse blockhash                                                                             |
| `INSUFFICIENT_FUNDS_FOR_FEE` | Onvoldoende SOL        | Stort saldo op de fee payer of gebruik [fee abstraction](/docs/payments/send-payments/payment-processing/fee-abstraction) |
| `INSUFFICIENT_FUNDS`         | Onvoldoende tokens     | Gebruiker heeft meer saldo nodig                                                                                  |
| `ACCOUNT_NOT_FOUND`          | token account ontbreekt | Maak ATA aan in de transactie                                                                                |

## Gasloze transacties

Gebruikers verwachten te betalen in stablecoins en niet eerst SOL te hoeven
verwerven voor netwerkkosten. Gasloze transacties lossen dit op—vergelijkbaar
met hoe Venmo-gebruikers niet nadenken over ACH-kosten. Zie
[Fee Abstraction](/docs/payments/send-payments/payment-processing/fee-abstraction)
voor de volledige implementatie.
