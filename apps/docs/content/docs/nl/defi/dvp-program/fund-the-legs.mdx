Funden is een gewone `TransferChecked` naar de escrow van de leg, dus elke wallet of custody-oplossing die een tokenoverdracht kan versturen, kan een leg funden. Alleen het uitlezen van het trade-record vóór het funden vereist de DvP-client. Het programma controleert de escrow-saldi uitsluitend bij de afwikkeling; niets controleert de overdracht op het moment dat deze aankomt, dus elke partij leest het trade-record uit voordat ze overmaakt.

Deze pagina is een vervolg op
[een trade aanmaken](/docs/defi/dvp-program/create-a-trade); de client en de ondertekenaars
blijven hetzelfde.

## De voorwaarden controleren

Het aanmaken van een record is permissionless, en de escrow-adressen worden uitsluitend afgeleid van het record en de mint, nooit van de voorwaarden. Een overdracht naar een escrow kan dus aankomen bij voorwaarden waarmee je nooit akkoord bent gegaan, waaronder afwikkelingsbestemmingen die de opbrengst van je tegenpartij omleiden naar een derde adres. Lees vóór het funden het `SwapDvp`-account uit en controleer het aan de hand van de overeengekomen trade.

`verifySwapDvp` in TypeScript en `verify::decode_swap_dvp_account` in Rust bevestigen dat het account eigendom is van het DvP-programma, precies 458 bytes groot is en zich bevindt op het adres dat uit de eigen velden wordt afgeleid (`fetchSwapDvpChecked` voert alleen de eerste twee controles uit). De gewone readers `fetchSwapDvp` en `decodeSwapDvp` voeren geen van deze controles uit. De controles op partijen, bedragen, tijden en bestemmingen voert de aanroeper zelf uit aan de hand van de overeengekomen trade.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { unwrapOption } from "@solana/kit";
    import { verifySwapDvp } from "./dvp";

    const trade = await verifySwapDvp(client.rpc, swapDvp);
    const t = trade.data;

    const expectedAmountA = 1_000_000_000n;
    const expectedAmountB = 998_500_000n;
    const expectedEarliestSettlement: bigint | null = null; // as agreed
    const expectedExpiry = 1_798_761_600n; // as agreed, unix seconds

    if (
      t.userA !== userA ||
      t.userB !== userB ||
      t.mintA !== mintA ||
      t.mintB !== mintB ||
      t.settlementAuthority !== settlementAuthority ||
      t.tokenProgramA !== tokenProgramA ||
      t.tokenProgramB !== tokenProgramB ||
      t.amountA !== expectedAmountA ||
      t.amountB !== expectedAmountB ||
      unwrapOption(t.earliestSettlementTimestamp) !== expectedEarliestSettlement ||
      t.expiryTimestamp !== expectedExpiry ||
      t.userASettlementDestination !== userA ||
      t.userBSettlementDestination !== userB
    ) {
      throw new Error("Stored terms do not match the agreed trade; do not fund");
    }

    if (t.expiryTimestamp <= BigInt(Math.floor(Date.now() / 1000)) + 60n) {
      throw new Error("Trade expires too soon to fund safely");
    }
    ```

  </Tab>

    use solana_client::rpc_client::RpcClient;
    use solana_commitment_config::CommitmentConfig;

    // Read at confirmed: a record created moments ago is not visible at finalized yet.
    let rpc = RpcClient::new_with_commitment(

        CommitmentConfig::confirmed(),
    );

    let expected_amount_a: u64 = 1_000_000_000;
    let expected_amount_b: u64 = 998_500_000;
    let expected_earliest_settlement: Option<i64> = None; // as agreed
    let expected_expiry: i64 = 1_798_761_600; // as agreed, unix seconds

    if trade.user_a != user_a
        || trade.user_b != user_b
        || trade.mint_a != mint_a
        || trade.mint_b != mint_b
        || trade.settlement_authority != settlement_authority
        || trade.token_program_a != token_program_a
        || trade.token_program_b != token_program_b
        || trade.amount_a != expected_amount_a
        || trade.amount_b != expected_amount_b
        || trade.earliest_settlement_timestamp != expected_earliest_settlement
        || trade.expiry_timestamp != expected_expiry
        || trade.user_a_settlement_destination != user_a
        || trade.user_b_settlement_destination != user_b
    {
        return Err("stored terms do not match the agreed trade; do not fund".into());

    let now_seconds: i64 = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)?
        .as_secs() as i64;
    if trade.expiry_timestamp <= now_seconds + 60 {
        return Err("trade expires too soon to fund safely".into());
    }

Als het record is aangemaakt door je tegenpartij of door de afwikkelautoriteit, vergelijk dan elk veld met de voorwaarden die je buiten de ledger hebt afgesproken. Heb je het zelf aangemaakt, dan bevestigt deze uitlezing dat het is aangekomen zoals verzonden.

## Overmaken naar de escrow

Fund de leg met exact het overeengekomen bedrag. Het programma beperkt de afwikkeling tot `amount_x` en stort een eventueel overschot terug aan de partij van de leg, dus een overschot gaat niet verloren, maar het zorgt voor een tweede overdracht bij de afwikkeling en kan mislukken bij sommige transfer hooks (zie de opmerkingen hieronder).

Gebruik `TransferChecked`, niet een ongecontroleerde `Transfer`. Token-2022-mints met extensies die afhankelijk zijn van het mint account, zoals Pausable, weigeren een overdracht waarbij dit niet wordt meegegeven. Een mint met een transfer hook vereist bovendien dat de accounts van de hook worden opgelost en op dezelfde manier worden toegevoegd als bij elke andere overdracht van dat token.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">

    ```ts
    import {
      findAssociatedTokenPda,
      getTransferCheckedInstruction,

    const [userAAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: userA,

    });
    const [userBAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: userB,
      tokenProgram: tokenProgramB,
    });

    const fundAssetLeg = getTransferCheckedInstruction({
      source: userAAtaA,
      mint: mintA,
      destination: escrowA,
      authority: userASigner,
      amount: t.amountA,
      decimals: 6,
    }, { programAddress: tokenProgramA });

    await client.sendTransaction([fundAssetLeg]);
    ```

    De partij van de cashleg doet hetzelfde voor escrow B met `userBAtaB`, `mintB`,
    `userBSigner`, `t.amountB` en `{ programAddress: tokenProgramB }`.

Een funding-overdracht die op [`confirmed`](/docs/rpc#configuring-state-commitment) wordt gezien, kan nog steeds worden vervangen. Het programma leest het escrow-saldo onchain uit bij de afwikkeling, dus een Settle die wordt verstuurd terwijl de funding-overdracht niet is aangekomen, mislukt met `LegNotFunded` en er wordt niets verplaatst; de kosten zijn een mislukte Settle en een nieuwe poging. Beschouw een leg pas als gefund wanneer de overdracht `finalized` is.

## Opmerkingen

- **Wrapped SOL-legs.** Het programma leest het saldo van een native escrow uit nadat het is gesynchroniseerd, dus lamports die via een systeemoverdracht naar een wrapped-SOL-escrow zijn gestuurd, worden meegeteld. Stuur nooit SOL naar een escrow voor een andere mint: het programma kan het niet terugsturen en het gaat naar degene die het account sluit.
- **Gated mints.** Bij een mint met Default Account State op frozen wordt de escrow bevroren aangemaakt en mislukt de overdracht totdat de uitgever deze ontdooit of toelaat. Het [overzicht](/docs/defi/dvp-program#mint-configuration-constraints) beschrijft de interactie met Token ACL.
- **Transfer hooks.** Fund escrows met een hook met exact het overeengekomen bedrag. Als een overschot bij de afwikkeling een terugbetaling afdwingt, hergebruikt die terugbetaling de hook-accounts van de leg met een andere bestemming en een ander bedrag, wat sommige hooks weigeren. Het herstel is Reclaim, opnieuw funden met het exacte bedrag en opnieuw afwikkelen.
- **Funden na de vervaldatum.** Niets voorkomt een overdracht na `expiry_timestamp`. Deze komt aan, afwikkeling is niet meer mogelijk, en de partij van de leg haalt het bedrag terug met Reclaim zolang de trade open is, of met Recover nadat deze is gesloten. Zie [een trade ongedaan maken](/docs/defi/dvp-program/unwind-a-trade).
- **Wie fund eerst.** Het programma bepaalt niet de volgorde van de twee legs. De volgorde is een zaak van de partijen; elke partij kan haar eigen leg op elk moment vóór de afwikkeling terugvorderen, tenzij een mint authority (freeze, pause of transfer hook) de escrow blokkeert.
