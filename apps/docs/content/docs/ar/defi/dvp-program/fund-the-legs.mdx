التمويل عبارة عن `TransferChecked` عادي إلى حساب الضمان الخاص بالشق، لذا يمكن لأي محفظة أو
نظام حفظ قادر على إرسال تحويل رموز أن يموّل أحد الشقّين. وحدها قراءة
سجل الصفقة قبل التمويل تتطلب عميل DvP. لا يتحقق البرنامج من
أرصدة حسابات الضمان إلا عند التسوية؛ ولا شيء يتحقق من التحويل عند وصوله،
لذا يقرأ كل طرف سجل الصفقة قبل إجراء التحويل.

تتابع هذه الصفحة ما بدأناه في
[إنشاء صفقة](/docs/defi/dvp-program/create-a-trade)؛ إذ يستمر استخدام العميل
والموقّعين أنفسهم.

## التحقق من الشروط

إنشاء السجل لا يتطلب أي إذن، وتُشتق عناوين حسابات الضمان من السجل ومن
mint فقط، وليس من الشروط إطلاقًا. لذلك قد يصل تحويل إلى حساب ضمان مرتبط
بشروط لم توافق عليها قط، بما في ذلك وجهات تسوية تعيد توجيه عائدات الطرف
المقابل إلى عنوان ثالث. قبل التمويل، اقرأ حساب `SwapDvp` وقارنه بالصفقة المتفق عليها.

تتحقق `verifySwapDvp` في TypeScript و`verify::decode_swap_dvp_account` في Rust
من أن الحساب مملوك لبرنامج DvP، وأن حجمه 458 بايت بالضبط، وأنه
يقع على العنوان الذي تشتقه حقوله نفسها (أما `fetchSwapDvpChecked` فتجري
الفحصين الأولين فقط). أما قارئا `fetchSwapDvp` و`decodeSwapDvp` العاديان
فلا يجريان أيًّا من هذه الفحوص. ويتولى المستدعي إجراء الفحوص المتعلقة بالأطراف
والمبالغ والأوقات والوجهات مقارنةً بالصفقة المتفق عليها.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { unwrapOption } from "@solana/kit";
    import { verifySwapDvp } from "./dvp";

    const trade = await verifySwapDvp(client.rpc, swapDvp);
    const t = trade.data;

    const expectedAmountA = 1_000_000_000n;
    const expectedAmountB = 998_500_000n;
    const expectedEarliestSettlement: bigint | null = null; // as agreed
    const expectedExpiry = 1_798_761_600n; // as agreed, unix seconds

    if (
      t.userA !== userA ||
      t.userB !== userB ||
      t.mintA !== mintA ||
      t.mintB !== mintB ||
      t.settlementAuthority !== settlementAuthority ||
      t.tokenProgramA !== tokenProgramA ||
      t.tokenProgramB !== tokenProgramB ||
      t.amountA !== expectedAmountA ||
      t.amountB !== expectedAmountB ||
      unwrapOption(t.earliestSettlementTimestamp) !== expectedEarliestSettlement ||
      t.expiryTimestamp !== expectedExpiry ||
      t.userASettlementDestination !== userA ||
      t.userBSettlementDestination !== userB
    ) {
      throw new Error("Stored terms do not match the agreed trade; do not fund");
    }

    if (t.expiryTimestamp <= BigInt(Math.floor(Date.now() / 1000)) + 60n) {
      throw new Error("Trade expires too soon to fund safely");
    }
    ```

  </Tab>

    ```rust
    use solana_client::rpc_client::RpcClient;

    // Read at confirmed: a record created moments ago is not visible at finalized yet.

    let expected_amount_a: u64 = 1_000_000_000;
    let expected_amount_b: u64 = 998_500_000;
    let expected_earliest_settlement: Option<i64> = None; // as agreed
    let expected_expiry: i64 = 1_798_761_600; // as agreed, unix seconds

    if trade.user_a != user_a
        || trade.user_b != user_b
        || trade.mint_a != mint_a
        || trade.mint_b != mint_b
        || trade.settlement_authority != settlement_authority
        || trade.token_program_a != token_program_a
        || trade.token_program_b != token_program_b
        || trade.amount_a != expected_amount_a
        || trade.amount_b != expected_amount_b
        || trade.earliest_settlement_timestamp != expected_earliest_settlement
        || trade.expiry_timestamp != expected_expiry
        || trade.user_a_settlement_destination != user_a
        || trade.user_b_settlement_destination != user_b
    {
        return Err("stored terms do not match the agreed trade; do not fund".into());
    }

    let now_seconds: i64 = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)?
        .as_secs() as i64;
    if trade.expiry_timestamp <= now_seconds + 60 {
        return Err("trade expires too soon to fund safely".into());
    }
    ```

إذا أنشأ الطرف المقابل أو جهة التسوية السجل،
فقارن كل حقل بالشروط التي اتفقتم عليها خارج السجل. وإذا أنشأته
بنفسك، فإن هذه القراءة تؤكد أنه وصل كما أُرسل.

## التحويل إلى حساب الضمان

موّل الشق بالمبلغ المتفق عليه بالضبط. يحدّ البرنامج التسوية بقيمة
`amount_x` ويعيد أي فائض إلى طرف الشق، لذا فالفائض لا يضيع،
لكنه يضيف تحويلًا ثانيًا عند التسوية وقد يفشل مع بعض
خطافات التحويل (انظر الملاحظات أدناه).

استخدم `TransferChecked` وليس `Transfer` غير المُتحقَّق منه. فعملات Token-2022 ذات
الإضافات التي تعتمد على mint account، مثل Pausable، ترفض أي تحويل
لا يوفّره، وعملة mint ذات خطاف تحويل تحتاج إلى حلّ حسابات الخطاف
وإلحاقها بالطريقة نفسها المتّبعة في أي تحويل آخر لذلك
الرمز.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    يموّل طرف شق الأصل، بالتوقيع بصفته `userASigner`، حساب الضمان A:

    ```ts
    import {
      findAssociatedTokenPda,
      getTransferCheckedInstruction,
    } from "@solana-program/token-2022";

    const [userAAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: userA,
      tokenProgram: tokenProgramA,
    });
    const [userBAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: userB,
      tokenProgram: tokenProgramB,
    });

    const fundAssetLeg = getTransferCheckedInstruction({
      source: userAAtaA,
      mint: mintA,
      destination: escrowA,
      authority: userASigner,
      amount: t.amountA,
      decimals: 6,
    }, { programAddress: tokenProgramA });

    await client.sendTransaction([fundAssetLeg]);
    ```

    ويفعل طرف الشق النقدي الأمر نفسه لحساب الضمان B باستخدام `userBAtaB` و`mintB` و
    `userBSigner` و`t.amountB` و`{ programAddress: tokenProgramB }`.

  </Tab>

  <Tab value="Rust">

    ```rust
    let fund_asset_leg = transfer_checked(

        &user_a_ata_a,
    ```

    يبني طرف الشق النقدي التعليمة نفسها لحساب الضمان B باستخدام `mint_b` و
    `user_b` و`trade.amount_b`.

قد يتم استبدال تحويل تمويل شوهد بحالة [`confirmed`](/docs/rpc#configuring-state-commitment)
لاحقًا. يقرأ البرنامج رصيد حساب الضمان على السلسلة عند
التسوية، لذا فإن إرسال Settle مقابل تحويل تمويل لم يصل يفشل
مع الخطأ `LegNotFunded` ولا يتحرك شيء؛ وتكلفة ذلك هي فشل Settle وإعادة المحاولة.
اعتبر الشق ممولًا عندما يصبح تحويله `finalized`.

## ملاحظات

- **شقوق SOL المغلّفة.** يقرأ البرنامج رصيد حساب الضمان الأصلي بعد
  مزامنته، لذا تُحتسب الـ lamports المرسلة إلى حساب ضمان wrapped-SOL عبر تحويل
  النظام. لا ترسل SOL أبدًا إلى حساب ضمان لأي mint آخر: فالبرنامج لا يستطيع
  إعادتها، وتذهب إلى من يغلق الحساب.
- **عملات mint المقيّدة.** في عملة mint ذات حالة الحساب الافتراضية مجمّدة، يُنشأ حساب الضمان
  مجمّدًا ويفشل التحويل إلى أن تُلغي الجهة المصدِرة التجميد أو تقبله. يصف
  [النظرة العامة](/docs/defi/dvp-program#mint-configuration-constraints)
  التفاعل مع Token ACL.
- **خطافات التحويل.** موّل حسابات الضمان ذات الخطافات بالمبلغ المتفق عليه بالضبط. إذا
  اضطر فائضٌ إلى استرداد عند التسوية، فإن الاسترداد يعيد استخدام حسابات خطاف الشق
  مع وجهة ومبلغ مختلفين، وهو ما ترفضه بعض الخطافات. والحل
  هو Reclaim، ثم إعادة التمويل بالمبلغ الدقيق، ثم التسوية مرة أخرى.
- **التمويل بعد انتهاء الصلاحية.** لا شيء يمنع التحويل بعد `expiry_timestamp`. فهو
  يصل، لكن التسوية لم تعد ممكنة، ويستردّه طرف الشق عبر
  Reclaim ما دامت الصفقة مفتوحة أو Recover بعد إغلاقها. انظر
  [التراجع عن صفقة](/docs/defi/dvp-program/unwind-a-trade).
- **من يموّل أولًا.** لا يرتّب البرنامج الشقّين بتسلسل معيّن. فالترتيب
  شأن الأطراف؛ ويمكن لأي جانب استرداد شقّه في أي وقت
  قبل التسوية، ما لم تمنع جهة صلاحية mint (التجميد أو الإيقاف المؤقت أو خطاف التحويل)
  حساب الضمان.
