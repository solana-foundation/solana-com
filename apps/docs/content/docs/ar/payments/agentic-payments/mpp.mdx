يطبّق [بروتوكول مدفوعات الآلات (Machine Payments Protocol - MPP)](https://mpp.dev/) دلالات مصادقة HTTP
على المدفوعات. يوجّه الخادم تحديًا إلى الطلب غير المدفوع، ويعيد العميل بيانات اعتماد الدفع، ثم يُرجع الخادم إيصالًا بعد
قبوله الدفعة.

يفصل MPP بين ثلاثة جوانب:

- يصف **القصد (intent)** التفاعل التجاري، مثل `charge` لمرة واحدة
  أو `session` مقاسة الاستخدام.
- تصف **طريقة الدفع** كيفية انتقال القيمة. تدعم طريقة سولانا
  عملة SOL الأصلية ورموز SPL للرسوم.
- ينقل **وسيط HTTP** التحديات وبيانات الاعتماد والإيصالات والأخطاء.

يُنشر MPP على هيئة مجموعة من مسودات الإنترنت (Internet-Drafts). اعتبر
[المواصفات الحالية](https://paymentauth.org/) المصدر المرجعي، وتوقّع أن تتغير التفاصيل
ما دامت المسودات قيد العمل.

## تبادل HTTP

يستخدم MPP حقول مصادقة HTTP القياسية بدلًا من ترويسات الدفع الخاصة
بالبروتوكول:

| الرسالة                 | تمثيل HTTP                                         |
| ----------------------- | ----------------------------------------------------------- |
| تحدي الدفع       | `402 Payment Required` مع `WWW-Authenticate: Payment ...` |
| بيانات اعتماد الدفع      | طلب معاد إرساله مع `Authorization: Payment ...`           |
| الإيصال الناجح      | استجابة المورد مع `Payment-Receipt: ...`               |
| تفاصيل دفع غير صالحة | محتوى Problem Details باستخدام `application/problem+json`       |

```mermaid title="MPP Charge Flow"
sequenceDiagram
    participant Client
    participant Server
    participant Solana
    Client->>Server: GET /report
    Server-->>Client: 402 + WWW-Authenticate: Payment
    Note over Client: Validate terms and authorize payment
    Client->>Server: GET /report + Authorization: Payment
    Server->>Server: Verify challenge binding and transaction
    Server->>Solana: Broadcast signed transfer
    Solana-->>Server: Confirmed transaction
    Server-->>Client: 200 + report + Payment-Receipt
```

يتضمن التحدي معرّفًا يولّده الخادم، والنطاق (realm)، والطريقة، والقصد، وطلب
الدفع المشفّر، وتاريخ الانتهاء. تعيد بيانات الاعتماد صدى التحدي وتضيف
إثبات الدفع الخاص بالطريقة. يجب على الخادم التحقق من الجزأين؛ فلا يجوز لتحويل صالح
يخص تحديًا مختلفًا أن يفتح الوصول إلى المورد.

## رسوم سولانا لمرة واحدة

يدعم القصد `charge` في سولانا نوعين من بيانات الاعتماد:

- يستخدم **وضع السحب (Pull)** معاملة موقّعة. يوقّع العميل التحويل
  ويرسل المعاملة إلى الخادم. يتحقق الخادم منها، ويضيف اختياريًا
  توقيع دافع الرسوم، ثم يبثّها ويؤكدها ويعيد توقيع المعاملة
  في إيصاله.
- يستخدم **وضع الدفع (Push)** توقيع معاملة. يبثّ العميل المعاملة أولًا، ثم
  يرسل التوقيع المؤكَّد إلى الخادم. يجلب الخادم المعاملة ويتحقق منها
  قبل إرجاع المورد.

يتيح وضع السحب تحمّل الخادم لرسوم المعاملات ومنطق إعادة المحاولة من جانب الخادم.
يفيد وضع الدفع عندما تتطلب المحفظة أن يرسل العميل معاملته بنفسه،
لكنه لا يستطيع استخدام رعاية الخادم للرسوم.

للاطلاع على الحقول المعيارية وقواعد التحقق، راجع
[مواصفة رسوم سولانا](https://paymentauth.org/draft-solana-charge-00.html).

## إضافة رسوم MPP إلى واجهة Express API

توفّر Solana Pay Kit تكاملًا حديثًا بلغة TypeScript مع MPP وx402.
ثبّتها مع Express:

```bash
pnpm add @solana/pay-kit @solana/kit@^6.9.0 express
pnpm add --save-dev @types/express tsx
```

يستخدم هذا المثال الأبسط بيئة Surfpool التجريبية المستضافة والمستلم التجريبي العام
للحزمة. وهو مخصص للتطوير المحلي فقط:

```ts filename=server.ts
import express from "express";
import { createPayKit, usd } from "@solana/pay-kit";

const pay = await createPayKit({
  accept: ["mpp"],
  rpcUrl: "https://402.surfnet.dev:8899"
});

const app = express();

app.get("/report", pay.express(usd("0.01")), (_req, res) => {
  res.json({ report: "Paid report" });
});

app.listen(4567, () => {
  console.log("Paid API listening on http://127.0.0.1:4567");
});
```

شغّله وقارن بين طلب غير مدفوع وطلب مدرك للدفع:

```bash
pnpm tsx server.ts
curl -i http://127.0.0.1:4567/report
pay --sandbox curl http://127.0.0.1:4567/report
```

لا يعمل معالج المسار إلا بعد أن تقبل الوسيطة (middleware) الدفعة.

<Callout type="warn" title="استبدل جميع الإعدادات الافتراضية للبيئة التجريبية في الإنتاج">
  اضبط شبكة صريحة، ومستلم التاجر، وRPC مخصصًا، وسرًّا ثابتًا لربط
  التحدي، وموقّعًا للإنتاج، ومخزنًا دائمًا لمنع إعادة التشغيل. لا توجّه
  أبدًا مدفوعات حقيقية إلى موقّع تجريبي مضمّن في الحزمة.
</Callout>

## الجلسات المقاسة

استخدم `session` في MPP على سولانا عندما يجري العميل مدفوعات صغيرة ومترابطة كثيرة.
تفتح الجلسة قناة دفع على السلسلة بحد أقصى للإيداع، ثم تستخدم
قسائم موقّعة تراكمية مع نمو الاستخدام. يمكن للخادم التحقق من القسائم
خارج السلسلة وتسوية أعلى مبلغ مقبول لاحقًا.

يفيد هذا في الاستدلال المقاس بالرموز، والتنزيلات المقاسة بالبايتات، والبيانات المباشرة،
واستدعاءات الأدوات المتكررة. وهو يختلف عن إرسال دفعة منفصلة على السلسلة
لكل حدث.

```mermaid title="MPP Session Lifecycle"
sequenceDiagram
    participant Client
    participant Server
    participant Solana
    Client->>Server: Request + session support
    Server-->>Client: 402 + capped session challenge
    Client->>Solana: Open channel and deposit maximum
    Solana-->>Server: Channel confirmed
    loop Metered usage
        Client->>Server: Request + increasing signed voucher
        Server-->>Client: Resource + receipt
    end
    Server->>Solana: Settle highest accepted voucher
    Solana-->>Client: Return unused deposit when closed
```

سمِّ الجلسة **دفع جلسة** أو **قناة دفع** أو **تفويضًا متكررًا بحد أقصى**. ولا تسمِّها دفعًا متدفقًا
إلا إذا كانت الخدمة وعقد الدفع يقيسان فعليًا تدفقًا من الاستخدام.

## التحقق في بيئة الإنتاج

في كل رسوم على سولانا، يجب على الخادم التحقق على الأقل مما يلي:

- أن التحدي أصلي وغير منتهي الصلاحية ومرتبط بهذا الطلب ومخصص
  لهذا النطاق (realm).
- أن المعاملة تستخدم الشبكة والأصل أو الـ mint والمستلم والمبلغ
  وبرنامج الرموز (token program) المتوقعة.
- أن أي تعليمات لدافع الرسوم أو لحساب الرمز المرتبط (associated token account) مسموح بها صراحةً
  ولا يمكنها استنزاف موقّع الخادم.
- أن المعاملة نجحت عند مستوى الالتزام (commitment level) المطلوب.
- أن توقيع المعاملة لم يُستهلك من قبل.
- أن فحص إعادة التشغيل وعملية الاستهلاك ذريّان عبر جميع نسخ الخادم.

وبالنسبة إلى الجلسات، احفظ أيضًا حالة القناة والمبلغ التراكمي المقبول
وعلامة التسوية (settlement watermark) في مخزن مشترك. ووثّق كيف يستعيد العملاء الأموال غير المستخدمة
إذا أصبح الخادم غير متاح.
