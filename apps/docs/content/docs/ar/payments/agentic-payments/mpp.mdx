يطبّق [بروتوكول مدفوعات الآلات (MPP)](https://mpp.dev/) دلالات مصادقة HTTP
على المدفوعات. يرسل الخادم تحدّيًا إلى الطلب غير المدفوع، ثم يُعيد
العميل بيانات اعتماد الدفع، ثم يُرجع الخادم إيصالًا بعد
قبوله الدفعة.

يفصل MPP بين ثلاثة محاور:

- يصف **القصد (intent)** التفاعل التجاري، مثل عملية
  `charge` لمرة واحدة أو جلسة `session` مُقاسة.
- تصف **طريقة الدفع** كيفية انتقال القيمة. تدعم طريقة سولانا
  عملة SOL الأصلية ورموز SPL في عمليات الدفع (charges).
- يحمل **نقل** HTTP التحديات وبيانات الاعتماد والإيصالات والأخطاء.

يُنشر MPP على هيئة مجموعة من مسودات الإنترنت (Internet-Drafts). اعتبر
[المواصفات الحالية](https://paymentauth.org/) المصدر المرجعي الموثوق، وتوقّع
أن تتغير التفاصيل ما دامت المسودات قيد العمل.

## تبادل HTTP

يستخدم MPP حقول مصادقة HTTP القياسية بدلًا من ترويسات الدفع الخاصة
بالبروتوكول:

| الرسالة                 | تمثيل HTTP                                         |
| ----------------------- | ----------------------------------------------------------- |
| تحدّي الدفع       | `402 Payment Required` مع `WWW-Authenticate: Payment ...` |
| بيانات اعتماد الدفع      | طلب مُعاد إرساله مع `Authorization: Payment ...`           |
| إيصال ناجح      | استجابة المورد مع `Payment-Receipt: ...`               |
| تفاصيل دفع غير صالحة | نص Problem Details باستخدام `application/problem+json`       |

```mermaid title="MPP Charge Flow"
sequenceDiagram
    participant Client
    participant Server
    participant Solana
    Client->>Server: GET /report
    Server-->>Client: 402 + WWW-Authenticate: Payment
    Note over Client: Validate terms and authorize payment
    Client->>Server: GET /report + Authorization: Payment
    Server->>Server: Verify challenge binding and transaction
    Server->>Solana: Broadcast signed transfer
    Solana-->>Server: Confirmed transaction
    Server-->>Client: 200 + report + Payment-Receipt
```

يتضمن التحدّي معرّفًا يولّده الخادم، والنطاق (realm)، والطريقة، والقصد، وطلب
الدفع المُرمَّز، وتاريخ الانتهاء. تُردّد بيانات الاعتماد التحدّي وتضيف
إثبات الدفع الخاص بالطريقة. يجب على الخادم التحقق من الجزأين؛ فلا يجوز لتحويل صالح
يعود إلى تحدٍّ مختلف أن يفتح الوصول إلى المورد.

## عمليات الدفع لمرة واحدة على سولانا

يدعم القصد `charge` على سولانا نوعين من بيانات الاعتماد:

- يستخدم **وضع السحب (Pull mode)** معاملة موقَّعة. يوقّع العميل التحويل
  ويرسل المعاملة إلى الخادم. يتحقق الخادم منها، ويضيف اختياريًا
  توقيع دافع الرسوم، ثم يبثّها ويؤكدها ويُرجع توقيع المعاملة
  في إيصاله.
- يستخدم **وضع الدفع (Push mode)** توقيع معاملة. يبثّ العميل المعاملة أولًا، ثم
  يرسل التوقيع المؤكَّد إلى الخادم. يجلب الخادم المعاملة ويتحقق منها
  قبل إرجاع المورد.

يتيح وضع السحب (Pull mode) رعاية الخادم لرسوم المعاملات ومنطق إعادة المحاولة من جانب الخادم.
ويفيد وضع الدفع (Push mode) عندما تتطلب المحفظة أن يرسل العميل
معاملته بنفسه، لكنه لا يستطيع استخدام رعاية الرسوم من الخادم.

للاطلاع على الحقول المعيارية وقواعد التحقق، راجع
[مواصفات الدفع (charge) على سولانا](https://paymentauth.org/draft-solana-charge-00.html).

## إضافة عملية دفع MPP إلى واجهة Express API

توفّر Solana Pay Kit تكاملًا حديثًا بلغة TypeScript مع MPP وx402.
ثبّتها مع Express:

```bash
pnpm add @solana/pay-kit @solana/kit@^6.9.0 express
pnpm add --save-dev @types/express tsx
```

يستخدم هذا المثال المبسّط بيئة Surfpool التجريبية المستضافة والمستلم التجريبي العام
الخاص بالحزمة. وهو مخصص للتطوير المحلي فقط:

```ts filename=server.ts
import express from "express";
import { createPayKit, usd } from "@solana/pay-kit";

const pay = await createPayKit({
  accept: ["mpp"],
  rpcUrl: "https://402.surfnet.dev:8899"
});

const app = express();

app.get("/report", pay.express(usd("0.01")), (_req, res) => {
  res.json({ report: "Paid report" });
});

app.listen(4567, () => {
  console.log("Paid API listening on http://127.0.0.1:4567");
});
```

شغّله وقارن بين طلب غير مدفوع وطلب مدعوم بالدفع:

```bash
pnpm tsx server.ts
curl -i http://127.0.0.1:4567/report
pay --sandbox curl http://127.0.0.1:4567/report
```

لا يعمل معالج المسار إلا بعد أن يقبل البرنامج الوسيط الدفعة.

<Callout type="warn" title="استبدل كل الإعدادات الافتراضية للبيئة التجريبية في الإنتاج">
  اضبط شبكة صريحة، ومستلمًا للتاجر، وRPC مخصصًا، وسرًّا ثابتًا لربط
  التحدّي، وموقِّعًا للإنتاج، ومخزنًا دائمًا لمنع إعادة التشغيل (replay). لا
  توجّه مدفوعات حقيقية أبدًا إلى موقِّع تجريبي مضمَّن في الحزمة.
</Callout>

## الجلسات المُقاسة

استخدم جلسة `session` من MPP على سولانا عندما سيُجري العميل مدفوعات صغيرة ومترابطة كثيرة.
تفتح الجلسة قناة دفع على السلسلة بحد أقصى للإيداع، ثم تستخدم
قسائم موقَّعة تراكمية مع نمو الاستخدام. يمكن للخادم التحقق من القسائم
خارج السلسلة وتسوية أعلى مبلغ مقبول لاحقًا.

يفيد هذا في الاستدلال المقاس بالرموز، والتنزيلات المقاسة بالبايت، والبيانات الحية،
واستدعاءات الأدوات المتكررة. وهو ليس مماثلًا لإرسال دفعة منفصلة على السلسلة
عن كل حدث.

```mermaid title="MPP Session Lifecycle"
sequenceDiagram
    participant Client
    participant Server
    participant Solana
    Client->>Server: Request + session support
    Server-->>Client: 402 + capped session challenge
    Client->>Solana: Open channel and deposit maximum
    Solana-->>Server: Channel confirmed
    loop Metered usage
        Client->>Server: Request + increasing signed voucher
        Server-->>Client: Resource + receipt
    end
    Server->>Solana: Settle highest accepted voucher
    Solana-->>Client: Return unused deposit when closed
```

سمِّ الجلسة **دفع جلسة** أو **قناة دفع** أو **تفويضًا متكررًا محدود السقف**. ولا تسمِّها دفعًا متدفقًا
إلا إذا كانت الخدمة وعقد الدفع يقيسان فعليًا تدفقًا من الاستخدام.

## التحقق في بيئة الإنتاج

في كل عملية دفع (charge) على سولانا، يجب على الخادم التحقق على الأقل مما يلي:

- أن التحدّي أصلي وغير منتهي الصلاحية ومرتبط بهذا الطلب ومخصص
  لهذا النطاق (realm).
- أن المعاملة تستخدم الشبكة المتوقعة، والأصل أو عملة mint، والمستلم، والمبلغ،
  وبرنامج الرمز.
- أن أي تعليمات لدافع الرسوم أو لحساب الرمز المرتبط (associated token account) مسموح بها صراحةً
  ولا يمكنها استنزاف موقِّع الخادم.
- أن المعاملة نجحت عند مستوى الالتزام (commitment level) المطلوب.
- أن توقيع المعاملة لم يُستهلك من قبل.
- أن فحص إعادة التشغيل وعملية الاستهلاك ذريّان (atomic) عبر جميع نسخ الخادم.

وفي الجلسات، احفظ أيضًا حالة القناة والمبلغ التراكمي المقبول و
علامة التسوية (settlement watermark) في مخزن مشترك. ووثّق كيف يستعيد العملاء الأموال
غير المستخدمة إذا أصبح الخادم غير متاح.
