هذا الدليل مخصص لمزودي خدمات المحفظة والمطورين الذين يرغبون في دمج حلول إدارة
المفاتيح الجديدة في مكتبة `solana-keychain`. من خلال إضافة تطبيق الموقّع الخاص
بك، ستمكّن المطورين من استخدام خدمتك للتوقيع الآمن على معاملات سولانا من خلال
واجهة موحدة.

تحافظ Keychain على تكافؤ تطبيقاتها بلغات Rust وTypeScript وPython وGo.
نفضّل بشدة طلبات الدمج (PRs) التي تشمل اللغات الأربع جميعها. وإذا كان بإمكانك المساهمة
بلغة واحدة فقط فلا بأس بذلك، لكن توقّع أن تكون اللغات الأخرى مطلوبة قبل أن يُطرح الموقّع
ضمن أحد الإصدارات.

_هل تستخدم Claude Code؟ تقوم
[مهارة `add-signer-ci`](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)
الموجودة في المستودع بإعداد مسارات عمل CI لموقّع جديد تمت المساهمة به عبر PR من fork._

## نظرة عامة على البنية المعمارية

تعتمد المكتبة بنية قائمة على السمات (traits) معرّفة في `src/traits.rs`. يطبّق كل
موقّع السمة الأساسية `SolanaSigner` (`pubkey` و`sign_message` و
`is_available`) إضافةً إلى سمة قدرات واحدة بالضبط تتوافق مع طبيعة المزوّد:

- `TransactionSigner` (`sign_transaction`): يوقّع المزوّد بايتات المستدعي
  ويتولى المستدعي بثّها. وهو الخيار لمعظم الواجهات الخلفية.
- `ModifyingSigner` (`modify_and_sign_transaction`): يعيد المزوّد كتابة
  المعاملة ثم يوقّعها دون بثّها.
- `SendingSigner` (`sign_and_send_transaction`): يوقّع المزوّد المعاملة
  ويبثّها من جهة الخادم.

توفّر المكتبة أيضًا تعدادًا موحّدًا `Signer` يغلّف جميع
التطبيقات، مما يتيح اختيار واجهات التوقيع الخلفية أثناء التشغيل. ولا ينفّذ
سوى السمة الأساسية؛ أما القدرات فيمكن الوصول إليها عبر `as_transaction_signer()`
و`as_modifying_signer()` و`as_sending_signer()`.

## قائمة التحقق السريعة للدمج

- إنشاء وحدة الموقّع الخاصة بك مع التطبيق
- نفّذ السمة الأساسية `SolanaSigner` (`pubkey` و`sign_message` و
  `is_available`) إضافةً إلى سمة القدرات الواحدة التي تتوافق مع طبيعة مزوّدك
  (غالبًا `TransactionSigner`)
- أضف علامة ميزة (feature flag) في `Cargo.toml`، بما في ذلك العلامة الداخلية `_remote` إذا
  كان موقّعك يستخدم reqwest
- حدّث التعداد `Signer` في `src/lib.rs` (المتغيّر، وفرع `dispatch_signer!`، وفرعًا
  في دالة الوصول إلى القدرات يتوافق مع طبيعة موقّعك)
- فرض HTTPS وتكوين المهلات الزمنية على عملاء HTTP
- وقّع بايتات الرسالة وتحقّق من التوقيع المُعاد قبل إرفاقه
- أضف اختبارات وحدات شاملة (قائمة على wiremock، داخل وحدتك)
- أضف ملف اختبار تكامل وحدّث `.env.example`
- أضف تطبيقات TypeScript وPython وGo
- تحديث التوثيق
- تحديثات مسار عمل CI (نسّق مع المشرفين، راجع
  [تحديثات مسار عمل CI](#ci-workflow-updates-fork-prs))
- إرسال طلب السحب

## الخطوة 2: تعريف بنية الموقّع الخاصة بك

في `src/your_service/mod.rs`، عرّف بنية الموقّع الخاصة بك:

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,
}

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## الخطوة 3: تطبيق المُنشئ والطرق المساعدة

يجب على الموقّعين عن بُعد **فرض** HTTPS وتكوين المهلات الزمنية لـ HTTP. استخدم
بنية `HttpClientConfig` المشتركة لإعدادات المهلة الزمنية.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## الخطوة 4: تنفيذ سمات الموقّع

تحتوي السمة الأساسية `SolanaSigner` على دالتين غير متزامنتين (`sign_message` و
`is_available`) إضافةً إلى `pubkey()`. أما توقيع المعاملات فيوضع في سمة قدرات؛
وينفّذ معظم المزوّدين `TransactionSigner` التي تعيد دالتها `sign_transaction` القيمة
`SignTransactionResult` (تعداد موسوم يشير إلى أن المعاملة موقّعة بالكامل أو
جزئيًا).

وقّع بايتات الرسالة، وليس المعاملة الكاملة بصيغة الشبكة، وتحقّق من
توقيع المزوّد مقابلها قبل إرفاقه. استخدم دوال المساعدة المشتركة
`TransactionUtil` للتوقيع والتسلسل.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

إذا كان مزوّدك يعيد كتابة المعاملة قبل توقيعها، فنفّذ
`ModifyingSigner` بدلًا من ذلك واستبدل معاملة المستدعي بالكامل ببايتات
المزوّد. وإذا كان يبثّ المعاملة من جهة الخادم، فنفّذ `SendingSigner`
واترك معاملة المستدعي دون تغيير. لا تنفّذ أبدًا قدرة
لا يستطيع مزوّدك تقديمها.

## الخطوة 6: إضافة علامة الميزة

حدّث `Cargo.toml` لإضافة موقّعك كميزة اختيارية. تتضمن الواجهات الخلفية البعيدة
العلامة الداخلية `_remote` التي تتحكم في التنفيذ `From<reqwest::Error>`
في `src/error.rs`؛ وبدونها لن يُترجم الرمز `?` على استدعاءات reqwest عند تفعيل
ميزتك وحدها.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## الخطوة 7: تحديث تعداد الموقّع

أضف موقّعك إلى `src/lib.rs`. يوجّه التنفيذ الأساسي لـ `SolanaSigner` الاستدعاءات عبر
الماكرو `dispatch_signer!`، لذا أضف فرعًا واحدًا هناك. ويقع الوصول إلى القدرات في
دوال الوصول `as_transaction_signer()` و`as_modifying_signer()` و`as_sending_signer()`:
أضف فرع `Some(s)` إلى الدالة المطابقة لسمة القدرات الخاصة بك (وأضف أيضًا،
للواجهة الخلفية التي ترسل أو تعدّل، فرع `None` في `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## الخطوة 8: إضافة اختبارات شاملة

أضف الاختبارات إلى الوحدة الخاصة بك (في أسفل `src/your_service/mod.rs`):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

غطِّ أيضًا حالة فشل التحقق من التوقيع: يجب أن تُرجع الاستجابة الوهمية التي لا يتحقق
توقيعها خطأً.

## الخطوة 9: إضافة اختبارات التكامل

أنشئ `rust/src/tests/test_<name>_integration.rs`. تُشغَّل اختبارات التكامل
مقابل واجهة API الحقيقية للخدمة (وليس wiremock) وتكون مشروطة بميزة
`integration-tests`. يحتاج كل ملف إلى:

- تصريحات `pub const` لأسماء متغيرات البيئة
- دالة مساعدة `get_signer()` تقرأ متغيرات البيئة عبر `dotenvy`
- ثلاث دوال اختبار: `test_<name>_sign_message` و
  `test_<name>_sign_transaction` و`test_<name>_is_available`
- بوابات الميزات: `#[cfg(feature = "your_service")]` على الوحدة و
  `#[cfg(feature = "integration-tests")]` على كل اختبار

راجع `rust/src/tests/test_para_integration.rs` للاطلاع على مرجع كامل، ثم
صرّح بوحدتك في `rust/src/tests/mod.rs`:

```rust
pub mod test_your_service_integration;
```

## الخطوة 11: تحديث التوثيق

أضف الموقّع الخاص بك إلى جدول الخلفيات المدعومة في README.md:

| الخلفية         | حالة الاستخدام                                       | علامة الميزة   |
| --------------- | ---------------------------------------------- | -------------- |
| **Memory**      | أزواج المفاتيح المحلية، التطوير، الاختبار           | `memory`       |

أضف أيضًا واجهتك الخلفية إلى جدول قدرات الموقّعين في ملف README
الخاص بكل لغة. ثم أضف مثالًا للاستخدام:

```rust
use solana_keychain::{Signer, SolanaSigner};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let signer = Signer::from_your_service(
        "your-api-key".to_string(),
        "your-api-secret".to_string(),
        "your-wallet-id".to_string(),
        "your-public-key".to_string(),
    )?;

    let pubkey = signer.pubkey();
    println!("Public key: {}", pubkey);

    Ok(())
}
```

## تحديثات مسار عمل CI (طلبات PR من fork)

CI عملية من مرحلتين. نسّق مع المشرفين لتجهيز `main` قبل أن يمكن
اختبار طلب PR الخاص بك: فهم يحدّثون `fork-external-live-manual.yml`، ويضيفون متغيرات البيئة
إلى `ci.yml`، ويهيئون أسرار GitHub (Secrets).

يجب أن يتضمن طلب PR الخاص بك تغييرات المرحلة 2 هذه إلى جانب رمز موقّعك:

- **`ci.yml`**: أضف ميزة Rust الخاصة بك إلى مصفوفة `backend` (قبل `all`) و
  دالة اختبار التكامل الخاصة بك إلى مصفوفة `test`
- **`typescript-ci.yml`**: أضف حزمتك إلى مصفوفتي اختبارات الوحدات والتكامل،
  وأضف متغيرات البيئة إلى خطوة اختبار التكامل
- **`typescript-publish.yml`**: أضف حزمتك إلى `PUBLISH_PACKAGES`، وإلى مصفوفة
  `packages` الخاصة بإصدار GitHub Release، وإلى جدول الملخص
- **`python-ci.yml`**: أضف الواجهة الخلفية إلى بوابة `CI_SIGNER_*` في
  `resolve-signers` وإلى مصفوفة التكامل
- **`go-ci.yml`**: أضف الواجهة الخلفية إلى بوابة `CI_SIGNER_*` وإلى
  `moduleBySigner`

## موقّع TypeScript

إذا كنت تضيف أيضًا حزمة موقّع TypeScript، فقم بإنشائها في
`typescript/packages/your-signer/`. الأنماط الرئيسية:

- تُرجع دالة المصنع `createYourSigner()` النوع
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>`؛ أبقِ
  فئة الموقّع داخلية وصدّر فقط المصنع ونوع إعداداته
- تصدير واجهة الإعدادات (`YourSignerConfig`)
- إذا كانت واجهتك الخلفية لا تستطيع توقيع الرسائل، فاحذف `SolanaMessageSigner` ولا تعرض
  أي دالة `signMessages` على الإطلاق: يصنّف Kit الموقّعين بحسب وجود الدوال، لذا فإن
  دالة وهمية ترمي خطأً ستؤدي إلى تصنيف الموقّع تصنيفًا خاطئًا
- فرض HTTPS على حقول الإعداد `apiBaseUrl` باستخدام `assertHttpsUrl()` من
  `@solana/keychain-core`
- نفّذ الاستدعاءات البعيدة عبر `fetchSignerJson()` من `@solana/keychain-core`،
  التي تتولى تحويل الأخطاء، وتنقية الاستجابات، ورفض إعادة التوجيه، والمهلة
  الافتراضية
- نقِّ أي نص خطأ آخر من واجهة API البعيدة باستخدام `sanitizeRemoteErrorResponse()`
  من `@solana/keychain-core`
- استخدام `throwSignerError(SignerErrorCode.*, { cause, message })` من
  `@solana/keychain-core`
- احترم `config?.abortSignal` في كل دالة توقيع، ومرّره إلى
  `fetchSignerJson()` و`signBatchStaggered()`
- تحقّق من `requestDelayMs` باستخدام `validateRequestDelayMs()` ونفّذ المعالجة الدفعية عبر
  `signBatchStaggered()`
- إضافة `@throws` JSDoc إلى دوال المصنع التي تسرد رموز الأخطاء
- صرّح بحزم `@solana/*` كاعتماديات نظيرة (peer dependencies) بالإصدار `>=8.1.0`
- اختبارات الوحدات باستخدام vitest مع `fetch` وهمية؛ واختبارات التكامل باستخدام
  `runSignerIntegrationTest` من `@solana/keychain-test-utils`

### موقّعو الإرسال

إذا كان مزوّدك يعيد كتابة المعاملة أو يبثّها من جهة الخادم، فلا يمكن
تطبيق توقيعه على معاملة المستدعي، لذا يجب أن يكون
`SolanaSendingSigner` بدلًا من `SolanaTransactionSigner`:

- نفّذ `signAndSendTransactions()` ولا تعرض **أي** `signTransactions`
  (ولا `signMessages`، ما لم توقّع الواجهة الخلفية الرسائل فعلًا)
- احترم `config?.abortSignal`. بمجرد أن يقبل المزوّد عملية الإنشاء، أبلغ عن
  أي فشل (بما في ذلك الإلغاء) على أنه `BROADCAST_UNCONFIRMED` مع معرّف
  معاملة المزوّد، مع الاحتفاظ بسبب الإلغاء في `cause`
- أضف تحميلًا زائدًا (overload) مكتوبًا للدالة `createKeychainSigner` يُرجع نوع موقّع الإرسال الخاص بك
- استبعد واجهتك الخلفية من `KeychainKitPluginConfig` في
  `typescript/packages/kit-plugin/src/keychain-plugin.ts`، لأن موقّع الإرسال
  لا يمكن أن يعمل كـ `payer` أو `identity` لعميل Kit
- تحقّق في اختبارات الوحدات من أن `isTransactionPartialSigner()` تُرجع false وأن
  `isTransactionSendingSigner()` تُرجع true لكائناتك

### تحديث الحزمة الشاملة

حدّث `typescript/packages/keychain/` (7 ملفات للتعديل):

1. `src/types.ts`: أضف `YourSignerConfig` إلى الاتحاد المميَّز
   `KeychainSignerConfig`
2. `src/create-keychain-signer.ts`: أضف حالة switch (تُحمَّل حزمة كل واجهة خلفية
   عبر `import()` ديناميكي)
3. `src/resolve-address.ts`: أضفها إلى حالة switch الخاصة بالمسار السريع أو مسار الجلب
4. `src/index.ts`: أضف تصديرات نوع الإعداد ومساحة الأسماء ودالة المصنع
5. `package.json`: أضف الاعتمادية `@solana/keychain-your-signer: "workspace:*"`
6. `tsconfig.json`: أضف المرجع `{ "path": "../your-signer" }`
7. `typescript/scripts/test-treeshake-umbrella.mjs`: أضف حزمتك إلى
   `SIGNER_MARKERS` ومصنعك إلى `FACTORIES`

تحتوي عبارات switch على فحوصات `never` شاملة، لذا سيُظهر TypeScript خطأً
إذا أضفت إلى الاتحاد وفاتتك حالة. شغّل `just ts-treeshake` بعد ذلك:
يجب أن تظل كل حزمة والحزمة الشاملة قابلة لإزالة الرمز غير المستخدم (tree-shaking).

## موقّع Python

أنشئ الوحدة في `python/src/solana_keychain/your_signer/` (`__init__.py`
مع `signer.py`). الأنماط الأساسية:

- اشتق من `SolanaSigner` في `solana_keychain.core` (الخاصية `pubkey`، و
  `async sign_message()`، و`async is_available()`) إضافةً إلى فئة قدرات واحدة بالضبط:
  `TransactionSigner` (`async sign_transaction()`) أو `ModifyingSigner`
  (`async modify_and_sign_transaction()`) أو `SendingSigner`
  (`async sign_and_send_transaction()`)
- صدّر مصنع `async create_your_signer()` ينتظر `init()` عندما
  تحدد الواجهة الخلفية عنوانها عن بُعد؛ وقبل التهيئة يُطلق التوقيع الخطأ
  `SignerErrorCode.NOT_INITIALIZED`
- صدّر فئة بيانات للإعداد (`YourSignerConfig`) مع تعليم الأسرار بـ
  `field(repr=False)`
- افرض HTTPS على حقول عنوان URL الأساسي باستخدام `assert_https_url()`، ومرّر كل
  طلب عبر `fetch_signer_json()`
- تحقّق من توقيع المزوّد قبل إرجاعه؛ واستخدم
  `signed_message_bytes()` للحصول على البايتات التي يغطيها التوقيع، ولا تستخدم أبدًا
  بادئة إصدار مكتوبة يدويًا
- سجّل الواجهة الخلفية في `_BACKENDS` داخل
  `python/src/solana_keychain/keychain.py`
- إذا كانت الواجهة الخلفية تحتاج إلى SDK من المزوّد، فاحمِ عملية الاستيراد، وأطلق `ImportError`
  يذكر `pip install 'solana-keychain[your-signer]'`، وأعلن الإضافة الاختيارية في
  `python/pyproject.toml`، ولا تستورد الواجهة الخلفية استيرادًا مبكرًا من جذر
  الحزمة
- اختبارات الوحدة باستخدام pytest: `respx` للواجهات الخلفية التي تعتمد على HTTP، وعملاء وهميون (stubs) للواجهات الخلفية التي تعتمد على SDK، وفحص يضمن عدم ظهور أي سر في `str()` أو `repr()` للأخطاء المُطلَقة
- أضف دالة مصنع `make_your_signer()` إلى
  `python/tests/integration/test_live_signers.py` وسجّلها في
  `_MESSAGE_CAPABLE` (أو في `_TRANSACTION_ONLY` للواجهات الخلفية التي لا تدعم
  `sign_message`)

## موقّع Go

كل واجهة خلفية بلغة Go هي وحدة (module) مستقلة، في المسار `go/signers/yoursigner/` ومسار الوحدة
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`. راجع
`go/signers/para/` كمرجع. أهم الأنماط:

- نفّذ `core.SolanaSigner` (`Pubkey()` و`SignMessage(ctx, message)` و
  `IsAvailable(ctx)`) بالإضافة إلى واجهة قدرات واحدة فقط:
  `core.TransactionSigner` أو `core.ModifyingSigner` أو `core.SendingSigner`.
  يتم اكتشاف القدرة عبر type assertion، لذا يجب ألا تحتوي الواجهة الخلفية التي لا تستطيع توقيع
  معاملة على أي دالة `SignTransaction` على الإطلاق
- صدّر بنية `Config` ودالة إنشاء `New` (`New(ctx, cfg)` عندما
  تحلّ الواجهة الخلفية عنوانها عن بُعد؛ وقبل ذلك، أعد
  `core.NewNotInitializedError`)
- أنشئ عملاء HTTP باستخدام `core.NewHTTPClient` أو `core.ResolveHTTPClient`، و
  تحقق من عناوين URL الأساسية باستخدام `core.NormalizeHTTPSBaseURL`
- وقّع المعاملات باستخدام `core.SignTransactionWith`، التي توقّع بايتات
  الرسالة وتُرفق التوقيع؛ وتحقق من توقيعات المزوّد باستخدام
  `core.VerifySignature`
- أعد الأخطاء باستخدام `core.NewSignerError` / `core.WrapSignerError` ورموز
  ثابتة مثل `core.CodeSigningFailed`
- اختبارات الوحدة باستخدام `httptest`؛ واختبارات التكامل في `integration_test.go` خلف
  وسم `//go:build integration`

## قائمة التحقق قبل التقديم

قبل تقديم طلب السحب الخاص بك:

- اتباع اصطلاحات التسمية (snake_case للغتَي Rust وPython، وcamelCase للغة
  TypeScript)

- تضمين تنفيذات TypeScript وPython وGo (أو التخطيط لها مع

## نصائح التنفيذ

### معالجة الأخطاء

استخدم دائمًا متغيرات `SignerError` الموجودة. كلٌّ من `Display` و`Debug` في
`SignerError` يُخفي المحتوى الحساس، لذا اجعل الرسائل عامة ولا تُضمّن أبدًا بيانات
استجابة API الخام. لا تستخدم أبدًا `.expect()` أو `.unwrap()` على استجابات API غير الموثوقة:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### متطلبات الأمان

هذه ليست مجرد اقتراحات: فالمستهلكون يختارون الواجهة الخلفية بناءً عليها. إذا
جعل مزوّدك أحدها مستحيلًا، فاذكر ذلك في طلب السحب (PR) وفي ملف المستودع
`docs/SECURITY_MODEL.md`.

- **تحقّق مما وقّعه المزوّد.** احسب بايتات الرسالة محليًا وتحقق من
  التوقيع المُعاد مقابلها في الموضع الذي يتطلبه موقّعك قبل إرفاقه.
  التوقيع الذي لا يجتاز التحقق يجب أن يفشل، ولا يُرفق أبدًا.
- **صرّح ما إذا كان المزوّد يبثّ المعاملة.** إذا كان ينفّذها من جهة الخادم،
  فنفّذ نمط الإرسال وأعد التوقيع الذي يحدد المعاملة التي تم تأكيدها على الشبكة. وإذا لم يكن لدى المزوّد
  نقطة نهاية للتوقيع فقط، فاجعل الواجهة الخلفية للإرسال فقط بدلًا من
  إرسال المعاملة من وراء ظهر المستدعي.
- **لا تترك المستدعي أبدًا بمعاملة لا يغطيها التوقيع.**
  المزوّد الذي يعيد كتابة المعاملة يوقّع بايتاته الخاصة: إما أن تترك
  معاملة المستدعي دون تغيير (حالة البث المُدار)، أو تعتمد نمط التعديل
  وتستبدلها بالكامل ببايتات المزوّد.
- **أبلغ عن عدم اليقين في البث كما هو.** قد يكون الفشل بعد الإرسال قد تم تأكيده فعليًا.
  أظهر `BROADCAST_UNCONFIRMED` بدلًا من خطأ عام، وأرفق
  معرّف معاملة المزوّد متى توفر لديك، وأرسل مفتاح idempotency مشتقًّا من الرسالة
  مع كل عملية إنشاء كي تكون إعادة الإرسال المطابقة بايتًا ببايت
  آمنة.
- **لا توقّع أبدًا قبل التهيئة.** استخدم `Option<Pubkey>` (وليس `Pubkey::default()`) من أجل
  المفتاح العام قبل `init()`، وأفشل العملية بخطأ في الإعدادات إذا
  جرت محاولة التوقيع قبلها.
- لا تسجّل أبدًا بيانات حساسة (المفاتيح الخاصة، وأسرار API، واستجابات API الخام)، و
  استخدم تنفيذ `Debug` يخفي الحقول الحساسة
- فرض HTTPS (`https_only(true)`، مع تقييده بـ `#[cfg(not(test))]` من أجل
  wiremock) وإعداد مهلات الطلب والاتصال عبر `HttpClientConfig`
  (القيم الافتراضية: 30 ثانية / 5 ثوانٍ)
- صفّر (Zeroize) مواد المفاتيح الوسيطة باستخدام `zeroize::Zeroizing<Vec<u8>>`

### الاختبار باستخدام العناصر الوهمية (Mocks)

استخدم `wiremock` لمحاكاة واجهات برمجة تطبيقات HTTP. قم بالتأكيد على نوع الخطأ
فقط، وليس على نص رسالة الخطأ:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
