تأكد من توفر ما يلي قبل نشر تطبيقك على الشبكة الرئيسية (Mainnet):

- ملف ELF الخاص بالبرنامج - وهو عادةً ناتج الأمر `anchor build` أو
  `cargo-build-sbf` وينتهي بالامتداد `.so`
- keypair الخاص بالبرنامج - ملف JSON يحتوي على مصفوفة من الأعداد الصحيحة

في هذا القسم، سنوضح مكان العثور على هذه الأصول وكيفية تجهيزها.

## تجهيز ملف ELF الخاص بك

يحتوي ملف ELF على الشيفرة البايتية المُصرَّفة ومعلومات تخطيط الذاكرة والبيانات الوصفية اللازمة لآلة سولانا الافتراضية (SVM) كي تفهم كيفية تحميل برنامجك وتشغيله. يُنشأ ملف ELF عند تصريف الشيفرة المصدرية.

لإنشاء ملف ELF الخاص بك، يمكنك تشغيل الأمر التالي لإطار العمل Anchor:

```bash
anchor build
```

أو الأمر التالي لأطر العمل الأخرى:

```bash
cargo build-sbf
```

يمكنك بعد ذلك العثور على ملف ELF في مجلد مثل
`target/deploy/<PROGRAM_NAME>.so`.

يكون برنامجك جاهزًا عندما يُصرَّف ملف ELF إلى
[sBPFv3](https://www.anza.xyz/blog/migrating-solana-programs-to-sbpfv3). للتحقق من برنامجك، يمكنك تشغيل الأمر التالي على Linux:

```bash
readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

والأوامر التالية على macOS:

```bash
# brew install llvm
$(brew --prefix llvm)/bin/llvm-readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

إذا ظهر لك ناتج مشابه لما يلي، فبرنامجك جاهز:

```
  Flags:                             0x3
```

وإن لم يكن كذلك، فاتبع دليل الترحيل المرتبط
[هنا](https://solana.com/upgrades/sbpfv3-programs).

## تجهيز عنوان برنامجك

عنوان برنامجك هو معرّف البرنامج (program ID) الذي ستستخدمه لاستدعاء تعليمات برنامجك. يمكنك إما 1) استخدام keypair الخاص بالبرنامج الذي أُنشئ أثناء البناء، أو 2) توليد keypair جديد يبدأ عنوانه ببادئة مخصصة، أو 3) اشتقاق عنوان حساب من عنوان أساسي و seed. الخياران الأولان ينتجان keypair يمكنه التوقيع نيابةً عن program account. أما الحساب المُنشأ باستخدام seed فليس له مفتاح خاص به؛ إذ يتحكم فيه الحساب الأساسي.

### استخدام keypair المُنشأ

افتراضيًا، يضع كلٌّ من `anchor build` و`cargo build-sbf` keypair الخاص بالبرنامج في المسار:

```text
target/deploy/<PROGRAM_NAME>-keypair.json
```

احتفظ بنسخة احتياطية من هذا الملف قبل تنظيف مجلد البناء. يمكن لأي شخص يملك حق الوصول إلى keypair التوقيع بصفته program account، لذا لا تُضِفه إلى نظام التحكم بالمصدر.

### توليد keypair ببادئة مخصصة

استخدم [`vanity`](https://github.com/cavemanloverboy/vanity) للبحث عن keypair من نوع Ed25519 يبدأ مفتاحه العام ببادئة base58 محددة. ثبّت نسخة CPU من crates.io:

```bash
cargo install vanity
```

يوفر المشروع أيضًا إصدارات CUDA وMetal وOpenCL لعمليات البحث المُسرَّعة بواسطة وحدة معالجة الرسوميات (GPU). راجع تعليمات تثبيت `vanity` لمعرفة متطلبات كل واجهة خلفية.

```bash
vanity grind-keypair --pattern Acme...
```

عند العثور على تطابق، يطبع `vanity` المفتاح العام، والبذرة الخاصة بصيغة hex، ومصفوفة JSON لـ keypair متوافقة مع سولانا. احفظ ملف JSON في مكان آمن، ثم تأكد من أنه يحتوي على المفتاح العام المتوقع:

```bash
solana-keygen pubkey path/to/keypair.json
```

تعامل مع ناتج الأمر وملف JSON المحفوظ على أنهما مواد مفتاح خاص.

### إنشاء حساب باستخدام seed

لإجراء بحث أسرع، يبحث `vanity grind` في سلاسل seed الخاصة بـ `CreateAccountWithSeed` بدلًا من توليد keypair من نوع Ed25519. قدّم المفتاح العام للحساب الأساسي الذي سيصرّح بالإنشاء، ومالك الحساب، والبادئة المطلوب البحث عنها. وبالنسبة إلى program account القابل للترقية، استخدم محمّل BPF القابل للترقية بصفته المالك:

```bash
vanity grind \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --pattern Acme...
```

تتضمن النتيجة العنوان المشتق وسلسلة seed. تحقق منهما قبل إنشاء الحساب:

```bash
vanity verify \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --seed <SEED>
```

استخدم العنوان الأساسي نفسه و seed والمالك نفسه لاشتقاق العنوان عبر `Pubkey::create_with_seed`، ثم أرسل تعليمة `create_account_with_seed` الخاصة بـ System Program. يجب أن يوقّع كلٌّ من الحساب الأساسي وحساب التمويل على المعاملة. ولأن الحساب المشتق ليس له keypair مستقل، يتطلب هذا الخيار مسارًا لإنشاء الحساب ونشره يعتمد على الحساب الأساسي بدلًا من ملف keypair الخاص بالبرنامج.

### تحديث عنوان البرنامج في الشيفرة المصدرية

بعد اختيار keypair أو حساب مُنشأ باستخدام seed، استخدم عنوانه العام بصفته معرّف البرنامج في كل موضع يصرّح فيه المشروع بهذا المعرّف. إذا بقي العنوان القديم في الشيفرة المصدرية، فقد ترسل العملاء التعليمات إلى برنامج خاطئ، وقد تفشل عمليات التحقق من المعرّف أثناء التشغيل.

في مساحة عمل Anchor، حدّث إدخال البرنامج في ملف `Anchor.toml` الموجود في الجذر، واستدعاء `declare_id!` في `programs/<PROGRAM_NAME>/src/lib.rs`. المفتاح الموجود تحت `[programs.<CLUSTER>]` هو اسم البرنامج في مساحة العمل. حدّث كل جدول cluster تنوي استخدام العنوان الجديد فيه؛ ويحدّث المثال أدناه الشبكة الرئيسية (Mainnet).

في Anchor.toml:

```diff
 [programs.mainnet]
-my_program = "<OLD_PROGRAM_ID>"
+my_program = "<NEW_PROGRAM_ID>"
```

في `programs/<your_program>/lib.rs`:

```diff
-declare_id!("<OLD_PROGRAM_ID>");
+declare_id!("<NEW_PROGRAM_ID>");
```

لا يستخدم Pinocchio الملف `Anchor.toml`. حدّث استدعاء `declare_id!` في الملف `src/lib.rs` الخاص بحزمة البرنامج (crate). تستورد مشاريع Pinocchio الحالية هذا الماكرو من `pinocchio::address`.

يصرّح Quasar أيضًا بالعنوان في الملف `src/lib.rs` الخاص بحزمة البرنامج على السلسلة (onchain)، ولا يستخدم `Anchor.toml`. يتوفر الماكرو `declare_id!` عبر `quasar_lang::prelude::*`.

أعد بناء البرنامج وأعد توليد أي ملفات IDL أو مخرجات خاصة بالعميل بعد تغيير العنوان. ابحث أيضًا في سكربتات النشر والاختبارات وإعدادات التطبيق عن معرّف البرنامج القديم، واستبدل أي إشارات مكتوبة فيها بشكل ثابت.
