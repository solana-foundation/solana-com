<Callout type="info" title="Resumo">
  Os programas são compilados para sBPF via LLVM e executados numa VM isolada com um
  orçamento de 1,4 M CU por transação. O runtime armazena em cache até 512 programas compilados,
  fornece syscalls para logging, CPI, criptografia e memória, e atrasa novos
  deployments em 1 slot.
</Callout>

## Compilação

A Solana usa [LLVM](https://llvm.org/) para compilar programas em
binários [ELF](https://en.wikipedia.org/wiki/Executable_and_Linkable_Format)
contendo o Solana Bytecode Format (sBPF). O binário ELF é armazenado onchain numa
conta executável.

<Callout>
  sBPF é a variante personalizada da Solana do bytecode [eBPF](https://en.wikipedia.org/wiki/EBPF),
  adaptada para o runtime da Solana. Não é eBPF padrão e possui
  modificações específicas da Solana.
</Callout>

## Escrever programas

Os programas Solana são escritos principalmente em
[Rust](https://rust-book.cs.brown.edu/title-page.html) usando uma das três
abordagens:

<Cards>
  <Card title="Anchor" href="https://www.anchor-lang.com/docs">
    Um framework que utiliza macros Rust para reduzir o código repetitivo. Recomendado para
    a maioria dos desenvolvedores.
  </Card>
  <Card title="Pinocchio" href="/docs/clients/official/rust#program-crates">
    Uma biblioteca Rust leve e zero-copy otimizada para consumo de computação e
    tamanho do binário. Inclui crates específicos de programas para CPIs comuns.
  </Card>
  <Card title="Rust Nativo" href="/docs/programs/rust">
    Rust direto sem frameworks. Oferece controle total, mas requer mais
    implementação manual.
  </Card>
</Cards>

Consulte [Cross-Program Invocations](/docs/core/cpi) para conceitos e exemplos de CPI
que se aplicam a todas essas abordagens.

## Modelo de execução de programas

Quando uma transação é processada, o runtime executa cada instrução
sequencialmente por meio de
[`process_message()`](https://github.com/anza-xyz/agave/blob/v3.1.8/svm/src/message_processor.rs#L15).
Para cada instrução, o runtime:

1. **Prepara o contexto da instrução.** Chama
   [`prepare_next_top_level_instruction()`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L436)
   para mapear os índices de conta da instrução, definir flags de signatário e de escrita, e
   configurar o
   [`TransactionContext`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L467).

2. **Verifica os precompiles.** Se o programa for um
   [precompile](/docs/core/programs/precompiles), o runtime chama
   [`process_precompile()`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L491),
   que ainda empurra e retira um frame de pilha (via _rs`push()`_ e _rs`pop()`_)
   mas ignora a VM sBPF e a busca no cache de programas, executando código nativo
   diretamente.

3. **Empurra um frame de pilha.** (Os passos 3-6 ocorrem dentro de
   [`InvokeContext::process_instruction()`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L481)
   e
   [`process_executable_chain()`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L507),
   chamados a partir de _rs`process_message()`_.) Chama
   [`push()`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L233)
   em
   [`InvokeContext`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L184),
   que incrementa a altura da pilha de instruções e aplica a
   regra de reentrância: um programa só pode reingressar em si mesmo se o chamador **imediato** (o
   programa no topo atual da pilha de instruções) for o mesmo programa.
   A autorrecursão profunda (A -> A -> A) é permitida, sujeita aos limites de profundidade de pilha.
   Outros padrões de reentrância (ex.: A chama B que chama A) retornam
   _rs`InstructionError::ReentrancyNotAllowed`_.

4. **Resolve o programa.** O runtime chama
   [`process_executable_chain()`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L507)
   que determina o loader. Se o proprietário do program account for o
   [native loader](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L517),
   o programa é um builtin e sua função de entrypoint é consultada diretamente
   do
   [`ProgramCacheForTxBatch`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L706).
   Se o proprietário for um dos BPF loaders (`bpf_loader_deprecated`,
   `bpf_loader`, `bpf_loader_upgradeable` ou `loader_v4`), o próprio entrypoint
   builtin do loader é invocado.

5. **Executa o programa BPF.** Para programas BPF, o
   [entrypoint do loader](https://github.com/anza-xyz/agave/blob/v3.1.8/programs/bpf_loader/src/lib.rs#L385)
   busca o executável compilado no cache de programas. A função
   [`execute()`](https://github.com/anza-xyz/agave/blob/v3.1.8/programs/bpf_loader/src/lib.rs#L1449)
   então:
   - Serializa os dados da conta num buffer de parâmetros plano
   - Cria a VM sBPF com regiões de pilha, heap e memória
   - Executa o código compilado, consumindo unidades de computação durante a execução. Retorna
     _rs`ComputationalBudgetExceeded`_ se o orçamento for excedido.
   - Desserializa os dados da conta do buffer de volta ao estado da conta

6. **Retira o frame de pilha.** Chama
   [`pop()`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/invoke_context.rs#L268)
   que verifica se a instrução não violou as regras de contabilidade do runtime
   (os saldos de lamport estão equilibrados, as contas somente leitura não foram modificadas,
   os tamanhos dos dados das contas estão dentro dos limites).

7. **Acumula unidades de computação.** As unidades de computação consumidas pela instrução
   são adicionadas ao total da transação via
   [`saturating_add`](https://github.com/anza-xyz/agave/blob/v3.1.8/svm/src/message_processor.rs#L53).

## Cache de programas

O runtime mantém um
[`ProgramCache`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L677)
global que armazena programas verificados e compilados. Ele é ciente do fork-graph e lida com
regras de visibilidade de deployment, evicção e recompilação no limite de epoch.

### Tipos de entrada no cache

Cada programa em cache possui um
[`ProgramCacheEntryType`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L132)
que determina seu comportamento em tempo de execução:

| Tipo                                                                                                              | Descrição                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [`Loaded`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L147)             | Programa verificado e compilado, pronto para execução.                                                                                                                                                                                                                                              |
| [`Builtin`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L149)            | Programa nativo compilado no binário do validator (System, Stake, Vote, etc.). Não armazenado onchain.                                                                                                                                                                                               |
| [`Unloaded`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L145)           | Programa previamente verificado cujo executável compilado foi removido da memória para liberar espaço. Ainda rastreia estatísticas de uso. Pode ser recarregado sem reverificação.                                                                                                                             |
| [`FailedVerification`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L134) | Tombstone para programas que não passaram no verificador sBPF com o conjunto de funcionalidades atual. Pode tornar-se `Loaded` se as ativações de funcionalidades alterarem as regras de verificação.                                                                                                                              |
| [`Closed`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L139)             | Tombstone para programas que foram explicitamente encerrados ou nunca implantados. Também usado para contas (como contas de buffer) que pertencem a um loader mas não contêm código executável.                                                                                                               |
| [`DelayVisibility`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L141)    | Tombstone sintético retornado por [`ProgramCacheForTxBatch::find()`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L755) quando uma entrada `Loaded` existe mas ainda não está em vigor (seu `effective_slot` está no futuro). Nunca armazenado diretamente no cache. |

### Atraso de visibilidade

Programas recém-implantados ou atualizados não entram em vigor imediatamente. A
constante [`DELAY_VISIBILITY_SLOT_OFFSET`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L32)
é `1`, o que significa que um programa implantado no slot N entra em vigor no slot
N+1. Durante o slot de implantação, qualquer tentativa de invocar a nova versão retorna
_rs`DelayVisibility`_, fazendo com que o runtime reporte "Program is not deployed."

### Política de evicção

O cache comporta até
[`MAX_LOADED_ENTRY_COUNT`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L31)
(512) entradas de programas compilados. Quando o limite é atingido, os programas
menos utilizados são removidos para o estado _rs`Unloaded`_. O uso é rastreado por
[`tx_usage_counter`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L197)
(incrementado cada vez que uma transação referencia o programa) e
[`latest_access_slot`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L199).

### Recompilação no limite de epoch

Se uma ativação de funcionalidade alterar os
[`ProgramRuntimeEnvironments`](https://github.com/anza-xyz/agave/blob/v3.1.8/program-runtime/src/loaded_programs.rs#L529)
no limite de um epoch, todos os programas em cache são
[recompilados](https://github.com/anza-xyz/agave/blob/v3.1.8/runtime/src/bank.rs#L1494)
contra o novo ambiente.

## Dados de retorno

Os programas podem definir dados de retorno via a syscall `sol_set_return_data`. Os dados são
armazenados numa
[`TransactionReturnData`](https://github.com/anza-xyz/agave/blob/v3.1.8/transaction-context/src/lib.rs#L499)
estrutura em nível de transação que contém os bytes de dados e o `program_id` do programa cuja
instrução chamou a syscall. O tamanho máximo é de 1.024 bytes
(_rs`MAX_RETURN_DATA`_).
