## Gestão de chaves

- **Nunca exponha chaves privadas no código do frontend.** Use assinatura no backend, carteiras de hardware, carteiras multiassinatura ou serviços de gestão de chaves.
- **Separe carteiras quentes e frias.** Carteira quente para operações, carteira fria para a tesouraria.
- **Faça backup de todas as chaves de produção.** Guarde backups encriptados em vários locais seguros. Perder uma chave significa perder o acesso de forma permanente.
- **Use chaves diferentes para a devnet e a mainnet.** As suas chaves da devnet não devem ser as mesmas da mainnet. Use uma configuração baseada no ambiente para garantir que as chaves corretas são carregadas em cada rede.

## Infraestrutura de assinatura

Para a assinatura no backend em produção, use o [Keychain](/docs/tools/keychain), uma biblioteca de assinatura unificada que abstrai vários backends de gestão de chaves através de uma única interface: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP, Para, Dfns, Crossmint, Openfort e Utila. Isto permite-lhe desenvolver localmente com chaves em memória e depois migrar para backends de nível de produção sem alterar o código da aplicação.

Não sabe qual backend é o mais adequado? Consulte [Escolher um backend](/docs/tools/keychain/choosing-a-backend). O Keychain está disponível para [Rust](https://crates.io/crates/solana-keychain) e [TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Segurança de RPC

Trate os endpoints RPC como chaves de API: não os exponha no código do frontend, onde podem ser extraídos e utilizados de forma abusiva. Use um proxy de backend ou variáveis de ambiente que não sejam incluídas no código do cliente.

- [QuickNode: Endpoint Security Best Practices](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Protect Your Solana API Keys: Security Best Practices](https://www.helius.dev/docs/rpc/protect-your-keys)

## Monitorização

Acompanhe estas métricas em produção:

| Métrica                   | Motivo                    |
| ------------------------ | ---------------------- |
| Taxa de sucesso das transações | Detetar problemas cedo    |
| Latência de confirmação     | Monitorizar a saúde da rede |
| Gasto em taxas de prioridade       | Gestão de custos        |
| Taxa de erros de RPC           | Saúde do provedor        |

Configure alertas para:

- Transferências da tesouraria acima de um limite
- Picos na taxa de transações falhadas
- Padrões incomuns de destinatários
- Aumentos na taxa de erros de RPC

Para a monitorização de transações em tempo real e em grande escala, consulte o nosso [Guia de indexação](/docs/payments/accept-payments/indexing).

## Verificar endereços

Cada token e cada programa tem exatamente um endereço correto na mainnet. Tokens falsificados que imitam a USDC ou outras stablecoins são comuns: têm o mesmo nome e símbolo, mas um mint diferente. A sua aplicação deve codificar de forma fixa ou incluir numa lista de permissões os endereços de mint (de acordo com os seus requisitos) e nunca aceitá-los dinamicamente de fontes não confiáveis.

**Configuração baseada no ambiente:** A Devnet e a Mainnet usam frequentemente mints de token completamente diferentes. Configure a sua aplicação para carregar os endereços corretos por ambiente: não codifique de forma fixa endereços da mainnet e se esqueça de os trocar durante os testes, nem, pior ainda, envie endereços da devnet para produção.

Alguns mints comuns de stablecoins são:

| Token | Emissor | Endereço do mint                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Os endereços dos programas também são importantes. Enviar instruções para o programa errado falhará ou, pior ainda, resultará na perda irreversível de fundos. Os endereços do Token Program são:

| Programa            | Endereço                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Incluir os endereços corretos numa lista de permissões protege contra tokens falsificados, mas não protege contra o envio para o _tipo_ errado de conta. Um endereço de destinatário pode ser uma carteira, uma token account, um mint ou um programa, e cada um exige um tratamento diferente. SOL nativo enviado para qualquer coisa que não seja uma carteira sai do controlo do remetente — perdido definitivamente no caso de um mint ou de um programa, e recuperável apenas pelo proprietário da conta no caso de uma token account — sem qualquer transação falhada que avise o utilizador.

<Callout type="warn" title="Valide os destinatários antes de enviar">
  Classifique cada endereço de destinatário antes de assinar uma transferência. Consulte [Verificar endereço](/docs/payments/send-payments/verify-address) para ver a árvore de decisão completa e o código de referência que distingue carteiras, token accounts, mints e programas.
</Callout>
