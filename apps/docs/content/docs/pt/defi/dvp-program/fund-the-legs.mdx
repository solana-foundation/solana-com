Financiar uma perna é uma simples `TransferChecked` para o escrow da perna, pelo que qualquer carteira ou
sistema de custódia capaz de enviar uma transferência de tokens pode financiá-la. Apenas a leitura do
registo da negociação antes do financiamento exige o cliente DvP. O programa verifica os
saldos do escrow somente na liquidação; nada valida a transferência quando ela chega,
por isso cada parte lê o registo da negociação antes de transferir.

Esta página dá continuidade a
[criar uma negociação](/docs/defi/dvp-program/create-a-trade); o cliente e os signatários
continuam os mesmos.

## Verificar os termos

Criar um registo não requer permissões, e os endereços de escrow derivam apenas do
registo e do mint, nunca dos termos. Uma transferência para um escrow pode
portanto chegar associada a termos com os quais nunca concordou, incluindo destinos de
liquidação que redirecionam os fundos da sua contraparte para um terceiro endereço.
Antes de financiar, leia a conta `SwapDvp` e confira-a com a negociação
acordada.

`verifySwapDvp` em TypeScript e `verify::decode_swap_dvp_account` em Rust
confirmam que a conta pertence ao programa DvP, tem exatamente 458 bytes e
está no endereço que os seus próprios campos derivam (`fetchSwapDvpChecked` executa apenas
as duas primeiras verificações). Os leitores simples `fetchSwapDvp` e `decodeSwapDvp`
não executam nenhuma destas verificações. As verificações de partes, montantes, prazos e destinos são
feitas pelo chamador em relação à negociação acordada.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { unwrapOption } from "@solana/kit";
    import { verifySwapDvp } from "./dvp";

    const trade = await verifySwapDvp(client.rpc, swapDvp);
    const t = trade.data;

    const expectedAmountA = 1_000_000_000n;
    const expectedAmountB = 998_500_000n;
    const expectedEarliestSettlement: bigint | null = null; // as agreed
    const expectedExpiry = 1_798_761_600n; // as agreed, unix seconds

    if (
      t.userA !== userA ||
      t.userB !== userB ||
      t.mintA !== mintA ||
      t.mintB !== mintB ||
      t.settlementAuthority !== settlementAuthority ||
      t.tokenProgramA !== tokenProgramA ||
      t.tokenProgramB !== tokenProgramB ||
      t.amountA !== expectedAmountA ||
      t.amountB !== expectedAmountB ||
      unwrapOption(t.earliestSettlementTimestamp) !== expectedEarliestSettlement ||
      t.expiryTimestamp !== expectedExpiry ||
      t.userASettlementDestination !== userA ||
      t.userBSettlementDestination !== userB
    ) {
      throw new Error("Stored terms do not match the agreed trade; do not fund");
    }

    if (t.expiryTimestamp <= BigInt(Math.floor(Date.now() / 1000)) + 60n) {
      throw new Error("Trade expires too soon to fund safely");
    }
    ```

  </Tab>

  <Tab value="Rust">
    ```rust
    use dvp_swap_program_client::verify::decode_swap_dvp_account;
    use solana_client::rpc_client::RpcClient;
    use solana_commitment_config::CommitmentConfig;

    // Read at confirmed: a record created moments ago is not visible at finalized yet.
    let rpc = RpcClient::new_with_commitment(
        "https://api.devnet.solana.com".to_string(),
        CommitmentConfig::confirmed(),
    );
    let account = rpc.get_account(&swap_dvp)?;
    let trade = decode_swap_dvp_account(&swap_dvp, &account)?;

    let expected_amount_a: u64 = 1_000_000_000;
    let expected_amount_b: u64 = 998_500_000;
    let expected_earliest_settlement: Option<i64> = None; // as agreed
    let expected_expiry: i64 = 1_798_761_600; // as agreed, unix seconds

    if trade.user_a != user_a
        || trade.user_b != user_b
        || trade.mint_a != mint_a
        || trade.mint_b != mint_b
        || trade.settlement_authority != settlement_authority
        || trade.token_program_a != token_program_a
        || trade.token_program_b != token_program_b
        || trade.amount_a != expected_amount_a
        || trade.amount_b != expected_amount_b
        || trade.earliest_settlement_timestamp != expected_earliest_settlement
        || trade.expiry_timestamp != expected_expiry
        || trade.user_a_settlement_destination != user_a
        || trade.user_b_settlement_destination != user_b
    {
        return Err("stored terms do not match the agreed trade; do not fund".into());
    }

    let now_seconds: i64 = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)?
        .as_secs() as i64;
    if trade.expiry_timestamp <= now_seconds + 60 {
        return Err("trade expires too soon to fund safely".into());
    }
    ```

  </Tab>
</Tabs>

Se o registo foi criado pela sua contraparte ou pela autoridade de liquidação,
compare cada campo com os termos que acordou fora do ledger. Se foi você quem o
criou, esta leitura confirma que ele chegou tal como foi enviado.

## Transferir para o escrow

Financie a perna exatamente com o montante acordado. O programa limita a liquidação a
`amount_x` e devolve qualquer excedente à parte da perna, pelo que o excedente não se perde,
mas acrescenta uma segunda transferência na liquidação e pode falhar com alguns
transfer hooks (consulte as notas abaixo).

Use `TransferChecked`, e não uma `Transfer` sem verificação. Os mints Token-2022 com
extensões que dependem da mint account, como Pausable, rejeitam uma transferência
que não a forneça, e um mint com transfer hook exige que as contas do hook
sejam resolvidas e anexadas da mesma forma que em qualquer outra transferência desse
token.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    A parte da perna de ativo, assinando como `userASigner`, financia o escrow A:

    ```ts
    import {
      findAssociatedTokenPda,
      getTransferCheckedInstruction,
    } from "@solana-program/token-2022";

    const [userAAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: userA,
      tokenProgram: tokenProgramA,
    });
    const [userBAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: userB,
      tokenProgram: tokenProgramB,
    });

    const fundAssetLeg = getTransferCheckedInstruction({
      source: userAAtaA,
      mint: mintA,
      destination: escrowA,
      authority: userASigner,
      amount: t.amountA,
      decimals: 6,
    }, { programAddress: tokenProgramA });

    await client.sendTransaction([fundAssetLeg]);
    ```

    A parte da perna de numerário faz o mesmo para o escrow B com `userBAtaB`, `mintB`,
    `userBSigner`, `t.amountB` e `{ programAddress: tokenProgramB }`.

  </Tab>

  <Tab value="Rust">
    ```rust

    use spl_token_2022_interface::instruction::transfer_checked;

    let fund_asset_leg = transfer_checked(
        &token_program_a,
        &user_a_ata_a,
        &mint_a,

        &user_a,
        &[],
    ```

    A parte da perna de numerário cria a mesma instrução para o escrow B com `mint_b`,
    `user_b` e `trade.amount_b`.

  </Tab>

Uma transferência de financiamento vista em [`confirmed`](/docs/rpc#configuring-state-commitment)
ainda pode ser substituída. O programa lê o saldo do escrow on-chain na
liquidação, por isso uma instrução Settle enviada com base numa transferência de financiamento que não chegou falha
com `LegNotFunded` e nada é movimentado; o custo é uma Settle falhada e uma nova tentativa.
Considere uma perna como financiada quando a sua transferência estiver `finalized`.

## Notas

- **Pernas em SOL embrulhado (wrapped SOL).** O programa lê o saldo de um escrow nativo depois de
  o sincronizar, por isso os lamports enviados para um escrow de wrapped SOL através de uma transferência do sistema
  são contabilizados. Nunca envie SOL para um escrow de qualquer outro mint: o programa não consegue
  devolvê-lo, e ele vai para quem fechar a conta.
- **Mints com restrições.** Num mint com Default Account State congelado, o escrow é
  criado congelado e a transferência falha até o emissor o descongelar ou o admitir. A
  [visão geral](/docs/defi/dvp-program#mint-configuration-constraints) descreve
  a interação com o Token ACL.
- **Transfer hooks.** Financie escrows com hooks exatamente com o montante acordado. Se
  um excedente obrigar a um reembolso na liquidação, o reembolso reutiliza as contas do hook
  da perna com um destino e um montante diferentes, o que alguns hooks rejeitam. A
  recuperação consiste em Reclaim, voltar a financiar com o montante exato e liquidar novamente.
- **Financiar após o vencimento.** Nada impede uma transferência após `expiry_timestamp`. Ela
  chega, a liquidação já não é possível, e a parte da perna recupera o valor com
  Reclaim enquanto a negociação estiver aberta ou com Recover depois de ela fechar. Consulte
  [desfazer uma negociação](/docs/defi/dvp-program/unwind-a-trade).
- **Quem financia primeiro.** O programa não ordena as duas pernas. A ordem
  é decidida pelas partes; qualquer um dos lados pode recuperar a sua própria perna a qualquer momento
  antes da liquidação, a menos que uma autoridade do mint (congelamento, pausa ou transfer hook)
  bloqueie o escrow.
