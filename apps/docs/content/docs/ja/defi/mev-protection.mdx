# Jito DontFrontによるMEV対策

Maximal Extractable Value(MEV)とは、ブロック内のトランザクションの並べ替え、挿入、除外によって獲得できる価値のことです。MEVは特定のチェーンに限ったものではなく、ブロックプロデューサーがトランザクションの順序を制御するあらゆるブロックチェーンに共通する性質です。アービトラージのように、DEX間の価格差を是正して市場の効率性を保つ役割を果たすMEVもあります。一方、サンドイッチ攻撃のようにユーザーから直接価値を抜き取るものもあります。DeFiアプリケーションを構築する開発者にとって、これは取引の約定価格の悪化や利益の損失につながる可能性があります。

このガイドでは、有害なMEVの代表例であるサンドイッチ攻撃と、Jitoの`dontfront`機能を使ってそれを軽減する方法に焦点を当てます。

事前に読むことをおすすめします:
[Jito Bundles](https://solana.com/docs/tools/transaction-landing#jito-bundles)

## SolanaにおけるMEV

Solanaのアーキテクチャは、パブリックなmempoolを持つチェーンと比べて、MEVの攻撃対象領域をすでに縮小しています。トランザクションは共有mempoolに滞留するのではなく、次のブロックリーダーに直接転送され、未処理のトランザクションは約150ブロック(約1分)後に失効します。これにより、サーチャーが保留中のトランザクションを観測して対応できる時間は大幅に狭められています。

とはいえ、MEVの抽出は依然として行われています。最適化されたインフラとvalidatorへの直接接続を持つサーチャーは、トランザクションの流れを観測して対応できます。SolanaにおけるMEV活動の大部分は、アトミックなアービトラージ、つまり単一のトランザクションでDEX間の価格差を是正するボットによるものです。この種のMEVは市場間の価格の一貫性を高めるため、一般的に有益です。

開発者が積極的に防御すべきなのは、有害なタイプであるサンドイッチ攻撃です。

## サンドイッチ攻撃とは?

サンドイッチ攻撃は、サーチャーが保留中のスワップを検知し、トランザクションの順序を悪用することで発生します:

1. **フロントラン**: サーチャーがあなたの取引の前にトークンを購入し、価格を押し上げます
2. **あなたの取引が実行される**: 想定より不利な価格で約定します
3. **バックラン**: サーチャーがあなたの取引の後にトークンを売却し、差額を手に入れます

Solanaでは、これは[Jitoバンドル](https://docs.jito.wtf/lowlatencytxnsend/#what-are-bundles)を通じて行われる可能性があります。サーチャーは`[frontrun_tx, your_tx, backrun_tx]`のようなトランザクションのバンドルを送信し、ブロックエンジンがそれらを順番どおりにアトミックに実行します。被害者は不利な約定価格となり、サーチャーはスプレッドから利益を得ます。

## DontFrontの仕組み

[DontFront](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation)は、バンドル内でサーチャーがあなたのトランザクションより前にトランザクションを配置することを防ぐ、Jitoブロックエンジンの機能です。

仕組みは次のとおりです。`jitodontfront`で始まる有効なSolanaの公開鍵を、トランザクション内の任意のinstructionに追加します。ブロックエンジンはこのプレフィックスを認識し、**あなたのトランザクションを含むバンドルでは、そのトランザクションを必ずインデックス0に配置する**というルールを適用します。

```
Without dontfront:  [frontrun_tx, your_tx, backrun_tx]  ← sandwich possible
With dontfront:     [your_tx, ...]                       ← your tx must be first
```

### 手順

1. **`jitodontfront`で始まる有効なアドレスを選びます**(例: `jitodontfront111111111111111111111111111111`)。このアカウントはオンチェーンに存在する必要はなく、読み取りも書き込みも行われません。文字列が有効なアドレスかどうかは、@solana/kitの[`assertIsAddress`](https://www.solanakit.com/api/functions/assertIsAddress)関数で検証するか、Solana Explorerにアドレスを入力して解決されるかを確認できます。[無効なアドレス](https://explorer.solana.com/address/jitodontfront11111111111111111111111111111INVALID)の例はこちらです。

2. **読み取り専用かつ非署名者のアカウントとして**、トランザクション内の任意のinstructionに追加します。ランディング速度を最適にするため、読み取り専用に設定してください。ほとんどのプログラム(System Programを含む)は、想定以外の余分なアカウントを無視します。

3. **Jitoブロックエンジン経由で送信します**:
   - `sendTransaction`:
     `https://mainnet.block-engine.jito.wtf/api/v1/transactions`
   - `sendBundle`: `https://mainnet.block-engine.jito.wtf/api/v1/bundles`

   ドキュメント: [sendTransaction](https://docs.jito.wtf/lowlatencytxnsend/#sendtransaction)および[sendBundle](https://docs.jito.wtf/lowlatencytxnsend/#sendbundle)

4. ブロックエンジンが`jitodontfront`プレフィックスを検出し、順序ルールを適用します。

### ブロックエンジンでの処理

ブロックエンジンは、`jitodontfront`アカウントを含むトランザクションを検出すると、次のように処理します:

- `sendTransaction`経由の場合: トランザクションは保護されます。どのバンドルも、そのトランザクションより前に別のトランザクションを配置できません
- `sendBundle`経由の場合: トランザクションはインデックス0に配置されている必要があり、そうでない場合はバンドル全体が拒否されます

`jitodontfront`アカウントを含まないトランザクションやバンドルには影響しません。

## バンドルの順序ルール

これらのルールは、`jitodontfront`トランザクションがバンドルに含まれている場合に適用されます。

### 許可されるパターン

```
[tx_with_dontfront, tip]
[tx_with_dontfront, arbitrage, tip]
[tx_with_dontfront_signer1, tx_with_dontfront_signer1_and_signer2, tip]
```

### 1つのバンドルに複数のDontFrontトランザクションを含める場合

1つのバンドルに複数のdontfrontトランザクションを含めることは、**次の両方**の条件を満たす場合に許可されます:

1. すべてのdontfrontトランザクションが、バンドルの**先頭に連続して**配置されている
2. 各dontfrontトランザクションが、最初のdontfrontトランザクションと**少なくとも1つの署名者を共有している**

```
✅ [txA_df, txB_df, txC_df, arbitrage, tip]
   (contiguous at front, overlapping signers)

✅ [txA_df_signer1_signer2, txB_df_signer1_signer3, txC_df_signer2_signer4]
   (each shares a signer with txA)
```

### 拒否されるパターン

```
❌ [tip, tx_with_dontfront]
   → dontfront tx is not at index 0

❌ [txA_df_signer1, txB_df_signer2]
   → no overlapping signer between txA and txB

❌ [trade, tx_with_dontfront, arbitrage, tip]
   → dontfront tx is not at the front
```

## 統合例

簡単なコードレシピについては、[MEV Protectionクックブックのエントリ](/developers/cookbook/transactions/mev-protection)をご覧ください。

### TypeScript(@solana/kit)

基本となるのは、任意のinstructionにdontfrontアカウントを追加するヘルパーです:

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
import {
  address,
  AccountRole,
  type Instruction,
  type Address
} from "@solana/kit";

const DONT_FRONT: Address = address(
  "jitodontfront111111111111111111111111111111"
);

// !mark(1:9)
function withDontFront(ix: Instruction): Instruction {
  return {
    ...ix,
    accounts: [
      ...(ix.accounts ?? []),
      { address: DONT_FRONT, role: AccountRole.READONLY }
    ]
  };
}
```

```rs !! title="Rust"
use solana_sdk::{
    instruction::{AccountMeta, Instruction},
    pubkey::Pubkey,
};
use std::str::FromStr;

const DONT_FRONT_ACCOUNT: &str =
    "jitodontfront111111111111111111111111111111";

// !mark(1:6)
fn with_dontfront(ix: &mut Instruction) {
    let dontfront =
        Pubkey::from_str(DONT_FRONT_ACCOUNT).unwrap();
    ix.accounts
        .push(AccountMeta::new_readonly(dontfront, false));
}
```

</CodeTabs>

その後、署名済みトランザクションを、標準のRPCノードではなくJitoブロックエンジンに送信します。エンコードには必ずbase64を使用してください。JitoのAPIでは、Base58は非推奨です。

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
// !mark(1:2)
const response = await fetch(
  "https://mainnet.block-engine.jito.wtf/api/v1/transactions",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      jsonrpc: "2.0",
      id: 1,
      method: "sendTransaction",
      // !mark
      params: [base64Tx, { encoding: "base64" }]
    })
  }
);
```

```rs !! title="Rust"
let serialized = bincode::serialize(&tx)?;
// !mark
let base64_tx = base64::engine::general_purpose::STANDARD
    .encode(&serialized);

// !mark(1:2)
let response = client
    .post("https://mainnet.block-engine.jito.wtf/api/v1/transactions")
    .json(&serde_json::json!({
        "jsonrpc": "2.0",
        "id": 1,
        "method": "sendTransaction",
        "params": [base64_tx, {"encoding": "base64"}]
    }))
    .send()
    .await?;
```

## ベストプラクティス

DontFrontは保護レイヤーの1つにすぎません。堅牢なMEV対策では、複数のアプローチを組み合わせます:

### トランザクションレベルの保護

- **スリッページ許容値を厳しく設定する。** サンドイッチ攻撃に対する最も効果的な防御策は、スワップで許容するスリッページを制限することです。スリッページの許容幅が小さいほど攻撃者が得られる利益幅が減り、あなたのトランザクションはサンドイッチの標的として魅力が薄れます。

- **適切なチップとプライオリティフィーを設定する。** 混雑時には、チップとプライオリティフィーを高くすることで、トランザクションやバンドルが素早く着地する可能性が高まり、サーチャーが動ける時間を短縮できます。適切なチップの設定方法については、Jitoのドキュメント[Tip Amounts](https://docs.jito.wtf/lowlatencytxnsend/#tip-amount)をご覧ください。

- **コンピュートユニットの使用量を最適化する。** 各ブロックで利用できるコンピュートユニットの数には限りがあり(アカウントごとにもブロックあたりの上限があります)、トランザクションやバンドルがブロックに含まれる可能性を最大化するには、コンピュートユニットの使用量を最適化する必要があります。詳細は[Solanaでコンピュート使用量を最適化する方法](/developers/cookbook/transactions/optimize-compute)のガイドをご覧ください。

### DontFront固有の対策

1. **dontfrontアカウントを読み取り専用に設定する。** 書き込み可能に設定しても動作しますが、読み取り専用にすると[ランディング速度が最適化](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation)されます。

2. **アプリケーションごとに固有のdontfront pubkeyを使用する。** `jitodontfront`で始まるpubkeyであればどれでも機能します。固有のバリエーション(例: `jitodontfront111111111111111111111111111123`)を使用すると、オンチェーンデータを調べる際にアプリごとの利用状況を区別できます。

3. **DontFrontはAddress Lookup Tableをサポートしています。** dontfrontアカウントはALT経由で含めることができます。ただし、チップアカウントにはALTを使用しないでください。

## 制限事項

- **ブロックエンジンのみ。** DontFrontはJitoブロックエンジンによって適用されます。validatorに直接送信されたトランザクション(Jitoを経由しないもの)は保護されません。

- **保証ではありません。** Jitoのドキュメントより: _「この機能はサンドイッチ攻撃の軽減に役立つ可能性がありますが、その効果は保証されておらず、第三者によるものを含む、トランザクション順序のあらゆるバリエーションに対する解決策ではありません。」_

- **MainnetおよびTestnetのみ。** これはJitoブロックエンジンの機能です。devnetやlocalhostでは動作しません。
