# Jito DontFront によるMEV対策

Maximal Extractable Value(MEV、最大抽出可能価値)とは、ブロック内のトランザクションの並べ替え、挿入、除外によって獲得できる価値を指します。MEV は特定のチェーンに固有のものではなく、ブロックプロデューサーがトランザクションの順序を制御するあらゆるブロックチェーンに共通する本質的な性質です。アービトラージのように、DEX 間の価格差を是正して市場の効率性を保つ助けとなる MEV もあります。一方、サンドイッチ攻撃のように、ユーザーから直接価値を奪うものもあります。DeFi アプリケーションを構築する開発者にとっては、取引の約定条件の悪化や利益の損失につながる可能性があります。

このガイドでは、有害な MEV の代表例であるサンドイッチ攻撃と、Jito の `dontfront` 機能を使ってそれを軽減する方法に焦点を当てます。

事前に読んでおくことをおすすめします:
[Jito バンドル](https://solana.com/docs/tools/transaction-landing#jito-bundles)

## Solana における MEV

Solana のアーキテクチャは、パブリックな mempool を持つチェーンと比べて、MEV の攻撃対象領域をすでに小さくしています。トランザクションは共有の mempool に留まらず、次のブロックリーダーに直接転送されます。また、未処理のトランザクションは約150ブロック(約1分)後に期限切れとなります。これにより、サーチャーが保留中のトランザクションを観測して対応できる時間枠が大幅に狭まります。

とはいえ、MEV の抽出は依然として行われています。最適化されたインフラと validator への直接接続を持つサーチャーは、トランザクションフローを観測し、それに対応できます。Solana における MEV 活動の多くは、単一のトランザクションで DEX 間の価格差を是正するボットによるアトミックなアービトラージです。この種の MEV は、市場間の価格の一貫性を高めるため、一般的に有益です。

開発者が積極的に防御すべきなのは、有害な種類であるサンドイッチ攻撃です。

## サンドイッチ攻撃とは?

サンドイッチ攻撃は、サーチャーが保留中のスワップを検知し、トランザクションの順序を悪用することで発生します:

1. **フロントラン**: サーチャーがあなたの取引の前にトークンを購入し、価格を押し上げます
2. **あなたの取引が実行される**: 想定よりも不利な価格で約定します
3. **バックラン**: サーチャーがあなたの取引の後にトークンを売却し、差額を手にします

Solana では、[Jito バンドル](https://docs.jito.wtf/lowlatencytxnsend/#what-are-bundles)を通じてこれが可能になります。サーチャーは `[frontrun_tx, your_tx, backrun_tx]` のようなトランザクションのバンドルを送信し、ブロックエンジンはそれらを順序どおりにアトミックに実行します。被害者は不利な約定価格となり、サーチャーはスプレッドから利益を得ます。

## DontFront の仕組み

[DontFront](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation) は、Jito ブロックエンジンの機能で、バンドル内であなたのトランザクションより前にサーチャーがトランザクションを配置することを防ぎます。

仕組みは次のとおりです。`jitodontfront` で始まる有効な Solana 公開鍵を、トランザクション内の任意の instruction に追加します。ブロックエンジンはこのプレフィックスを認識し、**あなたのトランザクションを含むバンドルでは、そのトランザクションを必ずインデックス0に配置する**というルールを適用します。

```
Without dontfront:  [frontrun_tx, your_tx, backrun_tx]  ← sandwich possible
With dontfront:     [your_tx, ...]                       ← your tx must be first
```

### ステップごとの手順

1. **有効なアドレスを選ぶ**: `jitodontfront` で始まるアドレス(例: `jitodontfront111111111111111111111111111111`)を選びます。このアカウントがオンチェーンに存在している必要はなく、読み取りも書き込みも行われません。文字列が有効なアドレスかどうかは、@solana/kit の [`assertIsAddress`](https://www.solanakit.com/api/functions/assertIsAddress) 関数で確認できます。または、Solana Explorer にアドレスを入力して解決されるかどうかを確認することもできます。こちらは[無効なアドレス](https://explorer.solana.com/address/jitodontfront11111111111111111111111111111INVALID)の例です。

2. **読み取り専用かつ非署名者のアカウントとして追加する**: トランザクション内の任意の instruction に追加します。ランディング速度を最適にするため、読み取り専用にしてください。ほとんどのプログラム(System Program を含む)は、想定している以外の余分なアカウントを無視します。

3. **Jito ブロックエンジン経由で送信する**:
   - `sendTransaction`: `https://mainnet.block-engine.jito.wtf/api/v1/transactions`
   - `sendBundle`: `https://mainnet.block-engine.jito.wtf/api/v1/bundles`

   ドキュメント: [sendTransaction](https://docs.jito.wtf/lowlatencytxnsend/#sendtransaction) および [sendBundle](https://docs.jito.wtf/lowlatencytxnsend/#sendbundle)

4. ブロックエンジンは `jitodontfront` プレフィックスを検出し、順序ルールを適用します。

### ブロックエンジンでの処理

ブロックエンジンは、`jitodontfront` アカウントを含むトランザクションを検出すると、次のように処理します:

- `sendTransaction` 経由の場合: トランザクションは保護されます。どのバンドルも、他のトランザクションをその前に配置することはできません
- `sendBundle` 経由の場合: トランザクションはインデックス0に配置されている必要があり、そうでない場合はバンドル全体が拒否されます

`jitodontfront` アカウントを含まないトランザクションとバンドルは影響を受けません。

## バンドルの順序ルール

これらのルールは、`jitodontfront` トランザクションがバンドル内に含まれる場合に適用されます。

### 許可されるパターン

```
[tx_with_dontfront, tip]
[tx_with_dontfront, arbitrage, tip]
[tx_with_dontfront_signer1, tx_with_dontfront_signer1_and_signer2, tip]
```

### 1つのバンドル内に複数の DontFront トランザクションがある場合

1つのバンドル内に複数の dontfront トランザクションを含めることは、**両方**の条件を満たす場合に許可されます:

1. すべての dontfront トランザクションが、バンドルの**先頭に連続して**配置されている
2. 各 dontfront トランザクションが、最初の dontfront トランザクションと**少なくとも1つの署名者**を共有している

```
✅ [txA_df, txB_df, txC_df, arbitrage, tip]
   (contiguous at front, overlapping signers)

✅ [txA_df_signer1_signer2, txB_df_signer1_signer3, txC_df_signer2_signer4]
   (each shares a signer with txA)
```

### 拒否されるパターン

```
❌ [tip, tx_with_dontfront]
   → dontfront tx is not at index 0

❌ [txA_df_signer1, txB_df_signer2]
   → no overlapping signer between txA and txB

❌ [trade, tx_with_dontfront, arbitrage, tip]
   → dontfront tx is not at the front
```

## 統合例

手早くコードのレシピを確認したい場合は、[MEV 対策のクックブックエントリ](/developers/cookbook/transactions/mev-protection)を参照してください。

### TypeScript(@solana/kit)

中心となるのは、任意の instruction に dontfront アカウントを追加するヘルパーです:

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
import {
  address,
  AccountRole,
  type Instruction,
  type Address
} from "@solana/kit";

const DONT_FRONT: Address = address(
  "jitodontfront111111111111111111111111111111"
);

// !mark(1:9)
function withDontFront(ix: Instruction): Instruction {
  return {
    ...ix,
    accounts: [
      ...(ix.accounts ?? []),
      { address: DONT_FRONT, role: AccountRole.READONLY }
    ]
  };
}
```

```rs !! title="Rust"
use solana_sdk::{
    instruction::{AccountMeta, Instruction},
    pubkey::Pubkey,
};
use std::str::FromStr;

const DONT_FRONT_ACCOUNT: &str =
    "jitodontfront111111111111111111111111111111";

// !mark(1:6)
fn with_dontfront(ix: &mut Instruction) {
    let dontfront =
        Pubkey::from_str(DONT_FRONT_ACCOUNT).unwrap();
    ix.accounts
        .push(AccountMeta::new_readonly(dontfront, false));
}
```

</CodeTabs>

その後、署名済みのトランザクションを、標準の RPC ノードではなく Jito ブロックエンジンに送信します。エンコーディングには必ず base64 を使用してください。Jito の API では Base58 は非推奨です。

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
// !mark(1:2)
const response = await fetch(
  "https://mainnet.block-engine.jito.wtf/api/v1/transactions",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      jsonrpc: "2.0",
      id: 1,
      method: "sendTransaction",
      // !mark
      params: [base64Tx, { encoding: "base64" }]
    })
  }
);
```

```rs !! title="Rust"
let serialized = bincode::serialize(&tx)?;
// !mark
let base64_tx = base64::engine::general_purpose::STANDARD
    .encode(&serialized);

// !mark(1:2)
let response = client
    .post("https://mainnet.block-engine.jito.wtf/api/v1/transactions")
    .json(&serde_json::json!({
        "jsonrpc": "2.0",
        "id": 1,
        "method": "sendTransaction",
        "params": [base64_tx, {"encoding": "base64"}]
    }))
    .send()
    .await?;
```

## ベストプラクティス

DontFront は保護レイヤーの1つにすぎません。堅牢な MEV 対策戦略では、複数のアプローチを組み合わせます:

### トランザクションレベルの保護

- **スリッページ許容値を厳しく設定する**: サンドイッチ攻撃に対する最も効果的な防御策は、スワップで許容するスリッページを制限することです。スリッページの許容幅が小さいほど、攻撃者が得られる利益幅が減り、あなたのトランザクションはサンドイッチの標的として魅力が低くなります。

- **適切なチップと優先手数料を設定する**: 混雑時には、チップと優先手数料を高くすることで、トランザクションやバンドルが素早くランディングする可能性が高まり、サーチャーが介入できる時間枠が狭まります。適切なチップの設定方法の詳細については、Jito のドキュメント[Tip Amounts](https://docs.jito.wtf/lowlatencytxnsend/#tip-amount)を参照してください。

- **コンピュートユニットの使用量を最適化する**: 各ブロックで利用可能なコンピュートユニットの数には上限があります(アカウントごとにもブロックあたりの上限があります)。トランザクションやバンドルがブロックに含まれる可能性を最大化するには、コンピュートユニットの使用量を最適化する必要があります。詳細は[Solana でコンピュート使用量を最適化する方法](/developers/cookbook/transactions/optimize-compute)ガイドを参照してください。

### DontFront 固有の注意点

1. **dontfront アカウントを読み取り専用にする**: 書き込み可能として指定しても動作しますが、読み取り専用にすると[ランディング速度が最適化されます](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation)。

2. **アプリケーションごとに固有の dontfront pubkey を使用する**: `jitodontfront` で始まる pubkey であればどれでも動作します。固有のバリエーション(例: `jitodontfront111111111111111111111111111123`)を使用すると、オンチェーンデータを調べる際に、アプリごとの利用状況を区別できます。

3. **DontFront は Address Lookup Table をサポートしています**: dontfront アカウントは ALT 経由で含めることができます。ただし、チップアカウントには ALT を使用しないでください。

## 制限事項

- **ブロックエンジンのみ**: DontFront は Jito ブロックエンジンによって適用されます。Jito を経由せず validator に直接送信されたトランザクションは保護されません。

- **保証ではない**: Jito のドキュメントには次のとおり記載されています: _「この機能はサンドイッチ攻撃の軽減に役立つ可能性がありますが、その効果は保証されておらず、第三者が行うものを含め、トランザクション順序のあらゆるバリエーションに対する解決策でもありません。」_

- **Mainnet/Testnet のみ**: これは Jito ブロックエンジンの機能です。devnet や localhost では動作しません。
