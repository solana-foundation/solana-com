入金はレッグのエスクローへのプレーンな `TransferChecked` なので、トークン転送を送信できるウォレットやカストディシステムであれば、どれでもレッグに入金できます。入金前のトレードレコードの読み取りにのみ、DvPクライアントが必要です。プログラムがエスクロー残高を確認するのは決済時のみで、転送が着金した時点では何も検証されません。そのため、各当事者は転送の前にトレードレコードを読み取ってください。

このページは[トレードの作成](/docs/defi/dvp-program/create-a-trade)の続きです。クライアントと署名者はそのまま引き継ぎます。

## 条件を検証する

レコードの作成はパーミッションレスで、エスクローアドレスはレコードとmintのみから導出され、条件には依存しません。そのため、合意していない条件のトレードに対してエスクローへの転送が着金してしまう可能性があり、これには相手方の受取分を第三のアドレスにリダイレクトする決済先も含まれます。入金する前に `SwapDvp` アカウントを読み取り、合意したトレードと照合してください。

TypeScriptの `verifySwapDvp` とRustの `verify::decode_swap_dvp_account` は、アカウントがDvPプログラムの所有であること、サイズがちょうど458バイトであること、そしてアカウント自身のフィールドから導出されるアドレスに存在することを確認します(`fetchSwapDvpChecked` が実行するのは最初の2つのチェックのみです)。プレーンな `fetchSwapDvp` と `decodeSwapDvp` のリーダーは、これらのいずれも確認しません。当事者、金額、時刻、決済先に関するチェックは、呼び出し側が合意したトレードに照らして行います。

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { unwrapOption } from "@solana/kit";
    import { verifySwapDvp } from "./dvp";

    const trade = await verifySwapDvp(client.rpc, swapDvp);
    const t = trade.data;

    const expectedAmountA = 1_000_000_000n;
    const expectedAmountB = 998_500_000n;
    const expectedEarliestSettlement: bigint | null = null; // as agreed
    const expectedExpiry = 1_798_761_600n; // as agreed, unix seconds

    if (
      t.userA !== userA ||
      t.userB !== userB ||
      t.mintA !== mintA ||
      t.mintB !== mintB ||
      t.settlementAuthority !== settlementAuthority ||
      t.tokenProgramA !== tokenProgramA ||
      t.tokenProgramB !== tokenProgramB ||
      t.amountA !== expectedAmountA ||
      t.amountB !== expectedAmountB ||
      unwrapOption(t.earliestSettlementTimestamp) !== expectedEarliestSettlement ||
      t.expiryTimestamp !== expectedExpiry ||
      t.userASettlementDestination !== userA ||
      t.userBSettlementDestination !== userB
    ) {
      throw new Error("Stored terms do not match the agreed trade; do not fund");
    }

    if (t.expiryTimestamp <= BigInt(Math.floor(Date.now() / 1000)) + 60n) {
      throw new Error("Trade expires too soon to fund safely");
    }
    ```

  </Tab>

    ```rust
        || trade.mint_a != mint_a
        || trade.mint_b != mint_b
        || trade.settlement_authority != settlement_authority
        || trade.token_program_a != token_program_a
        || trade.token_program_b != token_program_b
        || trade.amount_a != expected_amount_a
        || trade.amount_b != expected_amount_b
        || trade.earliest_settlement_timestamp != expected_earliest_settlement
        || trade.expiry_timestamp != expected_expiry
        || trade.user_a_settlement_destination != user_a
        || trade.user_b_settlement_destination != user_b

        return Err("stored terms do not match the agreed trade; do not fund".into());

        .duration_since(std::time::UNIX_EPOCH)?
        .as_secs() as i64;
    if trade.expiry_timestamp <= now_seconds + 60 {
        return Err("trade expires too soon to fund safely".into());
    }
    ```

レコードが相手方または決済権限者によって作成された場合は、台帳外で合意した条件とすべてのフィールドを照合してください。自分で作成した場合は、この読み取りで送信したとおりに登録されたことを確認できます。

## エスクローへ転送する

レッグには合意した金額ちょうどを入金してください。プログラムは決済を `amount_x` に制限し、超過分はレッグの当事者に返却するため、超過分が失われることはありません。ただし、決済時に追加の転送が発生し、一部のトランスファーフックでは失敗する可能性があります(下記の注意事項を参照)。

チェックなしの `Transfer` ではなく、`TransferChecked` を使用してください。Pausableなど、mint account に依存する拡張機能を持つToken-2022のmintは、それが指定されていない転送を拒否します。また、トランスファーフックを持つmintでは、他のトークンの転送と同様に、フックのアカウントを解決して追加する必要があります。

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    アセットレッグの当事者が `userASigner` として署名し、エスクローAに入金します:

    ```ts
    import {
      findAssociatedTokenPda,
      getTransferCheckedInstruction,
    } from "@solana-program/token-2022";

    const [userAAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: userA,
      tokenProgram: tokenProgramA,
    });
    const [userBAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: userB,
      tokenProgram: tokenProgramB,
    });

    const fundAssetLeg = getTransferCheckedInstruction({
      source: userAAtaA,
      mint: mintA,
      destination: escrowA,
      authority: userASigner,
      amount: t.amountA,
      decimals: 6,
    }, { programAddress: tokenProgramA });

    await client.sendTransaction([fundAssetLeg]);
    ```

    キャッシュレッグの当事者は、`userBAtaB`、`mintB`、`userBSigner`、`t.amountB`、`{ programAddress: tokenProgramB }` を使って、エスクローBに対して同様に入金します。

  </Tab>

[`confirmed`](/docs/rpc#configuring-state-commitment) で確認された入金転送も、後から置き換えられる可能性があります。プログラムは決済時にオンチェーンでエスクロー残高を読み取るため、着金しなかった入金転送に対して送信したSettleは `LegNotFunded` で失敗し、資産は一切移動しません。コストは失敗したSettleと再試行のみです。転送が `finalized` になった時点で、そのレッグを入金済みとみなしてください。

## 注意事項

- **ラップドSOLのレッグ。** プログラムはネイティブエスクローの残高を同期した後に読み取るため、システム転送でwrapped-SOLエスクローに送られたlamportsもカウントされます。他のmintのエスクローには、SOLを絶対に送らないでください。プログラムは返却できず、アカウントをクローズした人の手に渡ります。
- **ゲート付きmint。** Default Account Stateがfrozenのmintでは、エスクローがfrozen状態で作成され、発行者がthawするか許可するまで転送は失敗します。Token ACLとのやり取りについては[概要](/docs/defi/dvp-program#mint-configuration-constraints)で説明しています。
- **トランスファーフック。** フック付きのエスクローには、合意した金額ちょうどを入金してください。超過分により決済時に返金が必要になると、返金ではレッグのフックアカウントが異なる宛先と金額で再利用されますが、一部のフックはこれを拒否します。復旧方法は、Reclaimを実行し、正確な金額で再入金して、再度決済することです。
- **期限後の入金。** `expiry_timestamp` を過ぎても転送自体は止められません。転送は着金しますが決済はもうできず、レッグの当事者は、トレードがオープンの間はReclaim、クローズ後はRecoverで回収します。[トレードの巻き戻し](/docs/defi/dvp-program/unwind-a-trade)を参照してください。
- **どちらが先に入金するか。** プログラムは2つのレッグの順序を制御しません。順序は当事者間で決めるものです。mint権限者(freeze、pause、またはトランスファーフック)がエスクローをブロックしていない限り、どちらの側も決済前ならいつでも自分のレッグをreclaimできます。
