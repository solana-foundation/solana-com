入金は、レッグのエスクローへの通常の `TransferChecked` で行うため、トークン転送を送信できるウォレットやカストディシステムであれば、どれでもレッグに入金できます。入金前の取引レコードの読み取りにのみ、DvPクライアントが必要です。プログラムがエスクロー残高を確認するのは決済時のみで、転送が着金した時点では何も検証されません。そのため、各当事者は転送前に取引レコードを読み取ります。

このページは[取引を作成する](/docs/defi/dvp-program/create-a-trade)の続きです。クライアントと署名者はそのまま引き継ぎます。

## 条件を検証する

レコードの作成には許可が不要で、エスクローのアドレスはレコードとmintのみから導出され、条件には依存しません。そのため、合意していない条件に対してエスクローへの転送が着金してしまう可能性があり、その中には、相手方の受取分を第三のアドレスにリダイレクトする決済先も含まれます。入金する前に `SwapDvp` アカウントを読み取り、合意した取引と照合してください。

TypeScriptの `verifySwapDvp` とRustの `verify::decode_swap_dvp_account` は、アカウントがDvPプログラムによって所有されていること、サイズがちょうど458バイトであること、自身のフィールドから導出されるアドレスに存在することを確認します(`fetchSwapDvpChecked` は最初の2つのチェックのみを実行します)。通常の `fetchSwapDvp` および `decodeSwapDvp` リーダーは、これらをいずれもチェックしません。当事者、金額、時刻、決済先のチェックは、呼び出し側が合意した取引と照らして行います。

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { unwrapOption } from "@solana/kit";
    import { verifySwapDvp } from "./dvp";

    const trade = await verifySwapDvp(client.rpc, swapDvp);
    const t = trade.data;

    const expectedAmountA = 1_000_000_000n;
    const expectedAmountB = 998_500_000n;
    const expectedEarliestSettlement: bigint | null = null; // as agreed
    const expectedExpiry = 1_798_761_600n; // as agreed, unix seconds

    if (
      t.userA !== userA ||
      t.userB !== userB ||
      t.mintA !== mintA ||
      t.mintB !== mintB ||
      t.settlementAuthority !== settlementAuthority ||
      t.tokenProgramA !== tokenProgramA ||
      t.tokenProgramB !== tokenProgramB ||
      t.amountA !== expectedAmountA ||
      t.amountB !== expectedAmountB ||
      unwrapOption(t.earliestSettlementTimestamp) !== expectedEarliestSettlement ||
      t.expiryTimestamp !== expectedExpiry ||
      t.userASettlementDestination !== userA ||
      t.userBSettlementDestination !== userB
    ) {
      throw new Error("Stored terms do not match the agreed trade; do not fund");
    }

    if (t.expiryTimestamp <= BigInt(Math.floor(Date.now() / 1000)) + 60n) {
      throw new Error("Trade expires too soon to fund safely");
    }
    ```

  </Tab>

    ```rust
    use solana_client::rpc_client::RpcClient;

    let expected_amount_b: u64 = 998_500_000;

    let expected_expiry: i64 = 1_798_761_600; // as agreed, unix seconds

        || trade.mint_a != mint_a
        || trade.mint_b != mint_b
        || trade.settlement_authority != settlement_authority
        || trade.token_program_a != token_program_a
        || trade.token_program_b != token_program_b
        || trade.amount_a != expected_amount_a
        || trade.amount_b != expected_amount_b
        || trade.earliest_settlement_timestamp != expected_earliest_settlement
        || trade.expiry_timestamp != expected_expiry
        || trade.user_a_settlement_destination != user_a
        || trade.user_b_settlement_destination != user_b
    {
        return Err("stored terms do not match the agreed trade; do not fund".into());
    }

    let now_seconds: i64 = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)?
        .as_secs() as i64;
    if trade.expiry_timestamp <= now_seconds + 60 {
        return Err("trade expires too soon to fund safely".into());
    }
    ```

レコードを相手方または決済権限者が作成した場合は、台帳外で合意した条件とすべてのフィールドを照合してください。自分で作成した場合は、この読み取りで送信どおりに着金したことを確認できます。

## エスクローへ転送する

レッグには、合意した金額ちょうどを入金してください。プログラムは決済額を `amount_x` に制限し、超過分はレッグの当事者に返却するため、超過分が失われることはありませんが、決済時に追加の転送が発生し、一部のトランスファーフックでは失敗する可能性があります(下記の注意事項を参照)。

チェックなしの `Transfer` ではなく、`TransferChecked` を使用してください。Pausableなど、mint account に依存する拡張機能を持つToken-2022のmintは、それが指定されていない転送を拒否します。また、トランスファーフックを持つmintでは、他のトークン転送と同様に、フックのアカウントを解決して追加する必要があります。

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    アセットレッグの当事者が `userASigner` として署名し、エスクローAに入金します。

    ```ts
    import {
      findAssociatedTokenPda,
      getTransferCheckedInstruction,
    } from "@solana-program/token-2022";

    const [userAAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: userA,
      tokenProgram: tokenProgramA,
    });
    const [userBAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: userB,
      tokenProgram: tokenProgramB,
    });

    const fundAssetLeg = getTransferCheckedInstruction({
      source: userAAtaA,
      mint: mintA,
      destination: escrowA,
      authority: userASigner,
      amount: t.amountA,
      decimals: 6,
    }, { programAddress: tokenProgramA });

    await client.sendTransaction([fundAssetLeg]);
    ```

    キャッシュレッグの当事者は、`userBAtaB`、`mintB`、`userBSigner`、`t.amountB`、`{ programAddress: tokenProgramB }` を使って、エスクローBに対して同様に入金します。

  </Tab>

[`confirmed`](/docs/rpc#configuring-state-commitment) の時点で確認された入金転送であっても、後から無効になる可能性があります。プログラムは決済時にオンチェーンでエスクロー残高を読み取るため、着金していない入金転送を前提に送信したSettleは `LegNotFunded` で失敗し、何も移動しません。コストは失敗したSettleと再試行です。転送が `finalized` になった時点で、そのレッグを入金済みとみなしてください。

## 注意事項

- **ラップドSOLのレッグ。** プログラムはネイティブエスクローの残高を同期してから読み取るため、システム転送でラップドSOLのエスクローに送られた lamports もカウントされます。他のmintのエスクローには決してSOLを送らないでください。プログラムは返却できず、アカウントをクローズした人に渡ります。
- **ゲート付きmint。** Default Account Stateがfrozenのmintでは、エスクローがフリーズ状態で作成され、発行者が解除または許可するまで転送は失敗します。Token ACLとの相互作用については[概要](/docs/defi/dvp-program#mint-configuration-constraints)を参照してください。
- **トランスファーフック。** フック付きのエスクローには、合意した金額ちょうどを入金してください。超過分により決済時に返金が必要になると、返金ではレッグのフックアカウントが異なる宛先と金額で再利用されるため、拒否するフックがあります。復旧手順は、Reclaim、正確な金額での再入金、再度の決済です。
- **期限後の入金。** `expiry_timestamp` を過ぎても転送は止められません。転送は着金しますが、決済はできなくなり、レッグの当事者は、取引がオープンな間はReclaim、クローズ後はRecoverで取り戻します。[取引を巻き戻す](/docs/defi/dvp-program/unwind-a-trade)を参照してください。
- **先に入金する側。** プログラムは2つのレッグの順序を制御しません。順序は当事者間で決めることで、決済前であればどちら側もいつでも自分のレッグをReclaimできます。ただし、mint権限者(フリーズ、一時停止、トランスファーフック)がエスクローをブロックしている場合を除きます。
