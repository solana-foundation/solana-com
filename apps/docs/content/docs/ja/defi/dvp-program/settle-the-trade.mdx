`SettleDvp` は、取引レコードに指定された決済権限者が署名します。1つのトランザクションで、資産レッグの `amount_a` をキャッシュレッグ側の当事者の送金先へ、キャッシュレッグの `amount_b` を資産レッグ側の当事者の送金先へ移動し、いずれかのエスクローに残った余剰分をそのレッグの当事者に返却したうえで、レコードと両方のエスクローをクローズします。これらの転送のいずれかが完了できない場合、instruction は失敗し、何も移動しません。

このページは、[取引を作成する](/docs/defi/dvp-program/create-a-trade)と[各レッグに資金を入れる](/docs/defi/dvp-program/fund-the-legs)の続きです。クライアント、署名者、`trade`、および当事者の token account は引き継がれます。

## 署名前に再検証する

決済権限者は両レッグを移動するトランザクションに署名するため、署名前に各当事者と同じ読み取りを行います。オーナー、サイズ、当事者、mint、金額、有効期限、および両方の送金先を確認します([各レッグに資金を入れる](/docs/defi/dvp-program/fund-the-legs#verify-the-terms)を参照)。プログラム自体も決済時に、各 mint が作成時に記録された token program に引き続き属していること、ブロック対象の拡張機能を持たないこと、取引作成時と同じ mint authority を持つことを再確認します。そのため、ブロック対象の拡張機能付きで再作成された mint、異なる token program、または異なる mint authority の mint では決済できません。

## 受取アカウントを作成する

Settle は、プログラムが作成しない4つの token account に書き込みます。

| アカウント                | 受取内容                     | オーナー                           |
| ---------------------- | ---------------------------- | ------------------------------- |
| `userADestinationAtaB` | キャッシュレッグ(`amount_b`)    | `user_a_settlement_destination` |
| `userBDestinationAtaA` | 資産レッグ(`amount_a`)   | `user_b_settlement_destination` |
| `userAAtaA`            | 資産レッグの余剰分 | `user_a`                        |
| `userBAtaB`            | キャッシュレッグの余剰分  | `user_b`                        |

余剰分用のアカウントは、エスクローに合意額を超える残高がある場合にのみ使用されますが、mint を保有していれば誰でも、エスクローに少量の最小単位を送ることで余剰を生み出せます。返金先のアカウントが存在しないと、Settle 全体が失敗するため、4つすべてを同じトランザクション内で冪等に作成してください。

    import {
      findAssociatedTokenPda,

    const destinationA = t.userASettlementDestination; // defaults to userA

    const [userADestinationAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: destinationA,
      tokenProgram: tokenProgramB,
    });
    const [userBDestinationAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: destinationB,
      tokenProgram: tokenProgramA,
    });
    // userAAtaA and userBAtaB are from fund the legs.

    const createRecipientAccounts = [
      { ata: userADestinationAtaB, owner: destinationA, mint: mintB, tokenProgram: tokenProgramB },
      { ata: userBDestinationAtaA, owner: destinationB, mint: mintA, tokenProgram: tokenProgramA },
      { ata: userAAtaA, owner: userA, mint: mintA, tokenProgram: tokenProgramA },
      { ata: userBAtaB, owner: userB, mint: mintB, tokenProgram: tokenProgramB },
    ].map(({ ata, owner, mint, tokenProgram }) =>
      getCreateAssociatedTokenIdempotentInstruction({
        payer: authoritySigner,
        ata,
        owner,
        mint,
        tokenProgram,
      }),
    );

## 決済する(Settle)

`legAExtrasCount` は、固定リストの後ろに追加されたアカウントのうち、いくつが資産レッグの transfer hook に属するかをプログラムに伝えます。残りはキャッシュレッグの transfer hook に渡されます。transfer hook のない mint では、ゼロを渡し、何も追加しません。memo program の program account は instruction で必須であり、メモを必要とする送金先に対してのみ使用されます。

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { MEMO_PROGRAM_ADDRESS } from "@solana-program/memo";
    import { getSettleDvpInstruction } from "./dvp";

    const settleInstruction = getSettleDvpInstruction({
      settlementAuthority: authoritySigner,
      swapDvp,
      mintA,
      mintB,
      dvpAtaA: escrowA,
      dvpAtaB: escrowB,
      userADestinationAtaB,
      userBDestinationAtaA,
      userAAtaA,
      userBAtaB,
      tokenProgramA,
      tokenProgramB,
      memoProgram: MEMO_PROGRAM_ADDRESS,
      legAExtrasCount: 0,
    });

    const { context: settleContext } = await client.sendTransaction([
      ...createRecipientAccounts,
      settleInstruction,
    ]);
    const settleSignature = settleContext.signature;
    console.log("Submitted:", settleSignature);

    // sendTransaction returns at the client's commitment (confirmed by default).
    // Wait for finalized before recording the trade as settled.
    let finalized = false;
    for (let attempt = 0; attempt < 30 && !finalized; attempt++) {
      const {
        value: [status],
      } = await client.rpc.getSignatureStatuses([settleSignature]).send();
      if (status?.err) {
        throw new Error("Settle transaction failed");
      }
      finalized = status?.confirmationStatus === "finalized";
      if (!finalized) {
        await new Promise((resolve) => setTimeout(resolve, 2_000));
      }
    }
    if (!finalized) {
      // A closed record means it settled; an open one is safe to settle again.
      throw new Error("Settle not finalized after 60s; read the trade record");
    }
    console.log("Settled:", settleSignature);
    ```

### Transfer hook

生成された IDL には固定アカウントのみが記載されるため、生成されたビルダーは hook アカウントを認識しません。各 hook mint の追加アカウントメタは、そのトークンを直接転送する場合と同じ方法で解決し、instruction に追加します。順序は資産レッグのアカウントが先、次にキャッシュレッグのアカウントで、`legAExtrasCount` には最初のグループの数を設定します。TypeScript では、解決したメタを instruction の `accounts` 配列に展開(スプレッド)し、Rust ではビルダーの `add_remaining_accounts` を使用します。上限は、hook プログラムと検証アカウントを含めて1レッグあたり32アカウントです。両方のレッグに hook がある場合は、トランザクションのアカウント数の上限が先に制約となることがあります。プログラムは転送されるすべてのアカウントから署名者フラグを取り除くため、hook がこの経路で決済権限者の署名を取得することはできません。

## 結果を記録する

Settle トランザクションが `finalized` に達した時点で、取引が決済されたものとみなしてください。決済後はレコードと両方のエスクローが存在しなくなるため、後で条件が必要なシステムは、決済前の読み取り結果または作成トランザクションから条件を保存しておきます。クローズされたアカウントの rent は決済権限者に渡っています。

## Settle のエラー

`LegNotFunded` は、エスクローの残高が合意額に満たないことを意味します。`DvpExpired` と `SettlementTooEarly` は、時間枠を逃したことを意味します。`MintAuthorityChanged` と `BlockedMintExtension` は、作成後に mint が変更されたことを意味します。`RecipientAtaMismatch` は、送金先または返金先の token account が存在しないか、期待されるオーナーと mint にもはや属していないことを意味し、通常は上記のアカウント作成ステップを省略したことが原因です。いずれの場合も何も移動しておらず、mint の権限による制約のもとで、当事者は取引を巻き戻せます([取引を巻き戻す](/docs/defi/dvp-program/unwind-a-trade)を参照)。
