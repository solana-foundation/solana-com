Keychainは署名バックエンドを抽象化しますが、本番環境でのサイナーの運用は
依然としてお客様の責任です。これらのプラクティスはすべてのバックエンドに適用されます。バックエンドの選択については
[バックエンドの選択](/docs/tools/keychain/choosing-a-backend)を参照してください。

## ホットサイナーとコールドサイナーを分離する

頻繁な自動トランザクションには残高の少ない運用用（「ホット」）サイナーを使用し、
資金の移動には別の高額（「コールド」）サイナーを使用します。
コールドサイナーはMPCカストディまたはクラウドHSMで保護し、署名前に承認ポリシーを
必須とします。インターフェースは同一であるため、各ロールは呼び出し箇所を変更することなく
異なるバックエンドを使用できます。

## 計画的に鍵をローテーションする

Solanaでは署名鍵がアカウントアドレスそのものであるため、鍵をローテーションすると
新しいアドレスが生成されます。ローテーションはマイグレーションとして計画してください。新しい鍵を
プロビジョニングし、関連する権限（または資金）を新しいアドレスに再割り当てしてから、古い鍵を
廃止します。環境ごとに異なる鍵を使用し、devnetの鍵がmainnetで再利用されないようにしてください。

## 最小権限アクセスを付与する

各バックエンドの認証情報を、署名に必要な最小限のスコープに制限します。AWS KMSの場合は、
特定の鍵に対する`kms:Sign`と`kms:DescribeKey`のみを付与し、静的認証情報よりも
IAMロールを優先します。VaultポリシーおよびマネージドウォレットのAPIキーにも同じ原則を適用してください。

## 可用性を計画する

リモートバックエンドはネットワークサービスに依存します。サイナーを利用する前に`isAvailable()`を
呼び出し、一時的な障害に対してはバックオフ付きのリトライを適用し、障害発生時のフォールバック
パスを定義してください。KeychainはリモートバックエンドにHTTPSを強制し、デフォルトの
リクエストタイムアウトを適用します。

## シークレットとトランスポートを保護する

- すべてのリモートバックエンドはHTTPS経由で通信します。HTTPS以外のエンドポイントは拒否されます。
- APIキー、トークン、および認証情報はシークレットマネージャーまたは環境変数から
  供給してください。ハードコードしたり、ソース管理にコミットしたりしないでください。
- Keychainはエラーレスポンスをサニタイズしてシークレットがログに漏洩するのを防ぎます。
  独自のログにも生の認証情報や鍵素材が含まれないようにしてください。

## 署名をモニタリングおよび監査する

署名の成功率、レイテンシ、および失敗数を追跡し、急増時にはアラートを発報してください。
メトリクスの詳細については[本番環境の準備状況](/docs/tools/production-readiness#monitoring)を参照してください。
プロバイダー側の監査ログ（KMS、Vault、またはカストディアン）を有効にし、
アプリケーションが送信するトランザクションと照合してください。
