Keychain はすべてのバックエンドに対して 1 つの `SolanaSigner` 基底インターフェースを公開しているため、ほとんどのバックエンドでは、選択はアーキテクチャ上の問題ではなく運用上の問題です。後から設定で変更できます。例外はトランザクションの形式です。Crossmint と Fordefi のネイティブ自動モードはサーバー側で署名とブロードキャストを行い、Fordefi のネイティブ手動モードは署名前にトランザクションを書き換えます。そのため、これらへ移行する場合や、これらから移行する場合は、署名者の呼び出し方法が変わります。このため、**製品からではなく、要件から考え始めてください。** 判断のほとんどは次の 2 つの問いで決まります。_秘密鍵はどこに置かれ、誰がその鍵による署名を承認できるのか?_

Ledger を除くすべてのバックエンドは、4 つの言語(Rust、TypeScript、Python、Go)すべてで提供されています。Ledger は Rust 専用で、オプトインの `ledger` フィーチャーが必要です。

万能の最適なバックエンドはありません。それぞれが、特定の制約条件に適しています。たとえば、すでに利用しているクラウド、鍵インフラを自分で運用したいかどうか、必要とされるカストディや承認コントロールなどです。以下のフローは、そうした制約条件をバックエンドに対応付けたものです。

<Callout type="info">
  このガイドでは、バックエンド(サーバー側)での署名を扱います。エンドユーザーがブラウザー上で自身のトランザクションに署名する場合は、代わりに Wallet Standard を通じてウォレットを使用してください。[本番環境での署名](/docs/core/transactions/signing-in-production)を参照してください。
</Callout>

```mermaid title="Choosing a Keychain backend"

    Start -->|Your own app| Q2{Need multi-party approval,<br/>institutional custody,<br/>or regulatory controls?}
    Q2 -->|Yes| MPC[MPC / institutional custody<br/>Fireblocks · Dfns · Para · Utila · Fordefi]

    Q4 -->|AWS| AWS[AWS KMS]

    Q3 -->|Run it myself /<br/>multi-cloud / on-prem| Vault[HashiCorp Vault]
```

<Callout type="info">
  ローカル開発やテストでは、これらは一切不要です。プロトタイピングには **Memory** バックエンドを使用し、その後、設定を通じて上記のいずれかの本番用バックエンドに切り替えてください。
</Callout>

## 質問を順に確認する

<Steps>

<Step>

### 署名は自社アプリケーション向けですか、それともエンドユーザー向けですか?

**エンドユーザー**が所有・操作するウォレットをプロビジョニングする場合(コンシューマー向けアプリ、オンボーディングフローなど)は、**埋め込み型/マネージドウォレット**のバックエンドを使用してください。Privy、Turnkey、CDP、Crossmint、Openfort が該当します。これらは、ユーザーごとのウォレットと認証を代行して管理します。

**自社アプリケーション**として署名する場合(手数料支払者、トレジャリー、バックエンドの自動化など)は、以下に進んでください。

</Step>

<Step>

### マルチパーティ承認、機関投資家向けカストディ、または規制対応のコントロールが必要ですか?

署名が生成される前に、承認ポリシー、支出上限、コンプライアンスワークフローを通過する必要がある場合や、規制対象のカストディアンに鍵を保管してもらう必要がある場合は、**MPC/機関投資家向けカストディ**のバックエンドを使用してください。Fireblocks、Dfns、Para、Utila、Fordefi が該当します。これらは鍵を分割または保管し、ポリシーに従って共同署名します。

要求に応じて署名する鍵だけが必要な場合は、以下に進んでください。

</Step>

<Step>

### 鍵を自分で保持しますか、それともプロバイダーに保持させますか?

クラウドプロバイダーにハードウェアで保護されたインフラ上で鍵を保持させ、署名できるユーザーを IAM ポリシーで制御したい場合は、そのクラウドの KMS を使用してください。

- **AWS で稼働している場合** → AWS KMS
- **GCP で稼働している場合** → GCP KMS

鍵インフラを自分で運用したい場合、またはマルチクラウドやオンプレミス環境の場合は、**HashiCorp Vault** を使用してください。運用と監査はご自身で行い、鍵は Transit エンジン内に留まったまま、要求に応じて署名します。

</Step>

</Steps>

## カストディモデル

バックエンドは 6 つのカストディモデルに分類されます。上のフローを辿ると、そのいずれかに行き着きます。

- **セルフカストディ(プロセス内)**:アプリケーションが生の秘密鍵を保持します。開発には便利ですが、本番環境には適しません。バックエンド:**Memory**。
- **セルフカストディ(ハードウェアウォレット)**:鍵は Ledger デバイスの外に出ることはなく、すべての署名は画面上で担当者が確認します。対話的なオペレーター署名に適しており、無人運用のサービスには向きません。Rust のみ対応、オプトイン方式で、監査の対象外です。バックエンド:**Ledger**。
- **セルフホスト型の鍵管理**:鍵インフラを自分で運用します。鍵はその内部に留まり、要求に応じて署名します。バックエンド:**HashiCorp Vault**。
- **クラウド KMS/HSM**:クラウドプロバイダーが、ハードウェアで保護されたインフラ上に鍵を保管します。鍵がサービスの外に出ることはなく、署名できるユーザーは IAM ポリシーで制御されます。バックエンド:**AWS KMS**、**GCP KMS**。
- **MPC と機関投資家向けカストディ**:鍵はプロバイダー間で分割または保管され、プロバイダーがポリシー(承認、上限など)に従って共同署名します。バックエンド:**Fireblocks**、**Dfns**、**Para**、**Utila**、**Fordefi**。
- **埋め込み型・マネージドウォレット**:プロバイダーがウォレットを代行して管理します。エンドユーザーのオンボーディングに使われることが多い方式です。バックエンド:**Privy**、**Turnkey**、**CDP**、**Crossmint**、**Openfort**。

## バックエンド比較

| バックエンド         | カストディモデル                  | 最適な用途                                     | 備考                                                                                                              |
| --------------- | ------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Memory          | セルフカストディ（プロセス内）      | ローカル開発、テスト、CI                 | 生の鍵がプロセス内に存在するため、本番環境では使用しないでください                                                                       |
| Ledger          | セルフカストディ(ハードウェアウォレット) | Rust ツールからの対話的なオペレーター署名 | Rust のみ、オプトインの `ledger` フィーチャー、監査対象外。すべての署名をデバイス上で確認                                 |
| HashiCorp Vault | セルフホスト型鍵管理     | 独自の鍵インフラを運用するチーム   | Transitエンジン使用；運用および監査はユーザー側で実施                                                                           |
| AWS KMS         | クラウドKMS / HSM                | AWSで稼働するバックエンド                      | 鍵はKMS外に出ない；IAMが署名を制御                                                                         |
| GCP KMS         | クラウドKMS / HSM                | GCPで稼働するバックエンド                      | 鍵はKMS外に出ない；IAMが署名を制御                                                                         |
| Fireblocks      | MPC / 機関向けカストディ    | トレジャリー、取引所、規制対応カストディ     | ポリシーエンジンと承認ワークフロー                                                                               |
| Dfns            | MPCウォレットインフラ      | ポリシー制御付きプログラマティックウォレット    | Ed25519署名                                                                                                    |
| Para            | MPCウォレット                    | MPCバックアップウォレットを求めるアプリ            | APIキー＋ウォレットID                                                                                                |
| Utila           | MPCカストディ＋共同署名者        | 既存のUtila管理Solanaウォレット        | `signMessage` 非対応；txのブロードキャストはユーザー側で実施                                                                    |
| Fordefi         | MPC / 機関向けカストディ    | ポリシーコントロールを備えた機関向けカストディ   | ブラックボックス:ご自身で送信します。ネイティブ自動:Fordefi が書き換えて送信します。ネイティブ手動:Fordefi が書き換え、その結果をご自身で送信します |
| Privy           | 組み込みウォレット               | ウォレットへユーザーをオンボーディングするコンシューマーアプリ    | アプリ管理の組み込みウォレット                                                                                       |
| Turnkey         | 非カストディ型鍵管理   | ポリシーゲート付きプログラマティック署名           | 非カストディ型鍵管理                                                                                       |
| CDP             | マネージドウォレット（Coinbase）      | Coinbaseデベロッパープラットフォーム上のアプリ      | `signMessage` はUTF-8ペイロードのみ受け付ける                                                                          |
| Crossmint       | マネージドウォレット                | マーケットプレイスおよびマネージドウォレットアプリ         | 送信専用:サーバー側でブロードキャストし、ガススポンサーシップのために書き換える場合があります。`signMessage` は非対応                   |
| Openfort        | 組み込みバックエンドウォレット       | サーバーサイドウォレット                          | TEE保管鍵                                                                                                    |

## 機能の形式

カストディとは別に、各バックエンドにはそれぞれ 1 つのトランザクション形式があり、署名者の呼び出し方法はそれによって決まります。

- **署名**:プロバイダーが、ご自身で構築したバイト列に署名し、ブロードキャストはご自身で行います。Ledger や Fordefi のブラックボックスモードを含む、ほとんどのバックエンドが該当します。
- **書き換えて署名**:プロバイダーがトランザクションを書き換えたうえで、ブロードキャストせずに署名します。返されたトランザクションを引き継いで処理を続けます。Fordefi のネイティブ手動モードが該当します。
- **署名してブロードキャスト**:プロバイダーがサーバー側で署名とブロードキャストを行うため、失敗したからといって何も反映されていないとは限りません。Crossmint と Fordefi のネイティブ自動モードが該当します。

各言語の README にあるシグナー機能の表に、すべてのバックエンドの形式が一覧で掲載されています。各形式が何を保証するかについては、[セキュリティモデル](https://github.com/solana-foundation/solana-keychain/blob/main/docs/SECURITY_MODEL.md)で説明しています。

## エンタープライズシナリオ

1 つのアプリケーションが、これらを同時に複数必要とすることもよくあります。インターフェースは共通なので、バックエンド同士が同じ機能形式を持つ限り、呼び出し箇所を変更することなく、役割ごとに異なるバックエンドを使い分けられます。

- **トレジャリー運用**
  — 運用上の「ホット」署名者と「コールド」トレジャリー署名者を分離します。トレジャリーはMPCカストディまたはクラウドHSMでバックアップし、高額署名の前に承認ポリシーを必須とします。
- **承認ワークフロー** —
  MPCおよびカストディバックエンド（例：Fireblocks）は、署名が生成される前にマルチパーティ承認を強制します。
- **コンプライアンスと監査**
  — クラウドKMS（AWS/GCP）およびVaultは署名監査ログを出力し、機関投資家向けカストディアンはポリシー適用とレポーティングを追加します。
- **規制対応環境**
  — 鍵素材をHSM、KMS、または機関投資家向けカストディアンに保管し、生の鍵がアプリケーションに触れないようにします。

これらのバックエンドを安全に運用するには、[本番環境のベストプラクティス](/docs/tools/keychain/production-best-practices)をご参照ください。
