このガイドは、`solana-keychain`ライブラリに新しい鍵管理ソリューションを統合したいウォレットサービスプロバイダーや開発者向けです。署名者の実装を追加することで、統一されたインターフェースを通じて、開発者が安全なSolanaトランザクション署名にあなたのサービスを使用できるようになります。

Keychainは、Rust、TypeScript、Python、Goの各実装の機能を同等に保っています。
4つすべてを含むPRを強く推奨します。1つだけの貢献でも問題ありませんが、signerをリリースに含める前に、残りの実装も必須となりますのでご了承ください。

## アーキテクチャ概要

このライブラリは、`src/traits.rs` で定義されたトレイトベースのアーキテクチャを採用しています。すべてのsignerは、`SolanaSigner` 基本トレイト（`pubkey`、`sign_message`、`is_available`）に加えて、プロバイダーの形態に合致するケイパビリティトレイトをちょうど1つ実装します。

- `TransactionSigner`（`sign_transaction`）: プロバイダーが呼び出し元のバイト列に署名し、呼び出し元がブロードキャストします。ほとんどのバックエンドが該当します。
- `ModifyingSigner`（`modify_and_sign_transaction`）: プロバイダーがトランザクションを書き換えたうえで署名し、ブロードキャストは行いません。
- `SendingSigner`（`sign_and_send_transaction`）: プロバイダーがサーバー側で署名とブロードキャストを行います。

このライブラリは、すべての実装をラップする統合 `Signer` enumも提供しており、実行時に署名バックエンドを選択できます。このenumが実装するのは基本トレイトのみで、ケイパビリティへは `as_transaction_signer()`、`as_modifying_signer()`、`as_sending_signer()` を通じてアクセスします。

## クイック統合チェックリスト

- 実装を含む署名者モジュールを作成
- `SolanaSigner` 基本トレイト（`pubkey`、`sign_message`、`is_available`）と、プロバイダーの形態に合致するケイパビリティトレイト1つ（通常は `TransactionSigner`）を実装する

- HTTPSを強制し、HTTPクライアントのタイムアウトを設定

- 網羅的なユニットテストを追加する（wiremockベース、ご自身のモジュール内）
- 統合テストファイルを追加し、`.env.example` を更新する
- TypeScript、Python、Goの実装を追加する
- ドキュメントを更新
- CIワークフローの更新（メンテナーと調整してください。詳細は
  [CIワークフローの更新](#ci-workflow-updates-fork-prs)を参照）
- PRを提出

## ステップ2：署名者構造体の定義

`src/your_service/mod.rs`で、署名者構造体を定義します：

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,
}

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## ステップ3：コンストラクタとヘルパーメソッドの実装

リモート署名者は、HTTPSを**必ず**強制し、HTTPタイムアウトを設定する必要があります。タイムアウト設定には共有の`HttpClientConfig`構造体を使用してください。

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## ステップ4：Signerトレイトを実装する

`SolanaSigner` 基本トレイトには、2つの非同期メソッド（`sign_message`、`is_available`）と `pubkey()` があります。トランザクションの署名はケイパビリティトレイトに実装します。ほとんどのプロバイダーは `TransactionSigner` を実装し、その `sign_transaction` は `SignTransactionResult`（トランザクションが完全に署名済みか部分的に署名済みかを示すタグ付きenum）を返します。

トランザクション全体のワイヤ形式ではなく、メッセージのバイト列に署名し、それに対するプロバイダーの署名を検証してから付加してください。署名とシリアライズには、共通の `TransactionUtil` ヘルパーを使用します。

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

プロバイダーが署名前にトランザクションを書き換える場合は、代わりに `ModifyingSigner` を実装し、呼び出し元のトランザクションをプロバイダーのバイト列で丸ごと置き換えます。サーバー側でブロードキャストする場合は、`SendingSigner` を実装し、呼び出し元のトランザクションには手を加えません。プロバイダーが対応できないケイパビリティは、決して実装しないでください。

## ステップ6：機能フラグの追加

`Cargo.toml` を更新して、signerをオプションのフィーチャーとして追加します。リモートバックエンドには内部用の `_remote` マーカーを含めます。これは `src/error.rs` の `From<reqwest::Error>` 実装を有効にするもので、これがないと、ご自身のフィーチャーのみを有効にした場合にreqwest呼び出しへの `?` がコンパイルできません。

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## ステップ7：署名機能Enumの更新

`src/lib.rs` にsignerを追加します。基本の `SolanaSigner` 実装は `dispatch_signer!` マクロ経由でディスパッチされるため、そこにアームを1つ追加します。ケイパビリティへのアクセスは `as_transaction_signer()`、`as_modifying_signer()`、`as_sending_signer()` の各アクセサにあります。ご自身のケイパビリティトレイトに対応するアクセサに `Some(s)` アームを追加してください（送信型または変更型のバックエンドの場合は、`as_transaction_signer()` にも `None` アームを追加します）。

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## ステップ8：包括的なテストの追加

モジュールにテストを追加してください（`src/your_service/mod.rs`の最下部）：

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

署名検証の失敗もテストしてください。署名が検証を通らないモックレスポンスは、エラーを返す必要があります。

## CIワークフローの更新（フォークPR）

CIは2段階のプロセスです。PRをテストできるようにするには、事前にメンテナーと調整して `main` を準備する必要があります。メンテナーは `fork-external-live-manual.yml` を更新し、`ci.yml` に環境変数を追加し、GitHub Secretsを設定します。

PRには、signerのコードに加えて、以下のフェーズ2の変更を含める必要があります。

- **`ci.yml`**：`backend` マトリクスに（`all` の前に）Rustフィーチャーを追加し、`test` マトリクスに統合テスト関数を追加する
- **`typescript-ci.yml`**：ユニットテストと統合テストの各マトリクスにパッケージを追加し、統合テストのステップに環境変数を追加する
- **`typescript-publish.yml`**：`PUBLISH_PACKAGES`、GitHub Releaseの `packages` 配列、およびサマリーテーブルにパッケージを追加する
- **`python-ci.yml`**：`resolve-signers` 内の `CI_SIGNER_*` によるゲート制御と、統合マトリクスにバックエンドを追加する
- **`go-ci.yml`**：`CI_SIGNER_*` によるゲート制御と `moduleBySigner` にバックエンドを追加する

## TypeScript署名機能

TypeScript署名機能パッケージも追加する場合は、`typescript/packages/your-signer/`に作成してください。主要なパターン：

- ファクトリ関数 `createYourSigner()` は `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>` を返します。signerクラスは内部に留め、ファクトリとその設定型のみをエクスポートしてください
- 設定インターフェース（`YourSignerConfig`）をエクスポート
- バックエンドがメッセージに署名できない場合は、`SolanaMessageSigner` を省略し、`signMessages` メソッドを一切公開しないでください。Kitはメソッドの有無でsignerを分類するため、例外を投げるスタブを置くとsignerが誤って分類されてしまいます
- `apiBaseUrl` 設定フィールドには、`@solana/keychain-core` の `assertHttpsUrl()` でHTTPSを強制します
- リモート呼び出しは `@solana/keychain-core` の `fetchSignerJson()` 経由で行います。この関数がエラーマッピング、レスポンスのサニタイズ、リダイレクトの拒否、デフォルトのタイムアウトを担います
- その他のリモートAPIのエラーテキストは、`@solana/keychain-core` の `sanitizeRemoteErrorResponse()` でサニタイズします
- `@solana/keychain-core` の
  `throwSignerError(SignerErrorCode.*, { cause, message })` を使用
- すべての署名メソッドで `config?.abortSignal` を尊重し、`fetchSignerJson()` と `signBatchStaggered()` に引き渡してください
- `requestDelayMs` は `validateRequestDelayMs()` で検証し、`signBatchStaggered()` でバッチ処理します
- ファクトリ関数にエラーコードを列挙する `@throws` JSDoc を追加
- `@solana/*` パッケージは、`>=8.1.0` のピア依存関係として宣言します
- ユニットテストにはvitestとモック化した `fetch` を使用し、統合テストには `@solana/keychain-test-utils` の `runSignerIntegrationTest` を使用します

### Sending Signer

プロバイダーがトランザクションを書き換える場合、またはサーバー側でブロードキャストする場合、その署名は呼び出し元のトランザクションに適用できません。そのため、`SolanaTransactionSigner` ではなく `SolanaSendingSigner` にする必要があります。

- `signAndSendTransactions()` を実装し、`signTransactions` は公開**しない**でください（バックエンドが実際にメッセージへ署名する場合を除き、`signMessages` も同様です）
- `config?.abortSignal` を尊重してください。プロバイダーが作成リクエストを受理した後は、あらゆる失敗（中断を含む）を、プロバイダーのトランザクションIDを添えた `BROADCAST_UNCONFIRMED` として報告し、中断の理由は `cause` として保持します
- ご自身のsending signer型を返す、型付きの `createKeychainSigner` オーバーロードを追加します
- `typescript/packages/kit-plugin/src/keychain-plugin.ts` の `KeychainKitPluginConfig` からご自身のバックエンドを除外します。sending signerはKitクライアントの `payer` や `identity` としては使えないためです
- ユニットテストで、ご自身のインスタンスについて `isTransactionPartialSigner()` がfalse、`isTransactionSendingSigner()` がtrueであることをアサートします

### アンブレラパッケージの更新

`typescript/packages/keychain/` を更新します（変更するファイルは7つ）。

1. `src/types.ts`：`KeychainSignerConfig` の判別共用体に `YourSignerConfig` を追加する
2. `src/create-keychain-signer.ts`：switchのcaseを追加する（各バックエンドパッケージは動的な `import()` で読み込まれます）
3. `src/resolve-address.ts`：高速パスまたはフェッチパスのswitchのcaseに追加する
4. `src/index.ts`：設定型、名前空間、ファクトリ関数のエクスポートを追加する
5. `package.json`：`@solana/keychain-your-signer: "workspace:*"` 依存関係を追加する
6. `tsconfig.json`：`{ "path": "../your-signer" }` の参照を追加する
7. `typescript/scripts/test-treeshake-umbrella.mjs`：`SIGNER_MARKERS` にパッケージを、`FACTORIES` にファクトリを追加する

switch文には網羅性を確認する `never` チェックがあるため、共用体に追加してcaseを忘れるとTypeScriptがエラーを出します。その後、`just ts-treeshake` を実行してください。すべてのパッケージとアンブレラパッケージがツリーシェイク可能な状態を保つ必要があります。

## Python Signer

モジュールを `python/src/solana_keychain/your_signer/`（`__init__.py` と `signer.py`）に作成します。主なパターンは以下のとおりです。

- `solana_keychain.core` の `SolanaSigner`（`pubkey` プロパティ、`async sign_message()`、`async is_available()`）をサブクラス化し、さらにケイパビリティクラスをちょうど1つ継承します：`TransactionSigner`（`async sign_transaction()`）、`ModifyingSigner`（`async modify_and_sign_transaction()`）、または `SendingSigner`（`async sign_and_send_transaction()`）
- バックエンドがアドレスをリモートで解決する場合は、`init()` をawaitする `async create_your_signer()` ファクトリをエクスポートします。初期化前に署名を行うと、`SignerErrorCode.NOT_INITIALIZED` が発生します
- シークレットに `field(repr=False)` を指定した設定用dataclass（`YourSignerConfig`）をエクスポートします
- ベースURLフィールドには `assert_https_url()` でHTTPSを強制し、すべてのリクエストを `fetch_signer_json()` 経由で送信します
- プロバイダーの署名は、返す前に検証します。署名が対象とするバイト列には `signed_message_bytes()` を使用し、独自に実装したバージョンプレフィックスは決して使わないでください
- `python/src/solana_keychain/keychain.py` の `_BACKENDS` にバックエンドを登録します
- バックエンドでプロバイダーSDKが必要な場合は、インポートをガードし、
  `pip install 'solana-keychain[your-signer]'` を示す `ImportError` を発生させ、
  `python/pyproject.toml` に extra を宣言してください。また、パッケージルートから
  バックエンドを即時インポートしてはいけません
- pytest によるユニットテスト: HTTPバックエンドには `respx`、SDKバックエンドには
  スタブクライアントを使用し、発生したエラーの `str()` や `repr()` にシークレットが
  含まれないことを確認します
- `python/tests/integration/test_live_signers.py` に `make_your_signer()` ファクトリを
  追加し、`_MESSAGE_CAPABLE` に登録します(`sign_message` を持たないバックエンドの場合は
  `_TRANSACTION_ONLY`)

## Go Signer

Goの各バックエンドは独立したモジュールで、`go/signers/yoursigner/` に配置し、モジュールパスは
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2` とします。リファレンスとして
`go/signers/para/` を参照してください。主なパターン:

- `core.SolanaSigner`(`Pubkey()`、`SignMessage(ctx, message)`、
  `IsAvailable(ctx)`)を実装し、さらに機能インターフェースを1つだけ実装します:
  `core.TransactionSigner`、`core.ModifyingSigner`、`core.SendingSigner` のいずれかです。
  機能は型アサーションで検出されるため、トランザクションに署名できないバックエンドには
  `SignTransaction` メソッドを一切持たせてはいけません
- `Config` 構造体と `New` コンストラクタをエクスポートします(バックエンドがアドレスを
  リモートで解決する場合は `New(ctx, cfg)`。それ以前は
  `core.NewNotInitializedError` を返します)
- HTTPクライアントは `core.NewHTTPClient` または `core.ResolveHTTPClient` で構築し、
  ベースURLは `core.NormalizeHTTPSBaseURL` で検証します
- トランザクションの署名には `core.SignTransactionWith` を使用します。これはメッセージの
  バイト列に署名し、その署名を付与します。プロバイダーの署名は
  `core.VerifySignature` で検証します
- エラーは `core.NewSignerError` / `core.WrapSignerError` と、
  `core.CodeSigningFailed` などの安定したコードを使って返します
- ユニットテストには `httptest` を使用し、統合テストは `integration_test.go` に記述して
  `//go:build integration` タグの背後に置きます

## 実装のヒント

### エラー処理

既存の `SignerError` バリアントを必ず使用してください。`SignerError` の `Display` と `Debug` は
どちらもリダクトされているため、メッセージは汎用的なものにし、APIレスポンスの生データは
決して含めないでください。信頼できないAPIレスポンスに対して `.expect()` や `.unwrap()` を
使用してはいけません:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### セキュリティ要件

これらは単なる提案ではありません。利用者はこれらを根拠にバックエンドを選びます。
プロバイダーの仕様上、いずれかの要件を満たせない場合は、PRおよびリポジトリの
`docs/SECURITY_MODEL.md` にその旨を明記してください。

- **プロバイダーが署名した内容を検証すること。** メッセージのバイト列をローカルで計算し、
  署名を付与する前に、Signerが要求する位置で、返された署名をそのバイト列に対して
  検証してください。検証に失敗した署名は必ずエラーとし、決して付与してはいけません。
- **プロバイダーがブロードキャストを行うかどうかを明示すること。** プロバイダーがサーバー側で
  実行する場合は、sending 形式を実装し、確定したトランザクションを識別できる署名を返してください。
  プロバイダーに署名のみのエンドポイントがない場合は、呼び出し元の知らないところで送信するのではなく、
  バックエンドを sending 専用にしてください。
- **署名がカバーしていないトランザクションを呼び出し元に持たせないこと。**
  トランザクションを書き換えるプロバイダーは、自身のバイト列に署名します。その場合は、
  呼び出し元のトランザクションに一切手を加えない(ブロードキャスト管理型のケース)か、
  modifying 形式を採用して、プロバイダーのバイト列で全体を置き換えてください。
- **ブロードキャストの不確実性はそのまま報告すること。** 送信後の失敗であっても、
  トランザクションが確定している可能性があります。汎用的なエラーではなく
  `BROADCAST_UNCONFIRMED` を返し、プロバイダーのトランザクションIDがある場合は
  常に含め、作成のたびにメッセージから導出した冪等性キーを送信してください。
  これにより、バイト列が同一の再送でも安全になります。
- **初期化前に署名しないこと。** `init()` の前の公開鍵には `Pubkey::default()` ではなく
  `Option<Pubkey>` を使用し、先に署名が試みられた場合は設定エラーで失敗させてください。
- 機密データ(秘密鍵、APIシークレット、APIの生レスポンス)は決してログに出力せず、
  機密フィールドを隠す `Debug` 実装を使用してください
- HTTPSを強制し(`https_only(true)`。wiremock 用に `#[cfg(not(test))]` で制御)、
  リクエストと接続のタイムアウトを `HttpClientConfig` で設定してください
  (デフォルト: 30秒/5秒)
- 中間的な鍵素材は `zeroize::Zeroizing<Vec<u8>>` でゼロ化してください

### モックを使用したテスト

HTTP
APIのモックには`wiremock`を使用してください。エラーメッセージのテキストではなく、エラータイプに対してアサートを行います：

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
