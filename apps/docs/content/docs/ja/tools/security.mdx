## 鍵管理

- **フロントエンドコードに秘密鍵を絶対に公開しないでください。** バックエンドでの署名、ハードウェアウォレット、マルチシグウォレット、鍵管理サービスを利用してください。
- **ホットウォレットとコールドウォレットを分離してください。** ホットウォレットは運用用、コールドウォレットはトレジャリー用に使用します。
- **本番環境のすべての鍵をバックアップしてください。** 暗号化したバックアップを、安全な複数の場所に保管します。鍵を紛失すると、永久にアクセスできなくなります。
- **devnetとmainnetで異なる鍵を使用してください。** devnetの鍵をmainnetの鍵として使用してはいけません。環境ベースの設定を使用して、各ネットワークに正しい鍵が読み込まれるようにしてください。

## 署名インフラストラクチャ

本番環境のバックエンド署名には、[Keychain](/docs/tools/keychain)を使用してください。Keychainは、Memory、Vault、Privy、Turnkey、AWS KMS、Fireblocks、GCP KMS、CDP、Para、Dfns、Crossmint、Openfort、Utilaといった複数の鍵管理バックエンドを単一のインターフェースで抽象化する、統合署名ライブラリです。これにより、ローカルではインメモリの鍵で開発し、アプリケーションコードを変更することなく本番グレードのバックエンドへ切り替えられます。

どのバックエンドが適しているかわからない場合は、[バックエンドの選び方](/docs/tools/keychain/choosing-a-backend)をご覧ください。Keychainは[Rust](https://crates.io/crates/solana-keychain)と[TypeScript](https://www.npmjs.com/package/@solana/keychain)の両方で利用できます。

## RPCのセキュリティ

RPCエンドポイントはAPIキーと同様に扱ってください。フロントエンドコードに公開すると、抽出されて悪用される可能性があります。バックエンドプロキシや、クライアントコードにバンドルされない環境変数を使用してください。

- [QuickNode: エンドポイントセキュリティのベストプラクティス](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: SolanaのAPIキーを保護する: セキュリティのベストプラクティス](https://www.helius.dev/docs/rpc/protect-your-keys)

## モニタリング

本番環境では、次の指標を追跡してください。

| 指標                   | 目的                    |
| ------------------------ | ---------------------- |
| トランザクション成功率 | 問題の早期検出    |
| 承認レイテンシ     | ネットワークの健全性の監視 |
| 優先手数料の支出       | コスト管理        |
| RPCエラー率           | プロバイダーの健全性        |

次の場合にアラートを設定してください。

- トレジャリーからのしきい値を超える送金
- トランザクション失敗率の急上昇
- 通常と異なる受取人のパターン
- RPCエラー率の上昇

大規模なリアルタイムのトランザクション監視については、[インデックス作成ガイド](/docs/payments/accept-payments/indexing)をご覧ください。

## アドレスの検証

メインネット上では、すべてのトークンとプログラムに、正しいアドレスがちょうど1つ存在します。USDCなどのステーブルコインを装った偽トークンはよく見られ、名前とシンボルは同じでもミントが異なります。アプリケーションでは、(要件に応じて)ミントアドレスをハードコードするか許可リストに登録し、信頼できないソースから動的に受け取ることは決してしないでください。

**環境ごとの設定:** devnetとmainnetでは、まったく異なるトークンミントが使われることがよくあります。環境ごとに正しいアドレスを読み込むよう、アプリケーションの設定を構成してください。mainnetのアドレスをハードコードしてテスト時に差し替え忘れたり、さらには devnetのアドレスを本番環境にリリースしてしまったりすることのないようにしましょう。

一般的なステーブルコインのミントには、次のものがあります。

| トークン | 発行元 | ミントアドレス                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

プログラムのアドレスも重要です。誤ったプログラムに instructions を送信すると失敗します。さらに悪い場合は、資金を取り戻せない損失につながります。Token Program のアドレスは次のとおりです。

| プログラム            | アドレス                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

正しいアドレスを許可リストに登録すれば偽のトークンからは保護されますが、誤った _種類_ のアカウントへの送信は防げません。受取人アドレスにはウォレット、token account、ミント、プログラムのいずれもあり得て、それぞれ扱いが異なります。ネイティブの SOL をウォレット以外に送信すると、送信者の管理下から離れてしまいます。ミントやプログラム宛ての場合は完全に失われ、token account 宛ての場合はそのアカウントの所有者だけが回収できます。しかも、ユーザーに警告する失敗トランザクションは発生しません。

<Callout type="warn" title="送信前に受取人を検証する">
  送金に署名する前に、すべての受取人アドレスを分類してください。ウォレット、token account、ミント、プログラムを区別するための判定ツリーと参考コードについては、[アドレスの検証](/docs/payments/send-payments/verify-address)をご覧ください。
</Callout>
