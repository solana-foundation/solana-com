## キー管理

- **秘密鍵をフロントエンドコードで公開しないでください。** バックエンドでの署名、ハードウェアウォレット、マルチシグウォレット、またはキー管理サービスを使用してください。
- **ホットウォレットとコールドウォレットを分けてください。** ホットウォレットは運用用、コールドウォレットはトレジャリー用に使用します。
- **本番環境のすべてのキーをバックアップしてください。** 暗号化したバックアップを複数の安全な場所に保管してください。キーを紛失すると、永久にアクセスできなくなります。
- **devnetとmainnetで異なるキーを使用してください。** devnetのキーをmainnetのキーとして使い回してはいけません。環境ごとの設定を使用して、各ネットワークで正しいキーが読み込まれるようにしてください。

## 署名インフラストラクチャ

本番環境のバックエンド署名には、[Keychain](/docs/tools/keychain)の使用をおすすめします。Keychainは、Memory、Vault、Privy、Turnkey、AWS KMS、Fireblocks、GCP KMS、CDP、Para、Dfns、Crossmint、Openfort、Utilaといった複数のキー管理バックエンドを単一のインターフェースで抽象化する統合署名ライブラリです。これにより、ローカルではインメモリのキーで開発し、アプリケーションコードを変更せずに本番グレードのバックエンドへ切り替えることができます。

どのバックエンドが適しているかわからない場合は、[バックエンドの選び方](/docs/tools/keychain/choosing-a-backend)をご覧ください。Keychainは[Rust](https://crates.io/crates/solana-keychain)と[TypeScript](https://www.npmjs.com/package/@solana/keychain)の両方で利用できます。

## RPCセキュリティ

RPCエンドポイントはAPIキーと同様に扱ってください。フロントエンドコードで公開すると、抽出されて悪用される可能性があります。バックエンドプロキシ、またはクライアントコードにバンドルされない環境変数を使用してください。

- [QuickNode: エンドポイントセキュリティのベストプラクティス](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Solana APIキーを保護する: セキュリティのベストプラクティス](https://www.helius.dev/docs/rpc/protect-your-keys)

## モニタリング

本番環境では、次のメトリクスを追跡してください。

| メトリクス                   | 目的                    |
| ------------------------ | ---------------------- |
| トランザクション成功率 | 問題を早期に検知する    |
| 承認レイテンシー     | ネットワークの健全性を監視する |
| 優先手数料の支出       | コスト管理        |
| RPCエラー率           | プロバイダーの健全性        |

次の項目についてアラートを設定してください。

- トレジャリーからしきい値を超える送金が行われた場合
- 失敗したトランザクションの割合が急増した場合
- 通常とは異なる受取先のパターンが見られた場合
- RPCエラー率が上昇した場合

大規模なリアルタイムのトランザクション監視については、[インデックス作成ガイド](/docs/payments/accept-payments/indexing)をご覧ください。

## アドレスの検証

メインネット上では、すべてのトークンとプログラムに正しいアドレスがちょうど1つ存在します。USDCなどのステーブルコインを装った偽トークンはよく見られ、名前とシンボルは同じでもミントが異なります。アプリケーションでは、（要件に応じて）ミントアドレスをハードコードするか許可リストに登録し、信頼できないソースから動的に受け入れることは決してしないでください。

**環境ごとの設定:** devnetとMainnetでは、まったく異なるトークンミントが使われることがよくあります。アプリケーションの設定で、環境ごとに正しいアドレスを読み込むようにしてください。mainnetのアドレスをハードコードしてテスト時に切り替えを忘れたり、さらに悪いことにdevnetのアドレスを本番環境にリリースしたりしないよう注意してください。

一般的なステーブルコインのミントは次のとおりです。

| トークン | 発行元 | ミントアドレス                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

プログラムのアドレスも重要です。誤ったプログラムに instructions を送信すると失敗し、さらに悪い場合は資金を取り戻せない形で失うことになります。Token Programのアドレスは次のとおりです。

| プログラム            | アドレス                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

正しいアドレスを許可リストに登録すれば偽トークンは防げますが、誤った*種類*のアカウントへの送信は防げません。受取先アドレスはウォレット、token account、ミント、プログラムのいずれにもなり得て、それぞれ異なる扱いが必要です。ネイティブのSOLをウォレット以外に送信すると、送信者の管理下から離れてしまいます。ミントやプログラムに送った場合は完全に失われ、token accountに送った場合はアカウント所有者のみが回収できます。しかも、ユーザーに警告する失敗トランザクションは発生しません。

<Callout type="warn" title="送信前に受取先を検証する">
  送金に署名する前に、すべての受取先アドレスを分類してください。ウォレット、token account、ミント、プログラムを区別するための完全な判断ツリーと参照コードについては、[アドレスの検証](/docs/payments/send-payments/verify-address)をご覧ください。
</Callout>
