Koraは3つのクレートで構成されるRustワークスペースです。

- `kora-lib`はコアロジックとRPCサーバーを含みます。
- `kora-cli`はオペレーターが実行する`kora`バイナリをビルドします。
- `kora-deploy`は専用のプログラムデプロイツールで、個別にバージョン管理されています。
  特に記載がない限り、以下はすべて`crates/lib/src`内にあります。

## 各ステージの所在

| 図中のステージ | ソース                               | エントリーポイント                           |
| -------------------- | ------------------------------------ | ------------------------------------- |
| ゲートウェイ              | `rpc_server/server.rs`               | `run_rpc_server`                      |
| ディスパッチ             | `rpc_server/rpc.rs`                  | `KoraRpc`                             |
| メソッドごとのロジック     | `rpc_server/method/`                 | JSON-RPCメソッドごとに1ファイル          |
| 検証           | `validator/transaction_validator.rs` | `TransactionValidator`                |
| プラグイン              | `plugin/mod.rs`                      | `TransactionPluginRunner`             |
| 署名              | `signer/`                            | `solana-keychain`クレートによって支えられています |

知っておくべきファイルがあと2つあります。`config.rs`は`kora.toml`のスキーマ全体を定義し、
`state.rs`はデシリアライズされた設定をプロセスグローバルな状態として保持します。

### RPCサーバーを読む

`rpc.rs`は薄いディスパッチ層で、JSON-RPCエンドポイントごとに1つのメソッドがあり、
API全体を把握する最短の方法です。各メソッドのロジックは`rpc_server/method/`配下の
個別のファイルにあります。`sign_transaction.rs`は最初から最後まで読んでください。他の署名
メソッドはこれのバリエーションです。

### バリデーターを読む

`transaction_validator.rs`と`transaction/instruction_util.rs`には、トランザクションとinstructionsを
検証するロジックがあります。さらに、fee-payer-policyの
セーフティプロパティテストは、ゲート対象のプログラムごとに1ファイルずつ
`validator/transaction_validator/fee_payer_policy_props/`にあります。

## 知っておきたい規約

**デフォルトの検証。** `[validation.fee_payer_policy]`配下のすべてのフラグは
デフォルトで`false`であり、ポリシー構造体には`#[serde(default)]`が付いています。この
組み合わせは意図的なものです。新たにゲート対象となるinstructionを追加しても既存オペレーターの設定を壊してはならず、
また意図せず許可されるのではなく拒否として扱われなければなりません。フラグを追加する際は、この両方を維持してください。

**検証するのは解決済みのトランザクションであり、生のトランザクションではありません。** 生の
`VersionedTransaction`は静的アカウントキーしか公開しないため、そこからV0トランザクションを検証したり
料金を算出したりすると、ルックアップテーブルのアカウントが黙ってスキップされ、過小請求になります。
`VersionedTransactionResolved::from_transaction`はそれらのアドレスを事前に解決するため、
下流のすべてのステージは解決済みの型を受け取ります。

## トランザクションプラグインの追加

プラグインは`plugin/mod.rs`にある`TransactionPlugin`トレイトを実装します。メソッドは2つあります。
`validate`は署名フロー中にトランザクションごとに実行され、`validate_config`は起動時に1回実行され、
オペレーター向けにエラーと警告を返します。`PluginExecutionContext`は、4つの署名メソッドのうち
どれがプラグインを呼び出したかをプラグインに伝えます。

`TransactionPluginRunner::from_config`は、`config.rs`で定義されている`TransactionPluginType`で
マッチします。新しい組み込みプラグインを追加するには、そこに新しいバリアントを加え、ランナーに
新しいmatchアームを追加します。現在提供されているプラグインは`gas_swap`と`deploy_authority`の2つです。

## テスト

Koraは設定をプロセスグローバルな状態として保持するため、`tests/`ではフェーズごとに`[[test]]`ターゲットを
1つ宣言し、各ターゲットが独自の組み込みsurfnetとKoraノードを、ゼロから初期化して起動します。
バイナリごとに設定は1つです。新しいフェーズには、既存のモジュールに追加するのではなく、新しいターゲットが必要です。

```bash
cargo test -p tests --test <target>
```

それ以外はすべて`justfile`で連携されています。コマンドを手作業で組み立て直すのではなく、
そちらを読んでください。
