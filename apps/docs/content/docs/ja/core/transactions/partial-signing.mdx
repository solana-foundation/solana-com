部分署名を使うと、複数の関係者が異なるタイミングや異なるデバイスで同じトランザクションに署名できます。コーディネーターがメッセージを構築し、必要な各署名者がシリアライズ済みメッセージのバイト列そのものに署名します。コーディネーターは送信前に署名を検証してマージします。

<Callout type="warn" title="署名が承認するのはバイト列であり、意図ではありません">
  手数料支払者、blockhash、instruction の順序、アカウントリスト、または instruction data のいずれかを変更すると、別のメッセージになり、すでに集めたすべての署名が無効になります。
</Callout>

## 部分署名のフロー

1. トランザクションの instructions と、手数料を支払う主体について合意します。
2. トランザクションの有効期間と手数料支払者を設定します。
3. メッセージを一度だけシリアライズします。そのバイト列は変更不可として扱います。
4. メッセージのバイト列と、人間が読める概要を各署名者に配布します。
5. 各 Ed25519 署名を収集し、同じメッセージのバイト列に対して検証します。
6. 署名を、対応する必須署名者のアドレスに紐づけます。
7. 必要な署名がすべて揃っていて有効であることを確認してから、送信します。

## 署名前にメッセージを固定する

すべての署名は、シリアライズされたトランザクションメッセージを対象とします。メッセージには次のすべてが含まれます。

- 手数料支払者
- 最近の blockhash または durable nonce
- すべてのプログラムとアカウントのアドレス
- アカウントの署名者権限と書き込み可能権限
- instruction の順序と instruction data

まずこれらのフィールドを構築し、メッセージを一度だけシリアライズして、そのバイト配列をすべての署名者に配布します。各署名リクエストにメッセージのダイジェストを併せて保存しておくと便利です。これにより、コーディネーターは別のメッセージに対して返された署名を拒否できます。

メッセージをデシリアライズして変更し、以前に集めた署名が有効なままであることを期待してはいけません。期限切れの blockhash を置き換える、手数料支払者を変更するなど、運用上の変更に見えるものであっても、すべての署名者が再度署名する必要があります。

## 手数料支払者を調整する

手数料支払者は常に必須の署名者であり、メッセージを固定する前に決めておく必要があります。そのアカウントに、基本手数料と優先手数料を支払うのに十分な SOL があることを確認してください。スポンサーやバックエンドが手数料を支払う場合は、ユーザーの署名を集める前に、そのアドレスをメッセージに含めてください。スポンサーを後から追加すると、署名対象のバイト列が変わってしまいます。

コーディネーターは、受け取った署名が必須署名者として記載されたアドレスのものであることを検証する必要があります。任意の公開鍵を受け入れて、トランザクションに追加してはいけません。

## トランザクションの有効期間を管理する

最近の blockhash を使用するトランザクションは、その blockhash が validator の最近の blockhash キューに残っている間のみ有効です。複数の関係者による署名フローを開始する前に、すべての署名者が `lastValidBlockHeight` までに応答できるかどうかを見積もってください。

blockhash が期限切れになった場合は、新しい blockhash で新しいメッセージを構築し、すべての署名を改めて集めてください。時間がかかる可能性があるワークフローや、オフライン署名者を含むワークフローでは、[durable nonce](/docs/core/transactions/durable-nonces) を使用します。durable nonce を使うと最近の blockhash の有効期間の制約を回避できますが、その nonce を進めたり、他の形で消費したりすると、保留中のトランザクションは無効になります。

## 送信前に検証する

返されたすべての署名について、次の手順を行います。

1. 固定したメッセージのバイト列と、期待される署名者の公開鍵に対して署名を検証します。
2. トランザクションの署名配列内で、その署名者に対応する位置に署名を追加します。
3. 組み立てたトランザクションに、必須署名者全員分の有効な署名が含まれていることを確認します。
4. メッセージを再構築せずに、シリアライズ済みのトランザクションを送信します。

送信後は、署名済みメッセージに含まれていたものと同じ有効期間情報を使って確認を行います。確認の結果、blockhash の期限切れや nonce の消費が報告された場合は、変更したトランザクションで再試行せず、署名フローを最初からやり直してください。
