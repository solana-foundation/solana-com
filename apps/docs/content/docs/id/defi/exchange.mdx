Panduan ini menjelaskan cara menambahkan token asli Solana, SOL, ke bursa kripto
Anda.

## Pengaturan Node

Kami sangat menyarankan untuk menyiapkan setidaknya dua node pada komputer/instans
cloud berkualitas tinggi, segera melakukan pembaruan ke versi terbaru, dan memantau
operasi layanan menggunakan alat pemantauan bawaan.

Pengaturan ini memungkinkan Anda:

- memiliki gateway yang dikelola sendiri ke kluster mainnet Solana untuk mendapatkan
  data dan mengirimkan transaksi penarikan
- memiliki kendali penuh atas seberapa banyak data blok historis yang disimpan
- menjaga ketersediaan layanan Anda meskipun salah satu node mengalami kegagalan

Node Solana membutuhkan daya komputasi yang cukup tinggi untuk menangani blok
cepat dan TPS tinggi kami. Untuk persyaratan spesifik, silakan lihat
[rekomendasi perangkat keras](https://docs.anza.xyz/operations/requirements).

Untuk menjalankan node api:

1. [Instal suite alat command-line Solana](/docs/intro/installation)
2. Jalankan validator dengan setidaknya parameter berikut:

```shell
solana-validator \
  --ledger <LEDGER_PATH> \
  --identity <VALIDATOR_IDENTITY_KEYPAIR> \
  --entrypoint <CLUSTER_ENTRYPOINT> \
  --expected-genesis-hash <EXPECTED_GENESIS_HASH> \
  --rpc-port 8899 \
  --no-voting \
  --enable-rpc-transaction-history \
  --limit-ledger-size \
  --known-validator <VALIDATOR_ADDRESS> \
  --only-known-rpc
```

Sesuaikan `--ledger` ke lokasi penyimpanan ledger yang Anda inginkan, dan `--rpc-port`
ke port yang ingin Anda ekspos.

Parameter `--entrypoint` dan `--expected-genesis-hash` bersifat spesifik untuk
kluster yang Anda ikuti.
[Parameter saat ini untuk Mainnet](https://docs.anza.xyz/clusters/available#example-solana-validator-command-line-2)

Parameter `--limit-ledger-size` memungkinkan Anda menentukan berapa banyak
[shreds](/docs/references/terminology#shred) ledger yang disimpan node Anda di disk. Jika Anda
tidak menyertakan parameter ini, validator akan menyimpan seluruh ledger hingga
kehabisan ruang disk. Nilai default berupaya menjaga penggunaan disk ledger
di bawah 500GB. Penggunaan disk yang lebih banyak atau lebih sedikit dapat diminta
dengan menambahkan argumen pada `--limit-ledger-size` jika diinginkan. Periksa
`solana-validator --help` untuk nilai batas default yang digunakan oleh
`--limit-ledger-size`. Informasi lebih lanjut tentang memilih nilai batas kustom
[tersedia di sini](https://github.com/solana-labs/solana/blob/583cec922b6107e0f85c7e14cb5e642bc7dfb340/core/src/ledger_cleanup_service.rs#L15-L26).

Menentukan satu atau lebih parameter `--known-validator` dapat melindungi Anda dari
booting menggunakan snapshot yang berbahaya.
[Selengkapnya tentang manfaat booting dengan known validator](https://docs.anza.xyz/operations/guides/validator-start#known-validators)

Parameter opsional yang perlu dipertimbangkan:

- `--private-rpc` mencegah port RPC Anda dipublikasikan untuk digunakan oleh node
  lain
- `--rpc-bind-address` memungkinkan Anda menentukan alamat IP yang berbeda untuk
  mengikat port RPC

### Restart Otomatis dan Pemantauan

Kami menyarankan untuk mengonfigurasi setiap node Anda agar restart secara otomatis
saat keluar, guna memastikan Anda melewatkan sesedikit mungkin data. Menjalankan
perangkat lunak Solana sebagai layanan systemd adalah salah satu opsi terbaik.

Untuk pemantauan, kami menyediakan
[`solana-watchtower`](https://github.com/solana-labs/solana/blob/master/watchtower/README.md),
yang dapat memantau validator Anda dan mendeteksi apakah proses `solana-validator`
tidak berjalan dengan baik. Alat ini dapat dikonfigurasi langsung untuk memberi
tahu Anda melalui Slack, Telegram, Discord, atau Twilio. Untuk detailnya,
jalankan `solana-watchtower --help`.

```shell
solana-watchtower --validator-identity <YOUR VALIDATOR IDENTITY>
```

> Anda dapat menemukan informasi lebih lanjut tentang
> [praktik terbaik untuk Solana Watchtower](https://docs.anza.xyz/operations/best-practices/monitoring#solana-watchtower)
> di sini dalam dokumentasi.

#### Pengumuman Rilis Perangkat Lunak Baru

Kami merilis perangkat lunak baru secara rutin (sekitar 1 rilis/minggu). Terkadang
versi terbaru mencakup perubahan protokol yang tidak kompatibel, sehingga memerlukan
pembaruan perangkat lunak yang tepat waktu untuk menghindari kesalahan dalam
pemrosesan blok.

Pengumuman rilis resmi kami untuk semua jenis rilis (normal dan keamanan)
dikomunikasikan melalui saluran [discord](/discord) bernama
`#mb-announcement` (`mb` adalah singkatan dari `mainnet-beta`).

Seperti halnya validator yang di-stake, kami mengharapkan setiap validator yang
dioperasikan oleh bursa untuk diperbarui sesegera mungkin dalam satu atau dua
hari kerja setelah pengumuman rilis normal. Untuk rilis terkait keamanan,
tindakan yang lebih mendesak mungkin diperlukan.

### Kesinambungan Ledger

Secara default, setiap node Anda akan melakukan boot dari snapshot yang disediakan
oleh salah satu known validator Anda. Snapshot ini mencerminkan kondisi rantai
saat ini, tetapi tidak memuat ledger historis yang lengkap. Jika salah satu node
Anda keluar dan melakukan boot dari snapshot baru, mungkin akan terdapat celah
dalam ledger di node tersebut. Untuk mencegah masalah ini, tambahkan parameter
`--no-snapshot-fetch` pada perintah `solana-validator` Anda untuk menerima data
ledger historis, bukan snapshot.

Jangan gunakan parameter `--no-snapshot-fetch` saat boot awal karena tidak
mungkin melakukan boot node dari genesis block. Sebaliknya, lakukan boot dari
snapshot terlebih dahulu, lalu tambahkan parameter `--no-snapshot-fetch` untuk
reboot berikutnya.

Penting untuk dicatat bahwa jumlah ledger historis yang tersedia bagi node Anda
dari seluruh jaringan terbatas pada setiap saat. Setelah beroperasi, jika
validator Anda mengalami downtime yang signifikan, validator tersebut mungkin
tidak dapat menyusul jaringan dan perlu mengunduh snapshot baru dari known
validator. Dengan melakukan ini, validator Anda akan memiliki celah dalam data
ledger historisnya yang tidak dapat diisi.

### Meminimalkan Eksposur Port Validator

Validator memerlukan berbagai port UDP dan TCP yang terbuka untuk lalu lintas
masuk dari semua validator Solana lainnya. Meskipun ini adalah mode operasi yang
paling efisien dan sangat disarankan, validator dapat dibatasi sehingga hanya
memerlukan lalu lintas masuk dari satu validator Solana lainnya.

Pertama, tambahkan argumen `--restricted-repair-only-mode`. Ini akan menyebabkan
validator beroperasi dalam mode terbatas di mana ia tidak akan menerima push dari
validator lainnya, melainkan harus terus-menerus melakukan polling ke validator
lain untuk mendapatkan blok. Validator hanya akan mengirimkan paket UDP ke
validator lain menggunakan port _Gossip_ dan _ServeR_ ("serve repair"), dan hanya
menerima paket UDP pada port _Gossip_ dan _Repair_-nya.

Port _Gossip_ bersifat dua arah dan memungkinkan validator Anda tetap terhubung
dengan seluruh kluster. Validator Anda mengirimkan pada _ServeR_ untuk membuat
permintaan perbaikan guna mendapatkan blok baru dari seluruh jaringan, karena
Turbine kini dinonaktifkan. Validator Anda kemudian akan menerima respons
perbaikan pada port _Repair_ dari validator lain.

Untuk lebih membatasi validator agar hanya meminta blok dari satu atau lebih
validator, pertama tentukan identity pubkey untuk validator tersebut dan tambahkan
argumen `--gossip-pull-validator PUBKEY --repair-validator PUBKEY` untuk setiap
PUBKEY. Ini akan menyebabkan validator Anda menjadi beban sumber daya bagi setiap
validator yang Anda tambahkan, jadi lakukan ini dengan hemat dan hanya setelah
berkonsultasi dengan validator target.

Validator Anda sekarang seharusnya hanya berkomunikasi dengan validator yang
tercantum secara eksplisit dan hanya pada port _Gossip_, _Repair_, dan _ServeR_.

## Menyiapkan Akun Deposit

Akun Solana tidak memerlukan inisialisasi onchain; begitu berisi sejumlah SOL,
akun tersebut sudah ada. Untuk menyiapkan akun deposit bagi bursa Anda, cukup
buat keypair Solana menggunakan salah satu
[alat wallet](https://docs.anza.xyz/cli/wallets) kami.

Kami menyarankan penggunaan akun deposit unik untuk setiap pengguna Anda.

Akun Solana harus dibuat bebas rent dengan menyimpan saldo setara rent selama
2 tahun dalam SOL. Untuk menemukan saldo minimum bebas rent bagi akun deposit
Anda, lakukan kueri pada
[endpoint `getMinimumBalanceForRentExemption`](/docs/core/accounts/account-structure):

```shell
curl https://api.devnet.solana.com -X POST -H "Content-Type: application/json" -d '{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "getMinimumBalanceForRentExemption",
  "params": [0]
}'
```

##### Hasil

```json
{ "jsonrpc": "2.0", "result": 890880, "id": 1 }
```

### Akun Offline

Anda mungkin ingin menyimpan kunci untuk satu atau lebih akun koleksi secara
offline demi keamanan yang lebih baik. Jika demikian, Anda perlu memindahkan SOL
ke akun hot menggunakan
[metode offline](https://docs.anza.xyz/cli/examples/offline-signing) kami.

## Mendengarkan Deposit

Ketika pengguna ingin menyetorkan SOL ke bursa Anda, instruksikan mereka untuk
mengirim transfer ke alamat deposit yang sesuai.

### Migrasi Transaksi Berversi

Ketika jaringan Mainnet mulai memproses transaksi berversi, bursa **HARUS**
melakukan perubahan. Jika tidak ada perubahan yang dilakukan, deteksi deposit
tidak akan lagi berfungsi dengan benar karena pengambilan transaksi berversi
atau blok yang berisi transaksi berversi akan mengembalikan kesalahan.

- `{"maxSupportedTransactionVersion": 1}`

  Parameter `maxSupportedTransactionVersion` harus ditambahkan ke permintaan `getBlock` dan
  `getTransaction` untuk menghindari gangguan pada deteksi deposit. Versi transaksi terbaru adalah `0`, dengan
  [format v1](/docs/core/transactions/versioned-transactions#v1-message-format)
  yang akan aktif bersama Agave v4.2 — tetapkan nilainya ke integer `1` sekarang untuk
  mengantisipasi aktivasi tersebut (meminta versi yang lebih tinggi dari yang didukung node adalah
  aman). Satu transaksi dengan versi yang tidak didukung akan menggagalkan **seluruh**
  respons `getBlock`, sedangkan `getSignaturesForAddress` tidak pernah gagal karena versi — jadi
  tanpa opt-in, deposit v1 akan muncul dalam daftar tanda tangan tetapi tidak dapat
  diambil.

  Setelah v1 aktif, ada dua perubahan lagi yang perlu diperhatikan untuk pipeline deposit: transaksi v1
  membawa batas komputasi dan biaya dalam objek pesan `transactionConfig`
  alih-alih instruksi ComputeBudget (pipeline mana pun yang memindai
  instruksi untuk biaya akan melaporkan nol untuk v1), dan v1 tidak menggunakan tabel pencarian alamat.

Penting untuk dipahami bahwa transaksi berversi memungkinkan pengguna membuat
transaksi yang menggunakan kumpulan kunci akun lain yang dimuat dari tabel
lookup alamat onchain.

- `{"encoding": "jsonParsed"}`

  Saat mengambil blok dan transaksi, sekarang disarankan untuk menggunakan encoding
  `"jsonParsed"` karena menyertakan semua kunci akun transaksi (termasuk yang
  berasal dari tabel lookup) dalam daftar `"accountKeys"` pesan. Hal ini
  memudahkan penyelesaian perubahan saldo yang dirinci dalam `preBalances`
  / `postBalances` dan `preTokenBalances` / `postTokenBalances`.

  Jika encoding `"json"` digunakan sebagai gantinya, entri dalam `preBalances` /
  `postBalances` dan `preTokenBalances` / `postTokenBalances` mungkin merujuk pada
  kunci akun yang **TIDAK** ada dalam daftar `"accountKeys"` dan perlu diselesaikan
  menggunakan entri `"loadedAddresses"` dalam metadata transaksi.

### Poll untuk Blok

Untuk melacak semua akun deposit di bursa Anda, lakukan poll untuk setiap blok
yang dikonfirmasi dan periksa alamat yang relevan, menggunakan layanan JSON-RPC
dari node API Solana Anda.

- Untuk mengidentifikasi blok yang tersedia, kirimkan permintaan
  [`getBlocks`](/docs/rpc/http/getblocks), dengan meneruskan blok terakhir yang
  telah Anda proses sebagai parameter start-slot:

```shell
curl https://api.devnet.solana.com -X POST -H "Content-Type: application/json" -d '{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "getBlocks",
  "params": [160017005, 160017015]
}'
```

##### Hasil

```json
{
  "jsonrpc": "2.0",
  "result": [
    160017005, 160017006, 160017007, 160017012, 160017013, 160017014, 160017015
  ],
  "id": 1
```

urutan bilangan bulat tersebut.

### Tips Pengambilan Blok

- `{"rewards": false}`

Secara default, blok yang diambil akan mengembalikan informasi tentang biaya
validator pada setiap blok dan hadiah staking pada batas epoch. Jika Anda tidak
memerlukan informasi ini, nonaktifkan dengan parameter "rewards".

- `{"transactionDetails": "accounts"}`

Secara default, blok yang diambil akan mengembalikan banyak informasi transaksi
dan metadata yang tidak diperlukan untuk melacak saldo akun. Atur parameter
"transactionDetails" untuk mempercepat pengambilan blok.

```shell

  "id": 1,
  "method": "getBlock",
  "params": [

    {
```

## Mengirim Penarikan

Untuk mengakomodasi permintaan penarikan SOL dari pengguna, Anda harus membuat transaksi transfer Solana, dan mengirimkannya ke node API untuk diteruskan ke klaster Anda.

### Sinkron

Mengirim transfer sinkron ke klaster Solana memungkinkan Anda memastikan dengan mudah bahwa transfer berhasil dan telah difinalisasi oleh klaster.

Alat baris perintah Solana menawarkan perintah sederhana, `solana transfer`, untuk membuat, mengirimkan, dan mengonfirmasi transaksi transfer. Secara default, metode ini akan menunggu dan melacak kemajuan di stderr hingga transaksi difinalisasi oleh klaster. Jika transaksi gagal, metode ini akan melaporkan semua error transaksi.

```shell
solana transfer <USER_ADDRESS> <AMOUNT> --allow-unfunded-recipient --keypair <KEYPAIR> --url http://localhost:8899
```

[Solana Javascript SDK](https://github.com/solana-labs/solana-web3.js) menawarkan pendekatan serupa untuk ekosistem JS. Gunakan `SystemProgram` untuk membangun transaksi transfer, dan kirimkan menggunakan metode `sendAndConfirmTransaction`.

### Asinkron

Untuk fleksibilitas yang lebih besar, Anda dapat mengirimkan transfer penarikan secara asinkron. Dalam kasus ini, Anda bertanggung jawab untuk memverifikasi bahwa transaksi berhasil dan telah difinalisasi oleh klaster.

**Catatan:** Setiap transaksi berisi [blockhash terkini](/docs/core/transactions/transaction-structure#recent-blockhash) untuk menunjukkan aktualitasnya. Sangat **penting** untuk menunggu hingga blockhash ini kedaluwarsa sebelum mencoba kembali transfer penarikan yang tampaknya belum dikonfirmasi atau difinalisasi oleh klaster. Jika tidak, Anda berisiko melakukan pengeluaran ganda. Lihat selengkapnya tentang [kedaluwarsa blockhash](#blockhash-expiration) di bawah ini.

Pertama, dapatkan blockhash terbaru beserta tinggi blok terakhir yang valid menggunakan
[endpoint `getLatestBlockhash`](/docs/rpc/http/getlatestblockhash):

```shell
curl http://localhost:8899 -X POST -H "Content-Type: application/json" -d '{
  "jsonrpc":"2.0",
  "id":1,
  "method":"getLatestBlockhash",
  "params":[{"commitment":"finalized"}]
}'
```

Pada alat baris perintah, tambahkan argumen `--no-wait` untuk mengirim transfer secara asinkron, dan sertakan blockhash terkini Anda dengan argumen `--blockhash`:

```shell
solana transfer <USER_ADDRESS> <AMOUNT> --no-wait --allow-unfunded-recipient --blockhash <RECENT_BLOCKHASH> --keypair <KEYPAIR> --url http://localhost:8899
```

Anda juga dapat membangun, menandatangani, dan membuat serial transaksi secara manual, lalu mengirimkannya ke klaster menggunakan endpoint JSON-RPC [`sendTransaction`](/docs/rpc/http/sendtransaction).

#### Kedaluwarsa Blockhash

Anda dapat memeriksa apakah suatu blockhash tertentu masih valid dengan mengirimkan permintaan

### Memvalidasi Alamat Akun yang Diberikan Pengguna untuk Penarikan

Karena penarikan bersifat tidak dapat dibatalkan, sebaiknya validasi alamat akun yang diberikan pengguna sebelum mengotorisasi penarikan guna mencegah kehilangan dana pengguna secara tidak sengaja.

#### Verifikasi dasar

Alamat Solana adalah array 32 byte, yang dikodekan dengan alfabet base58 bitcoin. Hasilnya berupa string teks ASCII yang cocok dengan ekspresi reguler berikut:

```text
[1-9A-HJ-NP-Za-km-z]{32,44}
```

Pemeriksaan ini saja tidak cukup karena alamat Solana tidak memiliki checksum, sehingga kesalahan ketik tidak dapat terdeteksi. Untuk memvalidasi input pengguna lebih lanjut, string dapat didekode dan panjang array byte yang dihasilkan dikonfirmasi sebesar 32. Namun, ada beberapa alamat yang dapat didekode menjadi 32 byte meskipun terdapat kesalahan ketik seperti satu karakter yang hilang, karakter yang terbalik, dan huruf kapital yang diabaikan.

#### Verifikasi lanjutan

Karena kerentanan terhadap kesalahan ketik yang dijelaskan di atas, disarankan agar saldo dikueri untuk alamat penarikan kandidat dan pengguna diminta untuk mengonfirmasi niatnya jika saldo non-nol ditemukan.

#### Pemeriksaan pubkey ed25519 yang valid

Alamat akun normal di Solana adalah string berenkode Base58 dari kunci publik ed25519 256-bit. Tidak semua pola bit merupakan kunci publik yang valid untuk kurva ed25519, sehingga memungkinkan untuk memastikan alamat akun yang diberikan pengguna setidaknya merupakan pubkey ed25519 yang benar.

#### Java

Berikut adalah contoh Java untuk memvalidasi alamat yang diberikan pengguna sebagai pubkey ed25519 yang valid:

Contoh kode berikut mengasumsikan Anda menggunakan Maven.

`pom.xml`:

```xml
<repositories>
  ...
  <repository>
    <id>spring</id>
    <url>https://repo.spring.io/libs-release/</url>
  </repository>
</repositories>

...

<dependencies>
  ...
  <dependency>
      <groupId>io.github.novacrypto</groupId>
      <artifactId>Base58</artifactId>
      <version>0.1.3</version>
  </dependency>
  <dependency>
      <groupId>cafe.cryptography</groupId>
      <artifactId>curve25519-elisabeth</artifactId>
      <version>0.1.0</version>
  </dependency>
<dependencies>
```

```java
import io.github.novacrypto.base58.Base58;
import cafe.cryptography.curve25519.CompressedEdwardsY;

public class PubkeyValidator
{
    public static boolean verifyPubkey(String userProvidedPubkey)
    {
        try {
            return _verifyPubkeyInternal(userProvidedPubkey);
        } catch (Exception e) {
            return false;
        }
    }

    public static boolean _verifyPubkeyInternal(String maybePubkey) throws Exception
    {
        byte[] bytes = Base58.base58Decode(maybePubkey);
        return !(new CompressedEdwardsY(bytes)).decompress().isSmallOrder();
    }
}
```

## Biaya Prioritas dan Unit Komputasi

Pada periode permintaan tinggi, ada kemungkinan transaksi kedaluwarsa sebelum validator menyertakan transaksi tersebut dalam blok mereka karena mereka memilih transaksi lain dengan nilai ekonomi yang lebih tinggi. Transaksi yang valid di Solana dapat tertunda atau dibatalkan jika Biaya Prioritas tidak diimplementasikan dengan benar.

[Biaya Prioritas](/docs/references/terminology#prioritization-fee) adalah biaya tambahan yang dapat ditambahkan di atas [Biaya Transaksi dasar](/docs/core/fees/fee-structure#base-fee) untuk memastikan penyertaan transaksi dalam blok dalam situasi ini dan membantu memastikan keterjangkauannya.

Biaya prioritas ini ditambahkan ke transaksi dengan menambahkan instruksi Compute Budget khusus yang menetapkan biaya prioritas yang ingin dibayar.

<Callout type="warn" title="Catatan Penting">

Kegagalan mengimplementasikan instruksi ini dapat mengakibatkan gangguan jaringan dan transaksi yang dibatalkan. Sangat disarankan agar setiap bursa yang mendukung Solana menggunakan biaya prioritas untuk menghindari gangguan.

</Callout>

### Apa itu Biaya Prioritas?

Biaya Prioritas dihargai dalam micro-lamport per Unit Komputasi (misalnya, jumlah kecil SOL) yang ditambahkan di awal transaksi agar secara ekonomi menarik bagi node validator untuk disertakan dalam blok di jaringan.

### Berapa Besar Biaya Prioritas yang Harus Ditetapkan?

Metode untuk menetapkan biaya prioritas Anda harus melibatkan kueri biaya prioritas terkini untuk menetapkan biaya yang kemungkinan besar menarik bagi jaringan. Menggunakan metode RPC [`getRecentPrioritizationFees`](/docs/rpc/http/getrecentprioritizationfees), Anda dapat melakukan kueri biaya prioritas yang diperlukan untuk menempatkan transaksi dalam blok terkini.

Strategi penetapan harga untuk biaya prioritas ini akan bervariasi berdasarkan kasus penggunaan Anda. Tidak ada cara baku untuk melakukannya. Salah satu strategi untuk menetapkan Biaya Prioritas Anda mungkin adalah menghitung tingkat keberhasilan transaksi Anda, lalu meningkatkan Biaya Prioritas berdasarkan kueri ke API biaya transaksi terkini dan menyesuaikannya. Penetapan harga untuk Biaya Prioritas akan bersifat dinamis berdasarkan aktivitas di jaringan dan penawaran yang ditempatkan oleh peserta lain, yang hanya dapat diketahui setelah fakta terjadi.

Salah satu tantangan dalam menggunakan panggilan API `getRecentPrioritizationFees` adalah bahwa panggilan tersebut mungkin hanya mengembalikan biaya terendah untuk setiap blok. Ini sering kali bernilai nol, yang bukan merupakan perkiraan yang sepenuhnya berguna tentang Biaya Prioritas yang harus digunakan agar tidak ditolak oleh node validator.

API `getRecentPrioritizationFees` mengambil pubkey akun sebagai parameter, lalu mengembalikan nilai tertinggi dari biaya prioritas minimum untuk akun-akun tersebut. Jika tidak ada akun yang ditentukan, API akan mengembalikan biaya terendah untuk masuk ke blok, yang biasanya nol (kecuali blok penuh).

Bursa dan aplikasi harus melakukan kueri endpoint RPC dengan akun yang akan dikunci-tulis oleh transaksi. Endpoint RPC akan mengembalikan `max(account_1_min_fee, account_2_min_fee, ... account_n_min_fee)`, yang seharusnya menjadi titik dasar bagi pengguna untuk menetapkan biaya prioritas untuk transaksi tersebut.

Ada berbagai pendekatan untuk menetapkan Biaya Prioritas dan beberapa [API pihak ketiga](https://docs.helius.dev/solana-rpc-nodes/alpha-priority-fee-api) tersedia untuk menentukan biaya terbaik yang harus diterapkan. Mengingat sifat jaringan yang dinamis, tidak akan ada cara yang "sempurna" untuk menetapkan harga Biaya Prioritas Anda, dan analisis yang cermat harus diterapkan sebelum memilih jalan ke depan.

### Cara Mengimplementasikan Biaya Prioritas

Menambahkan biaya prioritas pada transaksi terdiri dari menambahkan dua instruksi Compute Budget di awal transaksi tertentu:

- satu untuk menetapkan harga unit komputasi, dan
- satu lagi untuk menetapkan batas unit komputasi

> Di sini, Anda juga dapat menemukan
> [panduan developer yang lebih lengkap tentang cara menggunakan biaya prioritas](/docs/core/fees) yang mencakup informasi lebih lanjut tentang mengimplementasikan biaya prioritas.

Buat instruksi `setComputeUnitPrice` untuk menambahkan Biaya Prioritas di atas Biaya Transaksi Dasar (5.000 lamport).

```typescript
// import { ComputeBudgetProgram } from "@solana/web3.js"
ComputeBudgetProgram.setComputeUnitPrice({ microLamports: number });
```

Nilai yang diberikan dalam micro-lamport akan dikalikan dengan anggaran Unit Komputasi (CU) untuk menentukan Biaya Prioritas dalam lamport. Misalnya, jika anggaran CU Anda adalah 1 juta CU, dan Anda menambahkan `1 microLamport/CU`, Biaya Prioritas akan menjadi 1 lamport (1 juta \* 0,000001). Total biaya kemudian akan menjadi 5.001 lamport.

Untuk menetapkan anggaran unit komputasi baru untuk transaksi, buat instruksi `setComputeUnitLimit`

```typescript
// import { ComputeBudgetProgram } from "@solana/web3.js"
ComputeBudgetProgram.setComputeUnitLimit({ units: number });
```

Nilai `units` yang diberikan akan menggantikan nilai anggaran komputasi default dari runtime Solana.

<Callout type="warn" title="Tetapkan CU minimum yang diperlukan untuk transaksi">

Transaksi harus meminta jumlah minimum unit komputasi (CU) yang diperlukan untuk eksekusi guna memaksimalkan throughput dan meminimalkan biaya keseluruhan.

Anda dapat mengetahui CU yang dikonsumsi oleh transaksi dengan mengirimkan transaksi di klaster Solana yang berbeda, seperti devnet. Misalnya, [transfer token sederhana](https://explorer.solana.com/tx/5scDyuiiEbLxjLUww3APE9X7i8LE3H63unzonUwMG7s2htpoAGG17sgRsNAhR1zVs6NQAnZeRVemVbkAct5myi17) membutuhkan 300 CU.

</Callout>

```typescript
// import { ... } from "@solana/web3.js"

const modifyComputeUnits = ComputeBudgetProgram.setComputeUnitLimit({
  // note: set this to be the lowest actual CU consumed by the transaction
  units: 300
});

const addPriorityFee = ComputeBudgetProgram.setComputeUnitPrice({
  microLamports: 1
});

const transaction = new Transaction()
  .add(modifyComputeUnits)
  .add(addPriorityFee)
  .add(
    SystemProgram.transfer({
      fromPubkey: payer.publicKey,
      toPubkey: toAccount,
      lamports: 10000000
    })
  );
```

## Mendukung Standar SPL Token

[SPL Token](https://spl.solana.com/token) adalah standar untuk pembuatan dan pertukaran token
terbungkus/sintetis di blockchain Solana.

Alur kerja SPL Token mirip dengan token SOL asli, tetapi ada beberapa perbedaan yang akan dibahas di bagian ini.

### Token Mints

Setiap _jenis_ SPL Token dideklarasikan dengan membuat sebuah _mint_ account. Akun ini menyimpan metadata yang mendeskripsikan fitur token seperti pasokan, jumlah desimal, dan berbagai otoritas yang mengendalikan mint. Setiap SPL Token account mereferensikan mint yang terkait dan hanya dapat berinteraksi dengan SPL Token dari jenis tersebut.

### Menginstal Alat CLI `spl-token`

SPL Token accounts dikueri dan dimodifikasi menggunakan utilitas baris perintah `spl-token`. Contoh-contoh yang disediakan di bagian ini memerlukan pemasangannya di sistem lokal.

`spl-token` didistribusikan dari Rust
[crates.io](https://crates.io/crates/spl-token) melalui utilitas baris perintah `cargo` Rust.
Versi terbaru `cargo` dapat diinstal menggunakan satu baris perintah yang praktis untuk platform Anda di [rustup.rs](https://rustup.rs). Setelah `cargo` terinstal, `spl-token` dapat diperoleh dengan perintah berikut:

```shell
cargo install spl-token-cli
```

Anda kemudian dapat memeriksa versi yang terinstal untuk memverifikasi

```shell
spl-token --version
```

Ini akan mencetak versi yang terpasang, misalnya:

```text
spl-token-cli 5.6.1
```

Gunakan versi 5.6.1 atau yang lebih baru jika Anda memerlukan dukungan SPL Token-2022.

### Penyetoran

Karena setiap pasangan `(wallet, mint)` memerlukan akun terpisah di onchain. Disarankan agar alamat untuk akun-akun ini diturunkan dari wallet deposit SOL menggunakan skema
[Associated Token Account](https://spl.solana.com/associated-token-account)
(ATA) dan bahwa _hanya_ deposit dari alamat ATA yang diterima.

Pemantauan transaksi deposit harus mengikuti metode
[block polling](#poll-for-blocks) yang dijelaskan di atas. Setiap blok baru harus
dipindai untuk menemukan transaksi yang berhasil yang menyertakan alamat token account pengguna dan bursa.

<Callout type="warn">

Kolom `preTokenBalances` dan `postTokenBalances` dari metadata transaksi harus digunakan untuk menentukan perubahan saldo efektif. Kolom-kolom ini mencakup token mint, pemilik token account (alamat wallet), serta saldo token account sebelum dan sesudah transaksi.

</Callout>

<Callout>

Jika token account dibuat sebagai bagian dari transaksi (misalnya saat menerima token untuk pertama kalinya), token account tersebut tidak akan muncul dalam array `preTokenBalances` karena belum ada sebelum transaksi. Dalam skenario ini, Anda harus memperlakukan saldo awal sebagai nol saat menghitung jumlah deposit. Akun yang baru dibuat hanya akan muncul dalam array `postTokenBalances` dengan saldo akhirnya setelah transaksi selesai.

</Callout>

#### Kalkulasi Deposit Token

Untuk melacak deposit token secara akurat, Anda harus membandingkan kolom `preTokenBalances` dan `postTokenBalance` dalam metadata transaksi. Kolom-kolom ini menunjukkan saldo token dan pemilik token account sebelum dan sesudah transaksi, memungkinkan Anda untuk menghitung jumlah pasti token yang ditransfer. Pendekatan ini memastikan Anda menangkap perubahan saldo yang sebenarnya.

- Jika kolom `owner` dari `preTokenBalances` dan `postTokenBalances`
  tetap sama, hitung selisih antara kolom `amount`.
- Jika kepemilikan token account berubah (kolom `owner` yang berbeda antara
  `preTokenBalances` dan `postTokenBalances`), dan pemilik baru dalam
  `postTokenBalance` cocok dengan alamat `owner` yang diharapkan bursa Anda, maka
  pertimbangkan seluruh saldo yang ditampilkan dalam kolom `amount` dari `postTokenBalances`
  sebagai jumlah yang didepositkan.

### Penarikan

Alamat penarikan yang diberikan pengguna harus berupa alamat dompet SOL mereka.

Sebelum mengeksekusi [transfer](#token-transfers) penarikan, exchange harus
memeriksa alamat tersebut sebagaimana
[dijelaskan di atas](#validating-user-supplied-account-addresses-for-withdrawals).
Selain itu, alamat ini harus dimiliki oleh System Program dan tidak memiliki
data akun. Jika alamat tidak memiliki saldo SOL, konfirmasi pengguna harus
diperoleh sebelum melanjutkan penarikan. Semua alamat penarikan lainnya
harus ditolak.

Dari alamat penarikan,
[Associated Token Account](https://spl.solana.com/associated-token-account)
(ATA) untuk mint yang sesuai diturunkan dan transfer diterbitkan ke akun tersebut
melalui instruksi
[TransferChecked](https://github.com/solana-labs/solana-program-library/blob/fc0d6a2db79bd6499f04b9be7ead0c400283845e/token/program/src/instruction.rs#L268).
Perlu dicatat bahwa alamat ATA mungkin belum ada,
di mana exchange harus mendanai akun atas nama pengguna. Untuk
akun SPL Token, mendanai akun penarikan akan memerlukan 0.00203928 SOL
(2.039.280 lamport).

Template perintah `spl-token transfer` untuk penarikan:

```shell
spl-token transfer --fund-recipient <exchange token account> <withdrawal amount> <withdrawal address>
```

### Pertimbangan Lainnya

#### Freeze Authority

Untuk alasan kepatuhan regulasi, entitas penerbit SPL Token dapat secara opsional
memilih untuk memegang "Freeze Authority" atas semua akun yang dibuat terkait
dengan mint-nya. Hal ini memungkinkan mereka untuk
[membekukan](https://spl.solana.com/token#freezing-accounts) aset di akun tertentu
sesuai keinginan, membuat akun tidak dapat digunakan hingga dicairkan. Jika fitur ini
digunakan, pubkey dari freeze authority akan terdaftar di mint account SPL Token.

### Dukungan Dasar untuk Standar SPL Token-2022 (Token Extensions)

[SPL Token-2022](https://spl.solana.com/token-2022) adalah standar terbaru untuk
pembuatan dan pertukaran token wrapped/sintetis di blockchain Solana.

Juga dikenal sebagai "Token Extensions", standar ini memiliki banyak fitur baru yang
dapat diaktifkan secara opsional oleh pembuat token dan pemegang akun. Fitur-fitur ini mencakup
Confidential Balances, biaya transfer, penutupan mint, metadata, delegasi permanen,
kepemilikan tidak dapat diubah, dan masih banyak lagi. Silakan lihat
[panduan ekstensi](https://spl.solana.com/token-2022/extensions) untuk informasi
lebih lanjut.

Jika exchange Anda mendukung SPL Token, tidak banyak pekerjaan tambahan yang diperlukan untuk
mendukung SPL Token-2022:

- alat CLI bekerja secara mulus dengan kedua program mulai dari versi 3.0.0.
- `preTokenBalances` dan `postTokenBalances` mencakup saldo SPL Token-2022
- RPC mengindeks akun SPL Token-2022, tetapi harus dikueri secara terpisah dengan
  program id `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb`

Associated Token Account bekerja dengan cara yang sama, dan menghitung dengan tepat jumlah
deposit SOL yang diperlukan untuk akun baru.

Namun karena adanya ekstensi, akun mungkin lebih besar dari 165 byte, sehingga
mungkin memerlukan lebih dari 0.00203928 SOL untuk didanai.

Sebagai contoh, program Associated Token Account selalu menyertakan ekstensi "immutable
owner", sehingga akun membutuhkan minimal 170 byte, yang memerlukan
0.00207408 SOL.

### Pertimbangan Khusus Ekstensi

Bagian sebelumnya menguraikan dukungan paling dasar untuk SPL Token-2022. Karena
ekstensi memodifikasi perilaku token, exchange mungkin perlu mengubah cara
mereka menangani token.

Dimungkinkan untuk melihat semua ekstensi pada mint atau token account:

```shell
spl-token display <account address>
```

#### Biaya Transfer

Token dapat dikonfigurasi dengan biaya transfer, di mana sebagian token yang ditransfer
ditahan di tujuan untuk pengumpulan di masa mendatang.

Jika exchange Anda mentransfer token-token ini, perlu diketahui bahwa tidak semua token akan tiba di
tujuan karena adanya jumlah yang ditahan.

Dimungkinkan untuk menentukan biaya yang diharapkan selama transfer untuk menghindari kejutan:

```shell
spl-token transfer --expected-fee <fee amount> --fund-recipient <exchange token account> <withdrawal amount> <withdrawal address>
```

#### Mint Close Authority

Dengan ekstensi ini, pembuat token dapat menutup mint, asalkan pasokan
token adalah nol.

Ketika mint ditutup, mungkin masih ada token account kosong yang ada, dan
token account tersebut tidak lagi dikaitkan dengan mint yang valid.

Aman untuk menutup token account tersebut:

```shell
spl-token close --address <account address>
```

#### Saldo Rahasia

Mint dapat dikonfigurasi dengan Confidential Balances, sehingga jumlah token
dienkripsi tetapi pemilik akun tetap bersifat publik.

Bursa dapat mengonfigurasi token account untuk mengirim dan menerima transfer rahasia,
guna menyembunyikan jumlah pengguna. Tidak diperlukan untuk mengaktifkan Confidential Balances
pada token account, sehingga bursa dapat memaksa pengguna mengirim token
secara non-rahasia.

Untuk mengaktifkan Confidential Balances, konfigurasikan akun:

```shell
spl-token configure-confidential-transfer-account --address <account address>
```

Dan untuk melakukan transfer:

```shell
spl-token transfer --confidential <exchange token account> <withdrawal amount> <withdrawal address>
```

Selama transfer rahasia, kolom `preTokenBalance` dan `postTokenBalance`
tidak akan menunjukkan perubahan. Untuk menyapu akun deposit, Anda harus mendekripsi
saldo baru guna menarik token:

```shell
spl-token apply-pending-balance --address <account address>
spl-token withdraw-confidential-tokens --address <account address> <amount or ALL>
```

#### Status Akun Default

Mint dapat dikonfigurasi dengan status akun default, sehingga semua token account baru
dibekukan secara default. Pembuat token ini mungkin mengharuskan pengguna untuk melalui
proses terpisah untuk mencairkan akun.

#### Non-Transferable

Beberapa token tidak dapat ditransfer, tetapi masih dapat dibakar dan akunnya
dapat ditutup.

#### Permanent Delegate

Pembuat token dapat menunjuk permanent delegate untuk semua token mereka. Permanent
delegate dapat mentransfer atau membakar token dari akun mana pun, yang berpotensi
mencuri dana.

Ini adalah persyaratan hukum untuk stablecoin di yurisdiksi tertentu, atau dapat
digunakan untuk skema penarikan kembali token.

Waspadai bahwa token-token ini mungkin ditransfer tanpa sepengetahuan exchange Anda.

#### Transfer Hook

Token dapat dikonfigurasi dengan program tambahan yang harus dipanggil selama
transfer, untuk memvalidasi transfer atau menjalankan logika lainnya.

Karena runtime Solana mengharuskan semua akun diteruskan secara eksplisit ke
program, dan transfer hook memerlukan akun tambahan, exchange perlu
membuat instruksi transfer secara berbeda untuk token-token ini.

CLI dan pembuat instruksi seperti
`createTransferCheckedWithTransferHookInstruction` menambahkan akun tambahan
secara otomatis, tetapi akun tambahan juga dapat ditentukan secara eksplisit:

```shell
spl-token transfer --transfer-hook-account <pubkey:role> --transfer-hook-account <pubkey:role> ...
```

#### Memo Wajib pada Transfer

Pengguna dapat mengonfigurasi token account mereka untuk mewajibkan memo pada transfer.

Exchange mungkin perlu menambahkan instruksi memo sebelum mentransfer token kembali
kepada pengguna, atau mereka dapat mengharuskan pengguna untuk menambahkan instruksi memo sebelum mengirim
ke exchange:

```shell
spl-token transfer --with-memo <memo text> <exchange token account> <withdrawal amount> <withdrawal address>
```
