## Arsitektur

Private Channels terdiri dari empat komponen: dua program Solana on-chain
(Escrow dan Withdraw) dan dua layanan off-chain (Gateway dan Auth Service).
Bersama-sama, keduanya membentuk protokol state channel di mana dana berada di Mainnet tetapi
transfer diselesaikan secara off-chain.

### Program Escrow

Program Escrow adalah program Solana on-chain yang menyimpan token SPL yang
didepositkan. Program ini adalah trust anchor sistem: semua dana pada akhirnya berada di
dalam escrow hingga operator memberikan bukti eksklusi Sparse Merkle Tree yang valid untuk
melepaskannya.

- Program ID: `9tgHa1DcnaSSUtmMsst8ovKTe1Gfxzezn27KnH9xXYeU`
- ID ini dikompilasi ke dalam binary program melalui `declare_id!()`. Layanan off-chain
  membaca ID yang sama saat compile time dari crate klien yang dihasilkan, bukan
  dari environment variable.
- Mengelola PDA `Instance`, `AllowedMint`, dan `Operator`
- Instruksi: `CreateInstance`, `AllowMint`, `BlockMint`, `AddOperator`,
  `RemoveOperator`, `SetNewAdmin`, `Deposit`, `ReleaseFunds`, `ResetSmtRoot`

### Program Withdraw

Program Withdraw berjalan di jaringan private channel, bukan di Solana Mainnet.
Pengguna memanggil `WithdrawFunds` untuk membakar saldo token sisi channel mereka. Pembakaran ini
tidak secara otomatis melepaskan dana; melainkan memberi sinyal kepada operator bahwa
penarikan sedang menunggu. Operator kemudian memanggil `ReleaseFunds` pada Program
Escrow dengan bukti SMT yang valid untuk menyelesaikan settlement.

- Program ID: `J231K9UEpS4y4KAPwGc4gsMNCjKFRMYcQBcjVW7vBhVi`
- ID ini dikompilasi ke dalam binary program. Layanan off-chain membaca ID yang sama
  saat compile time dari crate klien yang dihasilkan, bukan dari environment
  variable.

### Gateway

Gateway adalah proxy yang kompatibel dengan Solana JSON-RPC yang merutekan permintaan klien ke
write node (untuk pengiriman transaksi) dan read node (untuk
kueri) jaringan channel. Gateway dikonfigurasi melalui environment variable: `GATEWAY_PORT`,
`GATEWAY_WRITE_URL`, `GATEWAY_READ_URL`.

Endpoint health (tidak memerlukan autentikasi):

- `GET /health` - pemeriksaan liveness; mengembalikan `200 {"status":"ok"}`
- `GET /ready` - readiness mendalam, memeriksa write + read node; mengembalikan
  `200 {"status":"ready"}` atau `503 {"status":"degraded"}`

#### Perutean Metode RPC dan Akses

Gateway merutekan `sendTransaction` ke write node dan semua metode lainnya ke
read node. Permintaan yang lebih besar dari 64 KB akan ditolak dengan HTTP 413. Ketika
autentikasi diaktifkan, akses metode dijaga oleh peran JWT. Lihat
**[Autentikasi & Peran](/docs/tools/private-channels/concepts/auth)** untuk
matriks metode lengkap.

### Auth Service

Auth Service adalah komponen opsional yang menerbitkan JWT HS256 (masa berlaku 24 jam)
untuk kontrol akses gateway. Komponen ini diaktifkan saat environment variable `JWT_SECRET`
disetel. Tanpanya, gateway menerima semua koneksi.

Klaim JWT: `sub` (UUID pengguna), `role` (`"user"` atau `"operator"`), `iss`
(`"private-channel-auth"`), `aud` (`"private-channel-gateway"`), `exp` (Unix
timestamp). `iss` dan `aud` divalidasi oleh konfigurasi JWT gateway,
bukan dideserialisasi ke dalam struct klaim aplikasi: hanya `sub`, `role`, dan
`exp` yang tersedia untuk kode lapisan aplikasi.

Peran:

- `user` - akses dibatasi pada wallet terverifikasi milik sendiri; tidak dapat memanggil `getBlock`,
  `getTransaction`, atau `simulateTransaction`
- `operator` - melewati semua pemeriksaan kepemilikan; akses penuh ke metode RPC; harus
  disediakan dalam database (tidak ada eskalasi mandiri)

### Streamer

Streamer adalah server WebSocket yang mendorong pembaruan state channel ke
klien yang terhubung secara real time, menghilangkan kebutuhan untuk melakukan polling pada RPC. Streamer melakukan polling
PostgreSQL untuk perubahan state. Streamer merupakan bagian dari stack Docker Compose dasar, bukan
stack devnet yang di-deploy oleh panduan ini; lihat
[referensi Konfigurasi](/docs/tools/private-channels/operators/configuration#service-port-reference).

- Port: `8902`, dapat dikonfigurasi melalui `STREAMER_PORT`
- Koneksi: `ws://localhost:8902`
- Endpoint health: `GET /health` - mengembalikan `503` jika ada loop polling internal
  yang terhenti lebih dari 30 detik

<Callout type="warning">
  Skema event WebSocket belum terdokumentasi secara publik. Lihat
  [`core/src/bin/streamer.rs`](https://github.com/solana-foundation/solana-private-channels/blob/main/core/src/bin/streamer.rs)
  untuk detail implementasi hingga dokumentasi resmi tersedia.
</Callout>

## Pipeline Transaksi

```text
Transaction -> [1:Dedup] -> [2:SigVerify] -> [3:Sequencer] -> [4:Executor] -> [5:Settler] -> Database
```

Transaksi yang dikirimkan ke Gateway mengalir melalui pipeline lima tahap sebelum
state-nya di-commit:

1. **Dedup** - memfilter transaksi duplikat sebelum masuk ke pipeline
2. **SigVerify** - memvalidasi tanda tangan transaksi terhadap kunci publik penanda tangan
3. **Sequencer** - mengurutkan transaksi yang valid secara deterministik untuk membangun
   riwayat kanonik
4. **Executor** - mengeksekusi transaksi terhadap lapisan akun channel
   (BOB Cache + AccountsDB), memperbarui saldo secara off-chain
5. **Settler** - meng-commit hasil transaksi yang terakumulasi ke PostgreSQL dan
   memperbarui cache Redis; menghasilkan blockhash baru untuk siklus blok berikutnya.
   Settlement Mainnet (memanggil `ReleaseFunds`) ditangani secara terpisah oleh layanan
   `operator-private-channel`

## Fitur Utama

### Privasi

Transfer antar peserta channel tidak dicatat di Solana Mainnet. Hanya
deposit (masuk ke channel) dan penarikan akhir (keluar dari channel)
yang muncul on-chain. Identitas counterparty dan jumlah transfer tidak terlihat oleh
pengamat luar selama operasi channel berlangsung.

### Performa

Pipeline off-chain menghilangkan waktu blok Solana dari jalur kritis.
Transfer dikonfirmasi ketika sequencer memprosesnya, bukan ketika blok Solana
dikonfirmasi. Hal ini memungkinkan finalitas sub-detik dan throughput melampaui TPS
nasional Solana untuk transfer lapisan aplikasi.

### Settlement

Setiap penarikan dilindungi oleh bukti Sparse Merkle Tree on-chain. Root SMT
disimpan di `Instance.withdrawal_transactions_root` pada Program Escrow.
Ketika `ReleaseFunds` dipanggil, program pertama-tama memverifikasi bukti eksklusi untuk
nonce yang belum terlihat terhadap root on-chain saat ini, kemudian memverifikasi bukti
inklusi terpisah untuk nonce tersebut terhadap root baru yang disuplai pemanggil. Hanya setelah
kedua pemeriksaan lulus, root baru disimpan, sehingga double-spend tidak mungkin terjadi bahkan
jika kunci operator dikompromikan.

## Model Keamanan

**Kunci admin** - mengontrol pembuatan instance (`CreateInstance`) dan
provisioning operator (`AddOperator` / `RemoveOperator`). Kompromi kunci admin
memungkinkan provisioning operator secara sewenang-wenang. `SetNewAdmin` mentransfer otoritas admin
secara tidak dapat dibatalkan dalam satu langkah; lindungi kunci admin dengan tepat.

**Kunci operator** - dapat memanggil `ReleaseFunds` dan `ResetSmtRoot`. Kunci ini tidak dapat
melepaskan dana tanpa bukti eksklusi SMT yang valid terhadap root on-chain saat ini.
Pemeriksaan `verify_smt_exclusion_proof` on-chain adalah pertahanan terakhir
terhadap penarikan yang tidak sah: kunci operator yang dikompromikan saja tidak
cukup untuk menguras escrow.

**Root SMT** - disimpan on-chain di `Instance.withdrawal_transactions_root`.
Diperbarui secara atomik dengan setiap panggilan `ReleaseFunds`. Karena setiap bukti harusmereferensikan nonce yang belum terlihat, double-spending saldo channel yang sama tidak
mungkin terjadi bahkan jika kunci operator dikompromikan.

**Rotasi tree** - `Instance.current_tree_index` melacak epoch tree. Ketika
`ResetSmtRoot` dipanggil, indeks tree bertambah dan semua
nonce dari epoch tree sebelumnya dibatalkan, memberikan slate bersih untuk siklus
settlement baru.

## Keamanan Kunci Operasional

<Callout type="warning">
  Layanan off-chain menggunakan kosakata penanda tangan mereka sendiri, yang tidak terkait dengan
  otoritas admin/operator on-chain yang dijelaskan dalam Model Keamanan di atas.
  `ADMIN_PRIVATE_KEY` diperlukan untuk setiap layanan operator dan membayar
  biaya transaksi; `OPERATOR_PRIVATE_KEY` yang terpisah dan opsional menyuplai
  tanda tangan Operator on-chain untuk `ReleaseFunds` dan `ResetSmtRoot`, dan
  kembali ke nilai `ADMIN_PRIVATE_KEY` jika tidak disetel. Jangan pernah memasukkan kunci admin
  instance tingkat protokol (yang digunakan untuk `CreateInstance` / `AddOperator` / `SetNewAdmin`)
  ke dalam salah satu variabel atau mengeksposnya saat runtime; simpan kunci tersebut secara cold dan offline.
</Callout>

`ReleaseFunds` dan `ResetSmtRoot` memerlukan dua tanda tangan on-chain: fee payer
(dari `ADMIN_PRIVATE_KEY`) dan otoritas PDA Operator (dari
`OPERATOR_PRIVATE_KEY`, atau `ADMIN_PRIVATE_KEY` jika tidak disetel). Panduan deployment
ini dalam walkthrough devnet memasukkan keypair operator yang dihasilkan ke dalam
`ADMIN_PRIVATE_KEY` dan membiarkan `OPERATOR_PRIVATE_KEY` tidak disetel, sehingga keypair yang sama
mengisi kedua peran penanda tangan. Perlakukan kunci mana pun yang berakhir di `ADMIN_PRIVATE_KEY` dengan
kontrol yang sama seperti kunci privat hot wallet:

- Simpan hanya di file `.env` yang diabaikan git, jangan pernah di `.env.devnet` atau konfigurasi
  apa pun yang di-commit
- Untuk deployment produksi, pertimbangkan secrets manager (AWS Secrets Manager,
  HashiCorp Vault) daripada env var plaintext
- keypair admin instance tingkat protokol (yang digunakan untuk memanggil `AddOperator` /
  `SetNewAdmin`) harus disimpan secara cold; hanya diperlukan selama setup instance
  dan provisioning operator, bukan selama runtime

`SetNewAdmin` mentransfer hak admin **secara tidak dapat dibatalkan dalam satu transaksi**:
admin saat ini tidak memiliki jalur pemulihan tanpa kerja sama admin baru. Jangan
memanggil fungsi ini tanpa memverifikasi alamat target.
