Das Signieren einer Nachricht beweist, dass ein Nutzer eine Wallet kontrolliert – ohne Transaktion, ohne Fee und ohne Netzwerkaufruf. Apps verwenden signierte Nachrichten, um Nutzer anzumelden, festzuhalten, dass ein Nutzer die Nutzungsbedingungen akzeptiert hat, eine Wallet mit bestehenden Konten zu verknüpfen oder eine Aktion zu autorisieren, die Off-Chain stattfindet, etwa das Aufgeben einer Bestellung.

Solana-Wallets signieren Nachrichten auf zwei Arten:

- **Off-Chain-Nachrichten** (`solana:signOffchainMessage`) verpacken Ihren Text in ein Standardformat, das durch die [Spezifikation](https://docs.anza.xyz/proposals/off-chain-message-signing) für Off-Chain-Nachrichtensignierung (OCMS) definiert ist.
  Das Format kann nie mit einer Transaktion verwechselt werden, benennt die Konten, die es signieren müssen, und ist das Format, das Hardware-Wallets signieren.
- **Rohnachrichten** (`solana:signMessage`) signieren exakt die Bytes, die Ihre App übergibt, ohne Präfix und ohne deklarierte Signer. Die meisten Software-Wallets unterstützen sie, aber nichts in den Bytes kennzeichnet sie als Nachricht statt als Transaktion.

Verwenden Sie Off-Chain-Nachrichten, wo die Wallet sie unterstützt, und weichen Sie auf Rohnachrichten aus, wo dies nicht der Fall ist. Der Rest dieses Leitfadens verwendet die Anmeldung als durchgängiges Beispiel, aber dieselben Signier- und Verifizierungsschritte gelten für jede Nachricht.

## Ein Nachrichtenformat wählen

|                           | Off-Chain-Nachricht     | Rohnachricht   | Transaktion                   |
| ------------------------- | --------------------- | ------------- | ----------------------------- |
| Wallet-Funktion            | `signOffchainMessage` | `signMessage` | `signTransaction`             |
| Hardware-Wallet-Unterstützung   | Geräteabhängig     | Nein            | Ja                           |
| Für den Nutzer lesbar      | Ja                   | Nur Software | Geräteabhängig             |
| Deklariert erforderliche Signer | Ja                   | Nein            | Ja                           |
| RPC-Aufrufe und Fee        | Keine                  | Keine          | Blockhash, Senden, Fee, Bestätigen |

### Warum nicht eine Transaktion?

Hardware-Wallets konnten früher keine lesbare Nachricht signieren. Viele Apps wichen darauf aus, diese Nutzer stattdessen um die Signatur einer Transaktion ohne Funktion (No-op) zu bitten. Das funktioniert, bringt aber Latenz, Kosten und Risiken mit sich:

- **Netzwerk-Fee.** Eine Transaktion zahlt eine Fee, selbst wenn sie nichts bewirkt.
- **Mehrere RPC-Aufrufe.** Ihre App ruft einen Blockhash ab, simuliert, sendet und fragt anschließend die Bestätigung ab.
- **Zusätzliche Latenz.** Jeder dieser Aufrufe ist ein Roundtrip, bevor der Nutzer angemeldet ist.
- **Nichts Lesbares.** Der Nutzer genehmigt Transaktionsbytes, nicht eine Erklärung, wozu er zustimmt.
- **Verhaltensrisiko.** Wenn Nutzer allein für den Login eine Transaktion signieren sollen, lassen sie sich leichter dazu verleiten, eine schädliche Transaktion zu signieren.

Eine Off-Chain-Nachricht erspart all das. Der einzige Roundtrip geht an Ihren eigenen Server.

## Was die Wallet signiert

Eine Off-Chain-Nachricht beginnt mit einer festen Signing-Domain, `\xffsolana offchain`.
Keine gültige Transaktion beginnt mit diesen Bytes, daher kann eine signierte Nachricht nie als Transaktion verwendet werden. Version 1 des Formats listet anschließend die erforderlichen Signer auf und enthält die Nachricht als UTF-8-Text ohne Längenbegrenzung.

Die Wallet erstellt diese Bytes, signiert sie und gibt sie zusammen mit der Signatur zurück. Die
[Spezifikation](https://docs.anza.xyz/proposals/off-chain-message-signing)
beschreibt das vollständige Format, einschließlich der älteren Version 0.

<DocsDiagram
  src="/assets/docs/frontend/offchain-message-layout.svg"
  alt="A version 1 off-chain message is a 16-byte signing domain, a version byte, a signer count, each signer's 32-byte public key in sorted order, and the UTF-8 content. The envelope prefixes it with a signature count and one 64-byte signature per signer."
/>

## Eine Anmeldemethode wählen

Noch nicht jede Wallet unterstützt Off-Chain-Nachrichten. Prüfen Sie die Funktionen der verbundenen Konten, bevor Sie eine Signatur anfordern, und weichen Sie auf eine Alternative aus, wenn die Funktion fehlt:

1. Unterstützen die Konten `solana:signOffchainMessage` mit Nachrichtenversion 1,
   signieren Sie eine Off-Chain-Nachricht.
2. Andernfalls signieren Sie dieselbe Challenge mit `solana:signMessage`. Die meisten Software-Wallets unterstützen dies.
3. Bieten Sie Hardware-Wallet-Nutzern ohne Nachrichtenunterstützung ein explizites Opt-in an, etwa einen Schalter „Ich verwende eine Hardware-Wallet“, der stattdessen eine Anmelde-Transaktion signiert. Leiten Sie sie nicht standardmäßig auf diesen Weg.

/>

## Eine Nachricht im Browser signieren

<Tabs items={["Wallet Standard (Kit)", "Wallet Adapter"]}>
  <Tab value="Wallet Standard (Kit)">
    Installieren Sie die Wallet-Standard-Pakete zusammen mit Kit:

    ```terminal
    $ npm install @solana/kit @solana/wallet-standard-features @wallet-standard/ui @wallet-standard/ui-features @wallet-standard/ui-registry
    ```

    Diese Helper erwarten ein `UiWalletAccount`, etwa das `account`, das `useConnectedWallet` im [React-Leitfaden](/docs/frontend/react-hooks) zurückgibt:

    ```ts title="offchain-message.ts"
    import {
      SolanaSignOffchainMessage,
      type SolanaSignOffchainMessageFeature
    } from "@solana/wallet-standard-features";
    import type { UiWalletAccount } from "@wallet-standard/ui";
    import { getWalletAccountFeature } from "@wallet-standard/ui-features";
    import { getWalletAccountForUiWalletAccount } from "@wallet-standard/ui-registry";

    type OffchainMessageFeature =
      SolanaSignOffchainMessageFeature[typeof SolanaSignOffchainMessage];

    export function supportsOffchainMessages(account: UiWalletAccount) {
      if (!account.features.includes(SolanaSignOffchainMessage)) return false;
      const feature = getWalletAccountFeature(
        account,
        SolanaSignOffchainMessage
      ) as OffchainMessageFeature;
      return feature.supportedMessageVersions.includes(1);
    }

    export async function signOffchainMessage(
      account: UiWalletAccount,
      message: string
    ) {
      const feature = getWalletAccountFeature(
        account,
        SolanaSignOffchainMessage
      ) as OffchainMessageFeature;
      const [output] = await feature.signOffchainMessage({
        messageVersion: 1,
        account: getWalletAccountForUiWalletAccount(account),
        message,
        requiredSigners: [account.publicKey]
      });
      return output;
    }
    ```

  </Tab>

Es signiert eine Nachricht der Version 1, wobei die verbundenen Konten die erforderlichen Signer sind, und wird mit `WalletNotReadyError` abgelehnt, wenn die Wallet Version 1 nicht signieren kann:


    ```tsx title="SignOffchainMessage.tsx"
    "use client";

    import { useWallet } from "@solana/wallet-adapter";

    export function SignOffchainMessage({ challenge }: { challenge: string }) {
      const { publicKey, signOffchainMessage } = useWallet();

      const onClick = async () => {
        if (!publicKey || !signOffchainMessage) return;
        const { signature, signedOffchainMessage } =
          await signOffchainMessage(challenge);
        const valid = await publicKey.verifySignature(
          signature,
          signedOffchainMessage
        );
        // Server logic
      };

      return (
        <button onClick={onClick} disabled={!signOffchainMessage}>
          Sign in
        </button>
      );
    }
    ```

    `publicKey.verifySignature` prüft die Signatur im Browser anhand der signierten Bytes. Ihr Server muss weiterhin bestätigen, dass diese Bytes der von ihm ausgestellten Challenge entsprechen. Ist `signOffchainMessage` `undefined`, weichen Sie auf `signMessage` aus demselben Hook aus.

  </Tab>
</Tabs>

`signOffchainMessage` gibt `signedOffchainMessage`, die vollständigen von der Wallet signierten Bytes, sowie `signature` zurück. Kodieren Sie beide in Base64 und senden Sie sie zusammen mit der Wallet-Adresse an Ihren Server.

Formulieren Sie die Challenge so, dass sie sich auf einem kleinen Bildschirm gut lesen lässt. Nennen Sie Ihre App und Domain, erklären Sie, was das Signieren bewirkt, und fügen Sie eine einmalig verwendbare Nonce sowie einen Ausstellungszeitpunkt von Ihrem Server hinzu:

```text
swap.app wants you to sign in with your Solana account.

Signing in costs nothing and does not submit a transaction.

Nonce: 8f3a1c9e
Issued at: 2026-09-29T17:04:00Z
```

## Die Signatur auf Ihrem Server verifizieren

Die Verifizierung ist eine lokale Signaturprüfung und benötigt keine RPC-Verbindung. Dekodieren Sie die von der Wallet signierten Bytes, bestätigen Sie, dass sie der von Ihnen ausgestellten Challenge entsprechen, und prüfen Sie dann die Signatur:

```ts title="verify-sign-in.ts"
import {
  address,
  assertOffchainMessageV1Equal,
  getBase64Encoder,
  getOffchainMessageDecoder,
  verifyOffchainMessageEnvelope,
  type OffchainMessageBytes,
  type SignatureBytes
} from "@solana/kit";

export async function verifySignIn(input: {
  walletAddress: string;
  expectedMessage: string;
  signedOffchainMessage: string;
  signature: string;
}) {
  const signer = address(input.walletAddress);
  const base64 = getBase64Encoder();
  const content = base64.encode(
    input.signedOffchainMessage
  ) as OffchainMessageBytes;
  const signature = base64.encode(input.signature) as SignatureBytes;

  const received = getOffchainMessageDecoder().decode(content);
  if (received.version !== 1) {
    throw new Error(`Expected a v1 message, got v${received.version}`);
  }
  assertOffchainMessageV1Equal(received, {
    version: 1,
    requiredSignatories: [{ address: signer }],
    content: input.expectedMessage
  });

  await verifyOffchainMessageEnvelope({
    content,
    signatures: { [signer]: signature }
  });
}
```

`assertOffchainMessageV1Equal` wirft einen Fehler, wenn Inhalt oder Signer von Ihrer Erwartung abweichen. `verifyOffchainMessageEnvelope` wirft einen Fehler, wenn die Signatur fehlt oder ungültig ist. Schlagen Sie `expectedMessage` auf Ihrem Server anhand der Nonce nach, statt der vom Client zurückgesendeten Kopie zu vertrauen. Verbrauchen Sie die Nonce, sobald die Verifizierung erfolgreich war, damit sich mit derselben Signatur nicht zweimal anmelden lässt.

### Eine Rohnachricht verifizieren

Eine `signMessage`-Signatur deckt die Challenge-Bytes direkt ab, daher muss der Client nur die Signatur und die Wallet-Adresse senden. Prüfen Sie sie anhand der von Ihnen ausgestellten Challenge:

```ts title="verify-raw-sign-in.ts"
import {
  address,
  getBase64Encoder,
  getPublicKeyFromAddress,
  getUtf8Encoder,
  signatureBytes,
  verifySignature
} from "@solana/kit";

export async function verifyRawSignIn(input: {
  walletAddress: string;
  expectedMessage: string;
  signature: string;
}) {
  const publicKey = await getPublicKeyFromAddress(address(input.walletAddress));
  const signature = signatureBytes(getBase64Encoder().encode(input.signature));
  const message = getUtf8Encoder().encode(input.expectedMessage);
  if (!(await verifySignature(publicKey, signature, message))) {
    throw new Error("Invalid signature");
  }
}
```

Es gelten dieselben Nonce-Regeln: Schlagen Sie `expectedMessage` anhand der Nonce nach und verbrauchen Sie sie, sobald die Verifizierung erfolgreich war.

<Callout type="info">
  `@solana/kit` exportiert diese Helper aus `@solana/offchain-messages` erneut. Verwenden Sie das eigenständige Paket, wenn Ihr Server nicht von Kit abhängt.
</Callout>

## Sign In With Solana

[Sign In With Solana](https://github.com/phantom/sign-in-with-solana) (SIWS)
standardisiert die Challenge selbst. Ihre App übergibt strukturierte Felder wie
`domain`, `statement`, `nonce` und `issuedAt` an die Funktion `solana:signIn` der Wallet. Die Wallet formatiert sie zu einer Standardnachricht, stellt bei Bedarf eine Verbindung her und signiert sie in einem Schritt.

Version `1.1.0` von `solana:signIn` fügt die Option `useOffchainMessage` hinzu. Wenn Sie `useOffchainMessage: { messageVersion: 1 }` übergeben, verpackt die Wallet den SIWS-Text in eine Off-Chain-Nachricht der Version 1, wobei die signierenden Konten die einzigen erforderlichen Signer sind. Hardware-Wallets können sie anzeigen und signieren, und die Ausgabe meldet `signedMessageFormat: { kind: "offchainMessage", messageVersion: 1 }`. Wallets, die Version `1.0.0` angeben, kennen die Option nicht. Prüfen Sie daher zuerst die Funktionsversion und lassen Sie die Option andernfalls weg.

  <Tab value="Wallet Standard">
    `solana:signIn` ist eine Wallet-Funktion, keine Konten-Funktion, daher erwarten diese
    Helper ein `UiWallet`:

    ```ts title="sign-in.ts"
    import {
      SolanaSignIn,
      type SolanaSignInFeature,
      type SolanaSignInInput
    } from "@solana/wallet-standard-features";
    import type { UiWallet } from "@wallet-standard/ui";
    import { getWalletFeature } from "@wallet-standard/ui-features";

    type SignInFeature = SolanaSignInFeature[typeof SolanaSignIn];

    export function supportsOffchainSignIn(wallet: UiWallet) {
      if (!wallet.features.includes(SolanaSignIn)) return false;
      const feature = getWalletFeature(wallet, SolanaSignIn) as SignInFeature;
      return feature.version === "1.1.0";
    }

    export async function signIn(wallet: UiWallet, input: SolanaSignInInput) {
      const feature = getWalletFeature(wallet, SolanaSignIn) as SignInFeature;
      const [output] = await feature.signIn({
        ...input,
        ...(supportsOffchainSignIn(wallet) && {
          useOffchainMessage: { messageVersion: 1 }
        })
      });
      return output;
    }
    ```

  <Tab value="Wallet Adapter">
    `useWallet` stellt `signIn` bereit, wenn die ausgewählte Wallet `solana:signIn` unterstützt, und `supportsSignInWithOffchainMessage`, wenn sie Version `1.1.0` angibt. Wird `useOffchainMessage` an eine Wallet übergeben, die es nicht unterstützt, wird mit `WalletSignInError` abgelehnt:

    ```tsx title="SignIn.tsx"
    "use client";

    import {
      useWallet,
      verifySignIn,
      type SolanaSignInInput
    } from "@solana/wallet-adapter";

    export function SignIn({ input }: { input: SolanaSignInInput }) {
      const { signIn, supportsSignInWithOffchainMessage } = useWallet();

      const onClick = async () => {
        if (!signIn) return;
        const output = await signIn({
          ...input,
          ...(supportsSignInWithOffchainMessage && {
            useOffchainMessage: { messageVersion: 1 }
          })
        });
        const valid = await verifySignIn(input, output);
      };

      return (
        <button onClick={onClick} disabled={!signIn}>
          Sign in with Solana
        </button>
      );
    }
    ```

    `verifySignIn` prüft, dass die signierte Nachricht jedes Feld der Eingabe reproduziert und eine gültige Signatur der signierenden Konten trägt – unabhängig davon, ob die Wallet reinen SIWS-Text oder eine Off-Chain-Nachricht signiert hat. Führen Sie dieselbe Prüfung auf Ihrem Server aus, indem Sie sie aus `@solana/wallet-adapter/core` importieren, das keine React-Abhängigkeit hat.

  </Tab>
</Tabs>

Erstellen Sie die Eingabe auf Ihrem Server mit einer einmalig verwendbaren `nonce` und einem `issuedAt`-Zeitpunkt und bewahren Sie eine nach der Nonce indizierte Kopie auf. Verbrauchen Sie die Nonce, sobald die Anmeldung verifiziert wurde.

Ohne Wallet Adapter prüft `verifySignIn` aus `@solana/wallet-standard-util` nur reine SIWS-Ausgaben. Wenn `signedMessageFormat` eine Off-Chain-Nachricht meldet, ist `signedMessage` eine Off-Chain-Nachricht, deren Inhalt der SIWS-Text ist. Rekonstruieren Sie den erwarteten Text aus Ihrer gespeicherten Eingabe und der signierenden Adresse mit `createSignInMessageText` aus `@solana/wallet-standard-util` und verifizieren Sie ihn dann wie jede andere Off-Chain-Nachricht, wie unter
[Die Signatur auf Ihrem Server verifizieren](#verify-the-signature-on-your-server) beschrieben. Die
[`@solana/offchain-messages`-README](https://github.com/anza-xyz/kit/tree/main/packages/offchain-messages#verifying-a-signed-offchain-message)
behandelt diesen Ablauf in Kit.

## Für Wallets

Wallets ergänzen die Unterstützung, indem sie die Wallet-Standard-Funktion `solana:signOffchainMessage` aus `@solana/wallet-standard-features` implementieren:

- Melden Sie `version: "1.0.0"` und listen Sie die Nachrichtenversionen, die Sie signieren können, in
  `supportedMessageVersions` auf. Derzeit ist das `[1]`.
- Erstelle die Version-1-Präambel aus `requiredSigners`, das du sortierst und
  auf Duplikate prüfst. Weise die Anfrage ab, wenn die Konten nicht zu den
  erforderlichen Signern gehören.
- Zeige dem Nutzer den Nachrichtentext vor dem Signieren vollständig an, auch
  auf Hardware-Geräten.
- Gib die exakten Bytes, die du signiert hast, als `signedOffchainMessage`
  zurück, zusammen mit der Ed25519-`signature`.
- Um Off-Chain Sign In With Solana zu unterstützen, melde `version: "1.1.0"`
  für `solana:signIn`. Wenn die Eingabe `useOffchainMessage` enthält, signiere
  den SIWS-Text als Off-Chain-Nachricht der Version 1, gib deren Bytes als
  `signedMessage` zurück und setze `signedMessageFormat`.
- Unterstütze weiterhin `solana:signMessage`. Es bleibt unverändert, und Apps
  nutzen es weiterhin als Fallback.
