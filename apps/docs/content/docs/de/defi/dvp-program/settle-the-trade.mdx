`SettleDvp` wird von der im Trade-Datensatz benannten Abwicklungsautorität signiert. In
einer Transaktion überträgt es `amount_a` des Asset-Legs an das Ziel der
Cash-Leg-Partei und `amount_b` des Cash-Legs an das Ziel der Asset-Leg-Partei,
gibt jeden Überschuss in einem der beiden Escrows an die Partei des jeweiligen Legs zurück und schließt den Datensatz
sowie beide Escrows. Kann eine dieser Überweisungen nicht abgeschlossen werden, schlägt die Anweisung
fehl und es wird nichts bewegt.

Diese Seite setzt [Einen Trade erstellen](/docs/defi/dvp-program/create-a-trade)
und [Die Legs finanzieren](/docs/defi/dvp-program/fund-the-legs) fort; Client, Signer,
`trade` und die token accounts der Parteien werden übernommen.

## Vor dem Signieren erneut validieren

Die Abwicklungsautorität signiert die Transaktion, die beide Legs bewegt, und
führt daher vor dem Signieren dieselbe Prüfung durch wie jede Partei: Eigentümer, Größe, Parteien,
Mints, Beträge, Ablaufzeitpunkt und beide Ziele (siehe
[Die Legs finanzieren](/docs/defi/dvp-program/fund-the-legs#verify-the-terms)). Das
Programm selbst prüft bei der Abwicklung erneut, dass jeder Mint weiterhin zu dem bei der Erstellung
hinterlegten Token Program gehört, keine blockierte Erweiterung enthält und dieselbe
Mint Authority hat wie bei der Erstellung des Trades. Ein Mint, der mit einer blockierten
Erweiterung, einem anderen Token Program oder einer anderen Mint Authority neu erstellt wurde, kann daher nicht
abgewickelt werden.

## Die Empfänger-Konten erstellen

Settle schreibt in vier token accounts, die das Programm nicht erstellt:

| Konten                | Empfängt                     | Eigentümer                           |
| ---------------------- | ---------------------------- | ------------------------------- |
| `userADestinationAtaB` | Das Cash-Leg (`amount_b`)    | `user_a_settlement_destination` |
| `userBDestinationAtaA` | Das Asset-Leg (`amount_a`)   | `user_b_settlement_destination` |
| `userAAtaA`            | Jeder Überschuss im Asset-Leg | `user_a`                        |
| `userBAtaB`            | Jeder Überschuss im Cash-Leg  | `user_b`                        |

Die Überschuss-Konten werden nur verwendet, wenn ein Escrow mehr als den vereinbarten
Betrag enthält. Jeder, der den Mint besitzt, kann jedoch einen Überschuss erzeugen, indem er einige Basis-
einheiten in den Escrow sendet. Existiert das Rückerstattungskonto nicht, schlägt die gesamte Abwicklung
fehl. Erstelle daher alle vier idempotent in derselben Transaktion.

## Abwickeln

`legAExtrasCount` teilt dem Programm mit, wie viele der nach der
festen Liste angehängten Konten zum Transfer Hook des Asset-Legs gehören; der Rest gehört zu dem des
Cash-Legs. Bei Mints ohne Transfer Hooks übergibst du null und hängst nichts an. Das program account
des Memo-Programms wird von der Anweisung benötigt und nur für Ziele verwendet,
die ein Memo erfordern.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { MEMO_PROGRAM_ADDRESS } from "@solana-program/memo";
    import { getSettleDvpInstruction } from "./dvp";

    const settleInstruction = getSettleDvpInstruction({
      settlementAuthority: authoritySigner,
      swapDvp,
      mintA,
      mintB,
      dvpAtaA: escrowA,
      dvpAtaB: escrowB,
      userADestinationAtaB,
      userBDestinationAtaA,
      userAAtaA,
      userBAtaB,
      tokenProgramA,
      tokenProgramB,
      memoProgram: MEMO_PROGRAM_ADDRESS,
      legAExtrasCount: 0,
    });

    const { context: settleContext } = await client.sendTransaction([
      ...createRecipientAccounts,
      settleInstruction,
    ]);
    const settleSignature = settleContext.signature;
    console.log("Submitted:", settleSignature);

    // sendTransaction returns at the client's commitment (confirmed by default).
    // Wait for finalized before recording the trade as settled.
    let finalized = false;
    for (let attempt = 0; attempt < 30 && !finalized; attempt++) {
      const {
        value: [status],
      } = await client.rpc.getSignatureStatuses([settleSignature]).send();
      if (status?.err) {
        throw new Error("Settle transaction failed");
      }
      finalized = status?.confirmationStatus === "finalized";
      if (!finalized) {
        await new Promise((resolve) => setTimeout(resolve, 2_000));
      }
    }
    if (!finalized) {
      // A closed record means it settled; an open one is safe to settle again.
      throw new Error("Settle not finalized after 60s; read the trade record");
    }
    console.log("Settled:", settleSignature);
    ```

### Transfer Hooks

Die generierte IDL listet nur die festen Konten auf, daher kennen die generierten Builder
die Hook-Konten nicht. Löse die zusätzlichen Account-Metas jedes Hook-Mints
auf dieselbe Weise auf wie bei einer direkten Überweisung dieses Tokens und hänge sie dann an die
Anweisung an: zuerst die Konten des Asset-Legs, dann die des Cash-Legs, wobei
`legAExtrasCount` auf die Anzahl der ersten Gruppe gesetzt wird. In TypeScript verteilst du
die aufgelösten Metas per Spread auf das `accounts`-Array der Anweisung; in Rust verwendest du
`add_remaining_accounts` am Builder. Die Obergrenze liegt bei 32 Konten pro Leg,
einschließlich des Hook-Programms und des Validierungskontos; das Konten-Limit der Transaktion
kann zuerst greifen, wenn beide Legs Hooks haben. Das Programm entfernt das Signer-Flag
von jedem weitergeleiteten Konto, sodass ein Hook über diesen Pfad nicht die
Signatur der Abwicklungsautorität erlangen kann.

## Das Ergebnis erfassen

Betrachte den Trade als abgewickelt, wenn die Settle-Transaktion `finalized` erreicht. Der
Datensatz und beide Escrows existieren nach der Abwicklung nicht mehr. Ein System, das
die Konditionen später benötigt, speichert sie daher aus seiner Prüfung vor der Abwicklung oder aus der erstellenden
Transaktion. Die rent der geschlossenen Konten ist an die Abwicklungs-
autorität gegangen.

## Fehler bei der Abwicklung

`LegNotFunded` bedeutet, dass ein Escrow weniger als den vereinbarten Betrag enthält; `DvpExpired`
und `SettlementTooEarly` bedeuten, dass das Zeitfenster verpasst wurde; `MintAuthorityChanged`
und `BlockedMintExtension` bedeuten, dass sich ein Mint nach der Erstellung geändert hat;
`RecipientAtaMismatch` bedeutet, dass ein token account für Ziel oder Rückerstattung fehlt oder
nicht mehr dem erwarteten Eigentümer und Mint gehört, in der Regel, weil der oben beschriebene
Schritt zum Erstellen der Konten übersprungen wurde. In jedem Fall wurde nichts bewegt, und die
Parteien können rückabwickeln, vorbehaltlich der Authorities des Mints (siehe
[Einen Trade rückabwickeln](/docs/defi/dvp-program/unwind-a-trade)).
