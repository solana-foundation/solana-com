# MEV-Schutz mit Jito DontFront

Maximal Extractable Value (MEV) bezeichnet den Wert, der durch das Umordnen,
Einfügen oder Ausschließen von Transaktionen innerhalb eines Blocks abgeschöpft
werden kann. MEV ist nicht auf eine bestimmte Chain beschränkt, sondern eine
grundlegende Eigenschaft jeder Blockchain, in der Block-Produzenten die
Reihenfolge der Transaktionen kontrollieren. Einige Formen von MEV, wie
Arbitrage, tragen zur Markteffizienz bei, indem sie Preisunterschiede zwischen
DEXs ausgleichen. Andere, wie Sandwich-Angriffe, entziehen Nutzern direkt Wert.
Für Entwickler von DeFi-Anwendungen kann das eine schlechtere Trade-Ausführung
und entgangene Gewinne bedeuten.

Dieser Leitfaden konzentriert sich auf Sandwich-Angriffe, eine verbreitete Form
schädlichen MEVs, und darauf, wie Sie ihnen mit der `dontfront`-Funktion von Jito
entgegenwirken können.

Empfohlene Vorablektüre:
[Jito Bundles](https://solana.com/docs/tools/transaction-landing#jito-bundles)

## MEV auf Solana

Die Architektur von Solana verringert die MEV-Angriffsfläche bereits im
Vergleich zu Chains mit öffentlichen Mempools. Transaktionen werden direkt an
den nächsten Block-Leader weitergeleitet, statt in einem gemeinsamen Mempool zu
liegen, und unverarbeitete Transaktionen verfallen nach etwa 150 Blöcken (~1
Minute). Dadurch verengt sich das Zeitfenster erheblich, in dem Searcher
ausstehende Transaktionen beobachten und darauf reagieren können.

Dennoch findet weiterhin MEV-Extraktion statt. Searcher mit optimierter
Infrastruktur und direkten Verbindungen zu Validatoren können den
Transaktionsfluss beobachten und darauf reagieren. Ein Großteil der MEV-Aktivität
auf Solana ist atomare Arbitrage: Bots, die Preisunterschiede zwischen DEXs in
einer einzigen Transaktion ausgleichen. Diese Art von MEV ist im Allgemeinen
vorteilhaft, da sie die Preiskonsistenz über Märkte hinweg verbessert.

Die schädliche Variante, der Sandwich-Angriff, ist das, wogegen Entwickler sich
aktiv schützen sollten.

## Was ist ein Sandwich-Angriff?

Ein Sandwich-Angriff liegt vor, wenn ein Searcher Ihren ausstehenden Swap
erkennt und die Reihenfolge der Transaktionen ausnutzt:

1. **Front-Run**: Der Searcher kauft den Token vor Ihrem Trade und treibt dadurch
   den Preis nach oben
2. **Ihr Trade wird ausgeführt** – zu einem schlechteren Preis als erwartet
3. **Back-Run**: Der Searcher verkauft den Token nach Ihrem Trade und streicht die
   Differenz ein

Auf Solana kann dies über
[Jito Bundles](https://docs.jito.wtf/lowlatencytxnsend/#what-are-bundles) geschehen. Ein
Searcher reicht ein Bundle von Transaktionen ein, etwa:
`[frontrun_tx, your_tx, backrun_tx]`, und die Block Engine führt sie
atomar in dieser Reihenfolge aus. Das Opfer erhält einen schlechteren
Ausführungspreis, während der Searcher vom Spread profitiert.

## Wie DontFront funktioniert

[DontFront](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation) ist eine
Funktion der Jito Block Engine, die verhindert, dass Searcher in einem Bundle
Transaktionen vor Ihrer platzieren.

Der Mechanismus: Fügen Sie einer beliebigen Anweisung in Ihrer Transaktion einen
beliebigen gültigen öffentlichen Solana-Schlüssel hinzu, der mit `jitodontfront`
beginnt. Die Block Engine erkennt dieses Präfix und erzwingt eine Regel: **Jedes
Bundle, das Ihre Transaktion enthält, muss sie an Index 0 platzieren**.

```
Without dontfront:  [frontrun_tx, your_tx, backrun_tx]  ← sandwich possible
With dontfront:     [your_tx, ...]                       ← your tx must be first
```

### Schritt für Schritt

1. **Wählen Sie eine gültige Adresse**, die mit `jitodontfront` beginnt (z. B.
   `jitodontfront111111111111111111111111111111`). Das Konto muss nicht
   onchain existieren; es wird nie gelesen oder beschrieben. Sie können prüfen,
   ob ein String eine gültige Adresse ist, indem Sie die Funktion
   [`assertIsAddress`](https://www.solanakit.com/api/functions/assertIsAddress)
   aus @solana/kit verwenden oder die Adresse im Solana Explorer eingeben, um zu
   sehen, ob sie aufgelöst wird. Hier ist ein Beispiel für eine
   [ungültige Adresse](https://explorer.solana.com/address/jitodontfront11111111111111111111111111111INVALID).

2. **Fügen Sie sie als schreibgeschütztes Nicht-Signer-Konto** zu einer beliebigen
   Anweisung in Ihrer Transaktion hinzu. Markieren Sie sie für optimale
   Landing-Geschwindigkeit als schreibgeschützt. Die meisten Programme
   (einschließlich des System Program) ignorieren zusätzliche Konten über das
   Erwartete hinaus.

3. **Senden Sie über die Jito Block Engine**:
   - `sendTransaction`:
     `https://mainnet.block-engine.jito.wtf/api/v1/transactions`
   - `sendBundle`: `https://mainnet.block-engine.jito.wtf/api/v1/bundles`

   Dokumentation:
   [sendTransaction](https://docs.jito.wtf/lowlatencytxnsend/#sendtransaction)
   und [sendBundle](https://docs.jito.wtf/lowlatencytxnsend/#sendbundle)

4. Die Block Engine erkennt das Präfix `jitodontfront` und erzwingt die
   Reihenfolgeregeln.

### Was in der Block Engine passiert

Wenn die Block Engine eine Transaktion mit einem `jitodontfront`-Konto erkennt:

- Über `sendTransaction`: Die Transaktion ist geschützt. Kein Bundle kann eine
  andere Transaktion davor platzieren
- Über `sendBundle`: Die Transaktion muss an Index 0 stehen, andernfalls wird das
  gesamte Bundle abgelehnt

Transaktionen und Bundles, die kein `jitodontfront`-Konto enthalten, sind
nicht betroffen.

## Regeln zur Bundle-Reihenfolge

Diese Regeln gelten, wenn eine `jitodontfront`-Transaktion in einem Bundle
vorkommt.

### Erlaubte Muster

```
[tx_with_dontfront, tip]
[tx_with_dontfront, arbitrage, tip]
[tx_with_dontfront_signer1, tx_with_dontfront_signer1_and_signer2, tip]
```

### Mehrere DontFront-Transaktionen in einem Bundle

Mehrere dontfront-Transaktionen in einem einzigen Bundle sind erlaubt, wenn
**beide** Bedingungen erfüllt sind:

1. Alle dontfront-Transaktionen stehen **zusammenhängend am Anfang** des Bundles
2. Jede dontfront-Transaktion hat **mindestens einen Signer** mit der ersten
   dontfront-Transaktion gemeinsam

```
✅ [txA_df, txB_df, txC_df, arbitrage, tip]
   (contiguous at front, overlapping signers)

✅ [txA_df_signer1_signer2, txB_df_signer1_signer3, txC_df_signer2_signer4]
   (each shares a signer with txA)
```

### Abgelehnte Muster

```
❌ [tip, tx_with_dontfront]
   → dontfront tx is not at index 0

❌ [txA_df_signer1, txB_df_signer2]
   → no overlapping signer between txA and txB

❌ [trade, tx_with_dontfront, arbitrage, tip]
   → dontfront tx is not at the front
```

## Integrationsbeispiele

Ein schnelles Code-Rezept finden Sie im
[Cookbook-Eintrag zum MEV-Schutz](/developers/cookbook/transactions/mev-protection).

### TypeScript (@solana/kit)

Die Kernidee ist eine Hilfsfunktion, die das dontfront-Konto an eine beliebige Anweisung anhängt:

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
import {
  address,
  AccountRole,
  type Instruction,
  type Address
} from "@solana/kit";

const DONT_FRONT: Address = address(
  "jitodontfront111111111111111111111111111111"
);

// !mark(1:9)
function withDontFront(ix: Instruction): Instruction {
  return {
    ...ix,
    accounts: [
      ...(ix.accounts ?? []),
      { address: DONT_FRONT, role: AccountRole.READONLY }
    ]
  };
}
```

```rs !! title="Rust"
use solana_sdk::{
    instruction::{AccountMeta, Instruction},
    pubkey::Pubkey,
};
use std::str::FromStr;

const DONT_FRONT_ACCOUNT: &str =
    "jitodontfront111111111111111111111111111111";

// !mark(1:6)
fn with_dontfront(ix: &mut Instruction) {
    let dontfront =
        Pubkey::from_str(DONT_FRONT_ACCOUNT).unwrap();
    ix.accounts
        .push(AccountMeta::new_readonly(dontfront, false));
}
```

</CodeTabs>

## Best Practices

DontFront ist eine Schutzschicht. Eine robuste MEV-Schutzstrategie kombiniert
mehrere Ansätze:

### Schutz auf Transaktionsebene

- **Setzen Sie enge Slippage-Toleranzen.** Die wirksamste Einzelmaßnahme gegen
  Sandwich-Angriffe ist die Begrenzung der akzeptablen Slippage bei Swaps. Ein
  kleineres Slippage-Fenster verringert die für Angreifer verfügbare
  Gewinnspanne und macht Ihre Transaktion weniger attraktiv für Sandwiches.

- **Setzen Sie angemessene Tipps und priority fees.** Bei Überlastung erhöhen
  höhere Tipps und priority fees die Wahrscheinlichkeit, dass Ihre
  Transaktion bzw. Ihr Bundle schnell landet, und verkleinern so das Zeitfenster
  für Searcher. Weitere Details zur Festlegung angemessener Tipps finden Sie in
  der Jito-Dokumentation zu
  [Tip-Beträgen](https://docs.jito.wtf/lowlatencytxnsend/#tip-amount).

- **Optimieren Sie die Nutzung von Compute Units.** Jeder Block bietet nur eine
  begrenzte Anzahl an Compute Units (und Konten haben pro Block nur eine
  begrenzte Anzahl an Compute Units zur Verfügung). Damit die Wahrscheinlichkeit,
  dass Ihre Transaktion bzw. Ihr Bundle in einen Block aufgenommen wird,
  maximiert wird, sollten Sie Ihre Compute-Unit-Nutzung optimieren. Details
  finden Sie im Leitfaden
  [So optimieren Sie die Compute-Nutzung auf Solana](/developers/cookbook/transactions/optimize-compute).

### DontFront-spezifisch

1. **Markieren Sie das dontfront-Konto als schreibgeschützt.** Die Markierung als
   beschreibbar funktioniert zwar, aber schreibgeschützt
   [optimiert die Landing-Geschwindigkeit](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation).

2. **Verwenden Sie pro Anwendung einen eindeutigen dontfront-pubkey.** Jeder
   pubkey, der mit `jitodontfront` beginnt, funktioniert. Mit einer eindeutigen
   Variante (z. B. `jitodontfront111111111111111111111111111123`) können Sie bei
   der Prüfung von Onchain-Daten die Nutzung pro App unterscheiden.

3. **DontFront unterstützt Address Lookup Tables.** Das dontfront-Konto kann über
   eine ALT eingebunden werden. Verwenden Sie ALTs jedoch nicht für Tip-Konten.

## Einschränkungen

- **Nur Block Engine.** DontFront wird von der Jito Block Engine durchgesetzt.
  Transaktionen, die direkt an Validatoren gesendet werden (unter Umgehung von
  Jito), sind nicht geschützt.

- **Keine Garantie.** Aus der Jito-Dokumentation: _„This feature may help reduce sandwich
  attacks but is not guaranteed to do so and is not a solution for all
  variations in transaction ordering, including any ordering conducted by third
  parties.“_

- **Nur Mainnet/Testnet.** Dies ist eine Funktion der Jito Block Engine. Sie
  funktioniert nicht auf Devnet oder localhost.
