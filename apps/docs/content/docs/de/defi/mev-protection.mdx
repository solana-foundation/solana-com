# MEV-Schutz mit Jito DontFront

Maximal Extractable Value (MEV) bezeichnet den Wert, der durch das
Umsortieren, Einfügen oder Auslassen von Transaktionen innerhalb eines Blocks abgeschöpft werden kann. MEV ist nicht
auf eine bestimmte Chain beschränkt, sondern eine grundlegende Eigenschaft jeder Blockchain, in der
Blockproduzenten die Reihenfolge der Transaktionen kontrollieren. Manche Formen von MEV, wie Arbitrage,
helfen dabei, Märkte effizient zu halten, indem sie Preisunterschiede zwischen DEXs ausgleichen.
Andere, wie Sandwich-Angriffe, entziehen Nutzern direkt Wert. Für Entwickler,
die DeFi-Anwendungen bauen, kann das schlechtere Trade-Ausführung und entgangene
Gewinne bedeuten.

Dieser Leitfaden konzentriert sich auf Sandwich-Angriffe, eine verbreitete Form von schädlichem MEV, und darauf, wie du
ihnen mit Jitos `dontfront`-Funktion begegnen kannst.

Empfohlene Vorablektüre:
[Jito Bundles](https://solana.com/docs/tools/transaction-landing#jito-bundles)

## MEV auf Solana

Solanas Architektur verkleinert die MEV-Angriffsfläche bereits im Vergleich zu Chains
mit öffentlichen Mempools. Transaktionen werden direkt an den nächsten Block-
Leader weitergeleitet, statt in einem gemeinsamen Mempool zu liegen, und nicht verarbeitete Transaktionen
verfallen nach etwa 150 Blöcken (~1 Minute). Das verengt das
Zeitfenster für Searcher erheblich, ausstehende Transaktionen zu beobachten und darauf zu reagieren.

Dennoch findet MEV-Extraktion weiterhin statt. Searcher mit optimierter Infrastruktur
und direkten Verbindungen zu Validatoren können den Transaktionsfluss beobachten und darauf reagieren.
Ein Großteil der MEV-Aktivität auf Solana ist atomare Arbitrage: Bots, die Preis-
unterschiede zwischen DEXs in einer einzigen Transaktion ausgleichen. Diese Art von MEV ist in der Regel
vorteilhaft, da sie die Preiskonsistenz über Märkte hinweg verbessert.

Die schädliche Variante, die Sandwich-Angriffe, ist das, wogegen Entwickler sich aktiv
schützen sollten.

## Was ist ein Sandwich-Angriff?

Ein Sandwich-Angriff liegt vor, wenn ein Searcher deinen ausstehenden Swap erkennt und die
Reihenfolge der Transaktionen ausnutzt:

1. **Front-Run**: Der Searcher kauft den Token vor deinem Trade und treibt den
   Preis nach oben
2. **Dein Trade wird ausgeführt**, und zwar zu einem schlechteren Preis als erwartet
3. **Back-Run**: Der Searcher verkauft den Token nach deinem Trade und steckt die
   Differenz ein

Auf Solana kann das über
[Jito Bundles](https://docs.jito.wtf/lowlatencytxnsend/#what-are-bundles) geschehen. Ein
Searcher reicht ein Bundle von Transaktionen ein, etwa:
`[frontrun_tx, your_tx, backrun_tx]`, und die Block Engine führt sie
atomar in dieser Reihenfolge aus. Das Opfer erhält einen schlechteren Ausführungspreis, während der Searcher
vom Spread profitiert.

## So funktioniert DontFront

[DontFront](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation) ist eine
Funktion der Jito Block Engine, die verhindert, dass Searcher
Transaktionen vor deiner in einem Bundle platzieren.

Der Mechanismus: Füge einer beliebigen Anweisung in deiner Transaktion einen gültigen Solana Public Key hinzu, der mit `jitodontfront`
beginnt. Die Block Engine erkennt dieses Präfix
und erzwingt eine Regel: **Jedes Bundle, das deine Transaktion enthält, muss sie an
Index 0 platzieren**.

```
Without dontfront:  [frontrun_tx, your_tx, backrun_tx]  ← sandwich possible
With dontfront:     [your_tx, ...]                       ← your tx must be first
```

### Schritt für Schritt

1. **Wähle eine gültige Adresse**, die mit `jitodontfront` beginnt (z. B.
   `jitodontfront111111111111111111111111111111`). Das Konto muss nicht
   onchain existieren; es wird nie gelesen oder beschrieben. Du kannst prüfen, ob ein String eine
   gültige Adresse ist, mit der Funktion
   [`assertIsAddress`](https://www.solanakit.com/api/functions/assertIsAddress)
   aus @solana/kit, oder du gibst die Adresse im Solana Explorer ein, um
   zu sehen, ob sie aufgelöst wird. Hier ist ein Beispiel für eine
   [ungültige Adresse](https://explorer.solana.com/address/jitodontfront11111111111111111111111111111INVALID).

2. **Füge sie als schreibgeschütztes Konto ohne Signer** zu einer beliebigen Anweisung in deiner
   Transaktion hinzu. Markiere sie für optimale Landing-Geschwindigkeit als schreibgeschützt. Die meisten Programme
   (einschließlich des System Program) ignorieren zusätzliche Konten, die über das Erwartete hinausgehen.

3. **Sende über die Jito Block Engine**:
   - `sendTransaction`:
     `https://mainnet.block-engine.jito.wtf/api/v1/transactions`
   - `sendBundle`: `https://mainnet.block-engine.jito.wtf/api/v1/bundles`

   Dokumentation:
   [sendTransaction](https://docs.jito.wtf/lowlatencytxnsend/#sendtransaction)
   und [sendBundle](https://docs.jito.wtf/lowlatencytxnsend/#sendbundle)

4. Die Block Engine erkennt das Präfix `jitodontfront` und erzwingt die Regeln zur
   Reihenfolge.

### Was in der Block Engine passiert

Wenn die Block Engine eine Transaktion mit einem `jitodontfront`-Konto erkennt:

- Über `sendTransaction`: Die Transaktion ist geschützt. Kein Bundle darf
  eine andere Transaktion davor platzieren
- Über `sendBundle`: Die Transaktion muss an Index 0 stehen, andernfalls wird das gesamte Bundle
  abgelehnt

Transaktionen und Bundles, die kein `jitodontfront`-Konto enthalten, sind
nicht betroffen.

## Regeln zur Bundle-Reihenfolge

Diese Regeln gelten, wenn eine `jitodontfront`-Transaktion in einem Bundle vorkommt.

### Erlaubte Muster

```
[tx_with_dontfront, tip]
[tx_with_dontfront, arbitrage, tip]
[tx_with_dontfront_signer1, tx_with_dontfront_signer1_and_signer2, tip]
```

### Mehrere DontFront-Transaktionen in einem Bundle

Mehrere dontfront-Transaktionen in einem einzigen Bundle sind erlaubt, wenn **beide**
Bedingungen erfüllt sind:

1. Alle dontfront-Transaktionen stehen **zusammenhängend am Anfang** des Bundles
2. Jede dontfront-Transaktion hat **mindestens einen Signer** mit der ersten
   dontfront-Transaktion gemeinsam

```
✅ [txA_df, txB_df, txC_df, arbitrage, tip]
   (contiguous at front, overlapping signers)

✅ [txA_df_signer1_signer2, txB_df_signer1_signer3, txC_df_signer2_signer4]
   (each shares a signer with txA)
```

### Abgelehnte Muster

```
❌ [tip, tx_with_dontfront]
   → dontfront tx is not at index 0

❌ [txA_df_signer1, txB_df_signer2]
   → no overlapping signer between txA and txB

❌ [trade, tx_with_dontfront, arbitrage, tip]
   → dontfront tx is not at the front
```

## Integrationsbeispiele

Ein kurzes Code-Rezept findest du im
[Cookbook-Eintrag zum MEV-Schutz](/developers/cookbook/transactions/mev-protection).

### TypeScript (@solana/kit)

Die Kernidee ist ein Helper, der das dontfront-Konto an eine beliebige Anweisung anhängt:

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
import {
  address,
  AccountRole,
  type Instruction,
  type Address
} from "@solana/kit";

const DONT_FRONT: Address = address(
  "jitodontfront111111111111111111111111111111"
);

// !mark(1:9)
function withDontFront(ix: Instruction): Instruction {
  return {
    ...ix,
    accounts: [
      ...(ix.accounts ?? []),
      { address: DONT_FRONT, role: AccountRole.READONLY }
    ]
  };
}
```

```rs !! title="Rust"
use solana_sdk::{
    instruction::{AccountMeta, Instruction},
    pubkey::Pubkey,
};
use std::str::FromStr;

const DONT_FRONT_ACCOUNT: &str =
    "jitodontfront111111111111111111111111111111";

// !mark(1:6)
fn with_dontfront(ix: &mut Instruction) {
    let dontfront =
        Pubkey::from_str(DONT_FRONT_ACCOUNT).unwrap();
    ix.accounts
        .push(AccountMeta::new_readonly(dontfront, false));
}
```

</CodeTabs>

## Best Practices

DontFront ist eine Schutzschicht. Eine robuste MEV-Schutzstrategie kombiniert
mehrere Ansätze:

### Schutz auf Transaktionsebene

- **Setze enge Slippage-Toleranzen.** Die wirksamste Einzelmaßnahme gegen
  Sandwich-Angriffe ist, die akzeptable Slippage bei Swaps zu begrenzen. Ein kleineres Slippage-
  Fenster verringert die für Angreifer verfügbare Gewinnmarge und macht deine
  Transaktion weniger attraktiv für Sandwich-Angriffe.

- **Setze angemessene Tips und priority fee.** Bei Überlastung erhöhen höhere Tips und
  priority fee die Wahrscheinlichkeit, dass deine Transaktion bzw. dein Bundle schnell landet, und
  verkleinern so das Zeitfenster für Searcher. Weitere Details dazu, wie du angemessene Tips festlegst, findest du in Jitos Dokumentation zu
  [Tip-Beträgen](https://docs.jito.wtf/lowlatencytxnsend/#tip-amount).

- **Optimiere die Nutzung von Compute Units.** Jeder Block hat nur eine begrenzte Anzahl an Compute
  Units (und Konten haben nur eine begrenzte Anzahl an Compute Units
  pro Block). Damit die Wahrscheinlichkeit maximiert wird, dass deine Transaktion bzw. dein Bundle in einen
  Block aufgenommen wird, solltest du deine Nutzung von Compute Units optimieren. Details findest du im
  Leitfaden [So optimierst du die Compute-Nutzung auf Solana](/developers/cookbook/transactions/optimize-compute).

### DontFront-spezifisch

1. **Markiere das dontfront-Konto als schreibgeschützt.** Die Markierung als beschreibbar funktioniert, aber schreibgeschützt
   [optimiert die Landing-Geschwindigkeit](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation).

2. **Verwende pro Anwendung einen eindeutigen dontfront-pubkey.** Jeder pubkey, der mit
   `jitodontfront` beginnt, funktioniert. Mit einer eindeutigen Variante (z. B.
   `jitodontfront111111111111111111111111111123`) kannst du die Nutzung pro
   App unterscheiden, wenn du Onchain-Daten untersuchst.

3. **DontFront unterstützt Address Lookup Tables.** Das dontfront-Konto kann
   über eine ALT eingebunden werden. Verwende ALTs jedoch nicht für Tip-Konten.

## Einschränkungen

- **Nur Block Engine.** DontFront wird von der Jito Block Engine durchgesetzt.
  Transaktionen, die direkt an Validatoren gesendet werden (unter Umgehung von Jito), sind nicht
  geschützt.

- **Keine Garantie.** Aus Jitos Dokumentation: _"Diese Funktion kann dazu beitragen, Sandwich-
  Angriffe zu reduzieren, dies ist jedoch nicht garantiert, und sie ist keine Lösung für alle
  Varianten der Transaktionsreihenfolge, einschließlich jeglicher Reihenfolge, die von Dritten
  vorgenommen wird."_

- **Nur Mainnet/Testnet.** Dies ist eine Funktion der Jito Block Engine. Sie funktioniert
  nicht auf Devnet oder localhost.
