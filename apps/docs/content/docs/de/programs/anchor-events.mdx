Anchor-Events sind typisierte, Borsh-serialisierte Datensätze, die in der IDL eines Programms enthalten sind.
Sie ermöglichen es Clients, Programmaktivitäten zu interpretieren, ohne menschenlesbare Lognachrichten
parsen zu müssen.

Events eignen sich für Indexierung und Benachrichtigungen, sind aber kein
Programmzustand. Speichere jeden Wert, den das Programm erneut lesen muss, in Konten, und betrachte
Events als Datensatz, der aus einer erfolgreichen Transaktion abgeleitet wird.

## Ein Event definieren und emittieren

Füge `#[event]` zu einem Struct hinzu und rufe `emit!` auf, nachdem die Zustandsänderung erfolgreich war.

```rust title="lib.rs"
use anchor_lang::prelude::*;

#[program]
pub mod payments {
    use super::*;

    pub fn record_payment(ctx: Context<RecordPayment>, amount: u64) -> Result<()> {
        emit!(PaymentRecorded {
            authority: ctx.accounts.authority.key(),
            amount,
        });
        Ok(())
    }
}

#[derive(Accounts)]
pub struct RecordPayment<'info> {
    pub authority: Signer<'info>,
}

#[event]
pub struct PaymentRecorded {
    pub authority: Pubkey,
    pub amount: u64,
}
```

`emit!` schreibt die Event-Bytes mit dem Syscall `sol_log_data` von Solana. Transaktionslogs
zeigen das Ergebnis als `Program data: <base64>`. Der kodierte Wert beginnt mit
dem Event-Diskriminator, gefolgt von den Borsh-serialisierten Feldern.

Halte Events schlank. Große Strings und Vektoren verbrauchen Compute, vergrößern die
Transaktionsmetadaten und sind eher von der Kürzung von Logs betroffen.

## Zwischen Log- und CPI-Events wählen

Anchor unterstützt zwei Emissionswege:

| Pfad        | Speicherort                  | Kompromiss                                               |
| ----------- | --------------------------------- | ------------------------------------------------------ |
| `emit!`     | Programmdaten-Logs                 | Einfacher und günstiger, aber Logs können abgeschnitten werden         |
| `emit_cpi!` | Inner instruction data aus einem CPI | Dauerhaftere Metadaten, aber mit zusätzlichen Konten und höherem Compute-Aufwand |

Um CPI-Events zu verwenden, aktiviere das Feature `event-cpi` von Anchor:

```toml title="Cargo.toml"
[dependencies]
anchor-lang = { version = "1.1.2", features = ["event-cpi"] }
```

Annotiere dann das Konten-Struct der Anweisung mit `#[event_cpi]` und emittiere
aus einem Handler, dessen Kontextvariable `ctx` heißt:

```rust title="lib.rs"
pub fn record_payment(ctx: Context<RecordPayment>, amount: u64) -> Result<()> {
    emit_cpi!(PaymentRecorded {
        authority: ctx.accounts.authority.key(),
        amount,
    });
    Ok(())
}

#[event_cpi]
#[derive(Accounts)]
pub struct RecordPayment<'info> {
    pub authority: Signer<'info>,
}
```

`#[event_cpi]` fügt die Event-Authority und die Konten des aktuellen Programms hinzu, die für
den signierten Self-CPI erforderlich sind. CPI-Events können nicht über das Log-Event-Abonnement
von Anchor konsumiert werden; rufe stattdessen die Transaktion ab und dekodiere die passende
innere Anweisung.

<Callout type="info" title="Das Ledger als Quelle verwenden">
  RPC-Provider können Programmlogs kürzen. Wenn ein verpasstes Event Guthaben,
  Berechtigungen oder einen anderen korrektheitskritischen Workflow beeinträchtigen würde, leite das
  Ergebnis aus den Konten des Programms oder aus den instruction data der Transaktion ab. Nutze Events, um
  die Indexierung effizient zu machen – nicht als einzige Aufzeichnung des Zustands.
</Callout>

## Abonnieren mit TypeScript

Der aktuelle Anchor-TypeScript-Client ist `@anchor-lang/core`. Eine aus der Programm-IDL erstellte `Program`-Instanz
kann passende Log-Events dekodieren und sie über das RPC-Log-Abonnement bereitstellen:

```ts
const listenerId = program.addEventListener(
  "PaymentRecorded",
  (event, slot, signature) => {
    console.log({ event, slot, signature });
  },
  "confirmed"
);

// Remove the websocket subscription when it is no longer needed.
await program.removeEventListener(listenerId);
```

Der Callback erhält die dekodierten Event-Daten, den slot und die Transaktionssignatur.
Abonnements decken nur Logs ab, die geliefert werden, solange die Verbindung aktiv ist. Speichere verarbeitete Signaturen und hole verpasste Transaktionen nach einer Trennung nach,
wenn der Consumer eine lückenlose Historie benötigt.

## Abgerufene Transaktionslogs dekodieren

Für Backfills und einmalige Prüfungen rufe eine Transaktion ab und übergib jede
`Program data:`-Payload an den Event-Coder:

```ts
const transaction = await connection.getTransaction(signature, {
  commitment: "confirmed",
  maxSupportedTransactionVersion: 0
});

if (!transaction?.meta || transaction.meta.err) {
  throw new Error("Transaction was not found or did not succeed");
}

for (const log of transaction.meta.logMessages ?? []) {
  const prefix = "Program data: ";
  if (!log.startsWith(prefix)) continue;

  const decoded = program.coder.events.decode(log.slice(prefix.length));
  if (decoded) console.log(decoded.name, decoded.data);
}
```

Eine Transaktion kann mehrere Programme aufrufen. Verfolge in einem Produktions-Parser die
Log-Grenzen `Program <address> invoke` und `success` oder verwende den Event-Parser von Anchor,
damit der `Program data:`-Eintrag eines anderen Programms nicht als deiner dekodiert wird.
Fehlgeschlagene Transaktionen können Logs und innere Anweisungen aus Arbeit behalten, die vor dem Fehler
abgeschlossen wurde. Weise daher vor der Indexierung beider Event-Formen stets Transaktionsmetadaten mit einem `err`-Wert ungleich null zurück.
Das Log-Abonnement von Anchor führt diese Prüfung durch, bevor ein Event-Callback ausgelöst wird.

Suche bei einem `emit_cpi!`-Event den Self-CPI in `meta.innerInstructions`,
bestätige, dass seine Programm-ID deinem Programm entspricht, und dekodiere seine instruction
data mit base58. Prüfe vor dem Entfernen von Bytes das
[`EVENT_IX_TAG_LE`](https://github.com/solana-foundation/anchor/blob/v1.1.2/lang/src/event.rs#L1-L3) von Anchor:

```ts
import bs58 from "bs58";

const EVENT_IX_TAG_LE = Buffer.from("e445a52e51cb9a1d", "hex");
const instructionData = Buffer.from(bs58.decode(innerInstruction.data));

if (!instructionData.subarray(0, 8).equals(EVENT_IX_TAG_LE)) {
  // This is an ordinary self-CPI, not an emit_cpi! event.
  continue;
}

const eventData = instructionData.subarray(8).toString("base64");
const decoded = program.coder.events.decode(eventData);
```

Die Prüfung von Programm-ID und Tag verhindert, dass ein gewöhnlicher Self-CPI fälschlicherweise
für ein Event gehalten wird.

## Event-Schemas versionieren

Standardmäßig leitet Anchor einen 8-Byte-Event-Diskriminator aus dem Event-Namen ab.
Anchor unterstützt außerdem einen expliziten Diskriminator über
`#[event(discriminator = ...)]`. Diskriminatoren müssen innerhalb des
Programms eindeutig und für jeden Client, der das Event dekodiert, stabil bleiben.

Eine Änderung der Felder eines emittierten Structs ändert dessen Borsh-Layout. Definiere bei einer inkompatiblen
Schemaänderung ein neues Event wie `PaymentRecordedV2`, statt `PaymentRecorded`
stillschweigend zu ändern. Emittiere das alte Event während eines Migrationszeitraums weiter,
wenn bestehende Indexer noch davon abhängen.

Bevorzuge bei weiterentwickelbaren Daten Felder fester Breite und Identifikatoren, mit denen ein
Indexer umfangreichere Daten aus Konten separat abrufen kann. Veröffentliche die aktualisierte IDL vor oder
zusammen mit dem Programm-Upgrade, damit Consumer das neue Event sofort dekodieren können.

## Events testen

Teste den dekodierten Vertrag, nicht den base64-String. Registriere den Listener, bevor du
die Anweisung sendest, prüfe die dekodierten Felder und die Transaktionssignatur
und entferne den Listener stets:

```ts
let listenerId = 0;
const received = new Promise<{
  event: { authority: PublicKey; amount: BN };
  signature: string;
}>((resolve) => {
  listenerId = program.addEventListener(
    "PaymentRecorded",
    (event, _slot, signature) => resolve({ event, signature }),
    "confirmed"
  );
});

try {
  const signature = await program.methods.recordPayment(new BN(500)).rpc();
  const result = await received;

  assert.equal(result.signature, signature);
  assert.equal(result.event.amount.toString(), "500");
} finally {
  await program.removeEventListener(listenerId);
}
```

Teste außerdem, dass der Indexer Event-Bytes ignoriert, die in den Metadaten fehlgeschlagener Transaktionen erhalten bleiben,
und füge für jede unterstützte Event-Version ein Fixture hinzu. Wenn du
`emit_cpi!` verwendest, teste das Dekodieren aus `innerInstructions`, da Log-Listener diese Events nicht
direkt empfangen.
