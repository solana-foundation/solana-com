Eine Transaktion wird nur ausgeführt, wenn sie eine gültige
[Signatur](/docs/core/transactions/transaction-structure#signatures) von jedem
erforderlichen Signer trägt. Während der lokalen Entwicklung hält man diesen Key in der Regel als
[`Keypair`](/developers/cookbook/wallets/create-keypair) und signiert direkt. In der
Produktion stellt sich eine andere, entscheidende Frage: **Wo liegt der private Key,
und wer ist berechtigt, eine Signatur damit zu autorisieren?**

<Callout type="warn">
  Bette niemals private Keys in clientseitigen Code ein, bündele sie nicht in einem Frontend und
  committe sie nicht in die Versionsverwaltung. Wer einen Key erlangt, erhält die volle Kontrolle über
  die Mittel dieses Konten.
</Callout>

## Signing-Ansätze

| Ansatz                  | Wo der Key liegt                                     | Wer signiert                                          | Geeignet für                                                      |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **Lokales keypair**         | Eine Datei oder Umgebungsvariable auf dem Rechner           | Dein Code, direkt                                | Lokale Entwicklung, Tests, CI                                  |
| **Browser-Wallet**        | Die Wallet des Endbenutzers (z. B. Phantom, Solflare)          | Der Endbenutzer, pro Transaktion                      | Frontend-dApps, bei denen Nutzer ihre eigenen Transaktionen signieren        |
| **Cloud-KMS / HSM**       | Ein hardwaregestützter Key-Dienst (AWS KMS, GCP KMS, Vault) | Dein Backend fordert eine Signatur vom Dienst an | Backend-Dienste, Treasury-Operationen, regulierte Umgebungen |
| **Verwaltete / MPC-Wallets** | Aufgeteilt oder verwahrt in der Infrastruktur eines Anbieters   | Der Anbieter ko-signiert gemäß deiner Richtlinie     | Eingebettete Wallets, Genehmigungsworkflows, institutionelle Verwahrung   |

Das lokale keypair ist der einzige Ansatz, bei dem rohes Key-Material in deiner
Anwendung liegt. Jeder Produktionsansatz hält den Key in dedizierter Infrastruktur
und beauftragt diese Infrastruktur, in deinem Namen zu signieren.

## Backend-Signing

Wenn ein Server signieren muss — Fee zahlen, Programmtransaktionen senden oder
einen Treasury verwalten — verwende ein dediziertes Key-Management-Backend anstelle eines rohen
keypair. Die Solana Foundation pflegt [Keychain](/docs/tools/keychain), eine
einheitliche Signing-Bibliothek (Rust und TypeScript), die ein einziges `SolanaSigner`-Interface
über alle oben aufgeführten Backends hinweg bereitstellt: Memory, HashiCorp Vault, AWS
KMS, GCP KMS, Fireblocks, Privy, Turnkey, CDP, Crossmint, Dfns, Para, Openfort
und Utila.

Da das Interface über alle Backends hinweg identisch ist, kannst du lokal mit
einem In-Memory-Key entwickeln und per Konfiguration auf ein Produktions-Backend wechseln,
ohne den Anwendungscode neu schreiben zu müssen. Keychain ist kompatibel mit
[`@solana/kit`](/docs/clients/official/javascript) und dem
[Rust SDK](/docs/clients/official/rust).
