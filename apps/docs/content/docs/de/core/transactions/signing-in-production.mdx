Eine Transaktion wird nur ausgeführt, wenn sie eine gültige
[Signatur](/docs/core/transactions/transaction-structure#signatures) von jedem
erforderlichen Signer enthält. In der lokalen Entwicklung halten Sie diesen Schlüssel meist als
[`Keypair`](/developers/cookbook/wallets/create-keypair) und signieren direkt. In
der Produktion stellt sich eine andere, wichtige Frage: **Wo liegt der private Schlüssel,
und wer darf eine Signatur damit autorisieren?**

<Callout type="warn">
  Betten Sie private Schlüssel niemals in clientseitigen Code ein, bündeln Sie sie nicht in ein Frontend
  und committen Sie sie nicht in die Versionsverwaltung. Wer in den Besitz eines Schlüssels gelangt, erhält die volle Kontrolle
  über die Gelder der zugehörigen Konten.
</Callout>

## Signierverfahren

| Verfahren                  | Wo der Schlüssel liegt                                     | Wer signiert                                          | Am besten geeignet für                                                      |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **Lokales keypair**         | Eine Datei oder Umgebungsvariable auf dem Rechner           | Ihr Code, direkt                                | Lokale Entwicklung, Tests, CI                                  |
| **Browser-Wallet**        | Die Wallet des Endnutzers (z. B. Phantom, Solflare)          | Der Endnutzer, pro Transaktion                      | Frontend-dApps, in denen Nutzer ihre eigenen Transaktionen signieren        |
| **Cloud-KMS / HSM**       | Ein hardwaregestützter Schlüsseldienst (AWS KMS, GCP KMS, Vault) | Ihr Backend fordert eine Signatur vom Dienst an | Backend-Dienste, Treasury-Operationen, regulierte Umgebungen |
| **Verwaltete / MPC-Wallets** | Aufgeteilt oder verwahrt in der Infrastruktur eines Anbieters   | Der Anbieter signiert gemäß Ihrer Richtlinie mit     | Eingebettete Wallets, Freigabe-Workflows, institutionelle Verwahrung   |

Das lokale keypair ist der einzige Ansatz, der rohes Schlüsselmaterial in Ihre
Anwendung bringt. Jeder Produktionsansatz hält den Schlüssel in dedizierter Infrastruktur
und lässt diese Infrastruktur in Ihrem Auftrag signieren.

## Signieren im Backend

Wenn ein Server signieren muss (Fee-Zahlungen, Senden von Programmtransaktionen oder
Verwalten einer Treasury), verwenden Sie ein dediziertes Key-Management-Backend statt eines rohen
keypair. Die Solana Foundation pflegt [Keychain](/docs/tools/keychain), eine
einheitliche Signing-Bibliothek (Rust, TypeScript, Python und Go), die ein einziges
`SolanaSigner`-Interface für alle Backends in der obigen Tabelle bereitstellt: Memory,
HashiCorp Vault, AWS KMS, GCP KMS, Fireblocks, Privy, Turnkey, CDP, Crossmint,
Dfns, Para, Openfort, Utila und Fordefi.

Da das Interface für alle Backends gleich ist, können Sie lokal mit einem
Schlüssel im Arbeitsspeicher entwickeln und per Konfiguration auf ein Produktions-Backend umstellen, ohne
Ihren Anwendungscode umzuschreiben (Backends, die für Sie senden, wie Crossmint,
werden stattdessen über einen Sign-and-Send-Pfad aufgerufen). Keychain ist kompatibel mit
[`@solana/kit`](/docs/clients/official/javascript), dem
[Rust SDK](/docs/clients/official/rust), `solders` (Python) und `solana-go` v2
(Go).
