Kora ist ein Rust-Workspace mit drei Crates:

- `kora-lib` enthält die Kernlogik und den RPC-Server,
- `kora-cli` erzeugt die `kora`-Binärdatei, die Betreiber ausführen, und
- `kora-deploy` ist ein spezialisiertes Programm-Deployment-Tool mit eigener Versionierung.
  Alles Folgende befindet sich in `crates/lib/src`, sofern nicht anders angegeben.

## Wo sich die einzelnen Stufen befinden

| Stufe im Diagramm | Quelle                               | Einstiegspunkt                           |
| -------------------- | ------------------------------------ | ------------------------------------- |
| Gateway              | `rpc_server/server.rs`               | `run_rpc_server`                      |
| Dispatch             | `rpc_server/rpc.rs`                  | `KoraRpc`                             |
| Logik pro Methode     | `rpc_server/method/`                 | eine Datei pro JSON-RPC-Methode          |
| Validierung           | `validator/transaction_validator.rs` | `TransactionValidator`                |
| Plugins              | `plugin/mod.rs`                      | `TransactionPluginRunner`             |
| Signierung              | `signer/`                            | basiert auf dem Crate `solana-keychain` |

Zwei weitere Dateien, die man kennen sollte: `config.rs` definiert das gesamte `kora.toml`-Schema, und
`state.rs` hält die deserialisierte Konfiguration im prozessglobalen Zustand.

### Den RPC-Server lesen

`rpc.rs` ist eine schlanke Dispatch-Schicht mit einer Methode pro JSON-RPC-Endpunkt und der
schnellste Weg, die gesamte API zu überblicken. Die Logik jeder Methode liegt in einer eigenen Datei unter
`rpc_server/method/`. Lesen Sie `sign_transaction.rs` von Anfang bis Ende; die anderen Signierungsmethoden
sind Variationen davon.

### Den Validator lesen

`transaction_validator.rs` und `transaction/instruction_util.rs` enthalten die Logik zur
Validierung von Transaktionen und Anweisungen. Hinzu kommen die Safety-Property-Tests der
Fee-Payer-Policy, die pro abgesichertem Programm in einer eigenen Datei unter
`validator/transaction_validator/fee_payer_policy_props/` liegen.

## Wissenswerte Konventionen

**Standardvalidierung.** Jedes Flag unter `[validation.fee_payer_policy]`
hat den Standardwert `false`, und die Policy-Structs tragen `#[serde(default)]`. Diese
Kombination ist beabsichtigt: Das Hinzufügen einer neu abgesicherten Anweisung darf die
Konfiguration eines bestehenden Betreibers nicht beschädigen, und sie muss als Ablehnung statt als
versehentliche Erlaubnis wirken. Behalten Sie beides bei, wenn Sie ein Flag hinzufügen.

**Validieren Sie die aufgelöste Transaktion, niemals die rohe.** Die rohe
`VersionedTransaction` stellt nur die statischen Schlüssel der Konten bereit. Wer also eine V0-Transaktion darauf basierend validiert oder
bepreist, überspringt stillschweigend Lookup-Table-Konten und
berechnet zu wenig. `VersionedTransactionResolved::from_transaction` löst diese
Adressen gleich zu Beginn auf, weshalb jede nachgelagerte Stufe den aufgelösten Typ erwartet.

## Ein Transaktions-Plugin hinzufügen

Plugins implementieren den Trait `TransactionPlugin` in `plugin/mod.rs`. Er hat zwei
Methoden: `validate` läuft pro Transaktion während der Signierungsabläufe, und
`validate_config` läuft einmal beim Start und gibt Fehler und Warnungen für den
Betreiber zurück. Ein `PluginExecutionContext` teilt dem Plugin mit, welche der vier Signierungsmethoden
es aufgerufen hat.

`TransactionPluginRunner::from_config` führt ein Matching auf `TransactionPluginType` durch,
das in `config.rs` definiert ist. Ein neues integriertes Plugin besteht dort aus einer neuen Variante plus einem neuen
Match-Arm im Runner. Die beiden Plugins, die derzeit mitgeliefert werden, sind `gas_swap` und
`deploy_authority`.

## Tests

Kora hält die Konfiguration im prozessglobalen Zustand, daher deklariert `tests/` pro Phase ein
`[[test]]`-Target, und jedes Target startet sein eigenes eingebettetes Surfnet sowie
seinen eigenen Kora-Node, jeweils von Grund auf neu initialisiert. Eine Konfiguration pro Binärdatei: Eine neue Phase braucht ein neues
Target, kein neues Modul in einem bestehenden.

```bash
cargo test -p tests --test <target>
```

Alles andere ist über das `justfile` verdrahtet. Lesen Sie dieses, statt
Befehle von Hand zusammenzubauen.
