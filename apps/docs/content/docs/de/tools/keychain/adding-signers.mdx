Dieser Leitfaden richtet sich an Wallet-Dienstanbieter und Entwickler, die neue
Schlüsselverwaltungslösungen in die `solana-keychain`-Bibliothek integrieren
möchten. Durch das Hinzufügen Ihrer Signer-Implementierung ermöglichen Sie
Entwicklern, Ihren Dienst für die sichere Signierung von Solana-Transaktionen
über eine einheitliche Schnittstelle zu nutzen.

Keychain hält seine Implementierungen in Rust, TypeScript, Python und Go auf demselben Stand.
PRs, die alle vier enthalten, werden ausdrücklich bevorzugt. Wenn du nur eine
beisteuern kannst, ist das in Ordnung, aber rechne damit, dass die anderen verlangt werden, bevor der Signer
in einem Release ausgeliefert wird.

_Du nutzt Claude Code? Der
[`add-signer-ci`-Skill](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci) des Repos
richtet die CI-Workflows für einen neuen Signer ein, der über einen Fork-PR beigesteuert wird._

## Architekturübersicht

Die Bibliothek verwendet eine Trait-basierte Architektur, die in `src/traits.rs` definiert ist. Jeder
Signer implementiert den Basis-Trait `SolanaSigner` (`pubkey`, `sign_message`,
`is_available`) plus genau einen Capability-Trait, der zur Struktur des Providers passt:

- `TransactionSigner` (`sign_transaction`): Der Provider signiert die Bytes des
  Aufrufers, und der Aufrufer sendet sie per Broadcast. Die meisten Backends.
- `ModifyingSigner` (`modify_and_sign_transaction`): Der Provider schreibt die
  Transaktion um und signiert sie anschließend, ohne sie zu senden.
- `SendingSigner` (`sign_and_send_transaction`): Der Provider signiert und
  sendet serverseitig per Broadcast.

Die Bibliothek stellt außerdem ein einheitliches `Signer`-Enum bereit, das alle
Implementierungen kapselt und die Auswahl des Signing-Backends zur Laufzeit ermöglicht. Es implementiert
nur den Basis-Trait; auf Capabilities greift man über `as_transaction_signer()`,
`as_modifying_signer()` und `as_sending_signer()` zu.

## Schritt 3: Implementieren Sie Konstruktor- und Hilfsmethoden

Remote-Signer **müssen** HTTPS erzwingen und HTTP-Timeouts konfigurieren.
Verwenden Sie die gemeinsame `HttpClientConfig`-Struktur für
Timeout-Einstellungen.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## Schritt 4: Die Signer-Traits implementieren

Der Basis-Trait `SolanaSigner` hat 2 asynchrone Methoden (`sign_message`,
`is_available`) plus `pubkey()`. Das Signieren von Transaktionen gehört in einen Capability-Trait;
die meisten Provider implementieren `TransactionSigner`, dessen `sign_transaction`
`SignTransactionResult` zurückgibt (ein getaggtes Enum, das die Transaktion als vollständig oder
teilweise signiert kennzeichnet).

Signiere die Nachrichten-Bytes, niemals die gesamte Wire-Transaktion, und verifiziere die
Signatur des Providers dagegen, bevor du sie anhängst. Verwende die gemeinsamen
`TransactionUtil`-Helfer für Signierung und Serialisierung.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

Wenn dein Provider die Transaktion vor dem Signieren umschreibt, implementiere stattdessen
`ModifyingSigner` und ersetze die Transaktion des Aufrufers vollständig durch
die Bytes des Providers. Wenn er serverseitig sendet, implementiere `SendingSigner`
und lass die Transaktion des Aufrufers unverändert. Implementiere niemals eine Capability, die dein
Provider nicht bereitstellen kann.

## Schritt 6: Feature-Flag hinzufügen

Aktualisiere `Cargo.toml`, um deinen Signer als optionales Feature hinzuzufügen. Remote-Backends
enthalten den internen `_remote`-Marker, der die `From<reqwest::Error>`-
Implementierung in `src/error.rs` steuert; ohne ihn lässt sich `?` bei reqwest-Aufrufen nicht kompilieren, wenn nur
dein Feature aktiviert ist.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## Schritt 7: Signer-Enum aktualisieren

Füge deinen Signer in `src/lib.rs` hinzu. Die Basis-Implementierung von `SolanaSigner` leitet über
das Makro `dispatch_signer!` weiter, füge dort also einen Arm hinzu. Der Capability-Zugriff liegt in den
Accessoren `as_transaction_signer()`, `as_modifying_signer()` und `as_sending_signer()`:
Füge einen `Some(s)`-Arm zu dem Accessor hinzu, der zu deinem Capability-Trait passt (und,
bei einem sendenden oder modifizierenden Backend, einen `None`-Arm in `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## Schritt 8: Umfassende Tests hinzufügen

Fügen Sie Tests zu Ihrem Modul hinzu (am Ende von `src/your_service/mod.rs`):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

## Aktualisierungen der CI-Workflows (Fork-PRs)

CI ist ein zweistufiger Prozess. Stimme dich mit den Maintainern ab, um `main` vorzubereiten, bevor
dein PR getestet werden kann: Sie aktualisieren `fork-external-live-manual.yml`, fügen Umgebungsvariablen

Dein PR muss diese Änderungen der Phase 2 zusammen mit deinem Signer-Code enthalten:

- **`ci.yml`**: Füge dein Rust-Feature der `backend`-Matrix hinzu (vor `all`) und

- **`typescript-ci.yml`**: Füge dein Paket den Unit- und Integrationstest-
  Matrizen hinzu und ergänze Umgebungsvariablen im Integrationstest-Schritt
- **`typescript-publish.yml`**: Füge dein Paket zu `PUBLISH_PACKAGES`, zum
  `packages`-Array des GitHub Release und zur Übersichtstabelle hinzu
- **`python-ci.yml`**: Füge das Backend dem `CI_SIGNER_*`-Gating in
  `resolve-signers` und der Integrationsmatrix hinzu
- **`go-ci.yml`**: Füge das Backend dem `CI_SIGNER_*`-Gating und
  `moduleBySigner` hinzu

## TypeScript-Signer

Wenn Sie auch ein TypeScript-Signer-Paket hinzufügen, erstellen Sie es unter
`typescript/packages/your-signer/`. Wichtige Muster:

- Die Factory-Funktion `createYourSigner()` gibt
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>` zurück; halte die
  Signer-Klasse intern und exportiere nur die Factory und ihren Config-Typ
- Config-Interface exportieren (`YourSignerConfig`)
- Wenn dein Backend keine Nachrichten signieren kann, lass `SolanaMessageSigner` weg und stelle gar keine
  `signMessages`-Methode bereit: Kit klassifiziert Signer anhand des Vorhandenseins von Methoden, daher würde ein
  Stub, der eine Exception wirft, den Signer falsch klassifizieren
- Erzwinge HTTPS bei `apiBaseUrl`-Config-Feldern mit `assertHttpsUrl()` aus
  `@solana/keychain-core`
- Führe Remote-Aufrufe über `fetchSignerJson()` aus `@solana/keychain-core` aus,
  das für Fehler-Mapping, Bereinigung von Antworten, Ablehnung von Redirects und das
  Standard-Timeout zuständig ist
- Bereinige jeden anderen Fehlertext einer Remote-API mit `sanitizeRemoteErrorResponse()`
  aus `@solana/keychain-core`
- `throwSignerError(SignerErrorCode.*, { cause, message })` aus
  `@solana/keychain-core` verwenden
- Berücksichtige `config?.abortSignal` in jeder Signing-Methode und reiche es an
  `fetchSignerJson()` und `signBatchStaggered()` weiter
- Validiere `requestDelayMs` mit `validateRequestDelayMs()` und verarbeite Batches mit
  `signBatchStaggered()`
- `@throws` JSDoc zu Factory-Funktionen hinzufügen, die Fehlercodes auflisten
- Deklariere `@solana/*`-Pakete als Peer-Dependencies mit `>=8.1.0`
- Unit-Tests mit vitest und gemocktem `fetch`; Integrationstests mit
  `runSignerIntegrationTest` aus `@solana/keychain-test-utils`

### Sending Signer

Wenn dein Provider die Transaktion umschreibt oder serverseitig sendet, kann seine
Signatur nicht auf die Transaktion des Aufrufers angewendet werden, daher muss es ein
`SolanaSendingSigner` statt eines `SolanaTransactionSigner` sein:

- Implementiere `signAndSendTransactions()` und stelle **kein** `signTransactions`
  bereit (und auch kein `signMessages`, es sei denn, das Backend signiert tatsächlich Nachrichten)
- Berücksichtige `config?.abortSignal`. Sobald der Provider das Erstellen akzeptiert hat, melde
  jeden Fehler (einschließlich eines Abbruchs) als `BROADCAST_UNCONFIRMED` mit der
  Transaktions-ID des Providers und behalte den Abbruchgrund als `cause` bei
- Füge eine typisierte `createKeychainSigner`-Überladung hinzu, die deinen Sending-Signer-Typ zurückgibt
- Schließe dein Backend aus `KeychainKitPluginConfig` in
  `typescript/packages/kit-plugin/src/keychain-plugin.ts` aus, da ein Sending
  Signer nicht als `payer` oder `identity` eines Kit-Clients dienen kann
- Prüfe in Unit-Tests, dass `isTransactionPartialSigner()` für deine Instanzen false und
  `isTransactionSendingSigner()` true ist

### Umbrella-Paket aktualisieren

Aktualisiere `typescript/packages/keychain/` (7 zu ändernde Dateien):

1. `src/types.ts`: Füge `YourSignerConfig` zur diskriminierten Union
   `KeychainSignerConfig` hinzu
2. `src/create-keychain-signer.ts`: Füge den Switch-Case hinzu (jedes Backend-Paket wird
   mit einem dynamischen `import()` geladen)
3. `src/resolve-address.ts`: Füge ihn dem Switch-Case für den Fast-Path oder den Fetch-Path hinzu
4. `src/index.ts`: Füge die Exporte für Config-Typ, Namespace und Factory-Funktion hinzu
5. `package.json`: Füge die Dependency `@solana/keychain-your-signer: "workspace:*"` hinzu
6. `tsconfig.json`: Füge die Referenz `{ "path": "../your-signer" }` hinzu
7. `typescript/scripts/test-treeshake-umbrella.mjs`: Füge dein Paket zu
   `SIGNER_MARKERS` und deine Factory zu `FACTORIES` hinzu

Die Switch-Statements enthalten erschöpfende `never`-Prüfungen, daher meldet TypeScript einen Fehler,
wenn du die Union erweiterst, aber einen Case vergisst. Führe anschließend `just ts-treeshake` aus:
Jedes Paket und das Umbrella-Paket müssen tree-shakable bleiben.

## Python-Signer

Erstelle das Modul unter `python/src/solana_keychain/your_signer/` (`__init__.py`
plus `signer.py`). Wichtige Muster:

- Leite von `SolanaSigner` aus `solana_keychain.core` ab (`pubkey`-Property,
  `async sign_message()`, `async is_available()`) plus genau eine Capability-
  Klasse: `TransactionSigner` (`async sign_transaction()`), `ModifyingSigner`
  (`async modify_and_sign_transaction()`) oder `SendingSigner`
  (`async sign_and_send_transaction()`)
- Exportiere eine `async create_your_signer()`-Factory, die `init()` abwartet, wenn das
  Backend seine Adresse remote auflöst; vor dem Init löst das Signieren
  `SignerErrorCode.NOT_INITIALIZED` aus
- Exportiere eine Config-Dataclass (`YourSignerConfig`), bei der Secrets mit
  `field(repr=False)` markiert sind
- Erzwinge HTTPS bei Base-URL-Feldern mit `assert_https_url()` und leite jede
  Anfrage über `fetch_signer_json()`
- Verifiziere die Signatur des Providers, bevor du sie zurückgibst; verwende
  `signed_message_bytes()` für die Bytes, die eine Signatur abdeckt, niemals ein selbstgebautes
  Versionspräfix
- Registriere das Backend in `_BACKENDS` in
  `python/src/solana_keychain/keychain.py`
- Wenn das Backend ein Provider-SDK benötigt: Import absichern, einen `ImportError` auslösen, der `pip install 'solana-keychain[your-signer]'` nennt, das Extra in
  `python/pyproject.toml` deklarieren und das Backend niemals eager aus dem Package-Root importieren
- Unit-Tests mit pytest: `respx` für HTTP-Backends, Stub-Clients für SDK-Backends und eine Prüfung, dass in `str()` oder `repr()` ausgelöster Fehler kein Secret auftaucht
- Eine `make_your_signer()`-Factory zu
  `python/tests/integration/test_live_signers.py` hinzufügen und in
  `_MESSAGE_CAPABLE` registrieren (oder in `_TRANSACTION_ONLY` für Backends ohne
  `sign_message`)

## Go-Signer

Jedes Go-Backend ist ein eigenes Modul unter `go/signers/yoursigner/` mit dem Modulpfad
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`. Als Referenz siehe
`go/signers/para/`. Wichtige Muster:

- `core.SolanaSigner` implementieren (`Pubkey()`, `SignMessage(ctx, message)`,
  `IsAvailable(ctx)`) plus genau ein Capability-Interface:
  `core.TransactionSigner`, `core.ModifyingSigner` oder `core.SendingSigner`.
  Die Capability wird per Type Assertion erkannt, daher darf ein Backend, das keine
  Transaktion signieren kann, überhaupt keine `SignTransaction`-Methode besitzen
- Ein `Config`-Struct und einen `New`-Konstruktor exportieren (`New(ctx, cfg)`, wenn das
  Backend seine Adresse remote auflöst; davor `core.NewNotInitializedError` zurückgeben)
- HTTP-Clients mit `core.NewHTTPClient` oder `core.ResolveHTTPClient` erstellen und
  Basis-URLs mit `core.NormalizeHTTPSBaseURL` prüfen
- Transaktionen mit `core.SignTransactionWith` signieren, das die Nachrichten-Bytes signiert und die Signatur anhängt; Signaturen des Providers mit
  `core.VerifySignature` verifizieren
- Fehler mit `core.NewSignerError` / `core.WrapSignerError` und stabilen
  Codes wie `core.CodeSigningFailed` zurückgeben
- Unit-Tests mit `httptest`; Integrationstests in `integration_test.go` hinter
  dem Tag `//go:build integration`

## Implementierungstipps

### Fehlerbehandlung

Verwende immer die vorhandenen `SignerError`-Varianten. Sowohl `Display` als auch `Debug` von
`SignerError` sind maskiert, halte Meldungen daher generisch und nimm niemals rohe API-Antwortdaten
auf. Verwende niemals `.expect()` oder `.unwrap()` bei nicht vertrauenswürdigen API-Antworten:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### Sicherheitsanforderungen

Das sind keine Empfehlungen: Nutzer wählen ein Backend auf Grundlage dieser Punkte. Macht
dein Provider eine davon unmöglich, halte das im PR und in der `docs/SECURITY_MODEL.md` des Repos fest.

- **Verifiziere, was der Provider signiert hat.** Berechne die Nachrichten-Bytes lokal und
  verifiziere die zurückgegebene Signatur an der für deinen Signer erforderlichen Position dagegen,
  bevor du sie anhängst. Eine Signatur, die sich nicht verifizieren lässt, muss fehlschlagen und darf
  niemals angehängt werden.
- **Lege offen, ob der Provider broadcastet.** Wenn er serverseitig ausführt,
  implementiere die Sending-Variante und gib die Signatur zurück, die die gelandete Transaktion identifiziert.
  Hat der Provider keinen Endpunkt nur zum Signieren, mache das Backend sending-only, statt
  hinter dem Rücken des Aufrufers zu senden.
- **Hinterlasse dem Aufrufer niemals eine Transaktion, die von der Signatur nicht abgedeckt ist.**
  Ein Provider, der die Transaktion umschreibt, signiert seine eigenen Bytes: Entweder bleibt die
  Transaktion des Aufrufers unverändert (der broadcast-verwaltete Fall), oder du nutzt die
  modifizierende Variante und ersetzt sie vollständig durch die Bytes des Providers.
- **Melde Broadcast-Unsicherheit als solche.** Ein Fehler nach dem Absenden kann trotzdem
  gelandet sein. Gib `BROADCAST_UNCONFIRMED` statt eines generischen Fehlers zurück,
  übergib die Transaktions-ID des Providers, sobald du eine hast, und sende bei jedem Create einen
  aus der Nachricht abgeleiteten Idempotency-Key, damit ein byte-identisches erneutes Senden
  sicher ist.
- **Signiere nie vor der Initialisierung.** Verwende `Option<Pubkey>` (nicht `Pubkey::default()`) für
  den öffentlichen Schlüssel vor `init()` und brich mit einem Konfigurationsfehler ab, wenn zuvor
  signiert werden soll.
- Protokolliere niemals sensible Daten (private Schlüssel, API-Secrets, rohe API-Antworten) und
  verwende eine `Debug`-Implementierung, die sensible Felder verbirgt
- HTTPS erzwingen (`https_only(true)`, mit `#[cfg(not(test))]` für wiremock abgesichert) und Request- sowie Connect-Timeouts über `HttpClientConfig` konfigurieren
  (Standardwerte: 30 s/5 s)
- Zwischenschlüsselmaterial mit `zeroize::Zeroizing<Vec<u8>>` nullen

### Testen mit Mocks

Verwenden Sie `wiremock` zum Mocken von HTTP-APIs. Prüfen Sie nur den Fehlertyp,
nicht den Fehlermeldungstext:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
