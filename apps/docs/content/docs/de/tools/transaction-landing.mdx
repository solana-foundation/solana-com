## RPC-Infrastruktur

[Öffentliche Endpunkte](https://solana.com/docs/references/clusters#solana-public-rpc-endpoints)
(`api.mainnet.solana.com`) sind ratenbegrenzt und ohne SLA. Für die
Entwicklung sind sie in Ordnung, aber in produktiven Zahlungsabläufen versagen sie – so, als würdest du einen
Zahlungsabwickler über eine geteilte API ohne Verfügbarkeitsgarantie betreiben.

<Callout type="caution" title="Verwende in der Produktion niemals öffentliche RPCs">
  Nutze einen [privaten RPC-Anbieter](https://solana.com/rpc) für zuverlässigen Zugriff
  mit niedriger Latenz.
</Callout>

Achte bei der Wahl eines RPC-Anbieters auf Folgendes:

- **Zuverlässigkeit**: SLAs mit Verfügbarkeitsgarantien (99,9 %+)
- **Latenz**: Geografische Nähe zu deinen Nutzern
- **Funktionen**: Funktionen für Transaction Landing, Indexierung, priority fee APIs

Eine vollständige Liste von RPC-Anbietern findest du im Leitfaden
[RPC-Infrastruktur-Anbieter](https://solana.com/rpc).

### Redundante RPC-Konfiguration

Wie jeder Netzwerkdienstleister können auch RPC-Anbieter Ausfallzeiten oder
Phasen verminderter Leistung erleben. Damit deine Anwendung widerstandsfähig ist,
solltest du sie so konfigurieren, dass sie mehrere RPC-Anbieter verwendet.

[Solana Kit](https://github.com/anza-xyz/kit/tree/main/packages/rpc-transport-http)
bietet eine Bibliothek zur Anpassung von RPC-Transports, mit der du deinen
eigenen redundanten RPC-Client bauen kannst. Hier ist ein Beispiel, wie du damit einen
redundanten RPC-Client erstellen könntest:

```ts
import { RpcTransport } from "@solana/rpc-spec";
import { RpcResponse } from "@solana/rpc-spec-types";
import { createHttpTransport } from "@solana/rpc-transport-http";

// Create a transport for each RPC server
const transports = [
  createHttpTransport({ url: "https://mainnet-beta.my-server-1.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-2.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-3.com" })
];

// Create a wrapper transport that distributes requests to them
let nextTransport = 0;
async function roundRobinTransport<TResponse>(
  ...args: Parameters<RpcTransport>
): Promise<RpcResponse<TResponse>> {
  const transport = transports[nextTransport];
  nextTransport = (nextTransport + 1) % transports.length;
  return await transport(...args);
}
```

Wenn du keine eigenen Routing-Tools bauen möchtest, kannst du einen Drittanbieter-Dienst
wie [Iron Forge](https://www.ironforge.sanctum.so/) nutzen, der das
Routing für dich übernimmt.

## Transaction Landing

Im Devnet landen Transaktionen recht problemlos. Im Mainnet konkurrierst du um
Blockplatz. Um die Chancen zu erhöhen, dass deine Transaktion in einen
Block aufgenommen wird, solltest du sicherstellen, dass du deine Transaktion korrekt zusammengestellt hast. Das
bedeutet:

- vor dem Senden der Transaktion einen aktuellen Blockhash einzubinden
- eine Anweisung für die priority fee in die Transaktion aufzunehmen, mit einer wettbewerbsfähigen
  priority fee
- eine Anweisung für das Compute-Unit-Limit in die Transaktion aufzunehmen, mit einem Compute-Unit-Limit, das auf
  den geschätzten, für die Transaktion benötigten Compute Units basiert

Zusätzlich solltest du weitere Tools wie Jito Bundles in Betracht ziehen, um die
Chancen zu erhöhen, dass deine Transaktion in einen Block aufgenommen wird. Sehen wir uns diese Tools
genauer an.

### Konfiguration für das Senden von Transaktionen

Konfiguriere beim Senden von Transaktionen im Mainnet diese Parameter für optimale
Landing-Raten:

**Blockhash-Verwaltung:**

- Mit `confirmed`-Commitment abrufen
- Speichere den von `getLatestBlockhash` zurückgegebenen `lastValidBlockHeight` – er zeigt dir,
  wann deine Transaktion abläuft
- Blockhashes laufen nach einer vom Protokoll festgelegten Zeit ab, die von der slot-Länge
  abhängt.

**Sendeoptionen:**

- `maxRetries: 0` – Deaktiviert automatische RPC-Wiederholungen. Kümmere dich selbst um Wiederholungen,
  damit du den Blockhash bei Bedarf erneuern kannst.
- `skipPreflight: true` – Überspringt die Simulation vor dem Senden. Verwende dies, wenn du die Transaktion
  bereits validiert hast und die niedrigste Latenz möchtest. Lass es während der Entwicklung auf `false`,
  um Fehler frühzeitig zu erkennen.

```typescript
import { createSolanaRpc } from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);

// 1. Get blockhash with confirmed commitment
const { value: latestBlockhash } = await rpc
  .getLatestBlockhash({ commitment: "confirmed" })
  .send();

// 2. Build and sign your transaction with the blockhash
// ... (transaction building code)

// 3. Send with production settings
const signature = await rpc
  .sendTransaction(encodedTransaction, {
    encoding: "base64",
    maxRetries: 0n, // Handle retries yourself
    skipPreflight: true, // Skip simulation for speed (use false during dev)
    preflightCommitment: "confirmed"
  })
  .send();

// 4. Track expiration using lastValidBlockHeight
const { lastValidBlockHeight } = latestBlockhash;
// Stop retrying when current block height exceeds lastValidBlockHeight
```

### Priority Fee verwenden

Jede Solana-Transaktion erfordert eine Transaktions-Fee, die in SOL bezahlt wird. Die Transaktions-Fee
setzt sich aus zwei Teilen zusammen: der Base Fee und der priority fee. Die Base Fee
vergütet Validatoren für die Verarbeitung der Transaktion. Die priority fee ist ein
optionaler Betrag, der die Wahrscheinlichkeit erhöht, dass der aktuelle Leader deine
Transaktion verarbeitet. Stell dir das wie Expressversand vor: Du zahlst mehr für eine schnellere und
zuverlässigere Zustellung.

**So funktioniert die Fee-Berechnung:**

```
Total fee = Base fee (5,000 lamports per signature) + Priority fee
Priority fee (legacy/v0) = ceil(compute_unit_price * compute_unit_limit / 1,000,000) lamports
Priority fee (v1 only) = Absolute total in lamports set in the message config
```

**Reale Kosten:**

- Einfache USDC-Überweisung: ca. 0,001–0,005 $ unter normalen Bedingungen
- Bei Überlastung: ca. 0,01–0,05 $
- Spitzenauslastung: Kann noch höher steigen

**Beispielimplementierung:**

Das Paket
[`@solana-program/compute-budget`](https://github.com/solana-program/compute-budget)
bietet eine Hilfsfunktion, mit der du die Anweisung für den Compute-Unit-Preis
(in Mikro-Lamports) einer Transaktion einfach aktualisieren oder anhängen kannst.

```typescript
import { updateOrAppendSetComputeUnitPriceInstruction } from "@solana-program/compute-budget";

const tx = pipe(
  createTransactionMessage({ version: 0 }),
  (m) => setTransactionMessageFeePayerSigner(payer, m),
  (m) => setTransactionMessageLifetimeUsingBlockhash(latestBlockhash, m),
  (m) => appendTransactionMessageInstructions([myInstructions], m),
  (m) => updateOrAppendSetComputeUnitPriceInstruction(1000n as MicroLamports, m)
);
```

**Fee-Schätzungen abrufen:** Die meisten RPC-Anbieter bieten priority fee APIs an:

- [Helius Priority Fee API](https://docs.helius.dev/solana-apis/priority-fee-api)
- [QuickNode Priority Fee Add-on](https://marketplace.quicknode.com/add-on/solana-priority-fee)
- [Triton Priority Fees API](https://docs.triton.one/chains/solana/improved-priority-fees-api)

Die vollständigen Fee-Mechanismen findest du unter [Transaktions-Fee](/docs/core/fees) und in unserem
Leitfaden:
[So fügst du einer Transaktion eine priority fee hinzu](https://solana.com/developers/cookbook/transactions/add-priority-fees).

### Compute Units optimieren

Rechenleistung wird auf Solana in Compute Units (CUs) gemessen, die eine grobe Schätzung
des Arbeitsaufwands eines Programms darstellen. Die aktuellen Limits liegen bei 50 Millionen
CUs pro Block und 1,4 Millionen CUs pro Transaktion. Wenn du eine
Transaktion einreichst, musst du den voraussichtlichen Rechenaufwand schätzen und
das Compute-Unit-Limit entsprechend festlegen – das ist effektiv eine Anfrage, wie viel
der Gesamtkapazität für deine Transaktion reserviert werden soll. In
der Praxis bedeutet das: Eine korrekte Schätzung der für deine
Transaktion benötigten Compute Units ist entscheidend dafür, dass deine Transaktion in einen Block aufgenommen wird (und
wichtig für die Verwaltung deiner priority fee). Das Compute-Limit für Transaktionen und Blöcke
wird vom Protokoll bestimmt.

Die Solana JSON RPC API hat eine
[`simulatetransaction`](/docs/rpc/http/simulatetransaction)-Methode, mit der
die für eine Transaktion benötigten Compute Units geschätzt werden können, einschließlich einer
Schätzung der Compute Units, die verbraucht werden.
[`@solana/kit`](https://github.com/anza-xyz/kit) stellt Hilfsfunktionen bereit, die
die Ressourcenlimits einer Transaktion schätzen und in einem Schritt in der Nachricht setzen
(im Hintergrund über die Methode `simulatetransaction`). Bei Transaktionen der Version 1
schätzen diese Hilfsfunktionen zusätzlich das Größenlimit der Daten der geladenen Konten.

```ts
import {
  estimateResourceLimitsFactory,
  estimateAndSetResourceLimitsFactory
} from "@solana/kit";

const estimateResourceLimits = estimateResourceLimitsFactory({ rpc });
const estimateAndSetResourceLimits = estimateAndSetResourceLimitsFactory(
  estimateResourceLimits
);
const txWithResourceLimits = await estimateAndSetResourceLimits(tx);
```

<Callout type="info">
  Wenn du Transaktionen mit einem Kit-Plugin-Client erstellst und sendest, brauchst du diesen Schritt
  in der Regel nicht – der Client fügt die Compute-Budget-Anweisungen für dich hinzu,
  wenn er sendet (`.sendTransaction()`). Der oben beschriebene manuelle Ablauf gilt für den Fall, dass du
  Transaktionen direkt mit `@solana/kit` zusammenstellst.
</Callout>

Wenn du in der Produktion denselben Transaktionstyp mehrfach wiederholst,
solltest du erwägen, die Compute-Schätzung für diesen Transaktionstyp zu cachen, um
den Mehraufwand der Schätzung der Compute Units bei jedem Mal zu vermeiden.

### Jito Bundles

Jito Bundles sind ein Werkzeug zur atomaren Ausführung mehrerer Transaktionen.
Dazu werden mehrere Transaktionen mit einem Trinkgeld (Tip) an das Jito-Netzwerk gesendet.
Mit Tips lässt sich das Jito-Netzwerk dazu motivieren, deine
Transaktionen in einen Block aufzunehmen.

### Wiederholungsstrategien

Transaktionen können aus vielen Gründen fehlschlagen. Anders als herkömmliche Zahlungs-APIs, die
Erfolg oder Misserfolg sofort zurückmelden, erfordern Blockchain-Transaktionen eine Nachverfolgung
der Bestätigung.

**Zentrale Konzepte:**

- **Blockhash-Ablauf**: Blockhash-Ablauf: Transaktions-Blockhashes bleiben
  150 slots lang gültig (etwa 30 Sekunden bei 200 ms slot-Zeit). Die tatsächliche
  Ablaufzeit kann je nach Geschwindigkeit der Blockproduktion variieren. Verwende
  lastValidBlockHeight, um festzustellen, wann ein Blockhash abgelaufen ist.
- **Idempotenz**: Dieselbe signierte Transaktion erzeugt immer dieselbe
  Signatur – ein erneutes Senden ist sicher
- **Exponentielles Backoff**: Vermeide es, das Netzwerk mit schnellen Wiederholungen zu überlasten

```typescript
import {
  createSolanaRpc,
  createSolanaRpcSubscriptions,
  sendAndConfirmTransactionFactory,
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED
} from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);
const rpcSubscriptions = createSolanaRpcSubscriptions(process.env.RPC_WSS_URL!);

const sendAndConfirmTransaction = sendAndConfirmTransactionFactory({
  rpc,
  rpcSubscriptions
});

// Send with automatic confirmation tracking and block height monitoring
try {
  await sendAndConfirmTransaction(signedTransaction, {
    commitment: "confirmed",
    // Optional: abort after 75 seconds
    abortSignal: AbortSignal.timeout(75_000)
  });
} catch (e) {
  if (isSolanaError(e, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED)) {
    // Blockhash expired—rebuild transaction with fresh blockhash and retry
    rebuildAndRetryTransaction(); // implement your own logic for rebuilding and retrying the transaction
  }
  throw e;
}
```

Die `sendAndConfirmTransactionFactory` aus `@solana/kit` übernimmt das Bestätigungs-Polling
und die Verfolgung der Blockhöhe automatisch. Sie löst
`SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED` aus, wenn der Blockhash der Transaktion abläuft.
Das signalisiert, dass du die Transaktion mit einem aktuellen Blockhash neu aufbauen musst.

## Fehlerbehandlung

Solana Kit stellt typisierte Fehler über `isSolanaError()` bereit. Verwende spezifische Fehlercodes
anstelle von String-Vergleichen:

```typescript
import {
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED,
  SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE,
  SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND,
  SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS
} from "@solana/kit";

function handlePaymentError(error: unknown): {
  message: string;
  retryable: boolean;
} {
  // Blockhash expired—rebuild and retry
  if (
    isSolanaError(error, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED) ||
    isSolanaError(error, SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND)
  ) {
    return { message: "Transaction expired—rebuilding", retryable: true };
  }

  // Insufficient SOL for fees
  if (
    isSolanaError(
      error,
      SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE
    )
  ) {
    return { message: "Not enough SOL for fees", retryable: false };
  }

  // Insufficient token balance
  if (
    isSolanaError(error, SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS)
  ) {
    return { message: "Insufficient balance", retryable: false };
  }

  // Unknown error
  console.error("Payment error:", error);
  return { message: "Payment failed—please retry", retryable: true };
}
```

**Häufige Fehlercodes:**

| Fehlercode                   | Ursache                 | Behebung                                                                                                 |
| ---------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------- |
| `BLOCK_HEIGHT_EXCEEDED`      | Blockhash abgelaufen     | Mit aktuellem Blockhash neu aufbauen                                                                             |
| `BLOCKHASH_NOT_FOUND`        | Blockhash nicht gefunden   | Mit aktuellem Blockhash neu aufbauen                                                                             |
| `INSUFFICIENT_FUNDS_FOR_FEE` | Nicht genug SOL        | Fee Payer aufladen oder [Fee Abstraction](/docs/payments/send-payments/payment-processing/fee-abstraction) verwenden |
| `INSUFFICIENT_FUNDS`         | Nicht genug Token     | Nutzer benötigt mehr Guthaben                                                                                  |
| `ACCOUNT_NOT_FOUND`          | token account fehlt | ATA in der Transaktion erstellen                                                                                |

## Gasless-Transaktionen

Nutzer erwarten, in Stablecoins zu bezahlen, und nicht erst SOL für die Netzwerk-Fee besorgen zu müssen. Gasless-
Transaktionen lösen dieses Problem – ähnlich wie Venmo-Nutzer nicht über ACH-Fee nachdenken.
Siehe
[Fee Abstraction](/docs/payments/send-payments/payment-processing/fee-abstraction)
für die vollständige Implementierung.
