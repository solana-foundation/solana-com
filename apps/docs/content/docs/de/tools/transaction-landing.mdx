## RPC-Infrastruktur

[Öffentliche Endpunkte](https://solana.com/docs/references/clusters#solana-public-rpc-endpoints)
(`api.mainnet.solana.com`) sind ratenbegrenzt und bieten kein SLA. Für die
Entwicklung sind sie in Ordnung, versagen aber bei Zahlungsabläufen in der
Produktion – als würde man einen Zahlungsabwickler über eine geteilte API ohne
Verfügbarkeitsgarantie betreiben.

<Callout type="caution" title="Verwenden Sie in der Produktion niemals öffentliche RPC-Endpunkte">
  Nutzen Sie einen [privaten RPC-Anbieter](https://solana.com/rpc) für zuverlässigen Zugriff
  mit niedriger Latenz.
</Callout>

Achten Sie bei der Auswahl eines RPC-Anbieters auf Folgendes:

- **Zuverlässigkeit**: SLAs mit Verfügbarkeitsgarantien (99,9 %+)
- **Latenz**: Geografische Nähe zu Ihren Nutzern
- **Funktionen**: Funktionen für Transaction Landing, Indexierung, APIs für priority fee

Eine vollständige Liste von RPC-Anbietern finden Sie im Leitfaden
[RPC-Infrastruktur-Anbieter](https://solana.com/rpc).

### Redundante RPC-Konfiguration

Wie jeder Netzwerkdienstanbieter können auch RPC-Anbieter Ausfälle oder
Phasen mit eingeschränkter Leistung erleben. Damit Ihre Anwendung robust ist,
sollten Sie sie so konfigurieren, dass sie mehrere RPC-Anbieter verwendet.

[Solana Kit](https://github.com/anza-xyz/kit/tree/main/packages/rpc-transport-http)
bietet eine Bibliothek zur Anpassung von RPC-Transports, mit der Sie Ihren
eigenen redundanten RPC-Client bauen können. Hier ein Beispiel, wie Sie dafür
vorgehen könnten:

```ts
import { RpcTransport } from "@solana/rpc-spec";
import { RpcResponse } from "@solana/rpc-spec-types";
import { createHttpTransport } from "@solana/rpc-transport-http";

// Create a transport for each RPC server
const transports = [
  createHttpTransport({ url: "https://mainnet-beta.my-server-1.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-2.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-3.com" })
];

// Create a wrapper transport that distributes requests to them
let nextTransport = 0;
async function roundRobinTransport<TResponse>(
  ...args: Parameters<RpcTransport>
): Promise<RpcResponse<TResponse>> {
  const transport = transports[nextTransport];
  nextTransport = (nextTransport + 1) % transports.length;
  return await transport(...args);
}
```

Wenn Sie keine eigenen Routing-Tools bauen möchten, können Sie einen
Drittanbieter-Dienst wie [Iron Forge](https://www.ironforge.sanctum.so/) nutzen, der das Routing für Sie
übernimmt.

## Transaction Landing

Auf Devnet landen Transaktionen recht problemlos. Auf Mainnet konkurrieren Sie
um Blockplatz. Um die Chancen zu erhöhen, dass Ihre Transaktion in einen Block
aufgenommen wird, sollten Sie sicherstellen, dass Ihre Transaktion korrekt
zusammengestellt ist. Das bedeutet:

- einen aktuellen Blockhash einbinden, bevor die Transaktion gesendet wird
- eine Anweisung für die priority fee mit einer wettbewerbsfähigen priority fee
  in die Transaktion aufnehmen
- eine Anweisung für das Compute-Unit-Limit in die Transaktion aufnehmen, mit
  einem Limit auf Basis der geschätzten Compute Units, die für die Transaktion
  erforderlich sind

Zusätzlich sollten Sie weitere Tools wie Jito Bundles in Betracht ziehen, um
die Chancen zu erhöhen, dass Ihre Transaktion in einen Block aufgenommen wird.
Sehen wir uns diese Tools genauer an.

### Konfiguration für das Senden von Transaktionen

Konfigurieren Sie beim Senden von Transaktionen auf Mainnet diese Parameter für
optimale Landing-Raten:

**Blockhash-Verwaltung:**

- Mit dem Commitment `confirmed` abrufen
- Speichern Sie den von `getLatestBlockhash` zurückgegebenen
  `lastValidBlockHeight` – er zeigt Ihnen, wann Ihre Transaktion abläuft
- Blockhashes laufen nach einer vom Protokoll festgelegten Zeit ab, die von der
  Länge des slot abhängt.

**Sendeoptionen:**

- `maxRetries: 0` — Deaktiviert automatische RPC-Wiederholungen. Kümmern Sie sich
  selbst um Wiederholungen, damit Sie den Blockhash bei Bedarf erneuern können.
- `skipPreflight: true` — Überspringt die Simulation vor dem Senden. Verwenden Sie
  dies, wenn Sie die Transaktion bereits validiert haben und die niedrigste
  Latenz wünschen. Belassen Sie es während der Entwicklung bei `false`, um
  Fehler frühzeitig zu erkennen.

```typescript
import { createSolanaRpc } from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);

// 1. Get blockhash with confirmed commitment
const { value: latestBlockhash } = await rpc
  .getLatestBlockhash({ commitment: "confirmed" })
  .send();

// 2. Build and sign your transaction with the blockhash
// ... (transaction building code)

// 3. Send with production settings
const signature = await rpc
  .sendTransaction(encodedTransaction, {
    encoding: "base64",
    maxRetries: 0n, // Handle retries yourself
    skipPreflight: true, // Skip simulation for speed (use false during dev)
    preflightCommitment: "confirmed"
  })
  .send();

// 4. Track expiration using lastValidBlockHeight
const { lastValidBlockHeight } = latestBlockhash;
// Stop retrying when current block height exceeds lastValidBlockHeight
```

### Die priority fee nutzen

Jede Solana-Transaktion erfordert eine Transaktions-Fee, die in SOL bezahlt
wird. Transaktions-Fees setzen sich aus zwei Teilen zusammen: der Basis-Fee und
der priority fee. Die Basis-Fee vergütet Validatoren für die Verarbeitung der
Transaktion. Die priority fee ist optional und erhöht die Wahrscheinlichkeit,
dass der aktuelle Leader Ihre Transaktion verarbeitet. Stellen Sie es sich wie
Expressversand vor: Sie zahlen mehr für eine schnellere, zuverlässigere
Zustellung.

**So funktioniert die Fee-Berechnung:**

```
Total fee = Base fee (5,000 lamports per signature) + Priority fee
Priority fee (legacy/v0) = ceil(compute_unit_price * compute_unit_limit / 1,000,000) lamports
Priority fee (v1 only) = Absolute total in lamports set in the message config
```

**Reale Kosten:**

- Einfacher USDC-Transfer: ca. 0,001–0,005 $ unter normalen Bedingungen
- Bei Überlastung: ca. 0,01–0,05 $
- Bei Spitzenlast: Kann noch höher steigen

**Beispielimplementierung:**

Das Paket
[`@solana-program/compute-budget`](https://github.com/solana-program/compute-budget)
stellt eine Hilfsfunktion bereit, mit der Sie die Anweisung für den Compute-Unit-Preis
(in Micro-Lamports) einfach aktualisieren oder an eine Transaktion anhängen
können.

```typescript
import { updateOrAppendSetComputeUnitPriceInstruction } from "@solana-program/compute-budget";

const tx = pipe(
  createTransactionMessage({ version: 0 }),
  (m) => setTransactionMessageFeePayerSigner(payer, m),
  (m) => setTransactionMessageLifetimeUsingBlockhash(latestBlockhash, m),
  (m) => appendTransactionMessageInstructions([myInstructions], m),
  (m) => updateOrAppendSetComputeUnitPriceInstruction(1000n as MicroLamports, m)
);
```

**Fee-Schätzungen abrufen:** Die meisten RPC-Anbieter bieten APIs für priority fee an:

- [Helius Priority Fee API](https://docs.helius.dev/solana-apis/priority-fee-api)
- [QuickNode Priority Fee Add-on](https://marketplace.quicknode.com/add-on/solana-priority-fee)
- [Triton Priority Fees API](https://docs.triton.one/chains/solana/improved-priority-fees-api)

Die vollständigen Fee-Mechanismen finden Sie unter [Transaktions-Fee](/docs/core/fees)
und in unserer Anleitung:
[Wie man einer Transaktion eine priority fee hinzufügt](https://solana.com/developers/cookbook/transactions/add-priority-fees).

### Compute Units optimieren

Rechenleistung wird auf Solana in Compute Units (CUs) gemessen, einer groben
Schätzung der Arbeit, die das Programm leistet. Die aktuellen Compute-Limits
betragen 50 Millionen CUs pro Block und 1,4 Millionen CUs pro Transaktion. Wenn
Sie eine Transaktion einreichen, müssen Sie die Menge der benötigten Rechenleistung
schätzen und das Compute-Unit-Limit entsprechend festlegen – das ist faktisch eine
Anforderung, wie viel der Gesamtkapazität für Ihre Transaktion reserviert werden
soll. In der Praxis bedeutet das: Eine korrekte Schätzung der für Ihre
Transaktion erforderlichen Compute Units ist entscheidend dafür, dass Ihre
Transaktion in einen Block aufgenommen wird (und wichtig für die Verwaltung Ihrer
priority fee). Die Compute-Limits für Transaktion und Block werden vom Protokoll
bestimmt.

Die Solana JSON RPC API hat eine Methode
[`simulatetransaction`](/docs/rpc/http/simulatetransaction), mit der sich die für eine Transaktion
erforderlichen Compute Units schätzen lassen, einschließlich einer Schätzung der
tatsächlich verbrauchten Compute Units.
[`@solana/kit`](https://github.com/anza-xyz/kit) stellt Hilfsfunktionen bereit, die die Ressourcenlimits
einer Transaktion schätzen und in einem Schritt auf die Nachricht setzen (unter
der Haube mit der Methode `simulatetransaction`). Bei Transaktionen der Version 1
schätzen diese Helfer zusätzlich das Größenlimit der Daten geladener Konten.

```ts
import {
  estimateResourceLimitsFactory,
  estimateAndSetResourceLimitsFactory
} from "@solana/kit";

const estimateResourceLimits = estimateResourceLimitsFactory({ rpc });
const estimateAndSetResourceLimits = estimateAndSetResourceLimitsFactory(
  estimateResourceLimits
);
const txWithResourceLimits = await estimateAndSetResourceLimits(tx);
```

<Callout type="info">
  Wenn Sie Transaktionen mit einem Kit-Plugin-Client erstellen und senden,
  benötigen Sie diesen Schritt in der Regel nicht – der Client fügt die
  Compute-Budget-Anweisungen beim Senden (`.sendTransaction()`) automatisch
  hinzu. Der obige manuelle Ablauf gilt für den Fall, dass Sie Transaktionen
  direkt mit `@solana/kit` zusammenstellen.
</Callout>

Wenn Sie in der Produktion denselben Transaktionstyp mehrfach wiederholen,
sollten Sie die Compute-Schätzung für diesen Transaktionstyp zwischenspeichern,
um den Mehraufwand zu vermeiden, die Compute Units jedes Mal neu zu schätzen.

### Jito Bundles

Jito Bundles sind ein Werkzeug zur atomaren Ausführung mehrerer Transaktionen.
Dies wird erreicht, indem mehrere Transaktionen zusammen mit einem Tip an das
Jito-Netzwerk gesendet werden. Tips können als Anreiz dienen, damit das
Jito-Netzwerk Ihre Transaktionen in einen Block aufnimmt.

**Ressourcen:**

### Wiederholungsstrategien

Transaktionen können aus vielen Gründen fehlschlagen. Anders als herkömmliche
Zahlungs-APIs, die Erfolg oder Misserfolg sofort zurückmelden, erfordern
Blockchain-Transaktionen eine Bestätigungsverfolgung.

**Kernkonzepte:**

- **Ablauf des Blockhash**: Ablauf des Blockhash: Transaktions-Blockhashes bleiben
  für 150 slots gültig (etwa 30 Sekunden bei 200 ms slot-Zeit). Die tatsächliche
  Ablaufzeit kann je nach Geschwindigkeit der Blockproduktion variieren. Nutzen
  Sie lastValidBlockHeight, um zu bestimmen, wann ein Blockhash abgelaufen ist.
- **Idempotenz**: Dieselbe signierte Transaktion erzeugt immer dieselbe
  Signatur – ein erneutes Senden ist sicher
- **Exponentielles Backoff**: Vermeiden Sie es, das Netzwerk mit schnellen
  Wiederholungen zu überlasten

```typescript
import {
  createSolanaRpc,
  createSolanaRpcSubscriptions,
  sendAndConfirmTransactionFactory,
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED
} from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);
const rpcSubscriptions = createSolanaRpcSubscriptions(process.env.RPC_WSS_URL!);

const sendAndConfirmTransaction = sendAndConfirmTransactionFactory({
  rpc,
  rpcSubscriptions
});

// Send with automatic confirmation tracking and block height monitoring
try {
  await sendAndConfirmTransaction(signedTransaction, {
    commitment: "confirmed",
    // Optional: abort after 75 seconds
    abortSignal: AbortSignal.timeout(75_000)
  });
} catch (e) {
  if (isSolanaError(e, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED)) {
    // Blockhash expired—rebuild transaction with fresh blockhash and retry
    rebuildAndRetryTransaction(); // implement your own logic for rebuilding and retrying the transaction
  }
  throw e;
}
```

Die `sendAndConfirmTransactionFactory` aus `@solana/kit` übernimmt das
Bestätigungs-Polling und die Verfolgung der Blockhöhe automatisch. Sie wirft
`SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED`, wenn der Blockhash der Transaktion
abläuft. Das signalisiert, dass Sie die Transaktion mit einem frischen Blockhash
neu aufbauen müssen.

## Fehlerbehandlung

Solana Kit stellt typisierte Fehler über `isSolanaError()` bereit. Verwenden
Sie spezifische Fehlercodes statt String-Abgleich:

```typescript
import {
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED,
  SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE,
  SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND,
  SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS
} from "@solana/kit";

function handlePaymentError(error: unknown): {
  message: string;
  retryable: boolean;
} {
  // Blockhash expired—rebuild and retry
  if (
    isSolanaError(error, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED) ||
    isSolanaError(error, SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND)
  ) {
    return { message: "Transaction expired—rebuilding", retryable: true };
  }

  // Insufficient SOL for fees
  if (
    isSolanaError(
      error,
      SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE
    )
  ) {
    return { message: "Not enough SOL for fees", retryable: false };
  }

  // Insufficient token balance
  if (
    isSolanaError(error, SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS)
  ) {
    return { message: "Insufficient balance", retryable: false };
  }

  // Unknown error
  console.error("Payment error:", error);
  return { message: "Payment failed—please retry", retryable: true };
}
```

**Häufige Fehlercodes:**

| Fehlercode                   | Ursache                 | Behebung                                                                                                 |
| ---------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------- |
| `BLOCK_HEIGHT_EXCEEDED`      | Blockhash abgelaufen     | Mit frischem Blockhash neu aufbauen                                                                             |
| `BLOCKHASH_NOT_FOUND`        | Blockhash nicht gefunden   | Mit frischem Blockhash neu aufbauen                                                                             |
| `INSUFFICIENT_FUNDS_FOR_FEE` | Nicht genug SOL        | Fee Payer aufladen oder [Fee Abstraction](/docs/payments/send-payments/payment-processing/fee-abstraction) nutzen |
| `INSUFFICIENT_FUNDS`         | Nicht genug Token     | Nutzer benötigt ein höheres Guthaben                                                                                  |
| `ACCOUNT_NOT_FOUND`          | token account fehlt | ATA in der Transaktion erstellen                                                                                |

## Gasless-Transaktionen

Nutzer erwarten, in Stablecoins zu bezahlen, statt SOL für Netzwerk-Fees zu
beschaffen. Gasless-Transaktionen lösen dieses Problem – ähnlich wie Venmo-Nutzer
nicht über ACH-Fees nachdenken. Die vollständige Implementierung finden Sie unter
[Fee Abstraction](/docs/payments/send-payments/payment-processing/fee-abstraction).
