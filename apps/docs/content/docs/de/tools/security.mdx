## Schlüsselverwaltung

- **Geben Sie private Schlüssel niemals im Frontend-Code preis.** Nutzen Sie Backend-Signierung, Hardware-Wallets, Multisignatur-Wallets oder Key-Management-Dienste.
- **Trennen Sie Hot und Cold Wallets.** Die Hot Wallet dient dem laufenden Betrieb, die Cold Wallet der Treasury.
- **Sichern Sie alle Produktionsschlüssel.** Speichern Sie verschlüsselte Backups an mehreren sicheren Orten. Der Verlust eines Schlüssels bedeutet den dauerhaften Verlust des Zugriffs.
- **Verwenden Sie unterschiedliche Schlüssel für Devnet und Mainnet.** Ihre Devnet-Schlüssel sollten nicht Ihre Mainnet-Schlüssel sein. Nutzen Sie eine umgebungsbasierte Konfiguration, damit für jedes Netzwerk die richtigen Schlüssel geladen werden.

## Signing-Infrastruktur

Für die Signierung im Produktions-Backend verwenden Sie [Keychain](/docs/tools/keychain) – eine einheitliche Signing-Bibliothek, die mehrere Key-Management-Backends über eine einzige
Schnittstelle abstrahiert: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP,
Para, Dfns, Crossmint, Openfort und Utila. So können Sie lokal mit
In-Memory-Schlüsseln entwickeln und anschließend auf produktionsreife Backends umsteigen, ohne den
Anwendungscode zu ändern.

Sie sind unsicher, welches Backend passt? Siehe
[Auswahl eines Backends](/docs/tools/keychain/choosing-a-backend). Keychain ist
sowohl für [Rust](https://crates.io/crates/solana-keychain) als auch für
[TypeScript](https://www.npmjs.com/package/@solana/keychain) verfügbar.

## RPC-Sicherheit

Behandeln Sie RPC-Endpunkte wie API-Schlüssel – legen Sie sie nicht im Frontend-Code offen, wo sie
extrahiert und missbraucht werden können. Verwenden Sie einen Backend-Proxy oder Umgebungsvariablen, die
nicht in den Client-Code gebündelt werden.

- [QuickNode: Best Practices zur Endpunktsicherheit](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Schützen Sie Ihre Solana-API-Schlüssel – Best Practices zur Sicherheit](https://www.helius.dev/docs/rpc/protect-your-keys)

## Monitoring

Verfolgen Sie in der Produktion diese Metriken:

| Metrik                   | Grund                    |
| ------------------------ | ---------------------- |
| Erfolgsquote von Transaktionen | Probleme frühzeitig erkennen    |
| Bestätigungslatenz     | Netzwerkzustand überwachen |
| Ausgaben für priority fees       | Kostenkontrolle        |
| RPC-Fehlerrate           | Zustand des Anbieters        |

Richten Sie Benachrichtigungen ein für:

- Überweisungen aus der Treasury oberhalb eines Schwellenwerts
- Sprunghafte Anstiege der Quote fehlgeschlagener Transaktionen
- Ungewöhnliche Empfängermuster
- Steigende RPC-Fehlerraten

Für Echtzeit-Transaktionsüberwachung im großen Maßstab lesen Sie unseren
[Indexing-Leitfaden](/docs/payments/accept-payments/indexing).

## Adressen verifizieren

Jeder Token und jedes Programm hat im Mainnet genau eine korrekte Adresse. Gefälschte
Tokens, die USDC oder andere Stablecoins imitieren, sind weit verbreitet – sie haben denselben Namen
und dasselbe Symbol, aber einen anderen Mint. Ihre Anwendung sollte die Mint-Adressen (je nach Ihren Anforderungen)
fest codieren oder per Allowlist festlegen und sie niemals dynamisch
aus nicht vertrauenswürdigen Quellen akzeptieren.

**Umgebungsbasierte Konfiguration:** Devnet und Mainnet verwenden oft völlig
unterschiedliche Token-Mints. Richten Sie Ihre Anwendungskonfiguration so ein, dass pro Umgebung die korrekten
Adressen geladen werden – codieren Sie keine Mainnet-Adressen fest, um dann zu vergessen, sie
beim Testen auszutauschen, oder schlimmer noch, Devnet-Adressen in die Produktion auszuliefern.

Einige gängige Stablecoin-Mints sind:

| Token | Emittent | Mint-Adresse                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Auch Programmadressen sind wichtig. Das Senden von Anweisungen an das falsche Programm
schlägt fehl – oder führt schlimmstenfalls zu einem unwiderruflichen Verlust von Geldern. Die Adressen für das Token Program
lauten:

| Programm            | Adresse                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Eine Allowlist mit den richtigen Adressen schützt vor gefälschten Tokens, aber
nicht davor, an die falsche _Art_ von Konten zu senden. Eine Empfängeradresse
kann eine Wallet, ein token account, ein Mint oder ein Programm sein, und jede Art erfordert
eine andere Behandlung. Native SOL, die an etwas anderes als eine Wallet gesendet werden, verlassen die
Kontrolle des Absenders – bei einem Mint oder Programm sind sie endgültig verloren, bei einem token account nur vom
Eigentümer des token account wiederherstellbar – und keine fehlgeschlagene Transaktion warnt den Nutzer.

<Callout type="warn" title="Empfänger vor dem Senden validieren">
  Klassifizieren Sie jede Empfängeradresse, bevor Sie eine Überweisung signieren. Siehe [Adresse
  verifizieren](/docs/payments/send-payments/verify-address) für den vollständigen Entscheidungsbaum
  und Referenzcode, der Wallets, token accounts, Mints und
  Programme unterscheidet.
</Callout>
