## Key-Management

- **Gib Private Keys niemals im Frontend-Code preis.** Nutze Backend-Signierung, Hardware-Wallets, Multisignatur-Wallets oder Key-Management-Dienste.
- **Trenne Hot Wallets und Cold Wallets.** Die Hot Wallet dient dem laufenden Betrieb, die Cold Wallet der Treasury.
- **Sichere alle Produktions-Keys.** Speichere verschlüsselte Backups an mehreren sicheren Orten. Der Verlust eines Keys bedeutet den dauerhaften Verlust des Zugriffs.
- **Verwende unterschiedliche Keys für Devnet und Mainnet.** Deine Devnet-Keys sollten nicht deine Mainnet-Keys sein. Nutze eine umgebungsbasierte Konfiguration, damit für jedes Netzwerk die richtigen Keys geladen werden.

## Signierinfrastruktur

Für das Signieren im Produktiv-Backend verwende [Keychain](/docs/tools/keychain) – eine einheitliche Signierbibliothek, die mehrere Key-Management-Backends über eine einzige
Schnittstelle abstrahiert: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP,
Para, Dfns, Crossmint, Openfort und Utila. So kannst du lokal mit
In-Memory-Keys entwickeln und anschließend auf produktionstaugliche Backends umstellen, ohne
den Anwendungscode zu ändern.

Du weißt nicht, welches Backend passt? Siehe
[Ein Backend auswählen](/docs/tools/keychain/choosing-a-backend). Keychain ist
sowohl für [Rust](https://crates.io/crates/solana-keychain) als auch für
[TypeScript](https://www.npmjs.com/package/@solana/keychain) verfügbar.

## RPC-Sicherheit

Behandle RPC-Endpunkte wie API-Keys – gib sie nicht im Frontend-Code preis, wo sie
ausgelesen und missbraucht werden können. Verwende einen Backend-Proxy oder Umgebungsvariablen, die
nicht in den Client-Code eingebunden werden.

- [QuickNode: Best Practices für die Endpunktsicherheit](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Schütze deine Solana-API-Keys: Best Practices für die Sicherheit](https://www.helius.dev/docs/rpc/protect-your-keys)

## Monitoring

Überwache in der Produktion diese Metriken:

| Metrik                   | Warum                    |
| ------------------------ | ---------------------- |
| Erfolgsrate von Transaktionen | Probleme frühzeitig erkennen    |
| Bestätigungslatenz     | Netzwerkzustand überwachen |
| Ausgaben für priority fee       | Kostenkontrolle        |
| RPC-Fehlerrate           | Zustand des Anbieters        |

Richte Benachrichtigungen ein für:

- Überweisungen aus der Treasury oberhalb eines Schwellenwerts
- Sprünge bei der Rate fehlgeschlagener Transaktionen
- Ungewöhnliche Empfängermuster
- Anstieg der RPC-Fehlerrate

Für Echtzeit-Transaktionsüberwachung im großen Maßstab siehe unseren
[Indexing-Leitfaden](/docs/payments/accept-payments/indexing).

## Adressen verifizieren

Jeder Token und jedes Programm hat im Mainnet genau eine korrekte Adresse. Gefälschte
Tokens, die USDC oder andere Stablecoins imitieren, sind häufig – sie haben denselben Namen
und dasselbe Symbol, aber einen anderen Mint. Deine Anwendung sollte die Mint-Adressen
(je nach Anforderungen) fest codieren oder per Allowlist festlegen und niemals dynamisch
aus nicht vertrauenswürdigen Quellen akzeptieren.

**Umgebungsbasierte Konfiguration:** Devnet und Mainnet verwenden oft völlig
unterschiedliche Token-Mints. Richte die Konfiguration deiner Anwendung so ein, dass pro Umgebung die korrekten
Adressen geladen werden – codiere Mainnet-Adressen nicht fest, um sie dann beim Testen zu vergessen
auszutauschen, oder – schlimmer noch – Devnet-Adressen in die Produktion auszuliefern.

Einige gängige Stablecoin-Mints sind:

| Token | Emittent | Mint-Adresse                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Auch Programmadressen sind wichtig. Das Senden von Anweisungen an das falsche Programm schlägt
fehl – oder führt schlimmstenfalls zu einem unwiderruflichen Verlust von Geldern. Die Adressen des Token Program
lauten:

| Programm            | Adresse                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Das Allowlisting der richtigen Adressen schützt vor gefälschten Tokens, aber es
schützt nicht davor, an die falsche _Art_ von Konten zu senden. Eine Empfängeradresse
kann eine Wallet, ein token account, ein Mint oder ein Programm sein, und jede erfordert
eine andere Behandlung. Natives SOL, das an etwas anderes als eine Wallet gesendet wird, entzieht sich der
Kontrolle des Absenders – bei einem Mint oder Programm ist es endgültig verloren, bei einem token account
nur vom Eigentümer dieses token account wiederherstellbar – und keine fehlgeschlagene Transaktion warnt den Nutzer.

<Callout type="warn" title="Empfänger vor dem Senden validieren">
  Klassifiziere jede Empfängeradresse, bevor du eine Überweisung signierst. Siehe [Adresse
  verifizieren](/docs/payments/send-payments/verify-address) für den vollständigen Entscheidungsbaum
  und Referenzcode, der Wallets, token accounts, Mints und
  Programme unterscheidet.
</Callout>
