[Machine Payments Protocol (MPP)](https://mpp.dev/) soveltaa HTTP-todennuksen periaatteita maksamiseen. Palvelin esittää maksamattomalle pyynnölle haasteen, asiakas palauttaa maksutunnisteen (payment credential) ja palvelin palauttaa kuitin hyväksyttyään maksun.

MPP erottaa toisistaan kolme asiaa:

- **Intentio** (intent) kuvaa kaupallisen vuorovaikutuksen, esimerkiksi kertaluonteisen `charge`-veloituksen tai mitatun `session`-istunnon.
- **Maksutapa** kuvaa, miten arvo siirtyy. Solana-maksutapa tukee veloituksissa natiivia SOL-valuuttaa ja SPL-tokeneita.
- HTTP-**siirtokerros** kuljettaa haasteet, tunnistetiedot, kuitit ja virheet.

MPP julkaistaan Internet-Draft-luonnosten joukkona. Pidä [nykyisiä määrityksiä](https://paymentauth.org/) luotettavana lähteenä ja varaudu siihen, että yksityiskohdat muuttuvat luonnosten ollessa vielä työn alla.

## HTTP-vaihto

MPP käyttää tavallisia HTTP-todennuskenttiä protokollakohtaisten maksuotsikoiden sijaan:

| Viesti                 | HTTP-esitys                                         |
| ----------------------- | ----------------------------------------------------------- |
| Maksuhaaste       | `402 Payment Required` ja `WWW-Authenticate: Payment ...` |
| Maksutunniste      | Uudelleen lähetetty pyyntö, jossa on `Authorization: Payment ...`           |
| Onnistunut kuitti      | Resurssin vastaus, jossa on `Payment-Receipt: ...`               |
| Virheelliset maksutiedot | Problem Details -runko, jossa käytetään `application/problem+json`-muotoa       |

```mermaid title="MPP Charge Flow"
sequenceDiagram
    participant Client
    participant Server
    participant Solana
    Client->>Server: GET /report
    Server-->>Client: 402 + WWW-Authenticate: Payment
    Note over Client: Validate terms and authorize payment
    Client->>Server: GET /report + Authorization: Payment
    Server->>Server: Verify challenge binding and transaction
    Server->>Solana: Broadcast signed transfer
    Solana-->>Server: Confirmed transaction
    Server-->>Client: 200 + report + Payment-Receipt
```

Haaste sisältää palvelimen luoman tunnisteen, realmin, maksutavan, intention, koodatun maksupyynnön ja vanhenemisajan. Tunniste toistaa haasteen ja lisää siihen maksutapakohtaisen maksutodisteen. Palvelimen on varmennettava molemmat osat; pätevä siirto, joka kuuluu toiseen haasteeseen, ei saa avata resurssia.

## Kertaluonteiset Solana-veloitukset

Solanan `charge`-intentio tukee kahta tunnistetyyppiä:

- **Pull-tila** käyttää allekirjoitettua transaktiota. Asiakas allekirjoittaa siirron ja lähettää transaktion palvelimelle. Palvelin varmentaa sen, lisää tarvittaessa maksajan (fee payer) allekirjoituksen, lähettää transaktion verkkoon, vahvistaa sen ja palauttaa transaktion allekirjoituksen kuitissaan.
- **Push-tila** käyttää transaktion allekirjoitusta. Asiakas lähettää transaktion ensin verkkoon ja lähettää sitten vahvistetun allekirjoituksen palvelimelle. Palvelin hakee ja varmentaa transaktion ennen resurssin palauttamista.

Pull-tila mahdollistaa palvelimen sponsoroimat transaktiomaksut ja palvelinpuolen uudelleenyrityslogiikan. Push-tila on hyödyllinen, kun lompakko edellyttää, että asiakas lähettää transaktionsa itse, mutta se ei voi käyttää palvelimen maksusponsorointia.

Normatiiviset kentät ja varmennussäännöt löytyvät [Solana-veloitusmäärityksestä](https://paymentauth.org/draft-solana-charge-00.html).

## MPP-veloituksen lisääminen Express-rajapintaan

Solana Pay Kit tarjoaa ajantasaisen TypeScript-integraation MPP:lle ja x402:lle. Asenna se Expressin kanssa:

```bash
pnpm add @solana/pay-kit @solana/kit@^6.9.0 express
pnpm add --save-dev @types/express tsx
```

Tämä yksinkertaisin esimerkki käyttää isännöityä Surfpool-hiekkalaatikkoa ja paketin julkista demovastaanottajaa. Se on tarkoitettu vain paikalliseen kehitykseen:

```ts filename=server.ts
import express from "express";
import { createPayKit, usd } from "@solana/pay-kit";

const pay = await createPayKit({
  accept: ["mpp"],
  rpcUrl: "https://402.surfnet.dev:8899"
});

const app = express();

app.get("/report", pay.express(usd("0.01")), (_req, res) => {
  res.json({ report: "Paid report" });
});

app.listen(4567, () => {
  console.log("Paid API listening on http://127.0.0.1:4567");
});
```

Suorita se ja vertaa maksamatonta pyyntöä maksun huomioivaan pyyntöön:

```bash
pnpm tsx server.ts
curl -i http://127.0.0.1:4567/report
pay --sandbox curl http://127.0.0.1:4567/report
```

Reitinkäsittelijä suoritetaan vasta, kun välikerros (middleware) on hyväksynyt maksun.

<Callout type="warn" title="Korvaa kaikki hiekkalaatikon oletukset tuotannossa">
  Määritä eksplisiittinen verkko, kauppiaan vastaanottaja, oma RPC, vakaa haasteen sitomiseen käytettävä salaisuus, tuotantoallekirjoittaja ja pysyvä toistohyökkäysten estotallennus. Älä koskaan ohjaa oikeita maksuja paketin demoallekirjoittajalle.
</Callout>

## Mitatut istunnot

Käytä Solanan MPP-`session`-istuntoa, kun asiakas tekee paljon pieniä, toisiinsa liittyviä maksuja. Istunto avaa ketjunsisäisen maksukanavan, jolla on enimmäistalletus, ja käyttää sen jälkeen kumulatiivisia allekirjoitettuja vouchereita käytön kasvaessa. Palvelin voi varmentaa voucherit ketjun ulkopuolella ja selvittää korkeimman hyväksytyn summan myöhemmin.

Tämä sopii tokeniperusteiseen inferenssiin, tavuperusteisiin latauksiin, reaaliaikaiseen dataan ja toistuviin työkalukutsuihin. Se ei ole sama asia kuin erillisen ketjunsisäisen maksun lähettäminen jokaisesta tapahtumasta.

```mermaid title="MPP Session Lifecycle"
sequenceDiagram
    participant Client
    participant Server
    participant Solana
    Client->>Server: Request + session support
    Server-->>Client: 402 + capped session challenge
    Client->>Solana: Open channel and deposit maximum
    Solana-->>Server: Channel confirmed
    loop Metered usage
        Client->>Server: Request + increasing signed voucher
        Server-->>Client: Resource + receipt
    end
    Server->>Solana: Settle highest accepted voucher
    Solana-->>Client: Return unused deposit when closed
```

Kutsu istuntoa nimellä **istuntomaksu**, **maksukanava** tai **ylärajattu toistuva valtuutus**. Kutsu sitä suoratoistomaksuksi vain, jos palvelu ja maksusopimus todella mittaavat käytön virtaa.

## Tuotantovarmennus

Jokaisen Solana-veloituksen osalta palvelimen on varmennettava vähintään seuraavat asiat:

- Haaste on aito, voimassa, sidottu tähän pyyntöön ja tarkoitettu tälle realmille.
- Transaktio käyttää odotettua verkkoa, omaisuuserää tai mintiä, vastaanottajaa, summaa ja token programia.
- Kaikki maksajan (fee payer) tai associated token account -tilin ohjeet on sallittu nimenomaisesti, eivätkä ne voi tyhjentää palvelimen allekirjoittajaa.
- Transaktio onnistui vaaditulla vahvistustasolla (commitment level).
- Transaktion allekirjoitusta ei ole jo käytetty.
- Toistotarkistus ja käyttö merkitseminen ovat atomisia kaikkien palvelininstanssien kesken.

Tallenna istuntojen osalta myös kanavan tila, hyväksytty kumulatiivinen summa ja selvityksen vesileima (settlement watermark) jaettuun tallennustilaan. Dokumentoi, miten asiakkaat saavat käyttämättömät varat takaisin, jos palvelin ei ole käytettävissä.
