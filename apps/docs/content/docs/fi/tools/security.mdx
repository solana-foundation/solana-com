## Avainten hallinta

- **Älä koskaan paljasta yksityisiä avaimia frontend-koodissa.** Käytä backend-allekirjoitusta, laitelompakoita, monen allekirjoittajan lompakoita tai avaintenhallintapalveluita.
- **Erota kuuma ja kylmä lompakko toisistaan.** Käytä kuumaa lompakkoa operatiivisiin toimiin ja kylmää lompakkoa omaisuuden (treasury) säilytykseen.
- **Varmuuskopioi kaikki tuotantoavaimet.** Säilytä salatut varmuuskopiot useissa turvallisissa paikoissa. Avaimen menettäminen tarkoittaa pääsyn pysyvää menetystä.
- **Käytä eri avaimia devnetissä ja mainnetissä.** Devnet-avaimesi eivät saa olla mainnet-avaimiasi. Käytä ympäristökohtaista konfiguraatiota varmistaaksesi, että kullekin verkolle ladataan oikeat avaimet.

## Allekirjoitusinfrastruktuuri

Käytä tuotantoympäristön backend-allekirjoitukseen [Keychainia](/docs/tools/keychain) – yhtenäistä allekirjoituskirjastoa, joka abstrahoi useita avaintenhallinnan taustajärjestelmiä yhden rajapinnan taakse: Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP, Para, Dfns, Crossmint, Openfort ja Utila. Näin voit kehittää paikallisesti muistinvaraisilla avaimilla ja siirtyä sitten tuotantotason taustajärjestelmiin muuttamatta sovelluskoodia.

Etkö ole varma, mikä taustajärjestelmä sopii sinulle? Katso [Taustajärjestelmän valinta](/docs/tools/keychain/choosing-a-backend). Keychain on saatavilla sekä [Rustille](https://crates.io/crates/solana-keychain) että [TypeScriptille](https://www.npmjs.com/package/@solana/keychain).

## RPC-tietoturva

Kohtele RPC-päätepisteitä kuten API-avaimia – älä paljasta niitä frontend-koodissa, josta ne voidaan poimia ja joita voidaan käyttää väärin. Käytä backend-välipalvelinta (proxy) tai ympäristömuuttujia, joita ei paketoida asiakaskoodiin.

- [QuickNode: Endpoint Security Best Practices](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Protect Your Solana API Keys: Security Best Practices](https://www.helius.dev/docs/rpc/protect-your-keys)

## Valvonta

Seuraa tuotannossa näitä mittareita:

| Mittari                   | Miksi                    |
| ------------------------ | ---------------------- |
| Tapahtumien onnistumisprosentti | Ongelmien havaitseminen ajoissa    |
| Vahvistuksen viive     | Verkon tilan seuranta |
| Prioriteettimaksujen kulut       | Kustannusten hallinta        |
| RPC-virheiden määrä           | Palveluntarjoajan tila        |

Määritä hälytykset seuraaville:

- Kynnysarvon ylittävät siirrot omaisuudesta (treasury)
- Epäonnistuneiden tapahtumien määrän äkilliset piikit
- Epätavalliset vastaanottajakuviot
- RPC-virheiden määrän kasvu

Jos tarvitset laajamittaista reaaliaikaista tapahtumavalvontaa, katso [indeksointiopas](/docs/payments/accept-payments/indexing).

## Tarkista osoitteet

Jokaisella tokenilla ja ohjelmalla on mainnetissä täsmälleen yksi oikea osoite. Väärennetyt tokenit, jotka jäljittelevät USDC:tä tai muita stablecoineja, ovat yleisiä – niillä on sama nimi ja symboli, mutta eri mint. Sovelluksesi tulisi kovakoodata mint-osoitteet tai käyttää sallittujen osoitteiden luetteloa (vaatimustesi mukaan), eikä koskaan hyväksyä niitä dynaamisesti epäluotettavista lähteistä.

**Ympäristökohtainen konfiguraatio:** Devnet ja Mainnet käyttävät usein täysin eri token-mintejä. Määritä sovelluksesi konfiguraatio lataamaan oikeat osoitteet kullekin ympäristölle – älä kovakoodaa mainnet-osoitteita ja unohda vaihtaa niitä testauksen ajaksi, tai mikä pahempaa, julkaise devnet-osoitteita tuotantoon.

Joitakin yleisiä stablecoin-minttejä ovat:

| Token | Liikkeeseenlaskija | Mint-osoite                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Myös ohjelmien osoitteilla on väliä. Ohjeiden lähettäminen väärälle ohjelmalle epäonnistuu – tai mikä pahempaa, johtaa varojen peruuttamattomaan menetykseen. Token Program -ohjelman osoitteet ovat:

| Ohjelma            | Osoite                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Oikeiden osoitteiden sallittujen luettelo suojaa väärennetyiltä tokeneilta, mutta ei suojaa lähettämiseltä väärän _tyyppiselle_ tilille. Vastaanottajan osoite voi olla lompakko, token account, mint tai ohjelma, ja kukin vaatii erilaista käsittelyä. Muuhun kuin lompakkoon lähetetty natiivi SOL poistuu lähettäjän hallinnasta – mintille tai ohjelmalle lähetettynä se menetetään lopullisesti, ja token accountille lähetettynä sen voi palauttaa vain tilin omistaja – eikä mikään epäonnistunut tapahtuma varoita käyttäjää.

<Callout type="warn" title="Tarkista vastaanottajat ennen lähettämistä">
  Luokittele jokainen vastaanottajan osoite ennen siirron allekirjoittamista. Katso [osoitteen tarkistus](/docs/payments/send-payments/verify-address), jossa on täydellinen päätöspuu ja viitekoodi, jonka avulla erotetaan toisistaan lompakot, token accountit, mintit ja ohjelmat.
</Callout>
