Tämä opas on tarkoitettu lompakopalveluntarjoajille ja kehittäjille, jotka
haluavat integroida uusia avaintenhallintaratkaisuja
`solana-keychain`-kirjastoon. Lisäämällä oman allekirjoittajatoteutuksesi
mahdollistat kehittäjille palvelusi käytön turvalliseen Solana-transaktioiden
allekirjoitukseen yhtenäisen rajapinnan kautta.

Keychain pitää Rust-, TypeScript-, Python- ja Go-toteutuksensa tasavertaisina.
PR:t, jotka sisältävät kaikki neljä, ovat erittäin toivottuja. Jos voit tehdä vain
yhden, se käy, mutta odota, että muutkin vaaditaan ennen kuin signer julkaistaan
versiossa.

_Käytätkö Claude Codea? Repositorion
[`add-signer-ci`-skill](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)
määrittää CI-työnkulut forkki-PR:n kautta lisätylle uudelle signerille._

## Arkkitehtuurin yleiskatsaus

Kirjasto käyttää trait-pohjaista arkkitehtuuria, joka on määritelty tiedostossa `src/traits.rs`. Jokainen
signer toteuttaa `SolanaSigner`-perustraitin (`pubkey`, `sign_message`,
`is_available`) sekä täsmälleen yhden palveluntarjoajan rakennetta vastaavan capability-traitin:

- `TransactionSigner` (`sign_transaction`): palveluntarjoaja allekirjoittaa kutsujan
  tavut ja kutsuja lähettää ne verkkoon. Useimmat taustajärjestelmät.
- `ModifyingSigner` (`modify_and_sign_transaction`): palveluntarjoaja muokkaa
  transaktiota ja allekirjoittaa sen lähettämättä sitä verkkoon.
- `SendingSigner` (`sign_and_send_transaction`): palveluntarjoaja allekirjoittaa ja
  lähettää transaktion verkkoon palvelinpuolella.

Kirjasto tarjoaa myös yhtenäisen `Signer`-enumin, joka kietoo sisäänsä kaikki
toteutukset ja mahdollistaa allekirjoitustaustajärjestelmän valinnan ajon aikana. Se toteuttaa
vain perustraitin; capability-ominaisuuksiin päästään käsiksi funktioilla `as_transaction_signer()`,
`as_modifying_signer()` ja `as_sending_signer()`.

## Pikaintegroinnin tarkistuslista

- Luo allekirjoittajamoduulisi toteutuksineen
- Toteuta `SolanaSigner`-perustraiti (`pubkey`, `sign_message`,
  `is_available`) sekä yksi palveluntarjoajasi rakennetta vastaava capability-traiti
  (yleensä `TransactionSigner`)
- Lisää feature flag tiedostoon `Cargo.toml`, mukaan lukien sisäinen `_remote`-merkki,
  jos signerisi käyttää reqwestiä
- Päivitä `Signer`-enum tiedostossa `src/lib.rs` (variantti, `dispatch_signer!`-haara ja
  haara capability-accessorissa, joka vastaa rakennettasi)
- Pakota HTTPS ja konfiguroi HTTP-asiakkaiden aikakatkaisut
- Allekirjoita viestin tavut ja tarkista palautettu allekirjoitus ennen sen liittämistä
- Lisää kattavat yksikkötestit (wiremock-pohjaiset, omassa moduulissasi)
- Lisää integraatiotestitiedosto ja päivitä `.env.example`
- Lisää TypeScript-, Python- ja Go-toteutukset
- Päivitä dokumentaatio
- CI-työnkulun päivitykset (sovi ylläpitäjien kanssa, katso
  [CI-työnkulun päivitykset](#ci-workflow-updates-fork-prs))
- Lähetä PR

## Vaihe 2: Määritä allekirjoittaja-struct

Määritä `src/your_service/mod.rs`-tiedostossa allekirjoittaja-struct:

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,
}

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## Vaihe 3: Toteuta konstruktori ja apumetodit

Etäallekirjoittajien **on pakko** pakottaa HTTPS ja konfiguroida
HTTP-aikakatkaisut. Käytä jaettua `HttpClientConfig`-structia
aikakatkaisuasetusten hallintaan.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## Vaihe 4: Toteuta Signer-traitit

`SolanaSigner`-perustraitilla on 2 asynkronista metodia (`sign_message`,
`is_available`) sekä `pubkey()`. Transaktioiden allekirjoitus kuuluu capability-traitiin;
useimmat palveluntarjoajat toteuttavat `TransactionSigner`-traitin, jonka `sign_transaction` palauttaa
`SignTransactionResult`-arvon (tagged enum, joka merkitsee transaktion täysin tai
osittain allekirjoitetuksi).

Allekirjoita viestin tavut, älä koskaan koko wire-transaktiota, ja tarkista
palveluntarjoajan allekirjoitus niitä vasten ennen sen liittämistä. Käytä jaettuja
`TransactionUtil`-apufunktioita allekirjoitukseen ja serialisointiin.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

Jos palveluntarjoajasi muokkaa transaktiota ennen allekirjoitusta, toteuta sen sijaan
`ModifyingSigner` ja korvaa kutsujan transaktio kokonaan
palveluntarjoajan tavuilla. Jos se lähettää transaktion verkkoon palvelinpuolella, toteuta `SendingSigner`
ja jätä kutsujan transaktio koskematta. Älä koskaan toteuta capabilityä, jota
palveluntarjoajasi ei pysty tarjoamaan.

## Vaihe 6: Lisää ominaisuuslippu

Päivitä `Cargo.toml` lisätäksesi signerisi valinnaiseksi featureksi. Etätaustajärjestelmät
sisältävät sisäisen `_remote`-merkin, joka ohjaa `From<reqwest::Error>`-
toteutusta tiedostossa `src/error.rs`; ilman sitä `?` reqwest-kutsuissa ei käänny, kun vain
sinun featurasi on käytössä.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## Vaihe 7: Päivitä allekirjoittaja-enum

Lisää signerisi tiedostoon `src/lib.rs`. Perus-`SolanaSigner`-toteutus välittää kutsut
`dispatch_signer!`-makron kautta, joten lisää sinne yksi haara. Capability-käyttö sijaitsee
accessoreissa `as_transaction_signer()`, `as_modifying_signer()` ja `as_sending_signer()`:
lisää `Some(s)`-haara sille, joka vastaa capability-traitiasi (ja
lähettävälle tai muokkaavalle taustajärjestelmälle `None`-haara funktioon `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## Vaihe 8: Lisää kattavat testit

Lisää testit moduuliisi (`src/your_service/mod.rs`-tiedoston loppuun):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

Kata myös allekirjoituksen todennuksen epäonnistuminen: mockatun vastauksen, jonka allekirjoitus
ei täsmää, on palautettava virhe.

## Vaihe 9: Lisää integraatiotestit

Luo `rust/src/tests/test_<name>_integration.rs`. Integraatiotestit ajetaan
oikeaa palvelun API:a vasten (ei wiremockia), ja ne on rajattu
`integration-tests`-featuren taakse. Jokainen tiedosto tarvitsee:

- `pub const` -määrittelyt ympäristömuuttujien nimille
- `get_signer()`-apufunktion, joka lukee ympäristömuuttujat `dotenvy`:n avulla
- Kolme testifunktiota: `test_<name>_sign_message`,
  `test_<name>_sign_transaction` ja `test_<name>_is_available`
- Feature-rajaukset: `#[cfg(feature = "your_service")]` moduulissa ja
  `#[cfg(feature = "integration-tests")]` jokaisessa testissä

Katso täydellinen esimerkki tiedostosta `rust/src/tests/test_para_integration.rs` ja
esittele moduulisi tiedostossa `rust/src/tests/mod.rs`:

```rust
pub mod test_your_service_integration;
```

## CI-työnkulun päivitykset (forkki-PR:t)

CI on kaksivaiheinen prosessi. Sovi ylläpitäjien kanssa `main`-haaran valmistelusta, ennen kuin
PR:äsi voidaan testata: he päivittävät `fork-external-live-manual.yml`-tiedoston, lisäävät ympäristömuuttujat
tiedostoon `ci.yml` ja määrittävät GitHub Secretsit.

PR:säsi on sisällettävä nämä vaiheen 2 muutokset signer-koodisi rinnalla:

- **`ci.yml`**: lisää Rust-featuresi `backend`-matriisiin (ennen `all`-arvoa) ja
  integraatiotestifunktiosi `test`-matriisiin
- **`typescript-ci.yml`**: lisää pakettisi yksikkö- ja integraatiotestimatriiseihin
  ja lisää ympäristömuuttujat integraatiotestivaiheeseen
- **`typescript-publish.yml`**: lisää pakettisi `PUBLISH_PACKAGES`-arvoon,
  GitHub Releasen `packages`-taulukkoon ja yhteenvetotaulukkoon
- **`python-ci.yml`**: lisää taustajärjestelmä `CI_SIGNER_*`-rajaukseen kohdassa
  `resolve-signers` ja integraatiomatriisiin
- **`go-ci.yml`**: lisää taustajärjestelmä `CI_SIGNER_*`-rajaukseen ja
  `moduleBySigner`-rakenteeseen

## TypeScript-allekirjoittaja

Jos lisäät myös TypeScript-allekirjoittajapaketin, luo se sijaintiin
`typescript/packages/your-signer/`. Keskeiset mallit:

- Factory-funktio `createYourSigner()` palauttaa
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>`; pidä
  signer-luokka sisäisenä ja exporttaa vain factory ja sen config-tyyppi
- Vie config-rajapinta (`YourSignerConfig`)
- Jos taustajärjestelmäsi ei voi allekirjoittaa viestejä, jätä `SolanaMessageSigner` pois ja älä tarjoa
  `signMessages`-metodia lainkaan: Kit luokittelee signerit metodin olemassaolon perusteella, joten
  virheen heittävä stub luokittelisi signerin väärin
- Pakota HTTPS `apiBaseUrl`-konfiguraatiokentissä funktiolla `assertHttpsUrl()` paketista
  `@solana/keychain-core`
- Tee etäkutsut funktiolla `fetchSignerJson()` paketista `@solana/keychain-core`,
  joka hoitaa virheiden mappauksen, vastausten puhdistuksen, uudelleenohjausten hylkäämisen ja
  oletusaikakatkaisun
- Puhdista kaikki muu etä-API:n virheteksti funktiolla `sanitizeRemoteErrorResponse()`
  paketista `@solana/keychain-core`
- Käytä `throwSignerError(SignerErrorCode.*, { cause, message })` moduulista
  `@solana/keychain-core`
- Huomioi `config?.abortSignal` jokaisessa allekirjoitusmetodissa ja välitä se
  funktioille `fetchSignerJson()` ja `signBatchStaggered()`
- Validoi `requestDelayMs` funktiolla `validateRequestDelayMs()` ja eräajo
  funktiolla `signBatchStaggered()`
- Lisää `@throws` JSDoc tehdas-funktioihin listaten virhekoodit
- Määritä `@solana/*`-paketit peer-riippuvuuksiksi versiosta `>=8.1.0`
- Yksikkötestit vitestillä ja mockatulla `fetch`illä; integraatiotestit funktiolla
  `runSignerIntegrationTest` paketista `@solana/keychain-test-utils`

### Lähettävät signerit

Jos palveluntarjoajasi muokkaa transaktiota tai lähettää sen verkkoon palvelinpuolella, sen
allekirjoitusta ei voi soveltaa kutsujan transaktioon, joten sen on oltava
`SolanaSendingSigner` eikä `SolanaTransactionSigner`:

- Toteuta `signAndSendTransactions()` äläkä tarjoa **yhtään** `signTransactions`-metodia
  (eikä `signMessages`-metodia, ellei taustajärjestelmä todella allekirjoita viestejä)
- Huomioi `config?.abortSignal`. Kun palveluntarjoaja on hyväksynyt luontipyynnön, raportoi
  kaikki virheet (myös keskeytys) arvolla `BROADCAST_UNCONFIRMED`, joka sisältää
  palveluntarjoajan transaktiotunnisteen, ja säilytä keskeytyksen syy `cause`-kentässä
- Lisää tyypitetty `createKeychainSigner`-overload, joka palauttaa lähettävän signer-tyyppisi
- Sulje taustajärjestelmäsi pois tyypistä `KeychainKitPluginConfig` tiedostossa

- Varmista yksikkötesteissä, että `isTransactionPartialSigner()` on false ja

## Python-signer

Luo moduuli polkuun `python/src/solana_keychain/your_signer/` (`__init__.py`
sekä `signer.py`). Keskeiset mallit:

- Periytä `SolanaSigner` paketista `solana_keychain.core` (`pubkey`-property,
  `async sign_message()`, `async is_available()`) sekä täsmälleen yksi capability-
  luokka: `TransactionSigner` (`async sign_transaction()`), `ModifyingSigner`
  (`async modify_and_sign_transaction()`) tai `SendingSigner`
  (`async sign_and_send_transaction()`)
- Exporttaa `async create_your_signer()` -factory, joka awaitaa `init()`-kutsun, kun
  taustajärjestelmä selvittää osoitteensa etänä; ennen initiä allekirjoitus nostaa
  virheen `SignerErrorCode.NOT_INITIALIZED`
- Exporttaa config-dataclass (`YourSignerConfig`), jossa salaisuudet on merkitty
  `field(repr=False)`
- Pakota HTTPS base-URL-kentissä funktiolla `assert_https_url()` ja ohjaa jokainen
  pyyntö funktion `fetch_signer_json()` kautta
- Tarkista palveluntarjoajan allekirjoitus ennen sen palauttamista; käytä
  funktiota `signed_message_bytes()` allekirjoituksen kattamille tavuille, älä koskaan käsin rakennettua
  versioetuliitettä
- Rekisteröi taustajärjestelmä `_BACKENDS`-rakenteeseen tiedostossa
  `python/src/solana_keychain/keychain.py`
- Jos taustajärjestelmä tarvitsee palveluntarjoajan SDK:n, suojaa import, nosta `ImportError`,
  jossa mainitaan `pip install 'solana-keychain[your-signer]'`, esittele lisäosa
  (extra) tiedostossa `python/pyproject.toml` äläkä koskaan tuo taustajärjestelmää
  ennakkoon paketin juuresta
- Yksikkötestit pytestillä: `respx` HTTP-taustajärjestelmille, stub-asiakkaat SDK-pohjaisille
  taustajärjestelmille sekä tarkistus, ettei mikään salaisuus näy heitettyjen
  virheiden `str()`- tai `repr()`-tulosteessa
- Lisää `make_your_signer()`-tehdasfunktio tiedostoon
  `python/tests/integration/test_live_signers.py` ja rekisteröi se kohtaan
  `_MESSAGE_CAPABLE` (tai `_TRANSACTION_ONLY`, jos taustajärjestelmällä ei ole
  `sign_message`-toimintoa)

## Go-allekirjoittaja

Jokainen Go-taustajärjestelmä on oma moduulinsa polussa `go/signers/yoursigner/`, ja sen moduulipolku on
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`. Katso
viitteeksi `go/signers/para/`. Keskeiset mallit:

- Toteuta `core.SolanaSigner` (`Pubkey()`, `SignMessage(ctx, message)`,
  `IsAvailable(ctx)`) sekä täsmälleen yksi ominaisuusrajapinta:
  `core.TransactionSigner`, `core.ModifyingSigner` tai `core.SendingSigner`.
  Ominaisuus tunnistetaan tyyppivarmistuksella (type assertion), joten taustajärjestelmällä, joka ei voi allekirjoittaa
  transaktiota, ei saa olla lainkaan `SignTransaction`-metodia
- Julkaise `Config`-struct ja `New`-konstruktori (`New(ctx, cfg)`, kun
  taustajärjestelmä selvittää osoitteensa etänä; sitä ennen palauta
  `core.NewNotInitializedError`)
- Rakenna HTTP-asiakkaat funktiolla `core.NewHTTPClient` tai `core.ResolveHTTPClient` ja
  validoi perus-URL-osoitteet funktiolla `core.NormalizeHTTPSBaseURL`
- Allekirjoita transaktiot funktiolla `core.SignTransactionWith`, joka allekirjoittaa viestin
  tavut ja liittää allekirjoituksen; varmenna palveluntarjoajan allekirjoitukset funktiolla
  `core.VerifySignature`
- Palauta virheet funktioilla `core.NewSignerError` / `core.WrapSignerError` ja vakailla
  koodeilla, kuten `core.CodeSigningFailed`
- Yksikkötestit `httptest`-paketilla; integraatiotestit tiedostossa `integration_test.go`
  `//go:build integration` -tagin takana

## Toteutusvinkkejä

### Virheenkäsittely

Käytä aina olemassa olevia `SignerError`-variantteja. Sekä `Display` että `Debug`
`SignerError`-tyypissä on häivytetty (redacted), joten pidä viestit yleisluontoisina äläkä koskaan sisällytä raakaa API-
vastausdataa. Älä koskaan käytä `.expect()`- tai `.unwrap()`-kutsuja epäluotettaviin API-vastauksiin:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### Tietoturvavaatimukset

Nämä eivät ole ehdotuksia: käyttäjät valitsevat taustajärjestelmän niiden perusteella. Jos
palveluntarjoajasi tekee jommankumman mahdottomaksi, kerro siitä PR:ssä ja repositorion
tiedostossa `docs/SECURITY_MODEL.md`.

- **Varmenna, mitä palveluntarjoaja allekirjoitti.** Laske viestin tavut paikallisesti ja
  varmenna palautettu allekirjoitus niitä vasten allekirjoittajasi vaatimassa
  kohdassa ennen sen liittämistä. Allekirjoitus, joka ei täsmää, on hylättävä, eikä sitä saa
  koskaan liittää.
- **Ilmoita, lähettääkö palveluntarjoaja transaktion verkkoon.** Jos se suorittaa transaktion palvelinpuolella,
  toteuta lähettävä (sending) muoto ja palauta allekirjoitus, joka yksilöi
  vahvistetun transaktion. Jos palveluntarjoajalla ei ole pelkkää allekirjoitusta tarjoavaa rajapintaa, tee
  taustajärjestelmästä vain lähettävä sen sijaan, että lähetät transaktion kutsujan tietämättä.
- **Älä koskaan jätä kutsujalle transaktiota, jota allekirjoitus ei kata.**
  Palveluntarjoaja, joka kirjoittaa transaktion uudelleen, allekirjoittaa omat tavunsa: jätä joko
  kutsujan transaktio koskemattomaksi (verkkoonlähetyksen hallinnoima tapaus) tai käytä
  muokkaavaa (modifying) muotoa ja korvaa se kokonaan palveluntarjoajan tavuilla.
- **Ilmoita verkkoonlähetyksen epävarmuus sellaisenaan.** Lähetyksen jälkeinen virhe on voinut silti
  mennä läpi. Nosta esiin `BROADCAST_UNCONFIRMED` yleisen virheen sijaan,
  liitä mukaan palveluntarjoajan transaktiotunniste aina kun sellainen on, ja lähetä
  viestistä johdettu idempotenssiavain jokaisen luontikutsun yhteydessä, jotta tavu tavulta
  identtinen uudelleenlähetys on turvallinen.
- **Älä koskaan allekirjoita ennen alustusta.** Käytä tyyppiä `Option<Pubkey>` (ei `Pubkey::default()`)
  julkiselle avaimelle ennen `init()`-kutsua ja palauta konfiguraatiovirhe, jos allekirjoitusta
  yritetään ensin.
- Älä koskaan kirjaa arkaluonteisia tietoja (yksityisiä avaimia, API-salaisuuksia, raakoja API-vastauksia) lokiin, ja
  käytä `Debug`-toteutusta, joka piilottaa arkaluonteiset kentät
- Pakota HTTPS (`https_only(true)`, rajattu ehdolla `#[cfg(not(test))]`
  wiremockia varten) ja määritä pyyntöjen ja yhteyden aikakatkaisut `HttpClientConfig`-konfiguraation kautta
  (oletukset: 30 s / 5 s)
- Nollaa avainmateriaalin välivaiheet käyttämällä `zeroize::Zeroizing<Vec<u8>>`

### Testaus mock-objekteilla

Käytä `wiremock` HTTP-rajapintojen mock-testaukseen. Tarkista vain virhetyyppi,
ei virheviestin tekstiä:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
