Anchor olayları, bir programın IDL'ine dahil edilen, tür tanımlı ve Borsh ile serileştirilmiş kayıtlardır.
İstemcilerin, insan tarafından okunabilir log
mesajlarını ayrıştırmadan program etkinliğini yorumlamasını sağlarlar.

Olaylar indeksleme ve bildirimler için kullanışlıdır, ancak program
durumu değildirler. Programın tekrar okuması gereken her değeri bir hesapta saklayın ve
olayları başarılı bir işlemden türetilen bir kayıt olarak değerlendirin.

## Bir olayı tanımlama ve yayınlama

Bir struct'a `#[event]` ekleyin ve durum değişikliği başarılı olduktan sonra `emit!` çağırın.

```rust title="lib.rs"
use anchor_lang::prelude::*;

#[program]
pub mod payments {
    use super::*;

    pub fn record_payment(ctx: Context<RecordPayment>, amount: u64) -> Result<()> {
        emit!(PaymentRecorded {
            authority: ctx.accounts.authority.key(),
            amount,
        });
        Ok(())
    }
}

#[derive(Accounts)]
pub struct RecordPayment<'info> {
    pub authority: Signer<'info>,
}

#[event]
pub struct PaymentRecorded {
    pub authority: Pubkey,
    pub amount: u64,
}
```

`emit!`, olay baytlarını Solana'nın `sol_log_data` syscall'ı ile yazar. İşlem
logları sonucu `Program data: <base64>` olarak gösterir. Kodlanmış değer,
olay ayırt edicisi (discriminator) ve ardından Borsh ile serileştirilmiş alanlarıyla başlar.

Olayları odaklı tutun. Büyük string'ler ve vektörler hesaplama (compute) tüketir, işlem
meta verilerini artırır ve log kesilmesinden etkilenme olasılığı daha yüksektir.

## Log ve CPI olayları arasında seçim yapma

Anchor iki yayınlama yolunu destekler:

| Yol        | Depolama konumu                  | Ödünleşim                                               |
| ----------- | --------------------------------- | ------------------------------------------------------ |
| `emit!`     | Program veri logları                 | Daha basit ve ucuz, ancak loglar kesilebilir         |
| `emit_cpi!` | Bir CPI'dan gelen iç talimat verisi | Daha dayanıklı meta veri, ancak ek hesaplar ve hesaplama maliyeti ile |

CPI olaylarını kullanmak için Anchor'ın `event-cpi` özelliğini etkinleştirin:

```toml title="Cargo.toml"
[dependencies]
anchor-lang = { version = "1.1.2", features = ["event-cpi"] }
```

Ardından talimatın hesaplar struct'ını `#[event_cpi]` ile işaretleyin ve bağlam değişkeninin adı `ctx` olan
bir işleyiciden olayı yayınlayın:

```rust title="lib.rs"
pub fn record_payment(ctx: Context<RecordPayment>, amount: u64) -> Result<()> {
    emit_cpi!(PaymentRecorded {
        authority: ctx.accounts.authority.key(),
        amount,
    });
    Ok(())
}

#[event_cpi]
#[derive(Accounts)]
pub struct RecordPayment<'info> {
    pub authority: Signer<'info>,
}
```

`#[event_cpi]`, imzalı self-CPI için gereken olay yetkilisi (event authority) ve mevcut program hesaplarını ekler. CPI olayları Anchor'ın log olay
abonelğiyle tüketilemez; bunun yerine işlemi getirin ve eşleşen iç talimatı
çözümleyin.

<Callout type="info" title="Kaynak olarak defteri (ledger) kullanın">
  RPC sağlayıcıları program loglarını kesebilir. Bir olayın kaçırılması bakiyeleri, izinleri veya doğruluğun kritik olduğu başka bir iş akışını etkileyecekse,
  sonucu program hesaplarından veya işlem talimat verisinden türetin. Olayları
  indekslemeyi verimli kılmak için kullanın; durumun tek kaydı olarak kullanmayın.
</Callout>

## TypeScript'ten abone olma

Güncel Anchor TypeScript istemcisi `@anchor-lang/core`'dur. Program IDL'inden oluşturulan bir `Program`
örneği, eşleşen log olaylarını çözümleyebilir ve bunları
RPC log aboneliği üzerinden iletebilir:

```ts
const listenerId = program.addEventListener(
  "PaymentRecorded",
  (event, slot, signature) => {
    console.log({ event, slot, signature });
  },
  "confirmed"
);

// Remove the websocket subscription when it is no longer needed.
await program.removeEventListener(listenerId);
```

Geri çağırma (callback) çözümlenmiş olay verisini, slot'u ve işlem
imzasını alır. Abonelikler yalnızca bağlantı etkin olduğu sürede iletilen logları kapsar. Tüketici
tam geçmişe ihtiyaç duyuyorsa, işlenen imzaları kalıcı olarak saklayın ve bağlantı kesildikten sonra kaçırılan işlemleri geriye dönük olarak doldurun.

## Getirilen işlem loglarını çözümleme

Geriye dönük doldurma ve tek seferlik inceleme için bir işlemi getirin ve her
`Program data:` yükünü olay kodlayıcısına (event coder) iletin:

```ts
const transaction = await connection.getTransaction(signature, {
  commitment: "confirmed",
  maxSupportedTransactionVersion: 0
});

if (!transaction?.meta || transaction.meta.err) {
  throw new Error("Transaction was not found or did not succeed");
}

for (const log of transaction.meta.logMessages ?? []) {
  const prefix = "Program data: ";
  if (!log.startsWith(prefix)) continue;

  const decoded = program.coder.events.decode(log.slice(prefix.length));
  if (decoded) console.log(decoded.name, decoded.data);
}
```

Bir işlem birden fazla programı çağırabilir. Üretim ortamı için bir ayrıştırıcıda,
`Program <address> invoke` ve `success` log sınırlarını takip edin veya Anchor'ın olay
ayrıştırıcısını kullanın; böylece başka bir programın `Program data:` girdisi sizin programınızınmış gibi çözümlenmez.
Başarısız işlemler, hata oluşmadan önce tamamlanan işlerden kalan logları ve iç talimatları
tutabilir; bu nedenle her iki olay biçimini de indekslemeden önce `err` değeri null olmayan işlem meta verilerini
daima reddedin. Anchor'ın log aboneliği, bir olay geri çağırmasını iletmeden önce
bu kontrolü yapar.

Bir `emit_cpi!` olayı için, `meta.innerInstructions` içindeki self-CPI'ı bulun,
program ID'sinin sizin programınız olduğunu doğrulayın ve talimat verisini
base58 ile çözün. Herhangi bir bayt çıkarmadan önce Anchor'ın
[`EVENT_IX_TAG_LE`](https://github.com/solana-foundation/anchor/blob/v1.1.2/lang/src/event.rs#L1-L3) değerini doğrulayın:

```ts
import bs58 from "bs58";

const EVENT_IX_TAG_LE = Buffer.from("e445a52e51cb9a1d", "hex");
const instructionData = Buffer.from(bs58.decode(innerInstruction.data));

if (!instructionData.subarray(0, 8).equals(EVENT_IX_TAG_LE)) {
  // This is an ordinary self-CPI, not an emit_cpi! event.
  continue;
}

const eventData = instructionData.subarray(8).toString("base64");
const decoded = program.coder.events.decode(eventData);
```

Hem program ID'sini hem de etiketi (tag) kontrol etmek, sıradan bir self-CPI'ın
olay sanılmasını önler.

## Olay şemalarını sürümleme

Varsayılan olarak Anchor, olay adından 8 baytlık bir olay ayırt edicisi (discriminator) türetir.
Anchor ayrıca `#[event(discriminator = ...)]` ile açık bir ayırt ediciyi de destekler.
Ayırt ediciler program içinde benzersiz kalmalı ve olayı çözümleyen her istemci için
kararlı olmalıdır.

Yayınlanan bir struct'ın alanlarını değiştirmek, Borsh düzenini değiştirir. Geriye dönük uyumsuz bir
şema değişikliği için `PaymentRecorded` olayını sessizce değiştirmek yerine
`PaymentRecordedV2` gibi yeni bir olay tanımlayın. Mevcut indeksleyiciler hâlâ eski olaya bağımlıysa,
geçiş döneminde eski olayı yayınlamaya devam edin.

Gelişime açık veriler için sabit genişlikli alanları ve indeksleyicinin daha zengin hesap verisini
ayrıca getirmesini sağlayan tanımlayıcıları tercih edin. Güncellenmiş IDL'i program yükseltmesinden önce veya
yükseltmeyle birlikte yayınlayın; böylece tüketiciler yeni olayı hemen çözümleyebilir.

## Olayları test etme

Base64 string'ini değil, çözümlenmiş sözleşmeyi (contract) test edin. Dinleyiciyi,
talimatı göndermeden önce kaydedin, çözümlenmiş alanları ve işlem imzasını doğrulayın
ve dinleyiciyi her zaman kaldırın:

```ts
let listenerId = 0;
const received = new Promise<{
  event: { authority: PublicKey; amount: BN };
  signature: string;
}>((resolve) => {
  listenerId = program.addEventListener(
    "PaymentRecorded",
    (event, _slot, signature) => resolve({ event, signature }),
    "confirmed"
  );
});

try {
  const signature = await program.methods.recordPayment(new BN(500)).rpc();
  const result = await received;

  assert.equal(result.signature, signature);
  assert.equal(result.event.amount.toString(), "500");
} finally {
  await program.removeEventListener(listenerId);
}
```

Ayrıca indeksleyicinin başarısız işlem meta verilerinde kalan olay baytlarını yok saydığını test edin ve desteklenen her olay sürümü için bir fixture ekleyin. `emit_cpi!`
kullanıyorsanız, `innerInstructions` içinden çözümlemeyi test edin; çünkü log dinleyicileri
bu olayları doğrudan almaz.
