Αυτός ο οδηγός απευθύνεται σε παρόχους υπηρεσιών πορτοφολιού και προγραμματιστές
που θέλουν να ενσωματώσουν νέες λύσεις διαχείρισης κλειδιών στη βιβλιοθήκη
`solana-keychain`. Προσθέτοντας την υλοποίηση του υπογράφοντός σας, θα
επιτρέψετε στους προγραμματιστές να χρησιμοποιούν την υπηρεσία σας για ασφαλή
υπογραφή συναλλαγών Solana μέσω μιας ενοποιημένης διεπαφής.

Το Keychain διατηρεί τις υλοποιήσεις του σε Rust, TypeScript, Python και Go σε πλήρη ισοδυναμία.
Τα PR που περιλαμβάνουν και τις τέσσερις προτιμώνται ιδιαίτερα. Αν μπορείτε να συνεισφέρετε
μόνο μία, δεν πειράζει, αλλά να περιμένετε ότι θα απαιτηθούν και οι υπόλοιπες πριν το signer συμπεριληφθεί
σε κάποια έκδοση.

_Χρησιμοποιείτε το Claude Code; Το
[`add-signer-ci` skill](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)
του αποθετηρίου ρυθμίζει τα CI workflows για ένα νέο signer που συνεισφέρεται μέσω PR από fork._

## Επισκόπηση Αρχιτεκτονικής

Η βιβλιοθήκη χρησιμοποιεί αρχιτεκτονική βασισμένη σε traits, η οποία ορίζεται στο `src/traits.rs`. Κάθε
signer υλοποιεί το βασικό trait `SolanaSigner` (`pubkey`, `sign_message`,
`is_available`) και ακριβώς ένα trait δυνατοτήτων που ταιριάζει με τη μορφή του παρόχου:

- `TransactionSigner` (`sign_transaction`): ο πάροχος υπογράφει τα bytes του καλούντος
  και ο καλών κάνει τη μετάδοση. Οι περισσότερες υποδομές backend.
- `ModifyingSigner` (`modify_and_sign_transaction`): ο πάροχος αναδιατυπώνει τη
  συναλλαγή και στη συνέχεια την υπογράφει χωρίς να τη μεταδώσει.
- `SendingSigner` (`sign_and_send_transaction`): ο πάροχος υπογράφει και
  μεταδίδει από την πλευρά του διακομιστή.

Η βιβλιοθήκη παρέχει επίσης ένα ενοποιημένο enum `Signer` που περιβάλλει όλες τις
υλοποιήσεις και επιτρέπει την επιλογή των backends υπογραφής κατά το runtime. Υλοποιεί
μόνο το βασικό trait· οι δυνατότητες είναι προσβάσιμες μέσω των `as_transaction_signer()`,
`as_modifying_signer()` και `as_sending_signer()`.

## Λίστα Ελέγχου Γρήγορης Ενσωμάτωσης

- Δημιουργήστε τη μονάδα του υπογράφοντός σας με την υλοποίηση
- Υλοποιήστε το βασικό trait `SolanaSigner` (`pubkey`, `sign_message`,
  `is_available`) και το ένα trait δυνατοτήτων που ταιριάζει με τη μορφή του παρόχου σας
  (συνήθως `TransactionSigner`)
- Προσθέστε ένα feature flag στο `Cargo.toml`, συμπεριλαμβανομένου του εσωτερικού δείκτη `_remote`, αν
  το signer σας χρησιμοποιεί reqwest
- Ενημερώστε το enum `Signer` στο `src/lib.rs` (variant, κλάδος `dispatch_signer!` και
  ένας κλάδος στον accessor δυνατοτήτων που ταιριάζει με τη μορφή σας)
- Επιβάλετε HTTPS και διαμορφώστε timeouts στους πελάτες HTTP
- Υπογράψτε τα bytes του μηνύματος και επαληθεύστε την υπογραφή που επιστρέφεται πριν την επισυνάψετε
- Προσθέστε ολοκληρωμένα unit tests (με βάση το wiremock, στο module σας)
- Προσθέστε ένα αρχείο integration test και ενημερώστε το `.env.example`
- Προσθέστε τις υλοποιήσεις σε TypeScript, Python και Go
- Ενημερώστε την τεκμηρίωση
- Ενημερώσεις των CI workflows (συντονιστείτε με τους maintainers, δείτε
  [Ενημερώσεις CI Workflow](#ci-workflow-updates-fork-prs))
- Υποβάλετε PR

## Βήμα 1: Δημιουργήστε τη Μονάδα του Υπογράφοντός Σας

Δημιουργήστε έναν νέο κατάλογο στο `src/` για την υλοποίησή σας:

```
src/
├── your_service/
│   ├── mod.rs      # Main implementation with SolanaSigner trait
│   └── types.rs    # API request/response types (if needed)
```

## Βήμα 2: Ορίστε τη Δομή του Υπογράφοντός Σας

Στο `src/your_service/mod.rs`, ορίστε τη δομή του υπογράφοντός σας:

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,
}

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## Βήμα 3: Υλοποιήστε τον Constructor και τις Βοηθητικές Μεθόδους

Οι απομακρυσμένοι υπογράφοντες **πρέπει** να επιβάλλουν HTTPS και να
διαμορφώνουν timeouts HTTP. Χρησιμοποιήστε τη κοινόχρηστη δομή
`HttpClientConfig` για τις ρυθμίσεις timeout.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## Βήμα 4: Υλοποίηση των Traits του Signer

Το βασικό trait `SolanaSigner` έχει 2 ασύγχρονες μεθόδους (`sign_message`,
`is_available`) και το `pubkey()`. Η υπογραφή συναλλαγών ανήκει σε ένα trait δυνατοτήτων·
οι περισσότεροι πάροχοι υλοποιούν το `TransactionSigner`, του οποίου η `sign_transaction` επιστρέφει
`SignTransactionResult` (ένα tagged enum που δηλώνει ότι η συναλλαγή είναι πλήρως ή
μερικώς υπογεγραμμένη).

Υπογράψτε τα bytes του μηνύματος, ποτέ ολόκληρη τη wire συναλλαγή, και επαληθεύστε την
υπογραφή του παρόχου σε σχέση με αυτά πριν την επισυνάψετε. Χρησιμοποιήστε τους κοινούς βοηθούς
`TransactionUtil` για την υπογραφή και τη σειριοποίηση.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

Αν ο πάροχός σας αναδιατυπώνει τη συναλλαγή πριν την υπογραφή, υλοποιήστε αντί γι' αυτό το
`ModifyingSigner` και αντικαταστήστε εξ ολοκλήρου τη συναλλαγή του καλούντος με
τα bytes του παρόχου. Αν μεταδίδει από την πλευρά του διακομιστή, υλοποιήστε το `SendingSigner`
και αφήστε τη συναλλαγή του καλούντος ανέγγιχτη. Μην υλοποιείτε ποτέ δυνατότητα που ο
πάροχός σας δεν μπορεί να υποστηρίξει.

## Βήμα 6: Προσθέστε Feature Flag

Ενημερώστε το `Cargo.toml` για να προσθέσετε το signer σας ως προαιρετικό feature. Τα απομακρυσμένα backends
περιλαμβάνουν τον εσωτερικό δείκτη `_remote`, ο οποίος ελέγχει την υλοποίηση `From<reqwest::Error>`
στο `src/error.rs`· χωρίς αυτόν, το `?` στις κλήσεις reqwest δεν θα μεταγλωττίζεται όταν είναι ενεργοποιημένο μόνο
το feature σας.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## Βήμα 7: Ενημερώστε τον Απαριθμητή Υπογραφών

Προσθέστε το signer σας στο `src/lib.rs`. Η βασική υλοποίηση `SolanaSigner` γίνεται dispatch μέσω
της μακροεντολής `dispatch_signer!`, οπότε προσθέστε έναν κλάδο εκεί. Η πρόσβαση στις δυνατότητες βρίσκεται στους
accessors `as_transaction_signer()`, `as_modifying_signer()` και `as_sending_signer()`:
προσθέστε έναν κλάδο `Some(s)` σε αυτόν που ταιριάζει με το trait δυνατοτήτων σας (και,
για backend αποστολής ή τροποποίησης, έναν κλάδο `None` στο `as_transaction_signer()`).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## Βήμα 8: Προσθέστε Ολοκληρωμένες Δοκιμές

Προσθέστε δοκιμές στη μονάδα σας (στο κάτω μέρος του `src/your_service/mod.rs`):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

Καλύψτε επίσης την αποτυχία επαλήθευσης υπογραφής: μια προσομοιωμένη απόκριση της οποίας η υπογραφή
δεν επαληθεύεται πρέπει να επιστρέφει σφάλμα.

## Βήμα 9: Προσθήκη Integration Tests

Δημιουργήστε το `rust/src/tests/test_<name>_integration.rs`. Τα integration tests εκτελούνται
έναντι του πραγματικού API της υπηρεσίας (όχι wiremock) και ενεργοποιούνται μόνο με το
feature `integration-tests`. Κάθε αρχείο χρειάζεται:

- Δηλώσεις `pub const` για τα ονόματα των μεταβλητών περιβάλλοντος
- Έναν βοηθό `get_signer()` που διαβάζει μεταβλητές περιβάλλοντος μέσω του `dotenvy`
- Τρεις συναρτήσεις δοκιμής: `test_<name>_sign_message`,
  `test_<name>_sign_transaction` και `test_<name>_is_available`
- Feature gates: `#[cfg(feature = "your_service")]` στο module και
  `#[cfg(feature = "integration-tests")]` σε κάθε test

Δείτε το `rust/src/tests/test_para_integration.rs` για πλήρες παράδειγμα αναφοράς και
δηλώστε το module σας στο `rust/src/tests/mod.rs`:

```rust
pub mod test_your_service_integration;
```

## Βήμα 11: Ενημέρωση της Τεκμηρίωσης

Προσθέστε τον υπογράφοντά σας στον πίνακα υποστηριζόμενων backends στο
README.md:

| Backend         | Περίπτωση Χρήσης                                       | Feature Flag   |
| --------------- | ---------------------------------------------- | -------------- |
| **Memory**      | Τοπικά ζεύγη κλειδιών, ανάπτυξη, δοκιμές           | `memory`       |
| **Vault**       | Διαχείριση κλειδιών επιχειρήσεων με HashiCorp Vault | `vault`        |
| **Privy**       | Ενσωματωμένα πορτοφόλια με υποδομή Privy     | `privy`        |
| **Turnkey**     | Μη θεματοφυλακτική διαχείριση κλειδιών μέσω Turnkey       | `turnkey`      |
| **YourService** | Σύντομη περιγραφή της υπηρεσίας σας              | `your_service` |

Προσθέστε επίσης το backend σας στον πίνακα δυνατοτήτων signer στο README κάθε
γλώσσας. Προσθέστε ένα παράδειγμα χρήσης:

```rust
use solana_keychain::{Signer, SolanaSigner};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let signer = Signer::from_your_service(
        "your-api-key".to_string(),
        "your-api-secret".to_string(),
        "your-wallet-id".to_string(),
        "your-public-key".to_string(),
    )?;

    let pubkey = signer.pubkey();
    println!("Public key: {}", pubkey);

    Ok(())
}
```

## Ενημερώσεις CI Workflow (PR από Fork)

Το CI είναι μια διαδικασία δύο φάσεων. Συντονιστείτε με τους maintainers για να προετοιμάσουν το `main` πριν
μπορέσει να δοκιμαστεί το PR σας: ενημερώνουν το `fork-external-live-manual.yml`, προσθέτουν μεταβλητές περιβάλλοντος
στο `ci.yml` και ρυθμίζουν τα GitHub Secrets.

Το PR σας πρέπει να περιλαμβάνει αυτές τις αλλαγές της Φάσης 2 μαζί με τον κώδικα του signer σας:

- **`ci.yml`**: προσθέστε το Rust feature σας στον πίνακα `backend` (πριν από το `all`) και
  τη συνάρτηση integration test σας στον πίνακα `test`
- **`typescript-ci.yml`**: προσθέστε το πακέτο σας στους πίνακες unit και integration
  tests, και προσθέστε μεταβλητές περιβάλλοντος στο βήμα των integration tests
- **`typescript-publish.yml`**: προσθέστε το πακέτο σας στο `PUBLISH_PACKAGES`, στον πίνακα
  `packages` του GitHub Release και στον συνοπτικό πίνακα
- **`python-ci.yml`**: προσθέστε το backend στον έλεγχο `CI_SIGNER_*` στο

## Υπογράφων TypeScript

Εάν προσθέτετε επίσης ένα πακέτο υπογραφών TypeScript, δημιουργήστε το στο
`typescript/packages/your-signer/`. Κύρια μοτίβα:

- Η συνάρτηση factory `createYourSigner()` επιστρέφει
  `SolanaTransactionSigner<TAddress> & SolanaMessageSigner<TAddress>`· κρατήστε την
  κλάση του signer εσωτερική και εξάγετε μόνο το factory και τον τύπο ρυθμίσεων του
- Εξαγωγή διεπαφής config (`YourSignerConfig`)
- Αν το backend σας δεν μπορεί να υπογράψει μηνύματα, παραλείψτε το `SolanaMessageSigner` και μην εκθέσετε καμία
  μέθοδο `signMessages`: το Kit ταξινομεί τους signers με βάση την παρουσία μεθόδων, οπότε ένα
  stub που ρίχνει σφάλμα θα ταξινομούσε λανθασμένα το signer
- Επιβάλετε HTTPS στα πεδία ρυθμίσεων `apiBaseUrl` με το `assertHttpsUrl()` από το
  `@solana/keychain-core`
- Πραγματοποιήστε απομακρυσμένες κλήσεις μέσω του `fetchSignerJson()` από το `@solana/keychain-core`,
  το οποίο διαχειρίζεται την αντιστοίχιση σφαλμάτων, την εξυγίανση των αποκρίσεων, την απόρριψη ανακατευθύνσεων και το
  προεπιλεγμένο timeout
- Εξυγιάνετε οποιοδήποτε άλλο κείμενο σφάλματος απομακρυσμένου API με το `sanitizeRemoteErrorResponse()`
  από το `@solana/keychain-core`
- Χρήση `throwSignerError(SignerErrorCode.*, { cause, message })` από
  `@solana/keychain-core`
- Σεβαστείτε το `config?.abortSignal` σε κάθε μέθοδο υπογραφής, περνώντας το στο
  `fetchSignerJson()` και στο `signBatchStaggered()`
- Επικυρώστε το `requestDelayMs` με το `validateRequestDelayMs()` και κάντε batch με το
  `signBatchStaggered()`
- Προσθήκη `@throws` JSDoc στις συναρτήσεις εργοστασίου με λίστα κωδικών
  σφάλματος
- Δηλώστε τα πακέτα `@solana/*` ως peer dependencies στην έκδοση `>=8.1.0`
- Unit tests με vitest και mocked `fetch`· integration tests με
  `runSignerIntegrationTest` από το `@solana/keychain-test-utils`

### Sending Signers

Αν ο πάροχός σας αναδιατυπώνει τη συναλλαγή ή μεταδίδει από την πλευρά του διακομιστή, η
υπογραφή του δεν μπορεί να εφαρμοστεί στη συναλλαγή του καλούντος, οπότε πρέπει να είναι
`SolanaSendingSigner` αντί για `SolanaTransactionSigner`:

- Υλοποιήστε το `signAndSendTransactions()` και εκθέστε **καμία** μέθοδο `signTransactions`
  (ούτε `signMessages`, εκτός αν το backend υπογράφει πραγματικά μηνύματα)
- Σεβαστείτε το `config?.abortSignal`. Μόλις ο πάροχος αποδεχτεί τη δημιουργία, αναφέρετε
  κάθε αποτυχία (συμπεριλαμβανομένου ενός abort) ως `BROADCAST_UNCONFIRMED` που φέρει το
  αναγνωριστικό συναλλαγής του παρόχου, με τον λόγο του abort να διατηρείται ως `cause`
- Προσθέστε μια τυποποιημένη υπερφόρτωση `createKeychainSigner` που επιστρέφει τον τύπο sending-signer σας
- Εξαιρέστε το backend σας από το `KeychainKitPluginConfig` στο
  `typescript/packages/kit-plugin/src/keychain-plugin.ts`, καθώς ένας sending
  signer δεν μπορεί να λειτουργήσει ως `payer` ή `identity` ενός Kit client
- Επιβεβαιώστε στα unit tests ότι το `isTransactionPartialSigner()` είναι false και
  το `isTransactionSendingSigner()` είναι true για τα instances σας

### Ενημέρωση Πακέτου Umbrella

Ενημερώστε το `typescript/packages/keychain/` (7 αρχεία προς τροποποίηση):

1. `src/types.ts`: Προσθέστε το `YourSignerConfig` στη discriminated union
   `KeychainSignerConfig`
2. `src/create-keychain-signer.ts`: Προσθέστε το switch case (κάθε πακέτο backend
   φορτώνεται με δυναμικό `import()`)
3. `src/resolve-address.ts`: Προσθέστε στο switch case της fast-path ή της fetch-path
4. `src/index.ts`: Προσθέστε τις εξαγωγές του τύπου ρυθμίσεων, του namespace και της συνάρτησης factory
5. `package.json`: Προσθέστε το dependency `@solana/keychain-your-signer: "workspace:*"`
6. `tsconfig.json`: Προσθέστε την αναφορά `{ "path": "../your-signer" }`
7. `typescript/scripts/test-treeshake-umbrella.mjs`: Προσθέστε το πακέτο σας στο
   `SIGNER_MARKERS` και το factory σας στο `FACTORIES`

Οι εντολές switch έχουν εξαντλητικούς ελέγχους `never`, οπότε η TypeScript θα εμφανίσει σφάλμα
αν προσθέσετε στην union αλλά παραλείψετε ένα case. Εκτελέστε στη συνέχεια το `just ts-treeshake`:
κάθε πακέτο και το umbrella πρέπει να παραμένουν tree-shakable.

## Python Signer

Δημιουργήστε το module στο `python/src/solana_keychain/your_signer/` (`__init__.py`
και `signer.py`). Βασικά πρότυπα:

- Κάντε subclass το `SolanaSigner` από το `solana_keychain.core` (property `pubkey`,
  `async sign_message()`, `async is_available()`) και ακριβώς μία κλάση
  δυνατοτήτων: `TransactionSigner` (`async sign_transaction()`), `ModifyingSigner`
  (`async modify_and_sign_transaction()`) ή `SendingSigner`
  (`async sign_and_send_transaction()`)
- Εξαγάγετε ένα factory `async create_your_signer()` που κάνει await το `init()` όταν το
  backend επιλύει τη διεύθυνσή του απομακρυσμένα· πριν το init, η υπογραφή ρίχνει
  `SignerErrorCode.NOT_INITIALIZED`
- Εξαγάγετε μια config dataclass (`YourSignerConfig`) με τα μυστικά να σημειώνονται
  με `field(repr=False)`
- Επιβάλετε HTTPS στα πεδία base-URL με το `assert_https_url()` και δρομολογήστε κάθε
  αίτημα μέσω του `fetch_signer_json()`
- Επαληθεύστε την υπογραφή του παρόχου πριν την επιστρέψετε· χρησιμοποιήστε το
  `signed_message_bytes()` για τα bytes που καλύπτει μια υπογραφή, ποτέ μια χειροποίητη
  έκδοση προθέματος
- Καταχωρίστε το backend στο `_BACKENDS` στο
  `python/src/solana_keychain/keychain.py`
- Αν το backend χρειάζεται SDK παρόχου, προστατέψτε την εισαγωγή (import), εγείρετε ένα `ImportError`
  που να αναφέρει `pip install 'solana-keychain[your-signer]'`, δηλώστε το extra στο
  `python/pyproject.toml` και μην εισάγετε ποτέ το backend άμεσα (eagerly) από τη ρίζα του πακέτου
- Unit tests με pytest: `respx` για backends HTTP, stub clients για backends
  SDK και έλεγχος ότι κανένα μυστικό δεν εμφανίζεται στο `str()` ή στο `repr()` των σφαλμάτων
  που εγείρονται
- Προσθέστε μια factory `make_your_signer()` στο
  `python/tests/integration/test_live_signers.py` και καταχωρίστε την στο
  `_MESSAGE_CAPABLE` (ή στο `_TRANSACTION_ONLY` για backends χωρίς
  `sign_message`)

## Go Signer

Κάθε backend Go είναι ξεχωριστό module, στη διαδρομή `go/signers/yoursigner/` με module path
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`. Δείτε το
`go/signers/para/` ως αναφορά. Βασικά μοτίβα:

- Υλοποιήστε το `core.SolanaSigner` (`Pubkey()`, `SignMessage(ctx, message)`,
  `IsAvailable(ctx)`) και ακριβώς μία διεπαφή δυνατοτήτων:
  `core.TransactionSigner`, `core.ModifyingSigner` ή `core.SendingSigner`.
  Η δυνατότητα ανιχνεύεται με type assertion, επομένως ένα backend που δεν μπορεί να υπογράψει
  συναλλαγή δεν πρέπει να διαθέτει καθόλου μέθοδο `SignTransaction`
- Εξάγετε ένα struct `Config` και έναν constructor `New` (`New(ctx, cfg)` όταν το
  backend επιλύει τη διεύθυνσή του απομακρυσμένα· πριν από αυτό, επιστρέψτε
  `core.NewNotInitializedError`)
- Δημιουργήστε HTTP clients με `core.NewHTTPClient` ή `core.ResolveHTTPClient` και
  επικυρώστε τις βασικές διευθύνσεις URL με `core.NormalizeHTTPSBaseURL`
- Υπογράψτε τις συναλλαγές με `core.SignTransactionWith`, το οποίο υπογράφει τα bytes του μηνύματος
  και επισυνάπτει την υπογραφή· επαληθεύστε τις υπογραφές του παρόχου με
  `core.VerifySignature`
- Επιστρέψτε σφάλματα με `core.NewSignerError` / `core.WrapSignerError` και σταθερούς
  κωδικούς όπως `core.CodeSigningFailed`
- Unit tests με `httptest`· integration tests στο `integration_test.go` πίσω από
  το tag `//go:build integration`

## Συμβουλές Υλοποίησης

### Διαχείριση Σφαλμάτων

Χρησιμοποιείτε πάντα τις υπάρχουσες παραλλαγές `SignerError`. Τόσο το `Display` όσο και το `Debug` του
`SignerError` είναι redacted, γι' αυτό κρατήστε τα μηνύματα γενικά και μην συμπεριλαμβάνετε ποτέ ακατέργαστα δεδομένα απαντήσεων API.
Μην χρησιμοποιείτε ποτέ `.expect()` ή `.unwrap()` σε μη αξιόπιστες απαντήσεις API:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### Απαιτήσεις ασφάλειας

Αυτές δεν είναι απλές προτάσεις: οι καταναλωτές επιλέγουν backend βάσει αυτών. Αν
ο πάροχός σας καθιστά κάποια αδύνατη, αναφέρετέ το στο PR και στο
`docs/SECURITY_MODEL.md` του αποθετηρίου.

- **Επαληθεύστε τι υπέγραψε ο πάροχος.** Υπολογίστε τα bytes του μηνύματος τοπικά και
  επαληθεύστε την επιστρεφόμενη υπογραφή με βάση αυτά, στην απαιτούμενη θέση του signer σας,
  πριν την επισυνάψετε. Μια υπογραφή που δεν επαληθεύεται πρέπει να αποτυγχάνει και ποτέ να
  μην επισυνάπτεται.
- **Δηλώστε αν ο πάροχος κάνει broadcast.** Αν εκτελεί την ενέργεια στην πλευρά του server,
  υλοποιήστε το sending shape και επιστρέψτε την υπογραφή που προσδιορίζει τη
  συναλλαγή που καταχωρίστηκε. Αν ο πάροχος δεν διαθέτει endpoint μόνο για υπογραφή, ορίστε το
  backend ως μόνο-αποστολής αντί να υποβάλλετε συναλλαγές εν αγνοία του καλούντος.
- **Μην αφήνετε ποτέ τον καλούντα με μια συναλλαγή που η υπογραφή δεν καλύπτει.**
  Ένας πάροχος που ξαναγράφει τη συναλλαγή υπογράφει τα δικά του bytes: είτε αφήστε τη
  συναλλαγή του καλούντος ανέγγιχτη (η περίπτωση του broadcast-managed), είτε υιοθετήστε το
  modifying shape και αντικαταστήστε την ολόκληρη με τα bytes του παρόχου.
- **Αναφέρετε την αβεβαιότητα του broadcast ως τέτοια.** Μια αποτυχία μετά την υποβολή μπορεί παρ' όλα αυτά
  να έχει καταχωριστεί. Επιστρέψτε `BROADCAST_UNCONFIRMED` αντί για γενικό σφάλμα,
  συμπεριλάβετε το αναγνωριστικό συναλλαγής του παρόχου όποτε το έχετε και στέλνετε ένα
  idempotency key προερχόμενο από το μήνυμα σε κάθε δημιουργία, ώστε η επαναποστολή
  ταυτόσημων bytes να είναι ασφαλής.
- **Ποτέ μην υπογράφετε πριν το init.** Χρησιμοποιήστε `Option<Pubkey>` (όχι `Pubkey::default()`) για
  το δημόσιο κλειδί πριν από το `init()` και αποτύχετε με σφάλμα διαμόρφωσης αν
  επιχειρηθεί υπογραφή νωρίτερα.
- Μην καταγράφετε ποτέ ευαίσθητα δεδομένα (ιδιωτικά κλειδιά, μυστικά API, ακατέργαστες απαντήσεις API) και
  χρησιμοποιήστε υλοποίηση `Debug` που κρύβει τα ευαίσθητα πεδία
- Επιβάλετε HTTPS (`https_only(true)`, με έλεγχο μέσω `#[cfg(not(test))]` για
  wiremock) και ρυθμίστε timeouts αιτήματος και σύνδεσης μέσω `HttpClientConfig`
  (προεπιλογές: 30s/5s)
- Μηδενίστε (zeroize) το ενδιάμεσο υλικό κλειδιού με `zeroize::Zeroizing<Vec<u8>>`

### Δοκιμές με Mocks

Χρησιμοποιήστε το `wiremock` για την προσομοίωση HTTP APIs. Κάντε διεκδίκηση
μόνο στον τύπο σφάλματος, όχι στο κείμενο του μηνύματος σφάλματος:

```rust
#[cfg(test)]
mod tests {
    use wiremock::{MockServer, Mock, ResponseTemplate};

    #[tokio::test]
    async fn test_api_call() {
        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
