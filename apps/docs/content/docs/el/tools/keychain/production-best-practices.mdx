Το Keychain αφαιρεί την πολυπλοκότητα του signing backend, ωστόσο η λειτουργία ενός signer σε παραγωγή
παραμένει δική σας ευθύνη. Αυτές οι πρακτικές εφαρμόζονται σε όλα τα backends· ανατρέξτε στο
[Επιλογή backend](/docs/tools/keychain/choosing-a-backend) για την επιλογή του κατάλληλου.

## Διαχωρίστε τους hot και cold signers

Χρησιμοποιήστε έναν λειτουργικό signer χαμηλού υπολοίπου ("hot") για συχνές, αυτοματοποιημένες
συναλλαγές, και έναν ξεχωριστό signer υψηλής αξίας ("cold") για κινήσεις ταμείου.
Υποστηρίξτε τον cold signer με MPC custody ή cloud HSM και απαιτήστε πολιτικές έγκρισης
πριν υπογράψει. Επειδή η διεπαφή είναι πανομοιότυπη, κάθε ρόλος μπορεί να χρησιμοποιεί
διαφορετικό backend χωρίς αλλαγές στα σημεία κλήσης.

## Εναλλάσσετε κλειδιά με πρόθεση

Στο Solana το κλειδί υπογραφής _είναι_ η διεύθυνση του λογαριασμού, επομένως η εναλλαγή κλειδιού παράγει
νέα διεύθυνση. Σχεδιάστε την εναλλαγή ως μετεγκατάσταση: δημιουργήστε ένα νέο κλειδί, αναθέστε εκ νέου
τις σχετικές εξουσίες (ή μεταφέρετε κεφάλαια) στη νέα διεύθυνση, και στη συνέχεια αποσύρετε το παλιό.
Χρησιμοποιήστε διακριτά κλειδιά ανά περιβάλλον, ώστε τα κλειδιά devnet να μην επαναχρησιμοποιούνται ποτέ στο
mainnet.

## Παραχωρήστε πρόσβαση ελάχιστων δικαιωμάτων

Περιορίστε τα διαπιστευτήρια κάθε backend στο ελάχιστο που απαιτείται για την υπογραφή. Για το AWS KMS,
αυτά είναι τα `kms:Sign`, `kms:DescribeKey` και `kms:GetPublicKey` στο συγκεκριμένο κλειδί
(ο έλεγχος διαθεσιμότητας χρησιμοποιεί τα δύο τελευταία)· προτιμήστε ρόλους IAM αντί για στατικά
διαπιστευτήρια. Εφαρμόστε την ίδια αρχή στις πολιτικές του Vault και στα κλειδιά API των διαχειριζόμενων πορτοφολιών.

## Σχεδιάστε για διαθεσιμότητα

Τα απομακρυσμένα backends εξαρτώνται από μια υπηρεσία δικτύου. Ελέγξτε τη διαθεσιμότητα πριν βασιστείτε
σε έναν υπογράφοντα (`isAvailable()` στην TypeScript, `is_available()` στις Rust και Python,
`IsAvailable(ctx)` στη Go), επαναλάβετε τις αποτυχημένες αιτήσεις που αφορούν μόνο υπογραφή με backoff και ορίστε
εναλλακτική διαδρομή για τις διακοπές λειτουργίας. Μην επαναλαμβάνετε τυφλά ένα backend που εκτελεί broadcast
(Crossmint, αυτόματη λειτουργία native του Fordefi): δείτε
[Διαχείριση μη επιβεβαιωμένων broadcast](#handle-unconfirmed-broadcasts). Το Keychain
επιβάλλει HTTPS στις ρυθμισμένες βασικές διευθύνσεις URL, απορρίπτει τις ανακατευθύνσεις και εφαρμόζει προεπιλεγμένο
όριο χρόνου αιτήματος.

## Διαχείριση μη επιβεβαιωμένων broadcast

Το Crossmint και η αυτόματη λειτουργία native του Fordefi υπογράφουν και εκτελούν broadcast από την πλευρά του διακομιστή, οπότε μια
αποτυχημένη κλήση δεν σημαίνει ότι δεν έφτασε τίποτα. Όταν ο πάροχος ενδέχεται να έχει αποδεχθεί
τη συναλλαγή, το Keychain επιστρέφει `BROADCAST_UNCONFIRMED`
(`SignerError::BroadcastUnconfirmed` στη Rust). Το σφάλμα περιλαμβάνει το αναγνωριστικό συναλλαγής του παρόχου όταν η δημιουργία έγινε αποδεκτή και περιλαμβάνει πάντα το
κλειδί idempotency με το οποίο στάλθηκε η δημιουργία, το οποίο προκύπτει από το μήνυμα.

- Συμφωνήστε τα στοιχεία με τον πάροχο χρησιμοποιώντας το αναγνωριστικό συναλλαγής πριν κάνετε οτιδήποτε
  άλλο.
- Η επαναποστολή της συναλλαγής με πανομοιότυπα byte είναι ασφαλής: το κλειδί idempotency
  την αποδιπλασιάζει.
- Η αναδόμηση της συναλλαγής (για παράδειγμα με νέο blockhash) παράγει νέο κλειδί
  και επομένως νέα μεταφορά.

## Προστατέψτε μυστικά και μεταφορά

- Τα απομακρυσμένα backends επιβάλλουν HTTPS στις ρυθμισμένες βασικές διευθύνσεις URL και απορρίπτουν τις ανακατευθύνσεις.
  Η μόνη εξαίρεση είναι το Vault, που δέχεται απλό HTTP στο loopback, ώστε να λειτουργεί ένα τοπικό
  `vault server -dev`.
- Παρέχετε API keys, tokens και διαπιστευτήρια από έναν secret manager ή μεταβλητές περιβάλλοντος
  — μην τα κωδικοποιείτε ποτέ σε στατικό κώδικα ούτε να τα υποβάλλετε σε source control.
- Το Keychain εξυγιαίνει τις αποκρίσεις σφαλμάτων για να αποφύγει τη διαρροή μυστικών στα logs· διατηρείτε
  τα δικά σας logs απαλλαγμένα από ακατέργαστα διαπιστευτήρια και υλικό κλειδιών.

## Παρακολουθήστε και ελέγξτε τις υπογραφές

Παρακολουθήστε τον ρυθμό επιτυχίας υπογραφής, την καθυστέρηση και τον αριθμό αποτυχιών, και δημιουργήστε ειδοποιήσεις για αιχμές —
δείτε τις μετρικές στο
[Production Readiness](/docs/tools/production-readiness#monitoring). Ενεργοποιήστε
τα logs ελέγχου από την πλευρά του παρόχου (KMS, Vault ή custodian) και συσχετίστε τα με
τις συναλλαγές που υποβάλλει η εφαρμογή σας.

## Γνωρίστε τι ελέγχει το Keychain

- Το Keychain επικυρώνει το βήμα της υπογραφής, όχι τη συναλλαγή σας: δεν υπάρχει
  προσομοίωση, έλεγχος περιεχομένου της συναλλαγής ούτε μηχανισμός πολιτικών. Εφαρμόστε τα
  στην εφαρμογή σας ή στους ελέγχους πολιτικής του παρόχου.
- Η χειροκίνητη λειτουργία native του Fordefi ξαναγράφει τη συναλλαγή (blockhash, εντολές
  χρέωσης Compute Budget) πριν την υπογράψει. Συνεχίστε από τη συναλλαγή που επιστρέφεται,
  ποτέ από αυτήν που υποβάλατε, και εκτελέστε την πριν από οποιονδήποτε άλλο υπογράφοντα.
- Η Rust μηδενίζει τα ενδιάμεσα buffer κλειδιών· η Python και η Go δεν μπορούν. Με το backend Memory
  σε αυτές τις γλώσσες, αντιμετωπίστε όλη τη μνήμη της διεργασίας ως ευαίσθητη.
- Με το Ledger, η οθόνη της συσκευής είναι η μόνη αξιόπιστη περιγραφή του τι
  υπογράφεται. Μην ενεργοποιείτε τη λειτουργία `unsafe-debug` ούτε την καταγραφή `TRACE` για
  το `solana_remote_wallet` στην παραγωγή, καθώς και οι δύο καταγράφουν λεπτομέρειες συσκευής και συναλλαγής.

[μοντέλο ασφάλειας](https://github.com/solana-foundation/solana-keychain/blob/main/docs/SECURITY_MODEL.md)
