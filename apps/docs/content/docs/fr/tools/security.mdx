## Gestion des clés

- **N'exposez jamais de clés privées dans le code frontend.** Utilisez la signature côté backend, des portefeuilles matériels, des portefeuilles multisignatures ou des services de gestion de clés.
- **Séparez les portefeuilles chauds et froids.** Le portefeuille chaud sert aux opérations, le portefeuille froid à la trésorerie.
- **Sauvegardez toutes les clés de production.** Stockez des sauvegardes chiffrées dans plusieurs emplacements sécurisés. Perdre une clé signifie perdre définitivement l'accès.
- **Utilisez des clés différentes pour devnet et mainnet.** Vos clés devnet ne doivent pas être vos clés mainnet. Utilisez une configuration basée sur l'environnement pour vous assurer que les bonnes clés sont chargées pour chaque réseau.

## Infrastructure de signature

Pour la signature backend en production, utilisez [Keychain](/docs/tools/keychain), une bibliothèque de signature unifiée qui fait abstraction de plusieurs backends de gestion de clés via une interface unique : Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP, Para, Dfns, Crossmint, Openfort et Utila. Cela vous permet de développer en local avec des clés en mémoire, puis de passer à des backends de niveau production sans modifier le code de votre application.

Vous ne savez pas quel backend choisir ? Consultez [Choisir un backend](/docs/tools/keychain/choosing-a-backend). Keychain est disponible pour [Rust](https://crates.io/crates/solana-keychain) et [TypeScript](https://www.npmjs.com/package/@solana/keychain).

## Sécurité RPC

Traitez les endpoints RPC comme des clés d'API : ne les exposez pas dans le code frontend, où ils peuvent être extraits et utilisés à mauvais escient. Utilisez un proxy backend ou des variables d'environnement qui ne sont pas intégrées au code client.

- [QuickNode : bonnes pratiques de sécurité des endpoints](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius : protégez vos clés d'API Solana : bonnes pratiques de sécurité](https://www.helius.dev/docs/rpc/protect-your-keys)

## Surveillance

Suivez ces métriques en production :

| Métrique                   | Pourquoi                    |
| ------------------------ | ---------------------- |
| Taux de réussite des transactions | Détecter les problèmes rapidement    |
| Latence de confirmation     | Surveiller la santé du réseau |
| Dépenses en frais de priorité       | Maîtrise des coûts        |
| Taux d'erreur RPC           | Santé du fournisseur        |

Configurez des alertes pour :

- Les transferts de la trésorerie dépassant un seuil
- Les pics du taux de transactions échouées
- Les schémas de destinataires inhabituels
- Les hausses du taux d'erreur RPC

Pour la surveillance des transactions en temps réel à grande échelle, consultez notre [guide d'indexation](/docs/payments/accept-payments/indexing).

## Vérifier les adresses

Chaque token et chaque programme possède exactement une adresse correcte sur mainnet. Les faux tokens imitant l'USDC ou d'autres stablecoins sont courants : ils ont le même nom et le même symbole, mais un mint différent. Votre application doit coder en dur ou placer sur liste d'autorisation les adresses de mint (selon vos besoins), et ne jamais les accepter dynamiquement depuis des sources non fiables.

**Configuration basée sur l'environnement :** Devnet et Mainnet utilisent souvent des mints de tokens complètement différents. Configurez votre application pour charger les bonnes adresses selon l'environnement : ne codez pas en dur les adresses mainnet en oubliant de les remplacer pendant les tests, ou pire, ne livrez pas des adresses devnet en production.

Voici quelques mints de stablecoins courants :

| Token | Émetteur | Adresse du mint                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

Les adresses de programmes comptent aussi. Envoyer des instructions au mauvais programme échouera, ou pire, entraînera une perte irréversible de fonds. Les adresses du Token Program sont :

| Programme            | Adresse                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

Placer les bonnes adresses sur liste d'autorisation protège contre les faux tokens, mais cela ne protège pas contre l'envoi vers le mauvais _type_ de compte. Une adresse de destinataire peut être un portefeuille, un token account, un mint ou un programme, et chacun nécessite un traitement différent. Des SOL natifs envoyés vers autre chose qu'un portefeuille échappent au contrôle de l'expéditeur — perdus définitivement s'il s'agit d'un mint ou d'un programme, récupérables uniquement par le propriétaire du compte s'il s'agit d'un token account — sans qu'aucune transaction échouée n'avertisse l'utilisateur.

<Callout type="warn" title="Validez les destinataires avant l'envoi">
  Classez chaque adresse de destinataire avant de signer un transfert. Consultez [Vérifier une adresse](/docs/payments/send-payments/verify-address) pour l'arbre de décision complet et le code de référence permettant de distinguer les portefeuilles, les token accounts, les mints et les programmes.
</Callout>
