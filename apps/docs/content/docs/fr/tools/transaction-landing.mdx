## Infrastructure RPC

Les [endpoints publics](https://solana.com/docs/references/clusters#solana-public-rpc-endpoints)
(`api.mainnet.solana.com`) sont soumis à des limites de débit et ne sont couverts par aucun SLA. Ils conviennent au
développement, mais feront échouer vos flux de paiement en production, comme si vous essayiez de faire tourner un processeur de paiement
via une API partagée sans garantie de disponibilité.

<Callout type="caution" title="N'utilisez jamais un RPC public en production">
  Utilisez un [fournisseur RPC privé](https://solana.com/rpc) pour bénéficier d'un accès
  fiable et à faible latence.
</Callout>

Lorsque vous choisissez un fournisseur RPC, vérifiez les critères suivants :

- **Fiabilité** : des SLA avec garanties de disponibilité (99,9 % et plus)
- **Latence** : proximité géographique avec vos utilisateurs
- **Fonctionnalités** : fonctionnalités de transaction landing, indexation, API de frais de priorité

Pour obtenir la liste complète des fournisseurs RPC, consultez le guide
[Fournisseurs d'infrastructure RPC](https://solana.com/rpc).

### Configuration RPC redondante

Comme tout fournisseur de services réseau, les fournisseurs RPC peuvent connaître des interruptions ou
des périodes de performances dégradées. Pour garantir la résilience de votre application, vous
devriez la configurer pour utiliser plusieurs fournisseurs RPC.

[Solana Kit](https://github.com/anza-xyz/kit/tree/main/packages/rpc-transport-http)
fournit une bibliothèque permettant de personnaliser les transports RPC, ce qui vous permet de créer votre
propre client RPC redondant. Voici un exemple d'utilisation pour construire un
client RPC redondant :

```ts
import { RpcTransport } from "@solana/rpc-spec";
import { RpcResponse } from "@solana/rpc-spec-types";
import { createHttpTransport } from "@solana/rpc-transport-http";

// Create a transport for each RPC server
const transports = [
  createHttpTransport({ url: "https://mainnet-beta.my-server-1.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-2.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-3.com" })
];

// Create a wrapper transport that distributes requests to them
let nextTransport = 0;
async function roundRobinTransport<TResponse>(
  ...args: Parameters<RpcTransport>
): Promise<RpcResponse<TResponse>> {
  const transport = transports[nextTransport];
  nextTransport = (nextTransport + 1) % transports.length;
  return await transport(...args);
}
```

Si vous préférez ne pas développer vos propres outils de routage, vous pouvez utiliser un service
tiers comme [Iron Forge](https://www.ironforge.sanctum.so/) pour gérer le
routage à votre place.

## Transaction Landing

Sur Devnet, les transactions sont incluses assez facilement. Sur Mainnet, vous êtes en concurrence pour l'espace dans
les blocs. Pour augmenter les chances que votre transaction soit incluse dans un
bloc, vous devez vous assurer de l'avoir correctement assemblée. Cela
signifie :

- inclure un blockhash récent avant d'envoyer la transaction
- inclure dans la transaction une instruction de frais de priorité avec des frais de
  priorité compétitifs
- inclure dans la transaction une instruction de limite d'unités de calcul, dont la valeur
  est basée sur l'estimation des unités de calcul requises par la transaction

Vous devriez également envisager d'autres outils, comme les Jito Bundles, pour augmenter les
chances que votre transaction soit incluse dans un bloc. Examinons ces outils
plus en détail.

### Configuration de l'envoi des transactions

Lorsque vous envoyez des transactions sur Mainnet, configurez ces paramètres pour obtenir des
taux d'inclusion optimaux :

**Gestion du blockhash :**

- Récupérez-le avec le niveau de commitment `confirmed`
- Conservez la valeur `lastValidBlockHeight` renvoyée par `getLatestBlockhash` : elle vous indique
  quand votre transaction expire
- Les blockhashes expirent après une durée définie par le protocole, en fonction de la durée
  du slot.

**Options d'envoi :**

- `maxRetries: 0` — Désactive les nouvelles tentatives automatiques du RPC. Gérez-les vous-même afin
  de pouvoir actualiser le blockhash si nécessaire.
- `skipPreflight: true` — Ignore la simulation avant l'envoi. Utilisez cette option lorsque vous avez
  déjà validé la transaction et que vous souhaitez la latence la plus faible. Laissez-la à `false`
  pendant le développement pour détecter les erreurs au plus tôt.

```typescript
import { createSolanaRpc } from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);

// 1. Get blockhash with confirmed commitment
const { value: latestBlockhash } = await rpc
  .getLatestBlockhash({ commitment: "confirmed" })
  .send();

// 2. Build and sign your transaction with the blockhash
// ... (transaction building code)

// 3. Send with production settings
const signature = await rpc
  .sendTransaction(encodedTransaction, {
    encoding: "base64",
    maxRetries: 0n, // Handle retries yourself
    skipPreflight: true, // Skip simulation for speed (use false during dev)
    preflightCommitment: "confirmed"
  })
  .send();

// 4. Track expiration using lastValidBlockHeight
const { lastValidBlockHeight } = latestBlockhash;
// Stop retrying when current block height exceeds lastValidBlockHeight
```

### Utiliser les frais de priorité

Chaque transaction Solana nécessite des frais de transaction, payés en SOL. Les frais
de transaction se composent de deux parties : les frais de base et les frais de priorité. Les frais de base
rémunèrent les validators pour le traitement de la transaction. Les frais de priorité sont des frais
facultatifs, qui augmentent les chances que le leader actuel traite votre
transaction. Pensez-y comme à une livraison express : vous payez plus cher pour une livraison plus rapide et
plus fiable.

**Fonctionnement des frais :**

```
Total fee = Base fee (5,000 lamports per signature) + Priority fee
Priority fee (legacy/v0) = ceil(compute_unit_price * compute_unit_limit / 1,000,000) lamports
Priority fee (v1 only) = Absolute total in lamports set in the message config
```

**Coûts réels :**

- Simple transfert d'USDC : ~0,001-0,005 $ dans des conditions normales
- En cas de congestion : ~0,01-0,05 $
- Pic de congestion : les frais peuvent grimper encore plus haut

**Exemple d'implémentation :**

Le package
[`@solana-program/compute-budget`](https://github.com/solana-program/compute-budget)
fournit une fonction utilitaire permettant de mettre à jour ou d'ajouter facilement à une transaction l'instruction de
prix de l'unité de calcul (en micro-lamports).

```typescript
import { updateOrAppendSetComputeUnitPriceInstruction } from "@solana-program/compute-budget";

const tx = pipe(
  createTransactionMessage({ version: 0 }),
  (m) => setTransactionMessageFeePayerSigner(payer, m),
  (m) => setTransactionMessageLifetimeUsingBlockhash(latestBlockhash, m),
  (m) => appendTransactionMessageInstructions([myInstructions], m),
  (m) => updateOrAppendSetComputeUnitPriceInstruction(1000n as MicroLamports, m)
);
```

**Obtenir des estimations de frais :** la plupart des fournisseurs RPC proposent des API de frais de priorité :

- [API Helius Priority Fee](https://docs.helius.dev/solana-apis/priority-fee-api)
- [Module complémentaire QuickNode Priority Fee](https://marketplace.quicknode.com/add-on/solana-priority-fee)
- [API Triton Priority Fees](https://docs.triton.one/chains/solana/improved-priority-fees-api)

Pour connaître en détail le fonctionnement des frais, consultez [Frais de transaction](/docs/core/fees) et notre
guide :
[Comment ajouter des frais de priorité à une transaction](https://solana.com/developers/cookbook/transactions/add-priority-fees).

### Optimiser les unités de calcul

Sur Solana, le calcul se mesure en unités de calcul (CU), qui sont une estimation approximative
de la quantité de travail effectuée par le programme. Les limites de calcul actuelles sont de 50 millions
de CU par bloc et de 1,4 million de CU par transaction. Lorsque vous soumettez une
transaction, vous devez estimer la quantité de calcul qui sera utilisée et
définir la limite d'unités de calcul en conséquence : il s'agit en fait de demander quelle part
de la capacité totale doit être réservée à votre transaction. En
pratique, cela signifie qu'estimer correctement les unités de calcul requises par votre
transaction est essentiel pour qu'elle soit incluse dans un bloc (et
important pour gérer vos frais de priorité). Les limites de calcul par transaction et par bloc sont déterminées
par le protocole.

L'API JSON RPC de Solana dispose d'une
méthode [`simulatetransaction`](/docs/rpc/http/simulatetransaction) qui peut être
utilisée pour estimer les unités de calcul requises par une transaction, y compris
une estimation des unités de calcul qui seront utilisées.
[`@solana/kit`](https://github.com/anza-xyz/kit) fournit des fonctions utilitaires qui
estiment les limites de ressources d'une transaction et les appliquent au message en une seule étape
(en s'appuyant sur la méthode `simulatetransaction`). Pour les transactions
de version 1, ces fonctions estiment également la limite de taille des données des comptes chargés.

```ts
import {
  estimateResourceLimitsFactory,
  estimateAndSetResourceLimitsFactory
} from "@solana/kit";

const estimateResourceLimits = estimateResourceLimitsFactory({ rpc });
const estimateAndSetResourceLimits = estimateAndSetResourceLimitsFactory(
  estimateResourceLimits
);
const txWithResourceLimits = await estimateAndSetResourceLimits(tx);
```

<Callout type="info">
  Si vous créez et envoyez des transactions avec un client à plugins kit, vous n'avez généralement
  pas besoin de cette étape : le client ajoute pour vous les instructions de budget de calcul
  lors de l'envoi (`.sendTransaction()`). Le flux manuel ci-dessus est destiné au cas où vous
  assemblez directement les transactions avec `@solana/kit`.
</Callout>

En production, si vous répétez plusieurs fois le même type de transaction,
envisagez de mettre en cache l'estimation de calcul pour ce type de transaction afin
d'éviter le surcoût lié à l'estimation des unités de calcul à chaque fois.

### Jito Bundles

Les Jito Bundles sont un outil permettant de gérer l'exécution atomique de plusieurs transactions.
Pour cela, on envoie plusieurs transactions au réseau Jito avec un
pourboire. Les pourboires peuvent servir à inciter le réseau Jito à inclure vos
transactions dans un bloc.

**Ressources :**

### Stratégies de nouvelle tentative

Les transactions peuvent échouer pour de nombreuses raisons. Contrairement aux API de paiement traditionnelles qui
renvoient immédiatement un succès ou un échec, les transactions blockchain nécessitent un suivi
de la confirmation.

**Concepts clés :**

- **Expiration du blockhash** : Expiration du blockhash : les blockhashes des transactions restent
  valides pendant 150 slots (environ 30 secondes avec des slots de 200 ms). La durée
  d'expiration réelle peut varier en fonction de la vitesse de production des blocs. Utilisez
  lastValidBlockHeight pour déterminer quand un blockhash a expiré.
- **Idempotence** : une même transaction signée produit toujours la même
  signature, de sorte que la soumettre à nouveau est sans risque
- **Backoff exponentiel** : évitez de saturer le réseau avec des nouvelles tentatives rapprochées

```typescript
import {
  createSolanaRpc,
  createSolanaRpcSubscriptions,
  sendAndConfirmTransactionFactory,
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED
} from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);
const rpcSubscriptions = createSolanaRpcSubscriptions(process.env.RPC_WSS_URL!);

const sendAndConfirmTransaction = sendAndConfirmTransactionFactory({
  rpc,
  rpcSubscriptions
});

// Send with automatic confirmation tracking and block height monitoring
try {
  await sendAndConfirmTransaction(signedTransaction, {
    commitment: "confirmed",
    // Optional: abort after 75 seconds
    abortSignal: AbortSignal.timeout(75_000)
  });
} catch (e) {
  if (isSolanaError(e, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED)) {
    // Blockhash expired—rebuild transaction with fresh blockhash and retry
    rebuildAndRetryTransaction(); // implement your own logic for rebuilding and retrying the transaction
  }
  throw e;
}
```

La fonction `sendAndConfirmTransactionFactory` de `@solana/kit` gère automatiquement le polling de
confirmation et le suivi de la hauteur de bloc. Elle lève l'erreur
`SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED` lorsque le blockhash de la transaction expire,
ce qui signale que vous devez reconstruire la transaction avec un nouveau blockhash.

## Gestion des erreurs

Solana Kit fournit des erreurs typées via `isSolanaError()`. Utilisez des codes d'erreur spécifiques
plutôt que la comparaison de chaînes de caractères :

```typescript
import {
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED,
  SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE,
  SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND,
  SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS
} from "@solana/kit";

function handlePaymentError(error: unknown): {
  message: string;
  retryable: boolean;
} {
  // Blockhash expired—rebuild and retry
  if (
    isSolanaError(error, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED) ||
    isSolanaError(error, SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND)
  ) {
    return { message: "Transaction expired—rebuilding", retryable: true };
  }

  // Insufficient SOL for fees
  if (
    isSolanaError(
      error,
      SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE
    )
  ) {
    return { message: "Not enough SOL for fees", retryable: false };
  }

  // Insufficient token balance
  if (
    isSolanaError(error, SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS)
  ) {
    return { message: "Insufficient balance", retryable: false };
  }

  // Unknown error
  console.error("Payment error:", error);
  return { message: "Payment failed—please retry", retryable: true };
}
```

**Codes d'erreur courants :**

| Code d'erreur                   | Cause                 | Résolution                                                                                                 |
| ---------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------- |
| `BLOCK_HEIGHT_EXCEEDED`      | Blockhash expiré     | Reconstruire avec un nouveau blockhash                                                                             |
| `BLOCKHASH_NOT_FOUND`        | Blockhash introuvable   | Reconstruire avec un nouveau blockhash                                                                             |
| `INSUFFICIENT_FUNDS_FOR_FEE` | SOL insuffisants        | Approvisionner le payeur des frais ou utiliser l'[abstraction des frais](/docs/payments/send-payments/payment-processing/fee-abstraction) |
| `INSUFFICIENT_FUNDS`         | Tokens insuffisants     | L'utilisateur doit disposer d'un solde plus élevé                                                                                  |
| `ACCOUNT_NOT_FOUND`          | token account manquant | Créer l'ATA dans la transaction                                                                                |

## Transactions sans frais de gas

Les utilisateurs s'attendent à payer en stablecoins, et non à acquérir des SOL pour les frais de réseau. Les transactions
sans frais de gas résolvent ce problème, un peu comme les utilisateurs de Venmo ne se soucient pas des frais ACH.
Consultez
[Abstraction des frais](/docs/payments/send-payments/payment-processing/fee-abstraction)
pour une implémentation complète.
