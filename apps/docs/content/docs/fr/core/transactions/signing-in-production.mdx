Une transaction ne s'exécute que si elle porte une
[signature](/docs/core/transactions/transaction-structure#signatures) valide de chaque
signataire requis. Pendant le développement local, vous détenez généralement cette clé sous forme de
[`Keypair`](/developers/cookbook/wallets/create-keypair) et signez directement. En
production, la question importante est différente : **où se trouve la clé privée,
et qui est autorisé à générer une signature avec celle-ci ?**

<Callout type="warn">
  N'intégrez jamais de clés privées dans du code côté client, ne les incluez pas dans un frontend et ne les
  commitez pas dans le contrôle de version. Quiconque obtient une clé prend le contrôle total des
  fonds de ce compte.
</Callout>

## Approches de signature

| Approche                  | Emplacement de la clé                                     | Qui signe                                          | Idéal pour                                                      |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **keypair local**         | Un fichier ou une variable d'environnement sur la machine           | Votre code, directement                                | Développement local, tests, CI                                  |
| **Wallet de navigateur**        | Le wallet de l'utilisateur final (p. ex. Phantom, Solflare)          | L'utilisateur final, à chaque transaction                      | dApps frontend où les utilisateurs signent leurs propres transactions        |
| **KMS / HSM cloud**       | Un service de clés adossé à du matériel (AWS KMS, GCP KMS, Vault) | Votre backend demande une signature au service | Services backend, opérations de trésorerie, environnements réglementés |
| **Wallets managés / MPC** | Fractionnée ou conservée sur l'infrastructure d'un fournisseur   | Le fournisseur cosigne selon votre politique     | Wallets intégrés, workflows d'approbation, conservation institutionnelle   |

Le keypair local est la seule approche qui place le matériel de clé brut au sein de votre
application. Toutes les approches de production gardent la clé dans une infrastructure dédiée
et demandent à cette infrastructure de signer en votre nom.

## Signature côté backend

Lorsqu'un serveur doit signer (paiement des frais, envoi de transactions de programme ou
gestion d'une trésorerie), utilisez un backend de gestion de clés dédié plutôt qu'un
keypair brut. La Solana Foundation maintient [Keychain](/docs/tools/keychain), une
bibliothèque de signature unifiée (Rust, TypeScript, Python et Go) qui expose une seule interface
`SolanaSigner` pour tous les backends du tableau ci-dessus : Memory,
HashiCorp Vault, AWS KMS, GCP KMS, Fireblocks, Privy, Turnkey, CDP, Crossmint,
Dfns, Para, Openfort, Utila et Fordefi.

Comme l'interface est partagée entre les backends, vous pouvez développer en local avec une
clé en mémoire et passer à un backend de production via la configuration, sans
réécrire le code de l'application (les backends qui diffusent la transaction pour vous, comme Crossmint,
sont appelés via un chemin de signature et d'envoi à la place). Keychain est compatible avec
[`@solana/kit`](/docs/clients/official/javascript), le
[SDK Rust](/docs/clients/official/rust), `solders` (Python) et `solana-go` v2
(Go).
