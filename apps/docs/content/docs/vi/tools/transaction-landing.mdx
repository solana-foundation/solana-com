## Hạ tầng RPC

[Endpoint công khai](https://solana.com/docs/references/clusters#solana-public-rpc-endpoints)
(`api.mainnet.solana.com`) bị giới hạn tốc độ và không có SLA. Chúng phù hợp để
phát triển nhưng sẽ thất bại với các luồng thanh toán trên production—giống như
việc chạy một bộ xử lý thanh toán thông qua một API dùng chung không có cam kết
về thời gian hoạt động.

<Callout type="caution" title="Không bao giờ dùng RPC công khai cho production">
  Hãy dùng [nhà cung cấp RPC riêng](https://solana.com/rpc) để truy cập ổn định với độ trễ
  thấp.
</Callout>

Khi chọn nhà cung cấp RPC, hãy tìm những yếu tố sau:

- **Độ tin cậy**: SLA có cam kết thời gian hoạt động (99,9%+)
- **Độ trễ**: Vị trí địa lý gần người dùng của bạn
- **Tính năng**: Các tính năng đưa giao dịch lên chuỗi, indexing, API phí ưu tiên

Để xem danh sách đầy đủ các nhà cung cấp RPC, hãy xem hướng dẫn
[Các nhà cung cấp hạ tầng RPC](https://solana.com/rpc).

### Cấu hình RPC dự phòng

Giống như bất kỳ nhà cung cấp dịch vụ mạng nào, các nhà cung cấp RPC có thể
gặp sự cố ngừng hoạt động hoặc giai đoạn hiệu suất suy giảm. Để đảm bảo ứng
dụng của bạn có khả năng chịu lỗi, bạn nên cấu hình ứng dụng sử dụng nhiều nhà
cung cấp RPC.

[Solana Kit](https://github.com/anza-xyz/kit/tree/main/packages/rpc-transport-http)
cung cấp một thư viện để tùy chỉnh các RPC transport, cho phép bạn xây dựng
RPC client dự phòng của riêng mình. Dưới đây là ví dụ về cách bạn có thể sử dụng
nó để xây dựng một RPC client dự phòng:

```ts
import { RpcTransport } from "@solana/rpc-spec";
import { RpcResponse } from "@solana/rpc-spec-types";
import { createHttpTransport } from "@solana/rpc-transport-http";

// Create a transport for each RPC server
const transports = [
  createHttpTransport({ url: "https://mainnet-beta.my-server-1.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-2.com" }),
  createHttpTransport({ url: "https://mainnet-beta.my-server-3.com" })
];

// Create a wrapper transport that distributes requests to them
let nextTransport = 0;
async function roundRobinTransport<TResponse>(
  ...args: Parameters<RpcTransport>
): Promise<RpcResponse<TResponse>> {
  const transport = transports[nextTransport];
  nextTransport = (nextTransport + 1) % transports.length;
  return await transport(...args);
}
```

Nếu bạn không muốn tự xây dựng công cụ định tuyến, bạn có thể tận dụng dịch vụ
bên thứ ba như [Iron Forge](https://www.ironforge.sanctum.so/) để xử lý việc
định tuyến thay bạn.

## Đưa giao dịch lên chuỗi (Transaction Landing)

Trên Devnet, giao dịch được đưa lên chuỗi khá dễ dàng. Trên Mainnet, bạn phải
cạnh tranh không gian trong block. Để tăng khả năng giao dịch của bạn được đưa
vào một block, bạn cần đảm bảo đã lắp ráp giao dịch đúng cách. Điều này có
nghĩa là:

- thêm một blockhash mới trước khi gửi giao dịch
- thêm một instruction phí ưu tiên vào giao dịch với mức phí ưu tiên có tính
  cạnh tranh
- thêm một instruction giới hạn compute unit vào giao dịch, với giới hạn compute
  unit dựa trên số compute unit ước tính mà giao dịch cần

Ngoài ra, bạn nên cân nhắc các công cụ khác như Jito Bundles để tăng khả năng
giao dịch của bạn được đưa vào một block. Hãy cùng tìm hiểu chi tiết hơn về các
công cụ này.

### Cấu hình gửi giao dịch

Khi gửi giao dịch trên Mainnet, hãy cấu hình các tham số sau để đạt tỷ lệ đưa
giao dịch lên chuỗi tối ưu:

**Quản lý blockhash:**

- Lấy với mức commitment `confirmed`
- Lưu lại `lastValidBlockHeight` do `getLatestBlockhash` trả về—giá trị này cho
  bạn biết khi nào giao dịch hết hạn
- Blockhash hết hạn sau một khoảng thời gian do giao thức quy định, tùy thuộc
  vào độ dài của slot.

**Tùy chọn gửi:**

- `maxRetries: 0` — Tắt tính năng tự động thử lại của RPC. Hãy tự xử lý việc thử
  lại để có thể làm mới blockhash khi cần.
- `skipPreflight: true` — Bỏ qua bước mô phỏng trước khi gửi. Hãy dùng khi bạn đã
  xác thực giao dịch và muốn độ trễ thấp nhất. Hãy giữ giá trị `false` trong
  quá trình phát triển để phát hiện lỗi sớm.

```typescript
import { createSolanaRpc } from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);

// 1. Get blockhash with confirmed commitment
const { value: latestBlockhash } = await rpc
  .getLatestBlockhash({ commitment: "confirmed" })
  .send();

// 2. Build and sign your transaction with the blockhash
// ... (transaction building code)

// 3. Send with production settings
const signature = await rpc
  .sendTransaction(encodedTransaction, {
    encoding: "base64",
    maxRetries: 0n, // Handle retries yourself
    skipPreflight: true, // Skip simulation for speed (use false during dev)
    preflightCommitment: "confirmed"
  })
  .send();

// 4. Track expiration using lastValidBlockHeight
const { lastValidBlockHeight } = latestBlockhash;
// Stop retrying when current block height exceeds lastValidBlockHeight
```

### Sử dụng phí ưu tiên

Mỗi giao dịch Solana đều yêu cầu một khoản phí giao dịch, được trả bằng SOL.
Phí giao dịch được chia thành hai phần: phí cơ bản và phí ưu tiên. Phí cơ bản
bồi hoàn cho các validator khi xử lý giao dịch. Phí ưu tiên là khoản phí tùy
chọn nhằm tăng khả năng leader hiện tại sẽ xử lý giao dịch của bạn. Hãy hình
dung nó giống như giao hàng nhanh: bạn trả nhiều hơn để được giao nhanh và đáng
tin cậy hơn.

**Cách phí hoạt động:**

```
Total fee = Base fee (5,000 lamports per signature) + Priority fee
Priority fee (legacy/v0) = ceil(compute_unit_price * compute_unit_limit / 1,000,000) lamports
Priority fee (v1 only) = Absolute total in lamports set in the message config
```

**Chi phí thực tế:**

- Chuyển USDC đơn giản: ~$0,001-0,005 trong điều kiện bình thường
- Khi mạng bị nghẽn: ~$0,01-0,05
- Khi nghẽn cao điểm: Có thể tăng vọt cao hơn

**Ví dụ triển khai:**

Package
[`@solana-program/compute-budget`](https://github.com/solana-program/compute-budget)
cung cấp một hàm hỗ trợ để dễ dàng cập nhật hoặc thêm instruction giá compute
unit (tính bằng micro-lamport) vào một giao dịch.

```typescript
import { updateOrAppendSetComputeUnitPriceInstruction } from "@solana-program/compute-budget";

const tx = pipe(
  createTransactionMessage({ version: 0 }),
  (m) => setTransactionMessageFeePayerSigner(payer, m),
  (m) => setTransactionMessageLifetimeUsingBlockhash(latestBlockhash, m),
  (m) => appendTransactionMessageInstructions([myInstructions], m),
  (m) => updateOrAppendSetComputeUnitPriceInstruction(1000n as MicroLamports, m)
);
```

**Lấy ước tính phí:** Hầu hết các nhà cung cấp RPC đều cung cấp API phí ưu tiên:

- [Helius Priority Fee API](https://docs.helius.dev/solana-apis/priority-fee-api)
- [QuickNode Priority Fee Add-on](https://marketplace.quicknode.com/add-on/solana-priority-fee)
- [Triton Priority Fees API](https://docs.triton.one/chains/solana/improved-priority-fees-api)

Để biết đầy đủ cơ chế hoạt động của phí, hãy xem [Phí giao dịch](/docs/core/fees) và
hướng dẫn của chúng tôi:
[Cách thêm phí ưu tiên vào giao dịch](https://solana.com/developers/cookbook/transactions/add-priority-fees).

### Tối ưu hóa Compute Unit

Tài nguyên tính toán trên Solana được đo bằng compute unit (CU), là ước tính
khái quát về lượng công việc mà chương trình thực hiện. Giới hạn tính toán hiện
nay là 50 triệu CU mỗi block và 1,4 triệu CU mỗi giao dịch. Khi gửi một giao
dịch, bạn cần ước tính lượng tính toán sẽ được sử dụng và đặt giới hạn compute
unit tương ứng - về bản chất đây là yêu cầu về phần dung lượng trong tổng dung
lượng cần được dành riêng cho giao dịch của bạn. Trên thực tế, điều này có
nghĩa là việc ước tính chính xác số compute unit mà giao dịch cần là yếu tố then
chốt để giao dịch được đưa vào một block (và cũng quan trọng để quản lý phí ưu
tiên của bạn). Giới hạn tính toán của giao dịch và của block do giao thức quy
định.

Solana JSON RPC API có phương thức
[`simulatetransaction`](/docs/rpc/http/simulatetransaction) có thể được dùng
để ước tính số compute unit cần cho một giao dịch, bao gồm một ước tính về số
compute unit sẽ được sử dụng.
[`@solana/kit`](https://github.com/anza-xyz/kit) cung cấp các hàm hỗ trợ giúp
ước tính giới hạn tài nguyên của giao dịch và đặt chúng vào message chỉ trong
một bước (sử dụng phương thức `simulatetransaction` ở bên dưới). Đối với các
giao dịch phiên bản 1, các hàm hỗ trợ này cũng ước tính giới hạn kích thước dữ
liệu của các account được tải.

```ts
import {
  estimateResourceLimitsFactory,
  estimateAndSetResourceLimitsFactory
} from "@solana/kit";

const estimateResourceLimits = estimateResourceLimitsFactory({ rpc });
const estimateAndSetResourceLimits = estimateAndSetResourceLimitsFactory(
  estimateResourceLimits
);
const txWithResourceLimits = await estimateAndSetResourceLimits(tx);
```

<Callout type="info">
  Nếu bạn xây dựng và gửi giao dịch bằng một kit plugin client, thông thường bạn
  không cần bước này — client sẽ tự thêm các instruction compute budget cho bạn
  khi gửi (`.sendTransaction()`). Quy trình thủ công ở trên dành cho trường hợp
  bạn lắp ráp giao dịch trực tiếp bằng `@solana/kit`.
</Callout>

Trên production, nếu bạn lặp lại cùng một loại giao dịch nhiều lần, hãy cân
nhắc lưu cache ước tính compute cho loại giao dịch đó để tránh chi phí phát sinh
từ việc ước tính compute unit mỗi lần.

### Jito Bundles

Jito bundle là công cụ để quản lý việc thực thi nguyên tử (atomic) của nhiều
giao dịch. Điều này đạt được bằng cách gửi nhiều giao dịch đến mạng Jito kèm
theo một khoản tip. Tip có thể được dùng để khuyến khích mạng Jito đưa các giao
dịch của bạn vào một block.

### Chiến lược thử lại

Giao dịch có thể thất bại vì nhiều lý do. Không giống các API thanh toán truyền
thống trả về thành công/thất bại ngay lập tức, giao dịch blockchain đòi hỏi
phải theo dõi quá trình xác nhận.

**Các khái niệm chính:**

- **Hết hạn blockhash**: Blockhash của giao dịch có hiệu lực trong 150 slot
  (khoảng 30 giây với thời gian mỗi slot là 200ms). Thời gian hết hạn thực tế
  có thể thay đổi tùy theo tốc độ tạo block. Hãy dùng lastValidBlockHeight để
  xác định khi nào một blockhash đã hết hạn.
- **Tính idempotent**: Cùng một giao dịch đã ký luôn tạo ra cùng một chữ ký—nên
  việc gửi lại là an toàn
- **Exponential backoff**: Tránh làm quá tải mạng bằng các lần thử lại dồn dập

```typescript
import {
  createSolanaRpc,
  createSolanaRpcSubscriptions,
  sendAndConfirmTransactionFactory,
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED
} from "@solana/kit";

const rpc = createSolanaRpc(process.env.RPC_URL!);
const rpcSubscriptions = createSolanaRpcSubscriptions(process.env.RPC_WSS_URL!);

const sendAndConfirmTransaction = sendAndConfirmTransactionFactory({
  rpc,
  rpcSubscriptions
});

// Send with automatic confirmation tracking and block height monitoring
try {
  await sendAndConfirmTransaction(signedTransaction, {
    commitment: "confirmed",
    // Optional: abort after 75 seconds
    abortSignal: AbortSignal.timeout(75_000)
  });
} catch (e) {
  if (isSolanaError(e, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED)) {
    // Blockhash expired—rebuild transaction with fresh blockhash and retry
    rebuildAndRetryTransaction(); // implement your own logic for rebuilding and retrying the transaction
  }
  throw e;
}
```

`sendAndConfirmTransactionFactory` từ `@solana/kit` tự động xử lý việc polling
xác nhận và theo dõi block height. Nó ném ra
`SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED` khi blockhash của giao dịch hết hạn,
báo hiệu rằng bạn cần xây dựng lại giao dịch với một blockhash mới.

## Xử lý lỗi

Solana Kit cung cấp các lỗi có kiểu thông qua `isSolanaError()`. Hãy sử dụng
các mã lỗi cụ thể thay vì so khớp chuỗi:

```typescript
import {
  isSolanaError,
  SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED,
  SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE,
  SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND,
  SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS
} from "@solana/kit";

function handlePaymentError(error: unknown): {
  message: string;
  retryable: boolean;
} {
  // Blockhash expired—rebuild and retry
  if (
    isSolanaError(error, SOLANA_ERROR__BLOCK_HEIGHT_EXCEEDED) ||
    isSolanaError(error, SOLANA_ERROR__TRANSACTION_ERROR__BLOCKHASH_NOT_FOUND)
  ) {
    return { message: "Transaction expired—rebuilding", retryable: true };
  }

  // Insufficient SOL for fees
  if (
    isSolanaError(
      error,
      SOLANA_ERROR__TRANSACTION_ERROR__INSUFFICIENT_FUNDS_FOR_FEE
    )
  ) {
    return { message: "Not enough SOL for fees", retryable: false };
  }

  // Insufficient token balance
  if (
    isSolanaError(error, SOLANA_ERROR__INSTRUCTION_ERROR__INSUFFICIENT_FUNDS)
  ) {
    return { message: "Insufficient balance", retryable: false };
  }

  // Unknown error
  console.error("Payment error:", error);
  return { message: "Payment failed—please retry", retryable: true };
}
```

**Các mã lỗi thường gặp:**

| Mã lỗi                   | Nguyên nhân                 | Cách khắc phục                                                                                                 |
| ---------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------- |
| `BLOCK_HEIGHT_EXCEEDED`      | Blockhash đã hết hạn     | Xây dựng lại với blockhash mới                                                                             |
| `BLOCKHASH_NOT_FOUND`        | Không tìm thấy blockhash   | Xây dựng lại với blockhash mới                                                                             |
| `INSUFFICIENT_FUNDS_FOR_FEE` | Không đủ SOL        | Nạp tiền cho fee payer hoặc dùng [fee abstraction](/docs/payments/send-payments/payment-processing/fee-abstraction) |
| `INSUFFICIENT_FUNDS`         | Không đủ token     | Người dùng cần có thêm số dư                                                                                  |
| `ACCOUNT_NOT_FOUND`          | Thiếu token account | Tạo ATA trong giao dịch                                                                                |

## Giao dịch không phí gas (Gasless)

Người dùng muốn thanh toán bằng stablecoin, chứ không phải đi mua SOL để trả
phí mạng. Giao dịch gasless giải quyết vấn đề này—tương tự như cách người dùng
Venmo không phải nghĩ đến phí ACH. Xem
[Fee Abstraction](/docs/payments/send-payments/payment-processing/fee-abstraction)
để biết cách triển khai đầy đủ.
