이 가이드는 `solana-keychain` 라이브러리에 새로운 키 관리 솔루션을 통합하고자
하는 지갑 서비스 제공자와 개발자를 위한 것입니다. 귀하의 서명자 구현을
추가함으로써, 개발자들이 통합된 인터페이스를 통해 안전한 솔라나 트랜잭션 서명을
위해 귀하의 서비스를 사용할 수 있게 됩니다.

Keychain은 Rust, TypeScript, Python, Go 구현체를 동등한 수준으로 유지합니다.
PR에 네 가지가 모두 포함되어 있으면 가장 좋습니다. 하나만 기여하셔도 괜찮지만,
서명자가 릴리스에 포함되기 전에 나머지 구현도 필요하다는 점을 염두에 두세요.

_Claude Code를 사용 중이신가요? 저장소의
[`add-signer-ci` 스킬](https://github.com/solana-foundation/solana-keychain/tree/main/.claude/skills/add-signer-ci)이
포크 PR로 기여된 새 서명자의 CI 워크플로를 설정해 줍니다._

## 아키텍처 개요

이 라이브러리는 `src/traits.rs`에 정의된 트레이트 기반 아키텍처를 사용합니다. 모든
서명자는 `SolanaSigner` 기본 트레이트(`pubkey`, `sign_message`,
`is_available`)를 구현하며, 여기에 제공자의 형태에 맞는 기능 트레이트를 정확히 하나 더 구현합니다:

- `TransactionSigner`(`sign_transaction`): 제공자가 호출자의
  바이트에 서명하고, 브로드캐스트는 호출자가 수행합니다. 대부분의 백엔드가 여기에 해당합니다.
- `ModifyingSigner`(`modify_and_sign_transaction`): 제공자가
  트랜잭션을 재구성한 뒤 브로드캐스트 없이 서명합니다.
- `SendingSigner`(`sign_and_send_transaction`): 제공자가 서버 측에서
  서명하고 브로드캐스트합니다.

또한 이 라이브러리는 모든 구현을 감싸는 통합 `Signer` 열거형을 제공하여
런타임에 서명 백엔드를 선택할 수 있습니다. 이 열거형은 기본 트레이트만 구현하며,
기능은 `as_transaction_signer()`, `as_modifying_signer()`,
`as_sending_signer()`를 통해 접근합니다.

## 빠른 통합 체크리스트

- 구현과 함께 서명자 모듈 생성
- `SolanaSigner` 기본 트레이트(`pubkey`, `sign_message`,
  `is_available`)와 제공자의 형태에 맞는 기능 트레이트 하나(대개
  `TransactionSigner`)를 구현합니다
- `Cargo.toml`에 feature 플래그를 추가합니다. 서명자가 reqwest를 사용한다면
  내부용 `_remote` 마커도 포함합니다
- `src/lib.rs`의 `Signer` 열거형을 업데이트합니다(variant, `dispatch_signer!` arm,
  그리고 사용자의 형태에 맞는 기능 접근자의 arm)
- HTTP 클라이언트에 HTTPS 강제 적용 및 타임아웃 설정
- 메시지 바이트에 서명하고, 반환된 서명을 첨부하기 전에 검증합니다
- 포괄적인 단위 테스트를 추가합니다(wiremock 기반, 해당 모듈 내)
- 통합 테스트 파일을 추가하고 `.env.example`을 업데이트합니다
- TypeScript, Python, Go 구현을 추가합니다
- 문서 업데이트
- CI 워크플로 업데이트(유지 관리자와 조율하세요.
  [CI 워크플로 업데이트](#ci-workflow-updates-fork-prs) 참조)
- PR 제출

## 2단계: 서명자 구조체 정의

`src/your_service/mod.rs`에서 서명자 구조체를 정의하세요:

```rust
//! YourService API signer integration

use crate::sdk_adapter::{Pubkey, Signature, VersionedTransaction};
use crate::{error::SignerError, traits::SolanaSigner};
use std::str::FromStr;

/// YourService-based signer using YourService's API
#[derive(Clone)]
pub struct YourServiceSigner {
    api_key: String,
    api_secret: String,
    wallet_id: String,
    api_base_url: String,
    client: reqwest::Client,
    public_key: Pubkey,

impl std::fmt::Debug for YourServiceSigner {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("YourServiceSigner")
            .field("public_key", &self.public_key)
            .finish_non_exhaustive()
    }
}
```

## 3단계: 생성자 및 헬퍼 메서드 구현

원격 서명자는 **반드시** HTTPS를 강제 적용하고 HTTP 타임아웃을 설정해야 합니다.
타임아웃 설정을 위해 공유 `HttpClientConfig` 구조체를 사용하세요.

```rust
use crate::http_client_config::HttpClientConfig;

impl YourServiceSigner {
    pub fn new(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
        http_config: Option<HttpClientConfig>,
    ) -> Result<Self, SignerError> {
        let pubkey = Pubkey::from_str(&public_key)
            .map_err(|e| SignerError::InvalidPublicKey(format!("Invalid public key: {e}")))?;

        let http = http_config.unwrap_or_default();
        let builder = reqwest::Client::builder()
            .timeout(http.resolved_request_timeout())
            .connect_timeout(http.resolved_connect_timeout());

        // Enforce HTTPS in production; wiremock uses HTTP in tests
        #[cfg(not(test))]
        let builder = builder.https_only(true);

        let client = builder.build().map_err(|e| {
            SignerError::ConfigError(format!("Failed to build HTTP client: {e}"))
        })?;

        Ok(Self {
            api_key,
            api_secret,
            wallet_id,
            api_base_url: "https://api.yourservice.com/v1".to_string(),
            client,
            public_key: pubkey,
        })
    }

    /// Sign raw bytes using your service's API
    async fn sign(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let encoded_message = base64::engine::general_purpose::STANDARD.encode(message);

        let url = format!("{}/sign", self.api_base_url);
        let response = self
            .client
            .post(&url)
            .header("Authorization", format!("Bearer {}", self.api_key))
            .json(&serde_json::json!({
                "wallet_id": self.wallet_id,
                "message": encoded_message,
            }))
            .send()
            .await?;

        // Use generic error messages: never expose raw API response text
        if !response.status().is_success() {
            let status = response.status().as_u16();
            return Err(SignerError::remote_api(format!(
                "YourService API returned status {status}"
            )));
        }

        // Parse response: always use map_err, never .expect() or .unwrap()
        let response_data: SignResponse = response
            .json()
            .await
            .map_err(|e| SignerError::SerializationError(format!("Failed to parse response: {e}")))?;
        let sig_bytes = base64::engine::general_purpose::STANDARD
            .decode(&response_data.signature)
            .map_err(|e| SignerError::SerializationError(format!("Failed to decode signature: {e}")))?;

        let sig_array: [u8; 64] = sig_bytes
            .try_into()
            .map_err(|_| SignerError::SigningFailed("Invalid signature length".to_string()))?;

        Ok(Signature::from(sig_array))
    }
}
```

## 4단계: 서명자 트레이트 구현

`SolanaSigner` 기본 트레이트에는 비동기 메서드 2개(`sign_message`,
`is_available`)와 `pubkey()`가 있습니다. 트랜잭션 서명은 기능 트레이트에서 처리하며,
대부분의 제공자는 `TransactionSigner`를 구현합니다. 이 트레이트의 `sign_transaction`은
`SignTransactionResult`(트랜잭션이 완전히 서명되었는지 부분적으로 서명되었는지를
나타내는 태그가 지정된 열거형)를 반환합니다.

전체 와이어 트랜잭션이 아닌 메시지 바이트에 서명하고, 첨부하기 전에 제공자의
서명을 해당 바이트에 대해 검증하세요. 서명과 직렬화에는 공용
`TransactionUtil` 헬퍼를 사용합니다.

```rust
use crate::signature_util::verify_or_reject;
use crate::traits::{SignTransactionResult, TransactionSigner};
use crate::transaction_util::TransactionUtil;

#[async_trait::async_trait]
impl SolanaSigner for YourServiceSigner {
    fn pubkey(&self) -> Pubkey {
        self.public_key
    }

    async fn sign_message(&self, message: &[u8]) -> Result<Signature, SignerError> {
        let signature = self.sign(message).await?;
        verify_or_reject(&signature, &self.public_key, message)?;
        Ok(signature)
    }

    async fn is_available(&self) -> bool {
        let url = format!("{}/health", self.api_base_url);
        self.client
            .get(&url)
            .send()
            .await
            .map(|r| r.status().is_success())
            .unwrap_or(false)
    }
}

#[async_trait::async_trait]
impl TransactionSigner for YourServiceSigner {
    async fn sign_transaction(
        &self,
        tx: &mut VersionedTransaction,
    ) -> Result<SignTransactionResult, SignerError> {
        let message = tx.message.serialize();
        let signature = self.sign(&message).await?;
        verify_or_reject(&signature, &self.public_key, &message)?;

        TransactionUtil::add_signature_to_transaction(tx, &self.public_key, signature)?;
        let serialized = TransactionUtil::serialize_transaction(tx)?;
        Ok(TransactionUtil::classify_signed_transaction(
            tx,
            (serialized, signature),
        ))
    }
}
```

제공자가 서명 전에 트랜잭션을 재구성한다면 대신 `ModifyingSigner`를 구현하고,
호출자의 트랜잭션을 제공자의 바이트로 통째로 교체하세요. 서버 측에서 브로드캐스트한다면
`SendingSigner`를 구현하고 호출자의 트랜잭션은 그대로 두세요. 제공자가 지원할 수 없는
기능 트레이트는 절대 구현하지 마세요.

## 6단계: 기능 플래그 추가

`Cargo.toml`을 업데이트하여 서명자를 선택적 feature로 추가합니다. 원격 백엔드는
내부용 `_remote` 마커를 포함해야 하며, 이 마커는 `src/error.rs`의
`From<reqwest::Error>` impl을 제어합니다. 마커가 없으면 사용자의 feature만 활성화된 경우
reqwest 호출에 대한 `?`가 컴파일되지 않습니다.

```toml
[features]
default = ["memory", "sdk-v2"]
memory = []
vault = ["dep:reqwest", "_remote"]
privy = ["dep:reqwest", "dep:p256", "_remote"]
your_service = ["dep:reqwest", "_remote"]  # Add your feature
all = ["memory", "vault", "privy", "...", "your_service"]  # Update all
```

## 7단계: 서명자 열거형 업데이트

`src/lib.rs`에 서명자를 추가합니다. 기본 `SolanaSigner` impl은
`dispatch_signer!` 매크로를 통해 디스패치하므로 그곳에 arm을 하나 추가하세요. 기능 접근은
`as_transaction_signer()`, `as_modifying_signer()`, `as_sending_signer()`
접근자에 있습니다. 사용자의 기능 트레이트와 일치하는 접근자에 `Some(s)` arm을 추가하세요
(전송 또는 수정 백엔드의 경우 `as_transaction_signer()`에는 `None` arm을 추가합니다).

```rust
// Add feature-gated module
#[cfg(feature = "your_service")]
pub mod your_service;

// Re-export your signer type
#[cfg(feature = "your_service")]
pub use your_service::YourServiceSigner;

// Add to Signer enum
#[derive(Debug)]
pub enum Signer {
    #[cfg(feature = "memory")]
    Memory(MemorySigner),

    // ... existing variants

    #[cfg(feature = "your_service")]
    YourService(YourServiceSigner),  // Add your variant
}

// Add constructor method
impl Signer {
    #[cfg(feature = "your_service")]
    pub fn from_your_service(
        api_key: String,
        api_secret: String,
        wallet_id: String,
        public_key: String,
    ) -> Result<Self, SignerError> {
        Ok(Self::YourService(YourServiceSigner::new(
            api_key,
            api_secret,
            wallet_id,
            public_key,
            None, // uses default HttpClientConfig
        )?))
    }
}

// Update the dispatch macro: the base SolanaSigner impl uses it for
// pubkey, sign_message and is_available
macro_rules! dispatch_signer {
    ($self:ident, $signer:pat => $body:expr) => {
        match $self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService($signer) => $body,
        }
    };
}

// Add your arm to the capability accessor matching your shape
impl Signer {
    pub fn as_transaction_signer(&self) -> Option<&dyn TransactionSigner> {
        match self {
            // ... existing variants
            #[cfg(feature = "your_service")]
            Signer::YourService(s) => Some(s),
        }
    }
}
```

## 8단계: 포괄적인 테스트 추가

모듈에 테스트를 추가하세요 (`src/your_service/mod.rs` 하단):

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use solana_sdk::{signature::Keypair, signer::Signer};
    use wiremock::{
        matchers::{header, method, path},
        Mock, MockServer, ResponseTemplate,
    };

    #[tokio::test]
    async fn test_new() {
        let keypair = Keypair::new();
        let signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        );
        assert!(signer.is_ok());
    }

    #[tokio::test]
    async fn test_sign_message() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();
        let message = b"test message";
        let signature = keypair.sign_message(message);

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(200).set_body_json(serde_json::json!({
                "signature": base64::engine::general_purpose::STANDARD.encode(signature.as_ref())
            })))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "test-key".to_string(),
            "test-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(message).await;
        assert!(result.is_ok());
    }

    #[tokio::test]
    async fn test_sign_unauthorized() {
        let mock_server = MockServer::start().await;
        let keypair = Keypair::new();

        Mock::given(method("POST"))
            .and(path("/sign"))
            .respond_with(ResponseTemplate::new(401))
            .expect(1)
            .mount(&mock_server)
            .await;

        let mut signer = YourServiceSigner::new(
            "bad-key".to_string(),
            "bad-secret".to_string(),
            "test-wallet".to_string(),
            keypair.pubkey().to_string(),
            None,
        ).unwrap();
        signer.api_base_url = mock_server.uri();

        let result = signer.sign_message(b"test").await;
        assert!(result.is_err());
    }
}
```

서명 검증 실패 케이스도 다루세요. 서명이 검증되지 않는 모의 응답은
반드시 오류를 반환해야 합니다.

## 9단계: 통합 테스트 추가

`rust/src/tests/test_<name>_integration.rs`를 생성합니다. 통합 테스트는
(wiremock이 아닌) 실제 서비스 API를 대상으로 실행되며 `integration-tests` feature로
제한됩니다. 각 파일에는 다음이 필요합니다:

- 환경 변수 이름용 `pub const` 선언
- `dotenvy`를 통해 환경 변수를 읽는 `get_signer()` 헬퍼
- 세 개의 테스트 함수: `test_<name>_sign_message`,
  `test_<name>_sign_transaction`, `test_<name>_is_available`
- Feature 게이트: 모듈에는 `#[cfg(feature = "your_service")]`, 각 테스트에는
  `#[cfg(feature = "integration-tests")]`

완전한 참고 예시는 `rust/src/tests/test_para_integration.rs`를 확인하고,
`rust/src/tests/mod.rs`에 모듈을 선언하세요:

```rust
pub mod test_your_service_integration;
```

## 10단계: 환경 변수 업데이트

기존 패턴에 따라 루트의 `.env.example`에 서명자의 환경 변수를 추가하세요:

```bash
# YourService Configuration (for SIGNER_TYPE=your_service)
YOUR_SERVICE_API_KEY=your-api-key
```

필수 변수는 자리 표시자 값과 함께 먼저 나열하고, 선택 변수는 기본값과 함께 주석 처리하세요.
통합 테스트에서 사용하는 모든 환경 변수는 `.env.example`에 있어야 하며,
TypeScript, Python, Go 테스트 스위트도 동일한 이름을 사용합니다.

## 11단계: 문서 업데이트

README.md의 지원되는 백엔드 표에 서명자를 추가하세요:

| 백엔드         | 사용 사례                                       | 기능 플래그   |
| --------------- | ---------------------------------------------- | -------------- |
| **Memory**      | 로컬 keypair, 개발, 테스팅           | `memory`       |
| **Vault**       | HashiCorp Vault를 사용한 엔터프라이즈 키 관리 | `vault`        |
| **Privy**       | Privy 인프라를 사용한 임베디드 지갑     | `privy`        |
| **Turnkey**     | Turnkey를 통한 비수탁형 키 관리       | `turnkey`      |
| **YourService** | 귀하의 서비스에 대한 간단한 설명              | `your_service` |

각 언어의 README에 있는 서명자 기능 표에도 백엔드를 추가하세요. 사용 예시를 추가합니다:

```rust
use solana_keychain::{Signer, SolanaSigner};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let signer = Signer::from_your_service(
        "your-api-key".to_string(),
        "your-api-secret".to_string(),
        "your-wallet-id".to_string(),
        "your-public-key".to_string(),
    )?;

    let pubkey = signer.pubkey();
    println!("Public key: {}", pubkey);

    Ok(())
}
```

### 전송 서명자

제공자가 트랜잭션을 재구성하거나 서버 측에서 브로드캐스트한다면, 그 서명을 호출자의

- `signAndSendTransactions()`를 구현하고 `signTransactions`는 노출하지 **마세요**

- `config?.abortSignal`을 준수하세요. 제공자가 생성 요청을 수락한 이후에는

각 Go 백엔드는 `go/signers/yoursigner/` 경로에 있는 독립 모듈이며, 모듈 경로는
`github.com/solana-foundation/solana-keychain/go/signers/yoursigner/v2`입니다. 참고용으로

- 오류는 `core.NewSignerError` / `core.WrapSignerError`와 `core.CodeSigningFailed` 같은

- 단위 테스트는 `httptest`로 작성하고, 통합 테스트는 `integration_test.go`에

## 구현 팁

### 오류 처리

항상 기존 `SignerError` 변형(variant)을 사용하세요. `SignerError`의 `Display`와 `Debug`는 모두
민감 정보가 가려지므로, 메시지는 일반적인 내용으로 유지하고 원본 API 응답 데이터는 절대 포함하지 마세요.
신뢰할 수 없는 API 응답에는 `.expect()` 또는 `.unwrap()`을 절대 사용하지 마세요:

```rust
// Good: uses the constructor with a generic message
return Err(SignerError::remote_api(format!(
    "YourService API returned status {status}"
)));

// Good: converts from standard errors
let bytes = base64::decode(data)
    .map_err(|e| SignerError::SerializationError(format!("Failed to decode: {e}")))?;
```

### 보안 요구 사항

이는 단순한 권장 사항이 아닙니다. 사용자는 이 요구 사항을 신뢰하여 백엔드를 선택합니다. 공급자 때문에
요구 사항 중 하나를 충족할 수 없다면, PR과 리포지토리의 `docs/SECURITY_MODEL.md`에 그 사실을 명시하세요.

- **공급자가 서명한 내용을 검증하세요.** 메시지 바이트를 로컬에서 계산하고, 서명을 첨부하기 전에 서명자에게 요구되는
  위치에서 반환된 서명을 해당 바이트로 검증하세요. 검증에 실패한 서명은 반드시 실패로 처리해야 하며,
  절대 첨부해서는 안 됩니다.
- **공급자가 브로드캐스트하는지 명시하세요.** 공급자가 서버 측에서 실행한다면, 전송(sending) 형태를 구현하고
  체결된 트랜잭션을 식별할 수 있는 서명을 반환하세요. 공급자에 서명 전용 엔드포인트가 없다면,
  호출자 몰래 제출하지 말고 백엔드를 전송 전용으로 만드세요.
- **서명이 포함하지 않는 트랜잭션을 호출자가 갖게 두지 마세요.**
  트랜잭션을 재작성하는 공급자는 자신의 바이트에 서명합니다. 호출자의 트랜잭션을 그대로 두거나(브로드캐스트를
  공급자가 관리하는 경우), 수정(modifying) 형태를 사용해 공급자의 바이트로 전체를 교체하세요.
- **브로드캐스트 불확실성을 있는 그대로 보고하세요.** 제출 후 발생한 실패라도 트랜잭션이 이미 체결되었을 수 있습니다.
  일반 오류 대신 `BROADCAST_UNCONFIRMED`를 반환하고, 공급자 트랜잭션 ID가 있으면 항상 함께 전달하세요.
  또한 모든 생성 요청에 메시지에서 파생한 멱등성 키를 전송하여, 바이트가 동일한 재전송이 안전하도록 하세요.
- **초기화 전에는 절대 서명하지 마세요.** `init()` 이전의 공개 키에는 `Pubkey::default()`가 아닌
  `Option<Pubkey>`를 사용하고, 먼저 서명을 시도하면 구성 오류로 실패 처리하세요.
- 민감한 데이터(개인 키, API 시크릿, 원본 API 응답)는 절대 로그에 남기지 말고,
  민감한 필드를 숨기는 `Debug` 구현을 사용하세요
- HTTPS를 강제하고(`https_only(true)`, wiremock용으로 `#[cfg(not(test))]`로 제한), 요청 및 연결 타임아웃은
  `HttpClientConfig`로 설정하세요(기본값: 30초/5초)
- 중간 키 소재는 `zeroize::Zeroizing<Vec<u8>>`로 제로화(zeroize)하세요

### 모의 객체를 사용한 테스트

HTTP API 모킹에는 `wiremock`를 사용하세요. 오류 메시지 텍스트가 아닌 오류 유형에
대해서만 검증하세요:

```rust
#[cfg(test)]
mod tests {

    #[tokio::test]

        let mock_server = MockServer::start().await;

        Mock::given(method("POST"))
            .respond_with(ResponseTemplate::new(200))
            .mount(&mock_server)
            .await;

        // Use mock_server.uri() as your api_base_url
    }
}
```
