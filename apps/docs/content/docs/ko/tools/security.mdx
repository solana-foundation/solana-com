## 키 관리

- **프론트엔드 코드에 개인 키를 절대 노출하지 마세요.** 백엔드 서명, 하드웨어 지갑, 멀티시그 지갑 또는 키 관리 서비스를 사용하세요.
- **핫 월렛과 콜드 월렛을 분리하세요.** 핫 월렛은 운영용으로, 콜드 월렛은 트레저리용으로 사용합니다.
- **모든 프로덕션 키를 백업하세요.** 암호화된 백업을 여러 안전한 장소에 보관하세요. 키를 분실하면 접근 권한을 영구적으로 잃게 됩니다.
- **devnet과 mainnet에는 서로 다른 키를 사용하세요.** devnet 키를 mainnet 키로 사용해서는 안 됩니다. 환경 기반 설정을 사용하여 각 네트워크에 올바른 키가 로드되도록 하세요.

## 서명 인프라

프로덕션 백엔드 서명에는 [Keychain](/docs/tools/keychain)을 사용하세요. Keychain은 Memory, Vault, Privy, Turnkey, AWS KMS, Fireblocks, GCP KMS, CDP, Para, Dfns, Crossmint, Openfort, Utila 등 여러 키 관리 백엔드를 단일 인터페이스로 추상화한 통합 서명 라이브러리입니다. 이를 통해 로컬에서는 인메모리 키로 개발하고, 애플리케이션 코드를 변경하지 않고도 프로덕션급 백엔드로 전환할 수 있습니다.

어떤 백엔드가 적합한지 잘 모르겠나요? [백엔드 선택하기](/docs/tools/keychain/choosing-a-backend)를 참고하세요. Keychain은 [Rust](https://crates.io/crates/solana-keychain)와 [TypeScript](https://www.npmjs.com/package/@solana/keychain) 모두에서 사용할 수 있습니다.

## RPC 보안

RPC 엔드포인트는 API 키처럼 취급하세요. 프론트엔드 코드에 노출하면 추출되어 악용될 수 있습니다. 백엔드 프록시를 사용하거나, 클라이언트 코드에 번들되지 않는 환경 변수를 사용하세요.

- [QuickNode: 엔드포인트 보안 모범 사례](https://www.quicknode.com/guides/quicknode-products/endpoint-security/endpoint-security-best-practices)
- [Helius: Solana API 키 보호하기: 보안 모범 사례](https://www.helius.dev/docs/rpc/protect-your-keys)

## 모니터링

프로덕션 환경에서 다음 지표를 추적하세요:

| 지표                   | 이유                    |
| ------------------------ | ---------------------- |
| 트랜잭션 성공률 | 문제를 조기에 감지    |
| 컨펌 지연 시간     | 네트워크 상태 모니터링 |
| 우선순위 수수료 지출       | 비용 관리        |
| RPC 오류율           | 제공업체 상태        |

다음 상황에 대한 알림을 설정하세요:

- 트레저리에서 임계값을 초과하는 전송
- 실패한 트랜잭션 비율의 급증
- 비정상적인 수신자 패턴
- RPC 오류율 증가

대규모 실시간 트랜잭션 모니터링은 [인덱싱 가이드](/docs/payments/accept-payments/indexing)를 참고하세요.

## 주소 확인

메인넷에서 모든 토큰과 프로그램에는 정확히 하나의 올바른 주소가 있습니다. USDC나 다른 스테이블코인을 흉내 낸 가짜 토큰은 흔하며, 이름과 심볼은 같지만 민트(mint)가 다릅니다. 애플리케이션에서는 요구 사항에 따라 민트 주소를 하드코딩하거나 허용 목록(allowlist)으로 관리해야 하며, 신뢰할 수 없는 출처에서 동적으로 받아들여서는 안 됩니다.

**환경 기반 설정:** Devnet과 Mainnet은 완전히 다른 토큰 민트를 사용하는 경우가 많습니다. 애플리케이션 설정이 환경별로 올바른 주소를 로드하도록 구성하세요. mainnet 주소를 하드코딩해 두고 테스트 중에 교체하는 것을 잊거나, 더 심하게는 devnet 주소를 프로덕션에 배포하는 일이 없도록 하세요.

일반적인 스테이블코인 민트는 다음과 같습니다:

| 토큰 | 발행사 | 민트 주소                                   |
| ----- | ------ | ---------------------------------------------- |
| USDC  | Circle | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` |
| USDT  | Tether | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` |
| PYUSD | PayPal | `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| USDG  | Paxos  | `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` |

프로그램 주소도 중요합니다. 잘못된 프로그램으로 instruction을 보내면 실패하거나, 더 심각하게는 자금이 되돌릴 수 없이 손실될 수 있습니다. Token Program 주소는 다음과 같습니다:

| 프로그램            | 주소                                       |
| ------------------ | --------------------------------------------- |
| Token Program      | `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Token-2022 Program | `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb` |

올바른 주소를 허용 목록에 등록하면 가짜 토큰으로부터 보호할 수 있지만, 잘못된 _종류_의 계정으로 보내는 것까지 막아주지는 않습니다. 수신자 주소는 지갑, token account, 민트, 프로그램 중 하나일 수 있으며, 각각 다른 처리가 필요합니다. 지갑이 아닌 곳으로 보낸 네이티브 SOL은 송신자의 통제를 벗어나게 됩니다. 민트나 프로그램으로 보내면 완전히 손실되고, token account로 보내면 해당 계정의 소유자만 되찾을 수 있습니다. 이때 사용자에게 경고해 주는 실패한 트랜잭션도 발생하지 않습니다.

<Callout type="warn" title="전송 전에 수신자를 검증하세요">
  전송에 서명하기 전에 모든 수신자 주소의 종류를 분류하세요. 지갑, token account, 민트, 프로그램을 구분하는 전체 의사 결정 트리와 참조 코드는 [주소 검증](/docs/payments/send-payments/verify-address)을 참고하세요.
</Callout>
