---

애플리케이션을 메인넷에 배포하기 전에 다음 항목이 준비되어 있는지 확인하세요.

- 프로그램 ELF 파일 - 일반적으로 `anchor build` 또는
  `cargo-build-sbf`를 실행한 결과물이며 `.so`로 끝납니다
- 프로그램 keypair - 정수 배열이 담긴 JSON 파일

이 섹션에서는 이러한 자산을 어디에서 찾을 수 있고 어떻게 준비하는지
설명합니다.

## ELF 파일 준비하기

ELF 파일에는 컴파일된 바이트코드, 메모리 레이아웃 정보, 그리고 Solana 가상 머신(SVM)이 프로그램을 로드하고 실행하는 방법을 파악하는 데 필요한 메타데이터가 들어 있습니다. ELF 파일은 소스 코드를 컴파일할 때 생성됩니다.

ELF 파일을 생성하려면 Anchor에서는 다음 명령어를 실행하세요.

```bash
anchor build
```

다른 프레임워크에서는 다음 명령어를 실행하세요.

```bash
cargo build-sbf
```

그러면 `target/deploy/<PROGRAM_NAME>.so`와 같은 디렉터리에서
ELF 파일을 찾을 수 있습니다.

ELF 파일이 [sBPFv3](https://www.anza.xyz/blog/migrating-solana-programs-to-sbpfv3)로 컴파일되었다면 프로그램이 준비된 것입니다. 프로그램을
확인하려면 Linux에서 다음 명령어를 실행하세요.

```bash
readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

macOS에서는 다음 명령어를 실행하세요.

```bash
# brew install llvm
$(brew --prefix llvm)/bin/llvm-readelf -h target/deploy/<PROGRAM_NAME>.so | grep Flags:
```

다음과 같은 출력이 보이면 프로그램이 준비된 것입니다.

```
  Flags:                             0x3
```

그렇지 않다면 [여기](https://solana.com/upgrades/sbpfv3-programs)에 링크된
마이그레이션 가이드를 따르세요.

## 프로그램 주소 준비하기

프로그램 주소는 프로그램 인스트럭션을 호출할 때 사용하는 프로그램 ID입니다. 1) 빌드 중에 생성된 프로그램 keypair를 사용하거나, 2) 주소가 원하는 접두사로 시작하는 새 keypair를 그라인딩하거나, 3) 기본 주소와 seed로 계정 주소를 파생할 수 있습니다. 처음 두 가지 방법은 program account에 대해 서명할 수 있는 keypair를 만들어 냅니다. seed로 생성한 계정에는 자체 개인 키가 없으며, 기본 계정이 이를 제어합니다.

### 생성된 keypair 사용하기

기본적으로 `anchor build`와 `cargo build-sbf`는 프로그램 keypair를 다음 위치에 저장합니다.

```text
target/deploy/<PROGRAM_NAME>-keypair.json
```

빌드 디렉터리를 정리하기 전에 이 파일을 백업하세요. keypair에 접근할 수 있는 사람은 누구나 program account로 서명할 수 있으므로 소스 제어에 커밋하지 마세요.

### 사용자 지정 접두사로 keypair 그라인딩하기

[`vanity`](https://github.com/cavemanloverboy/vanity)를 사용하면 공개 키가 특정 base58 접두사로 시작하는
Ed25519 keypair를 검색할 수 있습니다. crates.io에서 CPU 버전을 설치하세요.

```bash
cargo install vanity
```

이 프로젝트는 GPU 가속 검색을 위한 CUDA, Metal, OpenCL 빌드도 제공합니다. 각 백엔드의 요구 사항은 `vanity` 설치 안내를 참조하세요.

```bash
vanity grind-keypair --pattern Acme...
```

일치하는 항목을 찾으면 `vanity`는 공개 키, 16진수로 표현된 비공개 시드, 그리고 Solana와 호환되는 keypair JSON 배열을 출력합니다. JSON 파일을 안전한 위치에 저장한 다음, 예상한 공개 키가 들어 있는지 확인하세요.

```bash
solana-keygen pubkey path/to/keypair.json
```

명령어 출력과 저장된 JSON 파일은 개인 키 자료로 취급하세요.

### seed로 계정 생성하기

더 빠르게 검색하려면 `vanity grind`를 사용하세요. 이 명령어는 Ed25519 keypair를 생성하는 대신 `CreateAccountWithSeed`용 seed 문자열을 검색합니다. 생성을 승인할 기본 계정의 공개 키, 계정 소유자, 그리고 검색할 접두사를 지정하세요. 업그레이드 가능한 program account의 경우 소유자로 업그레이드 가능한 BPF 로더를 사용하세요.

```bash
vanity grind \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --pattern Acme...
```

결과에는 파생된 주소와 seed 문자열이 포함됩니다. 계정을 생성하기 전에 이를 확인하세요.

```bash
vanity verify \
  --base <BASE_ACCOUNT_PUBKEY> \
  --owner BPFLoaderUpgradeab1e11111111111111111111111 \
  --seed <SEED>
```

동일한 기본 주소, seed, 소유자를 사용하여 `Pubkey::create_with_seed`로 주소를 파생한 다음, System Program `create_account_with_seed` 인스트럭션을 제출하세요. 기본 계정과 자금을 제공하는 계정이 트랜잭션에 서명해야 합니다. 파생된 계정에는 독립적인 keypair가 없으므로, 이 방법을 사용하려면 프로그램 keypair 파일이 아닌 기본 계정을 사용하는 계정 생성 및 배포 흐름이 필요합니다.

### 소스의 프로그램 주소 업데이트하기

keypair 또는 seed 기반 계정을 선택한 후에는 프로젝트에서 프로그램 ID를 선언하는 모든 곳에 해당 공개 주소를 사용하세요. 소스에 이전 주소가 남아 있으면 클라이언트가 잘못된 프로그램으로 인스트럭션을 보낼 수 있고 런타임 ID 검사가 실패할 수 있습니다.

Anchor 워크스페이스에서는 루트 `Anchor.toml`의 프로그램 항목과 `programs/<PROGRAM_NAME>/src/lib.rs`의 `declare_id!` 호출을 모두 업데이트하세요. `[programs.<CLUSTER>]` 아래의 키는 프로그램의 워크스페이스 이름입니다. 새 주소를 사용하려는 모든 클러스터 테이블을 업데이트하세요. 아래 예시는 메인넷을 업데이트합니다.

Anchor.toml에서:

```diff
 [programs.mainnet]
-my_program = "<OLD_PROGRAM_ID>"
+my_program = "<NEW_PROGRAM_ID>"
```

`programs/<your_program>/lib.rs`에서:

```diff
-declare_id!("<OLD_PROGRAM_ID>");
+declare_id!("<NEW_PROGRAM_ID>");
```

Pinocchio는 `Anchor.toml`을 사용하지 않습니다. 프로그램 크레이트의 `src/lib.rs`에서 `declare_id!` 호출을 업데이트하세요. 현재 Pinocchio 프로젝트는 `pinocchio::address`에서 매크로를 가져옵니다.

Quasar 역시 온체인 프로그램 크레이트의 `src/lib.rs`에서 주소를 선언하며 `Anchor.toml`을 사용하지 않습니다. `declare_id!` 매크로는 `quasar_lang::prelude::*`를 통해 사용할 수 있습니다.

주소를 변경한 후에는 프로그램을 다시 빌드하고 IDL 또는 클라이언트 아티팩트를 다시 생성하세요. 또한 배포 스크립트, 테스트, 애플리케이션 설정에서 이전 프로그램 ID를 검색하여 하드코딩된 참조를 모두 교체하세요.
