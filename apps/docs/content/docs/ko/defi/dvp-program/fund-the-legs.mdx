자금 입금은 레그의 에스크로로 보내는 일반 `TransferChecked`이므로, 토큰 전송을 보낼 수 있는 지갑이나
커스터디 시스템이라면 무엇이든 레그에 자금을 입금할 수 있습니다. 입금 전에 거래 레코드를 읽을 때만
DvP 클라이언트가 필요합니다. 프로그램은 정산 시점에만 에스크로 잔액을 확인하며, 전송이 도착할 때는
아무것도 검사하지 않으므로 각 당사자는 전송하기 전에 거래 레코드를 읽어야 합니다.

이 페이지는 [거래 생성하기](/docs/defi/dvp-program/create-a-trade)에서 이어집니다. 클라이언트와 서명자는
그대로 이어서 사용합니다.

## 조건 확인하기

레코드 생성에는 별도의 권한이 필요하지 않으며, 에스크로 주소는 조건이 아니라 레코드와 mint로만
파생됩니다. 따라서 합의하지 않은 조건의 에스크로로도 전송이 도착할 수 있으며, 여기에는 상대방의 정산 대금을
제3의 주소로 보내는 정산 목적지도 포함됩니다. 입금하기 전에 `SwapDvp` 계정을 읽고 합의한 거래와
대조하세요.

TypeScript의 `verifySwapDvp`와 Rust의 `verify::decode_swap_dvp_account`는 해당 계정이
DvP 프로그램 소유인지, 크기가 정확히 458바이트인지, 그리고 계정 자체의 필드에서 파생되는 주소에
있는지 확인합니다(`fetchSwapDvpChecked`는 앞의 두 가지 검사만 수행합니다). 일반 `fetchSwapDvp` 및
`decodeSwapDvp` 리더는 이러한 검사를 하나도 수행하지 않습니다. 당사자, 금액, 시간, 목적지에 대한 검사는
호출자가 합의한 거래와 대조하여 직접 수행해야 합니다.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    import { unwrapOption } from "@solana/kit";
    import { verifySwapDvp } from "./dvp";

    const trade = await verifySwapDvp(client.rpc, swapDvp);
    const t = trade.data;

    const expectedAmountA = 1_000_000_000n;
    const expectedAmountB = 998_500_000n;
    const expectedEarliestSettlement: bigint | null = null; // as agreed
    const expectedExpiry = 1_798_761_600n; // as agreed, unix seconds

    if (
      t.userA !== userA ||
      t.userB !== userB ||
      t.mintA !== mintA ||
      t.mintB !== mintB ||
      t.settlementAuthority !== settlementAuthority ||
      t.tokenProgramA !== tokenProgramA ||
      t.tokenProgramB !== tokenProgramB ||
      t.amountA !== expectedAmountA ||
      t.amountB !== expectedAmountB ||
      unwrapOption(t.earliestSettlementTimestamp) !== expectedEarliestSettlement ||
      t.expiryTimestamp !== expectedExpiry ||
      t.userASettlementDestination !== userA ||
      t.userBSettlementDestination !== userB
    ) {
      throw new Error("Stored terms do not match the agreed trade; do not fund");
    }

    if (t.expiryTimestamp <= BigInt(Math.floor(Date.now() / 1000)) + 60n) {
      throw new Error("Trade expires too soon to fund safely");
    }
    ```

  </Tab>

  <Tab value="Rust">
    ```rust
    use dvp_swap_program_client::verify::decode_swap_dvp_account;
    use solana_client::rpc_client::RpcClient;
    use solana_commitment_config::CommitmentConfig;

    // Read at confirmed: a record created moments ago is not visible at finalized yet.
    let rpc = RpcClient::new_with_commitment(
        "https://api.devnet.solana.com".to_string(),
        CommitmentConfig::confirmed(),
    );
    let account = rpc.get_account(&swap_dvp)?;
    let trade = decode_swap_dvp_account(&swap_dvp, &account)?;

    let expected_amount_a: u64 = 1_000_000_000;
    let expected_amount_b: u64 = 998_500_000;
    let expected_earliest_settlement: Option<i64> = None; // as agreed
    let expected_expiry: i64 = 1_798_761_600; // as agreed, unix seconds

    if trade.user_a != user_a
        || trade.user_b != user_b
        || trade.mint_a != mint_a
        || trade.mint_b != mint_b
        || trade.settlement_authority != settlement_authority
        || trade.token_program_a != token_program_a
        || trade.token_program_b != token_program_b
        || trade.amount_a != expected_amount_a
        || trade.amount_b != expected_amount_b
        || trade.earliest_settlement_timestamp != expected_earliest_settlement
        || trade.expiry_timestamp != expected_expiry
        || trade.user_a_settlement_destination != user_a
        || trade.user_b_settlement_destination != user_b
    {
        return Err("stored terms do not match the agreed trade; do not fund".into());
    }

    let now_seconds: i64 = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)?
        .as_secs() as i64;
    if trade.expiry_timestamp <= now_seconds + 60 {
        return Err("trade expires too soon to fund safely".into());
    }
    ```

</Tabs>

상대방이나 정산 권한자가 레코드를 생성한 경우, 원장 외부에서 합의한 조건과 모든 필드를 하나하나 비교하세요.
직접 생성한 경우에는 이 읽기를 통해 전송한 그대로 반영되었는지 확인할 수 있습니다.

## 에스크로로 전송하기

합의한 금액과 정확히 같은 금액으로 레그에 자금을 입금하세요. 프로그램은 정산 금액을 `amount_x`로
제한하고 초과분은 레그의 당사자에게 반환하므로 초과분이 유실되지는 않지만, 정산 시 전송이 한 번 더
발생하며 일부 전송 훅에서는 실패할 수 있습니다(아래 참고 사항 참조).

확인 없는 `Transfer`가 아니라 `TransferChecked`를 사용하세요. Pausable처럼 mint account에
의존하는 확장을 가진 Token-2022 mint는 이를 제공하지 않은 전송을 거부하며, 전송 훅이 있는 mint는
해당 토큰의 다른 전송과 마찬가지로 훅의 계정을 확인하여 추가해야 합니다.

<Tabs items={["TypeScript", "Rust"]}>
  <Tab value="TypeScript">
    자산 레그의 당사자가 `userASigner`로 서명하여 에스크로 A에 자금을 입금합니다.

    ```ts
    import {
      findAssociatedTokenPda,
      getTransferCheckedInstruction,
    } from "@solana-program/token-2022";

    const [userAAtaA] = await findAssociatedTokenPda({
      mint: mintA,
      owner: userA,
      tokenProgram: tokenProgramA,
    });
    const [userBAtaB] = await findAssociatedTokenPda({
      mint: mintB,
      owner: userB,
      tokenProgram: tokenProgramB,
    });

    const fundAssetLeg = getTransferCheckedInstruction({
      source: userAAtaA,
      mint: mintA,
      destination: escrowA,
      authority: userASigner,
      amount: t.amountA,
      decimals: 6,
    }, { programAddress: tokenProgramA });

    await client.sendTransaction([fundAssetLeg]);
    ```

    현금 레그의 당사자는 에스크로 B에 대해 `userBAtaB`, `mintB`,
    `userBSigner`, `t.amountB`, `{ programAddress: tokenProgramB }`를 사용하여 동일하게 진행합니다.

  </Tab>

  <Tab value="Rust">
    ```rust
    use spl_associated_token_account_client::address::get_associated_token_address_with_program_id;
    use spl_token_2022_interface::instruction::transfer_checked;

    let user_a_ata_a =
        get_associated_token_address_with_program_id(&user_a, &mint_a, &token_program_a);

    let fund_asset_leg = transfer_checked(
        &token_program_a,
        &user_a_ata_a,
        &mint_a,
        &escrow_a,
        &user_a,
        &[],
        trade.amount_a,
        6,
    )?;
    ```

    현금 레그의 당사자는 `mint_b`, `user_b`, `trade.amount_b`를 사용하여
    에스크로 B에 대해 동일한 명령을 구성합니다.

  </Tab>
</Tabs>

[`confirmed`](/docs/rpc#configuring-state-commitment) 상태로 확인된 입금 전송도
나중에 대체될 수 있습니다. 프로그램은 정산 시점에 온체인에서 에스크로 잔액을 읽으므로, 반영되지 않은
입금 전송을 기준으로 보낸 Settle은 `LegNotFunded`와 함께 실패하고 아무것도 이동하지 않습니다. 이 경우
Settle 실패와 재시도 비용이 발생합니다. 전송이 `finalized` 상태가 되었을 때 레그에 자금이 입금된 것으로
간주하세요.

## 참고 사항

- **래핑된 SOL 레그.** 프로그램은 네이티브 에스크로의 잔액을 동기화한 후 읽으므로, 시스템 전송으로
  래핑된 SOL 에스크로에 보낸 lamports도 집계됩니다. 다른 mint의 에스크로로는 절대 SOL을 보내지 마세요.
  프로그램이 이를 반환할 수 없으며, 해당 계정을 닫는 사람에게 넘어갑니다.
- **제한된 mint.** Default Account State가 동결로 설정된 mint에서는 에스크로가 동결된 상태로
  생성되며, 발행자가 동결을 해제하거나 허용할 때까지 전송이 실패합니다. Token ACL과의 상호작용은
  [개요](/docs/defi/dvp-program#mint-configuration-constraints)에서 설명합니다.
- **전송 훅.** 훅이 있는 에스크로에는 합의한 금액과 정확히 같은 금액을 입금하세요. 초과분 때문에 정산 시
  환불이 필요해지면, 환불은 레그의 훅 계정을 다른 목적지와 금액으로 재사용하는데, 일부 훅은 이를
  거부합니다. 복구 방법은 Reclaim을 실행하고, 정확한 금액으로 다시 입금한 뒤, 다시 정산하는 것입니다.
- **만료 이후 입금.** `expiry_timestamp` 이후의 전송을 막는 장치는 없습니다. 전송은 도착하지만 정산은 더 이상
  불가능하며, 레그의 당사자는 거래가 열려 있는 동안에는 Reclaim으로, 거래가 닫힌 후에는 Recover로
  회수합니다. [거래 되돌리기](/docs/defi/dvp-program/unwind-a-trade)를 참조하세요.
- **누가 먼저 입금하는가.** 프로그램은 두 레그의 순서를 지정하지 않습니다. 순서는 당사자들이 정할 문제이며,
  mint 권한자(동결, 일시 중지 또는 전송 훅)가 에스크로를 막지 않는 한, 어느 쪽이든 정산 전에는 언제든지
  자신의 레그를 회수할 수 있습니다.
