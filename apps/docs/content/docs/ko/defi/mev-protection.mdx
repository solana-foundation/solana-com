# Jito DontFront를 활용한 MEV 보호

MEV(Maximal Extractable Value, 최대 추출 가능 가치)는 블록 내 트랜잭션의 순서를 바꾸거나,
트랜잭션을 포함하거나 제외함으로써 얻을 수 있는 가치를 의미합니다. MEV는 특정 체인에만
국한된 것이 아니라, 블록 생성자가 트랜잭션 순서를 제어하는 모든 블록체인의 근본적인
속성입니다. 차익거래(arbitrage)와 같은 일부 MEV는 DEX 간 가격 불일치를 바로잡아
시장 효율성을 유지하는 데 도움이 됩니다. 반면 샌드위치 공격과 같은 MEV는 사용자로부터
직접 가치를 빼앗습니다. DeFi 애플리케이션을 구축하는 개발자에게 이는 거래 체결 가격
악화와 수익 손실로 이어질 수 있습니다.

이 가이드는 유해한 MEV의 대표적인 형태인 샌드위치 공격과, Jito의 `dontfront` 기능을
사용해 이를 완화하는 방법에 초점을 맞춥니다.

사전 읽기 권장:
[Jito 번들](https://solana.com/docs/tools/transaction-landing#jito-bundles)

## Solana에서의 MEV

Solana의 아키텍처는 공개 멤풀(mempool)을 사용하는 체인에 비해 MEV가 발생할 수 있는
범위를 이미 줄여줍니다. 트랜잭션은 공유 멤풀에 대기하지 않고 다음 블록 리더에게 직접
전달되며, 처리되지 않은 트랜잭션은 약 150개 블록(약 1분) 후에 만료됩니다. 이로 인해
서처(searcher)가 대기 중인 트랜잭션을 관찰하고 대응할 수 있는 시간이 크게 줄어듭니다.

그럼에도 MEV 추출은 여전히 발생합니다. 최적화된 인프라와 validator와의 직접 연결을
갖춘 서처는 트랜잭션 흐름을 관찰하고 이에 대응할 수 있습니다. Solana에서 발생하는
MEV 활동의 상당수는 원자적 차익거래, 즉 하나의 트랜잭션 안에서 DEX 간 가격 차이를
바로잡는 봇의 활동입니다. 이러한 유형의 MEV는 시장 전반의 가격 일관성을 높여주므로
일반적으로 유익합니다.

개발자가 적극적으로 방어해야 할 대상은 유해한 유형인 샌드위치 공격입니다.

## 샌드위치 공격이란?

샌드위치 공격은 서처가 대기 중인 스왑을 감지하고 트랜잭션 순서를 악용할 때 발생합니다.

1. **프론트런(Front-run)**: 서처가 사용자의 거래 전에 토큰을 매수하여 가격을
   끌어올립니다
2. **사용자의 거래가 실행됩니다**. 예상보다 불리한 가격으로 체결됩니다
3. **백런(Back-run)**: 서처가 사용자의 거래 후에 토큰을 매도하여 차익을
   챙깁니다

Solana에서는 [Jito 번들](https://docs.jito.wtf/lowlatencytxnsend/#what-are-bundles)을 통해 이러한 공격이 발생할 수 있습니다.
서처가 `[frontrun_tx, your_tx, backrun_tx]`와 같은 트랜잭션 번들을 제출하면,
블록 엔진이 이를 순서대로 원자적으로 실행합니다. 피해자는 더 불리한 체결 가격을
받게 되고, 서처는 스프레드에서 이익을 얻습니다.

## DontFront의 작동 방식

[DontFront](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation)는 서처가 번들 내에서 사용자의 트랜잭션 앞에 다른 트랜잭션을
배치하지 못하도록 막는 Jito 블록 엔진의 기능입니다.

작동 원리는 다음과 같습니다. `jitodontfront`로 시작하는 유효한 Solana 공개 키를
트랜잭션의 아무 instruction에나 추가합니다. 블록 엔진은 이 접두사를 인식하고
다음 규칙을 적용합니다. **해당 트랜잭션을 포함하는 모든 번들은 이 트랜잭션을
인덱스 0에 배치해야 합니다**.

```
Without dontfront:  [frontrun_tx, your_tx, backrun_tx]  ← sandwich possible
With dontfront:     [your_tx, ...]                       ← your tx must be first
```

### 단계별 안내

1. **`jitodontfront`로 시작하는 유효한 주소를 선택합니다** (예:
   `jitodontfront111111111111111111111111111111`). 이 계정은 온체인에 존재할 필요가
   없으며, 읽거나 쓰는 일도 없습니다. @solana/kit의
   [`assertIsAddress`](https://www.solanakit.com/api/functions/assertIsAddress)
   함수로 문자열이 유효한 주소인지 확인하거나, Solana Explorer에 주소를 입력해
   조회되는지 확인할 수 있습니다. 다음은
   [유효하지 않은 주소](https://explorer.solana.com/address/jitodontfront11111111111111111111111111111INVALID)의 예시입니다.

2. **이 주소를 읽기 전용, 비서명자(non-signer) 계정으로** 트랜잭션의 아무 instruction에나
   추가합니다. 최적의 랜딩 속도를 위해 읽기 전용으로 표시하세요. 대부분의 프로그램
   (System Program 포함)은 예상한 계정 외의 추가 계정을 무시합니다.

3. **Jito 블록 엔진을 통해 제출합니다**:
   - `sendTransaction`:
     `https://mainnet.block-engine.jito.wtf/api/v1/transactions`
   - `sendBundle`: `https://mainnet.block-engine.jito.wtf/api/v1/bundles`

   문서:
   [sendTransaction](https://docs.jito.wtf/lowlatencytxnsend/#sendtransaction)
   및 [sendBundle](https://docs.jito.wtf/lowlatencytxnsend/#sendbundle)

4. 블록 엔진이 `jitodontfront` 접두사를 감지하고 순서 규칙을 적용합니다.

### 블록 엔진에서 일어나는 일

블록 엔진이 `jitodontfront` 계정을 포함한 트랜잭션을 확인하면 다음과 같이 처리됩니다.

- `sendTransaction`을 통한 경우: 트랜잭션이 보호됩니다. 어떤 번들도 이 트랜잭션 앞에
  다른 트랜잭션을 배치할 수 없습니다
- `sendBundle`을 통한 경우: 트랜잭션이 인덱스 0에 있어야 하며, 그렇지 않으면 번들 전체가
  거부됩니다

`jitodontfront` 계정을 포함하지 않는 트랜잭션과 번들에는 영향이 없습니다.

## 번들 순서 규칙

이 규칙은 `jitodontfront` 트랜잭션이 번들에 포함된 경우에 적용됩니다.

### 허용되는 패턴

```
[tx_with_dontfront, tip]
[tx_with_dontfront, arbitrage, tip]
[tx_with_dontfront_signer1, tx_with_dontfront_signer1_and_signer2, tip]
```

### 하나의 번들에 여러 DontFront 트랜잭션이 있는 경우

하나의 번들에 여러 dontfront 트랜잭션을 포함하는 것은 **다음 두 조건을 모두**
충족할 때 허용됩니다.

1. 모든 dontfront 트랜잭션이 번들의 **맨 앞에 연속으로** 위치해야 합니다
2. 각 dontfront 트랜잭션은 첫 번째 dontfront 트랜잭션과 **최소 한 명 이상의 서명자**를
   공유해야 합니다

```
✅ [txA_df, txB_df, txC_df, arbitrage, tip]
   (contiguous at front, overlapping signers)

✅ [txA_df_signer1_signer2, txB_df_signer1_signer3, txC_df_signer2_signer4]
   (each shares a signer with txA)
```

### 거부되는 패턴

```
❌ [tip, tx_with_dontfront]
   → dontfront tx is not at index 0

❌ [txA_df_signer1, txB_df_signer2]
   → no overlapping signer between txA and txB

❌ [trade, tx_with_dontfront, arbitrage, tip]
   → dontfront tx is not at the front
```

## 통합 예제

간단한 코드 레시피는
[MEV 보호 쿡북 항목](/developers/cookbook/transactions/mev-protection)을 참고하세요.

### TypeScript (@solana/kit)

핵심 아이디어는 어떤 instruction에든 dontfront 계정을 추가해 주는 헬퍼를 만드는 것입니다.

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
import {
  address,
  AccountRole,
  type Instruction,
  type Address
} from "@solana/kit";

const DONT_FRONT: Address = address(
  "jitodontfront111111111111111111111111111111"
);

// !mark(1:9)
function withDontFront(ix: Instruction): Instruction {
  return {
    ...ix,
    accounts: [
      ...(ix.accounts ?? []),
      { address: DONT_FRONT, role: AccountRole.READONLY }
    ]
  };
}
```

```rs !! title="Rust"
use solana_sdk::{
    instruction::{AccountMeta, Instruction},
    pubkey::Pubkey,
};
use std::str::FromStr;

const DONT_FRONT_ACCOUNT: &str =
    "jitodontfront111111111111111111111111111111";

// !mark(1:6)
fn with_dontfront(ix: &mut Instruction) {
    let dontfront =
        Pubkey::from_str(DONT_FRONT_ACCOUNT).unwrap();
    ix.accounts
        .push(AccountMeta::new_readonly(dontfront, false));
}
```

</CodeTabs>

그런 다음 서명된 트랜잭션을 일반 RPC 노드가 아닌 Jito 블록 엔진에 제출하세요.
항상 base64 인코딩을 사용하세요. Jito API에서 Base58은 더 이상 사용되지 않습니다(deprecated).

<CodeTabs storage="guide-mev">

```ts !! title="Kit"
// !mark(1:2)
const response = await fetch(
  "https://mainnet.block-engine.jito.wtf/api/v1/transactions",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      jsonrpc: "2.0",
      id: 1,
      method: "sendTransaction",
      // !mark
      params: [base64Tx, { encoding: "base64" }]
    })
  }
);
```

```rs !! title="Rust"
let serialized = bincode::serialize(&tx)?;
// !mark
let base64_tx = base64::engine::general_purpose::STANDARD
    .encode(&serialized);

// !mark(1:2)
let response = client
    .post("https://mainnet.block-engine.jito.wtf/api/v1/transactions")
    .json(&serde_json::json!({
        "jsonrpc": "2.0",
        "id": 1,
        "method": "sendTransaction",
        "params": [base64_tx, {"encoding": "base64"}]
    }))
    .send()
    .await?;
```

## 모범 사례

DontFront는 하나의 보호 계층입니다. 견고한 MEV 완화 전략은 여러 접근 방식을
함께 결합합니다.

### 트랜잭션 수준의 보호

- **슬리피지 허용 범위를 좁게 설정하세요.** 샌드위치 공격에 대한 가장 효과적인 단일
  방어책은 스왑에서 허용되는 슬리피지를 제한하는 것입니다. 슬리피지 범위가 작을수록
  공격자가 얻을 수 있는 이익 폭이 줄어들어, 사용자의 트랜잭션이 샌드위치 공격의
  대상이 될 가능성이 낮아집니다.

- **적절한 팁과 우선순위 수수료를 설정하세요.** 네트워크가 혼잡할 때는 더 높은 팁과
  우선순위 수수료가 트랜잭션/번들이 빠르게 랜딩될 가능성을 높여, 서처가 개입할 수 있는
  시간을 줄여줍니다. 적절한 팁을 설정하는 방법에 대한 자세한 내용은 Jito 문서의
  [팁 금액](https://docs.jito.wtf/lowlatencytxnsend/#tip-amount)을 참고하세요.

- **컴퓨트 유닛 사용을 최적화하세요.** 각 블록에서 사용할 수 있는 컴퓨트 유닛 수는
  제한되어 있습니다(계정별로 블록당 사용할 수 있는 컴퓨트 유닛 수도 제한됩니다).
  트랜잭션/번들이 블록에 포함될 가능성을 극대화하려면 컴퓨트 유닛 사용을 최적화해야
  합니다. 자세한 내용은
  [Solana에서 컴퓨트 사용량을 최적화하는 방법](/developers/cookbook/transactions/optimize-compute)
  가이드를 참고하세요.

### DontFront 관련

1. **dontfront 계정을 읽기 전용으로 표시하세요.** 쓰기 가능으로 표시해도 동작하지만,
   읽기 전용으로 표시하면
   [랜딩 속도가 최적화됩니다](https://docs.jito.wtf/lowlatencytxnsend/#sandwich-mitigation).

2. **애플리케이션마다 고유한 dontfront pubkey를 사용하세요.** `jitodontfront`로 시작하는
   pubkey라면 무엇이든 동작합니다. 고유한 변형(예:
   `jitodontfront111111111111111111111111111123`)을 사용하면 온체인 데이터를 살펴볼 때
   앱별 사용량을 구분할 수 있습니다.

3. **DontFront는 Address Lookup Table을 지원합니다.** dontfront 계정은 ALT를 통해
   포함할 수 있습니다. 단, 팁 계정에는 ALT를 사용하지 마세요.

## 제한 사항

- **블록 엔진 전용입니다.** DontFront는 Jito 블록 엔진에서 적용됩니다. (Jito를 우회하여)
  validator에 직접 제출된 트랜잭션은 보호되지 않습니다.

- **보장되지 않습니다.** Jito 문서에 따르면: _"이 기능은 샌드위치 공격을 줄이는 데
  도움이 될 수 있으나, 그렇게 된다고 보장되지 않으며, 제3자가 수행하는 모든 순서 조작을
  포함한 트랜잭션 순서의 모든 변형에 대한 해결책도 아닙니다."_

- **메인넷/테스트넷 전용입니다.** 이 기능은 Jito 블록 엔진의 기능입니다. devnet이나
  localhost에서는 작동하지 않습니다.
