# Account Data Direct Mapping

October 2026 • Solana Foundation

Every time a Solana program runs, the validator copies each account's data into
the program's virtual machine, and copies it back out afterward. A cross-program
invocation (CPI) repeats that work in both directions. Direct mapping removes
the copies: the program reads and writes the account's data in place.

That only works if the runtime knows exactly which bytes a program touches.
Today a program can read past the end of an account, write to a read-only
account as long as it restores the original value, or reach across memory
regions (the separate address ranges the virtual machine gives the program's
read-only data, the stack, the heap, the instruction input, and each account's
data), and nobody notices. Direct mapping makes the runtime check every access,
and a program that breaks the rules now fails with an instruction error.

The rules come from
[SIMD-0219](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0219-stricter-abi-and-runtime-constraints.md),
which Anza and Firedancer later split in two. The first half, the rules for
pointers passed to CPI syscalls, has been live on mainnet since June 2026. This
article covers the second half, which ships as two feature gates: the stricter
memory rules, and direct mapping itself. Most programs never trigger one of the
new errors
([SIMD-0219, Impact](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0219-stricter-abi-and-runtime-constraints.md#impact)).
This article is for the ones that might.

- **Users:** Nothing to do. An app whose program breaks the rules can start
  failing; its team has to fix it.
- **Developers whose programs follow the rules:** Nothing changes. Test on
  devnet or testnet to confirm.
- **Developers whose programs read, write, or resize account data in unusual
  ways, or rely on stack layout:** Some transactions that succeed today will
  fail. Test now. See [Does This Affect Me?](#does-this-affect-me).
- **Validator operators:** Nothing to do. Every release at or above the current
  mainnet minimum already contains both gates.

## Test It Before Mainnet

Both gates are already active on devnet and testnet, so a program deployed there
runs under the new rules today. To check the status of a gate on any cluster:

```bash
solana feature status 7VgiehxNxu53KdxgLspGQY8myE6f7UokaWa4jsGcaSz --url mainnet-beta
```

While the gate is inactive on mainnet, the row reads like this:

```text
Feature                                      | Status                  | Activation Slot | Description
7VgiehxNxu53KdxgLspGQY8myE6f7UokaWa4jsGcaSz  | inactive                | NA              | SIMD-0460: Virtual Address Space Adjustments
```

On devnet the same command shows `active since epoch 1073` with activation slot
`463536000`, and on testnet `active since epoch 957` with slot `407900256`.

`solana-test-validator` activates every feature gate its build knows about, so
the new rules are on by default locally. To compare behavior, start a fresh
ledger with both gates switched off:

```bash
# All known gates are active by default, including both of these
solana-test-validator

# Reproduce mainnet behavior by deactivating both gates. The flag only applies
# when the ledger is created, so add --reset if you already ran the command above.
solana-test-validator --reset --deactivate-feature 7VgiehxNxu53KdxgLspGQY8myE6f7UokaWa4jsGcaSz CR3dVN2Yoo95Y96kLSTaziWDAQT2MNEpiWh5cqVq2pNE
```

If the output includes `--deactivate-feature argument ignored, ledger already
exists`, the gates are still on; rerun with `--reset`.

To check how a real mainnet transaction would behave, paste its signature into
[SVM Scope](https://svmscope.vercel.app/), a community tool that replays a
transaction from the last 30 days in an embedded SVM under mainnet's current
feature set. Note the replay result, then open its Features panel, switch on the
gate it lists as "direct mapping" (`7Vgieh…`), and replay again under the new
rules. A transaction that succeeds with the gate off and errors with it on
points at a program that needs a fix.

Anza has replayed mainnet traffic with the gate on and off and contacted the
teams whose programs diverge
([SIMD-0219, Impact](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0219-stricter-abi-and-runtime-constraints.md#impact)),
and a further impact experiment is running
([SIMD-0460, Impact](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0460-virtual-address-space-adjustments.md#impact)).
That replay only covers traffic it has seen, so a program that runs rarely can
still be missing. Test your own program rather than waiting to be contacted.

## Does This Affect Me?

<AudienceGroup>
<Audience title="For Users" summary="No action needed.">

Wallets, balances, fees, and confirmation times are unaffected. If an app you
use runs a program that still breaks these rules, a transaction that worked
yesterday can fail after activation. The app team needs to fix it. Your funds
are not at risk: a failed transaction changes no account state, and you pay only
the usual fee.

</Audience>

<Audience title="For Developers" summary="Most programs need nothing. If you read, write, or resize account data by hand, use unsafe code, or reassign Anchor accounts via CPI, test now and redeploy fixes before mainnet activation.">

Existing programs that stay inside their accounts keep working. The programs most
likely to be affected use `unsafe` code, hand-rolled account parsing, raw
pointers, custom entrypoints, an SDK older than `solana-account-info` 2.3.0
(which has no `resize`), or an Anchor build without the fix described below.

| If your program                                                                      | Breaking? | What you have to do                                                                                                       |
| ------------------------------------------------------------------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------- |
| **Uses** safe SDK or framework code and well-formed accounts                         | No        | Nothing. Run your test suite against devnet to confirm.                                                                   |
| **Indexes, decodes, or simulates** transactions                                      | No        | Nothing. Account state and results are unchanged for compliant programs.                                                  |
| **Parses** account bytes by hand, uses `unsafe` or raw pointers, or resizes accounts | Check     | Each pattern that breaks, and what to do about it, is in the Breaking Changes table above; every row links to its detail. |

Native and Pinocchio programs that parse account bytes themselves have to write
these bounds checks themselves.

**If you maintain a program:**

- Follow [Test It Before Mainnet](#test-it-before-mainnet): run your test suite
  against `solana-test-validator`, then against devnet or testnet, and replay
  recent mainnet transactions in SVM Scope with the gate on. A green suite only
  covers the paths it exercises, so include close, resize, and CPI paths.
- Search your code for `unsafe`, raw pointer casts, and `realloc`, and check
  each hit against [Breaking Changes in Detail](#breaking-changes-in-detail).
- Redeploy fixes before the mainnet gate. Immutable programs cannot be fixed in
  place, so deploy a new program and migrate users.

**If you use Anchor:**

Anchor's account types check lengths and ownership for you, but one pattern
needs attention. Anchor's generated exit code re-serializes every mutable typed
account after your handler returns, even if the instruction handed that account
to another program, for example through a CPI that reassigns its owner. Under
the new rules that write fails with `ExternalAccountDataModified`. Accounts
closed with Anchor's `close` constraint are not affected; Anchor has skipped
those for years.

Anchor PR [#5011](https://github.com/otter-sec/anchor/pull/5011) stops writing
to an account whose owner changed during the instruction: unchanged data passes,
and a pending change fails with Anchor's own `AccountOwnedByWrongProgram` rather
than being lost. As of October 2026 the change is merged on Anchor's `master`
branch but is not in a tagged release; neither v1.2.1 nor v2.0.0-rc.2 contains
it. Until a release ships it, declare an account you reassign to another program
in the same instruction as `UncheckedAccount` or `AccountInfo` rather than a
mutable `Account`. Once a release includes #5011, upgrade to it and rebuild.

**If you use another team's program:**

- Ask them whether they have tested against devnet. Report failures with the
  signature from SVM Scope.

</Audience>

<Audience title="For Validator Operators" summary="Nothing to do. Stay on a release at or above the mainnet minimum version; both gates are already in it.">

Agave and Firedancer implement the change behind the two feature gates, and the
code has shipped: Agave since
[v4.0.0-beta.0](https://github.com/anza-xyz/agave/releases/tag/v4.0.0-beta.0)
(March 2026) and Firedancer since
[v26.08.0](https://github.com/firedancer-io/firedancer/releases/tag/v26.08.0),
both at or below the mainnet minimum versions listed on the
[Feature Gate Tracker](https://github.com/anza-xyz/agave/wiki/Feature-Gate-Tracker-Schedule).
There is nothing to configure. Account data copies disappear once the second
gate activates, so expect less memory traffic per instruction, not a different
outcome; the runtime still produces identical account state for every program
that follows the rules. Watch the tracker for the activation epoch, and check
gate status with `solana feature status`.

</Audience>
</AudienceGroup>

## Breaking Changes in Detail

Account data violations are loud. The instruction returns an error, the
transaction fails, and no account state changes. A program cannot catch the
error in a CPI caller and carry on, because the failure aborts the transaction.
A failed transaction still pays the usual fee. The stack layout change is the
exception: it can alter a program's behavior without any error, as described in
the third section below.

### Breaking Change: Account Data Access Is Now Checked

Every read is checked against the account's current length, and every write
against the account's owner and writable flag and, when it reaches past the
end, against the resize limits. Before direct mapping, a bad access went
unnoticed as long as it stayed inside the reserved address space, or as long
as a write was undone before the program returned.

| The access                                                                                        | The error                                       | In the logs                                               |
| ------------------------------------------------------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------- |
| A read past the current length of a read-only account, or of an account your program does not own | `InstructionError::AccountDataTooSmall`         | `account data too small for instruction`                  |
| A read past the current length of a writable account your program owns                            | `InstructionError::InvalidRealloc`              | `Failed to reallocate account data`                       |
| A write to an account not flagged writable                                                        | `InstructionError::ReadonlyDataModified`        | `instruction modified data of a read-only account`        |
| A write to an account your program does not own                                                   | `InstructionError::ExternalAccountDataModified` | `instruction modified data of an account it does not own` |
| A write past the maximum account size or the growth limits                                        | `InstructionError::InvalidRealloc`              | `Failed to reallocate account data`                       |

The `InstructionError::` prefix never appears in output. The `err` field of a
simulation or `getTransaction` result carries the bare variant name, for example
`{"InstructionError": [0, "AccountDataTooSmall"]}`. Log messages, including the
output of `solana logs` and `solana confirm -v`, print the sentence form, for
example `Program <id> failed: account data too small for instruction`.

Reads never grow an account. Writes can: a write past the current length of a
writable account your program owns does not fail while it stays inside the
growth limits, meaning the 10 KiB an instruction may add to an account, the
10 MiB maximum account size, and the cap on total growth within one
transaction. The runtime treats it as a resize and zero-extends the account, so
you get no error. An access that reaches past that 10 KiB padding, or into
memory that belongs to no account, fails as a generic access violation, logged
as `Program <id> failed: Access violation ...` and reported as
`ProgramFailedToComplete`.

A typical case: a program casts account bytes to a fixed-size struct and the
account is shorter than the struct. Check `data_len()` first.

Two tempting fixes do not work. Catching the error in the calling program fails
because the error aborts the whole transaction. Restoring the original bytes
after the write fails because the runtime checks the write itself, not the final
value. Remove the write.

Programs that call `AccountInfo::realloc(len, false)` should move to
`AccountInfo::resize`. `realloc` was deprecated in `solana-account-info` 2.3.0
and removed in 3.0.0. With `zero_init = false` it grows the length without
writing the new bytes, so the first read of them is a read past the account's
real length and fails with `InvalidRealloc`. `resize` always zero-fills.

### Breaking Change: Accesses Cannot Span Memory Regions

A single load, store, or syscall that crosses from one memory region into the
next is now an access violation. Regions include the program's read-only data,
the stack, the heap, and, inside the input area, each account's metadata, each
account's data, and the instruction data. A `memcpy` that used to work because
two regions happened to sit next to each other must be split into one access per
region.

Slices handed out by the SDK stay inside one region, so this mainly affects
`unsafe` code and hand-written syscall calls.

### Breaking Change: Stack Frame Gaps Are Removed

[SIMD-0460](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0460-virtual-address-space-adjustments.md)
removes the unmapped gaps between stack frames for every program, including
programs compiled for sBPFv0, the oldest bytecode version, which still had
them. The stack becomes one contiguous range at lower addresses, and for sBPFv0
programs the amount the stack pointer moves on each `call` or `callx` (indirect
call) drops from 8 KiB to 4 KiB, which sBPFv3 already uses. The total mapped
stack size does not change.

Programs that use absolute stack addresses, compute addresses across frames, or
depend on an out-of-bounds access stopping at a frame boundary can break, and
this is the one change in this upgrade that does not always error. An access
that lands outside the new, smaller stack range, such as an absolute address
into the old upper half, fails with an access violation. An access that lands
inside it does not: an overrun past a frame boundary that used to hit an
unmapped gap now silently reads or writes the neighbouring frame, and an
absolute or cross-frame address that worked before now points at a different
frame's bytes. The program keeps running with different data and no error.

Anza's replay has seen one program consume slightly fewer compute units with the
first gate on and no other difference; the suspected cause is an out-of-bounds
stack access. Treat an unexplained compute unit change as a reason to check for
a stack overrun, and test stack-heavy `unsafe` code on devnet rather than
waiting for an error.

## Three Gates, Two Still Pending

[SIMD-0219](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0219-stricter-abi-and-runtime-constraints.md)
was split into two proposals so each half could ship on its own. The first,
[SIMD-0459](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0459-syscall-parameter-address-restrictions.md),
covers the pointers a program passes to syscalls: the `AccountInfo` structures
handed to a CPI must live on the stack or heap, and their `key`, `owner`,
`lamports`, and `data` pointers must point at what the runtime originally
serialized. A violation fails with `InvalidPointer`, logged as
`Invalid account info pointer`. Agave ships it as the gate
[`EDGMC5kxFxGk4ixsNkGt8bW7QL5hDMXnbwaZvYMwNfzF`](https://explorer.solana.com/address/EDGMC5kxFxGk4ixsNkGt8bW7QL5hDMXnbwaZvYMwNfzF/feature-gate),
which has been active on mainnet since the start of epoch 995 on June 30, 2026
at approximately 08:09 UTC. It is not controlled by the two gates in this
article, so deactivating `7Vgieh…` locally does not switch it off. If your
program CPIs successfully on mainnet today, it already complies.

The second half,
[SIMD-0460](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0460-virtual-address-space-adjustments.md),
is this upgrade's first gate. Direct mapping itself is a separate feature gate
with no SIMD of its own; Agave separated it from the behavior checks in
[anza-xyz/agave#7113](https://github.com/anza-xyz/agave/pull/7113) so the checks
could be deployed and fuzzed before the copies go away. Two gates remain:

1. **`7VgiehxNxu53KdxgLspGQY8myE6f7UokaWa4jsGcaSz`** tightens address
   translation and memory access, and removes stack frame gaps. This is the
   gate that can break programs.
2. **`CR3dVN2Yoo95Y96kLSTaziWDAQT2MNEpiWh5cqVq2pNE`** turns on direct mapping
   itself. The first gate already enforces every access rule in this article;
   the second changes how account data reaches the program, not which accesses
   are allowed, so it is not expected to produce new failures.

On devnet and testnet the two gates activated one epoch apart, and both are
active now, so a passing test there covers both. A replay that enables only the
first gate exercises the access rules but not the mapping itself; treat a pass
there as an expectation, not a guarantee, and confirm on devnet or testnet.

## Technical Details

### Four Copies Become Zero

Today an instruction can copy account data four times:

| Copy            | Direction                  |
| --------------- | -------------------------- |
| Serialization   | Runtime to virtual machine |
| CPI call edge   | Virtual machine to runtime |
| CPI return edge | Runtime to virtual machine |
| Deserialization | Virtual machine to runtime |

The validator also compares the data on the way back to find what changed.
Direct mapping points the virtual machine's memory at the account's data, so
none of these copies or comparisons are needed. Instructions that make CPIs or
touch large accounts save the most, because that is where the copies were.

### What Waits for Direct Mapping

One change waits for direct mapping:
[SIMD-0268](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0268-raise-cpi-nesting-limit.md)
raises the CPI nesting depth from 4 to 8 and specifies activation after
SIMD-0219. Its gate is inactive on every cluster. See
[Deeper CPI Nesting](/upgrades/cpi-nesting-depth).

Dynamic stack frames went the other way: they shipped first.
[SIMD-0166](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0166-dynamic-stack-frames.md)
has been live on mainnet since epoch 809 (June 2025) for sBPFv1 and later, and
it removed stack frame gaps for those versions because, in its words, they were
"incompatible with direct mapping". SIMD-0460 finishes that for sBPFv0
programs.

### Why Not Keep Both Behaviors

Direct mapping and the old copy-in, copy-out model cannot both run, because the
point of the change is that no copy exists. The old model hid out-of-bounds
reads and temporary writes by operating on a private copy. With the data mapped
in place, a stray write would change the real account. The runtime can only
protect the account by checking every access, so it fails the instruction.
