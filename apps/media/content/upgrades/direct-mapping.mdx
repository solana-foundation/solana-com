# Account Data Direct Mapping

October 2026 • Solana Foundation

Every time a Solana program runs, the validator copies each account's data into
the program's virtual machine, and copies it back out afterward. A cross-program
invocation (CPI) repeats that work in both directions. Direct mapping removes
the copies: the program reads and writes the account's data in place.

That only works if the runtime knows exactly which bytes a program touches.
Today a program can read past the end of an account, write to a read-only
account as long as it restores the original value, or reach across memory
regions, and nobody notices. Direct mapping makes the runtime check every
access, and a program that breaks the rules now fails with an instruction error.

Most programs never trigger one of these errors. This article is for the ones
that might.

- **Users:** Nothing changes.
- **Developers whose programs follow the rules:** Nothing changes. Test on
  devnet or testnet to confirm.
- **Developers whose programs read, write, or resize account data in unusual
  ways, or rely on stack layout:** Some transactions that succeed today will
  fail. Test now. See [Does This Affect Me?](#does-this-affect-me).
- **Validator operators:** Run an Agave or Firedancer release that includes both
  gates. There is nothing to configure.

## Test It Before Mainnet

Both gates are already active on devnet and testnet, so a program deployed there
runs under the new rules today. To check the status of a gate on any cluster:

```bash
solana feature status 7VgiehxNxu53KdxgLspGQY8myE6f7UokaWa4jsGcaSz --url mainnet-beta
```

While the gate is pending, the row reads like this:

```text
Feature                                      | Status   | Activation Slot | Description
7VgiehxNxu53KdxgLspGQY8myE6f7UokaWa4jsGcaSz  | inactive | NA              | SIMD-0460: Virtual Address Space Adjustments
```

`solana-test-validator` activates every feature gate its build knows about, so
the new rules are on by default locally. To compare behavior, switch the gate
off:

```bash
# All known gates are active by default, including this one
solana-test-validator

# Reproduce mainnet behavior by deactivating the first gate
solana-test-validator --deactivate-feature 7VgiehxNxu53KdxgLspGQY8myE6f7UokaWa4jsGcaSz
```

To check how a real mainnet transaction would behave, paste its signature into
[SVM Scope](https://svmscope.vercel.app/), a community tool that replays a
transaction with the feature enabled and disabled and shows both results. A
transaction that succeeds with the feature off and errors with it on points at a
program that needs a fix.

Anza also replays mainnet traffic continuously with the gate on and off and
records every transaction whose result differs, grouped by program. The list has
been shrinking as teams ship fixes, but it only covers traffic seen so far.
Programs that run rarely can still be missing, so test your own program rather
than waiting to be listed.

## Does This Affect Me?

<AudienceGroup>
<Audience title="For Users" summary="No action needed.">

Wallets, balances, fees, and confirmation times are unaffected. If an app you
use is on the list of programs that still diverge, a transaction that worked
yesterday can fail after activation. The app team needs to fix it. Your funds
are not at risk: a failed transaction changes no account state, and you pay only
the usual fee.

</Audience>

<Audience title="For Developers" summary="Most programs need nothing. If you read, write, or resize account data by hand, or use unsafe code, test on devnet now.">

Existing programs that stay inside their accounts keep working. The programs most
likely to be affected use `unsafe` code, hand-rolled account parsing, raw
pointers, custom entrypoints, or older SDK and framework versions.

| If your program                                                      | Breaking? | What you have to do                                                                                           |
| -------------------------------------------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------- |
| **Uses** safe SDK or framework code and well-formed accounts         | No        | Nothing. Run your test suite against devnet to confirm.                                                       |
| **Casts** account data to a fixed-size struct without a length check | **Yes**   | Check `data_len()` before the cast. A short account now fails with `AccountDataTooSmall`.                     |
| **Writes** to an account after closing it or assigning it away       | **Yes**   | Stop writing once the program no longer owns the account. This includes serialization in framework exit code. |
| **Writes** a read-only account, then restores the value              | **Yes**   | Remove the write. The restore no longer hides it.                                                             |
| **Resizes** accounts with the deprecated `realloc`                   | **Yes**   | Switch to `resize` and stay within the per-transaction growth budget.                                         |
| **Reads** or **writes** with one `memcpy` across two regions         | **Yes**   | Split the copy into one access per region.                                                                    |
| **Relies** on stack layout or overruns a stack frame                 | **Yes**   | Remove absolute stack addressing and out-of-bounds stack accesses.                                            |
| **Indexes, decodes, or simulates** transactions                      | No        | Nothing. Account state and results are unchanged for compliant programs.                                      |

Anchor's bounds-checked account handling avoids most of the above, but one
pattern needs attention. Anchor's exit code used to re-serialize an account after the instruction even if
the program had closed it or handed it to another program, which now fails with
`ExternalAccountDataModified`. A merged Anchor change,
[otter-sec/anchor#5011](https://github.com/otter-sec/anchor/pull/5011), skips
re-serialization when the account is no longer owned by the program. Upgrade to
an Anchor release that includes it and rebuild.

Native and Pinocchio programs that parse account bytes themselves carry the most
risk, because the bounds checks are theirs to write.

</Audience>

<Audience title="For Validator Operators" summary="Upgrade to a release that contains both gates. No configuration changes.">

Agave and Firedancer implement the change behind the two feature gates. There is
nothing to configure. Account data copies disappear from the hot path once the
second gate activates, so expect less memory traffic per instruction, not a
different outcome. The runtime still produces identical account state for every
program that follows the rules.

</Audience>
</AudienceGroup>

- Run your recent mainnet transactions through [SVM Scope](https://svmscope.vercel.app/).

## Breaking Changes in Detail

<AudienceGroup>
<Audience title="For Developers" summary="Five access patterns that used to pass now fail. Every one fails loudly with a named error.">

All of these failures are loud. The instruction returns an error, the
transaction fails, and no account state changes. A program cannot catch the
error in a CPI caller and carry on, because the failure aborts the transaction.
A failed transaction still pays the usual fee. None of these changes silently
returns wrong data.

### Breaking Change: Account Data Access Is Now Checked

Every read or write to an account's data region is validated against the
account's real length, owner, and writable flag. Before direct mapping, a bad
access went unnoticed as long as it stayed inside the reserved address space, or
as long as a write was undone before the program returned.

| The access                                       | The error                                       |
| ------------------------------------------------ | ----------------------------------------------- |
| A read past the account's current length         | `InstructionError::AccountDataTooSmall`         |
| A write to an account not flagged writable       | `InstructionError::ReadonlyDataModified`        |
| A write to an account the program does not own   | `InstructionError::ExternalAccountDataModified` |
| A write past the maximum length or growth budget | `InstructionError::InvalidRealloc`              |

Search for these exact names in transaction logs and simulation results. A typical
case: a program casts account bytes to a fixed-size struct and the account is
shorter than the struct.

The wrong-but-tempting fix is to write the original value back or to guard only
the final result. The runtime checks the write itself, so restoring the value
does not help. Remove the write.

Programs that resize with the deprecated SDK `realloc` should move to `resize`.
The old function reads from uninitialized memory before writing, which direct
mapping cannot allow.

### Breaking Change: Accesses Cannot Span Memory Regions

A single load, store, or syscall that crosses from one memory region into the
next is now an access violation. Regions include the stack, heap, input data, and
each account's data. A `memcpy` that used to work because two regions happened to
sit next to each other must be split into one access per region.

Safe Rust slices cannot cross regions, so this mainly affects `unsafe` code and
hand-written syscall calls.

### Breaking Change: Stack Frame Gaps Are Removed

[SIMD-0460](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0460-virtual-address-space-adjustments.md)
removes the unmapped gaps between stack frames for every program, including
sBPF v0 programs that still had them. The stack becomes one contiguous range at
lower addresses, and the frame bump on `call` and `callx` drops from 8 KiB to
4 KiB. The total mapped stack size does not change.

Programs that use absolute stack addresses, compute addresses across frames, or
depend on an out-of-bounds access stopping at a frame boundary can break. The
usual symptom is an access violation, and a program that was already overrunning
a frame can show slightly different compute unit consumption with the same
account state and results. If you see a small, unexplained CU change and nothing
else, check for a stack overrun.

### Breaking Change: CPI Account Pointers Must Come From the Runtime

[SIMD-0219](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0219-stricter-abi-and-runtime-constraints.md)
requires the `AccountInfo` structures a program passes to a CPI to live on the
stack or heap, and requires `key`, `owner`, `lamports`, and `data` pointers to
point at what the runtime originally serialized. A violation raises
`SyscallError::InvalidPointer`. Programs built with the standard SDKs already
comply. Programs that forge their own `AccountInfo`, or reuse one that points
somewhere else, do not.

</Audience>
</AudienceGroup>

## Why Two Feature Gates

Anza and Firedancer split the work in two to lower the risk of each step.

1. **`7VgiehxNxu53KdxgLspGQY8myE6f7UokaWa4jsGcaSz`** tightens address
   translation and memory access, and removes stack frame gaps. This is the
   gate that can break programs.
2. **`CR3dVN2Yoo95Y96kLSTaziWDAQT2MNEpiWh5cqVq2pNE`** turns on direct mapping
   itself. By then every program that passes the first gate already behaves in a
   way that maps cleanly, so this step should produce no new failures.

On devnet and testnet the two gates activated one epoch apart. If your program
passes on a cluster with the first gate active, you are covered for the second.

## Technical Details

### Four Copies Become Zero

Today an instruction copies account data four times:

| Copy            | Direction                  |
| --------------- | -------------------------- |
| Serialization   | Runtime to virtual machine |
| CPI call edge   | Virtual machine to runtime |
| CPI return edge | Runtime to virtual machine |
| Deserialization | Virtual machine to runtime |

The validator also compares the data on the way back to find what changed.
Direct mapping points the virtual machine's memory at the account's data, so
none of these copies or comparisons are needed. Every CPI benefits, and so does
every instruction with large accounts.

### What Direct Mapping Unlocks

Other changes build on direct mapping and wait for it:

- [SIMD-0268](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0268-raise-cpi-nesting-limit.md)
  raises the CPI nesting depth from 4 to 8 and specifies activation after
  SIMD-0219. See [Deeper CPI Nesting](/upgrades/cpi-nesting-depth).
- [SIMD-0166](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0166-dynamic-stack-frames.md)
  introduces dynamic stack frames, which the Agave team has tracked as depending
  on direct mapping.
- [SIMD-0339](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0339-increase-cpi-account-info-limit.md)
  raises the maximum number of account infos in a CPI from 64 to 255 and meters
  them.

### Why Not Keep Both Behaviors

Direct mapping and the old copy-in, copy-out model cannot both run, because the
point of the change is that no copy exists. The old model hid out-of-bounds
reads and temporary writes by operating on a private copy. With the data mapped
in place, a stray write would change the real account. The runtime can only
protect the account by checking every access, so it fails the instruction.

## About This Upgrade

Direct mapping removes the largest remaining copy cost in the program runtime,
and it replaces silent memory mistakes with named errors that a developer can
search for and fix. It also clears the way for deeper CPI nesting and dynamic
stack frames. Test your programs on devnet today; the only way to be caught out
on mainnet is not to have looked.
