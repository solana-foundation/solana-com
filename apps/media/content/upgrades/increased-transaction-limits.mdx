# Increased Transaction Limits

September 2026 • Solana Foundation

Solana is increasing two limits so one transaction can do more. The first is
the account lock limit. A transaction must list every account it needs to read,
change, or call. A higher limit gives the transaction more space to interact
with the network. With this change, a v1 transaction can use up to 96 accounts
instead of 64.

The second limit controls how many programs can call one another in a chain.
Solana calls this cross-program invocation, or CPI. The maximum CPI depth
increases from 4 to 8. This allows more complex behavior. It also gives
developers more confidence to build small, focused apps that work together,
because a transaction can pass through more program layers.

Together, these changes let apps combine more parts of Solana in one atomic
transaction. Users can complete a complex action as one operation instead of
approving several separate transactions. The higher limits are part of Solana's
continuous work to improve network capacity and make applications easier to
combine.

The higher account limit builds on the capabilities of the v1 transaction
format. The deeper CPI limit is separate from the transaction format and
applies to legacy, v0, and v1 transactions. Together, the changes give v1 apps
more room to include accounts and give every transaction format more room for
programs to work together. See
[Larger Transaction Sizes](/upgrades/larger-transaction-sizes) for v1 format
details and current SDK support.

The CPI depth change is tentatively planned to activate after the Agave 4.4
release, while the account lock limit change is tentatively planned to activate
after the Agave 4.5 release.

## Technical Details

### CPI Nesting Depth: 4 to 8

A cross-program invocation lets one Solana program call another program during
the same transaction. The called program can make another CPI, creating a chain
of program calls. Today that nesting stops at 4 calls.

[SIMD-0268](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0268-raise-cpi-nesting-limit.md)
raises the maximum nesting depth to 8. The change gives applications more room
to combine programs that each add a layer of abstraction. A smart wallet, for
example, may call an application that calls a router, which then calls one or
more liquidity programs. Deeper nesting allows these components to remain
modular instead of requiring developers to flatten or duplicate logic just to
stay under the runtime limit.

This is a runtime-wide execution limit. It applies to program calls made from
legacy, v0, and v1 transactions.

### V1 Account Addresses: 64 to 96

Every transaction names the accounts it reads or writes, as well as signers and
program IDs.
[SIMD-0596](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0596-increase-txv1-account-lock-limit-to-96.md)
raises the maximum number of those addresses in a v1 transaction from 64 to 96,
a 50% increase. Legacy and v0 transactions stay at their current 64-account
runtime limit.

The higher limit is useful when one atomic operation needs many accounts. An
onchain swap router, for example, can inspect or use more liquidity pools and
their supporting programs in one transaction, opening the door to more complex
routes and potentially better execution prices.

### Independent, Feature-Gated Rollout

The two limits address different parts of transaction execution and can roll
out independently. SIMD-0268 changes how deeply programs can call one another
for every transaction format. SIMD-0596 changes how many accounts a v1
transaction can name; legacy and v0 transactions stay at 64 accounts. Neither
change requires existing applications to migrate.

Applications must opt into the additional capacity. Transactions that stay
within today's limits continue to behave as before, while applications that
need deeper calls or more accounts can use the new headroom after the relevant
feature gate activates.

## About This Upgrade

Solana's application ecosystem is increasingly composable: smart wallets,
routers, markets, token programs, and other protocols are often combined in one
operation. CPI depth and account count determine how many of those components a
single atomic transaction can bring together.

Raising both limits gives developers more flexibility without changing the
behavior of existing transactions or raising the resource limits for legacy
and v0 formats. The changes preserve Solana's atomic execution model while
allowing richer transactions to fit inside it.
