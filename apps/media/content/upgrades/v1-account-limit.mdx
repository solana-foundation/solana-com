# More Accounts per Transaction

September 2026 • Solana Foundation

Every transaction names the accounts it reads or writes, plus its signers and
program IDs. That list is capped at 64 entries today. For v1 transactions the
cap rises to 96.

The higher limit matters when one atomic operation touches many accounts. An
onchain swap router can inspect or use more liquidity pools and their supporting
programs in a single transaction, which opens up more complex routes and
potentially better execution prices.

The change builds on the v1 transaction format. Legacy and v0 transactions stay
at 64 accounts. A separate change raises how deeply programs can call each
other; see [Deeper CPI Nesting](/upgrades/cpi-nesting-depth).

## Technical Details

### V1 Account Addresses: 64 to 96

[SIMD-0596](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0596-increase-txv1-account-lock-limit-to-96.md)
raises the maximum number of addresses in a v1 transaction from 64 to 96, a 50%
increase. The limit counts every address in the transaction: writable and
read-only accounts, signers, and program IDs.

Legacy and v0 transactions keep their current 64-account runtime limit. The
additional room is only available to applications that build v1 transactions,
which also gives them the 4096-byte size limit. See
[Larger Transaction Sizes](/upgrades/larger-transaction-sizes) for the v1
format and current SDK support.

### Opt-In Rollout

Transactions that stay within 64 accounts behave exactly as before. Nothing
needs to migrate. Applications that want the extra headroom build v1
transactions with more accounts once the feature gate activates. Until then,
transactions above 64 accounts are rejected as they are today.

## About This Upgrade

Account count determines how many components one atomic transaction can bring
together: pools, programs, signers, and the accounts they touch. Raising the v1
limit gives routers, batchers, and multi-step protocols more room without
changing anything for legacy and v0 transactions. The atomic execution model
stays the same; larger operations fit inside it.
