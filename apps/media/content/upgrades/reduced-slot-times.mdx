# Reduced Slot Times

**Updated August 2026** • Solana Foundation

Solana is reducing its slot times from 400ms to 200ms. This change was first
discussed in
[SIMD Discussion 469](https://github.com/solana-foundation/solana-improvement-documents/discussions/469)
and formally proposed and approved in
[SIMD-0525](https://github.com/solana-foundation/solana-improvement-documents/pull/525).
This change will make the protocol more competitive in terms of latency. It takes
advantage of the performance improvements made to Solana validator clients
especially in Turbine, and Replay.

This also doubles as a censorship resistance measure since it narrows the time a
leader has a monopoly over block building. Together with the separately proposed
[reduction of consecutive leader slots](https://github.com/solana-foundation/solana-improvement-documents/pull/498),
this improves fairness for validators and users by limiting individual leader control windows.

The first two 50ms steps activated on Mainnet on August 19 and August 26, 2026,
bringing its current target from 400ms to 300ms. The remaining steps each have
their own feature gate and turn on one at a time, in a later epoch than the one
before it, so the network can pause if block skip rates climb. Anza's
[feature gate tracker](https://github.com/anza-xyz/agave/wiki/Feature-Gate-Tracker-Schedule)
lists the current rollout status.

## Technical Details

### Slot Duration

The SDK's default slot duration is the default number of milliseconds per tick
(based on Solana's [proof of history](https://report.helius.dev/#chapter5))
multiplied by the default number of ticks per slot. Runtime feature gates can
change the network target without changing that SDK default. Mainnet currently
targets 300ms after the first two reductions; measured slot duration varies with
network conditions.

The decrease to 200ms will not change the ticks per slot, the leader span of
four slots, and the slots per epoch.

This time gives ample chance for the other validators to replay the transactions
within the block and vote on whether a block is valid and should be included in
the chain.

Concurrently, the next leader is receiving transactions via Gulf Stream and has
to complete its blocks within the same timeframe.

### Phased implementation

The network created four feature gates in successive epochs for this change. It
will reduce the slot times in 50ms decrements:

1. 400ms -> 350ms (active on Mainnet August 19, 2026)
2. 350ms -> 300ms (active on Mainnet August 26, 2026)
3. 300ms -> 250ms
4. 250ms -> 200ms

The agreement in the
[validator discussion](https://youtu.be/GLV4hIX46S4?list=PLilwLeBwGuK78yjGBZwYhTf7rao0t13Zw)
is that the network will not move to the next reduction if the block skip rates
are too high.

## About This Upgrade

Decreasing slot times allows the network to be more competitive to other
blockchain protocols. This change also sets a precedent for future latency
improvements.

Users will experience faster confirmation times on their transactions. Market
makers will be able to quote tighter spreads.

Validators will enjoy shorter epochs, which means they are rewarded faster for
adopting the performance improvements on Mainnet.
