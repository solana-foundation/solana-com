# SHA-512 Syscall

Q4 2026 • Solana Foundation

SHA-512 is already inside every Solana validator. It is a core primitive of
Ed25519 signature verification, so both Agave and Firedancer link an
implementation of it as an internal dependency. What has been missing is a way
for an onchain program to call it.
[SIMD-0512](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0512-sha512-syscall.md)
adds `sol_sha512`, a syscall with the same interface as `sol_sha256`, producing
a 64-byte digest.

Until now a program that needed SHA-512 had to implement it in sBPF. A single
hash of a short message costs thousands of compute units that way. Through the
syscall it costs fewer than 100 — the work moves into the validator, where it
runs as optimized native code rather than as interpreted program bytecode.

## Technical Details

### Syscall Signature

`sol_sha512` follows the interface already used by `sol_sha256`,
`sol_keccak256`, and `sol_blake3`. It takes an array of byte slices and hashes
them as if they were one contiguous input, writing the 64-byte digest to the
caller's `result` pointer.

The syscall aborts the virtual machine if:

- any byte in the slice array itself is unreadable,
- any byte in any of the referenced slices is unreadable,
- any of the 64 bytes at `result` is unwritable, or
- the number of slices exceeds the configured maximum, currently 20,000 per
  `SVMTransactionExecutionBudget`.

These are aborts, not recoverable errors. There is no error return value to
check.

### Compute Cost

Compute metering follows the same model and the same parameters as
`sol_sha256`: a base cost plus a per-byte cost over the input. SHA-512 processes
1024-bit blocks rather than SHA-256's 512-bit blocks, so for the same input it
performs fewer compression rounds on wider words.

The comparison that matters is not against `sol_sha256` but against the status
quo. A software SHA-512 in sBPF costs thousands of CUs for a short message. The
syscall costs under 100.

### What It Unblocks

The immediate case is Ed25519-adjacent verification logic. Ed25519 uses SHA-512
internally for key expansion and for the challenge hash, so a program doing
anything with Ed25519 structure — verifying a variant scheme, deriving from a
signature, checking a hash chain built on the same primitive — previously had to
carry its own implementation and pay for it on every call.

The broader case is any protocol that specifies SHA-512, which until now meant
either eating the sBPF cost or choosing a different hash for Solana. Neither is
a good option when the function is already sitting in the validator binary.

### Why Not Keep It in sBPF

Programs can implement SHA-512 today; nothing prevents it. The argument for the
syscall is that the cost is paid for no reason. Every validator already has an
audited, optimized SHA-512 linked in, and charging programs thousands of compute
units to recompute what the host could do natively wastes block capacity that
other transactions could use.

## About This Upgrade

This is the smallest kind of protocol change: no new behavior, no new trust
assumption, no migration. It is additive and gated, existing syscalls are
untouched, and a program that never calls `sol_sha512` cannot tell the
difference.

The security surface is the same as the other hash syscalls — the same input
validation, the same compute metering — and SHA-512 itself is a standardized,
well-studied function specified in FIPS 180-4.
