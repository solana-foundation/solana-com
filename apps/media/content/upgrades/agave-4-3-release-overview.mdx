# Agave 4.3 Release Overview

September 2026 • Solana Foundation

Agave 4.3 is the release that carries Alpenglow. Anza recommended it for general
mainnet adoption on **September 21, 2026**, and feature activation begins
**September 28**, per the
[v4.3 release schedule](https://github.com/anza-xyz/agave/wiki/v4.3-Release-Schedule).
Testnet has been running 4.3 since August 17 and devnet since August 24.

Two things ship here, and they are on very different timelines. The
[relax fee-payer constraint](/upgrades/relax-fee-payer-constraint) change has a
feature gate in the release and activates on the ordinary schedule.
[Alpenglow](/upgrades/alpenglow) is in the binary — its consensus code, its vote
path, and its `bank_id` plumbing — but switching a live cluster from TowerBFT to
Alpenglow is not a normal feature activation. It is already live on testnet
and devnet, and it activates on mainnet with
[Agave 4.4](/upgrades/agave-4-4-release-overview), not 4.3.

## Technical Details

### Relax Fee-Payer Constraint

[SIMD-0290](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0290-relax-fee-payer-constraint.md)
changes what happens when a blockhash transaction names a fee-payer that cannot
pay. Today that transaction invalidates the entire block containing it. After
activation the transaction is simply not executed: it may sit in the block, it
has no effect on account state, and the block around it stays valid.

The motivation is asynchronous execution. Deciding whether a block is valid
currently means executing enough of it to learn whether each fee-payer had the
lamports, which forces validation and execution to stay coupled. Removing the
constraint decouples them by one step.

For anyone reading blocks, this is the change that matters in 4.3: **a
transaction appearing in a block no longer means it ran.** Full detail, including
what a valid fee-payer now has to look like, is in
[Relax Fee-Payer Constraint](/upgrades/relax-fee-payer-constraint).

Feature gate: `FEEXbxUuKobtrt1qNK5pjtzbPQhsppBTrNNG74xu4mai`.

### Alpenglow: Ships in 4.3, Activates in 4.4

Agave 4.3 contains Alpenglow's first phase, Votor — direct validator votes,
aggregate BLS certificates, and a target finality around 150ms in place of
TowerBFT's 12.8 seconds. The feature gate is
`A1pengvuM6JEcyNuTnMqepBKhwHE3N6PmUrdATGawhJS`.

Shipping the code and switching mainnet are separate events, and only the first
has happened. The consensus migration is rehearsed on the
[Alpenglow community cluster](/upgrades/alpenglow#alpenglow-community-cluster),
which is taken down and restarted deliberately to test Alpenglow. Testnet and
devnet have since activated Alpenglow with the 4.3 release: testnet on
September 24, 2026 and devnet on September 25. Mainnet activates with
[Agave 4.4](/upgrades/agave-4-4-release-overview).

Two prerequisites already activated on mainnet under Agave 4.1: BLS pubkey
management (SIMD-0387) on July 8, 2026, and the
[Validator Admission Ticket](/upgrades/bls-pubkey-vat) (SIMD-0357) on July 22.
Operators without a registered BLS pubkey are already outside the admitted
validator set.

If you stream block data, the useful thing about 4.3 is that it adds `bank_id`
to Geyser one release before fast leader handover makes multiple banks per slot
common. That ordering is deliberate: it is the window to adopt the field while
the case it guards against is still rare. See
[Alpenglow](/upgrades/alpenglow#breaking-change-one-slot-can-contain-more-than-one-bank)
for the migration.

### What Is Not in 4.3

The mainnet activation of Alpenglow, and the runtime and program-facing work —
the syscalls, the virtual address space changes, direct mapping, the loader
change, and block revenue sharing — are in
[Agave 4.4](/upgrades/agave-4-4-release-overview), not here.

## About This Upgrade

Agave 4.3 is a small release in terms of feature activations, but it carries
important changes to the code base. The only feature activating
is the fee-payer relaxation, which is narrow in what it
changes. Any pipeline that treats block inclusion
as proof of execution needs to change their logic.
