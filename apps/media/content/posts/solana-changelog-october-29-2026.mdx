## Ecosystem work

SIMDs

- A discussion was started to add a new syscall for [optimized arithmetic operations](https://github.com/solana-foundation/solana-improvement-documents/discussions/708), especially vectorized ones. WTM - Vector arithmetic is done with an operation on the virtual machine called single-instruction, multiple data (SIMD, unironically) operations. This is a generally faster way of batching your arithmetic at once as opposed to doing a series of operations serially, that is, one at a time. This proposal seeks to create a new system call that will standardize these operations on Solana with the right static CUs, etc.

Validator clients (Agave, Firedancer, Mithril)

- A [new crate](https://github.com/anza-xyz/agave/pull/16235) for a [generalized worker pool pattern](https://github.com/anza-xyz/agave/tree/master/worker-pool) was created in Agave and set for implementation across the validator services including in the [ledger](https://github.com/anza-xyz/agave/pull/16416), [retransmit](https://github.com/anza-xyz/agave/pull/16417), and [shred sigverify](https://github.com/anza-xyz/agave/pull/16418) WTM - We’ve seen this pattern in previous Changelog issues where a Rayon thread pool is replaced with a custom thread pool implementation and a job queue via a work stealing pattern. This improves performance and has been seen to do repeated work all over the Agave stack, thus the need for a crate. It is possible then that this work will look similar to the wincode crate that Anza has already created to replace bincode.

- [Solana CLI will enable building transactions through the CLI](https://github.com/anza-xyz/agave/pull/16448), enabling V1 Transactions by default WTM - Solana CLI will soon have its durable nonce replacement program and CLI. This feature enables users to interact with the new nonce program via the CLI as well as other use cases. The new abstraction allows message payloads to be converted to actual transactions with a future where the Solana CLI will send it.

- Agave will publish [slot events](https://github.com/anza-xyz/agave/pull/16413) in its events service WTM - Slot events allow Agave to monitor the performance of the validator as it produces a block or participates in consensus. By monitoring events within the slot, validators are able to inspect bottlenecks and more closely understand other issues that might occur.

- Agave is improving its program upgrade runtime workflow to [make loading the program bytes faster during extension](https://github.com/anza-xyz/agave/pull/16280), and to [make shrinking the program bytes space faster](https://github.com/anza-xyz/agave/pull/16283) WTM - Solana will soon roll out the LoaderV3 instructions that will allow easier program upgrades. This includes ensuring that data and rent are allocated dynamically as the program size grows or shrinks. While the CLI already does some of this for you, it would be nice if this is done for you by the runtime. Both these changes are in support of that goal.

- Agave will [deprecate dalek](https://github.com/anza-xyz/agave/pull/16465) in favor of its own in-house solana-ed25519 crate WTM - This new crate was created to improve performance and minimize the number of CUs. Swapping one for the other will improve performance across the network since transaction signing, signature verification, etc are performed with the dalek ed25519 crate.

- Agave will implement its custom [validator configuration crate](https://github.com/anza-xyz/agave/pull/16334) WTM - This will not only allow custom configuration by validators, but will also allow operators to finetune their parameters to improve performance. This configuration file crate was envisioned when the flags for tuning XDP were found to be a hairer developer experience than anticipated.

- [Installing cargo-build-sbf has been decoupled](https://github.com/anza-xyz/agave/pull/15415) from the Solana CLI installation WTM - cargo-build-sbf is the standard binary for building Solana programs on any framework. It is shipped with the Solana CLI installation despite not being needed to run CLI commands. Removing this allows frameworks and developers to remove one dependency they will no longer be using in order to build their programs.

- Firedancer improved its memory usage by [judiciously allocating where the Sysvar Cache should go](https://github.com/firedancer-io/firedancer/pull/12581) WTM - In order to run Solana programs that require the Sysvars like the Clock, Instruction, Epoch, etc Sysvars, quick access to them to run them on the validator is needed. This change optimizes where the Sysvar Caches are loaded in memory, especially removing redundant allocations.

- Firedancer will support [VLAN networking](https://github.com/firedancer-io/firedancer/pull/12580) WTM - Firedancer increases its scope from just supporting AF\_XDP, Native mlx5, and GRE, to supporting VLAN interfaces for ingress and egress of network traffic. This allows for more network interface card (NIC) hardware to work on Firedancer.

- Mithril improved its [replay performance](https://github.com/Overclock-Validator/mithril/pull/335) WTM - Mithril made some changes with how it implements Replay, including prioritizing transactions by banking fork length and improvements to encoding/decoding. The pull request includes benchmarks against the current Agave implementation

RPC 2.0

- Superbank’s solparq crate will [support Alpenglow footers and V1 transactions](https://github.com/solana-rpc/superbank/pull/118) WTM - solparq is the interface for storing Solana account data for the Superbank service as parquet files. These are standard files for data storage, especially larger data warehouses, of which Superbank hopes to be an implementation of on the RPC layer. Supporting Alpenglow footers and V1 transactions keep solparq in line with where the network is today in terms of transaction and block formats.

- Shipstern [added Triton One’s Harmonic Preconfirmed Transactions data feed](https://github.com/solana-rpc/shipstern/pull/359) as a source WTM - Preconfirmed transactions were served as a product by both Jito’s BAM service and Termporal’s Harmonic service. This change allows Shipstern to use the latter’s service in order to push transactions for indexing.

Solana language clients (Web3.js, Solana Kit, Kit plugins, Solana SDK, Codama, Solana Go)

- Web3js will [wrap Solana Kit’s getTransactionsForAddress implementation](https://github.com/solana-foundation/solana-web3.js/pull/4002) WTM - Web3js has just been relaunched to be compatible with the previous v1.xx implementation. Now, v3 can focus on adding features that would be useful with the current tooling. One such change is a new RPC method popularized by Helius called getTransactionsForAddress. Previously, we would have had to use getSignaturesForAddress and each signature would be passed to a getTransaction query, which is very expensive. This change implements the new RPC method that is a better developer experience and now becoming a standard RPC API.

Solana Program Library (SPL) and Core BPF

- Several crates were impacted by RUST-SEC Advisories the past week. The impacted crates are: zstd-sys, pulldown-cmark, rustls-webpki, webpki-roots. Patches to the affected Solana Program clients were made and they should arrive in a future release

Testing frameworks (mollusk, litesvm, surfpool)

- Surfpool is working to [make agent-friendly environments possible](https://github.com/solana-foundation/surfpool/pull/902) in its testing environment WTM - Agents do most of the development today. In order to support building apps with agents on Solana, Surfpool is creating a sandbox environment to make this testing safe. Agents have been known to breach their security defenses and keeping them restricted to their sandbox environments is a known problem. This change is a step in that direction.
