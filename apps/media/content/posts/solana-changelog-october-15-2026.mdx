SIMDs

- [Specifying compute unit costs for syscalls on the Secp256r1 curve](https://github.com/solana-foundation/solana-improvement-documents/pull/695) were proposed WTM - Solana ensures it accounts for the amount of operations validators are performing via Compute Units (CUs). This allows the protocol to set limits on how much compute a block can have, set incentives by weighting how long, how much memory they use, etc. These units are assigned mostly arbitrarily (System Program instructions cost 10 CUs each). This change will specify in detail how much each operation on the cryptographic curve would cost.

- A discussion to [increase the CU limits to their previous levels following reduced slot times](https://github.com/solana-foundation/solana-improvement-documents/discussions/693) was proposed WTM - CU limits decreased per slot again when slot times were reduced. The actual allowed CU throughput per unit time onchain did not change, but in order to implement slot time reduction the limits had to be reduced. This proposal is suggesting that we increase those limits again since the slot time reduction to 200ms has reached Mainnet.

- [Post-Alpenglow improvements to the consensus implementation](https://github.com/solana-foundation/solana-improvement-documents/discussions/692) are being discussed WTM - Alpenglow will be activated on Mainnet soon. And along the way, core developers have found ways to further improve its implementation. Among the proposed changes is preparation work for a new multiple-proposers algorithm called minCP.

Validator clients (Agave, Firedancer, Mithril)

- Agave is working on [an events system](https://github.com/anza-xyz/agave/pull/16054) WTM - Geyser is the current way to stream blockchain events to users on Solana. But these are protocol-specific events, not Agave specific ones. Agave is building its own custom one. There are benefits to this, namely the ability to create custom metrics and more fine-tuned performance measurement.

- Agave is planning an in-protocol measure to [limit transaction execution time](https://github.com/anza-xyz/agave/pull/16037) WTM - Transactions don’t have a well-defined execution time limit on Solana. This draft proposal explores how that might be implemented. Setting limits allows the runtime to abort any transactions earlier so that it could be freed up to process others that may be waiting. This change may possibly require a SIMD depending on how the final implementation might turn out.

- Agave is [reducing the Sigverify shred batches from 1024 to 128](https://github.com/anza-xyz/agave/pull/15994) WTM - Memory has to be allocated for Sigverify batches to be created and processed. Decreasing the number of shreds per batch means sigverify can work with less at a given time, and can move on to the next batch faster. It also means less memory is used.

- Firedancer had made [memory improvements](https://github.com/firedancer-io/firedancer/pull/12239) to its implementation of Votor WTM - Votor’s memory can be expensive because it relies on offchain messaging in order to pass votes. This can be chatty and require a ton of memory allocations for vote traffic and connection handling. This implementation is a more judicious use of resources on that front.

RPC 2.0

- Shipstern will [use the block footers to take note of the Alpenglow vote certificates](https://github.com/solana-rpc/shipstern/pull/354) WTM - Block footers contain the Alpenglow vote certificates and quorum events are worth parsing. This change takes advantage of a subscription the block footer to parse the votes onchain.

Solana program frameworks (Anchor, Pinocchio, Steel, Quasar)

- Anchor is [working to have its AVM CLI use the latest cargo-build-sbf](https://github.com/otter-sec/anchor/pull/5178) installed on the user’s machine WTM - Previous versions of the AVM CLI use older versions of cargo-build-sbf. Upcoming changes enforcing deployments of only sBPFv3 will mean that the older versions will be rejected, which aren’t supported by cargo-build-sbf. This change forces the newest version so that it compiles Anchor programs to v3 by default and thus can deploy onchain successfully.

- Anchor is [exploring using sbpf-linker and upstream BPF compilers](https://github.com/otter-sec/anchor/pull/5162) under the hood WTM - This change will favor using an upstream BPF compiler instead of the custom toolchain that is commonly shipped by Solana program frameworks. This simplifies the dev tooling stack and will mean a simpler way to reason about our dependencies.

Testing frameworks (mollusk, litesvm, surfpool)

- Surfpool is working to allow users to [take a snapshot of account state](https://github.com/solana-foundation/surfpool/pull/857) while using their scenarios feature WTM - This feature would allow users to inspect custom account state changes given a scenario and run tests that way. It allows for better scenario planning and informs program development in a more proactive way.
