**Feature gates reduced mainnet slot times from 400ms to 350ms, while Testnet moved from 250ms to 200ms.** The week also brought releases across validator clients and developer tooling, alongside new work on transaction processing, program caching, and validator repair.

## Network feature activations

Recent feature gate activations adjusted slot times across clusters and upgraded the BPF Stake Program on Testnet.

- [Testnet reduced slot times from 250ms to 200ms](https://explorer.solana.com/address/iBRLjhJnkmDZgNoZRDMW11d8ZV7HvsL3vAyRjZB5npW?cluster=testnet).
- [The BPF Stake Program upgraded to v5.1.0 on Testnet](https://explorer.solana.com/address/iBRLL3k18HST852F1Mf3Lv83waTNQmmqvKDxvYGwQFL?cluster=testnet).
- [Devnet reduced slot times from 300ms to 250ms](https://explorer.solana.com/address/iBRLL3k18HST852F1Mf3Lv83waTNQmmqvKDxvYGwQFL?cluster=devnet).

## Proposals and validator client work

New Solana Improvement Documents (SIMDs) proposals address nonce transaction program IDs and inactive stake data. Agave and Mithril also advanced work on validator performance, transaction handling, and repair.

### SIMDs

- A [new SIMD proposal](https://github.com/solana-foundation/solana-improvement-documents/pull/602) would prevent nonce transactions from using their own nonce account addresses as program IDs. Every transaction instruction must specify a program ID, avoiding the reflexive case where an instruction stored in a nonce account refers to that account as its own program ID.
- Another [proposed SIMD](https://github.com/solana-foundation/solana-improvement-documents/pull/599) would remove inactive stakes from the runtime stakes cache. The proposal aims to avoid storing stake data that is not useful for transaction processing while ensuring the change does not negatively affect consensus through account stake lattice hashing.

### Validator clients

- Agave is [exploring dedicated worker threads for shred signature verification](https://github.com/anza-xyz/agave/pull/14641), replacing a Rayon implementation whose thread pool does not offer the flexibility needed to adjust compute resources with load.
- Agave is [making runtime account loading more customizable](https://github.com/anza-xyz/agave/pull/14540) from Accounts DB, allowing validator services to load account data based on specified conditions such as account ownership or rent.
- Agave is [working to prevent slot rolling](https://github.com/anza-xyz/agave/pull/14739), where transactions not processed in one slot are processed in another. The change schedules block processing for a specific slot to support cost tracking and compute-unit limits per slot.
- Agave is [considering a Gossip refactor](https://github.com/anza-xyz/agave/pull/14742). The draft explores a single event loop with worker threads for the validator communication service, which shares information including stake and network addresses.
- Agave is [requiring a program deployment slot when invalidating the program cache](https://github.com/anza-xyz/agave/pull/14690), enabling finer-grained control over loading program buffers and more predictable cache behavior.
- Agave’s TPU is [sanitizing transactions during ingress before signature verification](https://github.com/anza-xyz/agave/pull/14736). The change checks simpler invalidity conditions, including instruction and account-lock limits, before performing the more expensive signature calculation.
- Mithril is [opening itself to repair requests from other validators](https://github.com/Overclock-Validator/mithril/pull/264), allowing it to send missing shreds to validators that do not have a complete block.

## Language clients and programs

Language clients are preparing for V1 transactions, and the Ed25519 Programmatic Signer repository added an executor implementation.

- [Web3.js](https://github.com/solana-foundation/solana-web3.js/pull/3861) and [Solana Go](https://github.com/solana-foundation/solana-go/pull/481) are adding support for V1 transactions. Solana Kit had previous progress on the same transaction schema format.
- The Ed25519 Programmatic Signer Program [added an executor program implementation](https://github.com/solana-program/ed25519-programmatic-signer/pull/15). The exploratory repository includes a signer program, which verifies signatures and promotes PDAs as signers, and a nonce program for creating and modifying one-time-use nonce accounts; the executor advances and executes the nonce.
