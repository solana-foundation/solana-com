## Solana Improvement Documents

Contributors advanced several Solana Improvement Documents (SIMDs), covering inflation, validator stake data, LoaderV3 behavior, and program deployment behavior.

- Contributors merged the [proposal to double disinflation](https://github.com/solana-foundation/solana-improvement-documents/pull/550). Disinflation is the rate at which Solana decreases the rate by which it mints more SOL via validator and staking rewards; doubling the disinflation rate would make Solana reach its terminal inflation rate of 1.5% sooner.
- Contributors proposed [creating a Sysvar for epoch stakes](https://github.com/solana-foundation/solana-improvement-documents/pull/586). Validator stake values during an epoch represent how much of the leader schedule a validator occupies, its share of SOL rewards, and the weight of its voting power in Solana governance; the proposed account would surface these values in the Solana runtime.
- Contributors opened a discussion to [unblock specific instructions from LoaderV3 from being called by other programs or itself](https://github.com/solana-foundation/solana-improvement-documents/discussions/588). The discussion would unlock several restrictions made in SIMD-0219 and proposes a check between the program ID and the account itself, enabling use cases such as programs that change other programs that deploy other programs, along with other program administration needs.
- Contributors opened a discussion on [allowing programs to work within the slot they were modified](https://github.com/solana-foundation/solana-improvement-documents/discussions/589). Programs are disabled by default during the slot in which they are deployed; the discussion argues that this creates downtime for a program during the slot it changes, which conflicts with standard deployment practices that aim to avoid downtime for stateless software.

## Validator client work

Agave, Firedancer, and Mithril contributors worked on consensus limits, replay verification, dependency management, transaction parsing, account hashing, offline replay, and signature verification.

- Anza proposed [tightening Alpenglow block limits](https://github.com/anza-xyz/agave/pull/14122). These limits restrict the number of blocks a validator can hold at any given time while participating in consensus, and a new Alpenglow paper with updated limit thresholds will be released soon.
- Agave contributors created [a custom pool implementation for asynchronous transaction replay verification](https://github.com/anza-xyz/agave/pull/14128). The change moves the implementation from Rayon to a custom queue and thread pool built for the use case, and is intended to improve transaction replay performance.
- Agave contributors moved to [use an Anza fork of the rust-rocksdb interface](https://github.com/anza-xyz/agave/pull/14008). The fork gives Anza more control to slim down, customize, and add features to the dependency, including an [in-house rust-rocksdb change to minimize memory allocations](https://github.com/anza-xyz/rust-rocksdb/pull/1).
- Agave contributors began [preparations to parallelize parsing transactions](https://github.com/anza-xyz/agave/pull/14079) before loading them for ordering and execution. The change prepares Agave to validate incoming transactions in parallel before they are queued in the Banking Stage, instead of tightly coupling storage reservation, transaction data copying, and parsing on one thread.
- Agave contributors improved [account hashing performance on TPU and TVU](https://github.com/anza-xyz/agave/pull/14073). Account hashing occurs before account state updates in memory, both for leaders building blocks and non-leaders validating blocks for execution and voting.
- Firedancer contributors started building an [offline replay service](https://github.com/firedancer-io/firedancer/pull/10574). The service will let Firedancer test correctness between Agave and Firedancer so consensus stays tied between the two implementations, alongside [Agave conformance work](https://github.com/anza-xyz/agave/issues/12378).
- Mithril contributors improved [ed25519 signature verification](https://github.com/Overclock-Validator/mithril/pull/258). ed25519 is Solana’s chosen signature scheme, and all transactions have to be verified with it.

## Developer tooling and frameworks

Language clients, program frameworks, and testing frameworks also saw updates this week.

- The Solana Rust SDK added support for more cryptography primitives as syscalls through two pull requests: [keccak_p1600 syscall support](https://github.com/anza-xyz/solana-sdk/pull/838) and [big mod exp syscall support](https://github.com/anza-xyz/solana-sdk/pull/839). These syscalls support several cryptography operations on Solana and also require support across validator client implementations and related tooling.
- Anchor contributors worked to [make automatic updates safer](https://github.com/otter-sec/anchor/pull/4853). Because the `avm` and `anchor` CLI commands are critical infrastructure for many users, the change installs stable `avm` and `anchor` commands by default, with an opt-in flag for nightly updates.
- LiteSVM added support for [configuring epoch stake numbers](https://github.com/LiteSVM/litesvm/pull/383) within its testing harness. With upcoming governance votes and economics changes on Solana, the addition supports simulations of how stake values change with every epoch.
