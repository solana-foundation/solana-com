## Ecosystem work

### SIMDs

- A discussion has started about [cutting vote costs in half](https://github.com/solana-foundation/solana-improvement-documents/discussions/730)
  - WTM - The Vote Admission Ticket (VAT) is the amount of SOL paid to vote for a transaction. Recent changes to the Solana Foundation Delegation Program (SFDP) include a lower ceiling for exiting the program. This proposal would make participating in consensus less costly for validators that are starting out.

- New proposals would [remove durable nonces](https://github.com/solana-foundation/solana-improvement-documents/pull/723) and [disable their ability to pay transaction fees](https://github.com/solana-foundation/solana-improvement-documents/discussions/726)
  - WTM - Durable nonces let users store instructions onchain before executing them in a transaction. They have introduced security, runtime, and developer experience risks. These proposals begin the process of removing them from the protocol.

### Validator clients (Agave, Firedancer, Mithril)

- Agave proposed [showing a vote account’s current commission rate](https://github.com/anza-xyz/agave/pull/16897) in RPC responses
  - WTM - The `getVoteAccounts` RPC method returns stake information and the onchain identity for each validator. These values typically reset each epoch when stake and rewards are recalculated. If a validator changes its commission rate during an epoch, the method currently returns the rate for the next epoch. This change would let RPC callers retrieve the current rate.

- Agave proposed a new [`getAgBlockFooterCert`](https://github.com/anza-xyz/agave/pull/16892) RPC method
  - WTM - With Alpenglow, votes are recorded in block footers instead of onchain transactions. Non-validator consumers can access this data only through RPC methods. This API would let clients retrieve the vote data in Alpenglow block footers.

- Solana CLI implemented [more efficient writes of program data onchain](https://github.com/anza-xyz/agave/pull/16796)
  - WTM - Writing program data to buffer accounts is part of deploying a program onchain. The previous implementation did not pack as many bytes as possible into each account-data write. This change reimplements how Solana CLI calls BPF Loader V3 instructions, reducing the number of instructions needed to write program data.

- Mithril is improving its [runtime and replay implementations](https://github.com/Overclock-Validator/mithril/pull/352) and [interoperability with Harmonic](https://github.com/Overclock-Validator/mithril/pull/351)
  - WTM - A [discussion on X](https://x.com/fd_ripatel/status/2120447372606255111) identified jitter in Mithril’s Replay implementation. Replay runs transactions against the current state to determine whether a block is valid and can be voted on. These changes optimize the runtime and replay services and update how Mithril interoperates with Harmonic as a scheduler.

### Solana language clients (Web3.js, Solana Kit, Kit plugins, Solana SDK, Codama, Solana Go)

- Web3.js will [return `getTransaction` results with additional encoding options](https://github.com/solana-foundation/solana-web3.js/pull/4050)
  - WTM - Helius offers a more human-readable encoding of transaction RPC responses through enhanced parsing. This change lets Web3.js return the same encoding natively.

- Solana Go is improving [transaction confirmation handling](https://github.com/solana-foundation/solana-go/pull/526) and [transaction introspection](https://github.com/solana-foundation/solana-go/pull/523)
  - WTM - Transaction confirmation handling controls status checks and retry behavior for submitted transactions. This change stops waiting when a transaction expires so the application can continue other work. A new crate also adds transaction introspection, allowing applications to inspect transaction data after a transaction succeeds.

### Testing frameworks (Mollusk, LiteSVM, Surfpool)

- Surfpool will [show the error message for custom program errors](https://github.com/solana-foundation/surfpool/pull/950) when running a transaction
  - WTM - Solana programs often define custom errors for behavior not covered by software libraries. These errors usually appear as hexadecimal integers such as `0x3`. This change surfaces the message that corresponds to the error code so developers do not need to look it up.
